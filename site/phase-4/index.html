The speeds on these pages are measured on battery. A clean sweep of twelve core sets, run twice, is in; it corrected several of the first measurements, and the pages say where.

Phase 4 — threads

Phase 3 made one core fast. Phase 4 spreads each matrix product across several cores, using threads: streams of work that the operating system runs on separate cores. The hard part is not the arithmetic. Decode hands out a couple of hundred small jobs per token, and each job ends only when its slowest thread does. The first threaded build gained almost nothing beyond two cores. Fixing that taught most of what this phase is about.

Models used here

Most speeds on these pages come from Q4_0 models, whose weights are stored in 4 bits (32 weights in 18 bytes instead of 128), and the quantized kernels first turn the input into Q8_0, an 8-bit format. Those formats are taught on Block quantization in Phase 6. Here they only matter because fewer bytes per weight make each job shorter.

How do you share the work without waiting?

Each matrix product has to be split across threads. The split must avoid three costs: starting threads, one slow thread holding up the rest, and a change in the result. Four ideas handle them:

  • Keep one thread per core alive for the whole run, and hand it work by changing a counter it is watching. Starting threads or waking them through the kernel costs more than a job is worth, so doing it per job loses time.
  • Split each matrix product by rows, so every row is still summed by one thread in the same order and the result does not change.
  • Hand the rows out in small blocks, so faster cores take more and nobody waits long at the end.
  • Put the thread that does the serial work on the fastest core.

Then measure which cores are worth using: on this phone, speed stops growing at about six cores, and the last two add nothing measurable.

Takeaway: keep threads alive, split by rows, and hand out small blocks, or the slowest thread sets the pace.

Which page should I read first?

Four pages, in this order. The first explains the cost of a hand-out and how the pool pays less; the rest cover how work is split, how threads wait, and which cores to use.

  1. Threads that stay: how many jobs a token hands out, what a hand-out costs three ways, and how the pool does it with two counters.
  2. Splitting the work: rows, not pieces of rows; why equal shares failed; blocks from a shared counter; attention by head.
  3. Waiting: spin, then park: the trade between reacting fast and leaving the core free, the lost wake-up, and false sharing.
  4. Choosing cores: prime and performance cores, the caller on the fastest core, and what each core set measured.

Takeaway: read the pool page first, since the later pages build on the counters it explains.

What is still open?

Four things the sweep did not settle. Each one is a question for a later run, not a result.

  • A steadier sweep: the phone throttled during the Qwen and five-minute runs (clock caps fell to 1.6–2.0 GHz), and some runs started with another app in the foreground. A repeat on a cooler phone would settle the energy comparison and the 6–7 against 2–7 gap on Qwen.
  • Why 0–7 swings so much: with blocks it ran from 237 to 346 tokens per second between runs (Splitting the work).
  • Where the rest of the time goes: SmolLM2 on six cores reads its weights at about 38 % of the memory bandwidth (Choosing cores).
  • Multi-thread bandwidth: the GB/s numbers are calculated from tokens per second; gemv_bench only runs one thread.

Takeaway: the energy comparison and the 6–7 against 2–7 gap on Qwen need a steadier run on a cooler phone to settle.

What you should take away

Threads that stay alive and take work from a counter cost far less than fresh threads for each job.

Splitting by whole rows keeps the result the same, and small blocks keep the cores busy.

Measure the core sets before choosing one: on this phone, speed stopped growing at about six cores.

Measured numbers come from the iQOO 13 (SM8750) in October 2026, on battery, and are in results/ in the repo. Teal is measured, blue is calculated, amber is an assumption or an illustration.
