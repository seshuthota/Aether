Choosing cores

How many cores are worth using? On this phone, decode keeps getting faster up to six or seven cores and then stops. Two prime cores alone are well behind. This page covers what kinds of core the phone has, why the thread that calls the pool goes on the fastest one, what each of twelve core sets measured, and what turned out not to be true.

Are all the cores the same?

No. The Snapdragon 8 Elite has eight cores of one design (Oryon), in two groups. Cores 0–5 are performance cores with a top clock of 3.53 GHz. Cores 6–7 are prime cores with 4.32 GHz. Many other phone chips also have small efficiency cores, but this one has none.

On battery, the vendor caps both groups under load: about 2.44 GHz for prime and 2.40 GHz for performance measured in Phase 1. That is almost the same clock. Yet one prime core still reads much faster measured in Phase 1:

One core readingprime (core 7)performance (core 0)
from L1 cache~102 GB/s~61 GB/s
from L2 cache~67 GB/s~44 GB/s
from DRAM~61 GB/s~43 GB/s

L1 and L2 are small, fast memories close to each core. DRAM is the main memory. So the difference is not mostly the clock. Where it comes from (the caches, the path to memory, or something the vendor configures) has not been checked. For choosing cores, what matters is the measurement: a prime core does more work per second.

Takeaway: prime cores read faster than performance cores at almost the same clock, so choose cores by measurement, not by clock.

Which core should run the serial work?

Between two parallel jobs, the thread that called the pool works alone. It does RMSNorm, RoPE, residual adds, turns the input into Q8_0 for the quantized kernels, and chooses the next token at the end. While it does that, every worker waits. That serial work should run as fast as possible. So ThreadPool::new sorts the cores by their top clock and pins the caller to the first one. Pinning means fixing a thread to run on one named core. The code is in src/pool.rs, in two steps.

Step 1: sort the cores by top clock

let mut cores = cores.to_vec();
// Stable: equal-speed cores keep the order they were given in.
cores.sort_by_key(|&c| Reverse(cpu_max_freq_khz(c).unwrap_or(0)));
  • to_vec() makes a copy of the list, so the caller's list is not reordered.
  • Reverse flips the sort so the highest clock comes first.
  • unwrap_or(0) treats a core whose clock cannot be read as the slowest.

Step 2: pin the caller to the first core

affinity::pin_current_thread(&cores[..1])?;   // the caller: share 0
  • cores[..1] is the first core in the sorted list, which is the fastest.
  • The list holds one core, so the caller may run only on that core.

All together:

let mut cores = cores.to_vec();
// Stable: equal-speed cores keep the order they were given in.
cores.sort_by_key(|&c| Reverse(cpu_max_freq_khz(c).unwrap_or(0)));
affinity::pin_current_thread(&cores[..1])?;   // the caller: share 0

cpu_max_freq_khz reads cpuinfo_max_freq, the hardware top clock, not the current cap. On battery the caps are nearly equal, but the ranking still puts a prime core first, which is the right choice by the table above. Asked for cores 2–7, the pool runs the caller on core 6 and the workers on 7, 2, 3, 4 and 5.

Takeaway: the caller runs the serial work, so it goes on the fastest core, which the pool picks by sorting on top clock.

Which cores are worth using?

The engine can run decode on any set of cores. Pick cores to see the measured decode speed for that set. SmolLM2-135M Q4_0 (75.8 MB of weights) was run on battery, on a cool phone each time, with clock caps 2.40 and 2.44 GHz. Each set was run twice, once in each order measured. The bar shows the mean of the two passes, and the stats show both.

Which cores?

Reading the bars:

  • One prime core (160) does about 1.9× the work of one performance core (83).
  • Two prime cores (262) beat one by 1.6×. Four more performance cores (2–7, 335) add another 1.3×.
  • After about six cores the curve is flat: 2–7, 1–7 and 0–7 are all between 310 and 348. The two passes of one set differ by up to 10 % (0–7) and 25 % (0–5), so differences of a few percent between them mean nothing.

Qwen2.5-0.5B Q4_0 shows the same pattern with a bigger gap: 117 and 125 tokens per second on 2–7, against 87 and 71 on 6–7 measured. The clocks had dropped to 2.0 and then 1.8 GHz during those runs, so only compare numbers within that group, and the 6–7 pair is most affected. The file is results/phase-4.md.

Takeaway: speed climbs steeply to about six cores and then flattens, so more cores beyond that add little.

Do cores 0 and 1 slow the job down?

An earlier measurement said they did: all eight cores (228 tokens per second) came out slower than cores 2–7 (275). The explanation offered was that Android sends most hardware interrupts to cores 0 and 1. An interrupt is a signal from a device, such as a network chip, that makes a core stop what it is doing to handle it. So a thread there is interrupted more, and the whole job waits for it. That was a hypothesis. The clean sweep tested both parts:

  • The speed loss did not come back. 0–7 gave 340.6 and 310.5; 2–7 gave 326.4 and 343.4. Those are the same within the noise. The earlier numbers were single short runs, and the conditions of the 228 and 275 runs were not recorded at all measured.
  • The interrupts are real, but small. /proc/interrupts counts every interrupt per core since boot. With nothing of ours running for 60 seconds, core 0 took 49,597, core 1 took 12,371, cores 4 and 5 took 8,632 and 10,047, cores 2 and 3 about 3,000, and the prime cores almost none measured. During the five-minute runs, core 0 took 246,000 to 298,000, about 800 to 1,000 a second.

Whether that matters depends on what one interrupt costs, which was not measured. If it is 10 µs assumption, core 0 loses about 1 % of its time calculated, not the 17 % the first run seemed to show. So the interrupts are probably not the explanation, and nothing in this sweep needs one. The first loss was most likely throttling and noise, but its conditions are unknown, so that is not proved.

One thing did show up: core 0 alone decodes at 83 tokens per second, and cores 0–1 together at 136 and 145, while the two cores 6–7 reach 262. Core 1 alone was not run, so this cannot say whether core 0 is slower than the other performance cores, or whether interrupts have anything to do with it.

Takeaway: the loss on all eight cores did not repeat, so the interrupt explanation is not supported by this data.

Is decode close to the memory limit?

Decode reads every weight once per token, so tokens per second × weight bytes is the memory traffic. That traffic cannot pass the ~67 GB/s all eight cores read in Phase 1 calculated:

Model, corestok/sweights readshare of 67 GB/s
SmolLM2-135M Q4_0, 2–733575.8 MB × 335 ≈ 25.4 GB/s38 %
Qwen2.5-0.5B Q4_0, 2–7121278 MB × 121 ≈ 33.7 GB/s50 %

Neither is near the limit, and the smaller model is further from it. Its jobs are smaller (about 12 µs each), so the fixed costs per job weigh more: handing out the job, waiting for the last thread, and the serial work in between. llama.cpp shows what is possible on the bigger model: 123.7 tokens per second from the two prime cores alone, where ours reached 71 to 87 in the sweep. The llama.cpp figure is from an earlier day measured, results/phase-7.md. The Phase 7 pages follow that gap into the kernels.

Takeaway: decode uses at most half of the measured memory bandwidth, so memory is not the limit yet.

What about phones with efficiency cores?

Most phone chips before this one pair big cores with small, simple efficiency cores built to save power. For decode, the usual advice is to leave those out general claim, not measured here. With equal shares, one slow core sets the pace of every job. Even with blocks, it adds threads to wait for at every meeting. The pool's design would still pick sensibly, because the caller lands on the core with the highest top clock, and the blocks keep slow cores from holding up the rest. This phone cannot test any of that.

Takeaway: this phone has no efficiency cores, so the advice for phones that have them is untested here.

Check yourself

Why sort by cpuinfo_max_freq rather than the current clock?

The current clock moves all the time with load, heat and the battery caps; the top clock is a fixed property of the core and ranks prime above performance. On this phone, that matches the measured per-core speed.

One run said 0–7 was 17 % slower than 2–7; the sweep did not repeat it. How do you decide which to believe?

Repeat, in different orders, under recorded conditions. The first number was one short run with no conditions recorded; the sweep ran each set twice with the caps and the foreground app logged and found the sets equal within the noise. One surprising number needs a repeat before it needs an explanation.

Why does a small model use a smaller share of memory bandwidth than a big one?

Its jobs are shorter, so the fixed costs of each job (hand-out, waiting for the slowest thread, the serial work between jobs) are a larger part of the token time.

What you should take away

Prime cores are faster than performance cores at nearly the same clock, so the engine picks cores by measurement.

The caller runs the serial work on the fastest core, and decode stops gaining speed after about six cores.

Decode is far from the memory limit, so the remaining gap lies in the kernels and the per-job overhead.

Measured numbers come from the iQOO 13 (SM8750) in October 2026, on battery, and are in results/ in the repo. Teal is measured, blue is calculated, amber is an assumption or an illustration.
