Choosing cores

More threads is not automatically faster. On this phone, six cores decode faster than all eight, and two prime cores alone are well behind six. This page covers what kinds of core the phone has, why the thread that calls the pool goes on the fastest one, what each core set measured, and which explanations are still only guesses.

Two kinds of core

The Snapdragon 8 Elite has eight cores of one design (Oryon) in two groups: cores 0–5 are performance cores with a top clock of 3.53 GHz, cores 6–7 are prime cores with 4.32 GHz. Many other phone chips also have small efficiency cores; this one has none.

On battery, the vendor caps both groups under load: about 2.44 GHz for prime, 2.40 GHz for performance measured in Phase 1. Almost the same clock. Yet one prime core still reads much faster measured in Phase 1:

So the difference is not mostly the clock. Where it comes from (the caches, the path to memory, something the vendor configures) has not been checked. For choosing cores, what matters is the measurement: a prime core does more work per second.

The caller goes on the fastest core

Between two parallel jobs, the thread that called the pool works alone: RMSNorm, RoPE, residual adds, turning the input into Q8_0 for the quantized kernels, and choosing the next token at the end. While it does that, every worker waits. That serial work should run as fast as possible, so ThreadPool::new sorts the cores by their top clock and pins the caller to the first. src/pool.rs:

let mut cores = cores.to_vec();
// Stable: equal-speed cores keep the order they were given in.
cores.sort_by_key(|&c| Reverse(cpu_max_freq_khz(c).unwrap_or(0)));
affinity::pin_current_thread(&cores[..1])?;   // the caller: share 0

cpu_max_freq_khz reads cpuinfo_max_freq, the hardware top clock, not the current cap. On battery the caps are nearly equal, but the ranking still puts a prime core first, which is the right choice by the table above. Asked for cores 2–7, the pool runs the caller on core 6 and workers on 7, 2, 3, 4, 5.

Which cores?

Two prime cores beat one by 1.7×; adding four performance cores gives another 1.3×; adding cores 0 and 1 as well loses 17 %. On Qwen2.5-0.5B Q4_0 the gap between sets is larger: 128.8 tokens per second on 2–7 against 78.8 on 6–7 measured, results/phase-7.md.

Why not cores 0 and 1?

Going from 2–7 to 0–7 adds two cores and loses speed (274.7 → 227.9). The explanation in the commit is that Android sends most hardware interrupts to cores 0 and 1. A thread there is interrupted more often, finishes its blocks later, and the whole job waits for it. That is a hypothesis; nothing has measured it yet.

It is easy to test. /proc/interrupts counts every interrupt per core since boot. Read it before and after a run, subtract, and see where they went. The Phase 4 sweep does that for every run, plus 60 seconds with nothing running, and also times core 0 alone, 0–1, 2–5 and 0–5. If adding cores 0–1 to 2–5 (which makes 0–5) also loses speed, and cores 0–1 take most of the interrupts during the runs, the hypothesis gains support. If not, the reason lies elsewhere, for example other apps' threads.

Far from the memory limit

Decode reads every weight once per token. So tokens per second × weight bytes is the memory traffic, and it cannot pass the ~67 GB/s all eight cores read in Phase 1 calculated:

Qwen2.5-0.5B Q4_0, 2–7128.8278 MB × 128.8 ≈ 35.8 GB/s53 %

Neither is near the limit, and the smaller model is further from it. Its jobs are smaller (about 15 µs each), so the fixed costs per job weigh more: handing out the job, waiting for the last thread, the serial work in between. llama.cpp shows what is possible on the bigger model: 123.7 tokens per second from the two prime cores alone, where ours reaches 78.8 measured. The Phase 7 pages follow that gap into the kernels.

Phones with efficiency cores

Most phone chips before this one pair big cores with small, simple efficiency cores built to save power. For decode, the usual advice is to leave those out general claim, not measured here: with equal shares one slow core sets the pace of every job, and even with blocks it adds threads to wait for at every meeting. The pool's design would still pick sensibly, because the caller lands on the core with the highest top clock and the blocks keep slow cores from holding up the rest. This phone cannot test any of that.

Check yourself

Why sort by cpuinfo_max_freq rather than the current clock?

The current clock moves all the time with load, heat and the battery caps; the top clock is a fixed property of the core and ranks prime above performance. On this phone, that matches the measured per-core speed.

2–7 decodes at 274.7, 0–7 at 227.9. Name two things that could explain it, and how to tell them apart.

Interrupts landing on cores 0–1, or other work (apps, system services) running there. Counting interrupts per core during a run tests the first; recording what else is running (the sweep logs the foreground app and playing media) helps with the second.

Why does a small model use a smaller share of memory bandwidth than a big one?

Its jobs are shorter, so the fixed costs of each job (hand-out, waiting for the slowest thread, the serial work between jobs) are a larger part of the token time.
