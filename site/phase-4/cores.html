Choosing cores

How many cores are worth using? On this phone, decode keeps getting faster up to six or seven cores and then stops; two prime cores alone are well behind. This page covers what kinds of core the phone has, why the thread that calls the pool goes on the fastest one, what each of twelve core sets measured, and what turned out not to be true.

Two kinds of core

The Snapdragon 8 Elite has eight cores of one design (Oryon) in two groups: cores 0–5 are performance cores with a top clock of 3.53 GHz, cores 6–7 are prime cores with 4.32 GHz. Many other phone chips also have small efficiency cores; this one has none.

On battery, the vendor caps both groups under load: about 2.44 GHz for prime, 2.40 GHz for performance measured in Phase 1. Almost the same clock. Yet one prime core still reads much faster measured in Phase 1:

from L1 cache~102 GB/s~61 GB/s
from L2 cache~67 GB/s~44 GB/s
from DRAM~61 GB/s~43 GB/s

So the difference is not mostly the clock. Where it comes from (the caches, the path to memory, something the vendor configures) has not been checked. For choosing cores, what matters is the measurement: a prime core does more work per second.

The caller goes on the fastest core

Between two parallel jobs, the thread that called the pool works alone: RMSNorm, RoPE, residual adds, turning the input into Q8_0 for the quantized kernels, and choosing the next token at the end. While it does that, every worker waits. That serial work should run as fast as possible, so ThreadPool::new sorts the cores by their top clock and pins the caller to the first. src/pool.rs:

let mut cores = cores.to_vec();
// Stable: equal-speed cores keep the order they were given in.
cores.sort_by_key(|&c| Reverse(cpu_max_freq_khz(c).unwrap_or(0)));
affinity::pin_current_thread(&cores[..1])?;   // the caller: share 0

cpu_max_freq_khz reads cpuinfo_max_freq, the hardware top clock, not the current cap. On battery the caps are nearly equal, but the ranking still puts a prime core first, which is the right choice by the table above. Asked for cores 2–7, the pool runs the caller on core 6 and workers on 7, 2, 3, 4, 5.

Which cores?

Reading the bars:

  • One prime core (160) does about 1.9× one performance core (83).
  • Two prime cores (262) beat one by 1.6×; four more performance cores (2–7, 335) add another 1.3×.
  • After about six cores the curve is flat: 2–7, 1–7 and 0–7 are all between 310 and 348. The two passes of one set differ by up to 10 % (0–7) and 25 % (0–5), so differences of a few percent between them mean nothing.

Qwen2.5-0.5B Q4_0 shows the same pattern with a bigger gap: 117 and 125 tokens per second on 2–7 against 87 and 71 on 6–7 measured. The clocks had dropped to 2.0 and then 1.8 GHz during those runs, so only compare numbers within that group, and the 6–7 pair is most affected. The file is results/phase-4.md.

Do cores 0 and 1 hurt?

An earlier measurement said so: all eight cores (228 tokens per second) came out slower than cores 2–7 (275), and the explanation offered was that Android sends most hardware interrupts to cores 0 and 1, so a thread there is interrupted more and the whole job waits for it. That was a hypothesis. The clean sweep tested both parts:

  • The speed loss did not come back. 0–7 gave 340.6 and 310.5; 2–7 gave 326.4 and 343.4. Those are the same within the noise. The earlier numbers were single short runs, and the conditions of the 228 and 275 runs were not recorded at all measured.
  • The interrupts are real, but small. /proc/interrupts counts every interrupt per core since boot. With nothing of ours running for 60 seconds, core 0 took 49,597, core 1 took 12,371, cores 4 and 5 took 8,632 and 10,047, cores 2 and 3 about 3,000 and the prime cores almost none measured. During the five-minute runs core 0 took 246,000 to 298,000, about 800 to 1,000 a second.

Whether that matters depends on what one interrupt costs, which was not measured. If it is 10 µs assumption, core 0 loses about 1 % of its time calculated, not the 17 % the first run seemed to show. So the interrupts are probably not the explanation, and nothing in this sweep needs one. The first loss was most likely throttling and noise, but its conditions are unknown, so that is not proved.

One thing did show up: core 0 alone decodes at 83 tokens per second and cores 0–1 together at 136 and 145, while the two cores 6–7 reach 262. Core 1 alone was not run, so this cannot say whether core 0 is slower than the other performance cores, or whether interrupts have anything to do with it.

Far from the memory limit

Decode reads every weight once per token. So tokens per second × weight bytes is the memory traffic, and it cannot pass the ~67 GB/s all eight cores read in Phase 1 calculated:

Model, corestok/sweights readshare of 67 GB/s
SmolLM2-135M Q4_0, 2–733575.8 MB × 335 ≈ 25.4 GB/s38 %
Qwen2.5-0.5B Q4_0, 2–7121278 MB × 121 ≈ 33.7 GB/s50 %

Neither is near the limit, and the smaller model is further from it. Its jobs are smaller (about 15 µs each), so the fixed costs per job weigh more: handing out the job, waiting for the last thread, the serial work in between. llama.cpp shows what is possible on the bigger model: 123.7 tokens per second from the two prime cores alone, where ours reached 71 to 87 in the sweep (the llama.cpp figure is from an earlier day measured, results/phase-7.md). The Phase 7 pages follow that gap into the kernels.

Phones with efficiency cores

Most phone chips before this one pair big cores with small, simple efficiency cores built to save power. For decode, the usual advice is to leave those out general claim, not measured here: with equal shares one slow core sets the pace of every job, and even with blocks it adds threads to wait for at every meeting. The pool's design would still pick sensibly, because the caller lands on the core with the highest top clock and the blocks keep slow cores from holding up the rest. This phone cannot test any of that.

Check yourself

Why sort by cpuinfo_max_freq rather than the current clock?

The current clock moves all the time with load, heat and the battery caps; the top clock is a fixed property of the core and ranks prime above performance. On this phone, that matches the measured per-core speed.

One run said 0–7 was 17 % slower than 2–7; the sweep did not repeat it. How do you decide which to believe?

Repeat, in different orders, under recorded conditions. The first number was one short run with no conditions recorded; the sweep ran each set twice with the caps and the foreground app logged and found the sets equal within the noise. One surprising number needs a repeat before it needs an explanation.

Why does a small model use a smaller share of memory bandwidth than a big one?

Its jobs are shorter, so the fixed costs of each job (hand-out, waiting for the slowest thread, the serial work between jobs) are a larger part of the token time.
