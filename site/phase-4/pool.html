Threads that stay

The phone has eight cores, and Phase 3's engine used one. Giving the others work sounds like one line of code: start a thread per core. A thread is a sequence of instructions that the operating system runs on a core. Starting one per core is not enough, because decode does not hand out one big job. It hands out a couple of hundred small ones per token, and the cost of handing one out has to be tiny next to the job itself. This page measures that cost three ways and shows why the engine starts its threads once and keeps them.

How many jobs does one token need?

A decode step is a chain of matrix products, one after another. Each product needs the result of the one before it. Each product can be split across the cores, but the cores must all finish it before the next one starts. So the threads meet once per matrix product.

Count them for one layer: the three projections Q, K and V, the attention itself, the output projection, then gate, up and down in the MLP. That is 8 parallel jobs per layer, plus one for the final logits calculated:

ModelLayersJobs per token
stories15M66 × 8 + 1 = 49
SmolLM2-135M3030 × 8 + 1 = 241
Qwen2.5-0.5B2424 × 8 + 1 = 193

SmolLM2-135M Q4_0 decodes at about 335 tokens per second on cores 2–7 (326.4 and 343.4 in two passes) measured, which is 3.0 ms per token. Divided by 241 jobs, that is about 12 µs per job on average calculated, the serial work between jobs included. Whatever it costs to hand out a job has to be small next to 12 µs.

Takeaway: a token is about 200 small jobs, so each hand-out must cost far less than the 12 µs job, or the hand-outs alone take as long as the work.

Which way of handing out a job is cheapest?

The caller has to wake the workers, give each one its job, and learn when they have finished. There are three common ways to do this.

  1. Start fresh threads for every job, and wait for them to end (spawn and join). Simple, but the operating system must create, schedule and tear down a thread every time.
  2. Keep the threads, and wake them with a lock. Workers sleep on a condition variable, a way for a sleeping thread to wait for a signal. The caller takes a mutex (a lock that only one thread can hold at a time), writes the job, and signals. Waking a sleeping thread is a system call, a request from your program to the kernel, and so is putting it back to sleep.
  3. Keep the threads, and have them watch a counter. Each worker reads a shared number in a loop. The caller writes the job and adds one to the number. No system call at all, as long as the worker is still watching. This is Aether's ThreadPool.

Takeaway: keeping threads and watching a counter costs about 1 µs per hand-out on six threads, against 276 to 506 µs for the other two methods.

How does the pool hand out a job?

The caller must reach every worker without a system call per job, and it must know when they are done. The pool keeps one worker thread per core, pinned to that core (the operating system keeps it there) for the whole life of the model. Two counters do all the talking:

  • epoch, the job number. The caller stores a pointer to the job, then adds one to epoch. Each worker remembers the last epoch it ran. When the number changes, there is a new job.
  • done, the finished count. Each worker adds one when its part is finished. The caller waits until it reaches the number of workers.

The caller does not sit idle while it waits. It runs share 0 of the job itself, so "4 threads" means the caller plus 3 workers.

Watching a counter in a loop is called spinning. It keeps a whole core busy doing nothing useful, so between tokens, or while the user types, it would waste battery. A worker therefore spins only for a while and then goes to sleep. The next page, Waiting: spin, then park, is about that choice.

Takeaway: the caller hands out a job by adding one to a counter, and the workers see it by watching that counter.

What does the code look like?

The hand-out is short, but two details decide whether it is correct. The caller's side of run comes first, in three steps.

Step 1: publish the job

s.job.0.store(&job as *const &Job as *mut &Job, Ordering::Relaxed);
s.done.0.store(0, Ordering::Relaxed);
s.epoch.0.fetch_add(1, Ordering::Release);   // "new job": publish it
  • store writes the pointer to the job, and resets done to zero.
  • fetch_add(1, …) adds one to epoch, and that is the signal. Release keeps this write after the job pointer write (see below).

Step 2: wake the workers and do share 0

for w in &self.workers {
    w.thread().unpark();                       // no system call unless that worker sleeps
}
f(0, n);                                       // the caller does share 0
  • unpark wakes a worker that has gone to sleep. A worker that is still spinning sees the new epoch without it.
  • f(0, n) runs the caller's own share while the workers run theirs.

Step 3: wait for the workers

while s.done.0.load(Ordering::Acquire) != n - 1 {
    std::hint::spin_loop();                    // wait for the workers (then yield)
}
  • n - 1 is the number of workers. With 4 threads, done must reach 3.
  • spin_loop tells the CPU that this is a wait loop. The comment notes that the loop yields after a while, which means the thread gives up its turn on the core to others.

All three together

s.job.0.store(&job as *const &Job as *mut &Job, Ordering::Relaxed);
s.done.0.store(0, Ordering::Relaxed);
s.epoch.0.fetch_add(1, Ordering::Release);   // "new job": publish it
for w in &self.workers {
    w.thread().unpark();                       // no system call unless that worker sleeps
}
f(0, n);                                       // the caller does share 0
while s.done.0.load(Ordering::Acquire) != n - 1 {
    std::hint::spin_loop();                    // wait for the workers (then yield)
}

And each worker:

loop {
    let epoch = /* spin on s.epoch until it changes, then park */;
    seen = epoch;
    // SAFETY: the caller keeps the job alive until every worker has counted itself done.
    let f: &Job = unsafe { *s.job.0.load(Ordering::Relaxed) };
    f(share, n);                               // this worker's part
    s.done.0.fetch_add(1, Ordering::Release);  // "finished"
}

Two details carry the correctness:

  • Release and Acquire. These are memory-ordering rules: they say which writes another core must see before which reads. The caller writes the job pointer first, then the epoch, with Release. A worker that reads the new epoch with Acquire is guaranteed to also see the job pointer written before it. Without that pairing, the CPU or the compiler may reorder the two writes, and a worker could run the previous job.
  • The job lives on the caller's stack. run does not return until every worker has counted itself done, so the workers can never use the job after it is gone. The unsafe block depends on that rule, and the comment above it in src/pool.rs says so. If the caller returned early, a worker would read a job that no longer exists.

The tests in src/pool.rs run 2,000 jobs in a row and check that every share ran exactly once per job, and that a worker that went to sleep wakes up for the next one.

Takeaway: the hand-out is correct only because the epoch is written after the job and the job outlives its last worker.

Check yourself

Why does decode need so many hand-outs, when prefill could do with few?

Each matrix product needs the previous one's result, so the threads must finish and meet after every one: 8 per layer, every token. Prefill meets after every matrix product too, but each one covers every prompt token at once, so there is far more work per meeting. (Its attention still runs one token at a time, one meeting each.)

At 12 µs per job, what would spawning threads cost?

About 506 µs per job on the phone, forty times the job itself. A token of 241 jobs would take about 122 ms instead of 3 ms.

Why is the worker's read of the job pointer allowed to be Relaxed?

Because it happens after the worker read the new epoch with Acquire, and the caller wrote the pointer before the epoch with Release. The pair of orderings already makes the pointer visible; the pointer read itself needs no extra ordering.

What you should take away

Each token needs about 200 small hand-outs, so each one must cost far less than a 12 µs job.

Keeping threads and having them watch a counter makes a hand-out about a microsecond, where spawning costs hundreds.

The caller publishes a job by bumping a counter, and the workers see it by watching that counter.
