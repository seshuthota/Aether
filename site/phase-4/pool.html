Threads that stay

The phone has eight cores, and Phase 3's engine used one. Giving the others work sounds like one line of code: start a thread per core. It is not, because decode does not hand out one big job. It hands out a couple of hundred small ones per token, and the cost of handing one out has to be tiny next to the job itself. This page measures that cost three ways and shows why the engine starts its threads once and keeps them.

How many jobs per token

A decode step is a chain of matrix products, one after another, and each needs the result of the one before. Every matrix product can be split across cores, but the next one cannot start until all cores have finished this one. So the threads meet once per matrix product.

Count them for one layer: the three projections Q, K and V, the attention itself, the output projection, then gate, up and down in the MLP. That is 8 parallel jobs per layer, plus one for the final logits calculated:

stories15M66 × 8 + 1 = 49
SmolLM2-135M3030 × 8 + 1 = 241

SmolLM2-135M Q4_0 decodes at about 335 tokens per second on cores 2–7 (326.4 and 343.4 in two passes) measured, which is 3.0 ms per token. Divided by 241 jobs, that is about 12 µs per job on average calculated, the serial work between jobs included. Whatever it costs to hand out a job has to be small next to 12 µs.

Three ways to hand out a job

  1. Start fresh threads for every job, and wait for them to end (spawn and join). Simple, and the operating system has to create a thread, schedule it, and tear it down every time.
  2. Keep the threads, wake them with a lock. Workers sleep on a condition variable; the caller takes a mutex, writes the job, and signals. Waking a sleeping thread is a system call, and so is putting it back to sleep.
  3. Keep the threads, and have them watch a counter. Each worker reads a shared number in a loop. The caller writes the job and adds one to the number. No system call at all, as long as the worker is still watching. This is Aether's ThreadPool.

And every method gets dearer with more threads: the pool's own cost is 13 times higher on eight threads than on two, because more workers have to notice the change and report back. These runs were on battery with the clock caps at 2.40 and 2.44 GHz and the phone idle, but the hand-out cost moves with the caps and with what else runs, so read it as the right order of magnitude. The pool figure was measured with workers that were still spinning; it is the cost during decode, not after the workers have gone to sleep.

How the pool hands out a job

The pool keeps one worker thread per core, pinned to it, for the whole life of the model. Two counters do all the talking:

  • epoch, the job number. The caller stores a pointer to the job, then adds one to epoch. Each worker remembers the last epoch it ran; when the number changes, there is a new job.
  • done, the finished count. Each worker adds one when its part is finished. The caller waits until it reaches the number of workers.

The caller does not sit idle while it waits: it runs share 0 of the job itself. So “4 threads” means the caller plus 3 workers.

Watching a counter in a loop is called spinning, and it keeps a whole core busy doing nothing useful. Between tokens, or while the user types, that would waste battery. So a worker spins only for a while and then goes to sleep; the next page, Waiting: spin, then park, is about that choice.

The code

src/pool.rs, the caller's side of run, shortened:

s.job.0.store(&job as *const &Job as *mut &Job, Ordering::Relaxed);
s.done.0.store(0, Ordering::Relaxed);
s.epoch.0.fetch_add(1, Ordering::Release);   // "new job": publish it
for w in &self.workers {
    w.thread().unpark();                       // no system call unless that worker sleeps
}
f(0, n);                                       // the caller does share 0
while s.done.0.load(Ordering::Acquire) != n - 1 {
    std::hint::spin_loop();                    // wait for the workers (then yield)
}

And each worker:

loop {
    let epoch = /* spin on s.epoch until it changes, then park */;
    seen = epoch;
    let f: &Job = unsafe { *s.job.0.load(Ordering::Relaxed) };
    f(share, n);                               // this worker's part
    s.done.0.fetch_add(1, Ordering::Release);  // "finished"
}

Two details carry the correctness:

  • Release and Acquire. The caller writes the job pointer first, then the epoch, with Release. A worker that reads the new epoch with Acquire is guaranteed to also see the job pointer written before it. Without that pairing, the CPU or the compiler may reorder the two writes, and a worker could run the previous job.
  • The job lives on the caller's stack. run does not return until every worker has counted itself done, so the workers can never use the job after it is gone. The unsafe block depends on that rule, and the comment above it in src/pool.rs says so.

The tests in src/pool.rs run 2,000 jobs in a row and check that every share ran exactly once per job, and that a worker that went to sleep wakes up for the next one.

Check yourself

Why does decode need so many hand-outs, when prefill could do with few?

Each matrix product needs the previous one's result, so the threads must finish and meet after every one: 8 per layer, every token. Prefill meets after every matrix product too, but each one covers every prompt token at once, so there is far more work per meeting. (Its attention still runs one token at a time, one meeting each.)

At 12 µs per job, what would spawning threads cost?

About 506 µs per job on the phone, forty times the job itself. A token of 241 jobs would take about 122 ms instead of 3 ms.

Why is the worker's read of the job pointer allowed to be Relaxed?

Because it happens after the worker read the new epoch with Acquire, and the caller wrote the pointer before the epoch with Release. The pair of orderings already makes the pointer visible; the pointer read itself needs no extra ordering.
