Splitting the work

With threads that stay, the next question is how to divide one matrix product between them. The obvious answer, an equal share each, let six extra cores add almost nothing. This page shows why an equal share wastes cores that are not equal, and the fix: small blocks handed out one at a time, so a faster core simply takes more of them.

Why split by row, never inside a row?

A matrix-vector product makes one output number per row of the matrix. Each number is the dot product of that row with the input vector, meaning each pair of numbers is multiplied and the products are added up. Rows do not depend on each other, so threads can take different rows and never need to talk until the end.

The other way is to cut every row into pieces and give each thread a piece. Each thread then produces a partial sum, and the partial sums must be added together afterwards. That costs another meeting, and it adds the numbers in a different order. The last bits of the result would then change with the thread count (why order matters).

Split by rows, and each row's sum is still computed by one thread, in the same order as with one thread. The result is bit-identical, meaning the same bits, whatever the number of threads. The test threaded_matmuls_are_bit_identical in src/kernels/mod.rs checks it for every matrix shape in the goldens with 2, 3 and 8 threads.

Takeaway: splitting by rows keeps each sum in one thread's hands, so the answer is bit-identical for any thread count.

The reason is in how a job ends. The caller cannot move on until every thread is finished, so every job takes as long as its slowest thread. With equal shares, any thread that is a little slower makes all the others wait, about 200 times per token. And the threads are not equal: one prime core reads 61 GB/s from memory, one performance core 43 GB/s measured in Phase 1. A core that is also handling something else, such as another app or interrupts, falls further behind. Which thread was the slow one in that profile was not recorded.

Why do equal shares waste cores?

One matrix product of 1,536 rows (SmolLM2's gate projection) is split across a set of cores. Each bar is one thread, and its length is its time. A prime core here works at 61, a performance core at 43, in proportion to the Phase 1 read speeds. The slider slows one performance core further, as if it had other work illustration. The real cores also share one memory bus, which this sketch leaves out.

Takeaway: with equal shares, one slow thread sets the time for the whole job; with blocks, it only takes fewer blocks.

How do blocks fix it?

The fix (commit 67d334f) stops deciding shares in advance. The rows are cut into small blocks, and a shared counter says which block is next. Every thread, the caller included, loops: take the next block number, compute those rows, and repeat until the blocks run out. A fast thread comes back sooner and takes more. A counter here is a number in memory that all threads share, and an atomic operation changes it in one step that no other thread can interrupt.

The code is in src/pool.rs, in three steps. Step 1 creates the shared counter:

let next = AtomicUsize::new(0);                // one counter, shared by every thread
  • AtomicUsize is a counter that threads can change safely at the same time.
  • It starts at 0, so the first block is block 0.

Step 2 takes a block:

let b = next.fetch_add(1, Ordering::Relaxed);   // "I take block b"
let start = b * block;
if start >= len { break; }
  • fetch_add(1, …) adds one and returns the old value, in one atomic step. Two threads can never get the same number, so no block is computed twice.
  • start is the first row of block b. When it runs past the last row, the loop breaks and the thread stops.

Step 3 computes the block's rows:

f(start..(start + block).min(len));
  • min(len) stops the last block at the final row, since it may be shorter than the others.

All three together:

pub fn for_blocks(&self, len: usize, block: usize, f: &(dyn Fn(Range<usize>) + Sync)) {
    let next = AtomicUsize::new(0);
    self.run(&|_, _| loop {
        let b = next.fetch_add(1, Ordering::Relaxed);   // "I take block b"
        let start = b * block;
        if start >= len { break; }
        f(start..(start + block).min(len));
    });
}

How big should a block be? Too big and the end of the job is uneven again. Too small and the threads spend their time fighting over the counter. block_size aims at about 8 blocks per thread, in whole multiples of 16 rows (the kernel's step). For the 1,536-row matrix on 6 threads, that is 32 rows and 48 blocks calculated.

Which thread computes a block does not change what the block computes, so the result is still bit-identical. The same commit also put the caller on the fastest core (Choosing cores) and split attention by head. The table above is the result. On two equal prime cores, blocks make no difference (255 against 261, within noise, as expected). On six or eight cores, they turn extra cores that added nothing into 25 to 30 % more speed.

The first version of this page said all eight cores went from 98 to 228 tokens per second. That compared the first run (98, conditions only partly recorded) with a later run whose conditions were not recorded (228). The repeat above, under the same conditions for both, shows a smaller gain. Choosing cores has the full sweep.

Takeaway: a shared counter hands out small blocks, so faster threads simply take more of them.

How does the pool reach the matrix products?

The pool exists, and the matrix products need to use it. The forward pass from Phase 2 has to be handed the pool somehow, and each product has to split its rows across it. Four short steps in src/ do that.

Step 1: the model keeps the pool

// src/model/transformer.rs
pub fn set_pool(&mut self, pool: ThreadPool) {
    self.pool = Some(pool);
}
  • pool is a field of the model, an Option<ThreadPool>: None until set_pool is called, so a model without a pool runs on one thread as before.
  • Callers such as src/session.rs and examples/bench_suite.rs build a ThreadPool for the cores given with -c and call this.

Step 2: the forward pass passes it on

let pool = self.pool.as_ref();                      // Option<&ThreadPool>
k::linear_on(pool, &mut s.q, &s.xb, &lw.wq);       // was k::matmul(…) in Phase 2
  • as_ref() turns &Option<ThreadPool> into Option<&ThreadPool>, a borrow that can be handed to every call.
  • So the call sites in the forward pass do change: each gains the pool argument. The arithmetic does not. The attention step takes the pool too, to split heads.

Step 3: linear_on picks the kernel for the weight format

  • linear_on(pool, out, x, w) works for any storage format of the weights w (the formats are Phase 6). It calls linear_batch_on with one token.
  • For f32 weights and one token, that ends in matmul_on(pool, out, x, f). The other formats have their own _on versions.

Step 4: matmul_on splits the rows

pub fn matmul_on(pool: Option<&ThreadPool>, out: &mut [f32], x: &[f32], w: &[f32]) {
    let Some(pool) = pool.filter(|p| p.threads() > 1) else { return matmul(out, x, w) };
    let n = x.len();
    assert_eq!(w.len(), out.len() * n, "W must be out.len() x x.len()");
    let o = SharedOut(out.as_mut_ptr());
    let block = crate::pool::block_size(out.len(), pool.threads(), ROW_BLOCK);
    pool.for_blocks(out.len(), block, &|r| {
        // SAFETY: `for_blocks` hands each block of rows to exactly one thread.
        let mine = unsafe { std::slice::from_raw_parts_mut(o.ptr().add(r.start), r.len()) };
        matmul(mine, x, &w[r.start * n..r.end * n]);
    });
}
  • The let … else line is the fallback: with no pool, or a pool of one thread, it calls the plain single-threaded matmul.
  • SharedOut wraps the output’s raw pointer so that every thread may write into out. Each thread writes only its own rows, and the SAFETY comment gives the reason it is allowed.
  • block_size and for_blocks hand out blocks of 16 rows or more; How do blocks fix it? above shows both.
  • Inside a block, the closure calls the ordinary matmul on just those rows: w[r.start * n..r.end * n] is the rows r.start up to r.end of the weight matrix. That is why the result is bit-identical.

Without that line pool is still an Option, so the calls below would not compile. The fallback is what makes the no-pool and one-thread cases run single-threaded; an unwrap() would compile but panic, and an if let with no else would silently skip the product. If a thread wrote outside its own rows, two threads would write the same numbers at once.

Takeaway: the model stores an optional pool, the forward pass hands it to linear_on, and matmul_on splits the rows across it.

How do you split attention?

Attention is not one matrix product, but its heads are independent. Each head reads its own slice of the query and writes its own slice of the output. So the engine hands out heads as blocks of one. The catch is that there are few of them. SmolLM2 has 9 query heads. If every head takes the same time, 9 heads on 6 threads take two rounds, and in the second round 3 threads have nothing to do calculated:

ThreadsSmolLM2 (9 heads)Qwen2.5 (14 heads)
25 rounds, 90 % busy7 rounds, 100 % busy
62 rounds, 75 % busy3 rounds, 78 % busy
82 rounds, 56 % busy2 rounds, 88 % busy

(“Busy” = heads ÷ (threads × rounds).) Splitting each head's positions between threads would balance better at long contexts. The price is combining partial results of the softmax, the step that turns attention scores into weights. The engine does not do that yet.

Takeaway: with 9 heads on 6 threads, a head-per-thread split leaves threads idle in the second round.

Check yourself

Why is splitting by rows bit-identical, but splitting each row into pieces not?

By rows, each row's sum is computed start to finish by one thread, in the original order. In pieces, the partial sums are added in a new order, and float addition is not associative, so the last bits change.

Equal shares on two prime cores worked well. Why?

The two threads run at the same speed, so they finish at about the same time and neither waits long. Equal shares only hurt when the threads are unequal.

Why not use blocks of one row, for perfect balance?

Every block costs one atomic fetch_add on a counter all threads share, and that counter's cache line has to move between cores each time. With 1,536 one-row blocks, that traffic would cost more than the imbalance it removes.

What you should take away

Threads help only when the split is both correct and balanced.

Rows keep every sum in one thread, small blocks from a shared counter keep fast cores busy, and attention is limited by how many heads there are to share out.
