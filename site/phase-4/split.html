Splitting the work

With threads that stay, the next question is how to divide one matrix product between them. The obvious answer, an equal share each, let six extra cores add almost nothing. This page shows why an equal share wastes cores that are not equal, and the fix: small blocks handed out one at a time, so a faster core simply takes more of them.

Split by rows, never inside a row

A matrix-vector product makes one output number per row of the matrix: the dot product of that row with the input vector. Rows do not depend on each other, so threads can take different rows and never need to talk until the end.

The other way to split, cutting every row into pieces and giving each thread a piece, would need the partial sums added together afterwards. That costs another meeting, and it adds the numbers in a different order, so the last bits of the result would change with the thread count (why order matters).

Split by rows, each row's sum is still computed by one thread, in the same order as with one thread. The result is bit-identical whatever the number of threads. The test threaded_matmuls_are_bit_identical in src/kernels/mod.rs checks it for every matrix shape in the goldens with 2, 3 and 8 threads.

The equal split, and what it did

Eight cores were slower than two in every row. That run was taken on a throttled phone, though: its log records the performance cores capped at 1.79 GHz and the prime cores at 1.02 GHz, against 2.40 and 2.44 GHz on a cool phone. So the size of the slowdown is not reliable (see the repeat below). A profile of SmolLM2 Q4_0 on eight cores (simpleperf) found 58 % of the samples in the worker loop, spinning, and 26 % in the actual kernel measured. The threads spent most of their time waiting.

The reason is in how a job ends. The caller cannot move on until every thread is finished, so every job takes as long as its slowest thread. With equal shares, any thread that is a little slower makes all the others wait, about 200 times per token. And the threads are not equal: one prime core reads 61 GB/s from memory, one performance core 43 GB/s measured in Phase 1. A core that is also handling something else (another app, or interrupts) falls further behind. Which thread was the slow one in that profile was not recorded.

The repeat. To check, the old equal-share code was rebuilt and run next to the current code, one after the other, three rounds, phone cool and caps at 2.40 and 2.44 GHz. SmolLM2-135M Q4_0 decode in tokens per second, rounds 1, 2 and 3 measured:

Blocks from a shared counter

The fix (commit 67d334f) stops deciding shares in advance. The rows are cut into small blocks, and a shared counter says which block is next. Every thread, the caller included, loops: take the next block number, compute those rows, repeat until the blocks run out. A fast thread comes back sooner and takes more. src/pool.rs:

pub fn for_blocks(&self, len: usize, block: usize, f: &(dyn Fn(Range<usize>) + Sync)) {
    let next = AtomicUsize::new(0);
    self.run(&|_, _| loop {
        let b = next.fetch_add(1, Ordering::Relaxed);   // "I take block b"
        let start = b * block;
        if start >= len { break; }
        f(start..(start + block).min(len));
    });
}

fetch_add is one atomic instruction: two threads can never get the same number. How big should a block be? Too big and the end of the job is uneven again; too small and the threads spend their time fighting over the counter. block_size aims at about 8 blocks per thread, in whole multiples of 16 rows (the kernel's step). For the 1,536-row matrix on 6 threads that is 32 rows, 48 blocks calculated.

Which thread computes a block does not change what the block computes, so the result is still bit-identical. The same commit also put the caller on the fastest core (Choosing cores) and split attention by head. The table above is the result: on two equal prime cores blocks make no difference (255 against 261, within noise, as expected), and on six or eight cores they turn extra cores that added nothing into 25 to 30 % more speed.

The first version of this page said all eight cores went from 98 to 228 tokens per second. That compared the throttled first run (98) with a later run whose conditions were not recorded (228), and the repeat above, under the same conditions for both, shows a smaller gain; Choosing cores has the full sweep.

Attention: split by head

Attention is not one matrix product, but its heads are independent: each reads its own slice of the query and writes its own slice of the output. So the engine hands out heads as blocks of one. The catch is that there are few of them. SmolLM2 has 9 query heads; if every head takes the same time, 9 heads on 6 threads take two rounds, and in the second round 3 threads have nothing to do calculated:

(“Busy” = heads ÷ (threads × rounds).) Splitting each head's positions between threads would balance better at long contexts, at the price of combining partial softmax results. The engine does not do that yet.

Check yourself

Why is splitting by rows bit-identical, but splitting each row into pieces not?

By rows, each row's sum is computed start to finish by one thread, in the original order. In pieces, the partial sums are added in a new order, and float addition is not associative, so the last bits change.

Equal shares on two prime cores worked well. Why?

The two threads run at the same speed, so they finish at about the same time and neither waits long. Equal shares only hurt when the threads are unequal.

Why not use blocks of one row, for perfect balance?

Every block costs one atomic fetch_add on a counter all threads share, and that counter's cache line has to move between cores each time. With 1,536 one-row blocks, that traffic would cost more than the imbalance it removes.
