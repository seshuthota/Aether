Waiting: spin, then park

A worker with nothing to do has two choices. It can keep checking for new work, which reacts within a fraction of a microsecond but keeps a core busy doing nothing. Or it can ask the operating system to put it to sleep, which costs nothing while asleep but takes microseconds to wake. The engine does the first for a while, then the second. This page is about that trade, and two traps around it: a lost wake-up, and two counters sharing a cache line.

Should a waiting worker spin or sleep?

Between two jobs, a worker must wait, and either choice has a price. Here are the two ways to wait.

Spinning means reading the epoch counter in a loop until it changes. The new job is seen almost the moment it is published. But the core is busy the whole time: it cannot run anything else, and it cannot drop into a low-power state.

Parking means std::thread::park(), which asks the kernel to take the thread off the core until someone calls unpark on it. While parked, it costs nothing. Waking it is a system call on the caller's side, and then the kernel has to schedule the thread again, which takes microseconds.

Which is better depends on how long the wait will be. During decode, the next job comes a few microseconds after the last. Between two messages in a chat, it may come a minute later. So a worker spins first, and parks if nothing has come after SPIN = 20,000 polls. The code is in src/pool.rs, and it comes in two steps.

Step 1: check for a new job

let epoch = loop {
    let e = s.epoch.0.load(Ordering::Acquire);
    if e != seen || s.stop.0.load(Ordering::Acquire) { break e; }
    spins += 1;
  • The loop reads epoch. If it differs from the last one this worker ran, or the pool is stopping, the wait ends.
  • spins counts how many times the worker has checked without finding work.

Step 2: spin for a while, then park

    if spins < SPIN {
        std::hint::spin_loop();     // tells the core "I am only waiting"
    } else {
        thread::park();             // sleep until unpark()
    }
  • While spins is below SPIN, the worker spins, and the core stays ready for the next job.
  • After that, the worker parks. Without this limit, a worker that waits for a minute would keep a core busy for the whole minute.

All together

let epoch = loop {
    let e = s.epoch.0.load(Ordering::Acquire);
    if e != seen || s.stop.0.load(Ordering::Acquire) { break e; }
    spins += 1;
    if spins < SPIN {
        std::hint::spin_loop();     // tells the core "I am only waiting"
    } else {
        thread::park();             // sleep until unpark()
    }
};

How long 20,000 polls take on the phone is not measured. The comment in the code estimates tens of microseconds, so the widget assumes 40 µs assumption. The poll itself may not be cheap: on ARM, spin_loop can compile to an instruction that waits (ISB), so the time per poll is not a guess to trust until it is timed.

Takeaway: a worker spins briefly for a fast reaction, then parks so a long wait costs no core time.

What is the lost wake-up?

A job can be published at the worst moment. There is a gap between a worker's last check of epoch and its call to park(). Suppose the caller publishes a job and calls unpark right inside that gap. The worker has not gone to sleep yet, so there is nobody to wake. Then it parks, and sleeps through a job it should be running. The caller waits for it forever.

Rust's park and unpark avoid this with a token: an unpark that arrives before the park is remembered, and the next park returns at once. The worker then loops, sees the new epoch, and runs the job. That is why the caller can call unpark on every worker after every job without checking whether it is asleep. For a worker that is still spinning, unpark only sets the token, without a system call.

Takeaway: the token lets the caller wake every worker without checking whether it sleeps; without it, a job can be lost.

Why does each counter get its own cache line?

Two counters that sit side by side can slow each other down, even when neither one changes the other's value. A core does not read or write single bytes from memory. It moves 64-byte cache lines, and while workers spin, each keeps a copy of the line holding epoch in its own cache. When any core writes to that line, every other copy is thrown away and has to be fetched again.

If done sat in the same line as epoch, every worker finishing a job would write that line, and every spinning worker would lose its copy of epoch, although epoch itself did not change. That is false sharing. The pool puts each counter in its own line:

#[repr(align(64))]
struct Line<T>(T);

struct Shared {
    epoch: Line<AtomicU64>,     // read by spinning workers, written once per job
    done: Line<AtomicUsize>,    // written by each worker once per job
    stop: Line<AtomicBool>,
    ...
}
  • #[repr(align(64))] makes every Line start on a 64-byte boundary and take at least 64 bytes.
  • Each counter sits inside its own Line, so a write to done cannot touch the line that spinning workers are watching.

The 64 is the line size this phone reports in CTR_EL0 measured in Phase 1. How much time the padding saves here has not been measured.

Takeaway: put counters that different cores write into separate 64-byte lines, or each write evicts the other cores' copies.

What does spinning cost?

A spinning core shows up in a profile as busy. In the equal-split build, the profile of SmolLM2 Q4_0 on all eight cores found 58 % of samples in the worker loop. On the two prime cores, it found 17.5 % measured. Most of that is spinning: a worker that finished its share early spins until the next job.

On a phone, that waiting is not free. A spinning core draws power and makes heat, and it cannot take a slower clock or a sleep state while it spins. So a thread count that does not make decode faster could still make it more expensive per token. The sweep measured joules per token over five minutes of decoding for cores 7, 6–7, 2–7 and 0–7: 0.013, 0.011, 0.011 and 0.011 measured. The phone was throttled during those runs, and the charge counter it comes from is coarse. It disagreed with the other power reading by up to 30 %. So the honest reading is that the three multi-core sets cost about the same per token, and one prime core alone costs a little more. Whether the spinning shows up in the energy is not resolved by this.

The caller waits too, for the workers to finish. It spins and then calls thread::yield_now() instead of parking. It is always the one waiting for others, and the workers finish within microseconds.

Takeaway: spinning keeps cores busy, so a thread count that adds no speed can still cost energy per token.

Check yourself

Why spin at all, if parking costs nothing while asleep?

Because waking takes microseconds, and decode hands out a job every 12 µs or so. Parking between every two jobs would add a large fraction to every token.

Why park at all, if spinning reacts fastest?

Between tokens, or while the user is reading, nothing comes for seconds. A pool that spun forever would keep several cores busy and drain the battery while doing nothing.

What would happen without the token in park/unpark?

A job published just before a worker parks would be missed: the worker would sleep, and the caller would wait forever for its done.

What you should take away

A worker spins for a short while, then parks, so it reacts fast without wasting a core on long waits.

The park token stops a job from being lost, and each hot counter gets its own cache line.

Spinning is fast but costs energy, so the engine must not spin for long.
