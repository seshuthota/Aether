Matching Hugging Face

llama2.c gave Phase 2 one answer to match bit for bit. For SmolLM2 the reference is Hugging Face transformers, which adds numbers in a different order. The engine checks every layer to a tolerance, and the tokens and the tokenizer exactly.

What are we trying to do here?

The project’s rule is that correctness comes from outside: a second copy of our own code would share our bugs. For SmolLM2 the outside references are Hugging Face transformers, the Python library the model was published for, and tokenizers, its tokenizer library.

Three things are checked, each in a different way:

By the end of the page you can say why each check uses the kind of comparison it does, and what to look at first when a reference disagrees. The script is tools/hf_dump.py; the tests are in src/model/hf.rs, src/model/reference.rs and src/tokenizer/bytelevel.rs.

How do you get the reference’s numbers out of PyTorch?

transformers runs the whole model in one call and returns only the final scores. To compare layer by layer, the engine needs the vectors in between. PyTorch lets you attach a forward hook to any part of a model: a function that runs after that part and can copy its output.

def save(name):
    def hook(_mod, inputs, output):
        t = output[0] if isinstance(output, tuple) \
            else output
        acts[name] = t[0].detach().float().numpy()
    return hook

for l, layer in enumerate(m.layers):
    layer.input_layernorm.register_forward_hook(
        save(f"L{l}.attn_norm"))
    # ... v_proj, self_attn, mlp, the layer itself
  • Each layer gets hooks after its first norm, the value projection, attention, the second norm, the MLP, and the layer’s output.
  • The names (L3.attn_norm) are the ones the engine’s own observer uses when it traces a forward pass, so each pair can be matched by name.
  • The model is loaded in f32 with attn_implementation="eager", the plain attention code. bf16 weights widen exactly, as in the engine, so the only difference left is the order of additions.
  • The dump is written as a safetensors file. The engine reads it with the reader from page 01, so the test needs no Python.

Takeaway: hooks copy every layer out of transformers, under names the engine uses too, so each vector has a partner to compare with.

Why load the reference in f32 rather than its native bf16?

  • The engine computes in f32; a bf16 reference would differ by its own rounding
    Both sides then start from the same exact numbers, and only summation order differs.
  • bf16 cannot be hooked
    Hooks work in any dtype; the choice is about what is being compared.
  • f32 runs faster in PyTorch
    Speed does not matter for a one-off dump; matching arithmetic does.

Why not demand the same bits?

In Phase 2 the engine matched llama2.c bit for bit, because both added the numbers of each dot product in the same order. transformers does not: its matrix products go through optimised libraries that split and reorder the sums.

In f32, is (a + b) + c always equal to a + (b + c)?

  • No; each addition rounds, so a different order can round differently
    Each sum is rounded to 24 bits of mantissa, and the rounding depends on what was added first.
  • Yes; addition is associative
    It is for real numbers, not for floats, which round after every step.
  • Only when the numbers are negative
    The sign does not matter; rounding happens for any values.

Example in f32: (108 + 1) − 108 is 0, because 108 + 1 rounds back to 108; 108 − 108 + 1 is 1 calculated. So two correct engines give slightly different vectors, and the test needs a tolerance. The engine measures the error relative to the size of the reference vector:

let scale = reference.iter()
    .fold(0.0f32, |m, v| m.max(v.abs()));
let abs = ours.iter().zip(reference)
    .fold(0.0f32, |m, (&a, &r)| m.max((a - r).abs()));
(abs, abs / scale)
  • The worst difference is divided by the largest value in the reference. A difference of 0.001 in a vector whose values reach 100 is tiny; in a vector whose values reach 0.01 it is not.
  • The test fails above 1e-3. The worst over all 30 layers and every prompt position was 5.5e-5 measured, about twenty times inside the limit.
  • A real bug, such as a wrong RoPE layout or a wrong key/value group, gives errors of order 1, not 1e-4. The gap between the two is what makes a tolerance safe.

Takeaway: different summation orders change the last bits, so layers are compared relative to their size, with a limit far below what a bug produces.

A layer’s reference values reach at most 40, and the worst difference is 0.02. Does it pass a 1e-3 limit?

  • Yes: 0.02 ÷ 40 = 5e-4
    The relative error is under 1e-3, so the test passes.
  • No: 0.02 is above 1e-3
    The limit is relative; the absolute difference must first be divided by 40.
  • It depends on the number of positions
    The test takes the worst position; the count does not change the limit.

Why compare every layer, not just the output?

If only the final scores were compared, a wrong number would show that something is wrong, but not where. SmolLM2 has 30 layers with seven stages each.

The final scores are wrong. The comparison shows layer 0’s attention output matches, but layer 0’s MLP output does not. Where is the bug?

  • Between the two: the second norm, or the MLP
    Everything up to attention agrees, so the first stage that disagrees is in the MLP half of layer 0.
  • In the classifier
    The classifier comes after all 30 layers; the error already shows in layer 0.
  • In attention
    Attention’s output matched, so attention is not where the numbers first go wrong.

The test walks every recorded stage at every prompt position, and reports the worst error per stage name. A bug shows up as the first stage, in the first layer, whose error jumps.

  • The query and key vectors are not compared. transformers records them before RoPE, and the engine after. The attention output, which uses both, is compared instead.
  • The prompt runs as one batch (forward_batch_traced), so the batched prefill path is the one being checked.

Takeaway: comparing every stage points at the first one that goes wrong, which a final-output check cannot.

Why might greedy tokens disagree when the code is right?

After the layers, the test runs greedy generation, always taking the highest-scoring token, for 48 tokens, and compares the ids with transformers’ generate(do_sample=False). Ids are whole numbers: they either match or they do not, so this check is exact.

Small differences in the last bits could in principle change a token, when two candidates score almost the same. For SmolLM2’s 48 tokens it did not happen: all 48 matched measured.

For Qwen2.5-Instruct, the engine and transformers agree on every layer but disagree on the 20th greedy token. What should you check first?

  • The reference’s generation settings
    generate reads generation_config.json, which can add a repetition penalty even when sampling is off.
  • The attention kernel
    Every layer already matched, so the kernels compute the same scores.
  • The tokenizer
    The ids are compared directly; the tokenizer is not used after the prompt.

This trap is real. generate reads the model’s generation_config.json, and Qwen2.5-Instruct’s sets a repetition penalty of 1.05, which lowers the score of tokens already used. “Greedy” in transformers was then not plain greedy. hf_dump.py now passes repetition_penalty=1.0. SmolLM2’s generation config sets only the special token ids, so it was not affected.

Takeaway: tokens must match exactly; when they do not and the layers do, look at the reference’s settings before the code.

How do you test a tokenizer?

A tokenizer has no floating point, so there is nothing to round: every id must be the same. The question is which inputs to try. Plain English sentences would pass even with a broken Unicode table or a wrong whitespace rule.

Which input is most likely to catch a bug in the pre-tokenizer?

  • Text in several scripts, with runs of spaces and newlines
    Those exercise the letter table and the whitespace rules, where hand-written regex code goes wrong.
  • A long English paragraph
    It repeats the same easy cases: ASCII letters and single spaces.
  • A list of the most common English words
    Each is one word with no edge cases at its boundaries.

hf_dump.py writes a corpus of 433 strings with the ids and the decoded text that HF tokenizers gives for each. The corpus includes several scripts, emoji, emoji joined with zero-width joiners (ZWJ, as in family emoji), flags, code, and chat markup with special tokens. The test encodes and decodes every string and compares both directions.

  • All 433 match exactly, on the host and on the phone measured.
  • The regex has its own hand-checked cases too (the splits on page 03), so a failure can be traced to the split or to the merges.
  • The Phase 5 totals were 85 of 85 tests passing on 2026-10-22 measured.

One gap: SmolLM2-360M uses the same code but has not been run through this comparison. Until it is, “works for SmolLM2” means 135M.

Takeaway: a tokenizer test is only as good as its corpus, so it must include the scripts, spaces and emoji that break hand-written rules.

Why is the tokenizer compared exactly, while layers get a tolerance?

  • Tokenizing involves no arithmetic to reorder, so any difference is a bug
    Ids come from string rules and lookups; both sides must reach the same ids.
  • The tokenizer is simpler, so a tolerance is not needed
    It is not simpler; it has nothing that rounds.
  • A tolerance would be too slow to compute
    Speed is not the reason; an id is either equal or not.

What you should take away

Forward hooks copy every layer out of transformers; the engine compares each one relative to its size.

Floats differ in the last bits when sums are reordered, so layers get a tolerance; ids and the tokenizer must match exactly.

When tokens disagree but layers match, check the reference’s generation settings first.
