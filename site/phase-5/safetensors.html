Reading weights in place

A Hugging Face model keeps its weights in a safetensors file: a short JSON header, then the raw numbers. The engine maps that file into memory, reads each tensor where it lies, and widens the 16-bit numbers to f32 without losing a bit.

What are we trying to do here?

Phase 2 read stories15M from a llama2.c file: a fixed list of numbers in a fixed order, all in f32. SmolLM2-135M comes from Hugging Face as model.safetensors, a file that names every tensor and says where its bytes are. Its numbers are stored in bf16, a 16-bit float format, while the engine’s kernels compute in f32, the ordinary 32-bit float.

A tensor here is one named block of weights, such as one layer’s query matrix, with a shape like [576, 576]. The dtype (data type) says how each number is stored: F32, BF16 or F16.

By the end of this page you can read a safetensors header by hand, say what mmap gives a program on a phone, and convert a bf16 or f16 number to f32 in your head. The code is in src/format/safetensors.rs, src/format/mmap.rs and src/format/json.rs.

How does the file say where each tensor is?

The file has three parts. The first 8 bytes are a number N, the length of the header. The next N bytes are a JSON text that lists every tensor. Everything after that is the tensors’ bytes, packed one after another.

offset 0      8 bytes  N, a u64, little-endian
offset 8      N bytes  JSON: name, dtype, shape, data_offsets
offset 8 + N  rest     tensor bytes, packed, no padding

One entry of the header, for SmolLM2’s final norm:

{"model.norm.weight": {"dtype": "BF16",
  "shape": [576], "data_offsets": [0, 1152]}}

The header is 9,000 bytes long (N = 9000). At which byte of the file does model.norm.weight start?

  • 9,008
    Offsets count from the end of the header: 8 bytes of length plus 9,000 of JSON, plus 0.
  • 0
    0 is its offset in the data part, not in the file; the file starts with the length.
  • 9,000
    That forgets the 8 bytes that hold N before the header.
  • Offsets are relative to the data part. The tensor starts at byte 8 + N + 0 of the file. Reading from byte 0 would read the length and the JSON as if they were weights.
  • The shape gives the size. 576 numbers × 2 bytes per bf16 = 1,152 bytes calculated, which is the end offset.
  • The header is JSON, so the engine needs a JSON parser. Phase 5 writes one by hand in src/format/json.rs (about 300 lines). The same parser reads config.json and tokenizer.json.

Takeaway: a safetensors file is a length, a JSON table of contents, and packed bytes whose offsets start after the header.

A tensor has dtype F32 and shape [49152, 576]. How long should its data_offsets range be?

  • 113,246,208 bytes
    49,152 × 576 numbers × 4 bytes each.
  • 28,311,552 bytes
    That is the number of values; each f32 takes 4 bytes.
  • 56,623,104 bytes
    That is 2 bytes per number, the size in bf16, not f32.

What can a bad header do, and how is it caught?

The header is just text that someone wrote. The engine cannot trust it: a wrong offset could point past the end of the file, or two numbers could disagree with each other.

A tensor’s range is 1,000 bytes too short for its shape. What happens if the engine does not check?

  • It reads the next tensor’s bytes as the end of this one
    Packed data has no gaps, so a short range runs into its neighbour without any error.
  • The kernel crashes with an error
    Nothing marks where a tensor ends; the bytes after it are valid memory too.
  • The JSON parser rejects it
    The JSON is well formed; only the numbers inside it disagree.

So SafeTensors::open checks every entry while it reads the header, before any weight is used:

  • The range must lie inside the data part. An offset past the end would read memory the mapping does not own.
  • The range’s length must equal the product of the shape times the size of one element. A mismatch is reported with the tensor’s name.
  • The dtype must be one the engine knows (F32, BF16, F16).

The model loader then checks each shape against what config.json says it should be. Together, the two checks turn a broken file into an error at open, instead of a model that runs and writes nonsense.

Takeaway: check every offset and shape when the file opens, because a wrong one does not crash later, it just gives wrong numbers.

Why map the file instead of reading it?

The plain way to load weights is to allocate a buffer and read the whole file into it. Another way is mmap (memory mapping): ask the operating system to make the file appear as a range of addresses. Nothing is read at that moment. The first time the program touches a page (a 4 KB piece of memory), the kernel reads that piece from storage.

// SAFETY: a fresh private read-only mapping of an open
// file; the kernel checks the arguments and reports
// failure as MAP_FAILED.
let ptr = unsafe {
    libc::mmap(std::ptr::null_mut(), len, libc::PROT_READ,
        libc::MAP_PRIVATE, file.as_raw_fd(), 0)
};
  • PROT_READ makes the range read-only. A stray write crashes the program instead of changing a weight.
  • MAP_PRIVATE means no change could ever reach the file on disk.
  • The Mmap type calls munmap when it is dropped, so the mapping lives exactly as long as the tensors that borrow from it.

The phone runs low on memory. What can the kernel do with mapped weight pages that it cannot do with a heap buffer?

  • Drop them, and read them again from the file when they are next touched
    The file already holds the same bytes, so a clean mapped page costs nothing to give back.
  • Compress them
    Android may compress heap memory too; that is not the difference.
  • Nothing; both count the same
    Heap memory has no copy elsewhere, so the kernel cannot drop it, only kill the process.

That is the reason the comment in mmap.rs gives for phones. A heap copy is anonymous memory: it exists nowhere else, so under pressure Android’s low-memory killer may stop the app. A mapped file’s pages are file-backed: they can be dropped and re-read.

There is a cost. The first use of each page waits for storage. In Phase 8, the app’s first prompt after loading took 262 ms against about 200 ms once warm measured, because the first prefill touched the pages for the first time.

Inside the engine, SafeTensors::get returns a View: the dtype, the shape and a slice that points into the mapping. No bytes are copied until a caller asks for numbers.

Takeaway: mmap reads weights in place, lazily, and lets the phone drop and re-read them, at the price of a slow first touch.

The engine opens a 270 MB file with mmap and has not run a token yet. About how much of the file has been read from storage?

  • Only the pages the loader touched, such as the header
    mmap reads a page on first touch; untouched weights stay on storage.
  • All 270 MB
    That is what a plain read would do; mmap reads nothing up front.
  • None, not even the header
    Parsing the header touches its pages, so those are read.

Why is bf16 to f32 a single shift?

An f32 has 1 sign bit, 8 exponent bits (the power of two) and 23 mantissa bits (the digits). bf16 (“brain float 16”) keeps the sign, the same 8 exponent bits, and only the top 7 mantissa bits.

f32:  s eeeeeeee mmmmmmm mmmmmmmmmmmmmmmm
bf16: s eeeeeeee mmmmmmm

How do you turn the 16 bits of a bf16 into the 32 bits of an f32?

  • Put them in the top 16 bits and fill the bottom 16 with zeros
    bf16 is the top half of an f32, so the missing mantissa digits are zeros.
  • Put them in the bottom 16 bits
    That puts the sign and exponent where the mantissa goes; the value becomes tiny.
  • Re-bias the exponent, then shift
    bf16 uses f32’s own exponent bias, so nothing needs re-biasing.
pub fn bf16_to_f32(b: u16) -> f32 {
    f32::from_bits((b as u32) << 16)
}
  • Example: bf16 0x3F80 becomes 0x3F800000, which is exactly 1.0. A unit test checks this and three other values.
  • The conversion is exact: every bf16 value is also an f32 value. The rounding happened when the model was saved, not here.
  • The cost is memory. A weight takes 2 bytes in the file and 4 after widening calculated, and the widened copy is heap memory, not a mapping. Phase 6 quantizes the weights at load instead.

Takeaway: bf16 to f32 is a 16-bit shift and is exact; the price is twice the memory, in a copy the phone cannot drop.

What f32 value does the bf16 0xC000 become?

  • −2.0
    It becomes 0xC0000000: sign set, exponent one above 1.0’s, mantissa zero.
  • 2.0
    The top bit of 0xC is the sign bit, so the value is negative.
  • It cannot be known without rounding
    Widening never rounds; the low 16 bits are simply zero.

Why is f16 harder?

Some checkpoints use f16, IEEE half precision, instead. It has 1 sign bit, 5 exponent bits and 10 mantissa bits. Its exponent is stored with a bias of 15, where f32 uses 127, so the bits cannot simply be shifted into place.

let bits = match exp {
    0 if man == 0 => sign, // ±0
    // subnormal: man · 2^-24, renormalised
    0 => { /* shift the top set bit up */ }
    0x1F => sign | (0xFF << 23) | (man << 13),
    _ => sign | ((exp + 127 - 15) << 23) | (man << 13),
};
  • Normal numbers: add 127 − 15 = 112 to the exponent, and move the 10 mantissa bits to the top of f32’s 23.
  • Exponent 31 means infinity or NaN in f16, so it maps to f32’s exponent 255.
  • Subnormals, exponent 0 with a non-zero mantissa, are numbers too small for the normal form. f32 can hold them as normal numbers, so the code moves the top set bit up and lowers the exponent to match.

Every f16 value is also an f32 value, so this conversion is exact too. The unit test in safetensors.rs covers normal values, the largest finite value (65,504), the smallest and largest subnormals, infinity, NaN and negative zero.

Takeaway: f16 widens exactly as well, but its exponent must be re-biased and its smallest values renormalised.

An f16 has exponent bits 15 and mantissa 0. What f32 exponent field does it get?

  • 127, the value 1.0
    15 + 112 = 127: both are the bias, so the number is 2⁰ = 1.0.
  • 15
    Copying the field keeps f16’s bias; in f32, field 15 is a tiny number.
  • 142
    That adds 127 without subtracting f16’s own bias of 15.

mmap reads the weights in place and lets the phone drop them under pressure; the first touch of each page is slow.
