Byte-level BPE

SmolLM2’s tokenizer starts from the bytes of the text, not its characters, so no input is ever unknown. Before any merging it cuts the text into words with a regular expression, and that needs to know which characters are letters, in every script.

What are we trying to do here?

A model only understands the ids it was trained with, so the engine must split text exactly the way the model’s own tokenizer does. One different id in a prompt changes everything after it. For SmolLM2 the rules are in tokenizer.json: a vocabulary of 49,152 tokens, a list of merges, the special tokens and the pre-tokenizer settings.

Encoding takes four steps, and this page goes through them in order:

  1. Cut out the special tokens.
  2. Split the rest into words (pre-tokenization).
  3. Turn each word’s bytes into stand-in characters.
  4. Merge pairs of symbols, best rank first.

The code is src/tokenizer/bytelevel.rs, about 600 lines with its tests. By the end you can split a sentence into words by hand and apply merges in the right order.

Why start from bytes instead of characters?

Text in a file is UTF-8: each character is written as 1 to 4 bytes. English letters are 1 byte, “é” is 2, “中” is 3, and most emoji are 4. Unicode has over 150,000 characters, far more than a vocabulary of 49,152 can hold.

A character-based tokenizer meets a character that is not in its vocabulary. What can it do?

  • Replace it with an “unknown” token, losing what it was
    Without a smaller unit to fall back on, the character has no id, so its meaning is gone.
  • Split it into bytes
    Only if bytes are in its vocabulary; that is exactly the byte-level idea.
  • Nothing goes wrong; every character has an id
    No vocabulary of tens of thousands can hold every Unicode character.

A byte-level tokenizer starts from the 256 possible byte values, and all 256 are in the vocabulary. Any text, in any script, is a sequence of bytes, so it always has a starting point. Merges then join bytes into longer tokens wherever the merge list allows.

There is one problem: many byte values (space, newline, control codes) are not printable, and tokenizer.json stores tokens as text. GPT-2’s answer, which SmolLM2 inherits, is a table that gives every byte a printable stand-in character:

fn bytes_to_unicode() -> [char; 256] {
    // printable Latin-1 bytes stand for themselves;
    // the other 68 get U+0100, U+0101, ... in order
    let printable = |b: u32| (0x21..=0x7E).contains(&b)
        || (0xA1..=0xAC).contains(&b)
        || (0xAE..=0xFF).contains(&b);
    // ...
}
  • 188 bytes are printable and keep their own character, so ordinary English tokens look like English in the vocabulary.
  • The space byte, 0x20, is the 33rd non-printable one, so it becomes U+0100 + 32 = U+0120, which is Ġ. A newline becomes Ċ. That is why SmolLM2’s vocabulary has tokens like Ġthe.
  • Decoding runs the table backwards: stand-ins become bytes, bytes become text.

Takeaway: starting from the 256 bytes means every text has ids, and a fixed table makes each byte printable inside tokenizer.json.

Before any merge, how many symbols does “héllo” start as?

  • 6
    h, l, l and o are one byte each, and é is two bytes in UTF-8.
  • 5
    That counts characters; a byte-level tokenizer counts bytes.
  • 1
    That would be the result after merges, if the whole word were one token.

What happens to tokens like <|im_start|>?

Chat models mark turns with special tokens such as <|im_start|> and <|endoftext|>. Each is one id. If BPE saw them as plain text, it would split them into <, |, im and so on, and the model would never see its turn marker.

So encode searches for the special tokens first, takes the earliest one in the text (the longest, if two start at the same place), and gives it its id directly. Only the text between special tokens goes through the other three steps.

Takeaway: special tokens are cut out before anything else, so they always become their own single id.

A user types the text <|im_end|> into a chat box, and the app encodes it with special tokens on. What does the model see?

  • The real end-of-turn id, as if the turn had ended
    Matching is by string, so typed text matches too; apps that care must escape it.
  • Ordinary characters, because a user typed them
    The tokenizer does not know where text came from; it only matches strings.
  • An unknown token
    Byte-level BPE has no unknown token, and this string is in the vocabulary.

Where may a merge never cross?

If BPE ran on a whole sentence, a merge could join the end of one word to the start of the next, and the same word would get different ids depending on its neighbour. Pre-tokenization prevents that: it cuts the text into words first, and merges happen only inside a word.

The rule is GPT-2’s regular expression. At each position, the first alternative that matches wins:

's|'t|'re|'ve|'m|'ll|'d   contractions
 ?\p{L}+                  optional space, then letters
 ?\p{N}+                  optional space, then numbers
 ?[^\s\p{L}\p{N}]+        optional space, then symbols
\s+(?!\S)                 spaces not followed by text
\s+                       any other run of spaces

\p{L} means “any letter” and \p{N} “any number”, in every script. The space is glued to the front of the word after it, which is why tokens start with Ġ.

How does the regex split a␣␣␣b (three spaces)?

  • a, ␣␣, ␣b
    The space run gives up its last space, which then prefixes b as “ b”.
  • a, ␣␣␣, b
    \s+(?!\S) cannot end right before b, so the run stops one space early.
  • a, ␣, ␣, ␣b
    Whitespace runs are kept together; only the last space is split off.

The engine has no regex library; gpt2_split implements the alternatives by hand, in order. Its tests are splits checked by hand, for example:

"it's  ok!!" -> ["it", "'s", " ", " ok", "!!"]
"x\n\ny"     -> ["x", "\n", "\n", "y"]
"café 中文"  -> ["café", " 中文"]
  • Contractions match only in lowercase: 'LL is split as ' and LL.
  • SmolLM2’s tokenizer.json puts a Digits step first, with individual_digits set. Every digit becomes its own word, so “2026” is four tokens and the model sees numbers digit by digit.
  • Qwen2 (Phase 7) uses a different regex, with its own function qwen2_split. The loader reads which one a file asks for.

Takeaway: the text is cut into words first, and merges never cross a word boundary.

With SmolLM2’s settings, how is “in 1999” split into words?

  • in, ␣, 1, 9, 9, 9
    The Digits step cuts out each digit first, leaving “in ” for the regex.
  • in, ␣1999
    That is plain GPT-2; SmolLM2 splits digits off before the regex runs.
  • in, ␣1, 9, 9, 9
    The digits are cut out before the regex, so the space cannot attach to the 1.

How does the code know what a letter is?

The regex treats letters, numbers and everything else differently, in every script: “é”, “中” and “ж” are letters; “١” (Arabic one) is a number. Rust’s char::is_alphabetic is not the same set as \p{L}: it also counts some marks and symbols. A split that differs in one character gives different ids.

Where should the engine get its list of letters from?

  • From the Unicode database, generated into a table
    The regex is defined by Unicode’s categories, so the list must be Unicode’s own.
  • From Rust’s is_alphabetic
    It covers a slightly different set, so some splits would differ from Hugging Face.
  • Only A–Z and a–z
    Then “é” would split a French word in two.

tools/gen_unicode_tables.py reads Python’s unicodedata (Unicode 16.0.0) and writes src/tokenizer/unicode_tables.rs. Its LETTER table is a sorted list of 677 ranges of code points, and is_letter finds a character with a binary search:

pub fn is_letter(c: char) -> bool {
    let c = c as u32;
    LETTER.binary_search_by(|&(lo, hi)| {
        if hi < c { Less }
        else if lo > c { Greater }
        else { Equal }
    }).is_ok()
}
  • A range like (0x00C0, 0x00D6) covers À to Ö in one entry, so 677 ranges cover more than 140,000 letters.
  • The binary search takes about 10 comparisons per character.
  • The same file holds the tables for NFC normalisation, which Qwen2’s tokenizer needs in Phase 7.

Takeaway: “letter” means Unicode’s category L, so the engine generates the table from the Unicode database instead of guessing.

In what order are pairs merged?

Each word starts as one symbol per byte. The merge list in tokenizer.json is ordered: the first entry was the most common pair in the training text, and its position is its rank. Phase 2’s tokenizer picked the pair with the best score; this one picks the pair with the lowest rank.

Illustration, not SmolLM2’s real ranks

Merges: rank 0 Ġ t, rank 1 h e, rank 2 Ġt he. The word is Ġthe, starting as Ġ t h e.

With those merges, what are the steps?

  • Ġt h e, then Ġt he, then Ġthe
    Each step takes the lowest-ranked adjacent pair: rank 0, then 1, then 2.
  • Ġ t he first
    “h e” has rank 1; “Ġ t” has rank 0, so it merges first.
  • Straight to Ġthe
    Each step merges one pair of adjacent symbols; it takes three steps here.
loop {
    // the best-ranked adjacent pair, leftmost on ties
    let best = syms.windows(2).enumerate()
        .filter_map(|(i, w)| self.merges
            .get(&(w[0], w[1]))
            .map(|&(rank, id)| (rank, i, id)))
        .min();
    let Some((_, i, id)) = best else { break };
    syms[i] = id;
    syms.remove(i + 1);
}
  • merges maps a pair of ids to its rank and the id of the merged token, built once at load.
  • .min() on (rank, i, id) picks the lowest rank, and the leftmost position when the same pair appears twice.
  • The loop stops when no adjacent pair is in the list. A word with no merges stays as single bytes, which is how an unusual emoji becomes several tokens.

This is not the fastest way to do BPE: each step scans the whole word. Words are short, and the tokenizer runs once per prompt, so it does not show up next to the forward pass.

Takeaway: merges are applied one at a time, lowest rank first, and stop when no listed pair is left.

A word is a b a b, and the only merge is a b at rank 0. What is the result?

  • ab ab
    The leftmost pair merges first, then the second; there is no merge for “ab ab”.
  • abab
    That needs a merge of “ab ab”, which is not in the list.
  • ab a b
    The loop repeats until no listed pair is left, so the second “a b” merges too.
