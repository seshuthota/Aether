Built and verified

The engine now loads a real Hugging Face checkpoint, SmolLM2-135M, from its config.json, its model.safetensors file and its tokenizer.json. Every layer's activations match transformers within a relative error of 5.5e-5, the 48 greedy tokens match exactly, and 433 test strings encode and decode exactly as HF tokenizers does it. The checks pass on the host and on the phone. SmolLM2-360M is not verified yet. The detailed pages for this phase are still to write; this overview covers what was built and measured.

Phase 5 — real model files (SmolLM2)

Phases 2 to 4 ran one tiny model from one small llama2.c file. Phase 5 reads the files that Hugging Face publishes: a JSON config, a weights file in a format called safetensors, and a tokenizer described by a JSON file. The model is SmolLM2-135M. Reading these files adds three new ideas: how to map a file into memory without copying it, how a config file can decide the shape of the model, and how a byte-level tokenizer splits text. Most of the model's maths did not change.

What changed from stories15M, and why?

stories15M was a model made for llama2.c: a small file with a fixed layout, a tokenizer whose scores come from the same file, and one key/value head for each query head. SmolLM2 is a bigger model published by Hugging Face, with its own file layout and some different architecture choices. The engine could not run it until it read the new files and handled the new choices.

The SmolLM2 values come from its config.json. The stories15M values come from Phase 2 and the llama2.c loader. Each row is a choice that the code had to read or handle, not something that changes the arithmetic of one layer.

Three things were new to the engine: the file formats, the grouped-query attention, and the byte-level tokenizer. The rest of the model (RMSNorm, the matrix products, SwiGLU, the residual stream) is the code from Phases 2 to 4, with the new numbers.

Takeaway: SmolLM2 changed the file formats, the head layout and the tokenizer; the layer maths stayed the same.

How do you read a weights file without copying it?

A model file of this size is too big to read into a buffer you copy around. Hugging Face's format, safetensors, is simple enough to read in place. It starts with a length, then a JSON header that names every tensor (its data type, its shape and where its bytes sit), then the raw numbers packed one after another.

offset 0       8 bytes   N, a u64 (little-endian): the length of the header
offset 8       N bytes   JSON header: name, dtype, shape, data_offsets
offset 8 + N  rest       tensor bytes, packed, no padding; offsets count from here

An entry in the header looks like this. The numbers are the arithmetic for one tensor, the final norm of SmolLM2:

{"model.norm.weight": {"dtype": "BF16", "shape": [576],
                       "data_offsets": [0, 1152]}}
  • The shape says 576 numbers. Each bf16 number takes 2 bytes, so the data is 576 × 2 = 1152 bytes calculated.
  • The offsets are measured from the end of the header, not from the start of the file. Getting this wrong reads the header as weights.
  • The header is plain text, so the engine needs a JSON parser. Phase 5 writes one by hand, in src/format/json.rs. It handles escapes, surrogate pairs and reports where an error sits.

Now the second idea. mmap (memory mapping) asks the operating system to make a file appear in the program's address space. Nothing is read at that moment. The first time a page of the file is touched, the kernel reads it from storage. The engine maps the file read-only and privately, with one system call:

// SAFETY: a fresh private read-only mapping of an open file; the
// kernel checks the arguments and reports failure as MAP_FAILED.
let ptr = unsafe { libc::mmap(std::ptr::null_mut(), len, libc::PROT_READ, libc::MAP_PRIVATE, file.as_raw_fd(), 0) };
  • PROT_READ makes the memory read-only. A write to it crashes the program, so nothing can change the weights by accident.
  • The pages can be dropped under memory pressure and read again later. Heap memory is anonymous: the kernel cannot drop it, and on Android the low-memory killer can stop the app instead. The comment in mmap.rs makes this point for phones.
  • The mapping is the only copy. SafeTensors::get returns a slice that points into it, with no new allocation:
pub fn get(&self, name: &str) -> Option<View<'_>> {
    let info = self.info(name)?;
    Some(View { dtype: info.dtype, shape: &info.shape, bytes: &self.map.as_bytes()[info.bytes.clone()] })
}
  • View holds the dtype, the shape and a slice of bytes. No number is converted until a caller asks.
  • info.bytes was checked when the header was read: the range must lie inside the file, and its length must equal the shape times the element size. A bad file fails at open, not in the middle of a forward pass.
  • What breaks without the checks: an offset past the end of the file would read memory the mapping does not own.

Takeaway: the header says where each tensor sits, and mmap lets the engine read those bytes in place without a copy.

Why is bf16 converted to f32, and is it exact?

SmolLM2's file stores its weights in bf16 (bfloat16): 16 bits per number. The engine's kernels from Phases 2 to 4 compute in f32, 32 bits per number. A bf16 number has to be turned into an f32 before the maths can use it.

The trick is that bf16 is the top 16 bits of an f32. Both have the same sign bit and the same 8-bit exponent; bf16 keeps only 7 of the 23 mantissa bits. So converting is just putting the 16 bits back on top and filling the bottom 16 with zeros:

pub fn bf16_to_f32(b: u16) -> f32 {
    f32::from_bits((b as u32) << 16)
}
  • Example: the bf16 value 0x3F80 becomes the f32 bits 0x3F800000, which is exactly 1.0. The unit test in src/format/safetensors.rs checks this and three other values.
  • The conversion loses nothing, because every bf16 value is already an f32 value. The loss happened when the model was trained, not here.
  • f16 (IEEE half precision) is handled the same way, with its own bit layout. Every f16 value is also exactly an f32.
  • What breaks if you skip the shift: the bits are read as the wrong number, and every weight is wrong by a large factor. The model still runs, and writes nonsense.

The cost is memory. A bf16 weight takes 2 bytes in the file and 4 bytes after conversion calculated. Phase 6 later avoids the f32 copy by quantizing at load.

Takeaway: bf16 to f32 is a shift of 16 bits, and it is exact; the price is that the weights take twice the file size in memory.

How does one code path serve two model families?

The shapes of a model are not in the code. They are in config.json: the width, the number of layers, the number of heads, the vocabulary size and the RoPE base. The engine reads that file into one struct, Config, and every loop and buffer size comes from it. stories15M and SmolLM2 use the same forward pass with different numbers.

  • Hugging Face's key names differ from llama2.c's, but the loader maps them into the same struct. hidden_size becomes dim, and num_key_value_heads becomes n_kv_heads.
  • If num_key_value_heads is missing, the loader uses num_attention_heads. A config without grouping then means one key/value head per query head.
  • If lm_head.weight is missing, the classifier reuses the token embedding table. SmolLM2 sets tie_word_embeddings: true, so it has no separate classifier. The loader checks for the tensor, so it does not need to read the flag.
  • The loader checks each tensor's shape against what the config implies. A wrong shape fails with a message that names the tensor. Without this check, the engine would read the wrong bytes and produce wrong output without any error.

Two derived sizes do most of the work. They are short methods on Config:

/// Width of one attention head.
pub fn head_size(&self) -> usize {
    self.dim / self.n_heads
}

/// How many query heads share each K/V head.
pub fn kv_group(&self) -> usize {
    self.n_heads / self.n_kv_heads
}
  • For SmolLM2, head_size is 576 ÷ 9 = 64 calculated.
  • kv_group is 9 ÷ 3 = 3 for SmolLM2 and 6 ÷ 6 = 1 for stories15M calculated. The attention code uses this one number, and never asks which model it is running.

Takeaway: the config file gives the shapes, and one code path reads them; a second model needs a new config, not new maths.

Why do 9 query heads share 3 key/value heads?

Each token's key and value vectors are kept in the KV cache from Phase 2, for every layer and every position. The cache grows with the number of key/value heads. Phase 2 gave every query head its own key/value head, so the cache held one pair per query head. Grouped-query attention (GQA) lets several query heads read the same key/value head. The cache then shrinks by the size of the group.

query heads:   q0  q1  q2  |  q3  q4  q5  |  q6  q7  q8
                 \  |  /       \  |  /       \  |  /
kv heads:           kv0           kv1           kv2

Query head h reads key/value head h / kv_group, with integer division. Head 7 is 7 ÷ 3 = 2, so it reads kv2, the same keys and values as heads 6 and 8. The forward pass uses this one formula for every model: with a group of 1, it is just head h.

What the sharing saves, for SmolLM2 with the full 8192-position cache that the model allows:

  • The key/value width is 3 × 64 = 192 numbers per token, against 9 × 64 = 576 with one head per query head calculated.
  • The cache in f32 is 30 layers × 8192 positions × 192 numbers × 2 (keys and values) × 4 bytes = 377 MB calculated. With one head per query head it would be three times that, about 1.13 GB calculated.
  • The loader sizes the cache to the smaller of the model's limit and the max_seq the caller asks for, so a short run uses less.
Easy to get wrong

The query heads of one group must read the same key/value head. A wrong group size, or a loop that reads h instead of h / kv_group, does not crash. It gives a model that writes fluent but wrong text, because each query compares itself with the wrong keys.

Takeaway: GQA saves cache memory by reusing key/value heads, and SmolLM2's 9-to-3 layout cuts the cache to a third.

Which pairs does RoPE rotate?

Phase 2 explained RoPE: each pair of numbers in a head is rotated by an angle that depends on the token's position, so attention can tell how far apart two tokens are. The rotation is the same in both families. The difference is which two numbers form a pair. There are two common layouts, and a model must be run with the one it was trained with.

llama2.c (adjacent):   (0,1)  (2,3)  (4,5)  ...  (62,63)
Hugging Face (halves): (0,32) (1,33) (2,34) ...  (31,63)

The pairs above are for a head of 64 numbers, as in SmolLM2 calculated. The rotation of pair i uses the angle pos × θ^(−2i/head_size), with θ = 100,000 for SmolLM2 from its config (stories15M uses 10,000). Here is the halves version from src/kernels/scalar.rs, shortened:

pub fn rope_halves(v: &mut [f32], pos: usize, head_size: usize, theta: f32) {
    let half = head_size / 2;
    for head in v.chunks_exact_mut(head_size) {
        for i in 0..half {
            let freq = 1.0 / theta.powf((2 * i) as f32 / head_size as f32);
            let angle = pos as f32 * freq;
            let (sin, cos) = (angle.sin(), angle.cos());
            let (v0, v1) = (head[i], head[i + half]);
            head[i] = v0 * cos - v1 * sin;
            head[i + half] = v0 * sin + v1 * cos;
        }
    }
}
  • The loop runs over half the head. Each step takes element i and element i + half, the two halves of the head.
  • The angle is the same formula as the adjacent version. Only the indices differ.
  • The engine has both functions, rope_adjacent and rope_halves. The loader sets the halves layout for Hugging Face checkpoints. GGUF files from llama.cpp use the adjacent layout, because the converter permutes the query and key weights when it writes them.
  • What breaks: mixing the two layouts still runs and writes garbage. There is no crash to point at, so the check that catches it is the comparison with transformers below.

If you want the rotation itself again, read RoPE: position as rotation. That page explains the adjacent layout, which llama2.c uses.

Takeaway: the rotation is the same in both layouts, but the pairs are not, so the layout must match how the weights were saved.

How does a byte-level tokenizer turn text into ids?

Phase 2's tokenizer started from characters and merged the pairs with the best score. SmolLM2's tokenizer is byte-level BPE: it starts from the UTF-8 bytes of the text, not from characters, and it applies merges by their rank in a list. Its rules are in tokenizer.json. The engine reads them in src/tokenizer/bytelevel.rs, in four steps:

  1. Special tokens such as <|im_start|> are cut out first and become their ids directly.
  2. Pre-tokenization splits the text into words that BPE never merges across. SmolLM2 splits every digit on its own, then applies GPT-2's regular expression for contractions, words, numbers, symbols and whitespace. The engine implements that regex by hand.
  3. Byte-level mapping turns each word's bytes into printable stand-in characters. A space becomes Ġ, a newline becomes Ċ.
  4. BPE starts with one symbol per byte and repeatedly merges the adjacent pair with the lowest rank in the merge list, until no listed pair is left.

Step 3 is why nothing is unknown. Every one of the 256 byte values gets its own stand-in character, so any text, including emoji, has an id to start from:

fn bytes_to_unicode() -> [char; 256] {
    // printable Latin-1 bytes map to themselves; the rest to U+0100 onward
    let printable = |b: u32| (0x21..=0x7E).contains(&b) || (0xA1..=0xAC).contains(&b) || (0xAE..=0xFF).contains(&b);
    // ... fills table[b] with the printable char, or 255 + extra for the others
}
  • The table is GPT-2's. Its printable bytes keep their own letters, which is why ordinary English looks normal in the vocabulary.
  • Merges use rank, not score. Phase 2's tokenizer ranked pairs by a score stored with each token. SmolLM2's list says which pair merges first, so a lower rank wins.
  • What breaks if you skip step 2: BPE would merge across word boundaries, and the same word would get different ids in different positions.
Illustration, not a measurement

Take the text “Hello 👋”. The emoji is four UTF-8 bytes, so step 1 starts it with four symbols. Only the merges in the list can join them, and only as far as the list allows. Several tokens for one emoji is normal for byte-level BPE, and it is not an error.

The tokenizer's decode step runs the mapping backwards: it joins the stand-in characters and turns them back into bytes, then into text.

Takeaway: byte-level BPE starts from bytes, so no input is unknown, and merges are applied by rank in the file's own list.

How do you know it matches Hugging Face?

The reference is Hugging Face transformers for the model and tokenizers for the tokenizer. tools/hf_dump.py runs both on a fixed prompt and writes the results to files the engine can read with its own parser. It records the output of each layer with forward hooks, runs greedy generation, and encodes a corpus of test strings. The model runs in f32 with eager attention, so the only differences left are the order of additions.

The totals are 85 of 85 tests passing on 2026-10-22, on the host and on the phone measured.

Why a tolerance and not exact equality for the layers? Hugging Face adds the numbers of a matrix product in a different order from ours, and f32 addition is not associative. So the layers differ in the last few bits. The greedy tokens are still compared for exact equality, and they match. The tokenizer has no maths to reorder, so it must match exactly.

The gotcha

Greedy generation in transformers still applies a repetition penalty if generation_config.json sets one. Qwen2.5-Instruct sets 1.05 there. tools/hf_dump.py passes repetition_penalty=1.0 so the reference matches the engine's greedy decoding. SmolLM2's generation_config.json sets only the special token ids. If the reference and the engine disagree on tokens, check the generation settings before the code.

The method is the one from Bit-identical with llama2.c, now against a second reference.

Takeaway: the layers are compared to a tolerance because the order of additions differs, and the tokens and the tokenizer must match exactly.

How fast is it?

Phase 5 adds no speed of its own: the loader runs once, and the decode loop is the one from Phase 4. The speeds below are for SmolLM2-135M in Q4_0, a 4-bit format that Phase 6 explains. They come from the clean Phase 4 sweep, on battery, at about 2.4 GHz. The Phase 4 page explains the thread work behind them.

about 160 tok/sdecode, core 7 alone (a prime core), two passes measured
326 and 343 tok/sdecode on cores 2–7, the two passes of the same set measured
310 and 341 tok/sdecode on all eight cores, the two passes; no faster than 2–7 measured

Those numbers are a summary of results/phase-4.md. Two passes of one set can differ by 10 % or more, so the gap between the top sets is inside the noise. Read the numbers as "about 330 tokens per second on six cores", not as a precise figure.

Takeaway: SmolLM2 Q4_0 decodes at about 330 tokens per second on cores 2–7 on this phone, and the thread work, not the loader, set that speed.

What is still open?

Three things are not settled by Phase 5. Each one is a task, not a result.

  • SmolLM2-360M (item 5.6 in IMPLEMENTATION.md) uses the same code path, but it has not been checked against transformers. The check is the same as for 135M: every layer, the greedy tokens and the tokenizer corpus.
  • First-touch cost: the first use of a mapped page reads it from storage, so the first answer after launch can be slower. Phase 5 does not measure that; the app that uses the engine is covered in Phase 8.
  • The f32 copy: converting the weights at load doubles their size in memory. Phase 6 quantizes them instead.

Takeaway: the 360M check is the one gap in the verification; the other two are costs that later phases take on.

Check yourself

Why does the engine read the shapes from config.json instead of writing them into the code?

Because the same forward pass serves stories15M and SmolLM2, which differ in width, layer count, head count and vocabulary. The config gives those numbers, and the code uses them everywhere. A new model then needs a new config, not new maths.

If you use the adjacent RoPE layout on a Hugging Face checkpoint, what do you see?

The program runs and produces text, but the text is wrong. Nothing crashes, because the rotation is the same and only the pairs differ. The comparison with transformers is what catches it.

SmolLM2 has 9 query heads and 3 key/value heads. Which key/value head does query head 7 read?

Head 2, because 7 ÷ 3 = 2 with integer division. Query heads 6, 7 and 8 all read it.

Why are the layers compared with a tolerance, but the tokens with exact equality?

The layers are floating-point sums, and the order of additions differs from transformers, so the last bits differ. The tokens and the tokenizer are discrete: an id is either the same or it is not.

What you should take away

A Hugging Face model is a config file, a safetensors file and a tokenizer file. The engine reads each with a small parser, maps the weights without copying them, and uses the config for every shape.

SmolLM2 needed three new ideas: grouped-query attention, the rotate-half layout of RoPE, and a byte-level tokenizer. Each one is checked against Hugging Face, not against our own code.

SmolLM2-360M is the one model in this family that is not yet verified.

Phase 5 numbers were measured on the iQOO 13 (SM8750) in October 2026 unless tagged otherwise; the decode speeds are from the Phase 4 sweep on battery. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
