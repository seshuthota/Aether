One forward pass, two families

stories15M and SmolLM2 differ in width, depth, head layout and the way RoPE pairs numbers. None of that is written into the code. A config file gives the numbers, and the same forward pass runs both.

What are we trying to do here?

Phase 2 ran one model, stories15M, and its numbers came from the header of the llama2.c file. Phase 5 adds SmolLM2-135M from Hugging Face. Its layers do the same maths (RMSNorm, attention, SwiGLU), but almost every size is different, and two choices are new: several query heads share one key/value head, and RoPE pairs the numbers of a head differently.

The goal is one forward pass that reads all of this from data. By the end of the page you can read a config.json, say which key/value head a query head reads, and name the RoPE pairs for a head of any width. The code is src/model/config.rs and src/model/hf.rs.

Where do the model’s shapes come from?

A Hugging Face model ships a config.json next to its weights. The engine reads it into one struct, Config, and every loop bound and buffer size in the forward pass comes from that struct.

"hidden_size": 576          -> dim
"intermediate_size": 1536   -> hidden_dim
"num_hidden_layers": 30     -> n_layers
"num_attention_heads": 9    -> n_heads
"num_key_value_heads": 3    -> n_kv_heads
"max_position_embeddings"   -> seq_len (capped)
"rope_theta": 100000        -> rope_theta

A config has no num_key_value_heads key. What should the loader assume?

  • One key/value head per query head
    Without the key, the model was built the classic way, as in Phase 2.
  • One key/value head for all query heads
    That layout exists, but a missing key does not announce it.
  • The file is broken and must be rejected
    Older configs simply leave it out; rejecting them would refuse working models.
  • The loader uses num_attention_heads when num_key_value_heads is missing, and defaults rope_theta to 10,000 and rms_norm_eps to 1e-5 when those are missing.
  • seq_len is the smaller of the model’s limit (8,192 for SmolLM2) and the max_seq the caller asks for, so a short run allocates a short KV cache.
  • Two sizes are derived, not read: head_size = dim / n_heads (576 ÷ 9 = 64) and kv_group = n_heads / n_kv_heads (9 ÷ 3 = 3) calculated.
  • Every weight’s shape is checked against the config. A mismatch fails at load with the tensor’s name, not later as wrong text.

Takeaway: the shapes live in config.json, and a new model of the same kind needs a new config, not new code.

Qwen2.5-0.5B has hidden_size 896 and 14 attention heads. What is its head width?

  • 64
    896 ÷ 14 = 64, the same head width as SmolLM2.
  • 896
    That is the whole vector; it is split across the 14 heads.
  • It must be read from the config
    The engine derives it as dim ÷ n_heads; there is no separate key for it.

Why does SmolLM2 have no classifier matrix?

The first step of the model looks a token up in the embedding table, one row of 576 numbers per token id. The last step, the classifier, multiplies the final vector by a [vocabulary × width] matrix to score every token. The two matrices have the same shape.

SmolLM2’s file has no lm_head.weight. What does the engine use as the classifier?

  • The embedding table itself
    The model was trained with one shared matrix for both jobs, called tied embeddings.
  • A matrix of zeros
    Every token would score 0; the model could not choose anything.
  • Its transpose, copied at load
    The same [vocab, dim] layout serves both, so no copy or transpose is needed.

SmolLM2 sets "tie_word_embeddings": true: one matrix does both jobs. The loader does not read the flag. It looks for the tensor, and if lm_head.weight is absent the classifier reuses the embedding table.

  • Sharing saves 49,152 × 576 ≈ 28.3 million numbers calculated, about a fifth of the 135 million.
  • A row of the table is one token’s embedding; the same row, used in a dot product, is that token’s score. So the classifier asks “how close is the final vector to each token’s embedding?”

Takeaway: a tied model uses its embedding table as the classifier, so the loader checks for the tensor instead of trusting a flag.

How can 9 query heads share 3 key/value heads?

Attention keeps every past token’s keys and values in the KV cache, for every layer. In Phase 2 each query head had its own key/value head. Grouped-query attention (GQA) lets a group of query heads read the same key/value head, so the cache holds fewer of them.

query:  q0 q1 q2 | q3 q4 q5 | q6 q7 q8
           \|/        \|/        \|/
kv:        kv0        kv1        kv2

With 9 query heads and 3 key/value heads, which key/value head does query head 5 read?

  • kv1
    5 ÷ 3 = 1 with integer division: heads 3, 4 and 5 form the second group.
  • kv2
    That is 5 mod 3; groups are consecutive heads, not every third head.
  • kv5
    There is no kv5; only 3 key/value heads exist.

The rule in the attention loop is kv_head = h / kv_group. For stories15M the group is 1 and the rule gives back h, so the same line serves both models.

  • The key/value width per token is 3 × 64 = 192 numbers, against 9 × 64 = 576 without sharing calculated.
  • At SmolLM2’s full 8,192 positions in f32, the cache is 30 layers × 8,192 × 192 × 2 (keys and values) × 4 bytes ≈ 377 MB calculated; without GQA it would be about 1.13 GB.
  • The k and v matrices shrink with it: [192, 576] instead of [576, 576].

Getting the group wrong does not reliably crash. A loop that reads head h instead of h / kv_group reads past the three heads of a position into the next position’s keys; a wrong group size pairs queries with the wrong keys. Either way the model writes fluent nonsense, and the comparison with transformers is what catches it.

Takeaway: GQA makes query heads in a group share one key/value head, and the cache shrinks by the group size.

Qwen2.5-0.5B has 14 query heads and 2 key/value heads. What is its group size, and which key/value head does query head 9 read?

  • 7, and kv1
    14 ÷ 2 = 7; 9 ÷ 7 = 1, so heads 7 to 13 read kv1.
  • 2, and kv4
    That divides by the number of key/value heads, not by the group size.
  • 7, and kv2
    There are only kv0 and kv1; integer division rounds 9 ÷ 7 down to 1.

Which two numbers does RoPE rotate together?

RoPE rotates each pair of numbers in a head by an angle that grows with the token’s position. Pair i uses the angle pos × θ^(−2i / head_size). A head of 64 numbers has 32 pairs. Which two numbers make up pair i is a choice, made once when the model was trained.

A Hugging Face checkpoint is run with llama2.c’s adjacent pairs instead of its own layout. What happens?

  • It runs and writes wrong text
    The rotation is valid maths on the wrong pairs; nothing checks which pairing the weights expect.
  • It crashes on an index error
    Both layouts touch the same 64 numbers, so no index goes out of range.
  • Nothing changes; the layouts are equivalent
    They give the same result only if the q and k weights are permuted to match.
adjacent (llama2.c): (0,1) (2,3) ... (62,63)
halves (HF):         (0,32) (1,33) ... (31,63)

The halves version, from src/kernels/scalar.rs, shortened to one head:

let half = head_size / 2;
for i in 0..half {
    let freq = 1.0
        / theta.powf((2 * i) as f32 / head_size as f32);
    let angle = pos as f32 * freq;
    let (sin, cos) = (angle.sin(), angle.cos());
    let (v0, v1) = (head[i], head[i + half]);
    head[i] = v0 * cos - v1 * sin;
    head[i + half] = v0 * sin + v1 * cos;
}
  • The angle formula is the same as in rope_adjacent; only the indices i and i + half differ.
  • Config holds a RopeLayout: AdjacentPairs for llama2.c and Llama-type GGUF files, Halves for Hugging Face checkpoints and Qwen2 GGUF files.
  • The two layouts are related by a fixed reordering of each head’s numbers. llama.cpp’s converter applies it to the q and k weights of Llama-type models, which is why those GGUF files use adjacent pairs.

Takeaway: the rotation is the same in both layouts, but the pairs are not, so the engine must use the layout the weights were saved for.

In the halves layout, a head has 128 numbers. Which number is rotated together with number 10?

  • Number 74
    half = 64, so element 10 pairs with 10 + 64.
  • Number 11
    That is the adjacent layout’s pair.
  • Number 42
    That uses a half of 32, the value for a 64-wide head.

What you should take away

The model’s shapes come from config.json, and every loop reads them from one struct.

Grouped-query attention shares key/value heads: head h reads h / group, and the cache shrinks by the group size.

RoPE’s pairs depend on how the weights were saved; a wrong layout runs without error and writes wrong text.
