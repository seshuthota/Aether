Multiplying quantized weights: sdot and smmla

A matrix-vector product is one dot product per output row: the row's weights against the activation vector. Quantized weights make the rows smaller to read. The kernels still have to multiply them, and how they multiply depends on how the activation is stored. The last step is a matrix instruction, smmla, that serves two tokens at once for prefill.

Why do the weights need their own multiply?

Decode reads every weight once per generated token. The fewer bytes each weight takes, the less memory is read. A quantized format stores a small integer per weight and one shared scale per block of 32 weights. A block is 32 consecutive weights that share one scale d. The real weight is d × q, where q is the stored integer.

Two formats matter here. Q8_0 stores 32 int8 values (one signed byte each) plus one f16 scale: 34 bytes per block, which is calculated 8.5 bits per weight. Q4_0 packs two 4-bit values into each byte, plus the same f16 scale: 18 bytes per block, calculated 4.5 bits per weight.

Illustration (not a measurement): a block with d = 0.5 and stored values 3 and −2 holds the weights 1.5 and −1.0. The multiply has to produce the same answer as if those floats were used, but without turning every weight back into a float first.

Takeaway: the scale is shared by 32 weights, so a kernel can do integer work for a block and apply the scale once.

Option a: turn the weights back into floats

The simple route is style a. Widen each int8 weight to an f32, multiply by the f32 activation, and add up. This is dot_q8_0_f32 in src/kernels/neon_quant.rs. A register here is one 128-bit NEON vector: it holds 16 bytes, 8 halves, or 4 floats.

/// (a) Q8_0 row · f32 x.
pub fn dot_q8_0_f32(row: &[BlockQ8_0], x: &[f32]) -> f32 {
    assert_eq!(x.len(), row.len() * QK);
    // SAFETY: register-only NEON op (AArch64 baseline).
    let mut acc = unsafe { vdupq_n_f32(0.0) };
    for (blk, xs) in row.iter().zip(x.as_chunks::<QK>().0) {
        // SAFETY: each block holds 32 int8s; `xs` holds 32 floats.
        unsafe {
            let q0 = vld1q_s8(blk.qs.as_ptr());
            let q1 = vld1q_s8(blk.qs.as_ptr().add(16));
            let s = fma16(fma16(vdupq_n_f32(0.0), q0, xs.as_ptr()), q1, xs.as_ptr().add(16));
            acc = vfmaq_n_f32(acc, s, f16_to_f32(blk.d));
        }
    }
    // SAFETY: register-only NEON op.
    unsafe { vaddvq_f32(acc) }
}
  • fma16 handles 16 weights. It calls widen8 on each 8-byte half, which widens int8 to int16, then int32, then f32: three steps per 8 values, as the module doc says.
  • vfmaq_f32(acc, a, b) is a fused multiply-add (FMA): it computes acc + a × b for four floats in one instruction.
  • vfmaq_n_f32(acc, s, f16_to_f32(blk.d)) multiplies the block's sum by its scale once, not once per weight.
  • The loop reads the activation as f32, so every weight pays for a widen, a convert and a 4-lane FMA. The integer units do not do the work.

The phase-6 measurement shows the cost: the decode GEMV with this style ran at 12 GB/s measured.

Takeaway: style a is correct, but every weight goes through three widening steps and a float multiply.

Option b: quantize the activation too

The weights are integers and the activation is f32. Mixing them forces a conversion for every value. Style b removes that by quantizing the activation to Q8_0 as well, once per call. quantize_activation in src/kernels/mod.rs does it:

/// Quantizes one activation vector (a multiple of 32 long) to Q8_0 for the
/// integer dot-product kernels.
fn quantize_activation(x: &[f32]) -> Vec<BlockQ8_0> {
    let mut q = vec![BlockQ8_0 { d: 0, qs: [0; QK] }; x.len() / QK];
    crate::quant::quantize_q8_0(x, &mut q);
    q
}

In linear_batch_on the quantized activation is built once, and its scales are converted to f32 once too:

let xq: Vec<BlockQ8_0> = x.chunks_exact(n).flat_map(quantize_activation).collect();
// The activation's scales as f32, converted once rather than per row.
let xd: Vec<f32> = xq.iter().map(|b| crate::quant::f16_to_f32(b.d)).collect();
  • Quantizing costs one pass over the activation. Every output row then reuses it, so the cost is paid once per call, not once per row.
  • Both operands are now int8, so one instruction can multiply them directly.
  • If the activation were left as f32, the integer weights would need converting first, and the advantage of integer math would be lost.

The sdot instruction

sdot (Rust name vdotq_s32, from the dotprod extension) takes two registers of 16 int8 values. It multiplies them pair by pair, sums the products in groups of four, and writes four int32 numbers. Each of those four numbers is a lane: one 32-bit slot of the register.

weight bytes:  w0  w1  w2  w3 | w4  w5  w6  w7 | w8  w9  w10 w11 | w12 w13 w14 w15
activ. bytes:  x0  x1  x2  x3 | x4  x5  x6  x7 | x8  x9  x10 x11 | x12 x13 x14 x15
                  |                |                 |                 |
result lanes:  lane0            lane1             lane2             lane3
               = w0x0+w1x1      = w4x4+w5x5       = w8x8+w9x9       = w12x12+w13x13
                 +w2x2+w3x3       +w6x6+w7x7        +w10x10+w11x11    +w14x14+w15x15
  • One sdot does 16 multiplications and sums them into four lanes. That is 16 weights against 16 activations.
  • The four results are four separate int32 numbers. They are added together only at the end (vaddvq_f32).
  • The sums are exact. Each int8 product is at most 128 × 128 = 16,384 in size calculated. Thirty-two of them add to at most 524,288, which fits an int32 with no rounding. Only the int-to-float conversion and the scale multiply round.

One block: two sdot and one FMA

let block = |w: &BlockQ8_0, v: &BlockQ8_0| -> (float32x4_t, f32) {
    // SAFETY: each block holds 32 int8s.
    unsafe {
        let z = vdupq_n_s32(0);
        let d = vdotq_s32(vdotq_s32(z, vld1q_s8(w.qs.as_ptr()), vld1q_s8(v.qs.as_ptr())), vld1q_s8(w.qs.as_ptr().add(16)), vld1q_s8(v.qs.as_ptr().add(16)));
        (vcvtq_f32_s32(d), f16_to_f32(w.d) * f16_to_f32(v.d))
    }
};
  • Two vdotq_s32 calls cover the 32 values of the block. The first adds into a zero accumulator, the second adds into the first's result.
  • vcvtq_f32_s32 converts the four int32 lanes to floats: the only conversion in the block.
  • The closure returns the lanes and the scale d_w × d_x. The caller then does vfmaq_n_f32(acc0, s0, d0): one FMA by that scale, on all four lanes.
  • Blocks alternate between acc0 and acc1, so consecutive FMAs do not wait for each other. This is the same idea as the f32 GEMV.
  • If the scale is left out, every block is wrong by its own factor, and the sum is wrong even when the integers are right.

Q4_0 needs a nibble unpack first

A Q4_0 weight is 4 bits, and sdot needs bytes. Each byte of qs holds two values: element j in the low nibble and element j + 16 in the high nibble. unpack_q4 turns 16 bytes into two int8 vectors of 16 values each, in the range −8 to 7:

/// Q4_0 nibbles of one block → its 32 weights as int8 in −8..=7:
/// (elements 0..16, elements 16..32).
#[inline(always)]
fn unpack_q4(qs: uint8x16_t) -> (int8x16_t, int8x16_t) {
    // SAFETY: register-only NEON ops; NEON is part of the AArch64 baseline.
    unsafe {
        let eight = vdupq_n_s8(8);
        let lo = vreinterpretq_s8_u8(vandq_u8(qs, vdupq_n_u8(0x0F)));
        let hi = vreinterpretq_s8_u8(vshrq_n_u8(qs, 4));
        (vsubq_s8(lo, eight), vsubq_s8(hi, eight))
    }
}
  • vandq_u8(qs, 0x0F) keeps the low nibble of each byte. vshrq_n_u8(qs, 4) shifts the high nibble down.
  • vsubq_s8(…, eight) turns 0..15 into −8..7. Without it the sum is off by 8 times the sum of the activation values in the block.
  • Per 32 weights the Q4_0 kernel adds one AND, one shift and two subtracts before its two sdots. Q8_0 needs none of these.

Q4_0 moves fewer bytes than Q8_0, but it spends more instructions per weight. On one core the instructions run out before memory does. That is why Q4_0 stays compute-bound on one core at 12–15 GB/s, while Q8_0 reached 32 GB/s measured.

Takeaway: quantizing the activation once turns the work into int8 multiplies, and the scale is applied once per block.

What changes with many tokens?

Prefill runs the whole prompt through the model, so a matrix-vector product becomes a matrix-matrix product: t activation vectors, one per token. A 512-token prompt has 512 of them, and each one is multiplied by every weight row.

Before the smmla change, the code handled each token in turn. Here is the fallback loop in quant_rows, shortened:

let nb = xq.len() / t;
let fast = has_dot4();
let mut i = r.start;
while i < r.end {
    let step = if fast && i + 4 <= r.end { 4 } else { 1 };
    for tt in 0..t {
        let (x, s) = (&xq[tt * nb..(tt + 1) * nb], &xd[tt * nb..(tt + 1) * nb]);
        if step == 4 {
            let v = dot4(w, i, x, s);
            // ...
        } else {
            // ...
        }
    }
    i += step;
}
  • For each group of four rows, the inner loop runs once per token. The same weight blocks are loaded and unpacked again for each token. They come from L1 cache, not from main memory, but the work is repeated.
  • For Q4_0 that repeats the nibble unpack for every token.
  • The loop computes correct results. Its cost is that each weight is handled t times.

Takeaway: with t tokens the old loop does the weight work t times. The next step is to use each loaded weight for more than one token.

How does smmla work, and why is it written in asm?

smmla is a matrix instruction from the i8mm extension. It treats each 16-byte register as a 2 × 8 matrix of int8 values. Its comment in src/kernels/neon_quant.rs gives the layout:

// `smmla d, a, b` treats each 16-byte register as a 2×8 int8 matrix (bytes
// 0..8 are row 0, 8..16 row 1) and adds a · bᵀ, a 2×2 int32 matrix, to d:
//
//     a = [w0 k0..8 | w1 k0..8]      d.lane0 += w0·x0    d.lane1 += w0·x1
//     b = [x0 k0..8 | x1 k0..8]      d.lane2 += w1·x0    d.lane3 += w1·x1
//
// So each weight value loaded serves two tokens, where `sdot` serves one.

As a text diagram, with two weight rows (w0, w1) and two tokens (x0, x1):

        register a (weights)                   register b (tokens)
  [ w0: k0 .. k7 | w1: k0 .. k7 ]        [ x0: k0 .. k7 | x1: k0 .. k7 ]

  accumulator d, a 2 × 2 grid of int32:
                       token x0                  token x1
      row w0     lane 0: w0·x0            lane 1: w0·x1
      row w1     lane 2: w1·x0            lane 3: w1·x1

  one smmla = 2 rows × 2 tokens × 8 values = 32 multiplications
  • One smmla gives four outputs (2 rows × 2 tokens). One sdot works on one row and one token.
  • Each weight loaded for a smmla is used for two tokens. With sdot it is used for one.
  • The two rows and two tokens must be laid out in the register first: bytes 0..8 of a must be row 0 and bytes 8..16 row 1. The register does not do that itself.

Step 1: interleave two registers

The layout is made with zip8. It interleaves two vectors 8 bytes at a time, using two 64-bit zips:

/// Interleaves two 16-byte vectors 8 bytes at a time:
/// `([a0..8 | b0..8], [a8..16 | b8..16])`.
#[inline(always)]
fn zip8(a: int8x16_t, b: int8x16_t) -> (int8x16_t, int8x16_t) {
    // SAFETY: register-only NEON ops.
    unsafe {
        let (a, b) = (vreinterpretq_s64_s8(a), vreinterpretq_s64_s8(b));
        (vreinterpretq_s8_s64(vzip1q_s64(a, b)), vreinterpretq_s8_s64(vzip2q_s64(a, b)))
    }
}
  • The registers are reinterpreted as two 64-bit halves. vzip1q_s64 takes the low halves of a and b; vzip2q_s64 takes the high halves.
  • The result is a pair of registers, each holding one row's 8 bytes followed by the other row's 8 bytes.
  • The interleave costs instructions. Keeping it cheap is the open problem in the last section.

Step 2: one 32-value block

A 32-value block is two 16-byte vectors per row and per token. mmla_block zips each pair of rows (and of tokens) into interleaved registers, then runs four smmla in two chains:

fn mmla_block(w0: [int8x16_t; 2], w1: [int8x16_t; 2], x0: [int8x16_t; 2], x1: [int8x16_t; 2]) -> int32x4_t {
    let ((wa, wb), (wc, wd)) = (zip8(w0[0], w1[0]), zip8(w0[1], w1[1]));
    let ((xa, xb), (xc, xd)) = (zip8(x0[0], x1[0]), zip8(x0[1], x1[1]));
    // SAFETY: register-only NEON op.
    let z = unsafe { vdupq_n_s32(0) };
    // Two independent chains, so each `smmla` need not wait for the last.
    // SAFETY: register-only NEON op.
    unsafe { vaddq_s32(smmla(smmla(z, wa, xa), wb, xb), smmla(smmla(z, wc, xc), wd, xd)) }
}
  • Eight zip instructions prepare the operands for one block. Four smmla do the multiplies.
  • The result is [w0·x0, w0·x1, w1·x0, w1·x1] summed over 32 values, as exact int32.
  • Skipping the interleave gives the wrong pairs: a row's bytes would be multiplied against the other row's bytes.

Step 3: the smmla wrapper, and why it is asm

/// `d + a · bᵀ` for 2×8 int8 matrices `a`, `b` (see above). Written with
/// `asm!` because the `vmmlaq_s32` intrinsic is not stable on Rust 1.99.
/// Only call it from a `#[target_feature(enable = "i8mm")]` function, so the
/// assembler accepts the instruction once inlined.
#[inline(always)]
fn smmla(d: int32x4_t, a: int8x16_t, b: int8x16_t) -> int32x4_t {
    let mut r = d;
    // SAFETY: a register-only multiply-accumulate; touches no memory. The
    // caller runs only where i8mm is present.
    unsafe { std::arch::asm!("smmla {0:v}.4s, {1:v}.16b, {2:v}.16b", inout(vreg) r, in(vreg) a, in(vreg) b, options(pure, nomem, nostack)) };
    r
}
  • The normal route is the vmmlaq_s32 intrinsic. The code comment says it is not stable on the toolchain it targets, so the instruction is written by hand.
  • asm! lets Rust name the registers. inout(vreg) is the accumulator, read and written; in(vreg) is an input register.
  • options(pure, nomem, nostack) tells the compiler the block reads and writes no memory and uses no stack. It can then move or repeat it freely.
  • The function is not marked unsafe, but it may only be called where i8mm exists. Without i8mm, the CPU faults on the instruction.
  • Callers check the CPU at run time with has_i8mm(), which calls is_aarch64_feature_detected!("i8mm"), and mark their function #[target_feature(enable = "i8mm")].

Step 4: the 2 × 2 kernel in full

mmla2 computes two rows against two tokens over a whole row. It is generic over the block type, so Q8_0 and Q4_0 share it. Its load argument gives the 32 values of a block as two int8 vectors, plus the f16 scale:

#[target_feature(enable = "i8mm")]
unsafe fn mmla2<B>(rows: [&[B]; 2], x: [&[BlockQ8_0]; 2], xd: [&[f32]; 2], load: impl Fn(&B) -> ([int8x16_t; 2], u16)) -> [f32; 4] {
    // SAFETY: register-only NEON op (AArch64 baseline).
    let mut acc = unsafe { [vdupq_n_f32(0.0); 2] };
    let act = |v: &BlockQ8_0| {
        // SAFETY: each block holds 32 int8s.
        unsafe { [vld1q_s8(v.qs.as_ptr()), vld1q_s8(v.qs.as_ptr().add(16))] }
    };
    for b in 0..x[0].len() {
        // SAFETY: the caller guarantees every slice has at least b + 1
        // entries.
        unsafe {
            let ((w0, d0), (w1, d1)) = (load(rows[0].get_unchecked(b)), load(rows[1].get_unchecked(b)));
            let s = mmla_block(w0, w1, act(x[0].get_unchecked(b)), act(x[1].get_unchecked(b)));
            let (dx0, dx1) = (*xd[0].get_unchecked(b), *xd[1].get_unchecked(b));
            let scales = vmulq_f32(f16x4_to_f32([d0, d0, d1, d1]), vld1q_f32([dx0, dx1, dx0, dx1].as_ptr()));
            // Even and odd blocks into separate accumulators (as in the
            // `sdot` kernels), so consecutive FMAs do not wait on each other.
            acc[b & 1] = vfmaq_f32(acc[b & 1], vcvtq_f32_s32(s), scales);
        }
    }
    let mut out = [0.0; 4];
    // SAFETY: `out` holds 4 floats.
    unsafe { vst1q_f32(out.as_mut_ptr(), vaddq_f32(acc[0], acc[1])) };
    out
}
  • The loop goes block by block. Each block gives four int32 sums, one per (row, token) pair.
  • scales holds d_w0 · d_x0, d_w0 · d_x1, d_w1 · d_x0, d_w1 · d_x1 in the same lane order as the sums, so one FMA covers all four outputs.
  • Even and odd blocks go to acc[0] and acc[1], as in the sdot kernels.
  • The caller must give slices of equal length. The get_unchecked calls skip bounds checks, so a short slice is undefined behaviour. The unsafe fn marks that promise.

The two public wrappers choose the block format:

#[target_feature(enable = "i8mm")]
pub unsafe fn mmla2_q8_0(rows: [&[BlockQ8_0]; 2], x: [&[BlockQ8_0]; 2], xd: [&[f32]; 2]) -> [f32; 4] {
    // SAFETY: forwarded from the caller; each block holds 32 int8s.
    unsafe { mmla2(rows, x, xd, |w| ([vld1q_s8(w.qs.as_ptr()), vld1q_s8(w.qs.as_ptr().add(16))], w.d)) }
}

#[target_feature(enable = "i8mm")]
pub unsafe fn mmla2_q4_0(rows: [&[BlockQ4_0]; 2], x: [&[BlockQ8_0]; 2], xd: [&[f32]; 2]) -> [f32; 4] {
    // SAFETY: forwarded from the caller; 16 bytes of nibbles per block.
    unsafe {
        mmla2(rows, x, xd, |w| {
            let (lo, hi) = unpack_q4(vld1q_u8(w.qs.as_ptr()));
            ([lo, hi], w.d)
        })
    }
}
  • mmla2_q4_0 unpacks each row's nibbles once, then both tokens reuse them. That is the saving the next section measures.
  • The Q8_0 version loads the bytes directly.

Odd rows and tokens

Rows and tokens come in pairs, so an odd last row or token needs a partner. The caller pairs it with itself:

for i in r.clone().step_by(2) {
    let i1 = (i + 1).min(r.end - 1);
    for tt in (0..t).step_by(2) {
        let t1 = (tt + 1).min(t - 1);
        let v = mmla2(w, [i, i1], [tt, t1], xq, xd, nb);
        for (k, (ti, ii)) in [(tt, i), (t1, i), (tt, i1), (t1, i1)].into_iter().enumerate() {
            // SAFETY: element (ti, ii) lies in this call's rows; a
            // duplicate partner writes the same value twice.
            unsafe { *out.ptr().add(ti * d + ii) = v[k] };
        }
    }
}
  • .min(r.end - 1) and .min(t - 1) pick the row or token itself when there is no partner. The duplicate result is written twice to the same place.
  • Each output has its own lane, and its integer and float sums do not depend on the partner. So the value is the same whatever the partner is, and the same however the rows are split across threads. The threaded test checks this bit for bit.
  • If the partner leaked into the sum, the result would depend on how the work was split, and threaded and single-threaded runs would print different numbers.

Takeaway: smmla gives four outputs per instruction and needs its operands interleaved first. Asm is used because the intrinsic is not stable, and the CPU must be checked first.

Did smmla make prefill faster?

It helped Q4_0 and did nothing for Q8_0. The A/B below ran on the phone, Qwen2.5-0.5B, cores 2–7, on 2026-10-24. Each round ran the new build, the previous commit (sdot) and llama-bench back to back. Prefill tok/s, round 1 / round 2 measured:

Q4_0 smmla272 / 242264 / 231230 / 209
Q4_0 sdot (before)208 / 176196 / 169188 / 159
Q4_0 llama.cpp709 / 631734 / 614552 / 473

Q8_0 llama.cpp711 / 622765 / 649535 / 478

Conditions, from the results file: the phone was on battery at 51 %, the screen was on, and every run started below 48 °C. Round 2 ran about 10 % slower than round 1, so only numbers in the same round compare.

  • Q4_0 gained 22–37 %. The nibbles are unpacked once per pair of tokens instead of once per token. The unpack was the cost that the previous loop repeated.
  • Q8_0 gained nothing, and sometimes lost up to 5 %. Per 32-value block the 2 × 2 kernel spends 8 zip instructions and 4 smmla for 4 outputs. The 4-row sdot kernel spends 8 sdot and no interleaving for the same 4 outputs. The interleaving costs what smmla saves.
  • The gap to llama.cpp is still large: its Q4_0 prefill is 2.3–2.8× ours, against 2.9–3.7× for the sdot build; for Q8_0 it is 2.4–3.3× calculated from the table above.

Was it still correct?

Two checks. First, the batched golden test (testdata/quant_batch/) has nine shapes with odd row and token counts, from 2 to 64 tokens. Its reference is dequant(X_q8_0) @ dequant(W)ᵀ with llama.cpp's quantizers. It passes on the phone, and threaded output is bit-identical to one thread.

Takeaway: smmla helps when the work it removes is repeated across tokens. Q8_0 interleaves as much as it saves.

What comes next?

Phase 7 measured prefill at 2.1–5.8× slower than llama.cpp calculated from its table (the ratio of llama.cpp's tok/s to ours, per prompt length and core set). The reason it gives is that the quantized prefill ran sdot row kernels per token group, not a blocked integer matrix multiply. llama.cpp uses smmla on weights repacked at load, so the interleave is done once, not per call.

The results file lists the next steps, in order. The work is paused, so the learning track can catch up:

  • Interleave the activations once per call, not once per row pair. This removes the repeated part of the zip cost.
  • A 4 rows × 4 tokens tile, so each weight serves four tokens.
  • If the profile still shows interleaving, repack the weights at load, as llama.cpp does.

Takeaway: the next gain is to pay the interleave cost once per call, or once at load, instead of once per row pair.

Check yourself

Why must the activation be quantized to Q8_0 before the integer dot product?

Both operands have to be int8 for sdot and smmla to multiply them directly. If the activation stayed f32, every weight would need converting first, and the integer units would not do the work.

How many products does one sdot compute, and how many outputs does one smmla write?

sdot multiplies 16 pairs of int8 values and sums them in groups of four into four int32 lanes. smmla writes four outputs (2 rows × 2 tokens) and does 32 multiplications.

Why does an odd row or token get paired with itself?

So every smmla is full. Each output has its own lane, so its value does not depend on its partner. The same bits come out however the rows are split across threads.

Why does Q8_0 gain nothing from smmla while Q4_0 gains 22–37 %?

Q4_0 gains because its nibble unpack is now done once per pair of tokens. Q8_0 has no unpack to save, and its 2 × 2 kernel spends 8 zip instructions to feed 4 smmla, and the interleave eats what smmla saves.

What you should take away

Quantizing the activation once turns the weight work into int8 multiplies, with one scale applied per 32-value block.

For prefill, smmla reuses each loaded weight for two tokens. It pays off only where the interleave cost does not eat the saving.
