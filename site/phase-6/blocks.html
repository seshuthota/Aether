Block quantization: Q8_0 and Q4_0

An f32 weight takes 4 bytes. Quantization stores each weight in fewer bits. A block of 32 weights shares one scale number, so a few small integers still cover the right range. This page covers the two formats Aether quantizes into, and why its bytes must match llama.cpp's exactly.

Why store fewer bytes per weight?

Each token of decode reads every weight once (Decode ceiling). The time per token therefore follows the number of bytes in the weights. A block is a run of 32 consecutive weights in one row of a matrix; the formats below store each block as one unit. Quantization makes each weight smaller, so each block is smaller.

Takeaway: Q4_0 reads about a seventh of the f32 bytes per weight, so its decode ceiling is about seven times higher.

Why does each block get its own scale?

A 4-bit integer has only 16 values, 0 to 15. Something must say how large one step is. That is the scale, a number multiplied into every integer to get the real weight. One scale for a whole matrix would have to fit its largest weight, and the small weights would lose all their precision. One scale per 32 weights is the compromise. Each block fits its own range, and the scale costs only 2 bytes per 32 weights.

Illustration, made-up numbers

Suppose a scale of 1.0 covers values from −8 to +7. Then the weight 3.2 is stored as 3, and comes back as 3.0. The error is 0.2. With a scale of 0.25, the same weight is stored as 13 and comes back as 3.25, an error of 0.05.

Takeaway: the scale sets the step size, so a smaller block means its own, finer step.

How does Q8_0 pack 32 weights into 34 bytes?

Q8_0 stores each weight as an 8-bit signed integer, from −127 to 127. The largest weight in the block sets the scale.

  1. Find the largest magnitude amax in the 32 values.
  2. Set the scale d = amax / 127, so the largest value maps to 127.
  3. Store each weight as q = round(x / d). The real value is later q · d.
Illustration, made-up numbers

The block's largest weight is 1.0, so d = 1 / 127 ≈ 0.00787. The weight 0.4 gives q = round(50.8) = 51. Its value is 51 × 0.00787 ≈ 0.402, an error of about 0.002.

The code in src/quant.rs (shortened):

pub fn quantize_q8_0(x: &[f32], out: &mut [BlockQ8_0]) {
    // ...
    for (blk, v) in out.iter_mut().zip(x.as_chunks::<QK>().0) {
        let amax = v.iter().fold(0.0f32, |m, &a| m.max(a.abs()));
        let d = amax / 127.0;
        let id = if d != 0.0 { 1.0 / d } else { 0.0 };
        blk.d = f32_to_f16(d);
        for (q, &a) in blk.qs.iter_mut().zip(v) {
            *q = (a * id).round() as i8; // f32::round = C roundf (halves away from 0)
        }
    }
}
  • fold(0.0f32, ...) walks the 32 values and keeps the largest a.abs(). abs is the absolute value, so the sign is ignored here.
  • id is 1 / d, computed once per block. Multiplying by it is cheaper than dividing 32 times.
  • If the whole block is zero, d is 0 and id is set to 0. That avoids dividing by zero, and every q is 0.
  • round() sends halves away from zero: 2.5 becomes 3 and −2.5 becomes −3. A different rule, such as round-half-to-even, would change some values by one step.
  • The scale is stored as f16, a 16-bit float. f32_to_f16 rounds it to nearest, ties to even.

The block is 34 bytes: 2 for the scale, then 32 signed bytes, one per weight.

Q8_0 block, 34 bytes, #[repr(C)] so there is no padding

byte:   0   1   2   3   4  ...  33
      +---+---+---+---+---+ ... +---+
      | d (f16)|q[0]|q[1]| ... |q[31]|
      +---+---+---+---+---+ ... +---+
      2 bytes  one signed byte per weight

Takeaway: Q8_0 keeps almost all of f32's accuracy at about a quarter of the size, because the scale fits each block.

How does Q4_0 pack 32 weights into 18 bytes?

Four bits give 16 levels, and the weights are positive and negative. Q4_0 stores each level as an unsigned number from 0 to 15 and subtracts 8 when it reads it back. So the real value is (q − 8) · d, and the levels cover −8 to +7 steps. The scale is chosen so the weight with the largest magnitude lands exactly on one end. Here is the code (shortened):

pub fn quantize_q4_0(x: &[f32], out: &mut [BlockQ4_0]) {
    // ...
    for (blk, v) in out.iter_mut().zip(x.as_chunks::<QK>().0) {
        // The element of largest magnitude, first one on ties, sign kept.
        let (mut amax, mut max) = (0.0f32, 0.0f32);
        for &a in v {
            if amax < a.abs() {
                amax = a.abs();
                max = a;
            }
        }
        let d = max / -8.0;
        let id = if d != 0.0 { 1.0 / d } else { 0.0 };
        blk.d = f32_to_f16(d);
        let q = |a: f32| ((a * id + 8.5) as i8).min(15) as u8;
        for j in 0..QK / 2 {
            blk.qs[j] = q(v[j]) | (q(v[j + QK / 2]) << 4);
        }
    }
}
  • max keeps the signed value with the largest magnitude. The test amax < a.abs() is strict, so the first of two equal values wins.
  • d = max / -8. Level 0 gives (0 − 8) · d = −8d = max, so the largest weight is stored exactly. Level 15 gives 7d = −7/8 · max. The 16 levels therefore run from +max down to −7/8 of max. This is a consequence of the offset, not a rounding error.
  • a * id + 8.5 is never negative, because a / d stays between −8 and 8. The cast to i8 drops the fraction. Adding 8.5 and dropping the fraction is round-to-nearest with halves going up, and the +8 offset is already included. .min(15) caps the top level.
  • Each byte holds two weights. q(v[j]) goes in the low nibble (the lower four bits). q(v[j + 16]) << 4 shifts the other one into the high nibble (the upper four bits), and | joins them.

So element j of the block sits in the low nibble of byte j, and element j + 16 in the high nibble of the same byte. Reading back uses & 0x0F for the low nibble and >> 4 for the high one (dequantize_q4_0).

Q4_0 block, 18 bytes

      +---+---+---+---+ ... +---+---+---+
      |  d (f16) |  byte 0 ... byte 15  |
      +---+---+---+---+ ... +---+---+---+

Takeaway: Q4_0 spends 16 of its 18 bytes on the 4-bit values and 2 on the scale, and the scale is d = max / −8.

What happens to 32 numbers when I quantize them?

Type in any box, or press Randomise. Choose the format. The row x is your numbers, q is the integer stored for each, x̂ is the value the block gives back, and error is x̂ − x. Then turn on Add outlier, which sets value 0 to 8 times the largest other value, and watch the other errors grow.

Quantize 32 numbers

What to notice: Q8_0's step is the largest value divided by 127. Q4_0's step is the largest value divided by 8. So a Q4_0 step is about 16 times bigger (127 ÷ 8, calculated), and its errors are correspondingly larger.

Takeaway: the error is set by the step, and the step is set by the largest value in the block.

Why must the bytes match llama.cpp's?

Two engines can use slightly different rounding rules and both look right on a few tests. The difference only shows up later, as a worse perplexity that cannot be traced. The fix is a reference that is exact.

tools/gen_quant.py uses the gguf Python package from llama.cpp's repository to quantize the same arrays. The test quantizers_are_byte_identical_to_llama_cpp in src/quant.rs compares our blocks with those bytes using assert_eq!, so any difference fails the test.

  • A GGUF file written by llama.cpp can be read with no conversion. The block layout is the same, with no padding.
  • llama.cpp can be the accuracy reference. Our perplexity and KL numbers are compared against its llama-perplexity runs in results/phase-6.md.
  • Only the quantized blocks are identical. Sums in f32 can differ in order between engines, so the final logits are close but not identical bit for bit.

Takeaway: one value rounded differently changes a byte and fails the test, so the test catches the bug before any model runs.

What breaks with bigger blocks or one scale per row?

The scale is set by the largest value in its block. One large weight therefore makes the step large for every weight in that block.

Illustration, made-up numbers

A Q4_0 block holds 0.10, −0.20, 0.30 and one outlier of 8.0. With the formula above, d = 8.0 / −8 = −1.0. Each small weight is divided by −1 and gets q = trunc(x / d + 8.5) = 8, which is zero. So 0.10, −0.20 and 0.30 all come back as 0. The outlier comes back exactly. A block of 32 with one outlier loses most of its other 31 weights in the same way.

Bigger blocks make this worse. One scale for 4,096 weights means one outlier can wipe out 4,095 others. Smaller blocks fix it but cost more scales: at 16 weights per block, the scale overhead doubles from 0.0625 to 0.125 bytes per weight (calculated). Blocks of 32 are the llama.cpp choice, so Aether matches it and the files are compatible.

Takeaway: the block size trades precision against scale overhead, and 32 is the size the GGUF format uses.

Check yourself

A Q4_0 block has 18 bytes. What are the 2 bytes for, and why do the 16 others hold 32 weights?

The first 2 bytes hold the f16 scale d. The other 16 bytes hold 32 nibbles, one 4-bit value per weight, two per byte.

In a Q4_0 block, which nibble and which byte hold element 20?

Element 20 is j + 16 with j = 4, so it is in byte 4, in the high nibble.

The largest-magnitude value in a Q4_0 block is −3.0. What is d, and what level does −3.0 get?

d = max / −8 = −3.0 / −8 = 0.375. The level is q = trunc(−3.0 / 0.375 + 8.5) = trunc(0.5) = 0, and the value is (0 − 8) · 0.375 = −3.0, exact.

What you should take away

Each block of 32 weights has one scale, and the scale fits the block's largest value.

Q8_0 is 34 bytes per block and Q4_0 is 18. The bytes are laid out the way GGUF and llama.cpp lay them out.

A single large weight sets the step for its whole block, so block size is a precision choice.
