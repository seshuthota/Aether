Perplexity and KL: did quantization hurt?

A Q4_0 model is smaller and reads less memory, but a faster model can still be a worse one. Perplexity puts one number on how well a model predicts real text. KL divergence and top-token agreement compare a quantized model with its f32 original, token by token.

How do you know a smaller model still works?

Tokens per second say how fast a model runs. They say nothing about whether its words are right. A quantized model can run faster and still produce worse text, and the speed number would look fine.

The fix is to measure how well the model predicts a text that nobody trained it on. Take real sentences, hide each next word, and ask the model how likely it thought the real word was. Good models give the real word high probability. Quantization noise moves those probabilities, so the score shows the damage.

Takeaway: quality needs its own measurement. Speed numbers cannot show it.

How surprised is the model by the real next word?

The model's output for each position is a probability for every token in its vocabulary. Call p the probability it gave to the token that actually came next. A nat is the unit of a natural logarithm. The surprise of that token is −ln p, in nats.

  • If p is 1, the model was certain, and the surprise is 0.
  • If p is 0.5, the surprise is about 0.69 nats. Smaller p means more surprise.
  • Surprise grows without limit as p approaches 0. One very unlikely word can dominate a sum. That is why the score uses surprise, not the raw probability.

Illustration (not a measurement): the model must guess one of four words, and all four are equally likely. Each has p = 0.25, so the surprise is −ln 0.25 = ln 4 ≈ 1.386 nats. If you multiplied the probabilities of several words instead, the number would fall toward zero, and it would be hard to read. Adding surprises is easier.

Takeaway: surprise is −ln p. It is 0 for a certain guess and grows as the model gives the real word less probability.

What does perplexity add up to?

Perplexity is the average surprise, turned back into a count: perplexity = exp(mean of −ln p). The mean is taken over every scored token. The code in src/eval.rs does exactly this:

impl Score {
    pub fn ppl(&self) -> f64 {
        (self.nll / self.count as f64).exp()
    }
}
  • self.nll is the sum of all surprises, and self.count is how many tokens were scored. Their ratio is the mean.
  • exp reverses the logarithm, so the result is back on the scale of a count.
  • The file's doc comment reads this as a number of choices: a model that guessed uniformly among V tokens would score V.

Illustration (not a measurement): the model's guesses were uniform among four words, so every p is 0.25. The mean surprise is ln 4 = 1.386 nats, and exp(1.386) = 4. That matches the rule: a model that is uniform over four choices has perplexity 4.

Takeaway: perplexity is exp(mean surprise). Lower is better, and it reads as how many equally likely choices the model is behaving as if it faces.

Which tokens are scored, and why only half?

A text is a long stream of tokens. The engine cuts it into chunks of 512 tokens (--ctx, default 512). Each chunk is run from an empty cache, so a chunk never sees the previous one. Then only the second half of each chunk is scored.

The reason is context. The first predictions in a chunk have almost nothing before them, so they are poor for any model. Scoring them would measure how little context the model had, not how good it is. By the middle of the chunk, every prediction has at least 256 tokens to work from.

let first = n_ctx / 2;
...
// Rows predict the tokens after positions first..n_ctx-1; the last
// row has no next token inside the chunk and is not scored.
let ours = model.forward_batch_logits(chunk, 0, first).to_vec();
...
for r in 0..(n_ctx - 1 - first) {
    let next = chunk[first + r + 1];
  • With n_ctx 512, first is 256. Row r predicts the token after position 256 + r, and the loop runs 255 times.
  • So each chunk scores 255 tokens, the ones at positions 257 to 511. Twenty chunks give 5,100 scored tokens. That is the count in the phase 6 results.
  • The chunk's first token is replaced by the beginning-of-text token for models whose tokenizer adds one. The doc comment says llama.cpp does the same.
  • The procedure is llama-perplexity's, so the numbers can be compared. If the first half were scored too, the number would not match llama.cpp's, and the comparison would tell you nothing.

A run looks like this, with the flags from src/main.rs:

aether MODEL --ppl wiki.test.raw --chunks 20 -q q4_0 --kl
  • --ppl FILE scores the text in FILE instead of generating.
  • --chunks N stops after N chunks.
  • --kl also loads the f32 model and reports KL divergence and top-token agreement against it.
  • --base PATH names the reference model for --kl. Without it, the f32 version of MODEL is used.

Takeaway: the first half of each chunk is warm-up. Scoring only the second half gives a number that means the same thing as llama.cpp's.

How big is the error bar?

A perplexity from 5,100 tokens is an estimate, and it moves a little with the text. The error bar says how much. ppl_err computes one standard error, as llama.cpp prints it:

/// ± one standard error of the perplexity, as llama.cpp prints it.
pub fn ppl_err(&self) -> f64 {
    let n = self.count as f64;
    let (mean, mean2) = (self.nll / n, self.nll2 / n);
    ((mean2 - mean * mean).max(0.0) / (n - 1.0)).sqrt() * self.ppl()
}
  • mean2 − mean² is the variance of the surprises. The square root of its share over n − 1 is the standard error of the mean surprise.
  • Multiplying by ppl() turns that error from nats into perplexity units. This is the usual first-order step for a function of an average.
  • If two results differ by less than their error bars, the test cannot tell them apart. The f32 and Q8_0 rows below are an example.

Takeaway: a difference inside the error bar is noise. Only a difference bigger than the bar is a result.

How far did the quantized model move from f32?

Perplexity only looks at the token that actually came next. A quantized model can change its probabilities for other tokens and leave perplexity almost the same. KL divergence counts those changes too. For the f32 model's distribution P and the quantized model's Q over the vocabulary:

KL(P‖Q) = Σ over tokens v of  p(v) · (log p(v) − log q(v))
  • It is zero only when the two distributions are identical. Each term is a weighted gap between the two models' log-probabilities.
  • The weights are the f32 model's probabilities, so the tokens that matter most to the f32 model count most.
  • The code computes this for each scored position, with the base model's log-probabilities as lb and the quantized model's as lp:
score.nll_base -= lb[next];
score.kld += lb.iter().zip(&lp).map(|(&b, &q)| b.exp() * (b - q)).sum::<f64>();
score.same_top += usize::from(argmax(&lb) == argmax(&lp));
  • b.exp() turns the base log-probability back into the base probability, which is the weight.
  • same_top counts positions where both models' most likely token is the same token. The “same top” figure in the tables is that count as a percentage.
  • A low KL with a low same-top rate cannot happen. KL near zero means the two models rank the tokens the same way.

Takeaway: perplexity asks whether the model still predicts the real word. KL asks whether it still predicts the same distribution as the original.

Why match llama.cpp's numbers?

The project's rule is that correctness comes from external references, not from a second implementation of our own. Here the reference is llama.cpp's llama-perplexity, run on the same text and the same quantized files. If our procedure and our kernels are right, the numbers agree within llama.cpp's error bar.

They do not agree bit for bit, and they should not. The results file notes that llama.cpp's f32 path on x86 sums in a different order from ours, and its own runs differ from each other by about as much as ours differs from it.

Do small models suffer more?

Yes, on these two models. Q4_0 raised perplexity by a factor of about 1.41 for SmolLM2-135M, and about 1.21 for Qwen2.5-0.5B. The factors are the Q4_0 perplexity divided by the f32 perplexity from our own runs calculated: 27.7150 / 19.6715 and 19.7441 / 16.2745.

The KL divergence tells the same story: 0.34 nats for SmolLM2 against 0.18 for Qwen. The results file's reading is that a small model has fewer weights to absorb the rounding. Two models is a small sample, so treat that as a reading, not a law.

Q8_0 is close to lossless for both. Its same-top rate is 96 % or so, and its perplexity moves by less than its error bar.

Takeaway: the same 4-bit format costs a small model much more than a larger one. Measure each model, not each format.

Check yourself

A model gives the real next word probability 0.5 at every scored position. What is its perplexity?

The surprise is −ln 0.5 = ln 2 at every position, so the mean is ln 2 and exp(ln 2) = 2. The model behaves as if it were choosing between two equally likely words.

Why are the first 256 tokens of each 512-token chunk not scored?

Their predictions have little context, so they measure the lack of context more than the model. Scoring only the second half matches llama.cpp's procedure, so the numbers can be compared.

Two Q4_0 results differ by 0.02 in perplexity, and each has an error bar of ±0.8. What can you say?

Nothing. The difference is far inside the error bar, so the test cannot tell them apart.

Why compare with llama.cpp on the same files, instead of checking our f32 run against itself?

A self-check would repeat our own mistakes. llama.cpp is an independent implementation, so agreement within its error bar is evidence the procedure and the kernels are right.

What you should take away

Perplexity is exp of the mean surprise, measured on the second half of 512-token chunks. Lower is better, and a difference inside the error bar is noise.

KL and same-top rate show whether a quantized model still predicts like the f32 original. Match llama.cpp on the same files to know the numbers are right.
