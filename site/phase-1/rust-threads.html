Threads in Rust

Phase 1 needs threads twice. The power monitor runs beside the benchmark, sampling while the benchmark works. The parallel sweep runs one reader per core at the same moment. Both use the standard library; no crate needed.

What does handle.join() do?

  • Waits for the thread to finish and returns what it returned
    join waits, then hands back the closure’s result.
  • Stops the thread at once
    Tempting, since join ends the thread’s work. Stopping is done with a flag; join waits.
  • Starts the thread on a second core
    That is spawn. join waits for a thread that has already started.

A worker started with thread::scope is still running when the scope’s code ends. What happens?

    Every thread started in a scope is joined before the scope ends.
  • The worker keeps running on the borrowed buffer
    Tempting: a thread can keep running after its function returns. A scope does not allow that.
  • The program stops with an error
    Tempting: a leftover thread sounds like a bug. The scope is built to wait instead.

What are we trying to do here?

Phase 1 needs two things to happen at the same time. The power monitor samples the battery while the benchmark runs. One reading at the start and one at the end gives an average but not the shape of the run, so the sampler runs on a background thread. The parallel sweep starts one reader on each core together, so its result shows what all the cores can read at once.

A thread is one stream of instructions. A program can start more threads, and the operating system can run them on different cores at the same moment. A core is one of the processors on the chip. The standard library provides threads, so Phase 1 needs no extra crate. This page covers three things: starting a thread and waiting for its result, stopping a thread with a shared flag, and letting workers borrow one buffer. Each worker then pins itself to a core, as Calling Linux from Rust shows.

By the end you can read the sampler and the sweep skeleton line by line. You can say why the flag is shared, why join returns the samples, and why the barrier sits outside the clock.

What is a thread?

The sampler has to run while the benchmark runs, and one stream of instructions cannot do both. A program starts with one thread: one stream of instructions, running on one core at a time. A second thread is a second stream, which the operating system can run on another core at the same moment.

Threads in one program share its memory. That is what makes them useful, and why Rust is strict about them. Two threads writing the same value at once is a data race, and Rust refuses to compile code that could have one.

Takeaway: a thread is a second stream of instructions that shares memory, and Rust refuses data races at compile time.

Two threads both add to one counter variable, with no synchronisation. What does Rust do?

  • Refuses to compile it: that is a data race
    Two threads writing one value at once is a data race, and Rust rejects it at compile time.
  • Runs it, and the total may come out too low
    Tempting: that is what happens in C. Rust stops it before it runs.
  • Runs it, adding a lock for you
    Rust adds nothing silently. You choose the tool, such as an atomic.

How do you start a thread and wait for it?

You want the sampler to start on its own thread, and later you want its list of samples back. Two calls do that.

The sampler should start now and hand back its samples when the benchmark is done. Which code does that?

  • spawn the closure, then join its handle
    spawn starts the closure on a new thread. join waits for it and returns what it returned.
  • Call the closure directly and read a shared list afterwards
    Tempting: one call, one result. But it runs in line, so the benchmark waits for it.
  • spawn, sleep for the expected run time, then read the list
    A sleep guesses when the work ends. join waits for the real end and gives back the value.

std::thread::spawn starts a thread running a closure (a small function written inline, || { … }) and returns a handle. handle.join() waits for it to finish and hands back whatever the closure returned.

The closure is move, so it takes ownership of what it uses. The new thread may outlive the function that started it, so it can’t borrow local variables. If it could, a local might be gone while the thread still used it.

Takeaway: spawn starts, join waits and returns the result, and the closure must own what it uses.

The sampler’s closure uses a local variable flag, and you leave out move. The function returns while the thread still runs. What happens?

  • A compile error: the thread may outlive the local
    spawn cannot borrow locals. move hands the closure ownership of what it uses.
  • It runs, and the thread reads the flag safely
    That looks safe while the function is alive. The rule covers the case where it is not.
  • A panic when the thread starts
    The rule is checked at compile time. Nothing has run yet when the compiler refuses it.

How do you tell a thread to stop?

The sampler loops until the benchmark is done, so it needs a flag that one thread sets and another reads. A plain bool won’t compile: two threads touching one variable without synchronisation is the data race Rust forbids.

Two threads need one flag. Which change makes sharing it legal?

  • An AtomicBool in an Arc, with one handle per thread
    The atomic makes each read and write one step. The Arc gives each thread a handle to the same flag.
  • Give each thread its own copy of the bool
    Tempting: copies cannot race. But setting one copy does not stop the sampler’s copy.
  • Pass a reference to the bool
    A reference cannot go to a thread that may outlive the function, as the spawn section showed.

Two tools fix that:

  • An AtomicBool is a bool whose reads and writes are each one indivisible step, so sharing it is allowed.
  • Arc (“atomically reference counted”) lets both threads own a handle to the same flag.

Step 1: make the shared flag

let stop = Arc::new(AtomicBool::new(false));
let flag = Arc::clone(&stop);
  • Arc::clone makes a second handle to the same flag. It does not copy the bool.

Step 2: spawn the sampler

let sampler = thread::spawn(move || {
    let mut samples = Vec::new();
    while !flag.load(Ordering::Relaxed) {
        samples.push((Instant::now(), read_power()));
        thread::sleep(Duration::from_millis(100));
    }
    samples
});
  • move hands flag to the new thread.
  • The loop checks the flag, takes one sample, sleeps 100 ms, and repeats.
  • The last line, samples, is what join will return.

Step 3: stop it and collect

run_benchmark();
stop.store(true, Ordering::Relaxed);
let samples = sampler.join().unwrap();
  • store(true, …) sets the flag. The sampler sees it on its next check and leaves the loop.
  • .unwrap() takes the value out of join’s Result, and panics if the sampler thread had panicked.

All three together

use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::Arc;
use std::thread;
use std::time::{Duration, Instant};

let stop = Arc::new(AtomicBool::new(false));
let flag = Arc::clone(&stop);
let sampler = thread::spawn(move || {
    let mut samples = Vec::new();
    while !flag.load(Ordering::Relaxed) {
        samples.push((Instant::now(), read_power()));
        thread::sleep(Duration::from_millis(100));
    }
    samples
});

run_benchmark();
stop.store(true, Ordering::Relaxed);
let samples = sampler.join().unwrap();

Ordering::Relaxed is enough here. The flag carries no data; it only says “stop.” The samples come back through join, and join guarantees you see everything the thread wrote. Orderings matter when an atomic is guarding other data. That is a Phase 4 topic.

Keep each sample’s Instant. Then you can keep only the samples inside the timed window, and work out energy as each power reading times the gap to the next one, added up. Sampling intervals are never exactly 100 ms, so without the timestamps the sum is wrong.

Takeaway: share an Arc<AtomicBool> to stop a thread, return its data through join, and keep every sample’s timestamp.

Why does the stop flag need to be atomic, if only one thread ever writes it?

  • A read during a write is a race, even with one writer
    An atomic makes each access one step. It also stops the compiler assuming the flag never changes in the loop.
  • Only one writer means no race
    Tempting: one writer seems safe. The race is a read and a write overlapping, and that needs no second writer.
  • Atomics are faster than a bool
    Speed is not the reason. The atomic is there for safety: each access is one indivisible step.

How often should the sampler sample?

Faster sounds better. Drag the benchmark length and the interval to see how many samples land inside the run.

A benchmark runs 10 s, and the sampler takes one sample every 100 ms. How many samples land inside the run?

  • About 100
    10 s divided by 100 ms is 100. A run that long gets enough readings to average.
  • One, since a long run needs only one reading
    Tempting: one reading seems enough. The sampler reads every 100 ms for the whole run.
  • About 10,000, one per millisecond
    It mixes up the rate. The sampler takes one sample each 100 ms, not one each millisecond.

How many samples land inside the run?

The bar is the timed benchmark. Each tick is one sample.

Faster sampling is not free and is not always more information. Each sample is a few file reads, which cost the CPU something. And the battery gauge updates its reading on its own schedule. If ten samples in a row return the same current_now, you are sampling faster than the sensor changes assumption, so check by hand what this phone does.

A run that is short next to the interval gets one or two readings, which is a guess, not an average. Make energy runs long.

The sampler thread runs on a core too. For a single-core run, pin the sampler to a core you are not measuring. For the all-cores run there is no spare core; it sleeps almost all the time, so it costs little, but note it.

Takeaway: sample no faster than the sensor changes, and make the run long compared with the interval.

A 50 ms benchmark with a 100 ms sampler. What is the energy number worth?

  • Close to nothing
    At most one sample. Lengthen the window, or repeat the run inside it, to hold many samples.
  • It is fine: energy is power times time
    The formula is right. One or two readings are not an average.
  • A good estimate: 100 ms covers a 50 ms run
    It looks fast next to the run, but its interval is twice the run. Check the count, not the speed.

How do worker threads borrow the buffer?

The parallel sweep splits one big buffer into chunks, one per core. Each worker only needs to borrow its chunk.

Each worker must borrow its chunk of the main thread’s buffer. Which call lets it?

  • thread::scope, which joins every thread before it ends
    A scope joins its threads before it returns. Borrowing is then safe, and the compiler allows it.
  • spawn, with the chunk moved in
    Tempting, since spawn is the usual call. But spawn needs owned data, and a borrowed chunk isn’t owned.
  • A Barrier, a point where threads wait for each other
    A barrier does not let a thread borrow. It keeps start-up time out of the clock.

spawn can’t do that, because the thread might outlive the buffer. std::thread::scope can: every thread started inside the scope is joined before the scope ends, so borrowing is safe and the compiler allows it.

Starting a thread and pinning it take time, and that time is not bandwidth. A Barrier keeps it out of the clock: every worker gets ready, then waits there until all have arrived.

Step 1: cut the buffer

let per = data.len() / cpus.len();
data.chunks(per).zip(cpus)
  • chunks(per) cuts the buffer into pieces of per floats. zip(cpus) pairs each piece with a core number.
  • If the length doesn’t divide evenly, chunks makes one short extra chunk and zip drops it. Count per × cpus.len() floats, not data.len(), or the GB/s is slightly too high.

Step 2: each worker pins itself, then waits

s.spawn(move || {
    pin_to(cpu).expect("pin failed");  // each worker pins itself
    start.wait();                      // then waits for the others
    read_sum(chunk)
})
  • s.spawn is the scope’s version of spawn; it allows borrowing chunk.
  • .expect("pin failed") is unwrap with a message, so a failed pin stops the run.

Step 3: release everyone and start the clock

// everyone is pinned; go
start.wait();
let t0 = Instant::now();
for h in handles {
    h.join().unwrap();
}
t0.elapsed()
  • The barrier opens when the last of the n + 1 threads (the n workers and the main thread) has arrived, whichever thread that is. The main thread starts the clock as soon as its own wait() returns.
  • The GB/s is the bytes actually read over elapsed.

All three together

use std::sync::Barrier;

let per = data.len() / cpus.len();
// the workers plus this thread
let start = Barrier::new(cpus.len() + 1);
let elapsed = thread::scope(|s| {
    let handles: Vec<_> = data
        .chunks(per)
        .zip(cpus)
        .map(|(chunk, cpu)| {
            let start = &start;
            s.spawn(move || {
                // each worker pins itself
                pin_to(cpu).expect("pin failed");
                // then waits for the others
                start.wait();
                read_sum(chunk)
            })
        })
        .collect();
    // everyone is pinned; go
    start.wait();
    let t0 = Instant::now();
    for h in handles {
        h.join().unwrap();
    }
    t0.elapsed()
});

The black_box rule from Measuring time still applies to read_sum’s input and result. The sketch leaves it out to keep the shape visible.

Takeaway: thread::scope lets workers borrow, and the barrier keeps start-up time out of the clock.

Why does the main thread call start.wait() before Instant::now()?

  • So the clock starts only once every worker is pinned and ready
    Starting and pinning threads takes time that isn’t bandwidth. The barrier keeps it out of the clock.
  • So the workers start in core order
    A barrier releases everyone together; it sets no order.
  • So join can return the results
    join works without a barrier. The barrier is about when the clock starts.

What you should take away

Use spawn and join for the sampler, stopped by a shared Arc<AtomicBool>; keep every sample’s timestamp.

Use thread::scope so workers can borrow their chunk, and a Barrier so the clock starts when everyone is pinned and ready.

Sample no faster than the sensor changes, and make energy runs long.
