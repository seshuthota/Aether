Threads in Rust

Phase 1 needs threads twice. The power monitor runs beside the benchmark, sampling while the benchmark works. The parallel sweep runs one reader per core at the same moment. Both use the standard library; no crate needed.

How to use this page

Two patterns, each shown once. The snippets compile for aarch64-linux-android measured. read_power, run_benchmark, read_sum and pin_to are placeholders for code you write.

What a thread is

A program starts with one thread: one stream of instructions, running on one core at a time. A second thread is a second stream, which the operating system can run on another core at the same moment. Threads in one program share its memory. That is what makes them useful, and why Rust is strict about them: two threads writing the same value at once is a data race, and Rust refuses to compile code that could have one.

spawn and join

std::thread::spawn starts a thread running a closure and returns a handle. handle.join() waits for it to finish and hands back whatever the closure returned. The closure is move, so it takes ownership of what it uses. The new thread may outlive the function that started it, so it can’t borrow local variables.

Telling a thread to stop

The sampler loops until the benchmark is done. It needs a flag that one thread sets and another reads. A plain bool won’t compile: two threads touching one variable without synchronisation is the data race Rust forbids. An AtomicBool is a bool whose reads and writes are each one indivisible step, so sharing it is allowed. Arc (“atomically reference counted”) lets both threads own a handle to the same flag.

use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::Arc;
use std::thread;
use std::time::{Duration, Instant};

let stop = Arc::new(AtomicBool::new(false));
let flag = Arc::clone(&stop);
let sampler = thread::spawn(move || {
    let mut samples = Vec::new();
    while !flag.load(Ordering::Relaxed) {
        samples.push((Instant::now(), read_power()));
        thread::sleep(Duration::from_millis(100));
    }
    samples
});

run_benchmark();
stop.store(true, Ordering::Relaxed);
let samples = sampler.join().unwrap();

Ordering::Relaxed is enough here. The flag carries no data; it only says “stop.” The samples come back through join, and join guarantees you see everything the thread wrote. Orderings matter when an atomic is guarding other data. That is a Phase 4 topic.

Keep each sample’s Instant. Then you can keep only the samples inside the timed window, and work out energy as each power reading times the gap to the next one, added up. Sampling intervals are never exactly 100 ms.

How often to sample

How many samples land inside the run?

The bar is the timed benchmark. Each tick is one sample.

Faster sampling is not free and is not always more information. Each sample is a few file reads, which cost the CPU something. And the battery gauge updates its reading on its own schedule. If ten samples in a row return the same current_now, you are sampling faster than the sensor changes assumption, so check by hand what this phone does. A run that is short next to the interval gets one or two readings, which is a guess, not an average. Make energy runs long.

The sampler thread runs on a core too. For a single-core run, pin the sampler to a core you are not measuring. For the all-cores run there is no spare core; it sleeps almost all the time, so it costs little, but note it.

Scoped threads for the sweep

The parallel sweep splits one big buffer into chunks, one per core. Each worker only needs to borrow its chunk. spawn can’t do that, because the thread might outlive the buffer. std::thread::scope can: every thread started inside the scope is joined before the scope ends, so borrowing is safe and the compiler allows it.

use std::sync::Barrier;

let per = data.len() / cpus.len();
let start = Barrier::new(cpus.len() + 1);          // the workers plus this thread
let elapsed = thread::scope(|s| {
    let handles: Vec<_> = data
        .chunks(per)
        .zip(cpus)
        .map(|(chunk, cpu)| {
            let start = &start;
            s.spawn(move || {
                pin_to(cpu).expect("pin failed");  // each worker pins itself
                start.wait();                      // then waits for the others
                read_sum(chunk)
            })
        })
        .collect();
    start.wait();                                  // everyone is pinned; go
    let t0 = Instant::now();
    for h in handles {
        h.join().unwrap();
    }
    t0.elapsed()
});

The Barrier is there for the clock. Starting a thread and pinning it take time, and that time is not bandwidth. Every worker gets ready, then waits at the barrier. The main thread arrives there last, which releases everyone together, and starts the clock at that moment. The GB/s is the bytes actually read over elapsed. If the length doesn’t divide evenly, chunks makes one short extra chunk and zip drops it, so count per × cpus.len() floats, not data.len().

The black_box rule from Measuring time still applies to read_sum’s input and result. The sketch leaves it out to keep the shape visible.

Check yourself

Why does the stop flag need to be atomic, if only one thread ever writes it?

A read in one thread and a write in another at the same time is still a data race, which Rust forbids for plain values. An atomic makes each read and write one indivisible step. It also stops the compiler from assuming the flag never changes inside the loop.

Why thread::scope for the sweep and not thread::spawn?

The workers borrow chunks of a buffer the main thread owns. spawn requires the closure to own everything, because the thread could outlive the buffer. A scope joins every thread before it returns, so the borrow is safe.

A 50 ms benchmark with a 100 ms sampler. What is the energy number worth?

Close to nothing: at most one sample inside the run. Lengthen the run, or repeat it back to back inside one timed window, until the window holds many samples.
