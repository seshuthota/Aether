The memory hierarchy

A core can do hundreds of operations in the time it takes to fetch one number from main memory. Caches hide that gap, but only for data that gets used again soon. Decode reads gigabytes of weights once per token and never gets back to the start before they have been pushed out. So every token reads them from DRAM again, and memory speed, not core speed, sets the pace.

The problem: a fast core, a far memory

A prime core here runs at about 4.3 GHz, so one clock cycle lasts about a quarter of a nanosecond. In one cycle a core can start several instructions, for example a few adds or multiply-adds.

The weights live in DRAM, the phone’s main memory. DRAM is a separate chip, and a read that has to go all the way there typically takes on the order of 100 nanoseconds assumption. That is roughly 400 cycles. If the core waited for every number it needed, it would spend almost all its time idle.

An everyday picture

Think of a cook. The cutting board is right there. The fridge is a few steps away. The supermarket is across town. A sensible cook does not drive to the supermarket for every onion: they keep what they are using on the board and what they will need soon in the fridge. Registers, caches and DRAM are the board, the fridge and the supermarket.

What a cache does

A cache is a small, fast memory next to the core that keeps copies of data recently read from DRAM. The program does not manage it. The hardware does it automatically on every load.

  1. Check. The core needs a number at some address. It first asks the cache: do you have a copy?
  2. Miss. If not, that is a cache miss. The request goes on to DRAM, and the core waits for the slow trip.
  3. Copy a whole line. DRAM does not send just the 4 bytes asked for. It sends the whole 64-byte cache line around them, 16 f32s, and the cache keeps it.
  4. Hit. The next time the core needs that number, or one of its neighbours in the same line, the cache has it. That is a hit, and it takes a few cycles instead of hundreds.
  5. Evict. The cache is small. When it is full and a new line comes in, an old line is thrown out, usually one that has not been used for the longest time.

Locality: the bet caches make

A cache helps only if the program comes back to data it already loaded. Programs usually do, in two ways:

  • Temporal locality: if you used it, you will probably use it again soon. A loop counter, or a small table read over and over.
  • Spatial locality: if you used this byte, you will probably use the next one. Walking an array in order (stride 1) uses all 16 floats of every line it pays for. Walking down a column of a row-major matrix uses one float per line and throws the other 15 away.

Hardware also has a prefetcher: it notices a steady stream of addresses and asks DRAM for the next lines before the program does. That hides waiting for a stream. It cannot create reuse the program does not have.

The ladder

One cache is a compromise between big and fast, so real chips stack several. A load checks them from the top down and stops at the first level that has a copy. Each step down is larger and slower. The ratios are what to feel; the exact sizes and speeds on this phone are what the Phase 1 sweep will show.

  • Registers are the only storage an instruction works on directly. A NEON register is 128 bits: four f32s, or sixteen i8s. There are 32 NEON registers and 31 general-purpose ones, about 0.75 KB in all.
  • L1 is private to one core, split into an instruction cache and a data cache. A hit takes a few cycles. First-generation laptop Oryon had a 96 KB data L1 (Hot Chips 2024). This phone has a later mobile Oryon, so do not copy that number here. The sweep will show where the L1 cliff really is.
  • L2 on Oryon is shared by a cluster of cores, not tiny and private. Launch coverage of the 8 Elite said 12 MB per cluster, two clusters. assumption If the sweep on one prime core falls off well before 12 MB, the claim was wrong or one core cannot use the whole cluster cache by itself. Either result teaches something.
  • SLC, the system-level cache, sits in front of DRAM and is shared with the GPU and other parts of the chip. Its size on this phone is not published in anything we have checked.
  • DRAM is LPDDR5X. It is shared with Android, the GPU, the modem and the display. A read that misses every cache costs hundreds of cycles, and the whole chip shares the same bus.

How far away is each rung?

Nanoseconds are hard to feel. Switch to the human scale, where one nanosecond becomes one second. The numbers are typical for phone CPUs assumption, not measurements of this phone.

The bars use a log scale, so each step right is a multiple, not an addition. Drawn to normal scale, the DRAM bar would be 120 times the L1 bar. On the human scale an L1 hit is one second and a trip to DRAM is two minutes.

Latency vs bandwidth

These are two different numbers, and mixing them up is a classic mistake.

  • Latency is how long one load waits, start to finish. The widget above is about latency.
  • Bandwidth is how many bytes per second arrive when many loads are in flight at once.

Back to the cook. If every trip to the supermarket takes an hour, one shopper making one trip at a time brings home very little per day. A delivery service with twenty vans on the road still takes an hour per trip, yet groceries arrive twenty times as fast. The trip time (latency) did not change. The number of trips under way at once did.

A core can do the same. When the next load does not depend on the one before, it does not have to wait: it sends several requests to memory and keeps track of them until they come back. The prefetcher adds more. Those outstanding requests are what fill the bus.

Decode streams through gigabytes of weights, and every load is independent. So the number that limits it is bandwidth, not latency. A pointer-chasing benchmark measures latency; a streaming read measures bandwidth. Phase 1 measures the second one.

Why was the Phase 0 sum only 3.3 GB/s?

Each add waited for the add before it (s = s + x[i]). That chain of waits, not the memory, set the pace, so the loop never had enough loads in flight to show what the memory can do. A bandwidth kernel uses independent loads and counts bytes per second.

Why decode misses

To produce one token, decode runs every layer of the model in order. Each layer multiplies its weight matrices by one small vector, and in that multiply every weight is used exactly once. Then the next token starts again at layer 1.

Follow the cache through one token:

  1. The first weights stream in from DRAM. Each is a miss (the prefetcher can start them early, but they still come from DRAM).
  2. The cache fills up. From then on every new line pushes out an old one, and the oldest are the earliest layers.
  3. When the token ends, the cache holds only the last few megabytes of weights.
  4. The next token starts at layer 1. Those weights were pushed out gigabytes ago, so they miss again. So does everything after them.

Now the real sizes. A 0.5B-parameter model in f32 is 2 GB. Even if two clusters really have 12 MB of L2 each, plus a few megabytes of SLC, the caches hold around 1% of the weights. The other 99% come from DRAM on every token.

There are two kinds of miss here. A compulsory miss happens the first time a line is ever loaded; nothing avoids it. A capacity miss happens because the data the code keeps coming back to, its working set, is bigger than the cache. Decode’s weight misses are capacity misses, on every token, and no reordering of the loop changes that.

Will it fit?

Pick a working set and compare it with the cache sizes. The cache sizes are claims and orders of magnitude assumption, not measurements. SLC is left out because its size is unknown.

What actually helps

If every token has to read the weights from DRAM, the speed limit is simple:

tokens per second ≤ bandwidth (bytes/s) ÷ bytes read per token

That is the decode ceiling from Phase 0. Only two things move it:

  • Read fewer bytes. Quantization stores each weight in 8 or 4 bits instead of 32. The same model becomes 0.5 GB or less, so each token reads a quarter of the bytes.
  • Use each byte for more than one token. Prefill applies every weight to many prompt tokens per read, and batching or speculative decoding do the same. Then the weight is reused while it is still in cache.

A faster core is not on the list. It finishes its arithmetic sooner and then waits longer. The model is still 2 GB.

Why one core may not fill the bus

The plan says a single phone core usually cannot use all of DRAM’s bandwidth, which is why decode wants several threads. The reason follows from the previous sections:

  • A core can track only a limited number of outstanding misses. If it runs out before the bus is full, the bus waits on the core, like a delivery service that owns too few vans.
  • The path from one core to the memory controller has its own width. Laptop Oryon, a different chip, could pull on the order of 100 GB/s from one thread in Qualcomm’s own slides. That is a warning, not a result: this phone might fill the bus from one core, or it might not.
  • Several cores issuing misses together can fill a bus that one core cannot. They also compete with each other, and a slow core makes the others wait at the end of a shared job. Pinning lets you choose which cores run.
Do not import the laptop number

Chips and Cheese and Qualcomm’s Hot Chips talk describe first-generation Oryon in a laptop. This phone is a later mobile core, two clusters, a phone memory controller, and a thermal budget with no fan. Single-thread DRAM bandwidth here is an open question. Write the guess down, then run the read benchmark.

What Phase 1 will measure

The working-set sweep reads a buffer over and over and records bytes per second, starting with a tiny buffer and doubling it each step. While the buffer fits in L1, every pass after the first hits L1 and the number is high. When it outgrows L1, it drops to L2 speed. When it outgrows L2 and SLC, it drops again to DRAM speed. Those drops, the cliffs, are where the real cache sizes are. The DRAM level is the bandwidth that sets the decode ceiling.

Check yourself

A cache hit and a cache miss: what is the difference, and roughly how big?

A hit means the cache already had a copy, so the load finishes in a few cycles. A miss means it did not, so the load goes further down the ladder, to DRAM in the worst case, which typically costs hundreds of cycles.

You read one f32. How many bytes come from DRAM?

A whole cache line: 64 bytes, 16 floats. If you then use the neighbours, they are free hits. If you skip them, as in a column walk, you paid for 64 bytes to use 4.

Does stories15M, at 60 MB in f32, fit in L2?

Not even under the 12 MB claim, nor with both clusters together. Even the tiny model streams from DRAM every token. Try it in the “Will it fit?” widget.

Why doesn’t a bigger L2 fix decode?

Because the model is gigabytes and the L2, even at the claimed size, is tens of megabytes. The misses are capacity misses. A bigger cache helps data that fits; the weights do not.

Latency did not change, but bandwidth went up. How?

More loads were in flight at once. Each trip took as long as before, but more trips overlapped, so more bytes arrived per second.

Why might eight cores read DRAM faster than one, and why not eight times faster?

Faster, if one core cannot keep enough misses in flight to fill the bus. Not eight times, if the bus fills up first, if cores sharing an L2 get in each other’s way, or if the memory controller is the limit. The pinned sweep shows which of these happened.
