A benchmark says how long. A profile says where inside that time the cycles went. Optimizing before you have both is how you speed up a function that was not the cost.

What it is

simpleperf is Android’s perf. It samples the CPU while a process runs: at a regular interval it records where the program counter is, and which process and thread that was. Aggregated, that is a histogram of where time went. It is a sampler, not a tracer. A function that is 40% of samples is about 40% of CPU time. A function that ran once for a microsecond may not appear at all.

It can also count hardware events: cycles, instructions, cache misses, branch misses. Those counters are how you tell “we are stalled on memory” from “we are retiring a lot of instructions.” The GB/s benchmark already answers the first question for a streaming read. The counters become important when a kernel is slower than the streaming read and you need to know if the extra time is misses, branches, or just more instructions.

The tool lives on the device, or is pushed next to your binary. Phase 1 does not need a wrapper around it. The habit is: release binary, symbols on, pin the thread, record, report. Build the habit on the bandwidth benchmark, where you already know the answer should be “almost all the samples are in the read loop.” If the report says something else, the binary you timed is not the binary you think you built.

Why symbols are already on

Cargo.toml sets debug = true in the release profile. That keeps names and line numbers in the optimized binary. simpleperf can then say bench::read_loop instead of an address in an anonymous mapping. The hello-world binary being not stripped and 482 KB was the same fact at a smaller scale.

debug = true is not the debug profile. The debug profile turns optimization down. A profile of a debug build tells you where the unoptimized code spent time, which is a different program. Record release binaries.

Fat LTO and one codegen unit will inline aggressively. A function you expected to see may have disappeared into its caller. That is not a broken profile. It is the compiler doing what the release profile asked. If you need a function to remain visible, #[inline(never)] is the same tool Phase 0 used on sum. Use it to learn, and take it off when the learning is done, because it also changes the timing.

When to reach for it

Not before a correct, timed result exists. The order that does not waste a week:

  1. The kernel matches an external reference, or, for the bandwidth kernels, the bytes and the checksum are not optimized away.
  2. The harness says how long, with a median and a spread, on a pinned core, in release.
  3. You compare that time to the roofline or to the pure-read bandwidth. If you are close to the roof, stop. The residual is not where a profile will find a 2× win.
  4. If you are far from the roof, then record. The profile tells you whether the time is in your loop, in a surprise allocation, in adb’s own noise, or in a function you thought was free.

Phase 0’s sum is a worked example of step 3 without a profile. 3.3 GB/s against an unknown DRAM roof was already enough to say “this is not a memory-bandwidth result.” A profile would have shown the samples in the add loop, which you already knew from the source. Profiling would not have been wrong. It would have been redundant. Save it for the surprise.

How to read a report

A typical record/report pair, once simpleperf is on the phone next to the binary:

simpleperf record -p <pid> --duration 5 -o /data/local/tmp/aether/perf.data
simpleperf report -i /data/local/tmp/aether/perf.data

The flags worth knowing before the rest of the manual:

  • -p attaches to the already-running benchmark, so you do not profile process startup and the page faults of the first touch unless you mean to.
  • --duration keeps the file small. Five seconds of a DRAM read is a lot of samples.
  • The report’s percentages are of samples, which approximate CPU time. A thread that is asleep or descheduled is not running, so it collects no samples at all: the profile cannot show you time spent off the CPU. If the benchmark’s wall-clock time is much longer than its sampled CPU time, something took the core away, and the profile will not say what.
  • DSO and symbol columns tell you if time is in your binary, in libc, or in the Linux kernel. Waiting on memory does not move samples into the kernel: a stalled load is still your instruction, so a DRAM-bound read loop shows up as samples in your own loop, often piled on the load or the instruction right after it. Large kernel time instead means page faults, system calls, or interrupts. For the bandwidth kernel, that usually means the buffer was touched for the first time inside the timed region.
  • To tell “stalled on memory” from “too many instructions,” count events instead of time: simpleperf stat -e cpu-cycles,instructions. Few instructions per cycle on a streaming loop is the signature of waiting on memory.

Call-graph mode (-g) attributes samples to callers. Useful when LTO has inlined everything into main. Heavier. Turn it on when the flat report is a single blob.

The exact invocation will move with the NDK’s simpleperf version. Treat the manual on the machine as the flag list. The idea will not move: sample a pinned release run, name the functions, decide whether the time is where you thought.

What it will not tell you

  • It will not give you GB/s. The harness does that. The profile explains a GB/s you already have.
  • It will not notice a wrong answer. Correctness is still an external reference, or a checksum that black_box kept alive.
  • It will not see a core you did not pin, cleanly. Samples follow threads. If the thread migrated, the profile mixes cores. Pin first.
  • It is not a thermal log. Frequency changes during a record show up as fewer or more instructions retired, not as a temperature. Keep the Phase 1 sampler for that.

The plan’s rule stands: profile before optimizing, and do not optimize before a correct end-to-end model exists. Phase 1 is allowed to profile the bandwidth kernels because those kernels are the measurement, not an optimization of a model you do not have yet.

Check yourself

Why is debug = true in the release profile not the same as a debug build?

The release profile still optimizes. debug = true only keeps symbol information in that optimized binary. A debug build is a different profile: low optimization, different machine code, timings that do not transfer.

The report shows 90% of samples in the read loop, and the loop is at 40% of measured DRAM bandwidth. Where do you look next?

Not for a different function. The time is already in the loop. Look at how the loop issues loads: dependency chains, missing prefetch, a bad stride, too few outstanding misses. Hardware counters for misses and instructions help. Rewriting a function that is 2% of samples will not move the 40%.

When is it too early to profile?

Before the result is correct, and before a timing says you are far from the roof you care about. A profile of a wrong kernel, or of a kernel already at the roof, does not choose the next edit.
