The roofline

Every piece of code is held back by one of two things: waiting for bytes to arrive from memory, or doing the arithmetic. The roofline is one picture that tells you which. The deciding number is simple: how much math the code does for each byte it reads.

1. What can hold a kernel back?

A kernel is slow for one of two reasons, and it is the one that runs out first that counts. A core needs:

  • Bytes. The numbers it works on have to come from memory. How fast they can arrive is bandwidth, in GB/s.
  • Arithmetic. Once a number has arrived, the core does math on it. Each single add or multiply is one FLOP (floating-point operation). How many the core can do per second is its peak compute, in GFLOP/s: billions of FLOPs per second.
An everyday picture

A cook gets groceries from a delivery van. The van brings a few bags per minute (bandwidth). The cook can chop a certain number of vegetables per minute (compute). If each bag only needs one quick chop, the cook spends most of the time waiting for the van. If each bag needs an hour of careful work, the bags pile up and the van waits. What decides it is not how fast the van is or how fast the cook is on their own. It is how much chopping each bag needs.

Takeaway: a kernel is held back by its bytes or by its arithmetic, whichever runs out first, and speeding up the other one changes nothing.

2. How much work does each byte carry?

Two kernels can read the same bytes and still need very different speeds. The difference is how much math each byte gets. Three examples from this project, then the name for the ratio.

  1. The Phase 0 sum. Each f32 is 4 bytes and gets one add. 1 FLOP ÷ 4 bytes = 0.25 FLOP/byte. For the whole run: 4×106 adds over 16×106 bytes calculated.
  2. Decode’s matrix × vector (GEMV). Each weight is 4 bytes and is used for one multiply and one add, then never again for this token. 2 FLOPs ÷ 4 bytes = 0.5 FLOP/byte. The output vector is tiny next to the weights, so it barely changes this.
  3. Prefill with 32 tokens. The same weight, once read, is used for all 32 tokens of the prompt: 32 times the work for the same 4 bytes. 0.5 × 32 = 16 FLOP/byte. Same weights, very different kernel.

That “chopping per bag” has a name: arithmetic intensity, the number of FLOPs the code does for each byte it reads from memory.

arithmetic intensity = FLOPs done ÷ bytes read (in FLOP per byte)

Count only the bytes that come from the level you are waiting on. If the weights stream from DRAM, the bytes that count are DRAM bytes, not the times the same line is read again from cache. Count the cache hits and the intensity is wrong, so the kernel lands in the wrong place on the chart.

Takeaway: the same weights have 0.5 or 16 FLOP per byte, depending on how many tokens use them in one pass.

3. Which limit wins for a given kernel?

Intensity alone does not give a speed. Memory delivers bytes at a fixed rate, so it can feed only so many FLOPs per second:

FLOPs per second memory can feed = intensity × bandwidth

The core can never go faster than its own peak either. The kernel gets whichever limit is lower:

best possible speed = the smaller of (intensity × bandwidth) and (peak compute)

A worked example with made-up roofs assumption: bandwidth 30 GB/s, peak 28 GFLOP/s.

Those made-up roofs are only for the arithmetic. On the real core, Phase 3 later calculated about 60 GFLOP/s for prefill on one core, more than twice the toy 28 (Prefill), so do not read 28 as this phone’s peak.

  • GEMV: 0.5 × 30 = 15 GFLOP/s from memory. The core could do 28. Memory is the lower limit, so GEMV is memory-bound: the core is idle almost half the time, waiting for weights.
  • Prefill, 32 tokens: 16 × 30 = 480 GFLOP/s from memory. The core can only do 28. Now the core is the lower limit, so prefill is compute-bound: the bytes are waiting for the math.

Which limit wins?

Slide the work per byte, or pick a kernel. The roofs are fixed at the made-up 30 GB/s and 28 GFLOP/s assumption.

Takeaway: a kernel runs at the smaller of its memory limit and the compute peak.

4. How do both limits look as one chart?

Plot every intensity against its best possible speed, and the two limits join into one shape. Put intensity along the bottom and the best speed up the side. You get two lines that together look like a roof:

  • The bandwidth roof is the slope on the left: intensity × bandwidth. Twice the work per byte, twice the speed, because each byte brings more work with it.
  • The compute roof is the flat line on the right, at the core’s peak. More work per byte no longer helps: the core is already doing math as fast as it can.
  • The ridge is where they meet: peak ÷ bandwidth. With the made-up roofs, 28 ÷ 30 ≈ 0.93 FLOP/byte. Anything left of the ridge is memory-bound. Anything right of it is compute-bound.

Rooflines are drawn with both axes on a log scale, where each gridline is ten times the one before. Without it, 0.25 and 16 cannot share one chart. The log scale also makes the slope a straight line.

Takeaway: left of the ridge a kernel is memory-bound, and right of it the kernel is compute-bound.

The Q4_0 row is the decode ceiling drawn as a roofline. A 4-bit format does the same FLOPs from about 7× fewer bytes (32 weights in 18 bytes instead of 128), so its dot moves about 7× further right, and the slope there is about 7× higher: fewer bytes per FLOP means more FLOPs per second from the same memory. It climbs until it meets the flat roof. Which one is true is a measurement, not a guess. And the arithmetic matters more than this ideal dot shows: unpacking 4-bit values costs extra instructions it does not count. Phase 6 will measure them.

The lesson for f32 decode: it lives on the slope, far from the flat roof. Making the arithmetic faster does not help it. Reading fewer bytes does, until the bytes are so few that the arithmetic becomes the limit.

Takeaway: f32 decode sits on the slope, so faster arithmetic does nothing for it and fewer bytes does.

6. What if a kernel sits below the roof?

A roof is a limit, not a promise, so a kernel can sit anywhere under it.

The Phase 0 sum is the example. Its roof at 0.25 FLOP/byte is intensity × whatever DRAM can really do. What it actually reached was 4×106 adds in ~4.9 ms measured, which is 0.82 GFLOP/s calculated, the same thing as the 3.3 GB/s from Phase 0. That is far below the slope. It was not waiting on memory; it was waiting on its own chain of adds, each one needing the answer of the last.

The wrong lesson

If you set the bandwidth roof to 3.3 GB/s, the sum sits exactly on it and looks “memory-bound”. That is backwards: 3.3 was never the speed of DRAM. Set the roof to what Phase 1 measures, and the sum drops well below the slope. That gap is latency, not a slow memory bus.

A point under both roofs is not “fine”. It means something else is slowing it down: latency, a dependency, a bad memory pattern, a throttled core, a pin that did not stick. Noticing that gap, and finding its cause, is the skill.

Takeaway: a point under both roofs has a cause, such as latency, a dependency or a throttled core, and finding it is the work.

Here is the full chart, drawn on log scales. The blue dots are kernels placed by their work per byte, sitting on whichever roof applies. The copper dot is the Phase 0 sum you measured. It does not move when you move the roofs, because it is a measurement.

Assumed roofs

Both sliders are assumptions. 30 GB/s is the Phase 0 exercise, not a measurement. 28 GFLOP/s is a toy: one 128-bit FMA (multiply-add) per cycle, 4 lanes × 2 FLOPs, at ~3.5 GHz. If the core can issue four per cycle, as wide cores often can, the roof is four times higher, about 110. Neither is a counted peak for this core.

Things to try:

  • Move the bandwidth roof anywhere a phone could plausibly reach. GEMV stays on the slope every time.
  • Raise the compute roof. The flat part rises and the ridge moves right, which makes GEMV more memory-bound, not less.
  • Set the bandwidth roof to 3 GB/s and watch the copper dot touch the slope: the wrong lesson from section 6.

Takeaway: moving the bandwidth roof moves the decode ceiling, and raising the compute roof only pushes the ridge right.

8. How will the chart get real numbers?

The roofs on this chart are guesses until they are measured. Each one has a source.

  • The bandwidth roof comes from the sweep. The single-core DRAM read from the bandwidth page is the roof for one thread; the all-core read is the roof for a threaded GEMV.
  • The compute roof has to be measured too. Do not write “4 FMAs per cycle at 3.53 GHz” and call it a fact: Phase 0 never read Oryon’s FMA throughput from anywhere. Measure a kernel that is obviously compute-bound, or count instructions with simpleperf. A made-up peak carried into a ceiling makes every ceiling built on it wrong.
  • Report the right number. For decode, report achieved GB/s as a fraction of the bandwidth roof. GFLOP/s is the wrong headline there. It becomes the right one for prefill, once the compute roof is a measurement.

Takeaway: the bandwidth roof is measured already; the compute roof is not, so any GFLOP/s ceiling is provisional.

Check yourself

A kernel reads 8 bytes and does 4 FLOPs with them. What is its work per byte?

4 ÷ 8 = 0.5 FLOP/byte, the same as f32 GEMV.

GEMV does 0.5 FLOP/byte. The ridge is at 2 FLOP/byte. Which roof matters?

Bandwidth. The kernel is left of the ridge. Raising peak FLOPs moves the flat roof up and the ridge to the right, which makes GEMV more bandwidth-bound, not less.

Why is the scalar sum not on the bandwidth roof?

Work per byte predicts which roof applies. It does not promise the kernel reaches it. One accumulator cannot keep enough loads in flight, so it achieves far less than the bus allows. The roofline is an upper bound, like the decode ceiling.

When is GFLOP/s the right number to report?

When the kernel is at or right of the ridge: prefill, or anything whose bytes are reused enough that the arithmetic is the limit. Decode GEMV is not that kernel.

What you should take away

Every kernel is held back by its bytes or its arithmetic, and its intensity says which.

The roof is an upper bound, and the gap below it is where the work is.

Measure the compute roof before trusting any GFLOP/s ceiling.
