Plotting the sweep

The working-set sweep produces dozens of numbers per core set: 65 sizes on one core, from 4 KiB, and 49 for the all-core runs, which start at 64 KiB measured. You read them as a picture: plateaus and cliffs. The phone prints the numbers, the PC saves and draws them, and both files go in results/.

What are we trying to do here?

A working set is how much memory the loop touches on each pass. The sweep runs the pure read at many working-set sizes, and each run gives one number: the bandwidth at that size. Dozens of numbers in a column are hard to read. A plateau is a stretch where the speed holds steady, and a cliff is where it drops. The picture shows those at a glance, and every later kernel is compared against these numbers.

The phone cannot make that picture itself. It has no Python, and it should spend its time on the benchmark. So the work is split: the phone measures and prints, and the PC saves the numbers as a CSV file in results/ and draws them with a Python script.

By the end you can write a CSV that keeps its conditions, explain why the size axis is logarithmic, and read the script that draws the sweep line by line.

How do the numbers get from phone to picture?

The numbers start on the phone and must end as a picture on the PC. Something has to carry them across, and something has to draw them.

The sweep runs on the phone. How do its numbers end up in results/sweep-cpu6.csv on the PC?

  • It prints them; adb carries the output back, and > on the PC writes the file
    Only printed output travels back through adb. The redirect on the PC saves it.
  • It writes the CSV into results/ on the phone
    Tempting, since the phone makes the numbers. But results/ lives on the PC; the phone only prints.
  • You read them off the phone’s screen and type them in
    Dozens of numbers by hand invites typos. Printing and redirecting copies them exactly.

The phone runs the sweep and prints its numbers. They travel to the PC through adb (the Android debug bridge), land in a CSV file in results/, and the plotting script draws them as a PNG.

The phone does no drawing. It doesn’t have Python, and it shouldn’t be busy with anything but the benchmark. The PC already has Python and matplotlib 3.10 measured. matplotlib is the Python plotting library.

Takeaway: the phone only measures; the PC draws the picture and keeps the files.

The command ends with > results/sweep-cpu6.csv. Why are Cargo’s build messages not in the file?

  • > captures only what the program printed; Cargo’s messages go to stderr
    Cargo’s own messages go to stderr, so > captures only what your program printed.
  • Cargo never prints anything during a run
    Tempting if you think of cargo as silent. The messages exist; they just don’t go into the file.
  • The phone strips the build messages before sending
    Tempting, because the phone is the one that sends the output. But the messages come from Cargo on the PC.

How do we save numbers with their conditions?

A number without its conditions cannot be compared with anything. The file has to carry the conditions along with the numbers.

A friend sends you 20 numbers with no details. What do you still need before you compare them with yours?

  • The conditions: screen, charging, start temperature and commit
    Without the screen, charging, temperature and commit, a number cannot be compared fairly.
  • Nothing; the numbers are enough
    Tempting, since the numbers are the result. But the same number can come from different conditions.
  • Only the date they were measured
    The date helps, but the screen, charging, temperature and commit matter too.

CSV (comma-separated values) is a table written as text, one row per line. Here is the whole format in a small example.

# sweep: pure read, f32, pinned cpu6
# date=2026-10-20 screen=off charging=no start_temp_c=31.2
# commit=5632c75
working_set_bytes,median_gbps
4096,88.41
8192,92.07
…
  • Lines that start with # hold the conditions of the run, as plain text.
  • working_set_bytes,median_gbps is the header. It names the two columns.
  • The real sweep files have more columns: kernel, threads, repetitions, best and worst. A script that finds columns by name ignores the extra ones.
  • Each later line is one measurement: a working-set size in bytes, then its bandwidth in GB/s.

The conditions sit at the top, so they can never be separated from the numbers. Rust writes the file with two println! calls, each one line.

println!("working_set_bytes,median_gbps");
println!("{},{:.2}", bytes, gbps);
  • {:.2} prints the number with two digits after the decimal point. Without it, Rust prints every digit the float holds.
  • If you leave out the header, the script cannot find working_set_bytes or median_gbps by name.

One file per core set (sweep-cpu6.csv, sweep-cpu0.csv, sweep-cpu0-5.csv) keeps each run complete. The numbers above are an example, not results. The real runs are in results/phase-1/raw/, for example sweep-read-core7.csv.

Takeaway: one CSV per core set, with the conditions as # lines at the top.

Why do the conditions go inside the CSV, not in a separate notes file?

  • Files get copied, renamed and compared months later, and inside the file the conditions travel with the numbers
    A number separated from “which core, screen on or off, how hot” can’t be compared with anything.
  • Because a CSV file can hold more numbers
    Size isn’t the point. The conditions are still plain # lines in the same file.
  • So the plotting script can draw the conditions as a title
    Tempting, since the script drops the # lines. It skips them; the point is to keep them with the numbers.

Why is the size axis logarithmic?

A doubling is going from one size to twice that size: 4 KB to 8 KB, for example. A linear axis puts equal steps of size at equal distances. A log axis puts each doubling at equal distances instead.

Plot sizes from 4 KB to 256 MB on a linear axis. Where do most of the points end up?

  • Crowded into the left edge
    Small sizes take little room on a linear axis, while 256 MB spans the whole width.
  • Spread evenly across the width
    Tempting, because the ticks look evenly spaced. A linear axis spaces the sizes, not the steps between them.
  • At the right edge, since the largest sizes make the most points
    Large sizes do sit at the right, but most of the points are the smaller sizes.

The sweep takes four sizes per doubling; counting only the doublings themselves (4 KB, 8 KB, 16 KB … 256 MB) gives 17 sizes spanning a factor of 65,536. On an ordinary axis the first twelve power-of-two sizes (about 45 points), everything up to 8 MB, crowd into the left 3% calculated, which is exactly where the L1 and L2 cliffs are.

Same points, two axes

An illustrative curve with the shape from the Bandwidth page, not data from this phone.

On a log axis, every doubling is the same distance, so each cache level gets room in proportion to its doublings. The y axis stays linear, so you can read GB/s directly.

Takeaway: a log size axis spreads the cache cliffs out; a linear one squeezes them against the left edge.

On a linear axis, where is the 8 MB point if the axis ends at 256 MB?

  • At about 3% of the width
    8 ÷ 256 ≈ 3%. Everything from 4 KB to 8 MB, both L1 and L2, fits in that 3%.
  • Halfway, at 128 MB
    Tempting if you read a linear axis as halving. It measures size, not doublings.
  • Halfway along either axis
    Neither. On a log axis 8 MB is 11 of 16 doublings in (69%); on a linear one, 3%.

How do we write the plotting script?

The script goes in tools/, where host-side Python lives (it runs on the PC, not the phone). It takes one or more CSV files and draws them on the same axes. It has one job: draw a picture and save it as a file, with no window to click. We build it in four steps, then show it whole.

Step 1: imports and a drawing mode with no window

import csv
import sys
from pathlib import Path

import matplotlib
# write a file; no window needed
matplotlib.use("Agg")
import matplotlib.pyplot as plt
from matplotlib.ticker import FuncFormatter
  • import loads a library: csv reads the file, sys gives the command-line file names, Path gets a short name.
  • matplotlib.use("Agg") picks the mode that writes a file and opens no window.
  • FuncFormatter lets us write our own axis labels.

Step 2: a label function for sizes

def size_label(b, _pos):
    return (f"{b / 2**10:.0f} KiB" if b < 2**20
            else f"{b / 2**20:.0f} MiB")
  • matplotlib calls this once per tick mark, with the size in bytes as b. _pos is unused.
  • 2**10 is 1,024, so b / 2**10 turns bytes into KiB. 4096 ÷ 1024 = 4, so 4096 bytes shows as “4 KiB”.
  • Below 2**20 (1 MiB) the label uses KiB, above it MiB. .0f means no decimals.

Step 3: read each file and plot it

fig, ax = plt.subplots(figsize=(8, 4.5))
for path in sys.argv[1:]:
    with open(path) as f:
        rows = list(csv.DictReader(
            line for line in f if not line.startswith("#")))
    x = [int(r["working_set_bytes"]) for r in rows]
    y = [float(r["median_gbps"]) for r in rows]
    ax.plot(x, y, marker="o", label=Path(path).stem)
  • sys.argv[1:] is the list of files named on the command line.
  • DictReader uses the header line, so r["working_set_bytes"] finds the column by name. # lines are dropped first.
  • int(...) and float(...) turn the text into numbers. Each measured point gets a dot. A line between two dots is not a measurement.

Step 4: axes, labels and the file

# each step right = twice the size
ax.set_xscale("log", base=2)
ax.xaxis.set_major_formatter(FuncFormatter(size_label))
ax.set_xlabel("working set")
ax.set_ylabel("read bandwidth (GB/s)")
ax.set_ylim(bottom=0)
ax.grid(True, alpha=0.3)
ax.legend()
fig.tight_layout()
fig.savefig("results/sweep.png", dpi=150)
print("wrote results/sweep.png")
  • base=2 makes each step a doubling, which is how the sweep sizes were chosen.
  • set_ylim(bottom=0) keeps the y axis from starting at, say, 10 GB/s, which would make a small drop look like a cliff.
  • savefig writes the file. The path is relative, so run the script from the project root.

Tested on the Phase 1 sweep files and on a copy with Windows-style line endings measured. Run it from the project root. The repository’s tools/plot_sweep.py is a longer version: it also labels each line from the file’s # lines and shades the band between the best and worst run.

Takeaway: the script reads columns by name, sets the axes, and saves a PNG under results/.

The header line says size,median_gbps instead of working_set_bytes,median_gbps. What does the script do?

  • It fails: r["working_set_bytes"] finds no column with that name
    DictReader finds columns by the header name, so the lookup for working_set_bytes has nothing to find.
  • It uses the first column, as many CSV readers do
    Tempting, since many readers go by position. This one goes by name.
  • Nothing changes, because the # lines are dropped first
    The # lines are dropped, but the header line is still read for the column names.

Bytes or gigabytes: which one?

Bandwidth is counted in bytes per second, and GB/s is one of its units. Both kinds of unit use the letters K, M and G, so they are easy to mix up.

Which is more bytes: 1 GB, or 230 bytes?

  • 230 bytes, about 7% more than 109
    230 is about 1.074 × 109, a 7% gap.
  • They are the same, a billion bytes
    Tempting, since 230 looks like a round billion. It is about 7% more than 109.
  • 1 GB, since decimal units are the bigger ones
    Decimal units are not the bigger ones here. 230 is the bigger number.

The sizes are powers of two: 4096 bytes is 4 KiB, and 1,048,576 bytes is 1 MiB. Those are KiB and MiB, which is how the script labels them. Bandwidth uses the other convention: GB/s means 109 bytes per second, which is what the decode ceiling and published figures use. Both are fine. Mixing them silently is a 7% error at the gigabyte scale (230 / 109 ≈ 1.074) calculated.

So the Rust side computes gbps = bytes_read as f64 / seconds / 1e9, and the header says median_gbps. Next month you won’t remember which one it was.

Takeaway: KiB and MiB count sizes, GB/s counts 109 bytes; say which one each number uses.

A plateau sits at 45 “GB/s” computed with 230. What is it in the site’s units?

  • About 48.3 GB/s (109)
    45 × 1.074 ≈ 48.3. Pick one convention and say which.
  • 45 GB/s, since the number is unchanged
    Tempting, but the same bytes give a different number once the unit changes.
  • About 41.9 GB/s
    That divides instead of multiplies. 230 is the bigger unit, so the number in 109 grows.
