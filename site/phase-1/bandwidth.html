Bandwidth

Decode’s yardstick is how many bytes per second a core can read, not how many FLOPs it can retire. Phase 1 measures that yardstick before any matmul exists, so a later kernel has something honest to be a percentage of.

Which four kernels do we time?

Each kernel is a small loop over arrays. We copy the habits of STREAM, a standard benchmark for memory bandwidth, and add a plain read that STREAM’s copy does not isolate. Each loop streams: it walks the array once, in order. None should wait on the data it read last, or the test turns back into the Phase 0 sum.

KernelPer elementBytes counted (STREAM)What it stresses

scalea[i] = q * b[i]same as copy, plus a multiplyWhether a little arithmetic slows the stream.
adda[i] = b[i] + c[i]3 × n × 4: two reads, one write. About 4 × n × 4 on the busMore reads in flight. Closer to “can the core request enough.”
read / suma reduction into several independent accumulators1 × n × 4, reads onlyThe decode case. Weights are read, not written back.

An accumulator is the variable that holds a running total. With s += x there is one, so each add waits for the add before it. With four or eight, the adds run in separate chains and are added together at the end, so the core has independent work to overlap. Use several accumulators: one is the latency chain from Phase 0, and it reports ~3 GB/s again and teaches you nothing about DRAM. The final add of the accumulators is negligible.

Wrap inputs and the reduction result in black_box, which tells the compiler not to optimize the value away. Time with the harness only when one iteration takes milliseconds, not tens of nanoseconds. A 4 KB buffer is too small for per-call timing. Time a batch of passes over the small buffer and divide. That is the batch timer Phase 0 deliberately did not add. This is where it earns its place.

Takeaway: use several accumulators and black_box, or the number measures the adds, not memory.

How many bytes did the loop really move?

GB/s is bytes moved divided by seconds, so the numerator is where a number can lie. Example: a copy of 1,000 floats reads 4,000 bytes and writes 4,000 bytes, so it moves 8,000 bytes if you count both, or 4,000 if you count only the read.

  • Pick one convention, write it in the results file, and never compare a “read-only GB/s” with a “read+write GB/s” under the same name. Mixing them makes two kernels look different when only the counting differs.
  • Writes move more than they look. Before a core writes into a line that is not in its cache, it reads that line from DRAM first (write-allocate). DRAM is the phone’s main memory, behind the caches. So a copy really moves about 12n bytes: read b, read a’s old line, write a. STREAM counts 8n anyway, and so do our results. Phase 1 measured copy at 42 GB/s counted that way measured; × 1.5 for the hidden reads gives about 63 GB/s of real traffic calculated, the same as the pure read.
  • The pure read moves 4n bytes. That is the number to put next to a later f32 GEMV, which also reads each weight once and writes a much smaller output.
  • Do not count a write that stayed in cache, if what you wanted was DRAM bandwidth. For a working set that fits in L1 (the fastest cache), the GB/s you compute is cache bandwidth, and that is the point of the sweep. Label the plateau. Do not call every plateau DRAM, or a cache number will pass for memory speed.
  • Use the harness median, not a single pass. A 256 MB read is long enough that one pass is a real sample. A 4 KB read is not, unless you repeat it, because one short pass is mostly noise.

Takeaway: count the bytes the same way every time, and say which cache level a number came from.

What does a working-set sweep show?

The working set is how much memory the loop touches on each pass. A sweep runs the pure read at many working-set sizes and plots GB/s against size. Run it from about 4 KB to about 256 MB, four sizes per doubling. What you are looking for is plateaus and cliffs. A plateau means “this whole region hits in the same level.” A cliff means “the working set just stopped fitting.”

How to read a cliff without a datasheet, from left to right:

  1. The leftmost fast plateau is the data that fits in L1. Its right edge is near the L1 data size, often a bit past it because of associativity and because you are streaming, not randomly accessing.
  2. The next plateau is L2, the second-level cache, if the core can use a cluster L2 alone. If launch coverage is right, look for something that stays fast into the megabytes and falls before or around 12 MB. If it falls at 2 MB, believe the phone.
  3. A small further step, or none, is the SLC. On some chips it is visible. On some it is a slope into DRAM. Do not invent a step to match a diagram.
  4. The right-hand flat line, from tens of megabytes out to 256 MB, is DRAM. That flat value, on one pinned core, is the single-core read bandwidth the GEMV will be judged against.

Repeat the sweep pinned to one prime core, one performance core, and a set of cores in parallel. Pinned means the test is locked to one core. That gives three curves, not one. The parallel curve shows whether one core was leaving the bus idle.

Random access, as opposed to streaming, is a different plot: it shows latency, the wait for one value to arrive, and prefetchers help less. A prefetcher is hardware that guesses the next address and loads it early. Do the stream first; it is the decode analogue. A latency plot is optional and should not be labeled bandwidth.

Takeaway: read the plot for cliffs, and label each plateau by the cache it fits in.

Why is the pure read the number that matters?

A weight during decode is loaded and not stored back. Take copy, which reads and writes. A matmul reads its weights without writing them back, so copy measures traffic the matmul does not have. Writes are often slower or separately limited. If you only measure copy, you will compare a GEMV against the wrong ceiling. The kernel will look “efficient” because it matches a number that was already dragged down by stores.

Add and scale are there so you can see whether a little arithmetic changes the stream. If scale matches copy, arithmetic is free at that intensity. If scale is much slower, you are no longer bandwidth-bound, which is a useful surprise before you write a kernel that assumes the opposite.

The Phase 0 sum is the cautionary version of this kernel: one accumulator, 3.3 GB/s, latency-bound. If the new read benchmark, with several accumulators and a 64 MB buffer, still reports a few GB/s, the accumulators are not independent enough, or the compiler deleted them. Check the result with black_box. Predict that a DRAM-sized buffer should be far above 3.3 if the core can stream at all. If it is not far above, believe the measurement and find out why, rather than “fixing” the number.

Takeaway: compare decode against the pure read, not against copy.

What conditions must we write down?

Write these next to every row. A GB/s without them cannot be compared with the row you take next week.

  • which cores, and that the pin succeeded,
  • screen on or off,
  • charging or not — charging changes thermals and, on some phones, the current sensor,
  • starting temperature, from /sys/class/thermal/,
  • scaling_cur_freq during the run, not only the max,
  • release build, and the commit.

The long run is separate. Run 5 minutes or more of the DRAM-sized read, logging frequency and temperature. The governor is the software that sets the clock speed. The first 10 seconds show the optimistic number. The number after the governor has pulled the clocks down is the one a chat session will actually live at. Both belong in results/. They are not the same result.

Takeaway: a GB/s without its conditions cannot be compared, and the first seconds are not the long-run number.

Check yourself

Why is s += x not the read benchmark?

Each add waits for the previous add. The core cannot keep the memory system busy, and the time you measure is add latency. Several independent accumulators break that chain. The Phase 0 number is what you get when you forget.

A 32 KB read reports 80 GB/s and a 128 MB read reports 18 GB/s. Which one is DRAM?

The 128 MB one, if 128 MB is past every cache. The 80 GB/s is a cache plateau. Quoting 80 as “the phone’s bandwidth” will make every DRAM-bound kernel look terrible for the wrong reason. Label the plateau by the cliff, not by the biggest number on the plot.

Copy reports 12 GB/s and the pure read reports 20 GB/s on the same core and the same large size. Is the read kernel “better”?

They are not the same numerator. Copy moves reads and writes, and each write first reads its line too (write-allocate). The read kernel moves reads only. 20 GB/s of reads can coexist with a lower copy number because stores are extra traffic. Compare a future GEMV to the read, not to the copy.

What you should take away

Bandwidth is bytes moved per second, so count the bytes the same way every time.

A sweep shows the cache plateaus and the DRAM line, and the flat DRAM value is what a decode kernel is judged against.

Write down the conditions, because a number without them is not comparable.
