Bandwidth

Decode’s yardstick is how many bytes per second a core can read, not how many FLOPs it can retire. Phase 1 measures that yardstick before any matmul exists, so a later kernel has something honest to be a percentage of.

The four kernels

These are the STREAM habits, plus the read that STREAM’s copy does not isolate. Each one streams. None of them should have a loop-carried dependence on the data, or you will remeasure the Phase 0 sum.

KernelPer elementBytes counted (STREAM)What it stresses
copya[i] = b[i]2 × n × 4 for f32: one read, one write. About 3 × n × 4 really crosses the memory bus (see below)Read and write bandwidth together.
scalea[i] = q * b[i]same as copy, plus a multiplyWhether a little arithmetic slows the stream.
adda[i] = b[i] + c[i]3 × n × 4: two reads, one write. About 4 × n × 4 on the busMore reads in flight. Closer to “can the core request enough.”
read / suma reduction into several independent accumulators1 × n × 4, reads onlyThe decode case. Weights are read, not written back.

The reduction has to be several accumulators, not s += x. One accumulator is the latency chain from Phase 0, and it will report ~3 GB/s again and teach you nothing about DRAM. Four or eight independent sums, added together at the end, give the core enough independent work to keep loads in flight. The final add of the accumulators is negligible.

Wrap inputs and the reduction result in black_box. Time with the harness only when one iteration is milliseconds, not tens of nanoseconds. A 4 KB buffer will be too small for per-call timing. Time a batch of passes over the small buffer and divide. That is the batch timer Phase 0 deliberately did not add. This is where it earns its place.

Count bytes honestly

GB/s is bytes moved divided by seconds. The lie is in the numerator.

  • A copy of n floats moves 8n bytes if you count the read and the write, or 4n if you count only the read. Pick one convention, write it in the results file, and never compare a “read-only GB/s” with a “read+write GB/s” under the same name.
  • Writes move more than they look. Before a core writes into a line that is not in its cache, it reads that line from DRAM first (write-allocate), so a copy really moves about 12n bytes: read b, read a’s old line, write a. STREAM counts 8n anyway, and so do our results. Phase 1 measured copy at 42 GB/s counted that way measured; × 1.5 for the hidden reads gives about 63 GB/s of real traffic calculated, the same as the pure read.
  • The pure read moves 4n bytes. That is the number to put next to a later f32 GEMV, which also reads each weight once and writes a much smaller output.
  • Do not count a write that stayed in cache and never reached DRAM, if what you wanted was DRAM bandwidth. For a working set that fits in L1, the GB/s you compute is cache bandwidth, and that is the point of the sweep. Label the plateau, do not call every plateau DRAM.
  • Use the harness median, not a single pass. A 256 MB read is long enough that one pass is a real sample. A 4 KB read is not, unless you repeat it.

The working-set sweep

Run the pure read at sizes from about 4 KB to about 256 MB, a few sizes per doubling. Plot GB/s against size. You are looking for plateaus and cliffs. The plateaus are “this whole region hits in the same level.” The cliffs are “the working set just stopped fitting.”

How to read a cliff without a datasheet:

  1. The leftmost fast plateau is the data that fits in L1, plus whatever the prefetcher hides. Its right edge is near the L1 data size, often a bit past it because of associativity and the fact that you are streaming, not randomly accessing.
  2. The next plateau is L2, if the core can use a cluster L2 alone. If launch coverage is right, look for something that stays fast into the megabytes and falls before or around 12 MB. If it falls at 2 MB, believe the phone.
  3. A small further step, or none, is the SLC. On some chips it is visible. On some it is a slope into DRAM. Do not invent a step to match a diagram.
  4. The right-hand flat line, from tens of megabytes out to 256 MB, is DRAM. That flat value, on one pinned core, is the single-core read bandwidth the GEMV will be judged against.

Repeat the sweep pinned to one prime core, one performance core, and a set of cores in parallel. Three curves, not one. The parallel curve is how you see whether one core was leaving the bus idle.

Random access, as opposed to streaming, is a different plot: it shows latency, and prefetchers help less. Do the stream first. It is the decode analogue. A latency plot is optional and should not be labeled bandwidth.

Why the pure read is the one that matters

A weight during decode is loaded and not stored back. Copy bandwidth includes write traffic the matmul does not have, and writes are often slower or separately limited. If you only measure copy, you will compare a GEMV against the wrong ceiling and conclude the kernel is “efficient” because it matches a number that was already dragged down by stores.

Add and scale are there so you can see whether a little arithmetic changes the stream. If scale matches copy, arithmetic is free at that intensity. If scale is much slower, you are no longer bandwidth-bound, which is a useful surprise before you write a kernel that assumes the opposite.

The Phase 0 sum is the cautionary version of this kernel: one accumulator, 3.3 GB/s, latency-bound. If the new read benchmark, with several accumulators and a 64 MB buffer, still reports a few GB/s, the accumulators are not independent enough, or the compiler deleted them. Check the result with black_box and by predicting that a DRAM-sized buffer should be far above 3.3 if the core can stream at all. If it is not far above, believe the measurement and find out why, rather than “fixing” the number.

Conditions

Write these next to every row. A GB/s without them cannot be compared with the row you take next week.

  • which cores, and that the pin succeeded,
  • screen on or off,
  • charging or not — charging changes thermals and, on some phones, the current sensor,
  • starting temperature, from /sys/class/thermal/,
  • scaling_cur_freq during the run, not only the max,
  • release build, and the commit.

The long run is separate: 5 minutes or more of the DRAM-sized read, logging frequency and temperature. The first 10 seconds are the optimistic number. The number after the governor has pulled the clocks down is the one a chat session will actually live at. Both belong in results/. They are not the same result.

Check yourself

Why is s += x not the read benchmark?

Each add waits for the previous add. The core cannot keep the memory system busy, and the time you measure is add latency. Several independent accumulators break that chain. The Phase 0 number is what you get when you forget.

A 32 KB read reports 80 GB/s and a 128 MB read reports 18 GB/s. Which one is DRAM?

The 128 MB one, if 128 MB is past every cache. The 80 GB/s is a cache plateau. Quoting 80 as “the phone’s bandwidth” will make every DRAM-bound kernel look terrible for the wrong reason. Label the plateau by the cliff, not by the biggest number on the plot.

Copy reports 12 GB/s and the pure read reports 20 GB/s on the same core and the same large size. Is the read kernel “better”?

They are not the same numerator. Copy moves reads and writes, and each write first reads its line too (write-allocate). The read kernel moves reads only. 20 GB/s of reads can coexist with a lower copy number because stores are extra traffic. Compare a future GEMV to the read, not to the copy.
