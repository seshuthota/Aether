What Phase 1 measured

The Phase 1 pages before this one were written before anything was measured. This page is the answer sheet: the yardstick table from results/phase-1.md, the two sweeps as plots, and what each number means for the engine. Every later kernel is compared against these numbers.

Conditions

All runs on 2026-10-21, on battery (adb over Wi-Fi, so no USB power), screen kept on, battery saver off, each run started with the hottest CPU zone below 44–48 °C measured.

On battery, the vendor caps the clocks well below their maximum: under load the prime cores (max 4.32 GHz) ran at 2.44 GHz and the performance cores (max 3.53 GHz) at 2.40 GHz. With the screen off the caps fall further, to 1.02 and 1.79 GHz, which is why every run keeps the screen on. So every number here is an on-battery number. Plugged in, or in a performance mode, they would be different, and that has not been measured.

Two smaller facts from the same runs: the CPU reports a 64-byte cache line through the CTR_EL0 register, so 64-byte alignment is the right choice; and there are no efficiency cores, so “prime vs efficiency” in the plan became prime vs performance.

Programs: examples/bw_sweep.rs and examples/bw_sustained.rs, run by scripts/phase1-runs.sh. Every CSV in results/phase-1/raw/ starts with the conditions it ran under.

The read sweep

This is the plot Bandwidth told you to look for. One buffer per run, read again and again; the size grows from 4 KB to 256 MB, four sizes per doubling. For the multi-core lines the buffer is split between the threads, so the x axis is the total size.

How to read it, following the blue line (one prime core) from left to right:

  1. Up to about 90 KB: ~102 GB/s. The whole buffer fits in L1. The cliff sits just below 96 KB, Oryon’s L1 data cache size. The first steady plateau is the cache size you can see without any documentation.
  2. 128 KB to about 2–3 MB: ~67 GB/s. L2. Its edge is less clean to read off, likely because the L2 is shared by a cluster of cores (12 MB per cluster, according to launch coverage assumption).
  3. 4 to 8 MB: a dip to 46–57 GB/s, slower than DRAM itself. Not explained yet (see still open).
  4. 64 MB and up: ~61 GB/s. DRAM. Every line converges here: the bus, not the cores, is the limit.

The orange line (one performance core) has the same shape, lower everywhere: about 0.6× the prime core in L1 and 0.7× from DRAM, at nearly the same clock cap (2.40 vs 2.44 GHz). The same cores, the same caps, but a large difference. Phase 2 hit the same puzzle with the scalar model.

The multi-core lines start at 64 KB, so their L1 region is where each thread’s piece fits its own L1: eight L1 caches together give about 400 GB/s. That is the speed of data a kernel already has close by, and the reason GEMM works hard to reuse it.

One core nearly fills the bus

The plan expected one core to fall well short of the whole phone’s bandwidth, so that decode would need several threads just to read the weights fast enough. On this phone that is true only for a performance core: 43 of ~67 GB/s, about 64 %. One prime core gets 61 of ~67, about 90 % calculated.

So decode on one prime core is close to the memory limit already, if the kernel keeps up. Phase 2’s scalar loop read only 5.4 GB/s; Phase 3’s NEON GEMV reached 41–49 GB/s from DRAM. The yardstick says how much is left: about 61.

For stories15M in f32, 60.8 MB per token and 61 GB/s gives a ceiling of about 1,000 tokens per second on one prime core calculated. Phase 3 reached 422.

Copy, scale, add, and misalignment

  • In L1, copy and add beat read (up to ~145 GB/s counted). They move a read and a write per element, and a core can usually run loads and stores side by side assumption, so in cache the two add up.
  • From DRAM they lose: 42 / 43 / 46 GB/s for copy / scale / add. The writes have a hidden cost: before writing into a line, the cache first reads it from DRAM (write-allocate). The real traffic is 1.5× the counted bytes for copy and scale, 1.33× for add. 42 × 1.5 ≈ 63 GB/s, the same as the read limit calculated.
  • From DRAM, scale tracks copy (43 vs 42 GB/s): one multiply per element costs nothing when the stream is the limit. In L1 it does show: scale peaks near 120 GB/s, copy near 145.
  • Misalignment costs 3–5 %: 97 vs 102 GB/s in L1, 59 vs 61 from DRAM. Measurable, small. AlignedBuf (src/aligned.rs) is kept mostly so every benchmark starts from the same layout.

Five minutes of heat

A fresh number and a sustained number answer different questions (Power and heat). Over 5 minutes:

  • All 8 cores lost only 2.6 % (70.2 → 68.4 GB/s), although the phone reached 88 °C and the governor cut the clocks from 2.40 / 2.44 GHz to 1.36 / 1.02 GHz. Eight cores at a low clock still keep enough loads in flight to fill the bus. A memory-bound job does not need full clocks.
  • One prime core lost about 22 % (61 fresh → 47.5 average). A single core needs its clock to issue loads fast enough.

For decode, this means a single-thread speed measured on a cool phone is optimistic for a long chat; several threads hold their speed better.

Energy per gigabyte

The plan’s method, reading current_now from /sys/class/power_supply, does not work here: SELinux denies those files to the shell user. Android’s battery service is readable instead, but it refreshes only every 45–85 seconds. So energy was measured from the battery’s charge counter: the charge used between its first and last step inside each 5-minute run, times the battery voltage, minus a 5-minute idle baseline measured just before.

The prime core moved 47 % more bytes per second at 18 % more power, so each gigabyte cost it less in total. Above idle, the two are within this method’s resolution. The total is the one that matters for a phone: the screen, radio and the rest draw power the whole time the job runs, so finishing sooner (“race to idle”) wins for memory-bound work.

How precise is this?

One step of the charge counter is about 1 mAh, about 3.6 % of a 5-minute prime-core run, and the idle baseline itself varied from 0.53 to 0.70 W between runs. Treat differences under about 10 % as noise. The 0.082 vs 0.066 total is a real difference; 0.060 vs 0.055 above idle is not.

Still open

  • The 4–8 MB dip. One core reads slower from a 4–8 MB buffer than from DRAM (46–57 vs 61 GB/s). Candidates: the 12 MB L2 being shared by the cluster, the system-level cache, prefetcher behaviour. A simpleperf question.
  • Why the performance core is so much slower at nearly the same clock cap. The real clock under load may be lower than the cap.
  • Plugged-in numbers. Everything here is on battery caps.
  • The compute roof. Phase 1 measured the memory roof of the roofline; the peak FMA rate has not been measured.

Check yourself

Why does the read sweep have flat steps instead of a smooth slope?

Each step is one level of memory. While the whole buffer fits in a level, every read comes from it at that level’s speed. Past its size, reads spill to the next, slower level, and the speed drops to the next step.

Copy reports 42 GB/s from DRAM and read reports 61. Is the bus slower for copies?

No. Copy’s count leaves out the reads that write-allocate adds. Its real traffic is about 1.5 × 42 ≈ 63 GB/s, the same limit.

All-core bandwidth fell 2.6 % in 5 minutes, one prime core fell 22 %. Why the difference?

Eight cores have far more loads in flight than the bus needs, so even at a low clock they keep it full. One core is just barely enough at full clock; when the governor lowers its clock, it issues loads more slowly and the bandwidth falls with it.

What is the decode ceiling for stories15M (60.8 MB per token) on one prime core?

About 61 GB/s ÷ 60.8 MB ≈ 1,000 tokens per second, if the kernel kept up with memory. It is a ceiling, not a prediction.
