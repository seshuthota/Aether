Cores and pinning

The scheduler decides where your thread runs, and it can move the thread at any time. A bandwidth number from an unpinned run is a blend of cores, and the next run blends them differently. Pinning lets a measurement name the core it used.

Which cores are which?

Linux gives each core a number, and the number does not say how fast the core is. The map has to come from the chip. Phase 0 read it from cpuinfo_max_freq and /proc/cpuinfo measured. It is repeated here because every Phase 1 run should say which of these it used.

Current frequency is scaling_cur_freq, not the max. A core listed at 4.32 GHz may run much slower when the benchmark starts, and the governor may pull it down again once the phone is hot. Skip the current reading and a 4.32 GHz label describes a clock you never had. Record both: the max tells you the core class, and the current frequency during the run tells you what the core actually did.

Takeaway: read the core map from the chip, and record the clock each run actually used.

Are the prime cores a different design?

On many phones the fast and slow cores are different designs: a wide core and a narrow one, with different caches and different NEON throughput. This phone’s cpuinfo does not say that. Every core reports the same part number. The split we measured is the maximum frequency.

That still matters, for two reasons. You have to measure both rather than deduce them:

  • A higher clock can finish a dependency chain sooner. That is a run of operations where each step waits for the one before. The Phase 0 sum was that kind of kernel, so a prime core might finish it quicker. A streaming read that is already waiting on DRAM might not, because the core is not the limit.
  • A higher clock usually costs more energy per second. It does not automatically cost more energy per byte. If the prime core finishes a GB sooner, joules can go either way. Phase 1’s energy comparison is this question. The plan’s “efficiency core is more efficient” sentence does not apply until you have shown that 3.53 GHz is the efficient choice on this chip, or that it is not.
Design habit

Keep core numbers in one config, not scattered through kernels. The engine should ask for “the prime set” and get {6, 7} on this phone. Another phone will number them differently. Phase 1 can hard-code the set in the benchmark binary. The habit is to write it down in one place and in the results log.

Takeaway: on this phone the prime and performance cores differ in clock, so measure whether that clock helps each kernel.

What does pinning actually do?

An unpinned thread can move between cores while it runs, so one timing mixes several cores. Pinning stops that. sched_setaffinity, called through libc (the C library Rust uses on Android), takes a thread and a set of CPUs it may run on. A set of one CPU is a pin. The kernel will not migrate that thread to another core for load balance.

Pinning does not do everything you might hope:

  • It does not set the clock. The governor still ramps and throttles. Pinning to cpu6 does not mean you are at 4.32 GHz.
  • It does not reserve the core. Another process can still be scheduled there if you only set affinity and do not isolate the CPU. On a phone you usually cannot isolate. Run with the screen in a known state, and treat a noisy max as the scheduler, the way Phase 0 did.
  • It does not pin memory. DRAM is shared. Pinning a thread does not give it a private memory controller.

Call it at the start of the benchmark thread, and check the return value. A failed pin that you ignore is an unpinned run wearing a comment that says otherwise.

Takeaway: pinning fixes which core runs the thread, but not the clock or the shared memory.

Which core sets should you measure?

A result only means something for the cores it ran on, so pick each set on purpose. The plan’s sweep, applied to this phone rather than to a phone with efficiency cores:

  1. One prime core, cpu6 or cpu7. Single-thread DRAM read, and the working-set curve.
  2. One performance core, any of cpu0–cpu5. Same kernels. The comparison is the point: does the clock gap show up in GB/s, or only in latency-bound code?
  3. All six performance cores. Then, separately, performance plus prime. “All cores” is not one configuration when the cores are not equal. Write down the set.

Do not include a fictional efficiency core. There isn’t one. If a later phone has one, the config struct grows a third set. This phone’s table should not have an empty row pretending to be little-core data.

Thread count and core set are different knobs. Six threads pinned to six performance cores is not the same as six threads free to land on the two prime cores as well. Record both.

Takeaway: name the core set in every result, because the same thread count on different cores is a different run.

Check yourself

Why are the fast cores 6 and 7, not 0 and 1?

Because that is what cpuinfo_max_freq said on this phone. Linux CPU numbers are not a performance ranking. Read the file. Do not copy a diagram from another SoC.

Does pinning to a prime core mean the benchmark ran at 4.32 GHz?

No. 4.32 GHz is the maximum. scaling_cur_freq during the run is the clock you actually got. Thermals and the governor move it. A results line that says “prime” without a frequency trace is incomplete.

Why might a streaming read look the same on cpu0 and cpu6, while the Phase 0 sum does not?

The sum waits on add latency, which scales with clock. A streaming read waits on the memory system, which may not. If they differ, the memory path from the two clusters is not the same. If they match, the clock is not the limit. Both answers are useful. Neither is known yet.

What you should take away

The core map comes from the chip, so read it and write the core set down with every number.

Pinning fixes the core, but not the clock, the shared memory or the thermal state.

Measure the prime and performance cores separately, and say which clock each one ran at.
