Reading /sys from Rust

Core clocks, temperatures, battery current and voltage are all plain text files under /sys. Reading one is a single standard-library call. The care goes into turning the text into a number with the right unit.

What are we trying to do here?

The benchmarks need to know what the phone is doing while they run: how fast the cores are clocked, how hot the chip is, and how much current the battery draws. Android publishes these as files under /sys, so reading those files is the way in. The Power and heat page says which files the plan wants, and why energy and heat matter to the engine.

Each of those files is only text. A bare 3532800 has no unit, and a file can name a different unit on another phone. A wrong unit gives a wrong number and no error, so the code has to get the unit right on purpose.

By the end of this page you can read one sysfs file into an i64, convert it to real units, and find the right sensor by its name rather than its number.

Is a sysfs file stored anywhere?

The current clock speed is in a file called scaling_cur_freq. But ls -l shows 4096 bytes for most of these files, and the text inside is a few characters. sysfs is the part of the filesystem under /sys where the kernel shows its state as files.

scaling_cur_freq holds a number that changes as the clock changes. Is that number stored in the file on disk?

  • No. The kernel works the number out when you read the file.
    The text is made fresh on every read. Nothing is kept on disk.
  • Yes. The kernel writes it each time the clock changes.
    The clock does change, but the kernel does not save the text. Each read builds it.
  • Yes, and 4096 bytes is the length of that stored number.
    4096 is a placeholder size, not the length of the text.

The size is a placeholder, not the length of the text. Nothing under /sys is stored on disk. When you open scaling_cur_freq, the kernel works out the current clock and hands you text, such as 3532800 and a newline. Read it again a millisecond later and you may get a different number.

So reading is the measurement. The value is true for the moment of the read and nothing longer. Keep an old reading and you are reporting the past.

Takeaway: a sysfs file is computed when you read it, so every read is a fresh measurement.

A friend reads scaling_cur_freq at noon, gets 3532800, and says the clock was 3.5 GHz all afternoon. What is wrong?

  • The read is a measurement of one moment. The next read may differ.
    Each read is fresh, so one noon reading says nothing about the afternoon.
  • Nothing: the file keeps its last value until the next boot.
    That treats the file as stored. The text is computed on each read.
  • Nothing: the 4096-byte size shows the value is current.
    The size is a placeholder. It says nothing about how fresh the text is.

How do you read a number from one?

The file gives you text like "3532800\n". The program needs an i64, a signed 64-bit whole number. Four small steps get there.

The file you name does not exist. Should the function panic, or return an error to its caller?

  • Return an error, so the caller decides what a missing file means
    A Result lets the caller decide. The ? in step 1 hands the error back.
  • Panic, so the bug is found at once
    A panic stops the whole benchmark. The caller may want to record the sensor as missing.
  • Return Ok(0)
    Zero looks like a real reading, so a missing sensor would pass as a value.

Step 1: read the text

let text = std::fs::read_to_string(path)?;     // "3532800\n"
  • read_to_string opens the file, reads everything and closes it.
  • The ? returns the error to the caller if the read failed.

Step 2: remove the newline

text.trim()                                    // "3532800"
  • trim() removes the trailing newline. Without it, parse fails on every file.

Step 3: turn it into a number

// Ok(3532800), or Err if not a number
.parse::<i64>()
  • ::<i64> picks the number type. It is i64, signed, because current_now can be negative.

Step 4: give the function one error type

.map_err(|e| std::io::Error::new(std::io::ErrorKind::InvalidData, e))
  • map_err turns a parse error into an I/O error, so the function has one error type.
  • A Result lets the caller decide what a missing file means.

All four together

fn read_number(path: &str) -> std::io::Result<i64> {
    let text = std::fs::read_to_string(path)?;     // "3532800\n"
    text.trim()
        .parse::<i64>()
        .map_err(|e| {
            std::io::Error::new(std::io::ErrorKind::InvalidData, e)
        })
}

It can fail three ways. Each one tells you something, and handling it badly stops your benchmark:

ErrorUsually means
NotFoundThis phone names the file differently, or the core or zone number doesn’t exist.
PermissionDeniedThe shell user may not read it. Android limits some of /sys with SELinux. Record the sensor as unavailable rather than crash the benchmark.
InvalidDataThe text wasn’t one number. Some files hold words (status is Discharging) or several values. Read those with read_to_string and keep the text.

Takeaway: read, trim, parse, and return the error; never assume the file exists or holds one number.

The sampler gets PermissionDenied on one thermal zone. Should the benchmark stop?

  • No. Record the zone as unreadable and keep the rest.
    The benchmark is the measurement; the sensor is extra. Say so in the results.
  • Yes: any unreadable file makes the run invalid.
    One sensor is extra. The benchmark itself is still valid.
  • No, and skip the zone silently so the results stay clean.
    Hiding a missing sensor hides a gap. Record it in the results.

What unit is the number in?

A bare 3532800 means nothing until you know its unit. A unit says how big one step of the number is. Hertz (Hz) counts cycles per second; kHz, MHz and GHz are a thousand, a million and a billion of them.

scaling_cur_freq reads 3532800. How big is one step of that number?

  • 1 kHz, so the clock is 3.5328 GHz
    The kernel documents this file in kHz. 3,532,800 kHz is 3.5328 GHz.
  • 1 Hz, so the clock is 3.5 MHz
    Hz is the SI base unit, but this file is documented in kHz, not Hz.
  • 1 MHz, so the clock is 3.5 THz
    The file is documented in kHz, so one step is not 1 MHz.

For this one it is kHz, so the clock is 3,532,800 ÷ 1,000,000 = 3.5328 GHz. The kernel’s documentation fixes the unit for each file. Phone vendors usually follow it, not always.

power_supply/battery/current_nowµA÷ 1,000,000 → A. Sign varies by device.

Convert to f64 before multiplying. Microamps times microvolts is 10−12 watts per unit, and the raw product of two seven-digit numbers is fine in f64 but easy to get wrong in your head. Write the unit into the name: current_ua, power_w. Skip that and a milliampere gets read as an ampere without anything complaining.


Takeaway: look up the unit, convert in f64, and put the unit in the variable name.

How do you find the right files?


The plan lists paths such as thermal_zone0, but thermal zone numbers aren’t stable across phones, and the plan’s paths are examples. A thermal zone is one of the kernel’s temperature readings, each in its own numbered folder under /sys/class/thermal.



  
The plan’s path is thermal_zone0. Does that number name the same sensor on every phone?

  
    
    
  • No. Zone numbers differ between phones, so read the type file. 
    The number is just the folder’s name. The type file says what the sensor is.
    • 
    
  • Yes. Zone 0 is always the first sensor on any phone. 
    The lowest number is not a promise. The plan’s path is an example.
    • 
    
  • Yes, if the phone runs the same Android version. 
    The number is not a stable name, whatever the software version.
    • 
  




A wrong guess reads the wrong sensor. Each zone has a type file that names its sensor, so list the directory and read them:


for entry in std::fs::read_dir("/sys/class/thermal")? {
    let path = entry?.path();
    if let Ok(kind) = std::fs::read_to_string(path.join("type")) {
        println!("{}  {}", path.display(), kind.trim());
    }
}


    
  
  • read_dir lists the entries of a directory. Each entry is itself a Result, hence the ? twice.
    • 
  
  • path.join("type") builds the path to that zone’s type file.
    • 
  
  • if let Ok(kind) skips any entry whose type can’t be read.
    • 
  
  • The directory also holds cooling_deviceN folders, which control cooling rather than measure temperature. They have a type file too, so they show up in this list; ignore them.
    • 



Pick the zones you want by name once, by hand, and write the names in the results file. A CPU sensor and a battery sensor answer different questions.


Takeaway: choose sensors by their type name, not by zone number.

What does a read cost?


You may want to read these files often. Every read is a system call, a request to the kernel.



  
Can you read sysfs files inside a timed benchmark loop without changing the timing?

  
    
    
  • No. Each read is a kernel request that takes microseconds, so keep it out. 
    A kernel request costs roughly microseconds (an assumption). Reads belong in the sampler.
    • 
    
  • Yes. A read is just a memory access. 
    A read goes through the kernel and may ask a hardware chip. It is not a memory access.
    • 
    
  • Yes. The kernel keeps the text ready, so reads are free. 
    The kernel builds the text fresh on every read. Nothing is kept ready.
    • 
  




The kernel runs driver code to produce the text, and some drivers have to ask a hardware chip. That is roughly microseconds assumption: nothing at ten samples a second, but far too much inside a loop you are timing. Reads belong in the sampler thread, never in the benchmark.


If you want to know the real cost, time a thousand reads of one file with the Phase 0 harness. That is a good first sysfs experiment.


Takeaway: sysfs reads are cheap for a sampler and too dear for the code under test.



  
While the benchmark runs, the sampler reads the battery ten times a second. Does that disturb the timed code?

  
    
    
  • No. The reads run on the sampler’s thread, away from the timed code. 
    Ten reads a second is small, and the reads sit in the sampler for this reason.
    • 
    
  • Yes. Any read at all adds its cost to the timing. 
    The cost matters for reads inside the timed code. The sampler’s reads are on another thread.
    • 
    
  • Yes. The sampler must wait until the benchmark ends. 
    The sampler runs beside the benchmark, not after it. See the sampler figure on the power page.

What you should take away


A sysfs file is text the kernel makes when you read it, so each read is one fresh measurement.


Read, trim, parse, return the error, then convert using the documented unit.


Find sensors by name, and read them from the sampler, not from the benchmark.
