Reading /sys from Rust

Core clocks, temperatures, battery current and voltage are all plain text files under /sys. Reading one is a single standard-library call. The care goes into turning the text into a number with the right unit.

How to use this page

Power and heat lists which files the plan wants. This page is how the Rust code reads them. Before writing any code, read each one by hand with adb shell cat.

Is a sysfs file stored anywhere?

You want the current clock speed, and a file called scaling_cur_freq has it. But ls -l shows 4096 bytes for most of these files, and the text inside is a few characters. sysfs is the part of the filesystem under /sys where the kernel shows its state as files. The size is a placeholder, not the length of the text.

Nothing under /sys is stored on disk. When you open scaling_cur_freq, the kernel works out the current clock and hands you text, such as 3532800 and a newline. Read it again a millisecond later and you may get a different number.

So reading is the measurement. The value is true for the moment of the read and nothing longer. Keep an old reading and you are reporting the past.

Takeaway: a sysfs file is computed when you read it, so every read is a fresh measurement.

How do you read a number from one?

The file gives you text like "3532800\n". You want an i64. Four small steps get there.

Step 1: read the text

let text = std::fs::read_to_string(path)?;     // "3532800\n"
  • read_to_string opens the file, reads everything and closes it.
  • The ? returns the error to the caller if the read failed.

Step 2: remove the newline

text.trim()                                    // "3532800"
  • trim() removes the trailing newline. Without it, parse fails on every file.

Step 3: turn it into a number

.parse::<i64>()                                // Ok(3532800), or Err if not a number
  • ::<i64> picks the number type. It is i64, signed, because current_now can be negative.

Step 4: give the function one error type

.map_err(|e| std::io::Error::new(std::io::ErrorKind::InvalidData, e))
  • map_err turns a parse error into an I/O error, so the function has one error type.
  • A Result lets the caller decide what a missing file means.

All four together

fn read_number(path: &str) -> std::io::Result<i64> {
    let text = std::fs::read_to_string(path)?;     // "3532800\n"
    text.trim()
        .parse::<i64>()
        .map_err(|e| std::io::Error::new(std::io::ErrorKind::InvalidData, e))
}

It can fail three ways. Each one tells you something, and handling it badly stops your benchmark:

ErrorUsually means
NotFoundThis phone names the file differently, or the core or zone number doesn’t exist.
PermissionDeniedThe shell user may not read it. Android limits some of /sys with SELinux. Record the sensor as unavailable rather than crash the benchmark.
InvalidDataThe text wasn’t one number. Some files hold words (status is Discharging) or several values. Read those with read_to_string and keep the text.

Takeaway: read, trim, parse, and return the error; never assume the file exists or holds one number.

What unit is the number in?

A bare 3532800 means nothing until you know the unit. For this one it is kHz, so the clock is 3,532,800 ÷ 1,000,000 = 3.5328 GHz. The kernel’s documentation fixes the unit for each file. Phone vendors usually follow it, not always.

Convert to f64 before multiplying. Microamps times microvolts is 10−12 watts per unit, and the raw product of two seven-digit numbers is fine in f64 but easy to get wrong in your head. Write the unit into the name: current_ua, power_w. Skip that and a milliampere gets read as an ampere without anything complaining.


Takeaway: look up the unit, convert in f64, and put the unit in the variable name.



How do you find the right files?


The plan lists paths such as thermal_zone0, but thermal zone numbers aren’t stable across phones, and the plan’s paths are examples. A wrong guess reads the wrong sensor. Each zone has a type file that names its sensor, so list the directory and read them:


for entry in std::fs::read_dir("/sys/class/thermal")? {
    let path = entry?.path();
    if let Ok(kind) = std::fs::read_to_string(path.join("type")) {
        println!("{}  {}", path.display(), kind.trim());
    }
}

Pick the zones you want by name once, by hand, and write the names in the results file. A CPU sensor and a battery sensor answer different questions.


Takeaway: choose sensors by their type name, not by zone number.



What does a read cost?


You may want to read these files often. Every read is a system call, a request to the kernel. The kernel runs driver code to produce the text, and some drivers have to ask a hardware chip. That is roughly microseconds assumption: nothing at ten samples a second, but far too much inside a loop you are timing. Reads belong in the sampler thread, never in the benchmark.


If you want to know the real cost, time a thousand reads of one file with the Phase 0 harness. That is a good first sysfs experiment.


Takeaway: sysfs reads are cheap for a sampler and too dear for the code under test.



Check yourself


Why does "3532800\n".parse::<i64>() fail?

The newline. parse wants only digits (and a sign). trim() first.




current_now reads −512000 and voltage_now 4012000. What is the power?

0.512 A × 4.012 V ≈ 2.05 W. Whether the minus sign means discharging depends on the device. An idle, unplugged reading tells you which sign is discharge on this phone.




The sampler gets PermissionDenied on one thermal zone. Should the benchmark stop?

No. The benchmark is the measurement and the sensor is extra. Record that the zone was unreadable, keep the zones that work, and say so in the results.





What you should take away


A sysfs file is text the kernel makes when you read it, so each read is one fresh measurement.


Read, trim, parse, return the error, then convert using the documented unit.


Find sensors by name, and read them from the sampler, not from the benchmark.
