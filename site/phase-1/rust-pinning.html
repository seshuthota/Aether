Calling Linux from Rust

Rust’s standard library has no “run this thread on cpu6.” Linux does, as a C function called sched_setaffinity. Calling a C function from Rust is called FFI, and the libc crate is what makes it a one-liner.

One thread is pinned to the set {cpu0–cpu5}. Does it run on six cores at once?

  • No: it is one thread, which the scheduler may move between those six
    A wider set gives the scheduler choices. It doesn’t split one thread.
  • Yes: one copy on each allowed core
    A set allows cores; it does not make copies. Parallel work needs one thread per core.
  • No: a set with more than one core is rejected
    Several cores in one set is allowed; only a set with no usable core fails.

    A silent failed pin leaves the thread unpinned, so the label is wrong.
  • Nothing: the pin still holds, because the call failed
    A failed call did not pin anything.

What are we trying to do here?

Phase 1 measures how fast each core reads memory. A number means little unless you know which core made it, and an unpinned thread can move between cores while it runs. Pinning fixes that: it asks the Linux kernel, the part of the operating system that runs threads, to keep a thread on the cores you name. A thread is one stream of instructions, and a core is one processing unit on the chip.

The engine needs pinning so that every benchmark names its cores. The request is sched_setaffinity, and it lives in Android’s C library, not in Rust’s standard library. To make it from Rust you need three things, one section each below: a way to call a C function (FFI), the libc crate that declares it, and a CPU set that lists the cores you allow. unsafe marks code the compiler cannot fully check, so you vouch for it yourself.

By the end you can write a function that pins the current thread to one core. You can say why its call is unsafe, what to do when it fails, and how to check that the pin held.

How can Rust call a C function?

Pinning a thread needs a function that is written in C. Android’s C library, Bionic, already contains sched_setaffinity, and Rust reaches it through FFI, the foreign function interface.

Rust has no source code for sched_setaffinity. What must you give Rust so it can make the call?

  • The function’s exact name, argument types and return type
    That declaration is FFI. Rust trusts it, because it cannot read the C code.
  • Nothing: Rust finds the name and works out the types
    Rust cannot read the C code, so it cannot work out the types. They must be written down.
  • The C source file, compiled into your program
    The function is already compiled into Bionic. Rust needs its declaration, not its source.

It is compiled machine code with a C calling convention. Rust can call it, as long as Rust is told the function’s exact name, argument types and return type. That declaration is FFI.

The compiler can’t check that the declaration matches the real C function, or that you passed valid pointers. If you get either wrong, nothing warns you. So every FFI call is unsafe, for the same reason as on the raw memory page: you are vouching for something the compiler cannot see.

Takeaway: FFI means telling Rust a C function’s signature, and every call is unsafe because you vouch for it.

Why is calling sched_setaffinity unsafe in Rust, when the C function itself is fine?

  • The compiler cannot check the declaration or the pointer you pass
    The compiler can’t check the declaration, or that the pointer is a valid cpu_set_t of that size. You vouch.
  • C is less safe than Rust, so every call into it needs unsafe
    The C function is fine. The problem is what the compiler cannot see from the Rust side of the call.
  • Foreign code runs somewhere else on the phone
    Foreign means defined outside Rust. That is why a declaration is needed, not why the call is unsafe.

How do you get libc?

Phase 1 needs one C function and the C types it uses, and each has to be declared in Rust by name, type and constant.

What does the libc crate contain?

  • Declarations of C functions, types and constants, with almost no logic
    Those declarations are the work you would otherwise do by hand. The crate adds no logic of its own.
  • A faster version of sched_setaffinity, written in Rust
    libc does not replace the C function. It declares it, so the real C code runs.
  • The engine’s inference code, ready-made
    libc is the doorway to the operating system, not inference code. Engine logic is yours to write.

Writing those declarations by hand for every C function would be slow and easy to get wrong. The libc crate (a crate is a Rust library) is a big list of them, for every platform Rust supports, plus the C types and constants. It contains almost no logic of its own. One line in Cargo.toml:

[dependencies]
libc = "0.2"

Does this break the from-scratch rule? No. libc is the doorway to the operating system, not inference code. The plan names it for exactly this job.

Takeaway: libc is the declarations of the operating system’s C functions, not engine code.

What is a CPU set?

The call needs a list of the allowed cores, called a CPU set (cpu_set_t). A bit is a single digit, 0 or 1, and the set uses one bit per core.

The CPU set is a row of bits, one per core. Which set allows only cpu6?

  • Bit 6 on, every other bit off
    Each bit stands for one core number, counting from 0. Bit 6 is cpu6.
  • The number 6 written into the first byte
    The set holds one bit per core. It does not store the core number.
  • Every bit on except bit 6
    Set bits allow cores. You start from an empty set and turn on the bits you want.

A CPU set, cpu_set_t, is a row of bits, one per CPU number. For example, with only bit 6 set, “cpu6 is allowed.” On 64-bit Android it is 1024 bits long, far more than eight cores need. CPU_ZERO clears every bit and CPU_SET(n, …) turns bit n on.

What does the call look like?


The call takes four steps, all inside one unsafe block. Each is shown alone first.



  
Why must the call be given the size of the set?

  
    
    
  • C cannot know how long the set is, so you tell it in bytes 
    C needs the size because it cannot see the set’s length. You state it in bytes.
    • 
    
  • It picks which thread is pinned 
    The first argument picks the thread. The size only describes the set.
    • 
    
  • It caps how many cores you may allow 
    The set has room for 1024 bits, far more than eight cores. The size is not a core limit.
    • 
  





Step 1: make an empty set


let mut set: libc::cpu_set_t = std::mem::zeroed();
libc::CPU_ZERO(&mut set);


    
  
  • std::mem::zeroed() gives a value of all-zero bytes. C structs have no constructor. All-zero bytes is a valid empty set. It is unsafe because all-zero is not valid for every type; here it is.
    • 
  
  • CPU_ZERO is a macro in C. libc provides it as a Rust function, marked unsafe.
    • 




Step 2: allow one core


libc::CPU_SET(cpu, &mut set);


    
  
  • CPU_SET is also a macro in C, and an unsafe function in libc. It turns bit cpu on.
    • 




Step 3: ask Linux


let rc = libc::sched_setaffinity(
    0,
    std::mem::size_of::<libc::cpu_set_t>(),
    &set,
);


    
  
  • The first argument 0 says which thread. 0 means “the thread making this call.”
    • 
  
  • size_of::<cpu_set_t>(): C does not know how long the set is. You tell it, in bytes.
    • 




Step 4: check the result


if rc != 0 {
    return Err(std::io::Error::last_os_error());
}


    
  
  • C functions report failure with a return value, here −1, and leave the reason in errno. rc != 0 catches it.
    • 




All four together


fn pin_to(cpu: usize) -> std::io::Result<()> {
    // SAFETY: `set` is all-zero bytes, a valid empty cpu_set_t;
    // the size passed is the size of that type; `&set` stays
    // alive for the whole call.
    unsafe {
        let mut set: libc::cpu_set_t = std::mem::zeroed();
        libc::CPU_ZERO(&mut set);
        libc::CPU_SET(cpu, &mut set);
        let rc = libc::sched_setaffinity(
            0,
            std::mem::size_of::<libc::cpu_set_t>(),
            &set,
        );
        if rc != 0 {
            return Err(std::io::Error::last_os_error());
        }
    }
    Ok(())
}


Takeaway: zero a set, turn on the core, call with the set’s size, and check the return value.



  
You make a set with mem::zeroed() and then call CPU_SET for cpu6, without CPU_ZERO. Which cores are allowed?

  
    
    
  • Only cpu6: all-zero bytes are an empty set, and CPU_SET turns on bit 6 
    All-zero bytes are a valid empty set, so no bit is on before CPU_SET.
    • 
    
  • Every core, because mem::zeroed leaves the bits undefined 
    All-zero bytes are a valid empty set here. The zeroed start is defined, not undefined.
    • 
    
  • It doesn’t compile: mem::zeroed is unsafe 
    Inside pin_to’s unsafe block it compiles. You vouch that all-zero bytes are valid; for cpu_set_t they are.
    • 
  





What if it fails?


Pinning can fail, for example when you name a core the thread may not use. When it does, the call returns −1.



  
How do you find out why it failed, as readable text?

  
    
    
  • std::io::Error::last_os_error(), which reads errno 
    It reads errno and wraps it as a normal Rust error that prints as text.
    • 
    
  • Read the return value: −1 names the reason 
    −1 only says the call failed. The reason is in errno, not in the return value.
    • 
    
  • Nothing: the call prints its own message 
    The call returns −1 and stops there. The reason waits in errno until you read it.
    • 
  




The call returns −1 and leaves a number in errno, which is hard to read. std::io::Error::last_os_error() reads errno and gives you a normal Rust error that prints as text, like Invalid argument (os error 22). The common failure is EINVAL: the set contains no CPU the thread is allowed to use. Asking for cpu9 on an 8-core phone does that. So can Android itself, if the group of processes it put your shell in is restricted to some cores; the kernel only lets you pick inside what that group allows.


Easy to get wrong
Ignoring the return value. A pin that failed silently leaves the thread unpinned, and the result file still says “cpu6.” Return the error, and have the benchmark stop if it fails.


Takeaway: turn errno into a Rust error and stop the benchmark; a silent failed pin gives wrong results under the right label.



  
Your set holds only cpu9 on an 8-core phone. What does the error say?

  
    
    
  • Invalid argument (os error 22), after the call returns −1 
    That is EINVAL: the set contains no CPU the thread may use.
    • 
    
  • Nothing: the pin goes ahead on the cores that exist 
    A set with only cpu9 gives EINVAL, a failure, not a quiet pin.
    • 
    
  • A message saying the core does not exist 
    The text is the errno message, Invalid argument (os error 22), not a description of cpu9.
    • 
  





Does pinning apply to the whole program?


Pinning sets a mask on one thread. The parallel sweep starts eight workers from the main thread, so the question is what each worker starts with.



  
You pin the main thread to cpu6, then spawn eight workers and pin none of them. Where do the workers run?

  
    
    
  • All on cpu6, because each starts with a copy of its creator’s mask 
    A new thread copies its creator’s mask, so all eight inherit cpu6.
    • 
    
  • Spread over all eight cores, since the scheduler balances them 
    The scheduler moves threads, but only inside the mask they inherited.
    • 
    
  • Anywhere: a mask belongs to the program, not to a thread 
    A mask belongs to a thread. Each worker has its own copy, taken from main.
    • 
  




Where do they run? Linux keeps one affinity mask per thread, not per program. Two consequences for Phase 1:


    
  
  • A new thread starts with a copy of its creator’s mask. Pin the main thread to cpu6 and then spawn eight workers, and all eight crowd onto cpu6.
    • 
  
  • For the parallel sweep, each worker pins itself to its own core as the first thing it does. The Threads page shows that shape.
    • 



A mask with several cores on one thread is allowed, but it is not the parallel case. One thread with the set {0–5} is still one thread, which the scheduler may move between those six cores.


Takeaway: the mask belongs to a thread and is inherited, so each worker pins itself.



How do you check it worked?


libc::sched_getcpu() returns the core the calling thread is on right now. Each call costs a little time, so where you call it matters.


After pinning to cpu6 it should return 6, every time. Printing it once at the start of a run is a cheap check. Calling it inside a timed loop is not, because it is extra work in the thing you are measuring.


Takeaway: print sched_getcpu() once at the start, not inside the timed loop.



  
You pin to cpu6 and print sched_getcpu() once. It returns 3. What should you do?

  
    
    
  • Treat the pin as not working, and do not trust the run’s label 
    After pinning to cpu6 it should return 6, every time. So 3 means the pin did not hold.
    • 
    
  • Nothing: threads move, so 3 is normal 
    A pinned thread should stay on its core. Movement means the pin did not hold.
    • 
    
  • Call it again inside the timed loop and average the results 
    That adds work to the timed loop, which is the thing this check is meant to avoid.
    •

What you should take away


Rust reaches Linux’s pinning call through FFI, using libc; the call is unsafe because you vouch for it.


Build a one-bit CPU set, call with its size, and treat a failed pin as an error.


Each thread has its own mask: pin every worker itself, and check once with sched_getcpu().
