Calling Linux from Rust

Rust’s standard library has no “run this thread on cpu6.” Linux does, as a C function called sched_setaffinity. Calling a C function from Rust is called FFI, and the libc crate is what makes it a one-liner.

How to use this page

Cores and pinning explains what pinning is for. This page is the Rust side. The snippets compile for aarch64-linux-android against libc 0.2.190 measured; they have not been run on the phone as written. The engine’s own version, src/sys/affinity.rs, pins every benchmark since Phase 1.

What FFI is

Android’s C library, Bionic, already contains sched_setaffinity. It is compiled machine code with a C calling convention. Rust can call it, as long as Rust is told the function’s exact name, argument types and return type. That declaration is the “foreign function interface.”

The compiler can’t check that the declaration matches the real C function, or that you passed valid pointers. So every FFI call is unsafe, for the same reason as on the raw memory page: you are vouching for something the compiler cannot see.

Adding libc

The libc crate is a big list of those declarations, for every platform Rust supports, plus the C types and constants. It contains almost no logic of its own. One line in Cargo.toml:

[dependencies]
libc = "0.2"

This does not break the from-scratch rule. libc is the doorway to the operating system, not inference code. The plan names it for exactly this job.

A CPU set is a bitmask

cpu_set_t is a row of bits, one per CPU number. Bit 6 set means “cpu6 is allowed.” On 64-bit Android it is 1024 bits long, far more than eight cores need. CPU_ZERO clears every bit and CPU_SET(n, …) turns bit n on.

Click cores to allow them. Cores 0–5 are the 3.53 GHz performance cores and 6–7 the 4.32 GHz prime cores measured in Phase 0.


  





The call


fn pin_to(cpu: usize) -> std::io::Result<()> {
    unsafe {
        let mut set: libc::cpu_set_t = std::mem::zeroed();
        libc::CPU_ZERO(&mut set);
        libc::CPU_SET(cpu, &mut set);
        let rc = libc::sched_setaffinity(0, std::mem::size_of::<libc::cpu_set_t>(), &set);
        if rc != 0 {
            return Err(std::io::Error::last_os_error());
        }
    }
    Ok(())
}



  
PieceWhy it is there

  
    
std::mem::zeroed()C structs have no constructor. All-zero bytes is a valid empty set. It is unsafe because all-zero is not valid for every type; here it is.

    
CPU_ZERO, CPU_SETIn C these are macros. libc provides them as Rust functions, marked unsafe.

    
first argument 0Which thread. 0 means “the thread making this call.”

    
size_of::<cpu_set_t>()C does not know how long the set is. You tell it, in bytes.

    
rc != 0C functions report failure with a return value, here −1, and leave the reason in errno.

  




When it fails


std::io::Error::last_os_error() reads errno and gives you a normal Rust error that prints as text, like Invalid argument (os error 22). The common failure is EINVAL: the set contains no CPU the thread is allowed to use. Asking for cpu9 on an 8-core phone does that. So can Android itself, if the group of processes it put your shell in is restricted to some cores; the kernel only lets you pick inside what that group allows.


Easy to get wrong
Ignoring the return value. A pin that failed silently leaves the thread unpinned, and the result file still says “cpu6.” Return the error, and have the benchmark stop if it fails.



It is per thread


Linux keeps one affinity mask per thread, not per program. Two consequences for Phase 1:


    
  
  • A new thread starts with a copy of its creator’s mask. Pin the main thread to cpu6 and then spawn eight workers, and all eight crowd onto cpu6.
    • 
  
  • For the parallel sweep, each worker pins itself to its own core as the first thing it does. The Threads page shows that shape.
    • 



A mask with several cores on one thread is allowed, but it is not the parallel case. One thread with the set {0–5} is still one thread, which the scheduler may move between those six cores.



Checking it worked


libc::sched_getcpu() returns the CPU the calling thread is on right now. After pinning to cpu6 it should return 6, every time. Printing it once at the start of a run is a cheap check. Calling it inside a timed loop is not, because it is extra work in the thing you are measuring.



Check yourself


Why is calling sched_setaffinity unsafe in Rust, when the C function itself is fine?

The compiler cannot check the declaration against the real function, or that the pointer you pass points at a valid cpu_set_t of the size you claim. You vouch for both.




The mask for {cpu0, cpu6} as a byte, bit 7 on the left?

01000001, which is 0x41. Bit 0 for cpu0, bit 6 for cpu6.




You pin main to cpu7, then spawn six workers and pin none of them. Where do they run?

All on cpu7. They inherit main’s mask. The “parallel” run is six threads taking turns on one core, and its GB/s will say so.
