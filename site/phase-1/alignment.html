Alignment and cache lines

The cache cuts memory into fixed 64-byte pieces. Our code reads data 16 bytes at a time. If an array starts exactly on the edge of a piece, every 16-byte read fits inside one piece. If it starts somewhere in the middle, some reads straddle two pieces and cost a little extra. Alignment just means choosing where the array starts.

1. Is memory just a row of numbered bytes?

Picture memory as one very long row of boxes. Each box holds one byte, and each box has a number, its address: 0, 1, 2, and so on. Code reads memory by naming a start address and how many bytes it wants.

An f32 takes 4 bytes. An array of f32 is those 4-byte groups placed one after another, with no gaps. Example: if the array starts at address 1000, element 0 is in bytes 1000–1003 and element 1 is in bytes 1004–1007.

Takeaway: an address is a byte’s number, and an array is a run of bytes that starts at one address.

2. Why does the cache fetch 64 bytes at a time?

The cache is a small, fast copy of memory kept close to the core. As the memory hierarchy page showed, it never fetches a single byte. It fetches a whole cache line: 64 bytes, which is 16 f32s.

The line edges are fixed by the hardware. Lines always start at addresses 0, 64, 128, 192, and so on, every multiple of 64. You cannot move them. You can only choose where your array starts relative to them.

Almost every ARM64 core uses 64-byte lines. The CPU reports its line size in a register called CTR_EL0; we will read it when we write the allocator instead of trusting this number blindly.

Takeaway: cache lines are 64 bytes and their edges are fixed, so you choose only where your array starts.

3. How much does one NEON load read?

A matrix kernel does not read one float at a time. NEON is the phone CPU’s vector unit. Its registers hold 16 bytes, which is four f32s. One load instruction (vld1q_f32) fills a register with four floats, so a loop over an array walks it in 16-byte steps.

16 bytesone NEON load: 4 floats
64 bytesone cache line: 16 floats, or exactly 4 NEON loads

Takeaway: one load is four floats, and one cache line holds four loads.

4. Where should the array start?

Put the two pictures together: 16-byte loads walking along, over 64-byte lines with fixed edges. The start address decides whether a load crosses an edge.

  • Array starts on a line edge (address 0, 64, 128…). Four loads fill each line exactly. No load crosses an edge, so every load touches one line.
  • Array starts 4 bytes past an edge. Everything shifts by one float. Now every fourth load sticks out over a line edge: 12 bytes in one line and 4 in the next. That is a split load. It has to touch two lines, which costs extra.

Is a split load wrong?

No. On this phone’s 64-bit ARM CPU, a split load still returns the right four floats. It does not crash. It is only slower, because the hardware has to deal with two lines. How much slower on this core is something Phase 1 will measure, and it might turn out to be small.

You may read online that “NEON needs 16-byte alignment or it crashes.” That was true on older 32-bit ARM. On 64-bit ARM (AArch64), ordinary loads work at any address. Only special instructions like atomics still require alignment, and a matrix kernel does not use them.

Takeaway: a start on a line edge means no split loads; a start off the edge splits one load in four.

5. What does “aligned” mean?

Start with three addresses. 1024 is 16 × 64, so it is a multiple of 64 and is 64-aligned. 1040 is 65 × 16, so it is 16-aligned but not 64-aligned. 1028 is a multiple of 4 only: fine for one f32, but it will cause split loads.

An address is aligned to N when it is a multiple of N. In code: address % N == 0, where % is the remainder after dividing by N. A 64-aligned address is also 16-aligned and 4-aligned, because 64 is a multiple of both.

Is this address aligned?

So the rule for our buffers is: start every array at a 64-aligned address. If you ignore it, some loads split, and two benchmark runs may quietly compare different starting positions. With the rule, the array starts on a line edge, every 16-byte load stays inside one line, and the array does not share its first line with other data.

Takeaway: aligned to N means a multiple of N, and every array should start at a multiple of 64.

6. What does Rust promise about alignment?

Our Tensor stores its numbers in a Vec<f32>. A Vec (Rust’s growable array) only promises the alignment its element type needs. An f32 needs 4, so the only promise is that the start address is a multiple of 4.

In practice the allocator often hands back better-aligned memory, especially for big arrays. But “often” is luck, not a promise. Two risks follow:

  • A kernel that was fast in testing can get slower on a run where the array happens to start mid-line.
  • Two benchmark runs might quietly compare two different starting positions, so a difference you see could come from alignment rather than your code change.

Takeaway: a Vec promises a multiple of 4, not a multiple of 64, so the start is luck.

7. How do we get a guaranteed start?

We build a small aligned buffer: a block of memory whose start address is guaranteed to be a multiple of 64. The raw memory in Rust page shows how it is done. It needs to:

  • start at a 64-aligned address, for any length;
  • free its memory correctly, with the same size and alignment it asked for;
  • give the rest of the code an ordinary slice of f32, so Tensor’s indexing does not change at all;
  • work for awkward lengths: 0, 1, and lengths that are not a multiple of 4 (the leftover “tail” is a classic source of bugs).

Then a benchmark compares reading an aligned array with one deliberately shifted by 4 bytes. If the difference is lost in the noise, we say so. The buffer is still worth keeping, because it makes every later benchmark start from the same layout, and because of the next section.

Takeaway: the aligned buffer makes the start address a guarantee, not a habit of the allocator.

8. Why does 64 matter for threads?

This matters later, in Phase 4, when several threads run at once. Each core keeps its own copy of a cache line. Suppose two cores keep writing to different variables that sit in the same 64-byte line. Each write forces the other core to throw away its copy and fetch it again, so the line bounces between the cores. The program is still correct, just slow. This is called false sharing: the cores share a line, though not any data.

The fix uses the same number: give each thread’s data its own 64-byte line. Nothing to build for it in Phase 1; just remember why 64 keeps coming up.

Takeaway: 64 keeps coming up because threads that write nearby data slow each other down.

Check yourself

An array of f32 starts at address 2048. Will any 16-byte load split across lines?

No. 2048 is 32 × 64, so it is 64-aligned. Loads start at 2048, 2064, 2080, 2096, then the next line begins at 2112. Four loads fit each line exactly.

The same array starts at 2052 instead. What happens?

Everything is shifted by 4 bytes. The fourth load covers 2100–2115, which crosses the line edge at 2112. One load in every four is split.

Will a split load crash on this phone?

No. On 64-bit ARM, ordinary loads work at any address. A split load just touches two cache lines and costs a bit more time.

Why align to 64 instead of just 16?

Starting at a multiple of 16 is already enough to stop splits. 64 also puts the array’s start on a line edge, so it never shares its first line with other data. That is what false sharing needs later. And every multiple of 64 is a multiple of 16 anyway.

A big Vec came back 16-byte aligned today. Can the kernel rely on that?

No. Vec<f32> only promises 4. Today’s result is the allocator’s habit, not a guarantee. The aligned buffer type is the guarantee.

What you should take away

The cache loads 64-byte lines with fixed edges, and a load that crosses an edge is split and costs extra.

Starting every array at a multiple of 64 keeps each 16-byte load inside one line.

A Vec only promises a multiple of 4, so we build a buffer that promises 64.
