Phase 1 — hardware and the memory model

The point of this phase is a table you can explain, not a kernel. The pages below are the concepts behind it, written before the measurements; What Phase 1 measured is the table itself.

In what order should you read these pages? What counts as done? What is already known from Phase 0? What did Phase 1 build? What you should take away

In what order should you read these pages?

Read everything at once and the pages blur together. Take them in this order: the hardware first, then each Rust page just before the step that needs it, and the results last.

  1. Memory hierarchy — why a weight read is a trip to DRAM, and why one core may not fill the bus.
  2. Alignment — 16 bytes, 64 bytes, and what is wrong with Vec<f32> for the kernels you have not written.
  3. Cores and pinning — the map already measured, and sched_setaffinity.
  4. Bandwidth — which kernels to time, how to count bytes, and how a size sweep reveals caches.
  5. Roofline — the picture that puts the Phase 0 sum and a future GEMV on the same axes.
  6. Power and heat — joules, the battery files, and why a 5-minute run is a different experiment.
  7. simpleperf — what a profile is for, and why the release build already keeps symbols.

Then the Rust tools, each read just before the step that needs it:

  1. Raw memory in Rust — Layout, alloc, unsafe, and why the allocator is its own type.
  2. Calling Linux from Rust — FFI, the libc crate, and sched_setaffinity.
  3. Threads in Rust — the sampler’s stop flag, and scoped threads for the parallel sweep.
  4. Reading /sys from Rust — text to numbers, units, and failures.
  5. Plotting the sweep — CSV with conditions, a log axis, matplotlib.

And last, the answers:

  1. What Phase 1 measured — the yardstick table, the sweeps as plots, and what each number means.

Take them one at a time when you implement, the same way Phase 0 was taken. The pages are here so the explanation is waiting, not so the phase gets implemented in one sitting.

Takeaway: read the hardware first, each Rust page at the step that needs it, and the results last.

What counts as done?

You need a finish line before you start. The plan’s success criterion is a table in results/, recorded with the conditions of the run:

  • effective bandwidth at L1, L2, and whatever last-level cache the sweep shows,
  • single-core DRAM read bandwidth,
  • all-core DRAM read bandwidth,
  • sustained bandwidth after the phone has been hot for minutes,
  • energy per GB on a prime core versus a performance core.

Those numbers become the yardstick for every later kernel. A GEMV (a matrix times a vector) that moves 20 GB/s means nothing until you know what a pure read on the same core could move. Phase 0’s 3.3 GB/s sum is not that yardstick. It was latency-bound, meaning each step waited on the one before it.

A phase is finished when you can explain the table: where the cliffs are, why one core does not match eight, why the 5-minute number is lower, and which core class spends fewer joules per byte. Hitting a percentage of a theoretical peak is not the criterion.

Takeaway: the table is the finish line, and its numbers, recorded with their conditions, are the yardstick for later kernels.

What is already known from Phase 0?

Phase 0 already measured a few facts about the phone, so you start from them. Each bullet carries its tag: measured, calculated or assumption. An f32 is a 4-byte, 32-bit float.

  • Eight Oryon cores, CPU part 0x001. Cores 0–5 max 3.53 GHz, cores 6–7 max 4.32 GHz. No efficiency class. measured
  • NEON, dotprod, i8mm, bf16, fp16. No SVE. measured
  • A scalar f32 sum of 16 MB took ~4.9 ms, about 3.3 GB/s. That is a dependency chain. measured time, calculated rate.
  • Qualcomm’s brief: LPDDR5X up to 5300 MHz, up to 24 GB, 3 nm, SM8750. No published GB/s, no published cache sizes in the brief we read. Launch coverage said 12 MB of L2 per cluster. Treat that as a hypothesis for the sweep, not as a result. assumption
  • Tensor uses Vec<f32>. Alignment is 4 bytes.

Takeaway: the core layout and instruction set are measured, and the 3.3 GB/s sum measures the sum, not the memory.

What did Phase 1 build?

The plan’s five steps are all done. Here is where each one lives, and which page explains the Rust it uses.

The aligned buffer is src/aligned.rs, the sweeps are examples/bw_sweep.rs and examples/bw_sustained.rs, pinning and sysfs are in src/sys/, and the sampler is src/monitor.rs. Step 5 changed: the battery files could not be read, so energy comes from Android’s charge counter (why).

  1. An aligned allocator, so buffers can be 64-byte aligned instead of 4. Rust tools: raw memory.
  2. Bandwidth kernels: copy, scale, add, and a pure read. The read is the one that matches decode.
  3. A working-set sweep from about 4 KB to about 256 MB. Plot GB/s against size. The drops are the cache boundaries. Rust tools: plotting.
  4. The same sweep pinned to one prime core, one performance core, and the performance cores together. Pinning and scoped threads.
  5. A sampler, in a background thread, of battery current, voltage, core frequencies, and temperatures. Report average power and joules for the run. Threads and reading /sys.

Record, every time: which cores, screen on or off, charging or not, starting temperature. A number without those conditions cannot be compared with next week’s number.

Takeaway: Phase 1 built an aligned allocator, bandwidth kernels, sweeps, pinning and a sampler, and every number they produce is recorded with its conditions so it can be compared later.

What you should take away

Phase 1 is finished when you can explain the table in results, not when a percentage of peak is reached.

Each later kernel will be compared against the yardstick numbers from the sweeps.

Record the conditions with every number, or the number will not mean anything next week.
