Raw memory in Rust

The aligned allocator is the first thing Phase 1 builds. Vec<f32> cannot promise 64-byte alignment, so you ask the allocator directly. That means a raw pointer, an unsafe block, and a few rules the compiler can no longer check for you.

Is the address 0x1040 aligned to 64?

  • Yes
    An address is aligned to 64 when it is a multiple of 64, and 0x1040 is 65 × 64.
  • No, it doesn’t end in 00
    Multiples of 64 (0x40) end in 00, 40, 80 or C0 in hex.
  • Only if it holds an f32
    Alignment belongs to the address. The type only sets how much alignment you need.

Does let x: u32 = 1.5; compile inside an unsafe { } block?

  • Yes, unsafe turns the compiler’s checks off
    unsafe allows a few extra operations. Types, borrows and slice bounds are still checked.
  • No, types are still checked
    unsafe adds operations; it removes no checks.

You allocated 4,000 bytes at alignment 64. What must you pass to dealloc?

  • The same Layout: 4,000 bytes, alignment 64
    dealloc needs the exact Layout you allocated with.
  • Any Layout of 4,000 bytes
    Alignment matters when freeing too. A different Layout is undefined behaviour and can corrupt the allocator’s bookkeeping.
  • Nothing: Rust frees it when the pointer goes out of scope
    A raw pointer has no owner, so nothing frees it for you. Forgetting dealloc is a leak.

Which trait’s method does Rust call when a value goes away?

  • Drop
    Rust calls Drop::drop when the value goes out of scope.
  • Clone
    Clone makes copies; it runs only when you call .clone().
  • Send
    Send is a marker for “can move to another thread”. It has no method.

What are we trying to do here?

Memory is one long row of bytes. Each byte has a number, its address. A buffer is a run of neighbouring bytes, and its address is the address of its first byte. Every array of weights or activations in the engine lives in a buffer of f32 values, 4 bytes each.

The CPU does not fetch one byte at a time. It moves memory in 64-byte blocks called cache lines. If a buffer starts exactly at the start of a cache line, its first 16 floats arrive in one fetch. If it starts in the middle of one, some loads straddle two lines. The Alignment page covers what that costs. So Phase 1 wants every float buffer to start at an address that is a multiple of 64.

 memory:  ... | 64-byte line | 64-byte line | 64-byte line | ...
 good:          [buffer starts here ...........
 bad:                 [buffer starts mid-line .........

Rust’s usual tool for a buffer, Vec<f32>, does not let you ask for that. This page covers what you use instead: asking the allocator for memory directly, the unsafe code that takes, the rules you then have to keep yourself, and the small type that keeps them for you. By the end you can read and write every line of the allocator Phase 1 needs.

Why isn’t Vec enough?

Start from one plain fact. An address is aligned to 64 when it is a multiple of 64. 0x1040 is (it is 65 × 64). 0x1004 is not; it is only 4-aligned.

 0x1000          0x1040          0x1080     multiples of 64
 |---------------|---------------|
  ^ 0x1004         ^ 0x1040
    4-aligned only   64-aligned

You make a Vec<f32> of 1,000 floats. Does its buffer start on a multiple of 64?

  • Always: heap buffers start on a cache line
    Vec asks only for the alignment its element needs, and an f32 needs 4.
  • Sometimes, by luck; nothing promises it
    The allocator may hand back a multiple of 64, but Vec only asked for 4.
  • Never
    Nothing prevents it: any multiple of 4 can come back, including multiples of 64.

A Vec<f32> asks the allocator (the code that hands out heap memory) for 4-byte alignment, because that is all an f32 needs. So the answer to the guess is “sometimes”: the address might happen to be a multiple of 64, but nothing promises it, so the buffer may start in the middle of a cache line. The Alignment page covers why you want 64.

The next idea most people reach for: allocate 64-aligned memory yourself and hand it to a Vec. That fails. Vec::from_raw_parts requires that the memory was allocated with the same alignment as f32, because when the Vec is dropped it frees with alignment 4. Freeing with a different layout than you allocated with is undefined behaviour: the compiler assumes it never happens, so anything can happen. The buffer needs its own type that remembers how it was allocated.

Takeaway: Vec cannot promise 64-byte alignment, and it cannot adopt memory that has it.

You allocate 64-aligned memory yourself and turn it into a Vec<f32> with Vec::from_raw_parts. What goes wrong?

  • When the Vec is dropped, it frees with alignment 4
    It frees with a different Layout from the allocation: undefined behaviour, which from_raw_parts forbids.
  • Nothing; the Vec keeps the 64-byte alignment
    The Vec only knows its element type, f32, so it frees with alignment 4.
  • It fails to compile
    from_raw_parts is unsafe, so the compiler can’t check this rule. The bug shows at run time, if ever.

Does unsafe switch off the borrow checker?

The allocator hands back a raw pointer, *mut u8: just an address, with no owner and no lifetime. Safe Rust refuses to use one.

The allocator returns *mut u8, a raw pointer. Why does safe Rust refuse to read through it?

  • It has no owner and no lifetime, so the compiler can’t prove it’s valid
    The borrow checker works by tracking owners and borrows. A raw pointer gives it nothing to track.
  • Raw pointers are slow
    Speed is not the reason. The refusal is about what the compiler can prove.
  • It might be misaligned
    Alignment is one risk, but Rust refuses every raw-pointer read, because it can’t tell who owns the memory.

Safe Rust guarantees no dangling pointers, no double frees and no data races because the borrow checker tracks who owns each value and how long each borrow lives. For a raw pointer it has nothing to track.

An unsafe { } block lets you do five extra things. Two of them matter here:

  • call a function marked unsafe, such as alloc and dealloc,
  • read or write through a raw pointer.

So no, it does not switch anything off. Everything else is still checked inside the block: types, borrows, bounds on slices. A let x: u32 = 1.5; in there still fails to compile. unsafe does not mean “anything goes.” It means “I have checked the rules the compiler can’t, and I wrote down why.” The habit to build now: a short // SAFETY: comment above each block, saying what you checked.

Takeaway: unsafe adds a few operations and keeps every other check. The comment records what you checked.

Inside an unsafe { } block you take two &mut borrows of the same Vec and use both. What happens?

  • A compile error, the same as outside the block
    unsafe adds operations such as dereferencing raw pointers. Types, borrows and slice bounds are still checked.
  • It compiles, because the block is unsafe
    That is the “unsafe means anything goes” idea. References are checked inside the block as outside it.
  • It compiles but panics at run time
    The borrow checker runs at compile time and adds no run-time checks. This is refused before the program exists.

How do you describe an allocation?

The allocator needs two facts: how many bytes, and what alignment. A std::alloc::Layout holds both. The alignment must be a power of two. 1,000 floats are 4,000 bytes, at alignment 4 unless you ask for more. You pass the same Layout to allocate and to free.

let layout = Layout::array::<f32>(n) // n × 4 bytes, align 4
    .unwrap()
    .align_to(64)                     // ask for 64 instead
    .unwrap();

Layout::array::<f32>(1000).unwrap().align_to(1): what alignment comes out?

  • 1
    align_to raises the alignment and never lowers it.
  • 4
    f32 needs 4, and align_to keeps the larger of the two.
  • An error
    1 is a power of two (2⁰), so it is allowed.
  • ::<f32> names the element type, so the size of one element is known.
  • Layout::array::<f32>(n) fails only if n × 4 is too large to describe. It returns a Result.
  • .unwrap() takes the value out of the Result, and panics (stops the program with an error) if it was an error.
  • .align_to(64) keeps the size and raises the alignment. It never lowers it, so .align_to(1) still gives 4. Try 48 in the widget: not a power of two, so it returns an error.

How do you allocate, use and free it?


You need memory, a way to use it as a slice, and a way to give it back, and the compiler checks none of the order. Each step comes first on its own; the whole thing is at the end. The examples use n = 1000 and the layout above.



  
You allocate, make a slice from the pointer, free the memory, then read floats[0]. Which step does the compiler stop?

  
    
    
  • None of them 
    A slice from a raw pointer has no link to the allocation, so the compiler can’t see the free.
    • 
    
  • The read after the free 
    It would with a Vec. A slice from a raw pointer isn’t tied to the memory’s lifetime.
    • 
    
  • The free, because the slice still exists 
    The compiler doesn’t know the slice and the pointer share memory. That link exists only in your head.
    • 
  





Step 1: allocate


// SAFETY: layout.size() is 4000, not 0.
// p is a *mut u8, or null if out of memory.
let p = unsafe { alloc_zeroed(layout) };


    
  
  • alloc_zeroed asks the global allocator for layout.size() bytes at layout.align(), filled with zero bits. On Android the global allocator is the system one: Bionic’s malloc family underneath.
    • 
  
  • Zero bits are 0.0 as an f32, so every float has a value. Plain alloc leaves the bytes uninitialised, and reading them as floats before writing is undefined behaviour.
    • 
  
  • For a 64-byte alignment, Rust’s system allocator allocates and then writes the zeros itself: one pass over the memory at allocation time. That pass also touches every page, so the page faults happen there and not inside the timed loop.
    • 
  
  • p points at the first byte. It is null if the allocator could not give you memory.
    • 




Step 2: check it


if p.is_null() {
    handle_alloc_error(layout);
}
assert_eq!(p as usize % 64, 0);


    
  
  • handle_alloc_error aborts the program the same way Vec does on out-of-memory.
    • 
  
  • p as usize % 64 reads the address as a number. 0x1040 % 64 is 0, so the assert passes; 0x1004 % 64 is 4, so it would fail.
    • 




Step 3: make a slice


{
    // SAFETY: p is non-null and 64-aligned, so also 4-aligned,
    // as f32 needs. It is valid for n floats (zeroed, so each
    // is 0.0) and nothing else uses it.
    let floats: &mut [f32] = unsafe {
        std::slice::from_raw_parts_mut(p.cast::<f32>(), n)
    };
    floats[0] = 1.5;
}   // floats ends here


    
  
  • from_raw_parts_mut turns pointer plus length into an ordinary &mut [f32]. A slice is a pointer plus a length that Rust bounds-checks. You promise the pointer is valid for n floats and nothing else is using it.
    • 
  
  • p.cast::<f32>() changes the pointer’s type from *mut u8 to *mut f32, not the address. That is fine here: any multiple of 64 is also a multiple of 4, and 4 is all an f32 needs.
    • 
  
  • The { } block makes the end of the slice’s life visible. It ends before dealloc.
    • 




Step 4: free it


// SAFETY: p came from alloc_zeroed with this same layout,
// and this is the only dealloc.
unsafe { dealloc(p, layout) };


    
  
  • dealloc gives the memory back. It needs the exact Layout you allocated with, and it must run exactly once.
    • 




All four together


 alloc_zeroed ──► check null ──► { slice } ──► dealloc ──► any use = bug
                                         ^ the slice ends here


use std::alloc::{alloc_zeroed, dealloc, handle_alloc_error, Layout};

let n = 1000;                         // floats wanted
let layout = Layout::array::<f32>(n) // n × 4 bytes, align 4
    .unwrap()
    .align_to(64)                     // ask for 64 instead
    .unwrap();

// SAFETY: layout.size() is 4000, not 0.
// p is a *mut u8, or null if out of memory.
let p = unsafe { alloc_zeroed(layout) };
if p.is_null() {
    handle_alloc_error(layout);
}
assert_eq!(p as usize % 64, 0);

{
    // SAFETY: p is non-null and 64-aligned, so also 4-aligned,
    // as f32 needs. It is valid for n floats (zeroed, so each
    // is 0.0) and nothing else uses it.
    let floats: &mut [f32] = unsafe {
        std::slice::from_raw_parts_mut(p.cast::<f32>(), n)
    };
    floats[0] = 1.5;
}   // floats ends here

// SAFETY: p came from alloc_zeroed with this same layout,
// and this is the only dealloc.
unsafe { dealloc(p, layout) };    // same layout, exactly once




Takeaway: allocate, check, use, free, in that order, with the slice finished before dealloc.



  
Why alloc_zeroed and not plain alloc?

  
    
    
  • Reading uninitialised memory as f32 is undefined behaviour; zeroed bytes are valid floats 
    Zero bits are 0.0, so the buffer is safe to read straight away. The bytes from plain alloc are not.
    • 
    
  • alloc_zeroed is faster 
    It does more work: the zeros are written in an extra pass.
    • 
    
  • Plain alloc can’t give 64-byte alignment 
    Both take the same Layout, so both honour its alignment. Only the starting bytes differ.
    • 
  





Which rules do you keep now?


Some mistakes with raw memory hide in edge cases. The first one you will meet is an empty buffer, where n is 0.



  
Your buffer has n = 0 floats. What is layout.size(), and can you call alloc with it?

  
    
    
  • 0, and calling alloc with size 0 is undefined behaviour 
    The allocator is never allowed to see size 0. The empty case needs its own path.
    • 
    
  • 0, and alloc returns null 
    That would be a reasonable design, but the rule is stricter: calling it at all is undefined behaviour.
    • 
    
  • 64, because align_to(64) rounds the size up 
    align_to changes the alignment, not the size. Zero floats is zero bytes.
    • 
  




That is one of five rules. With a Vec, the compiler enforces these. With a raw allocation, you do:



  
RuleWhat breaks if you don’t

  
    
Free with the same Layout you allocated with.The allocator’s bookkeeping is corrupted. It may crash later, somewhere unrelated.

    
Free exactly once.Twice is a double free. Never is a leak.

    
No use after free.You read memory that now belongs to someone else.

    
Never call alloc with size 0.Undefined behaviour. For n = 0, skip the allocator and use a dangling pointer (non-null but pointing at nothing, NonNull::dangling()) with length 0, and skip dealloc too. The empty case is the one exception to 64-byte alignment: NonNull::dangling() is only 4-aligned, which does not matter because nothing is ever read through it.

    
Initialise before reading.alloc_zeroed handles this. Plain alloc does not.

  



None of these show up as compile errors. Some pass on the host and crash on the phone, or the reverse. That is why the tests on the Alignment page include awkward sizes and n = 0.


Takeaway: five rules, none checked by the compiler, each broken in a way that may only show up later.



  
What should the wrapper do for n = 0?

  
    
    
  • Skip the allocator: store a dangling, non-null pointer and length 0, and have Drop skip dealloc 
    The allocator never sees size 0, and an empty slice from the dangling pointer is fine.
    • 
    
  • Store a null pointer with length 0 
    A slice’s pointer must be non-null even when the slice is empty. That is what NonNull::dangling() is for.
    • 
    
  • Call alloc anyway; size 0 is harmless 
    Size 0 is the one size alloc must never get: undefined behaviour.
    • 
  





Why wrap the pointer in a type?


The rules above rest on you remembering them at every call site. Put the pointer, the length and the layout in one struct instead.



  
Put the pointer, the length and the layout in one struct. What could then call dealloc for you, exactly once?

  
    
    
  • Rust itself, when the struct goes away 
    That is the Drop trait: Rust calls its method once, when the value goes out of scope.
    • 
    
  • The borrow checker 
    The borrow checker only checks borrows at compile time. It never runs code.
    • 
    
  • Nothing; every caller still has to remember 
    That is the problem the struct removes. Callers can forget; Rust can’t.
    • 
  




The fields (name is a placeholder; the methods are yours to write):


struct AlignedBuf {
    ptr: NonNull<f32>,   // start of the memory
    len: usize,          // number of floats
    layout: Layout,      // what dealloc needs later
}


Then three things become automatic:


    
  
  1. Drop frees it. Drop is the trait whose method Rust calls when a value goes away. Implement it to call dealloc with the stored layout. Rust calls it exactly once. Double free is gone, and you can’t forget to free.
    2. 
  
  2. Borrows can’t outlive it. A method like fn as_slice(&self) -> &[f32] ties the slice to the struct. The borrow checker now refuses use-after-free, which it could not see with a loose pointer.
    3. 
  
  3. The unsafe is in one place. A handful of lines inside the type, each with a comment. Every caller writes safe code.
    4. 



A struct holding a raw pointer is not automatically shareable across threads (Send, the marker for “can move to another thread”). For the Phase 1 parallel sweep you won’t need it to be: each worker borrows a plain &[f32] chunk from as_slice, and slices of floats can be shared. See Threads.


Another route
A type like #[repr(align(64))] struct Line([f32; 16]); is 64-byte aligned, so a Vec<Line> is too, with no unsafe. The cost is that lengths come in steps of 16 floats and you convert to a flat &[f32] yourself. The plan asks for the allocator wrapper, which is also the better lesson.


Takeaway: one type holds the unsafe code, so Drop and the borrow checker enforce the rules for every caller.



  
The wrapper has fn as_slice(&self) -> &[f32]. You drop the buffer while a slice from it is still in use. What happens?

  
    
    
  • A compile error: the slice borrows the buffer 
    The slice’s lifetime is tied to &self, so the borrow checker refuses to let the buffer go first.
    • 
    
  • It compiles and reads freed memory 
    That is the loose-pointer code from the previous section. Tying the slice to &self is exactly what changes it.
    • 
    
  • It panics at run time 
    No check runs at run time. The borrow checker refuses it at compile time.
    •

What you should take away


A Vec cannot give you 64-byte alignment, so you allocate with a Layout and the raw allocator calls: allocate, check, slice, free.


unsafe lifts a few restrictions and keeps the rest; write a SAFETY: comment for every block.


Wrap it all in one type so Drop and the borrow checker keep the rules for you.
