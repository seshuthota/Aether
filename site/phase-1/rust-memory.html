Raw memory in Rust

The aligned allocator is the first thing Phase 1 builds. Vec<f32> cannot promise 64-byte alignment, so you ask the allocator directly. That means a raw pointer, an unsafe block, and a few rules the compiler can no longer check for you.

How to use this page

This is the Rust you need before writing the allocator, shown as small separate pieces. The wrapper type itself is yours to write in the session. The snippets compile for aarch64-linux-android measured, with Rust 1.99.

Why isn’t Vec enough?

You want a buffer of floats that starts on a 64-byte boundary. An address is aligned to 64 when it is a multiple of 64. 0x1040 is (it is 65 × 64). 0x1004 is not; it is only 4-aligned.

 0x1000          0x1040          0x1080     multiples of 64
 |---------------|---------------|
  ^ 0x1004         ^ 0x1040
    4-aligned only   64-aligned

A Vec<f32> asks the allocator (the code that hands out heap memory) for 4-byte alignment, because that is all an f32 needs. The address you get might happen to be a multiple of 64. Nothing promises it, so the buffer may start in the middle of a cache line. The Alignment page covers why you want 64.

Can you allocate 64-aligned memory yourself and hand it to a Vec? No. Vec::from_raw_parts requires that the memory was allocated with the same alignment as f32, because when the Vec is dropped it frees with alignment 4. Freeing with a different layout than you allocated with is undefined behaviour: the compiler assumes it never happens, so anything can happen. The buffer needs its own type that remembers how it was allocated.

Takeaway: Vec cannot promise 64-byte alignment, and it cannot adopt memory that has it.

Does unsafe switch off the borrow checker?

The allocator hands back a raw pointer, *mut u8: just an address, with no owner and no lifetime. Safe Rust refuses to use one. It guarantees no dangling pointers, no double frees and no data races because the borrow checker tracks who owns each value and how long each borrow lives. For a raw pointer it has nothing to track.

An unsafe { } block lets you do five extra things. Two of them matter here:

  • call a function marked unsafe, such as alloc and dealloc,
  • read or write through a raw pointer.

So no, it does not switch anything off. Everything else is still checked inside the block: types, borrows, bounds on slices. A let x: u32 = 1.5; in there still fails to compile. unsafe does not mean “anything goes.” It means “I have checked the rules the compiler can’t, and I wrote down why.” The habit to build now: a short // SAFETY: comment above each block, saying what you checked.

Takeaway: unsafe adds a few operations and keeps every other check. The comment records what you checked.

How do you describe an allocation?

The allocator needs two facts: how many bytes, and what alignment. A std::alloc::Layout holds both. The alignment must be a power of two. 1,000 floats are 4,000 bytes, at alignment 4 unless you ask for more. You pass the same Layout to allocate and to free.

let layout = Layout::array::<f32>(n)           // n × 4 bytes, alignment 4
    .unwrap()
    .align_to(64)                              // ask for 64 instead
    .unwrap();
  • ::<f32> names the element type, so the size of one element is known.
  • Layout::array::<f32>(n) fails only if n × 4 is too large to describe. It returns a Result.
  • .unwrap() takes the value out of the Result, and panics (stops the program with an error) if it was an error.
  • .align_to(64) keeps the size and raises the alignment. It never lowers it, so .align_to(1) still gives 4. Try 48 in the widget: not a power of two, so it returns an error.

How do you allocate, use and free it?


You need memory, a way to use it as a slice, and a way to give it back, and the compiler checks none of the order. Each step comes first on its own; the whole thing is at the end. The examples use n = 1000 and the layout above.



Step 1: allocate


// SAFETY: layout.size() is 4000, not 0.
let p = unsafe { alloc_zeroed(layout) };       // *mut u8, or null if out of memory


    
  
  • alloc_zeroed asks the global allocator for layout.size() bytes at layout.align(), filled with zero bits. On Android the global allocator is the system one: Bionic’s malloc family underneath.
    • 
  
  • Zero bits are 0.0 as an f32, so every float has a value. Plain alloc leaves the bytes uninitialised, and reading them as floats before writing is undefined behaviour.
    • 
  
  • p points at the first byte. It is null if the allocator could not give you memory.
    • 




Step 2: check it


if p.is_null() {
    handle_alloc_error(layout);
}
assert_eq!(p as usize % 64, 0);


    
  
  • handle_alloc_error aborts the program the same way Vec does on out-of-memory.
    • 
  
  • p as usize % 64 reads the address as a number. 0x1040 % 64 is 0, so the assert passes; 0x1004 % 64 is 4, so it would fail.
    • 




Step 3: make a slice


{
    // SAFETY: p is non-null and 64-aligned, so also 4-aligned as f32 needs.
    // It is valid for n floats (zeroed, so each is 0.0) and nothing else uses it.
    let floats: &mut [f32] = unsafe { std::slice::from_raw_parts_mut(p.cast::<f32>(), n) };
    floats[0] = 1.5;
}   // floats ends here


    
  
  • from_raw_parts_mut turns pointer plus length into an ordinary &mut [f32]. A slice is a pointer plus a length that Rust bounds-checks. You promise the pointer is valid for n floats and nothing else is using it.
    • 
  
  • p.cast::<f32>() changes the pointer’s type from *mut u8 to *mut f32, not the address. That is fine here: any multiple of 64 is also a multiple of 4, and 4 is all an f32 needs.
    • 
  
  • The { } block makes the end of the slice’s life visible. It ends before dealloc.
    • 




Step 4: free it


// SAFETY: p came from alloc_zeroed with this same layout, and this is the only dealloc.
unsafe { dealloc(p, layout) };


    
  
  • dealloc gives the memory back. It needs the exact Layout you allocated with, and it must run exactly once.
    • 




All four together


 alloc_zeroed ──► check null ──► { slice lives here } ──► dealloc
                                 ^ ends before dealloc   ^ any use after this is a bug


use std::alloc::{alloc_zeroed, dealloc, handle_alloc_error, Layout};

let n = 1000;                                  // floats wanted
let layout = Layout::array::<f32>(n)           // n × 4 bytes, alignment 4
    .unwrap()
    .align_to(64)                              // ask for 64 instead
    .unwrap();

// SAFETY: layout.size() is 4000, not 0.
let p = unsafe { alloc_zeroed(layout) };       // *mut u8, or null if out of memory
if p.is_null() {
    handle_alloc_error(layout);
}
assert_eq!(p as usize % 64, 0);

{
    // SAFETY: p is non-null and 64-aligned, so also 4-aligned as f32 needs.
    // It is valid for n floats (zeroed, so each is 0.0) and nothing else uses it.
    let floats: &mut [f32] = unsafe { std::slice::from_raw_parts_mut(p.cast::<f32>(), n) };
    floats[0] = 1.5;
}   // floats ends here

// SAFETY: p came from alloc_zeroed with this same layout, and this is the only dealloc.
unsafe { dealloc(p, layout) };                 // same layout, exactly once




Takeaway: allocate, check, use, free, in that order, with the slice finished before dealloc.



Which rules do you keep now?


With a Vec, the compiler enforces these. With a raw allocation, you do:



  
RuleWhat breaks if you don’t

  
    
Free with the same Layout you allocated with.The allocator’s bookkeeping is corrupted. It may crash later, somewhere unrelated.

    
Free exactly once.Twice is a double free. Never is a leak.

    
No use after free.You read memory that now belongs to someone else.

    
Never call alloc with size 0.Undefined behaviour. For n = 0, skip the allocator and use a dangling pointer (non-null but pointing at nothing, NonNull::dangling()) with length 0, and skip dealloc too. The empty case is the one exception to 64-byte alignment: NonNull::dangling() is only 4-aligned, which does not matter because nothing is ever read through it.

    
Initialise before reading.alloc_zeroed handles this. Plain alloc does not.

  



None of these show up as compile errors. Some pass on the host and crash on the phone, or the reverse. That is why the tests on the Alignment page include awkward sizes and n = 0.


Takeaway: five rules, none checked by the compiler, each broken in a way that may only show up later.



Why wrap the pointer in a type?


The rules above rest on you remembering them at every call site. Put the pointer, the length and the layout in one struct instead. The fields (name is a placeholder; the methods are yours to write):


struct AlignedBuf {
    ptr: NonNull<f32>,   // start of the memory
    len: usize,          // number of floats
    layout: Layout,      // what dealloc needs later
}


Then three things become automatic:


    
  
  1. Drop frees it. Drop is the trait whose method Rust calls when a value goes away. Implement it to call dealloc with the stored layout. Rust calls it exactly once. Double free is gone, and you can’t forget to free.
    2. 
  
  2. Borrows can’t outlive it. A method like fn as_slice(&self) -> &[f32] ties the slice to the struct. The borrow checker now refuses use-after-free, which it could not see with a loose pointer.
    3. 
  
  3. The unsafe is in one place. A handful of lines inside the type, each with a comment. Every caller writes safe code.
    4. 



A struct holding a raw pointer is not automatically shareable across threads (Send, the marker for “can move to another thread”). For the Phase 1 parallel sweep you won’t need it to be: each worker borrows a plain &[f32] chunk from as_slice, and slices of floats can be shared. See Threads.


Another route
A type like #[repr(align(64))] struct Line([f32; 16]); is 64-byte aligned, so a Vec<Line> is too, with no unsafe. The cost is that lengths come in steps of 16 floats and you convert to a flat &[f32] yourself. The plan asks for the allocator wrapper, which is also the better lesson.


Takeaway: one type holds the unsafe code, so Drop and the borrow checker enforce the rules for every caller.



Check yourself


Why can’t you allocate 64-aligned memory and turn it into a Vec<f32>?

The Vec would free it with alignment 4, a different Layout from the one it was allocated with. That is undefined behaviour. Vec::from_raw_parts forbids it for this reason.




Does code inside unsafe { } skip the borrow checker?

No. It allows a few extra operations, such as calling unsafe functions and dereferencing raw pointers. Types, borrows and slice bounds are still checked.




Why alloc_zeroed and not alloc?

Reading uninitialised memory as f32 is undefined behaviour in Rust. Zeroed bytes are valid floats (0.0), so the buffer is safe to read immediately. For a 64-byte alignment, Rust’s system allocator allocates and then writes the zeros itself: one pass over the memory at allocation time. That pass also touches every page, so the page faults happen there and not inside the timed loop.




What should the wrapper do for n = 0?

Not call the allocator. Store a dangling, non-null pointer and length 0, and have Drop skip dealloc. An empty slice from it is fine.





What you should take away


A Vec cannot give you 64-byte alignment, so you allocate with a Layout and the raw allocator calls: allocate, check, slice, free.


unsafe lifts a few restrictions and keeps the rest; write a SAFETY: comment for every block.


Wrap it all in one type so Drop and the borrow checker keep the rules for you.
