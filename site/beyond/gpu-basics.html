How the GPU runs our code

The phone’s Adreno 830 GPU has hundreds of lanes that run one small program side by side. This page covers how the engine hands it work through Vulkan, how a matrix-vector product is split across its lanes, and what that measured.

What are we trying to do here?

The SoC has a GPU (graphics processor) next to the CPU cores. The engine can run a whole decode step on it (built with --features vulkan). The code is src/kernels/vulkan.rs (the device, buffers, kernels), src/model/gpu.rs (the model) and shaders/*.comp (the programs the GPU runs).

Vulkan is the standard interface for talking to GPUs on Android. The engine calls it through the ash crate, which only declares Vulkan’s C functions; the phone’s own libvulkan.so does the work. No GPU library does the arithmetic for us.

By the end you can explain how work reaches the GPU, why it reads memory no faster than the CPU, and how 32 lanes share one row of a matrix.

How is a GPU organised?

A CPU core runs one stream of instructions fast, with NEON doing 4 floats per instruction. A GPU runs one small program, called a shader, on many lanes (also called invocations) at once. Three levels matter:

  • A subgroup (a “wave”) is a set of lanes that execute the same instruction together. On the Adreno 830 a subgroup has 64 lanes (128 is also possible) measured.
  • A workgroup is a set of lanes, chosen by the shader (64, 128, 256…), that can share fast on-chip memory, called shared memory (32 KB here), and wait for each other at a barrier().
  • A dispatch launches a grid of workgroups. They run in any order and cannot wait for each other.
dispatch: workgroup 0  workgroup 1  ...  workgroup 151
          [128 lanes]  [128 lanes]       [128 lanes]
             = 2 subgroups of 64 on the Adreno

Lanes of one subgroup want to add their 32 partial sums. What can they use that lanes in different workgroups cannot?

  • Subgroup operations that pass values between lanes directly
    Lanes in one subgroup run in lockstep, so a shuffle can read another lane’s register.
  • Nothing: every lane is independent
    Lanes of a subgroup execute together and can exchange values without memory.
  • A barrier across the whole dispatch
    There is no barrier across workgroups inside one dispatch; that needs a second dispatch.

Lanes of one subgroup can exchange registers with subgroup operations, such as subgroupShuffleXor(v, m): each lane gets v from the lane whose index differs from its own in the bits of m. A whole workgroup can share values through shared memory and a barrier. Different workgroups can only communicate through ordinary memory, in a later dispatch.

Takeaway: lanes run in lockstep subgroups inside workgroups; only lanes of the same workgroup can wait for each other.

Step A writes a vector that step B reads in full. Why must they be two dispatches with a barrier between them?

  • Workgroups of one dispatch cannot wait for each other, so B’s lanes could read before A’s are done
    The barrier between dispatches makes all of A’s writes visible before B starts.
  • A shader can only write one buffer
    A shader can write several buffers; the problem is ordering between workgroups.
  • They could share one dispatch with barrier()
    barrier() only waits for the lanes of one workgroup.

How does the engine hand work to the GPU?

Shaders are written in GLSL (a C-like shading language). build.rs compiles each shaders/*.comp file with the NDK’s glslc into SPIR-V, the GPU-neutral bytecode Vulkan accepts, and the bytes are built into the binary. At start-up the engine turns each into a pipeline: the driver compiles SPIR-V into the Adreno’s own instructions. One of these is a Kernel in vulkan.rs.

Data lives in buffers. On this phone, “GPU memory” is the same LPDDR5X RAM the CPU uses: one heap, so a buffer is one allocation both sides see, with no copies. The CPU writes the token’s embedding straight into the input buffer and reads the logits straight out.

The work for one token is recorded once into a command buffer: for each stage, bind the kernel with its buffers, push a few constants (sizes, offsets), dispatch, barrier. Per token, the engine writes the position and the RoPE table into a small params buffer, submits the command buffer, and waits on a fence, a flag the GPU sets when it is done.

// per token (GpuModel::forward, simplified)
embedding_row(token, x);   // CPU writes the input
params.pos = pos;          // and the position, RoPE table
gpu.submit(&step);         // the recorded step; waits on
                           // its fence
read(logits);              // CPU reads the output
  • Nothing is recorded per token, so the CPU’s side of a step is a few microseconds plus the wait.
  • Specialization constants are values fixed when a pipeline is created, such as the rows per lane group below. The driver compiles a separate, specialised program for each value.

Takeaway: the step is recorded once; per token the CPU writes a position, submits and waits.

Why does the position go into a buffer the shaders read, rather than into the recorded commands?

  • The commands are recorded once and reused for every position
    Values that change per token have to come from memory the CPU rewrites before each submit.
  • Shaders cannot take constants
    They take push constants, but those are fixed at recording time here.
  • The GPU computes the position itself
    The CPU writes it, together with the RoPE table it computes exactly as the CPU path does.

Can the GPU read the weights faster than the CPU?

Decode is limited by how fast the weights come from memory (the decode ceiling). Phase 1 measured about 67 GB/s for all eight CPU cores together.

A GPU has far more lanes than the CPU. How fast did a read shader stream a 16 MB buffer?

  • About 66 GB/s, the same as the CPU
    GPU and CPU share one memory controller and one set of RAM chips.
  • About 300 GB/s
    Desktop GPUs have their own fast memory; this one reads the phone’s shared RAM.
  • About 20 GB/s
    With enough workgroups the GPU reaches the memory’s limit.

examples/vk_bandwidth.rs measured 65–68 GB/s for 4–64 MB buffers measured. The GPU and the CPU read the same RAM through the same controller, so for decode the GPU cannot be faster than the CPU. It can do two other things: take the work off the CPU (heat and energy), and prefill, where arithmetic is the limit.

The same tool measured the fixed cost of a dispatch: an empty one with a barrier after it takes 1.7 µs, plus about 18 ns per workgroup measured.

Takeaway: on a phone the GPU shares the CPU’s memory, so it cannot make decode faster, only take it off the CPU.

How is a matrix-vector product split across lanes?

A Q4_0 row of Qwen2.5-0.5B has 896 columns, which is 28 blocks of 32 weights (blocks). Each block is 16 bytes of 4-bit values plus one f16 scale. At upload the engine splits llama.cpp’s 18-byte blocks into the 16 value bytes and the scales, so a lane can fetch a whole block’s values in one aligned 16-byte load.

The first version gave each row 64 lanes, half a block each, and added the 64 sums in shared memory with 6 barriers: 15–25 GB/s, half the CPU’s measured. Most lanes did one load and then waited at barriers.

What should each lane do so that every load is used more and barriers disappear?

  • Take a whole block, for several rows at once, and add sums with subgroup shuffles
    The lane’s 32 activations then serve R rows, and shuffles need no shared memory.
  • Take a single weight each
    That makes the loads smaller and the additions longer.
  • Use one lane per row
    A row would then be one long chain, and there would be too few rows to fill the GPU.

shaders/q4_0_gemv.comp: a group of 32 lanes computes R rows together. Lane l takes blocks l, l + 32, … of each row, loads that block’s 32 activations once and uses them for all R rows. Then the 32 partial sums of each row are added in five shuffle steps:

for m in [16, 8, 4, 2, 1]:
    sum += subgroupShuffleXor(sum, m)
// after 5 steps every lane holds the total
// lane 0 writes it
  • XOR with 16, 8, 4, 2, 1 never leaves an aligned group of 32 lanes, so the four groups of a 128-lane workgroup each add their own rows.
  • R is a specialization constant, so each matrix gets its best R. R sums held as R/4 vec4s ran 15 % faster than R separate floats: one shuffle then moves four sums.
  • A first version used subgroupClusteredAdd. The Adreno 830 does not support clustered subgroup operations, and its driver’s compiler crashed (SIGSEGV) instead of reporting an error.

On the 77 MB classifier this reaches 62 GB/s at R = 16, 94 % of the read test and 24 % above the CPU measured.

Takeaway: 32 lanes share R rows, one block per lane, and five shuffles add the sums with no barriers.

A row has 28 blocks and each group has 32 lanes. What happens to lanes 28–31?

  • They have no block, contribute 0 to the sum and wait
    An 896-column row leaves 4 of 32 lanes idle; bigger rows give some lanes several blocks.
  • They wrap around to block 0
    That would add block 0 twice; the loop stops at the row’s end.
  • They start the next row
    Rows are assigned per group of 32, not per lane.

Why are small matrices slow on the GPU?

Qwen2.5-0.5B’s layers have matrices of very different sizes. examples/vk_gemv.rs times each shape with a barrier between dispatches, as in the model, GB/s of Q4_0 bytes measured:

matrix (rows × columns)bytesGPUCPU, 6 threads
wk, wv: 128 × 8960.06 MB8–910
wq, wo: 896 × 8960.45 MB22–2929–31
gate, up: 4864 × 8962.5 MB41–4739–45
classifier: 151936 × 89677 MB6250–51

A 2.5 MB matrix at 66 GB/s would take 37 µs. It takes about 50. What does that suggest?

  • Each dispatch has a fixed cost of roughly 10 µs on top of its bytes
    Starting, filling and draining the GPU takes time that a small job cannot hide.
  • The shader reads each byte twice
    Each weight is read once; the same shader reaches 62 GB/s on a big matrix.
  • The memory is slower for small buffers
    The read test reaches full speed from 4 MB, and the extra time is about the same size for every matrix.

About 10 µs per dispatch is a small share of the classifier’s 1.2 ms and most of wk’s 7.5 µs. The fix that worked was fewer, bigger dispatches: wq, wk and wv stacked into one 1152-row matrix (32.2 → 20.4 µs), and gate over up as one 9728-row matrix (104.6 → 93.3 µs) measured. Their outputs share one buffer, and the shaders after them read views at offsets into it. Two other ideas were measured and dropped: unrolling the row loop (slower everywhere, likely too many registers) and splitting a row’s blocks across several groups of 32 lanes (never faster).

Takeaway: a GPU dispatch has a fixed cost, so small matrices run far below the bandwidth limit, and stacking them helps.

Why does stacking wq, wk and wv not change any result?

  • Each output row is still the same dot product of the same weights and input
    Stacking only changes which dispatch computes a row, not how it is computed.
  • It does change results slightly
    The GPU perplexities stayed identical to the last digit.
  • The shader sorts the rows back
    No sorting: the stacked outputs are simply q, then k, then v in one buffer.

What went wrong on the PC’s GPU?

The development PC has an Intel GPU, so the GPU tests can run there too. The GEMV test failed on it, with errors near 86 %. The shader relies on 32 lanes staying in one subgroup.

Intel reports a subgroup size of 32. Why would 32-lane shuffles still go wrong?

  • Intel may compile a shader for 8 or 16 lanes, and then a shuffle by 16 reaches past the subgroup
    The reported size is the largest; the driver picks the size per shader unless told otherwise.
  • Intel has no shuffles
    It supports shuffles, and even clustered operations.
  • Intel rounds floats differently
    Rounding differences are tiny; an 86 % error means wrong values were added.

Vulkan lets a pipeline require a subgroup size (VK_EXT_subgroup_size_control). On devices that may go below 32 lanes, the engine now asks for exactly 32. The Adreno never runs fewer than 64 lanes, so nothing changes on the phone. With that, every GPU test passes on the PC, and the GPU perplexities there match the phone’s to four decimals (SmolLM2-135M 27.6910, Qwen2.5-0.5B 19.7193) measured.

Takeaway: a shader that assumes a subgroup size must ask for it; the size a driver reports is not a promise.

Why is it useful that the GPU path now runs on the PC?

  • Shader changes can be checked against llama.cpp’s perplexity without the phone
    Correctness can be tested anywhere; only the speed has to be measured on the phone.
  • The PC’s numbers replace the phone’s
    Speed on the Intel GPU says nothing about the Adreno; only correctness carries over.
  • It makes the phone faster
    The phone path is unchanged.

What you should take away

A GPU runs one shader on lockstep subgroups inside workgroups; work reaches it as recorded dispatches separated by barriers.

On a phone it reads the same RAM as the CPU at the same speed, so it cannot speed up decode. Each dispatch has a fixed cost, which makes small matrices slow.

Numbers on this page were measured on the iQOO 13 (SM8750) on 2026-10-29 (results/phase-l3.md, steps 1, 2 and 6) unless tagged otherwise. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
