What is the NPU, and how does our code get on it?

The phone’s NPU is the Hexagon DSP, a processor besides the CPU and the GPU. Our engine runs a small library of its own on it, and every call into that library costs a fixed toll. This page shows what the DSP has, how a call reaches it, and what one empty call costs next to a token.

What are we trying to do here?

A phone chip has several processors that can multiply matrices. The CPU is one. The GPU is another (the previous page). The third is the NPU, the neural processing unit. On this phone the NPU is the Hexagon v79 compute DSP, called the cDSP here. A DSP (digital signal processor) is a processor built for long runs of arithmetic on numbers. The cDSP has its own vector units, a matrix unit, its own on-chip memory and its own operating system, QuRT.

Our engine runs code on it: dsp/aether_dsp.c, a C library built for the cDSP. The CPU calls into that library and gets the results back. By the end of this page you can say what the DSP contains, how a call reaches it, and what one call costs. The cost is the reason the next page is built the way it is.

What is inside the Hexagon DSP?

A vector unit runs one instruction on a fixed-width block of numbers at once. The block is called a vector. The DSP’s vectors are 128 bytes wide. An f32 is a 32-bit float, which takes 4 bytes.

How many f32 numbers fit in one 128-byte vector?

  • 32
    128 bytes divided by 4 bytes per f32 is 32 numbers.
  • 4
    That is the byte count of one f32, not how many fit.
  • 128
    That counts bytes. The vector holds numbers, four bytes each.

The cDSP has three parts that matter for us. Each is named by the code we wrote.

  • HVX is the vector unit: 128-byte vectors. dsp/aether_dsp.c says so in its own comment: “One HVX vector: 128 bytes, 32 floats.” The DSP has 6 HVX contexts, so up to six threads can each run vector code at once (qurt_hvx_get_units, measured).
  • HMX is the matrix unit. Our hmx_gemm call computes X times Wᵀ on it, a matrix product, and model_prefill uses it for the prompt.
  • VTCM is the DSP’s own memory, on the chip. The DSP has 8 MB of it. Some model products copy their weights into it by DMA (a copy engine that moves a block without the processor touching each byte).

Takeaway: the cDSP computes on 128-byte vectors, has a matrix unit, and keeps 8 MB of its own memory.

A block of 256 f32 numbers is loaded one HVX vector at a time. How many vector loads does it take?

  • 8
    Each vector holds 32 numbers, and 256 divided by 32 is 8.
  • 32
    That is the count per vector. The block needs 256 divided by 32 loads.
  • 256
    That counts numbers. Each load moves 32 of them.

How does a call reach code on the DSP?

The CPU and the DSP are two processors with their own memory and their own software. The CPU cannot jump into DSP code. A call goes through FastRPC (Fast Remote Procedure Call), the phone’s system layer for this. Its client library, libcdsprpc.so, is part of the phone, not of our project.

A signature is a certificate that says who built a piece of code. The DSP normally loads only signed libraries, and ours has no signature.

Our library is unsigned. What lets the DSP run it?

  • The session is opened in a mode that allows an unsigned module
    Our code sets that flag before it opens the session, so the library needs no certificate.
  • We pay Qualcomm for a signature
    Nothing in the build asks for one; the library is ours and runs as built.
  • The DSP runs any code without checking it
    The flag is set in our code before opening, so the check is switched off for us only.

The CPU side of src/kernels/hexagon.rs does three things:

  • It loads libcdsprpc.so with dlopen, the C call that loads a shared library while the program runs, and sets the unsigned flag before it opens the session.
  • It embeds our library in the binary at build time and writes it next to the binary. That folder goes first in ADSP_LIBRARY_PATH, the list where the DSP’s loader looks for libraries.
  • It packs each call itself. The first arguments say which method is called and how many buffers go in and out:
const DSPRPC_CONTROL_UNSIGNED_MODULE: u32 = 2;
const CDSP_DOMAIN_ID: c_int = 3;
const fn scalars(method: u32, n_in: u32, n_out: u32) -> u32 {
    (method & 0x1f) << 24 | (n_in & 0xff) << 16 | (n_out & 0xff) << 8
}
  • Method numbers 0 and 1 are open and close. The rest follow the order in dsp/aether_dsp.idl, so ping is 2.
  • One call is one remote_handle64_invoke. Its buffers are the input bytes and the output bytes.

Takeaway: a call travels through the phone’s FastRPC layer, and our unsigned library is found through a path we set.

We change the C code in dsp/aether_dsp.c and rebuild. What must the phone also receive for the new code to run?

  • The new library, which the build embeds in our binary and writes next to it
    The DSP loads the library from the folder our binary writes, so the new file must be there.
  • A new copy of libcdsprpc.so
    That is the phone’s system library; our change does not touch it.
  • A new signature from the SDK
    The session is unsigned, so no certificate is involved.

Who wrote the code that runs there?

Qualcomm’s Hexagon SDK (version 6.4.0.2 here) is a developer kit for the DSP. It has three parts we use. The toolchain is a C compiler that builds code for the DSP. The QuRT headers declare the functions of the DSP’s operating system. qaic is a generator that reads an interface file and writes glue code from it.

Who wrote the arithmetic our DSP calls run, such as the add and the matrix-vector product?

  • We did, in our C library under dsp/
    The SDK supplies tools and declarations; the kernels are in our library.
  • Qualcomm, shipped inside the SDK
    The SDK ships a compiler and headers, not the kernels our calls run.
  • The phone’s firmware
    The firmware runs QuRT, the DSP’s operating system, not our kernels.

The SDK gives tools and declarations, not the arithmetic. The Q4_0 product and the other functions our calls run are ours, in dsp/. The toolchain builds dsp/aether_dsp.c. qaic reads dsp/aether_dsp.idl and writes the DSP-side glue, which unpacks each call’s arguments and calls our function. We do not link qaic’s CPU-side stub: Dsp::call packs the same arguments itself, as the IDL comment says. The phone’s libcdsprpc.so and the QuRT system are the phone’s own, and they run under our code.

Takeaway: the SDK supplies the compiler, the headers and the glue generator; every arithmetic function our calls run is ours.

What does one call cost next to a token?

A token is one decode step: the work that produces one new word. On our CPU path a token takes about 5 ms. A call is the trip from the CPU to the DSP and back. An empty call does no work in the DSP, so its time is the toll of the trip alone.

One empty call takes 146 µs. About how many calls fit in one CPU token of about 5 ms?

  • About 35
    5 ms is 5,000 µs, and 5,000 divided by 146 is about 34 to 35.
  • About 3
    That makes a call as slow as a token. A call is well under a tenth of one.
  • About 350
    That needs a call of 14 µs. A call here takes 146 µs.

Three numbers, all measured on the phone on 2026-10-29:

  • Opening the session and loading our library takes 33 to 37 ms. This is paid once, not per call measured.
  • One empty call (ping): median 146 µs over 2,000 calls, with the 10th percentile at 136 µs and the 90th at 160 µs measured.
  • The same call without the clock request took 393 µs measured.

The clock request is HAP_power_set_DCVS_v3. It asks the DSP for its highest clocks and no sleep between calls. The code comment says why: “else every call wakes a sleeping DSP.” A CPU token takes about 5 ms; our step 3 measured 5.2 ms measured. Dividing 5 ms by 146 µs gives about 35 calls per token calculated.

Now the design question. Decode runs one matrix product after another. A model has about 170 of them per token (results/phase-l5.md, step 1). One call each would cost about 25 ms of trips alone, 170 times 146 µs calculated. That is five times a whole CPU token, so the calls would take longer than the work. The next page shows the design that avoids this: one call for the whole token.

Takeaway: one empty call costs about 146 µs, which is about 35 calls per CPU token, so calls must be few.

The clock request cut an empty call from 393 µs to 146 µs. Which explanation fits?

  • Without the request the DSP sleeps between calls, and each call wakes it
    The request keeps the DSP awake, so each call skips the wake-up.
  • The request makes the DSP’s arithmetic faster
    An empty call does no arithmetic, so the request cannot speed any up.
  • The request skips the copy of the buffers
    The copies are the same with or without the request; the wake-up differs.

What you should take away

The NPU is the Hexagon cDSP: 128-byte vector units, a matrix unit and 8 MB of its own memory. Our unsigned C library runs on it, reached through the phone’s FastRPC layer.

A call costs about 146 µs even when it does nothing, about 35 calls per CPU token. So the design must make few calls: one per token, on the next page.

Numbers on this page were measured on the iQOO 13 (SM8750) on 2026-10-29 (results/phase-l5.md, steps 1 to 3) unless tagged otherwise. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
