Why round the activations to 8 bits on the GPU?

Lookup on the GPU needs one pass over several tokens to cost little more than one. On the Adreno 830 each extra token cost nearly a whole decode step. Rounding the activations to 8 bits and multiplying them with integer dot products fixed that: 4 tokens now cost 2.2 decode steps. Prefill and decode got faster too. This page shows the rounding, and what it costs in accuracy.

What are we trying to do here?

Prompt lookup guesses the next tokens by copying text that already appeared in the prompt. The model then checks all the guesses in one pass over several tokens. A pass of 4 tokens saves time only if it costs much less than 4 separate decode steps.

The input vector of every product is called x, the activation. Each product multiplies x by a weight matrix. A dispatch is one run of a GPU shader over a grid of workgroups; each one has a fixed start cost (small matrices).

On the Adreno the first version of the few-token pass did not pay. Lookup ran at 47 tokens a second against 120 plain (step 13 of results/phase-l3.md). The rest of this page is what changed that.

Why did each extra token cost a whole step?

The decode shader reads the gate/up weights at about 40 GB/s, while the GPU can read about 66 GB/s measured. So memory is not what holds it back.

The shader reads at 40 GB/s and the GPU can read 66. What holds the shader back?

  • Its arithmetic, which every token in a pass repeats
    The weights are turned into floats again for each token.
  • The memory bus, which is full
    A full bus would read at its limit, and 40 is below 66.
  • The fixed cost of starting each dispatch
    A 4-token pass pays that cost once, so it cannot explain a per-token cost.

Step 13 timed gate/up with more tokens per dispatch. A 4-token pass took 896 µs, 224 µs a token. One token through the decode shader took 123–168 µs. So every extra token cost 1.4–1.9 one-token dispatches measured.

The decode shader unpacks each 4-bit weight, converts it to a float and multiplies it with x. Step 13 names this arithmetic as the limit, and it is repeated for each token. A pass of n tokens cannot cost much less than n steps.

Takeaway: on the Adreno, a float pass over n tokens costs about n decode steps, because the arithmetic is repeated for each token.

A new shader stores x as 8-bit codes and multiplies them with the weight nibbles directly, never making floats. What now grows with each extra token?

  • Only the integer multiply-adds for that token
    The unpacking and float conversion no longer repeat per token.
  • Almost nothing, since the weights are read once
    Reading once helps memory, but the arithmetic still repeats per token.
  • The float conversion, which it still needs
    That was the cost removed; the new shader makes no floats from the weights.

What does rounding x to 8 bits do?

The weights are already 4 bits each. The cost is in x, which is stored as f32. llama.cpp’s GPU backends round x to 8 bits for small batches. Its Q8_0 format keeps one scale per block of 32 values (how Q8_0 packs 32 weights). Our shaders/quant_x.comp does the same for x, with one change: the scale stays f32.

f32 x, one token     32 values per block, 4 bytes each
[x0 x1 ... x31] [x32 ... x63] ...
       |   d = max |x| / 127     one f32 scale per block
       v
int8 codes [q0 q1 ... q31]        -127 to 127, 1 byte each
       |
       v
OpSDot: weight bytes times codes, four products summed
       |
       v
int sum, times d and the weight block's scale: f32

The core of shaders/quant_x.comp, shortened:

float d = max(max(m.x, m.y), max(m.z, m.w)) / 127.0;
float inv = d == 0.0 ? 0.0 : 1.0 / d;
qv[k] = roundf(v[k] * inv);
  • m holds the largest magnitudes of the 32 values, so d maps the largest value to 127.
  • inv is computed once per piece. Each value then multiplies by it instead of dividing.
  • roundf rounds halves away from zero, as gguf-py does. The codes match gguf-py’s Q8_0 quantizer, with at most 1 in 1000 one step off (step 18).
  • The shader also stores the sum of each half’s codes. The weight formats’ offsets are taken out with those sums.
  • OpSDot is one GPU instruction that multiplies four pairs of signed bytes and adds the products. It comes from VK_KHR_shader_integer_dot_product. The weight nibbles are masked into bytes, so no weight becomes a float.
Illustration, made-up numbers

A piece of x has largest magnitude 2.54, so d = 2.54 / 127 = 0.02. The value 1.27 becomes 1.27 / 0.02 = 63.5, which rounds to the code 64.

A value’s rounding error is at most half a step of d: 0.01 in this piece calculated.

Takeaway: rounding x costs one f32 scale per 32 values, and it lets the products be integer multiply-adds.

Another piece of x has largest magnitude 2.54 too, but this time the engine multiplies by 127 instead of dividing. What is d?

  • 0.02
    d is the largest magnitude divided by 127.
  • 322.6
    That is 2.54 times 127. Dividing gives the scale.
  • 0.2
    That divides by 12.7, one place off from 127.

Does lookup pay on the GPU now?

Lookup pays when drafts are accepted. The int8 products cut what a 4-token pass costs. On Q4_0 the pass cost 2.23 decode steps for 4 tokens, against about 8 before, with one step at 9.7 ms measured (step 14; IMPLEMENTATION.md section 0).

Plain GPU decode of a Q4_K_M code reply ran at 63.8 tokens a second. With lookup at 4 drafts on the same GPU, after the int8 change, what did it run at?

  • 117.3 tokens a second, about 1.8 times as fast
    Code was the copying case in this table, and lookup paid there.
  • About 47 tokens a second, as in step 13
    That was the float pass, before the int8 products.
  • 63.8 again, since the drafts are the same
    The drafts are the same; the cost of a pass changed.

On a copying prompt lookup is calculated 18 % faster on Q4_0 (123.0 against 104.3) and 84 % faster on Q4_K_M (117.3 against 63.8). With few drafts accepted it is slower: 11 % and 15 % behind plain on Q4_K_M prose and story (64.0 against 72.2, and 63.0 against 74.4).

The rule changed later (step 25). On battery, GPU Q4_0 code ran at 139 and 127 tokens a second with adaptive lookup, against 120 and 100 plain. Prose and story ran behind plain again: 100 and 98 against 115 and 123 measured.

Takeaway: lookup on the GPU pays on copying text and loses when drafts miss, as it does on the CPU and the DSP.

Q4_K_M prose ran slower with lookup than plain (64.0 against 72.2). What is the main reason?

  • Only 10 of 60 drafts were accepted, so the passes cost more than the steps they replaced
    A rejected draft still pays for its whole pass.
  • The int8 rounding made the drafts wrong
    Rounding changes the numbers only slightly; the drafts missed for their text.
  • Lookup never pays on an Adreno GPU
    It pays on the copying prompts in the same table.

Did int8 help prefill and decode too?

Prefill reads the whole prompt in one pass, so the products run over many tokens at once. Decode makes one token at a time. Both use the same products.

Prefill for Qwen2.5-0.5B Q4_0 at 128 tokens went from 1,049 to 1,546 tokens a second, with the int8 product in place of the f16 one (commit a6d6838). The two int8 runs were 1,548 and 1,544; the two f16 runs were 1,049 and 1,052 measured. The Q4_K_M prefill at 128 tokens went from 634–644 to 1,027–1,029 measured (step 19).

Decode with int8 x, on the phone:

  • Q4_K_M, charging (step 23): 53.2 to 67.5 tokens a second, +27 % measured.
  • Q4_K_M, battery (step 24): +22 % to +60 % across depths 0, 256 and 1024 measured.
  • Q4_0, battery (step 24): about the same, +2 % to −11 %, the sign changing with depth and round measured.

Q4_K_M gained most because its K-quant decode was limited by arithmetic. It spent 12.3 ms of GPU time a token, against 9.0 ms for Q4_0 (step 11). Since step 24, int8 x is the default for decode; Options::decode_f32 keeps the f32 path.

Takeaway: int8 products sped up prefill in every format we measured, and decode most where the K-quant arithmetic was the limit.

What does the int8 prefill product replace in the shader?

  • The f16 multiply-adds, with OpSDot doing four integer products per instruction
    Only the arithmetic changed; the weights keep their 4-bit format.
  • The stored weights, which are re-quantized to int8
    The weights stay in their 4-bit format; only x is rounded.
  • The attention over the prompt
    Attention is a separate shader, changed in its own step.

Does rounding x cost accuracy?

Perplexity scores a text: lower is better. KL divergence compares the model’s whole next-token distribution with the f32 model’s, at every position; lower is closer.

The int8 pass moved Qwen2.5 Q4_0 perplexity by 0.02. Which check says whether that matters?

  • llama.cpp’s error bar, and KL against the f32 model
    Both compare the rounding with the reference, not with itself.
  • Whether the greedy text is the same as f32’s
    Greedy text can fork at a near tie without any error that matters.
  • The perplexity change alone
    Perplexity cannot rank the two; its error bar is wider than the move.

Perplexity’s error bar is wide: llama.cpp’s own run varies by ±0.7 to ±1.2 here, 20 to 50 times the f16 to int8 moves (step 20). So perplexity cannot rank the two; KL can.

For Qwen2.5 Q4_0 the int8 KL is 0.181107 and llama.cpp’s is 0.181010 ± 0.002752. Which reading fits?

  • int8 is within llama.cpp’s error bar; f16 is a little closer to f32
    The gap of 0.0012 is smaller than llama.cpp’s spread.
  • int8 is less accurate than llama.cpp, so the rounding is a bug
    llama.cpp’s own error bar covers the int8 figure.
  • A KL of 0.18 means about one token in five is wrong
    KL is a distance between distributions, in nats, not a share of wrong tokens.

What you should take away

On the Adreno a float pass cost about one step per extra token, because its arithmetic repeated for each token. Rounding x to 8 bits per 32 values, with OpSDot, made 4 tokens cost 2.2 steps, so lookup pays on copying text.

Prefill rose 47 % at 128 tokens, and decode gained most on Q4_K_M, with perplexity within llama.cpp’s error bar.

Numbers on this page were measured on the iQOO 13 (SM8750), 2026-10-31 to 2026-11-01, unless tagged otherwise. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
