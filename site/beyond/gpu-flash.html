Flash attention: was it the kernel or the batch?

Flash attention and a bigger prompt batch both went into the GPU’s prompt pass. The phone’s measurements say the speed came from the batch. The flash kernel alone was slower than the chunked pair it replaced. This page explains the online softmax that makes one pass exact, the two-dispatch version it replaces, and the measurements that separated the two causes.

What are we trying to do here?

A prompt is read in passes. Each pass takes a batch of prompt tokens and runs them through the whole model together, so each weight matrix is read once per pass instead of once per token. Attention is the part of each layer that looks back at every earlier position in the cache: the keys and values of all the tokens before. Its cost grows with the context.

Flash attention computes that look-back in one pass over the positions, without a separate step to find the largest score first. This page asks what made the GPU’s prompt pass faster in the last round of work: the new kernel, or the bigger batch it allowed. By the end you can explain the online softmax, say why the chunked version needed a merge, and read the three measurements that answer the question.

How does attention over a long context get split?

Attention for one new token takes its query and compares it with the key of every cached position. That gives one score per position. Softmax turns the scores into weights, and the output is the values weighted by them. A query head is one of the model’s attention heads; Qwen2.5-0.5B has 14. A workgroup is a group of GPU threads that the GPU schedules as one unit (How the GPU runs our code).

At depth 4096, one head has 4096 scores to compute. If each head is one workgroup, the GPU gets 14 workgroups for the whole token, and most of the GPU sits idle.

How can the attention of one token give the GPU more workgroups?

  • Cut the positions into chunks and give each (head, chunk) pair its own workgroup
    Each chunk is independent work, so the GPU can run the chunks side by side.
  • Give each head two workgroups, one for the keys and one for the values
    Splitting by data type leaves each workgroup walking every position.
  • Compute the softmax first, then the values, in two kernels
    Two kernels still walk every position once per head.

This is flash-decoding, the split used for decode (Decoding on the GPU). Each chunk of positions, here 64 of them, makes a partial result with three parts:

  • m, the largest score in the chunk;
  • l, the sum of escore − m over the chunk’s positions;
  • out, the chunk’s weighted sum of values, also taken relative to m.
one token, 14 query heads, 4096 cached positions

chunk 0    positions     0 ..   63   ->  m0,  l0,  out0
chunk 1    positions    64 ..  127   ->  m1,  l1,  out1
  ...
chunk 63   positions  4032 .. 4095   ->  m63, l63, out63
                    |
                    v
merge, one workgroup per head   ->  the head's output

A merge step combines the chunks of a head. With M the largest chunk max, it scales each chunk by emc − M, so every chunk shares one reference point. This is attention_merge.comp, used for decode and by the chunked prompt path:

float mx = -1.0 / 0.0;
for (uint c = 0; c < n; c++) mx = max(mx, parts[base + c * stride]);
float num = 0.0, den = 0.0;
for (uint c = 0; c < n; c++) {
    float w = exp(parts[base + c * stride] - mx);
    num += w * parts[base + c * stride + 2 + d];
    den += w * parts[base + c * stride + 1];
}
o[(t * n_heads + h) * hs + d] = num / den;
  • The first loop finds M, the largest chunk max.
  • w is the factor emc − M for one chunk. It is never above 1.
  • The sums num and den use the same factor, so the chunks add up correctly.
  • The division happens once, at the end.

At depth 4096 with 64-position chunks, a head has 64 chunks, so one token has 14 × 64 = 896 workgroups calculated. That keeps the GPU busy. The cost is one partial result per chunk, written and then read back. The split suits decode because a decode step has one token: without it there are only 14 heads of work, and splitting over positions is the only other source of parallel work.

Takeaway: a long context is cut into chunks; each gives (m, l, out), and a merge rescales them to one max.

At depth 8192, with 64-position chunks, how many chunks does one head have?

  • 128
    8192 divided by 64 positions a chunk.
  • 8192
    That counts positions. A chunk holds 64 of them, so there are far fewer chunks.
  • 14
    That is the number of heads. The chunks are a split of each head’s positions.

How can one pass give the exact softmax?

Softmax divides each score’s exponential by the sum of all of them. An exponential of a large score overflows: the float becomes too big to store and turns into infinity. The usual fix subtracts the largest score M from every score first, so every exponent is zero or below. That needs M before the first exponent, so the usual version reads every score twice: once to find M, once to add up.

Flash attention avoids the first read. It keeps two numbers as it goes: the running max m, the largest score so far, and the running sum l, the sum of escore − m so far.

Chunk 3 holds a score larger than the running max. The running sum holds terms measured against the old max. What must happen to the running sum?

  • It is multiplied by eold max − new max, and then the new terms are added
    The factor moves the old terms onto the new reference point.
  • Nothing: the new terms are simply added to it
    The old terms are still measured against the old max, so they are overstated.
  • It is reset to zero, and the chunk starts again
    That throws away the weight of every earlier position.

When a new score is larger than m, the old sum was measured against the old max, so it has to be scaled to the new one. For a new score s, with m′ = max(m, s):

l = l · e^(m − m′) + e^(s − m′)
  • If m′ equals m, the factor is e⁰ = 1 and the sum only grows.
  • If a larger score arrives, the factor is below 1 and shrinks the old sum to the new reference.
  • The weighted sum of values (acc) takes the same factor. At the end the output is acc ÷ l.

Takeaway: keep a running max and sum, and multiply the sum by eold max − new max whenever the max rises.

Chunk 4’s largest score is 3.5, and the running max is 4.0. What is the factor for the old running sum?

  • 1, because the max stays 4.0
    Only a larger score moves the max, so the old sum needs no change.
  • e3.5 − 4.0 = 0.6065
    The factor compares the old running max with the new one, not with the chunk’s max.
  • 0, because the old sum is dropped
    Dropping it loses every earlier position.

Why did the prompt pass need two dispatches and a parts buffer?

The prompt pass works on a batch of tokens at a time (Who reads the prompt?). The chunked prompt path gives each workgroup a head, a chunk and a group of 32 tokens. Its partial results need somewhere to go: a parts buffer with one slot per token, head and chunk, each holding (m, l, out). For a head of 64 values, a slot is 66 floats.

So the chunked prompt path is two dispatches per layer. attention_tile.comp writes the slots, and attention_merge.comp reads them back.

The parts buffer has a fixed budget of 32 MB, sized for the whole cache. What happens to the batch as the cache grows?

  • It shrinks, because the same budget holds fewer tokens’ slots
    More positions mean more chunks, so each token needs more slots.
  • It grows, because more chunks share the work
    More chunks mean more slots to store, which needs more room, not less.
  • It stays fixed, because the model’s layers set the batch
    The batch is set by the buffer’s size, not by the model.

Each slot has a fixed size, but a longer cache has more slots per token, so the budget holds fewer tokens. For Qwen2.5-0.5B the batch is 128 tokens at 4096 positions (the cap), 70 at 8192 and 17 at 32768 calculated from the budget in plans/flash-attention.md. At 17 tokens the 64-token matrix tiles run a quarter full, which slows the whole pass, not only attention.

The merge is short. This is the core of attention_merge.comp:

float mx = -1.0 / 0.0;
for (uint c = 0; c < n; c++) mx = max(mx, parts[base + c * stride]);
float num = 0.0, den = 0.0;
for (uint c = 0; c < n; c++) {
    float w = exp(parts[base + c * stride] - mx);
    num += w * parts[base + c * stride + 2 + d];
    den += w * parts[base + c * stride + 1];
}
o[(t * n_heads + h) * hs + d] = num / den;
  • Each token and head reads back every chunk it wrote, so the parts are read as well as written.
  • The parts are sized for the whole cache, not for the tokens that are actually there.

attention_flash.comp drops both problems. Each workgroup takes 32 tokens of one head, walks every position those tokens can see in one pass with the running max and sum, and writes the finished output to xb2. There is one dispatch per layer, no parts and no merge, and the batch no longer depends on the cache length. The default batch is now 256 tokens (commit 3f0aee0).

Takeaway: the chunked prompt path paid for its split in a parts buffer, and the buffer capped the batch as the cache grew.

Flash’s prompt attention runs once per layer. How many attention dispatches does that take?

  • One: each workgroup walks all of its positions, so there is no merge
    The running max and sum make a single pass exact, so the merge is gone.
  • Two: the tile shader and the merge, as before
    That is the chunked path. Flash has no parts, so it needs no merge.
  • One per chunk, so the chunks run in parallel
    Chunks are the chunked path’s split. Flash has none.

Did the flash kernel make the prompt faster?

The GPU record leads here, from step 22 to step 28. Step 22 replaced the first prompt attention shader, which gave each token its own workgroup, with attention_tile.comp. Attention at 512 tokens fell from 134.6 ms to 57.3 ms measured (profiled, phone charging). That was a real kernel gain, and it was kept.

The next question was whether one dispatch beats the chunked pair at depth, where the cache is long.

Flash has one dispatch and no merge. At depth 4096 with 512 tokens, is its attention kernel faster or slower than the chunked pair?

  • Slower, even with no merge
    On this phone the flash kernel took longer, with no merge to pay for.
  • Faster, since the merge is gone
    The merge was 109 ms of 918, so removing it cannot pay for a slower kernel.
  • The same, since both read the same keys and values
    Equal bytes are not equal time: the GPU needs enough workgroups running at once.

From depth 1024 up, the flash kernel was 1.2 to 1.7 times slower at every length. At depth 0 it was faster at pp64 and pp128 (3 and 7 ms against 4 and 10), about level at pp256 (23 against 22) and slower at pp512 (83 against 67). The reason is how the work is split, not extra work: both read the same keys and values. A 128-token pass gives flash 14 × 4 = 56 workgroups, each walking every position in turn. The chunked path dispatched 1,000 to 4,000 short workgroups, and the GPU stayed full.

The whole pass was level at depth 0 (408 against 417 ms at pp512) and 25 % slower at depth 4096 (1621 against 1296 ms). Flash lost on the kernel, and at depth it lost on the pass too.

Step 28 then raised the batch to 256 tokens, with the same flash kernel. Its attention fell, because 256 tokens double the token groups per head (8 instead of 4) and halve the number of passes.

So the gain is the batch, not the flash kernel. Flash at 128 tokens was no faster than the chunked path. At 256 tokens the whole pass was 11 to 19 % faster than flash at 128, and the stages other than attention dropped 8 to 10 %: each weight matrix is read twice for 512 tokens instead of four times. The flash kernel itself is still 1.10× the chunked one at depth 4096 (1007 against 918 ms). Flash’s real contribution is that it makes 256 tokens possible at any context. The chunked partial results would take about 68 MB at a 4.6K cache and about 480 MB at 32K. The chunked path was not measured at 256 tokens, so it might beat flash there.

Takeaway: the flash kernel was slower on this phone; the faster pass came from the 256-token batch that flash made possible.

Step 28 kept the shader and changed only the batch. Attention at depth 4096 fell from 1289 to 1007 ms. Why?

  • Each 256-token pass has twice as many token groups per head, so more workgroups run at once
    The same shader spreads over more workgroups, so the GPU is busier.
  • The shader now stores keys as f16
    Both batch sizes use the same f16 storage, and the shader did not change.
  • Each token attends to fewer positions
    Every token still sees the same positions; only the number of passes changed.

What should you compare before you credit a change?

This story changed two things: the kernel, flash in place of the chunked pair, and the batch, 128 tokens to 256. The phone also changes under you. During the flash session the CPU clock caps fell (step 26: cpu0 from 2.92 to 2.40 GHz), so one run can differ from the next for reasons that have nothing to do with the code.

You want to know whether flash’s kernel beats the chunked pair. Which comparison answers that?

  • Both kernels at the same batch, in one session, with the run order reversed in a second round
    Only one thing differs, and the drift hits both arms alike.
  • Flash at 256 tokens against chunked at 126, from last week’s session
    That changes two things and the session, so the difference has no single cause.
  • The fastest run of each, one run each
    One run can catch a clock spike, and the best of one run is noise.

The comparison that isolates the kernel holds the batch fixed. Each pair runs back to back, the order is reversed in the second round, and the figures are compared within a pair, not across the hour. A profile counts GPU time per stage, so the attention share can be read even when the whole run has drifted. The Phase 7 page on NEON attention, measured honestly teaches the same method on the CPU: one timing run can mislead, and run order matters.

Step 28’s batch comparison was across sessions, as its own text says. That is why this page reads the chunked column as a guide and not as a verdict.

Takeaway: change one thing per comparison, run the arms back to back in both orders, and profile by stage.

Two runs of the same pass are taken 20 minutes apart, and a clock cap fell between them. How should you read their difference?

  • As a guide only, unless the runs were back to back in both orders
    Drift over the hour is not a code difference; only back-to-back pairs compare.
  • Average the two runs, since the drift cancels out
    A number averaged across a drift matches neither run.
  • Take the faster run as the true speed
    A run can be fast because the clocks were high at that moment.
