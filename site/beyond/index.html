After Phase 8 — faster decoding and the GPU

By Phase 8 the engine ran in an app at close to the phone’s memory limit. The work since asks two questions. Can one read of the weights produce more than one token? And what is the phone’s GPU good for, when it reads the same memory as the CPU?

Why go further than the plan? What was built? What are the headline numbers? Which page should I read first? What is still open? Which files hold the code?

Why go further than the plan?

The plan’s section 13 lists later work: K-quant files, speculative decoding, Vulkan compute on the GPU, and the NPU. Decode had reached about 180 tokens per second for Qwen2.5-0.5B Q4_0, about 50 GB/s of weights calculated, close to the memory’s 61–67 GB/s. A faster kernel could not give much more. Getting several tokens per weight read could, and the GPU might do the same work for less energy.

Takeaway: once decode is near the memory limit, the next gains come from more tokens per read and from cheaper hardware, not faster kernels.

What was built?

  • Q4_K_M files. llama.cpp’s most common mix (Q5_0, Q4_K and Q6_K blocks) loads and runs, with perplexity checked against llama.cpp (results/phase-6.md, “Q4_K_M files”). Page: Q4_K_M files.
  • Speculative decoding. Draft tokens, copied from earlier text (prompt lookup) or proposed by a smaller model, checked in one batched pass. CLI --lookup K, --draft PATH; the app’s “lookup” checkbox.
  • Vulkan compute on the Adreno GPU. A Q4_0 matrix-vector and matrix-matrix shader, then a whole decode step, then the prompt: on the CPU with the KV cache handed to the GPU, or batched on the GPU. CLI --gpu; the app’s “GPU” checkbox.

Takeaway: three additions, each checked against an outside reference before any speed was measured.

What are the headline numbers?

+60–75 %decode with prompt lookup when the answer copies the prompt, greedy, Qwen2.5-0.5B measured
0.021–0.024 Jenergy per token on the GPU at 102.7 tok/s, against 0.029 J on the CPU at 157.6 measured
19.7193GPU perplexity of Qwen2.5-0.5B Q4_0; llama.cpp 19.7283 ± 0.836 measured
7×faster prompt in GPU mode when the CPU reads it and hands over the KV cache (345 tokens: ~4 s → ~0.55 s) measured

Takeaway: lookup pays on repeated text; the GPU is slower than the CPU but spends less energy per token.

Which page should I read first?

  1. Several tokens per weight read: drafts, the rule that keeps them, lookup against a draft model, and speculative sampling.
  2. How the GPU runs our code: lanes, workgroups, Vulkan, and how a matrix-vector product is split across lanes.
  3. Decoding on the GPU: the whole step, attention in chunks, clock swings, energy, and where the time goes.
  4. Who reads the prompt?: the KV-cache handoff from CPU to GPU, a misleading measurement, and a batched GPU pass.
  5. Q4_K_M files: llama.cpp’s most common mix, K-quant super-blocks, accuracy against llama.cpp, and two speed fixes.

Takeaway: the speculative and Q4_K_M pages stand alone; the three GPU pages build on each other.

What is still open?

  • Phone timing of the newest GPU work: stages folded into the matrix products, logits in cached memory, and the batched GPU prompt. All are correct on the PC’s GPU.
  • L.2, an importance-weighted quantizer of our own, only if a model needs it.
  • L.5, the NPU: not started. It would need Qualcomm’s SDK, which conflicts with writing the engine from scratch, so it needs a decision first.
