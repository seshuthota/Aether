Who reads the prompt?

Feeding a prompt through the GPU’s decode step one token at a time took seconds. The CPU reads the same prompt in one batch in about half a second, and its KV cache can be handed to the GPU, which then decodes. This page covers that handoff, a measurement that first pointed the wrong way, and a batched prompt pass on the GPU itself.

What are we trying to do here?

Before the first new token, the model has to read the whole prompt. That is prefill: every prompt token goes through every layer, and the keys and values of every position land in the KV cache. Prefill can share each weight read across many tokens, so it is limited by arithmetic, not memory (prefill).

The first GPU mode had no batched pass, so it fed the prompt through the decode step one token at a time. This page makes the prompt fast in GPU mode in two ways: let the CPU do it and hand over the KV cache (aether --gpu -c 2-7, and the app’s GPU mode), or give the GPU a batched pass of its own (GpuModel::forward_batch).

Why is the prompt slow through the decode step?

A decode step reads all 278 MB of Qwen2.5-0.5B’s weights for one token. Fed one at a time, every prompt token pays that read again. The CPU’s batched pass reads each weight once for many tokens and spends the time on arithmetic instead.

A 345-token prompt took 3.9–4.5 s through the GPU’s decode step. About how long did the CPU’s batched pass take on cores 2–7?

  • About 0.55 s, 7× faster
    The batched pass reads the weights once per batch, so the CPU’s arithmetic units set the pace.
  • About 4 s, the same
    That would be true if the CPU also went token by token.
  • About 0.05 s
    Batching removes the repeated reads, but the arithmetic for 345 tokens still takes time: 570–635 tokens per second.

Measured, Qwen2.5-0.5B Q4_0, the start of wikitext-2 as the prompt, two runs measured: token by token on the GPU 3,873 and 4,474 ms; batched on the CPU 602 and 543 ms.

Takeaway: through the decode step every prompt token pays a full weight read; a batched pass pays it once.

How can the CPU hand its work to the GPU?

After prefill, the only state the next token needs is the KV cache: the keys and values of every prompt position in every layer. The logits of the last prompt token give the first new token.

The CPU’s cache and the GPU’s use the same layout, one block per layer, one row of kv_dim floats per position:

layer 0: pos 0 | pos 1 | ... | pos seq_len-1
layer 1: pos 0 | pos 1 | ...
...
each row: kv_dim floats (128 for Qwen2.5-0.5B)

How much must be copied per prompt token for Qwen2.5-0.5B (24 layers, kv_dim 128, f32 keys and values)?

  • About 24 KB
    24 layers × 128 floats × 2 (keys and values) × 4 bytes = 24,576 bytes.
  • About 278 MB
    That is the weights, which the GPU already has.
  • About 3.5 KB, one activation vector
    Every layer keeps its own keys and values, so it is 24 layers’ worth.

GpuSession::open_hybrid loads a second copy of the model for the CPU. Per prompt: the CPU runs forward_batch, samples the first token from its logits, and GpuModel::load_kv copies rows 0..n of each layer into the GPU’s cache. Decoding continues on the GPU at position n. For the 345-token prompt that is about 8 MB calculated, a negligible share of the time.

The cost is memory: the weights are loaded twice, +278 MB. The check that it is right: on “Why is the sky blue?”, GPU-only and CPU-prompt-then-GPU printed the same greedy text, token for token, for 114 tokens. A wrong cache row would change the text within a few tokens. The C ABI test also runs both modes and compares their output.

Takeaway: the KV cache is all the state a prompt leaves, so with matching layouts the CPU can read the prompt and the GPU continue.

The CPU’s cache was sized for 400 positions and the GPU’s for 1,024. What must the copy take care of?

  • Each layer starts at a different offset in each cache
    Layer l starts at l × seq_len × kv_dim, so the copy uses each side’s own seq_len per layer.
  • Nothing: one block copy of n × kv_dim floats
    That copies layer 0 correctly and the other layers to the wrong place.
  • It cannot work unless both are equal
    It works per layer; load_kv takes the CPU’s seq_len for that reason.

Did decoding get slower after the handoff?

The first measurement, on a warm phone on the charger (44–50 °C), said yes: decode after the CPU prefill ran at 63–75 tokens per second, against 81–82 for GPU-only measured. The obvious suspects were the CPU’s threads still spinning, or the GPU’s clocks dropping during the half second it sat idle while the CPU read the prompt.

The same comparison was repeated on battery, at 34 °C, alternating the two modes and timing every token. What did it show?

  • The CPU-prompt mode decoded faster: 102–103 against 84–89 tok/s
    The earlier gap came from the phone’s state, not from the handoff.
  • The same 20 % gap
    The gap did not survive a cooler phone and alternating runs.
  • A slow start for 20 tokens, then equal speed
    Per-token times showed no slow start, only one slow token in each run.

Each step of the investigation removed one suspect measured:

  • One prefill core instead of six decoded no faster, and the pool’s threads park about 3 ms after the batch. The threads were not the cause.
  • Off the charger at 37–38 °C, the gap shrank to 3–11 %, about the spread between runs of the same mode.
  • At 34 °C, with every token’s time printed (aether --gpu --times), the CPU-prompt runs held 8–10 ms per token from the first token on; GPU-only runs sat at 11–12 ms after their 3.5 s of GPU prefill.

The lesson is the same as in NEON attention, measured honestly: on a phone, the conditions (heat, charger, the last few seconds of load) can be bigger than the change you are measuring, and only alternating runs under recorded conditions settle it.

Takeaway: the slowdown came from a warm, charging phone; alternating runs on a cool phone reversed it.

Why did per-token times settle the question when tokens per second could not?

  • They show whether a gap is a slow start or a steady difference
    A start-up loss and a sustained slowdown give the same average but different per-token traces.
  • They are more precise than an average
    The average uses the same tokens; the shape over time is what was missing.
  • They exclude the prompt
    The tokens-per-second figure excluded the prompt too.

Can the GPU read the prompt in one batch too?

The CPU copy costs 278 MB. A batched pass on the GPU itself needs no second copy. Every stage needs a batched form:

  • The matrix products become matrix-matrix products: q4_0_gemm.comp computes tiles of 64 rows × 64 tokens in shared memory, so each weight is read once per 64 tokens. On its own it reached about 260 GFLOP/s on the Adreno measured.
  • RMSNorm, bias + RoPE, attention and the merge take a token index from their workgroup ID. Token t is at position pos + t, and attends to the cache up to its own position, which includes the batch’s earlier tokens, written in the same pass.
  • With one token every index is 0, so the decode step runs the same shaders unchanged.

The batched GEMM adds numbers in a different order from the decode GEMV. What should scoring wikitext-2 through the batched pass give?

  • The same perplexity to four decimals
    The order changes the last bits of each logit, far below what an average over 5,100 tokens can show.
  • A clearly different perplexity
    The math is the same; only rounding differs, and f32 activations keep that tiny.
  • It cannot be scored in batches
    vk_ppl … batch returns every token’s logits from each pass.

Through vk_ppl … batch, 128 tokens per pass: SmolLM2-135M 27.6910 and Qwen2.5-0.5B 19.7193, the same as token by token measured (on the PC’s GPU, which matches the phone’s perplexities to four decimals).

Its speed on the phone is not measured yet. From the GEMM’s 260 GFLOP/s, a rough estimate is a few hundred tokens per second: several times the token-by-token GPU prompt, but likely below the CPU’s 570–635 estimate, not measured. So the app’s GPU mode keeps the CPU for the prompt, and the GPU batch is the option that saves the memory.

Takeaway: a batched GPU pass needs every stage to take a token index; it gives the same perplexity, and its phone speed decides when to use it.

Token 5 of a batch attends to positions up to its own. Where do the keys of tokens 0–4 of the same batch come from?

  • The cache, written by the bias + RoPE stage earlier in the same layer
    A barrier separates that stage from attention, so all of the batch’s keys are in the cache by then.
  • They are not used: a batch only attends to earlier batches
    Causal attention includes every earlier position, inside the batch too.
  • Each attention workgroup recomputes them
    They are computed once, by the stage before attention.

What you should take away

A prompt fed token by token pays a full weight read per token; a batched pass pays it once.

The KV cache is all a prompt leaves behind, so the CPU can read the prompt and hand it to the GPU. Measure such changes on a cool phone, alternating.

Numbers on this page were measured on the iQOO 13 (SM8750) on 2026-10-29 (results/phase-l3.md) unless tagged otherwise. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
