Several tokens per weight read

Decode reads every weight once per token, and the phone’s memory can only deliver so many bytes a second. Speculative decoding guesses a few tokens ahead and checks all the guesses in one pass over the weights. When the guesses are right, several tokens cost about one read.

What are we trying to do here?

After the speed work that followed Phase 8, decoding Qwen2.5-0.5B in Q4_0 ran at about 180 tokens per second on cores 2–7. Each token reads the 278 MB of weights, so that is about 50 GB/s calculated, close to the 61–67 GB/s Phase 1 measured as the phone’s memory bandwidth. A faster kernel cannot give much more.

The way past the ceiling is to get more than one token out of each read of the weights. Speculative decoding does that: something cheap proposes the next few tokens, called draft tokens, and the real model, the target, checks all of them in one batched pass, the way it reads a prompt.

This page covers the two kinds of drafts the engine has (copied from earlier text, or from a smaller model), the rule that decides which drafts to keep, why it still works with a random sampler, and what each one measured on the phone. The code is Session::generate_speculative in src/session.rs; the CLI flags are --lookup K and --draft PATH, and the app has a “lookup” checkbox.

Why can checking five tokens cost about as much as one?

A decode step multiplies each weight matrix by one vector. A batched pass, as in prefill, multiplies it by several vectors at once, and each weight loaded from memory is used for all of them. Decode is limited by bytes, not by arithmetic, so the extra vectors mostly use arithmetic units that were waiting anyway.

A decode step of Qwen2.5-0.5B Q4_0 took 5.5 ms. About how long did a batched pass of 4 tokens take?

  • About 8 ms
    The weights are read once for all four tokens; only the arithmetic and attention grow.
  • About 22 ms, four steps
    That would be four separate reads of the weights; a batch shares one read.
  • About 5.5 ms, the same
    Close, but the arithmetic for four tokens is not free; it adds a few milliseconds.

Measured on cores 2–7 measured: a batch of 2 tokens took 5.8 ms and a batch of 4 took 7.8 ms, against 5.5 ms for one decode step. Four tokens for 1.4 steps’ time.

That took a fix first. The smmla tiles of Phase 6 always covered 8 tokens, so a batch of 2 paid for 8 (11.3 ms). Tiles of 2, 4 and 6 tokens brought small batches down to the numbers above.

Takeaway: a batched pass of a few tokens costs little more than one decode step, because the weights are read once.

Why does the same trick not help prefill much more than it already does?

  • Prefill already shares every weight read across many prompt tokens
    A prompt is one large batch; speculative decoding brings that sharing to the tokens the model generates.
  • Prefill has no KV cache
    Prefill fills the KV cache; that is not what limits it.
  • Prefill cannot run batched passes
    Prefill is the batched pass; decode is the part that was one token at a time.

How does one pass tell which guesses were right?

Say the last certain token is c and the drafts are d1 d2 d3. The target runs c d1 d2 d3 as one batch and returns one row of logits per input. Row r is the model’s prediction for the token after input r, computed as if every input before it were true.

inputs:   c     d1    d2    d3
row:      0     1     2     3
predicts: d1?   d2?   d3?   next

With greedy decoding, the rule is:

  1. Keep d1 if it equals the argmax (highest logit) of row 0.
  2. If d1 was kept, keep d2 if it equals the argmax of row 1, and so on.
  3. At the first draft that does not match, take the argmax of the row before it instead. That token is certain too.

All three drafts match. How many new certain tokens does that pass produce?

  • Four
    The three drafts, plus row 3’s argmax: the prediction after d3 comes for free.
  • Three
    The last row still predicts one more token, and it is as certain as a decode step’s.
  • One
    One is the worst case, when the first draft is wrong: row 0’s argmax is still certain.

Every pass yields at least one certain token (row 0’s argmax, exactly what a plain decode step would give) and at most K + 1. The rejected drafts left keys and values in the KV cache; those positions are simply overwritten by the next pass. A test checks that on stories15M the output is byte for byte llama2.c’s greedy text.

Takeaway: drafts are kept while each matches the row before it, so a pass gives between 1 and K + 1 tokens and never a wrong one.

Drafts d1 d2 d3: d1 matches row 0, d2 does not match row 1. What does the pass produce?

  • d1 and row 1’s argmax
    Keep matching drafts; the first mismatch is replaced by the target’s own choice from the row before it.
  • d1 only
    Row 1’s argmax is certain too, so it is kept as well.
  • d1, row 1’s argmax and d3
    d3 was predicted after the wrong d2, so row 2 and later rows are discarded.

Where do guesses come from without a second model?

Qwen2.5-0.5B is the smallest model of its family, so there is no smaller Qwen to make drafts. Prompt lookup needs no model at all. It takes the last N tokens (the n-gram, 2 by default), finds the most recent earlier place in the prompt or the output where the same N tokens occurred, and copies up to K tokens that followed them there.

... the function returns the sum of a and b ...
                         ^^^^^^^^^^^^^ earlier
now: "returns the"  -> drafts: "sum of a"

Which task should speed up most with prompt lookup?

  • “Add comments to this function”, with the function in the prompt
    The answer copies the code back, so the drafts are nearly always right.
  • Writing a new short story
    Fresh prose rarely repeats earlier text, so lookup finds few drafts that match.
  • Both equally
    The drafts are only as good as the repetition between the text and what came before.

Qwen2.5-0.5B Q4_0, cores 2–7, two rounds, decode tokens per second measured:

Copying gains 60–75 % with greedy decoding. Fresh prose is about neutral: within −10 % to +15 %, inside the run-to-run spread. A longer n-gram (3) found too few matches to pay for its passes.

Takeaway: prompt lookup costs nothing to draft and pays when the output repeats earlier text.

Why didn’t a small draft model help more?

The classic version uses a draft model: a smaller model with the same vocabulary that decodes K tokens on its own, which the target then checks. SmolLM2 comes in 135M and 360M sizes, so the 135M model drafted for the 360M one.

The drafts were accepted 70–95 % of the time. Q4_0, prose prompt: plain decode of the 360M model ran at 179–196 tok/s. What did drafting with K = 3 reach?

  • About 230 tok/s, +17–29 %
    Drafting costs more than the 135M model’s size suggests, which eats most of the gain.
  • About 500 tok/s, nearly 3×
    That would need free drafts; the draft model’s own steps are a large share of each round.
  • About 150 tok/s, slower
    It did not gain on the code prompt, but on prose it gained a little.

The cost model explains it. The 135M model decoded only about twice as fast as the 360M one, not the 2.7× their sizes suggest: both have about 30 layers, and at this size a fixed cost per layer is a large share. A round with K = 3 costs about three draft steps (half a target step each) plus a batched check of 4 tokens (1.4 target steps): about 2.9 target steps for at most 4 tokens calculated. At 90 % acceptance that is about 3.6 tokens, so +25 % at best, which is what the prose prompt got.

Lookup did even better on prose here, because the 360M base model loops on that prompt, and repeating text is what lookup accepts for free. A draft model pays when the target is much bigger than the draft.

Takeaway: a draft model only pays when its steps are much cheaper than the target’s; at 2× it barely does.

The same pair stored in Q8_0 (twice the bytes) gained a little more often. Why?

  • The target got slower per step, so each draft step became relatively cheaper
    What matters is the ratio between draft and target step costs, not their absolute speed.
  • Q8_0 drafts are more often accepted
    Acceptance was high in both formats; the cost ratio moved more.
  • Q8_0 has no batched pass
    Both formats check drafts with the same batched pass.

Does it still work when the sampler is random?

With temperature and top-p, the next token is drawn at random from a distribution p (see sampling). “Keep the draft if it is the argmax” would change which tokens come out. The rule that keeps the output distributed exactly as p is speculative sampling:

  1. Compute p from the row, exactly as the sampler would.
  2. Keep the draft d with probability p(d).
  3. Otherwise, draw a token from p with d removed (the rest scaled up to sum to 1).

Why it is exact, for a token t other than d: it comes out only on the reject path, with probability (1 − p(d)) × p(t) / (1 − p(d)) = p(t). And d comes out with probability p(d). Greedy decoding is the temperature-0 case of the same call (Sampler::sample_draft). A test draws 200,000 times and compares against the closed-form probabilities, within 0.005 measured.

Takeaway: speculative sampling keeps a draft with probability p(d), so the output follows exactly the distribution plain sampling would.

Why does lookup gain less with sampling than with greedy on the code task (+25–50 % against +60–75 %)?

  • A draft is kept only with probability p(d), so even a likely draft is sometimes rejected
    With greedy, a draft that is the argmax is always kept; sampling turns some of those into rejections.
  • Sampling changes the drafts lookup finds
    Lookup copies from the text either way; what changes is how often a draft is kept.
  • Sampling makes the batched pass slower
    The pass costs the same; the sampler runs after it.

Why does the greedy text sometimes change?

On the copying prompts, lookup produced the same text as plain greedy decoding. On the story, the two texts went apart after about 80 tokens. No draft was kept wrongly: the batched pass and the single-token step compute the logits by different routes.

On the f32 model, the two routes agreed to within 0.00005 in every logit. On Q4_0, how far apart were they?

  • Up to 0.4–0.65 in a logit
    Activations are rounded to int8 before every product, and a tiny float difference sometimes flips one int8 value.
  • Still about 0.00005
    That holds for f32 only; quantizing the activations amplifies small differences.
  • Far apart: the routes compute different things
    They compute the same model; only the order of additions and the rounding points differ.

Before each matrix product, the Q4_0 path rounds the activations to int8. A difference of 1e-7 from another summation order now and then pushes one value across a rounding boundary, and 24 layers carry that on. Meanwhile the gap between the best and second-best token was as small as 0.02 at some steps, so the argmax can flip. The result is “greedy under the batched path’s numbers”: equally valid, not the same digits. llama.cpp’s own batched and single-token paths differ the same way.

Takeaway: quantized activations make the batched and single-token passes differ slightly, and where two tokens are nearly tied, greedy text forks.

How was lookup decoding’s correctness tested, given this?

  • On stories15M in f32, where the routes agree, against llama2.c’s greedy text
    An f32 model has no int8 rounding, so the output must match the reference byte for byte.
  • By comparing it with plain greedy on Qwen Q4_0
    Those legitimately fork, so equality there is not a valid test.
  • It was not tested
    Tests lookup_decoding_gives_llama2c_greedy_text and draft_model_decoding_gives_llama2c_greedy_text check it.

What you should take away

Decode is bandwidth-bound, so checking several guessed tokens in one batched pass costs little more than one step. Guesses are kept while each matches the target’s own choice, so the output is never wrong.

Prompt lookup pays when text repeats; a draft model only when it is much cheaper than the target.

Numbers on this page were measured on the iQOO 13 (SM8750) on 2026-10-29 (results/phase-6.md, “Prompt lookup decoding” and “Speculative decoding with a draft model”) unless tagged otherwise. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
