The NPU · 04

How does attention stream through VTCM?

Attention reads more of the cache at every token as the text grows. On the DSP, the cache sits in DRAM, so the DSP copies it through its on-chip memory in blocks of 256 positions, overlaps each copy with the work on the block before, and stores the keys and values as f16. At depth 2048 on Qwen2.5-0.5B these changes took attention from 17680 to 2234 µs per token.

What are we trying to do here?

Decode runs attention once per layer, for every token. The cache keeps a key and a value for every layer, every K/V head and every position so far (The KV cache). Attention reads them from there. On the DSP the cache is in DRAM, the phone’s main memory. The DSP also has its own on-chip memory, called VTCM, which is 8 MB on this phone. By the end you can explain how the DSP’s attention moves the cache through VTCM, why each change was made, and what each one measured at depth 2048.

Why does attention get slower with depth?

Each decode token runs two kinds of work. The weight products multiply the token by fixed matrices. Attention looks back at the earlier positions and mixes their values.

As the cache grows from 0 to 2048 positions, which work reads more bytes per token?

  • Attention, which reads the key and value of every cached position
    Each token scores against all cached keys and sums all cached values.
  • The weight products, which read the same matrices at any depth
    They do read the same matrices, but that does not change with depth; the cache does.
  • Neither, because the cache is only written, not read
    Attention reads the whole cache for every token; the write is one position.

Depth is the number of cached positions. Attention reads each position’s key and value, so its bytes per token grow with depth. The weight products read the same matrices at every depth, so their time stays flat. Qwen2.5-0.5B on the DSP spent 263 µs in attention at depth 0, 3464 µs at depth 512 and 17142 µs at depth 2048 measured, with the rest of the step within a few tens of microseconds across those depths.

Qwen has 14 query heads and 2 K/V heads, so each K/V head serves a group of 7 query heads. SmolLM2-135M has 9 and 3, groups of 3. A K/V head’s values are needed by every query head in its group.

Takeaway: attention’s bytes per token grow with every cached position; the weight products’ do not.

Qwen has 14 query heads and 2 K/V heads. For one token and one K/V head, how many query heads need its values?

  • 7, the group of query heads that share that K/V head
    Each K/V head serves one group of 7 query heads.
  • 14, one for every query head
    Query heads share K/V heads, so not every head needs its own copy.
  • 2, the number of K/V heads
    That counts the K/V heads, not the query heads that use each one.

How does attention fit a cache that VTCM cannot hold?

A DMA is a copy the DSP’s engine does while the thread goes on computing. Depth 2048 needs more K and V than VTCM holds, so attention cannot copy the whole cache first.

The cache at depth 2048 is larger than VTCM. What should attention do?

  • Copy one block of 256 positions at a time, and use each block for every query head that needs it
    A block that fits is copied once, and the whole group reads it from VTCM.
  • Copy the whole cache into VTCM before the layer starts
    The cache is bigger than VTCM, so the copy cannot fit.
  • Shrink the cache until it fits in VTCM
    Every position is needed; a smaller format helps, but does not make the cache fit.

Attention works in pieces of one K/V head and one block. A block is 256 positions of one K/V head: its keys are packed, and its values follow in order. The DMA copies it into one of two slots in the thread’s share of VTCM. Every query head of that K/V head reads the block there. Each thread keeps a running maximum, sum and output for each query head, so the softmax can be finished block by block. The merge is of the same kind as the one for the GPU’s chunks (Decoding on the GPU). The blocks merge in order after a barrier, the point where every thread waits for the others.

// dsp/model.c
#define ATTN_BLOCK 256
#define ATTN_STREAM_AT 256
  • Below 256 positions the cache is not streamed. Attention reads it from DRAM and asks L2 for bytes ahead of the loads: l2fetch, a request to the L2 cache to load bytes before they are used.
  • One slot holds the keys and values of one block: 64 KB at f16, calculated from 64 values per head and 256 positions calculated.
  • The pieces, (K/V head, block), are spread over the six threads, so a layer’s 2 or 3 K/V heads do not leave threads idle.

That order is the double buffer. While block n is computed from one slot, block n + 1 is copied into the other. The thread starts the next copy before it starts the current block, so the wait is only what the copy sticks out past the compute. The measured wait for the busiest thread at depth 2048 on Qwen was 494 µs with f32 K and V, and 254 µs with f16 (see What does an f16 cache change?) measured.

Takeaway: copy each block once into VTCM and overlap the next copy with the compute on this block.

Attention at depth 2048 uses blocks of 256 positions. How many blocks does one K/V head have?

  • 8, since 2048 divided by 256 is 8
    The block size divides the depth exactly at 2048.
  • 256, the block size itself
    The block size is the positions in one block, not the number of blocks.
  • 2, one per slot
    The slots hold one block each at a time; the cache has more blocks than slots.

Why compute four score vectors at once?

A score vector here is 32 scores, one per position, computed on the DSP’s 128-byte vector unit (HVX). Each step multiplies a key vector by a query value and adds the product to an accumulator, the register that holds a running total. Each add waits for the add before it in the same chain.

If four score vectors are computed together, each with its own running total, what changes?

  • Four chains of adds run side by side, so each waits less on the previous add
    Each chain still waits for its own add, but the other chains fill that time.
  • The scores change, since the adds happen in a new order
    Each score keeps the same add order, so the bits stay the same.
  • The exp is skipped for three of the four vectors
    Every score still goes through the exp; the change is in how many adds run at once.

The loop now computes four 32-position score vectors together. Each vector still adds its even and odd elements apart, then together, so every score has the same bits as before. Here is the inner loop in block_head (dsp/model.c), with one of the four key chunks shown:

HVX_Vector qe = splat_f(qh[e]), qo = splat_f(qh[e + 1]);
e0 = VADD(e0, VMUL(qe, ae0));
o0 = VADD(o0, VMUL(qo, be0));
e1 = VADD(e1, VMUL(qe, ao0));
  • A splat copies one value into every lane of a vector. Here qe is one query value, used by four loads.
  • Eight add chains (e0 to e3, o0 to o3) run side by side. Before, there were two.
  • The value sum uses the same idea: four accumulators, and one head’s four pairs are kept in named vectors, so they stay in registers, the fast slots the processor computes with.

At depth 2048 on Qwen, the busiest thread’s score time fell from 1338 to 764 µs, and SmolLM2’s from 957 to 547 µs measured. On SmolLM2 the DMA wait rose from 1302 to 1589 µs, because the shorter score no longer covered the copy. Value time for the busiest thread fell from 1776 to 837 µs on Qwen and from 1613 to 599 µs on SmolLM2 measured.

Few-token passes share the copies too. Prompt lookup checks several draft tokens in one call. Before, each token copied every block again. Now the tokens that reach a block share one copy. At depth 2048, eight tokens of attention cost 6.2 times one token on Qwen, where before the share it was 8.0 times measured.

Takeaway: independent chains hide each other’s waits, and the sharing cuts the copies.

Each score keeps the same add order after the change. What happened to perplexity?

  • It stayed at the same digits, because the scores have the same bits
    Same scores give the same softmax and the same output.
  • It dropped a little, because the new schedule rounds differently
    Rounding changes only when the add order changes; here it did not.
  • It improved, because four scores are computed more precisely
    Precision is set by the number format, which did not change.

Why add a vector to a power-of-two stride?

The keys are stored transposed: row e holds element e of the key for every position. The stride is how far apart those rows sit. Here is the rule in dsp/model.c:

M.att_stride = (M.seq_len + 63) / 64 * 64;
if (M.att_stride && (M.att_stride & (M.att_stride - 1)) == 0)
    M.att_stride += 64;
  • Round the context up to whole f16 vectors, 64 halves each.
  • If that is a power of two, add one more vector.
  • At context 4096, the pad removed 912 µs of Qwen’s depth-512 attention and 284 µs of SmolLM2’s, with f32 keys measured.

The results call the cost “set conflicts”, and say they were about a quarter of Qwen’s depth-512 attention before the pad. The pad was measured with f32 keys. The f16 cache keeps the rule, and the results do not rerun the pad with f16.

Takeaway: a power-of-two stride cost set conflicts in the measured runs; one extra vector removed them.

The context is 512 positions, with f16 keys. How many halves does one key row take?

  • 576, because 512 is a power of two, so one vector of 64 is added
    The rule adds one f16 vector to a power-of-two stride.
  • 512, with no pad
    Forgets the rule: a power-of-two stride gets the extra vector.
  • 544, the f32 pad of 32 elements
    The f32 cache padded by 32 floats; the f16 cache pads by a whole vector of 64 halves.

What does an f16 cache change?

Each number in the cache is an IEEE f16: a 16-bit float, half the size of the f32 float the arithmetic uses. The store converts f32 to f16 when a key or value is written. The loads convert back to f32, so the arithmetic is unchanged. At depth 2048 one K/V head’s keys and values take 1 MB in f32, and 512 KB in f16 calculated.

The cache now holds half as many bytes per value. How much less attention time does that buy at depth 2048?

  • Less DMA waiting, since each block is half the bytes; attention gains less than half
    The copies move half the bytes, but the converts and the merge add time back.
  • Exactly half, because attention time follows the bytes
    The convert and merge do not shrink with the bytes, so the gain is smaller.
  • None, because the DSP computes in f32 either way
    The bytes still halve in DRAM and VTCM, and the waiting follows the bytes.

The store costs more, and the wait costs less. On SmolLM2 the DMA wait for the busiest thread fell from 1589 to 265 µs at depth 2048, while its score rose from 547 to 677 µs for the convert measured. Attention went from 3151 to 2031 µs on SmolLM2 and from 2435 to 2234 µs on Qwen. Qwen’s DMA wait halved, from 494 to 254 µs, and its busiest thread’s merge rose from 153 to 547 µs. Perplexity did not move by more than 0.1 against llama.cpp’s f16 cache measured.

  • The bias, RoPE and cache store cost more on SmolLM2: 283 µs, against 160 before the change.
  • There is no f32 switch. The results say a branch in the inner loop is not cheap.

Takeaway: f16 halves the bytes and cuts the copy wait, but the convert gives back part of the gain.

On Qwen at depth 2048, the f16 cache cut attention from 2435 to 2234 µs. Why is that less than the byte count suggests?

  • On Qwen the bytes were the smaller share of the stage, so cutting them moved less
    Qwen’s DMA wait was already a smaller bucket than the score and merge work.
  • f16 does not change the bytes read from DRAM
    It does halve them; the limit is the other work in the stage.
  • The convert doubles the bytes again
    The convert changes the number format on load and store, not the byte count in memory.

What did each change buy at depth 2048?

The table is a chain: each row is the next change, and its sessions differ in clock speed and temperature. Read the order of the gains, not the exact ratios. The start is the wide value loop, measured in the same profile as the prefetch.

Five changes follow the wide value loop. Which one cut the most Qwen attention at depth 2048?

  • The l2fetch of the next blocks, from 17680 down to 7774 µs
    It removed about 9.9 ms, more than any later change.
  • Streaming through VTCM, the biggest design change
    It cut 3766 µs, less than the l2fetch step before it.
  • The f16 cache, since it halves the bytes
    It cut 201 µs on Qwen; the bytes were the smaller share there.

The biggest single cut was the l2fetch. At depth 2048 it removed 9.91 ms on Qwen, about half of that stage. The results say that half was DRAM latency: the bytes were already in the loop, waiting. Streaming then removed the repeated reads of each K/V head. At the final build, attention at depth 0, 512 and 2048 was 236, 953 and 2234 µs on Qwen, and 227, 937 and 2031 µs on SmolLM2 measured. Depth 0 still uses the prefetch path, because a context under 256 positions does not stream.

The f16 cache cut more on SmolLM2 (3151 to 2031 µs) than on Qwen (2435 to 2234 µs). The results call SmolLM2 the copy-bound model; on Qwen the bytes were still the smaller share at depth 2048.

Takeaway: the l2fetch gave the largest cut; each later change moved a smaller share.

In the last row, Qwen’s DSP step fell from 8.79 to 8.60 ms. What was the main reason?

  • Attention, which fell from 2435 to 2234 µs in the same row
    Attention fell 201 µs and the step 190 µs, so attention carried the change.
  • The weight products, which the f16 cache does not touch
    The products are a separate stage; the row’s change is in attention.
  • The clock, which rose during that run
    At depth 2048 the products matched the score run (gate/up 2100 against 2116 µs).

What you should take away

Attention reads every cached key and value, so its bytes per token grow with depth. The DSP copies the cache through VTCM in 256-position blocks, reads each block once for its whole query group, and overlaps each copy with the compute on the block before.

At depth 2048 on the phone, the changes took Qwen’s attention from 17680 to 2234 µs per token. The l2fetch gave the largest share, and f16 halved the bytes but gave back part of the gain.

Numbers on this page were measured on the iQOO 13 (SM8750) for L.5 (results/phase-l5.md) unless tagged otherwise. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
