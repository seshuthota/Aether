Q4_K_M files

Q4_K_M is the llama.cpp file most people download. It is not one format but a mix: K-quant blocks of 256 weights where a row allows them, and simpler 32-weight blocks where it does not. The engine reads all of them, matches llama.cpp’s accuracy, and on this phone runs them faster.

What are we trying to do here?

Phase 6 built two formats: Q8_0 (8-bit values, one f16 scale per 32 weights, 34 bytes per block) and Q4_0 (4-bit values, 18 bytes per block). Both store one scale per block of 32 weights. llama.cpp has a family of better formats, the K-quants, and its tool llama-quantize mixes them into presets. Q4_K_M (“4-bit K-quant, medium”) is the one most model pages offer first.

This page reads two such files, made with llama-quantize for SmolLM2-135M and Qwen2.5-0.5B. It covers the three new block formats (Q5_0, Q4_K, Q6_K), what they cost and buy in accuracy, and two speed fixes. The code is in src/quant.rs; every number is in results/phase-6.md, section “Q4_K_M files”.

What is actually inside a Q4_K_M file?

A K-quant packs 256 weights into one super-block. A block may not cross the end of a row, so a matrix can use a K-quant only if its rows are a multiple of 256 long.

SmolLM2’s rows are 576 long for most matrices, and 1536 for the MLP’s down projection (ffn_down). Which can be stored as K-quants?

  • Only ffn_down
    1536 = 6 × 256; 576 is 2.25 × 256, so those rows cannot be split into super-blocks.
  • All of them
    576 is not a multiple of 256; a super-block would cross the end of a row.
  • None of them
    1536 divides evenly by 256, so ffn_down qualifies.

When a row does not fit, llama.cpp falls back to a 32-weight format: Q5_0 in place of Q4_K, and Q8_0 in place of Q6_K. The two files contain:

FormatSmolLM2-135MQwen2.5-0.5B
Q5_0q, k, o, gate, up, half of vq, k, o, gate, up, half of v
Q4_K / Q6_Kffn_down: 16 / 14 layersffn_down: 12 / 12 layers
Q8_0the other half of v, token embeddingthe other half of v, token embedding

Qwen2.5-0.5B’s rows are 896 long (3.5 × 256) except ffn_down’s 4864 (19 × 256), so it has the same pattern. “M” means some layers get the bigger Q6_K, here about half of ffn_down.

Takeaway: on small models, Q4_K_M is mostly Q5_0, with K-quants only where rows are a multiple of 256.

A larger model has rows of 2048 everywhere. What would its Q4_K_M file mostly contain?

  • Q4_K and Q6_K
    2048 = 8 × 256, so every matrix can use the K-quants; no fallback is needed.
  • Q5_0, as in SmolLM2
    Q5_0 is only the fallback for rows that do not fit 256.
  • Q4_0
    Q4_0 is not part of the Q4_K_M mix at all.

How do you store 5 bits per weight?

Bytes hold 8 bits, and 5 does not divide 8. Packing 5-bit values end to end would split many of them across two bytes, and the kernel would spend its time cutting them out.

How could a block of 32 five-bit values be laid out so that unpacking stays cheap?

  • The low 4 bits as in Q4_0, and the 32 fifth bits together in one 32-bit word
    The nibbles reuse Q4_0’s unpacking; the fifth bits are one word, one bit per weight.
  • Each value in its own byte, with 3 bits unused
    That works but costs 8 bits per weight, the size of Q8_0, for 5 bits of precision.
  • Values packed end to end, 160 bits in a row
    Compact, but most values straddle two bytes, which makes unpacking slow.
pub struct BlockQ5_0 {
    pub d: u16,        // f16 scale
    pub qh: [u8; 4],   // bit j: fifth bit of value j
    pub qs: [u8; 16],  // low 4 bits, as in Q4_0
}                      // 22 bytes per 32 weights
  • A value is q = low nibble + 16 × fifth bit, from 0 to 31, and the weight is d × (q − 16).
  • 22 bytes for 32 weights is 5.5 bits per weight, counting the scale calculated.
  • The engine’s quantizer gives llama.cpp’s bytes exactly in 12 test cases, so -q q5_0 can make Q5_0 weights from any model too.

Takeaway: Q5_0 keeps Q4_0’s nibbles and adds the fifth bits as one 32-bit word, for 5.5 bits per weight.

A Q5_0 weight has low nibble 3, fifth bit 1, and scale d = 0.01. What is the weight?

  • 0.03
    q = 3 + 16 = 19, and 0.01 × (19 − 16) = 0.03.
  • 0.19
    That forgets the offset of 16, which makes the values signed.
  • −0.13
    That ignores the fifth bit: 0.01 × (3 − 16).

Why does a K-quant have scales of scales?

A Q4_0 block spends 16 bits on its scale for 32 weights: half a bit per weight, just for the scale. A smaller scale costs fewer bits, but an f16 is the smallest float the format has. The K-quant answer is to store the small scales as integers, and give the integers a float scale of their own.

pub struct BlockQ4_K {
    pub d: u16,           // f16: scale of the scales
    pub dmin: u16,        // f16: scale of the mins
    pub scales: [u8; 12], // 8 scales + 8 mins, 6 bits
    pub qs: [u8; 128],    // 256 values, 4 bits each
}                         // 144 bytes per 256 weights
  • The 256 weights are 8 sub-blocks of 32. Sub-block j has a 6-bit scale sc and a 6-bit m, packed into the 12 bytes.
  • A weight is d·sc·q − dmin·m, with q from 0 to 15. The min term lets a sub-block cover a range that does not sit around zero, which Q4_0’s d·(q − 8) cannot.
  • 144 bytes per 256 is 4.5 bits per weight, the same as Q4_0 calculated, but with a scale and a min per 32 weights for the price of Q4_0’s scale alone.

Q4_K and Q4_0 both use 4.5 bits per weight. Where does Q4_K find the bits for a min per sub-block?

  • Its per-32 scale and min are 6 bits each, not 16
    12 bits per sub-block, plus 32 bits of f16 per 256, replaces Q4_0’s 16 bits per 32.
  • It uses fewer bits for each weight
    Both store 4 bits per weight; the saving is in the scales.
  • It does not; its mins are shared by the whole super-block
    Each of the 8 sub-blocks has its own min; only dmin is shared.

Q6_K works the same way with more bits: 16 sub-blocks of 16 weights, each with an 8-bit signed scale, values of 6 bits (q − 32), and one f16 per 256. That is 210 bytes per 256, or 6.56 bits per weight calculated.

The gguf Python package can decode Q4_K and Q6_K but not encode them, so the tests use random block bytes: every bit of the layout is exercised, and the engine’s decoder gives exactly the package’s values.

Takeaway: K-quants store each sub-block’s scale as a small integer under one float per 256, which pays for a min per sub-block.

A sub-block’s weights all lie between 0.2 and 0.5. Why does Q4_K store it better than Q4_0?

  • Its min shifts the 16 levels onto 0.2–0.5; Q4_0’s levels are centred on zero
    Q4_0 must reach 0.5 from zero, so half its levels cover negative values nobody uses.
  • It has more levels per weight
    Both have 16 levels; Q4_K places them better.
  • It does not; the two are equal at 4.5 bits
    Same size, but the min lets Q4_K fit ranges away from zero.

What do the extra bits buy?

The test is the one from Phase 6: perplexity on wikitext-2 (20 chunks of 512 tokens), and KL divergence against each engine’s own f32 model. Our numbers were run on the phone, llama.cpp’s on the PC.

Our Q4_K_M KLD is about two of llama.cpp’s standard errors lower, while pure Q5_0 agrees to 0.2 %. What most likely explains it?

  • The two engines round the activations differently for K-quants
    Ours uses one scale per 32 activations everywhere; llama.cpp uses one per 256 for K-quants.
  • Our weights are decoded differently
    The decoders give the gguf package’s values exactly, so the weights are the same.
  • Chance
    Two standard errors in both models, in the same direction, points at a cause.

Before a dot product, both engines quantize the activation vector to 8 bits. Ours uses Q8_0 (one scale per 32 values) for every format. llama.cpp uses Q8_K for K-quants (one scale per 256), which rounds a little more coarsely. With Q5_0, both use Q8_0, and the two engines agree to 0.2 %.

What the format buys, for Qwen2.5-0.5B: Q4_K_M raises perplexity by 2.7 % over f32 (KLD 0.03); Q4_0 raises it by 21 % (KLD 0.18). The file is 380 MB against 265 MB, 1.4 times larger measured.

Takeaway: Q4_K_M matches llama.cpp, and for 1.4 times the file it cuts Qwen2.5-0.5B’s quantization loss from 21 % to 2.7 %.

Why was it slow at first, and what fixed it?

Decode reads every weight once per token, so a file 1.4 times larger should decode about 1.4 times slower. The first measurement was worse than that, in both engines: Qwen2.5-0.5B Q4_K_M decoded at 75.2 tok/s in ours and 85.0 in llama.cpp, against 153.4 for Q4_0 measured.

A profile shows decode spending 39 % of its time in the Q5_0 kernel. What is the likely cost?

  • Turning each block’s fifth bits into bytes, row by row
    Spreading 32 bits into 32 lanes took a table lookup and a bit test per block.
  • Reading the extra bytes from memory
    Q5_0 is only 22 % larger than Q4_0; that cannot explain half the speed.
  • Converting the f16 scales
    One scale per 32 weights is cheap; the per-weight bit work dominates.

Two fixes followed:

  • Q5_0 repacked four rows at a time. At load, the nibbles are laid out as for Q4_0’s four-row blocks, and the fifth bits are stored inverted and arranged so each byte feeds one vector the kernel builds. An inverted fifth bit is the sign bit of q − 16, so (nibble << 3) | (bit << 7), read as a signed byte, is exactly 8 × (q − 16): a shift, a mask and one bit-select per 16 weights. The factor 8 is divided out exactly when the integer sum becomes a float, so the results are bit-identical.
  • smmla for Q4_K and Q6_K in prefill. Each group of four rows is unpacked once per matrix product into 8-bit values with per-row scales, and every token of the prompt reuses it, instead of each token unpacking it again.

With the repack, decode is 13 % faster than llama.cpp’s on this phone, and with smmla prefill is about twice llama.cpp’s. The smmla row comes from a cycle-count run, because the timed A/B was spoiled by a clock change mid-run; its perplexity changed only in the summation order (16.7354 against 16.7088).

Takeaway: Q4_K_M was slow because of per-weight bit work, not bytes; repacking at load and reusing unpacked rows made it faster than llama.cpp’s here.

Why does unpacking a group of rows once per matrix product help prefill but not decode?

  • Prefill has many tokens to share one unpack; decode has one
    With one token, unpacking once or per token is the same work.
  • Decode does not use K-quants
    Decode reads the same ffn_down weights; it just has only one token to reuse them.
  • Decode is already at the memory limit
    It was not: Q4_K_M decode was limited by bit work, which the repack addressed.

What you should take away

Q4_K_M is a mix: K-quants where rows are a multiple of 256, Q5_0 and Q8_0 elsewhere; on small models it is mostly Q5_0.

K-quants spend their scale bits as small integers under one float per 256, which pays for a min per sub-block.

For 1.4 times the file, Qwen2.5-0.5B loses 2.7 % instead of 21 %, and after two kernel fixes it runs faster than llama.cpp’s on this phone.

Numbers were measured on the iQOO 13 (SM8750) in October 2026 unless tagged otherwise; llama.cpp’s perplexities were run on the PC. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
