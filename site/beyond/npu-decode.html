The NPU · 02

Why does decode run as one call per token?

The engine's DSP runs a whole token of Qwen2.5-0.5B in one call from the CPU: 6.75 ms, or 123 tokens per second, against 74 for llama.cpp's NPU backend. A call has a fixed cost, and a token has many matrix products. This page shows why the whole token goes in one call, and how the DSP's six threads and its DMA engine make that token fast.

What are we trying to do here?

A token is one pass of the model: every layer runs, then a last matrix (the classifier) scores all 151,936 words of the vocabulary and the best one is the next word. The pass is called decode. Each layer is built from matrix products: a weight matrix multiplied by a vector. Qwen2.5-0.5B has 24 layers with four matrix products each, plus the classifier.

The DSP is the phone's Hexagon compute core. The CPU reaches it through FastRPC: one call hands the DSP a method number and some buffers, the DSP runs the method, and the call returns. VTCM is the DSP's own 8 MB of fast on-chip memory. DMA is a copy engine that moves bytes from DRAM into VTCM while the vector units do other work.

By the end you can explain why a token is one call, and why the numbers below came out as they did.

What does a call cost, next to a token?

Setup: the CPU runs a Qwen token in about 5.2 ms measured. A call with no work in it costs about 146 µs measured (median of 2,000), once the CPU has asked the DSP for its highest clocks. Without that request the same empty call took 393 µs.

One design makes a call for each matrix product: about 170 calls per token in the first DSP measurement. Each call costs about 146 µs. What do the calls add up to per token, before any arithmetic?

  • About 25 ms, more than the whole token
    170 times 146 µs is about 24.8 ms, several times the 5.2 ms CPU token.
  • About 1 ms, since a call is cheap
    146 µs is the cost of a call that does nothing, and 170 of them add up.
  • About 6.75 ms, the same as the token
    That assumes the calls cost nothing beyond the arithmetic, which they do not.

So a DSP called once per matrix product would spend more time on calls than on the arithmetic. The 170 counts every matrix on its own: Qwen2.5-0.5B has 24 layers of seven matrices (q, k, v, o, gate, up, down), plus the classifier, which is 169 calculated. The figure shows the two designs. The call sliver and the token bar are drawn to scale from the measured numbers. The work between the calls is left out.

Two things follow. A call's cost is paid once per call, whatever the call does. And the one-call design pays it once per token, about 2 % of the 6.75 ms calculated.

Takeaway: a call costs about 146 µs whatever it does, so calls must be few and large.

The one-call design spends one 146 µs call on each 6.75 ms token. What share of the token is that call?

  • About 2 %
    146 µs is 0.146 ms, and 0.146 divided by 6.75 is about 0.022.
  • About 20 %
    That reads 146 µs as 1.46 ms, a unit slip that is ten times too big.
  • About a quarter
    A call is far smaller than the work it starts, so it cannot be a quarter.

Why put the whole token in one call?

The first DSP products were one call each. A matrix product was then the unit of work, and the call cost was paid for each. The fix was to move the whole token onto the DSP. The norms, RoPE, attention, SwiGLU, the classifier and the argmax all run there, so one call covers the token.

The model's weights are copied to the DSP once, when the model loads, into one shared buffer. A second shared buffer holds the state: activations, the KV cache and the logits. Per token, the CPU writes only the token's embedding and the RoPE table. The call's doc comment in src/kernels/hexagon.rs says what comes back:

/// One decode step of the loaded model at `pos` on `threads` DSP
/// threads: the greedy next token and the DSP's time in microseconds.
  • Shared, not copied. The buffers are mapped into the DSP once, so a call passes a descriptor, not the bytes.
  • The argmax runs on the DSP. Greedy decoding needs only the best word's number, so the CPU does not read the 151,936 logits.
  • Some time stays on the CPU. At the step the results measured, the wall time was 12.3 ms against the DSP's 10.5 ms measured. The 1.8 ms is the call, the embedding and RoPE writes, and the test tool's logits check.

The weights are already on the DSP when a token starts. What does the CPU still send per token?

  • The token's embedding row and the RoPE table for its position
    Those depend on the token and its position, so they change every step.
  • Every weight matrix again
    The weights were copied once, at load time, into the shared buffer.
  • The whole KV cache
    The cache lives in the state buffer, and the DSP writes it.

Takeaway: one call per token means the CPU sends little per token, and the DSP does the rest.

The call returns the greedy next word, not the 151,936 logits. What does the CPU lose by that?

  • Nothing for greedy decoding, since the next word is all it needs
    Greedy decoding picks the largest logit, and the DSP already found it.
  • The logits, so perplexity cannot be measured
    The perplexity run uses a different call that returns every logit.
  • The KV cache, which is sent back in the reply
    The cache stays in the DSP's state buffer and is not part of the reply.

How do six threads share one token?

The DSP has six HVX contexts, the units that run its 128-byte vector instructions (qurt_hvx_get_units). The token's work is split across six threads, one per context. Each thread takes a run of row groups of every product. Where a stage needs every thread's result, the threads wait at a barrier. A barrier is a point where each thread stops until all have arrived.

The DSP has six vector contexts. If the step used eight threads, would the token be faster or slower than with six?

  • Slower, because two threads have to share a context
    Measured: eight threads read DRAM slower than six, 39.2 against 45.9 GB/s.
  • Faster, since more threads hide more waiting
    The bandwidth test showed more threads than contexts reading slower, not faster.
  • The same, since waiting threads queue up anyway
    Queued threads still share the same units and memory bus.

Four threads give 7.12 ms per token, six give 6.79 ms. Which is the better choice, and why?

  • Six, because it is faster and matches the six contexts
    The table shows the lower time at six, and six is the number of units.
  • Four, because fewer threads means less contention
    Contention rises with threads, but the measured total still falls at six.
  • Either, since the difference is noise
    The same table gives 7.12 ms at four threads and 6.79 ms at six.

How do the weights reach the threads in time?

A token reads about 306 MB of Qwen's matrices. From DRAM, the DSP's read speed is 46 to 47 GB/s at best, so the reads cannot be hidden by the arithmetic alone. Before DMA, each thread prefetched its next rows into the L2 cache with l2fetch. That reached about 36 GB/s across the token.

Each thread has two VTCM slots, and only one is computed on at a time. Why does a thread need two?

  • The engine fills one slot while the vector units compute on the other
    Copy and compute overlap, so the copy's time is hidden behind the arithmetic.
  • One holds the weights and one holds a backup
    Nothing is checked against a backup; each slot holds a different pair of row groups.
  • One for each matrix type, so the two can differ
    The slots are reused for every matrix; the split is in time, not in matrix type.

The DMA engine copies a thread's next pair of row groups (2 × 32 rows, with all their blocks) from DRAM into one slot. The copy bypasses the L2. Each DSP hardware thread has its own queue. Each copy is described by a 16-byte descriptor, kept in a ring:

  • Start and link. dmstart begins a chain and dmlink appends to its tail; the thread polls each descriptor's done bit (dsp/aether_dsp.c).
  • A ring of 64. Each thread keeps 64 descriptors, so none is rewritten while the engine may still read it.
  • A fixed share. Each thread has VTCM/8. Before this, slots were placed by format, and a Q8_0 run could overwrite a neighbour still on Q5_0: perplexity 47530 on the phone, against 16.30 without DMA (commit c68da0a).

  • What broke first. VTCM is requested with HAP_compute_res_acquire. When all six threads asked at once, one got it and five waited inside the call, which never returned. The request is now made once, by the thread the call arrived on, before the workers start.

Takeaway: DMA copies the next weights into VTCM while the vector units work, and it wins on the big matrices.

DMA makes wo slower (18 to 24 µs), yet the token gets faster. What explains that?

  • wo is a small share of the token, and the big matrices save far more
    Gate/up saves 80 µs and the classifier 762 µs; wo's loss is 6 µs.
  • DMA is faster on every matrix in the decode step
    The table shows wo, the one matrix where DMA is slower.
  • DMA reads the weights in a smaller format
    Both paths read the same Q4_0 bytes; only the way they arrive changes.

What did one call per token buy?

The table sets the DSP's decode against the other engines on Qwen2.5-0.5B, Q4_0 measured. The GPU row is an approximation from the same comparison.

llama.cpp's NPU backend takes 13.5 ms per token on this model. Our DSP decode takes 6.75 ms. What is the ratio?

  • About 2 times faster
    13.5 divided by 6.75 is 2, so the DSP token takes half as long.
  • About the same speed
    Two tokens at 6.75 ms and 13.5 ms differ by a factor of two, not a few percent.
  • About 1.3 times faster
    13.5 over 10 is 1.35, the GPU's figure, not the NPU's.

The DSP's output matches llama.cpp's perplexity on wikitext-2, the usual check that a model's numbers are right. Ours gives 19.7584 for the decode step, against llama.cpp's 19.7283 ± 0.84 measured. The DMA change moved only how the bytes arrive, so perplexity did not change at all. What perplexity measures is on its own page.

Takeaway: one call per token runs twice as fast as llama.cpp's NPU backend here, with matching perplexity.

The DMA change left the perplexity unchanged to the last digit. Why would a faster way of loading bytes not change it?

  • It changes only when the bytes arrive, not the arithmetic on them
    The same numbers are multiplied in the same order, so the result is identical.
  • It switches to fp16 weights, which round the same way
    The weights stayed Q4_0; the format did not change.
  • It skips the classifier, which dominates perplexity
    The classifier still runs every token; DMA only changes how its weights arrive.

What you should take away

A call costs about 146 µs whatever it does, and a token has many matrix products. So the whole token goes in one call.

Six threads share the token with nine barriers per layer, and DMA fills VTCM while the vector units compute. Together they give 6.75 ms a token, 123 tokens per second.

Numbers on this page were measured on the iQOO 13 (SM8750) in October 2026 (results/phase-l5.md, steps 1, 2, 4 and 4b, and "Every engine, one benchmark") unless tagged otherwise. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
