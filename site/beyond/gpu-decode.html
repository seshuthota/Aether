Decoding on the GPU

The whole decode step of Qwen2.5-0.5B runs on the GPU and gives llama.cpp’s perplexity. It is slower than the CPU, about 100 against 158 tokens per second, but it uses about half the power and less energy per token. This page shows how the step is built, what made it faster, and why its speed jumps around.

What are we trying to do here?

The previous page built a matrix-vector shader. A decode step also needs RMSNorm, the q/k/v biases, RoPE, the KV cache, attention, SwiGLU and the residual adds. GpuModel in src/model/gpu.rs runs all of them as shaders, so the only work left on the CPU per token is writing the embedding row and reading the logits.

The GPU reads memory no faster than the CPU, so speed was never the point. The questions are whether it is correct, what it costs in energy, and what limits it. By the end you can explain each of those with this phone’s numbers. Try it with aether MODEL.gguf --gpu or the app’s GPU checkbox.

What does one decode step look like on the GPU?

Per layer, the step runs these stages, each one dispatch followed by a barrier:

rmsnorm      -> xb
q/k/v        -> q, k, v        (matrix products)
bias + RoPE  -> q; k, v into the KV cache
attention    -> partial results per chunk
merge        -> xb2
wo           -> x += ...       (residual add)
rmsnorm      -> xb
gate/up      -> hb, hb2
swiglu, down -> x += ...

After the 24 layers come a last RMSNorm and the classifier, the big matrix that produces the 151,936 logits.

The GPU keeps activations in f32; the CPU path rounds them to int8 before each product. How can we tell the GPU step is correct?

  • Compare its perplexity on wikitext-2 with llama.cpp’s for the same file
    Perplexity is an external reference that tolerates tiny rounding differences but catches a broken stage.
  • Require the same greedy text as the CPU path
    The rounding differs, so the texts legitimately fork where two tokens are nearly tied.
  • Require bit-identical logits with the CPU path
    Different rounding means different last digits; that would fail on a correct step.

examples/vk_ppl.rs scores wikitext-2 with every token through the GPU step, by llama-perplexity’s procedure measured:

Takeaway: the GPU step’s perplexity matches llama.cpp’s; its greedy text may fork from the CPU’s because it rounds differently.

RoPE needs a sine and cosine per pair, which depend on the position. Who computes them?

  • The CPU, exactly as the CPU path does, written into the params buffer each token
    The recorded step is reused for every position, so per-token values come from memory.
  • The GPU, with its own sin and cos
    That would give slightly different angles from the CPU path; the CPU writes the table.
  • They are recorded into the commands
    The commands are recorded once, before any position is known.

Why was attention slow at long contexts?

The first attention shader ran one workgroup per query head. Qwen2.5-0.5B has 14 heads, so attention was 14 workgroups, each walking through every cached position.

At depth 1024, how did attention’s share of the GPU step change compared with depth 0 (0.51 ms)?

  • It grew to 5.59 ms, almost half the step
    14 workgroups cannot fill a GPU built for hundreds, and each walked 1024 positions alone.
  • It stayed about the same
    Attention’s work grows with the number of cached positions.
  • It grew to about 1 ms
    It grew far more, because so few workgroups did all of it.

The fix is the CPU’s flash-decoding, done on the GPU: split the positions into chunks of 64. Workgroup (head, chunk) scores its 64 positions and writes three things: the chunk’s largest score m, the sum l of escore − m, and its weighted sum of values. A second shader merges the chunks of each head:

M   = max over chunks of m_c
out = sum_c e^(m_c - M) * out_c
    / sum_c e^(m_c - M) * l_c

Rescaling by em_c − M makes every chunk’s numbers relative to the same maximum, so the result is the same softmax as one pass over all positions. At depth 1024 attention went from 5.59 to 1.95 ms measured, and the perplexities did not change.

Takeaway: attention needs work split across positions as well as heads, or a few workgroups do it all.

The dispatch is recorded once, for every chunk the cache can hold. What do chunks past the current position do?

  • They return at once
    Their first position is beyond the current one, so they have nothing to score.
  • They score zeros and slow the merge down
    The merge only reads chunks up to the current position.
  • The dispatch is re-recorded every 64 tokens
    It is recorded once; empty chunks cost almost nothing.

Why does the same step take 7 ms in one run and 11 in the next?

Run to run, the same GPU decode measured anywhere from 50 to 105 tokens per second measured. A governor sets the GPU’s clock speed from its recent load, as the CPU’s does (power and heat), and so does the memory bus’s.

The classifier GEMV takes 1.23 ms when run back to back. What happens if the GPU sits idle for 20 ms before each run?

  • It takes about 3.3 ms, nearly 3× longer
    The governor lowered the clocks during the idle time, and they take a while to come back up.
  • It takes 1.23 ms, the same
    The work is the same, but the clock it runs at is not.
  • It is faster: the GPU is cool
    Temperature matters over minutes; this effect is about the last few milliseconds of load.

After 1, 5 and 20 ms of idle time, the classifier took 1.66, 2.70 and 3.34 ms measured. Decode is bursty: one token’s dispatches, then the CPU’s turn to sample. Vulkan has no way to ask for clocks, and the controls in /sys/class/kgsl/ need root.

So GPU comparisons on this phone need the same care as CPU ones: alternate the two versions, repeat, and compare per-stage GPU timestamps rather than one wall-clock number. A cool phone on battery and a warm phone on the charger gave different answers to the same question.

Takeaway: the GPU’s clocks follow its recent load, so its speed swings by 2× and comparisons must alternate.

If the GPU is slower, why use it?

Energy per token is power divided by tokens per second (power and heat). Both sides decoded Qwen2.5-0.5B Q4_0 for 120 seconds, in 64-token bursts, on battery, each starting below 42 °C.

The CPU decoded at 157.6 tok/s and the GPU at 102.7. Which used less energy per token?

  • The GPU, by about a quarter
    It drew about half the power, which more than makes up for being a third slower.
  • The CPU, because it finishes sooner
    Finishing sooner helps only if the power is similar; the CPU drew about twice as much.
  • They used the same
    Power differed by about 2×, speed by about 1.5×.

The GPU path uses about half the power and stays about 20 °C cooler. That is a real choice on a phone: the CPU when speed matters, the GPU for long generations or to leave the CPU free for the app. Polling the fence (the CPU spinning until the GPU is done) made the GPU path slower as well as costlier, probably because the spinning core competes for the shared power budget, so the engine sleeps on the fence.

Takeaway: the GPU is slower but spends less energy per token and runs much cooler.

Why might polling the fence make the GPU slower, not faster?

  • The busy CPU core draws power from the same budget the GPU’s clocks depend on
    The SoC shares power and heat limits between its parts.
  • Polling delays the GPU’s start
    The GPU starts when the work is submitted; polling only changes how the CPU waits.
  • The fence is slower to read than to wait on
    Reading it is cheap; the cost is a core kept busy for the whole wait.

Where does a GPU token’s time go?

Streaming 278 MB of weights at the GPU’s 66 GB/s would take about 4.2 ms per token calculated, yet a token took about 9–11 ms. Two tools separated the causes. vk_decode split timed the CPU’s part after each step: copying the 151,936 logits out of GPU memory and finding the largest took 0.3–1.1 ms. vk_decode queued recorded 8 steps into one submit, so the GPU never waited for the CPU.

With 8 steps queued back to back, how long did each step take?

  • 7.6–8.6 ms, about the same as one step per submit
    The gaps between tokens were not the main cost; the work inside the step was.
  • About 4.2 ms, the bandwidth limit
    That would mean the CPU’s gaps caused all of the slowdown.
  • Much longer, because the GPU overheated
    Eight steps take under 0.1 s, far too short to heat the phone.

The per-stage GPU timestamps show where the step goes: the matrix products are about 75 % of it, and run at 30–40 GB/s there, while the other stages total about 1.1 ms measured. Each dispatch’s fixed cost (about 10 µs) adds up over ~290 dispatches per token.

Measured on the phone: stacking wq/wk/wv and gate/up cut q/k/v’s GPU time by 20 % and gate/up’s by 6 %, about 3–4 % of a token. Built and checked on the PC since, waiting for the phone’s timing not yet measured on the phone: the residual adds, the SwiGLU and the RMS norms are folded into the matrix products next to them, which brings a token from ~290 to ~169 dispatches with the same perplexity.

Takeaway: GPU decode is limited by its matrix products and the fixed cost per dispatch, not by the CPU between tokens.

Folding RMSNorm into the next matrix product means each of that product’s workgroups recomputes the norm. Why is that still a saving?

  • The norm reads 896 floats from cache, far cheaper than a dispatch with a barrier
    Repeating a tiny computation beats paying a fixed cost per dispatch.
  • The norm is not needed any more
    It is still applied, just inside the product as the input is loaded.
  • Each workgroup computes a different part of the norm
    Each computes the whole sum of squares; the repetition is the price.

What you should take away

The GPU runs the whole decode step with llama.cpp’s perplexity, at about two thirds of the CPU’s speed for about half its power.

Its time goes to matrix products and fixed per-dispatch costs, and its clocks swing with load, so measure it by alternating runs and GPU timestamps.

Numbers on this page were measured on the iQOO 13 (SM8750) on 2026-10-29 (results/phase-l3.md, steps 4 to 6) unless tagged otherwise. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
