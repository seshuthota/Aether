How does the NPU read a prompt?

A prompt is many tokens through the same weights at once, so it is a matrix times a matrix, not the matrix times a vector that decoding does. On the phone that product runs on the NPU’s matrix unit, HMX, which takes 16-bit float tiles. This page shows how our five quantized formats become those tiles, one Q4_K bug that rounded small weights to zero, the prompt speeds we measured, and the size limit of one call.

What are we trying to do here?

The NPU is the Hexagon DSP on this phone, a chip inside the Snapdragon that runs our own C code. It has a vector unit (HVX) and a matrix unit (HMX). HMX multiplies 32 × 32 blocks of numbers, called tiles. A tile is a fixed-size block of fp16 values, where fp16 is a 16-bit floating-point number. HMX reads its tiles only from VTCM, the DSP’s own on-chip scratch memory, which is much smaller than DRAM.

By the end of this page you can say why a prompt needs the matrix unit, what the weights and the activations look like when they reach it, and what limits one call.

Why is a prompt a matrix times a matrix?

Decoding makes one token at a time. Each weight matrix is multiplied by one vector, the token’s activation. That is a matrix-vector product, or GEMV. An activation is the vector of numbers that one token holds as it passes through a layer.

A 128-token prompt goes through one weight matrix. Compared with decoding those 128 tokens one at a time, how many times is each weight read from DRAM?

  • Once, for all 128 tokens together
    The tokens share the weights while they are in the same call.
  • 128 times, once for each token
    That is decoding. A prompt batches its tokens, so the weights are used again while loaded.
  • Never, because the cache holds the weights
    The KV cache holds keys and values, not weights.

A prompt batches its tokens. Each weight is loaded once and multiplied by every token in the batch. The work is arithmetic, not reading DRAM. The phase-l5 notes say it this way: every weight is used by all the prompt’s tokens, so the work is arithmetic.

Example, calculated: a group of 32 tokens against a block of 32 inputs is 32 × 32 products. Its 32 × 32 weights are loaded once and used 32 times. Decoding the same 32 tokens would load them 32 times.

The CPU path works the same way, as prefill: many tokens at once explains, and its kernel is in Inside the GEMM micro-kernel.

Takeaway: a prompt reuses each weight across its tokens, so its products are matrix times matrix.

A one-token prompt goes through the same products. How many times is each weight read?

  • Once, and used once, as in decoding
    With one token there is nothing to share a weight load with.
  • Fewer times, because one token needs less arithmetic
    Arithmetic falls, but each weight still has to be read.
  • Not at all, because the matrix unit skips it
    Every product still reads its weights.

What form does the matrix unit need its numbers in?

Our weights are not stored as fp16. They are GGUF blocks: small integers, with one scale per block. A scale is one number that multiplies a block’s integers. Dequantizing means turning the packed integers back into real values with that scale. HMX multiplies only fp16 tiles, so the weights must be dequantized into tiles first.

HMX multiplies only fp16 tiles in VTCM. Our weights are packed 4-bit and 8-bit blocks. Which step makes the tiles?

  • A dequantize step: unpack each integer, multiply by its scale, store fp16 in VTCM
    That turns each packed value into a number the matrix unit can multiply.
  • HMX reads the packed blocks and converts them itself
    HMX only multiplies fp16 tiles; the packed form has to be unpacked first.
  • The CPU converts the whole model to fp16 once at load time
    The results say the weights stay in our Q4_0 layout in DRAM.

The layout is a block of weights in DRAM, a tile in VTCM, and the matrix unit’s result:

weights in DRAM, packed (Q4_0, Q5_0, Q8_0, Q4_K, Q6_K)
        |  hmx_weight_tiles: unpack, scale, round to fp16
        v
one fp16 weight tile, 32 x 32, in VTCM
        |  HMX multiplies it with an activation tile
        v
one 32 x 32 result tile -> f32 rows for our code
  • A tile of 32 × 32 fp16 values is calculated 2048 bytes (32 × 32 × 2).
  • The matrix unit only runs when it is powered on. Our session asks for it in dsp/aether_dsp.c (HAP_power_set_HMX). The results say an unpowered unit never finishes.
  • The activations are converted to plain fp16 tiles; only the weights go through the unpacking.

Every format is unpacked by one function, hmx_weight_tiles. The header says why this works:

// dsp/hmx_tiles.h: Every format uses the same layout, so
// the matrix unit does not care which quantizer the
// weights came from.
formatwhat the unpacking doesscale
Q4_0nibble minus 8, times the block scalef16
Q5_0adds the fifth bit, minus 16, times the scalef16
Q8_0stored byte minus 128, times the scalef16

  • Q4_0 keeps its 32 rows of a group in the 32 lanes of one vector, which is the layout of a tile’s 32 outputs. No lane shuffling is needed.
  • Q4_K and Q6_K scale in f32 and round once. The next section shows why.

Takeaway: every format is unpacked into the same fp16 tile; only the unpacking differs.

Q6_K and Q4_0 fill the same kind of tile. What is different about the Q6_K unpacking?

  • Its byte is a signed code, q minus 32, scaled in f32
    The table above lists it; the tile layout is the same for both.
  • It skips the scale, because 6-bit codes need none
    Q6_K has a scale; it is applied in f32.
  • It writes a different tile shape into VTCM
    Every format writes the same tile layout.

What did an f16 multiply lose from Q4_K weights?

An f16 is a 16-bit float: 1 sign bit, 5 exponent bits and 10 fraction bits. Ten fraction bits keep about three decimal digits. Near 0.05, two neighbouring f16 values are about 3e-5 apart calculated. Subtract two large numbers that nearly cancel, and their small difference can fall below that spacing: it comes out as 0 or as one step.

Q4_0 turns each nibble into (nibble − 8) times one scale. Q4_K also subtracts an offset, dmin·min, for each block. Both are stored in the tile as fp16.

The bug hit Q4_K weights and not Q4_0’s. Where in the Q4_K unpacking can a value vanish?

  • The offset subtraction, where the scaled value and the offset nearly cancel
    A tiny difference of two large numbers is what an f16 multiply can round to zero.
  • The 6-bit code unpacking, which overflows f16
    The codes are small; the trouble is a value too small, not too large.
  • The activation tile, which is scaled by Q4_K’s scale
    Activations stay plain fp16 with no scale.

The code states the cause. Above pair_f32 in dsp/hmx_tiles.h:

// Doing the multiply in f32 matters for Q4_K: the scale
// and the offset are large and nearly cancel, and an f16
// multiply flushes the difference to zero.

The fix multiplies in f32 and subtracts the offset in f32. Only the finished value is rounded to f16:

lo = Q6_Vsf_vmpy_VsfVsf(lo, scale);
hi = Q6_Vsf_vmpy_VsfVsf(hi, scale);
if (has_offset) {
    lo = Q6_Vsf_vsub_VsfVsf(lo, offset);
    hi = Q6_Vsf_vsub_VsfVsf(hi, offset);
}
return to_f16_pairs(lo, hi);
  • The rounding happens once, in to_f16_pairs, at the end.
  • Before the fix, a small Q4_K weight came out as 0. Its reference is about 7.6e-5 measured.
  • The check is sim_hmx_weight_tiles_match_gguf: the tiles agree with gguf-py within a relative 2e-3. HMX itself does not run on the simulator.

A teammate proposes rounding the scale to f16 first, then multiplying in f16. What happens to the bug?

  • It comes back, because the difference is again flushed to zero
    The code comment says the f16 multiply is the cause, and rounding first keeps it.
  • It is fixed, because the scale is smaller than the weight
    Size of the scale is not the issue; the difference of two large numbers is.
  • It is fixed, because f16 is more precise than f32
    f16 has fewer digits than f32, not more.

How fast is a prompt on the matrix unit?

Prompt speed here is tokens per second through the whole model’s prefill, as dsp_ppl measures it on the phone.

Qwen’s Q4_0 prompt runs at 376 tok/s at 32 tokens and at 778 tok/s at 128. Why does it speed up?

  • The unpacking cost per matrix is nearly fixed, and more tokens share it
    Each batch pays the unpacking once; a bigger batch spreads that cost.
  • The matrix unit clocks higher during a long call
    Nothing in the results says the clock rises with the call length.
  • Longer prompts use a smaller model
    The model is the same at every length.

measured on the phone, 2026-10-30 (results/phase-l5.md, step 5b). At 128 tokens, 1608 is SmolLM2 and 778 is Qwen, both Q4_0.

  • Q4_K_M at 128 tokens: SmolLM2 1544 tok/s. Qwen 746 on a cooler run and 696 on a warmer one measured.
  • Before Q4_K_M had HMX prefill, its 8-token HVX path ran a 241-token prompt at 272 tok/s, against 755 for Q4_0 on HMX over the same 241 tokens, both for Qwen2.5-0.5B measured.
  • llama.cpp’s NPU backend prefilled Qwen at about 330 tok/s on this phone measured (results cite phase-l3 step 8).

Takeaway: a whole-model prompt runs at 1608 tok/s for SmolLM2 and 778 for Qwen (Q4_0, 128 tokens).

Per matrix, unpacking costs the same for any batch. Which batch gives the most tokens per unpack?

  • The largest batch that still fits the activation bank
    Each batch shares one unpack across its tokens, and the bank sets the largest batch.
  • The smallest batch, so the tiles fit in VTCM
    Tile size does not change with the batch; the bank is what limits it.
  • 128 tokens, the size the tests use
    The tests use 128, but the limit is the bank, not the tests.

Why can Qwen not take 512 tokens in one call?

One call keeps its activation tiles in one VTCM bank. The bank’s size is A_MAX in dsp/hmx.c: 3u << 20, which is 3 MB (3 × 1024 × 1024 bytes). A call checks that its tiles fit, and refuses the call if they do not (dsp/model.c).

SmolLM2 takes 512 tokens in one call, but Qwen only 320. What makes the difference? (SmolLM2’s hidden size is 1536; Qwen’s down matrix has 152 blocks of 32 inputs.)

  • Qwen’s down matrix has more input blocks, so each token needs more tile space
    The tiles of a group grow with the number of input blocks.
  • Qwen has more layers, and each layer keeps state in the bank
    Layers run one after another, so only one layer’s tiles are in the bank at a time.
  • SmolLM2 uses smaller tiles because it is smaller
    Both use 32 × 32 fp16 tiles, which are the same size.

The arithmetic, calculated from the same numbers the results use:

  • Qwen’s down matrix has 152 blocks of 32 inputs, so one 32-token group needs 152 tiles.
  • 152 tiles of 2048 bytes are 311,296 bytes for each group of 32 tokens.
  • 512 tokens are 16 groups: 4.98 MB, over the 3 MB bank.
  • 320 tokens are 10 groups: 3.11 MB, which fits. 321 tokens need 11 groups, which does not.
  • SmolLM2’s hidden size is 1536, so 512 tokens fit in its bank (1.57 MB).

Takeaway: the largest call depends on the widest input of the model, because that sets the tile space each token needs.

A matrix has 1,024 inputs. How many bytes does one 32-token group of its tiles take in the bank?

  • 65,536 bytes: 32 tiles of 2048 bytes
    1,024 inputs are 32 blocks of 32, and each block is one 2048-byte tile.
  • 2,048 bytes: one tile for the whole matrix
    Each block of 32 inputs makes its own tile.
  • 2,097,152 bytes: 1,024 tiles of 2048 bytes
    Inputs are grouped by 32, not one tile per input.

What you should take away

A prompt reuses each weight across its tokens, so the NPU runs it as a matrix times a matrix on HMX.

Every format is unpacked into the same fp16 tile. Q4_K scales in f32 and rounds once, because in f16 the scaled value and the offset nearly cancelled and small weights rounded to zero.

A call’s activation tiles must fit the 3 MB bank: Qwen’s longest call is 320 tokens.

Numbers on this page were measured on the iQOO 13 (SM8750) (results/phase-l5.md, steps 5a, 5b and 6, and the Q4_K_M prompts section; IMPLEMENTATION.md section 0) unless tagged otherwise.
