CPU, GPU or NPU: which one should run the model?

The same model, Qwen2.5-0.5B in Q4_0, ran on the phone’s CPU, its GPU and its DSP, which is the Hexagon NPU. Each one is fastest at a different job. This page puts every measured row in one table, says what each engine is good at, and shows which one to pick for a long prompt, a long reply, or a phone that must last on battery.

What are we trying to do here?

An engine is the hardware that does the matrix products of a model. Three engines run this phone’s model. Our CPU code runs on six threads on cores 2 to 7. Our GPU code runs on the Adreno 830. Our DSP code runs on the Hexagon v79, the phone’s NPU. All three read the same 278 MB of Qwen2.5-0.5B Q4_0 weights.

A model does two jobs, and they stress the hardware differently. Prefill reads the prompt. All its tokens go through the model together, so one read of the weights serves many tokens. Decode writes the reply one token at a time, and each token reads all the weights again. Speed is counted in tokens per second (tok/s). Energy is counted in joules per token: the watts the phone drew, divided by the tokens per second. A joule is one watt for one second.

Takeaway: the engines differ in prefill, decode and energy, so the right one depends on the job.

What did each engine measure?

Every engine decoded the same model, for five minutes on battery, with the screen awake. The short runs and the five-minute runs come from the same evening. Each engine was cooled below 45 °C before its short run.

Which engine decodes fastest over five minutes on battery?

  • The CPU
    It is fastest in a short burst, but five minutes of heat slows it.
  • The GPU
    It draws the least power, but its tokens are the slowest of the three.
  • The DSP
    It held 130.6 tok/s for five minutes, the highest of the three.

  • The two sessions had different heat and clock states
    Clocks differ by 10–20 % between sessions, so only rows from one session compare.
  • The 10-30 benchmark had a bug that slowed the CPU
    The 10-30 file ran the same code and its checks passed; the phone’s state changed.
  • The 10-29 run used a smaller model
    Both runs used Qwen2.5-0.5B Q4_0, 278 MB of weights.

Which engine reads a long prompt fastest?

A prompt of 512 tokens is one prefill of 512 tokens. The bench reports prefill speed at 64 and at 512 tokens. A longer prompt makes the first answer come later, so prefill speed decides how long a user waits before the reply starts.

On 10-30, which of our engines prefills 512 tokens fastest?

  • The CPU
    It leads at 64 tokens, so it is tempting to take it to 512 too.
  • The DSP
    It runs prompts on its matrix unit, but it came second at 512.
  • The GPU
    It prefilled 692.6 tok/s at 512, ahead of the DSP and the CPU.

The CPU prefilled 776.9 tok/s at 64 tokens, the fastest of ours at that length. At 512 tokens it fell to 526.0. The GPU went the other way: 690.6 at 64, then 692.6 at 512. The DSP sat between them at 641.4 for 512 tokens measured.

The DSP’s own timer, which leaves out the CPU’s part, gave 778 tok/s for 128 tokens on 2026-10-30 (results/phase-l5.md, step 5b). The bench’s wall-clock figure for 128 tokens was 798.9 measured.

The GPU’s prompt pass has changed since 10-30. On 10-31, in one session with llama.cpp’s OpenCL build, our int8 pass reached 1,174 and 1,200 tok/s at 64 tokens, against llama.cpp’s 571 and 603. At 512 tokens it was 1,067 and 1,074, against llama.cpp’s 1,194 and 1,108. So on that day ours led at 64 tokens and trailed at 512 measured.

Takeaway: for a 512-token prompt the GPU was fastest of ours on 10-30; for 64 tokens the CPU was.

A user sends a 64-token question. Using the 10-30 table, which engine prefills it fastest?

  • The CPU, at 776.9 tok/s
    At 64 tokens it beats the GPU’s 690.6 and the DSP’s 679.0.
  • The GPU, which won at 512
    The GPU leads at 128 and 512, not at 64.
  • The DSP, which has the matrix unit
    At 64 tokens it was the slowest of the three.

Which engine writes a long reply fastest?

Decode reads all the weights for every token. It also reads the KV cache, the stored keys and values of every earlier token, so each step gets slower as the text grows. The table gives two depths. Depth 0 starts from an empty cache. Depth 512 has 512 tokens already in it.

A reply is written at depth 512 or more, in short bursts. Which engine is fastest there?

  • The DSP
    It is fastest over five minutes, so it should lead at depth too.
  • The CPU
    It decoded 124.5 tok/s at depth 512, against 90.0 for the DSP.
  • The GPU
    It is the coolest engine, so it should also be the fastest at depth.

At depth 0 the CPU and DSP are close: 135.8 and 131.1 tok/s. At depth 512 the gap opens: the CPU keeps 124.5 tok/s, the DSP falls to 90.0 and the GPU to 88.9 measured.

The five-minute run is a different test. The DSP held 130.6 tok/s on average, and the CPU averaged 107.3. The CPU started at 188.1 tok/s in the same file and fell as the phone heated.

The DSP’s depth-512 number has improved since 10-30. On 10-31 its own timer gave 8.45 ms a token at depth 512, after the key and value prefetch (results/phase-l5.md). That is about 118 tok/s calculated. The timer leaves out the CPU’s part, and it is a different session, so it is not in the table. The 8.45 ms itself is measured.

Takeaway: from a short start the DSP writes the longest reply fastest; once the cache holds 512 tokens, our bursts put the CPU first.

Which one spends the least energy per token?

Energy per token is the watts drawn divided by the tokens per second. An engine that is slow but low-powered can still cost more per token than a fast, hotter one. The five-minute runs used two readings of the phone’s battery and sensors. The charge counter is the battery’s own count of charge drawn, which the raw files label as a whole-phone figure. The sampler is the run’s monitor, which reads the phone every half second.

Over five minutes on battery, which engine used the least energy per token by the charge counter?

  • The GPU
    It drew the least power, 2.26 W, but its tokens were the slowest.
  • The CPU
    It started fastest, at 188.1 tok/s, so each token should be cheap.
  • The DSP
    It drew 3.28 W, but at 130.6 tok/s it spent 0.025 J a token.

By the charge counter, the CPU spent 0.030 J a token, the GPU 0.029 and the DSP 0.025 measured. The DSP’s 0.025 is about 17 % below the CPU’s 0.030 calculated. The counter covered 153 s of the CPU run, 212 s of the GPU run and 281 s of the DSP run, so these are not whole-run totals.

The sampler gives other values from the same runs. Its totals divided by the tokens give 0.032 J for the CPU, 0.023 for the GPU and 0.023 for the DSP calculated. By that meter the GPU and the DSP tie.

The 2-minute runs of 10-29 agree on one point. The CPU cost 0.029 J a token by the charge counter (0.027 by the sampler, calculated), against 0.021 for the GPU (0.024 by the sampler, calculated). The GPU ran at 67.6 °C, the CPU at 88.8 °C measured.

Takeaway: the CPU cost the most energy per token in every reading; the GPU and the DSP cost less, and which is lower depends on the meter.

By the charge counter, the GPU drew less power than the DSP, yet its energy per token was higher. Why?

  • Energy per token is power divided by speed, and the GPU was slower
    Its 78.2 tok/s is well below the DSP’s 130.6, so each token took longer.
  • The GPU’s power meter reads high
    All three engines were read with the same charge counter and sampler.
  • Heat makes the GPU use more power per token
    The results give no such effect; the GPU ran the coolest of the three.

What does the app’s selector change?

The app has one selector with three choices: CPU, GPU and DSP. It replaced the GPU checkbox in commit a240b0a on 2026-10-30. Each choice opens a different kind of session on the same model file.

Which choice splits one request between two engines?

  • CPU
    It uses six threads, but all six are on one engine, the CPU.
  • GPU
    The prompt is read on the CPU cores and the reply is decoded on the GPU.
  • DSP
    It is the newest choice, but its session holds the whole model.

The code picks the session from the choice:

"GPU" -> Aether.openGpu(file.path, coreList, MAX_SEQ)
"DSP" -> Aether.openDsp(file.path, filesDir.path, MAX_SEQ)
else  -> Aether.open(file.path, coreList, MAX_SEQ)

From android/app/src/main/java/dev/aether/chat/MainActivity.kt at a240b0a.

  • CPU runs the prompt and the reply on cores 2 to 7 (the chosen core list).
  • GPU runs the reply on the GPU, but the prompt on the CPU cores. The GPU session takes the prompt from the CPU, so this mode has a CPU prefill.
  • DSP runs the whole model on the Hexagon. The app’s files directory holds our library, and the user session was created in 28 ms.

The in-app runs on 10-30 gave these speeds, on a different model, sampling and load, so they are not in the table. On the instruct Q4_0 model, the DSP read a 35-token prompt at 462 tok/s and decoded 183 tokens at 112 tok/s. On the Q4_K_M base model, the GPU decoded 219 tokens at 53 tok/s and the CPU decoded 512 at 171 tok/s with lookup on. The GPU’s decode has risen since; on 11-01 its Q4_K_M decode went from 53.2 to 67.5 tok/s on the charger, in a run that is only indicative measured.

Takeaway: GPU mode splits the work, with the prompt on the CPU; DSP mode runs the whole model on the Hexagon.

The app’s DSP session loads our library from the app’s files directory. Why that directory?

  • The DSP loader reads the first directory in its search path, and the app puts its own there
    Step 1 of the DSP work put that directory first in ADSP_LIBRARY_PATH.
  • The CPU must copy the library to the DSP before each call
    The library is loaded once; the DSP reads shared memory, not copies.
  • The DSP cannot read files that are not in the app’s own storage
    The DSP reads our library from that path; this is about the search path, not storage rights.

What you should take away

The GPU prefills a 512-token prompt fastest of our engines, the DSP writes a long reply fastest from a short start, and the CPU is best once the cache is long.

The CPU costs the most energy per token in every reading. The GPU and the DSP cost less, and the order between them depends on the meter, so check both before you choose for battery.

Numbers on this page were measured on the iQOO 13 (SM8750) unless tagged otherwise. The 10-30 table is one session; 10-29 and 10-31 rows compare only inside their own session. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
