What are we trying to do here?

When you read the engine for the first time, the hard part is not any one file but knowing which file to open. A prompt passes through the files in a fixed order: it is read from the command line or the app, the model file is loaded, the text becomes tokens, the tokens go through the layers, and a token comes out and becomes text again.

The sections below follow that order. Line counts are from 2026-10-29 and include each file’s tests. The library (src/lib.rs) only lists the modules; nothing runs there.

Where does a run start?

There are two ways in: the aether command-line program and the Android app. Both end up in the same place.

The app (Kotlin) and the command line both generate text. How much of the engine do they share?

  • All of it below a thin entry layer
    Both open the same Session; only argument parsing and the C bridge differ.
  • Nothing; the app has its own engine in Kotlin
    The app calls the Rust engine through a C interface; no inference code is in Kotlin.
  • Only the tokenizer
    Everything from loading to sampling is the same Rust code.

You want to support a new file format that stores the same kind of Llama model. Which files change?

  • A new reader in format/ and a loader in model/; nothing after loading
    The loader’s output is the shared Weights, which the forward pass already handles.
  • transformer.rs, to read the new file
    The forward pass never sees files, only Weights.
  • Every kernel
    Kernels see only matrices in known storage formats; a new file format does not change them.

Before the model runs, the prompt has to become token ids, in exactly the way the model’s own tokenizer does it. After each step, one id has to be chosen and turned back into text.

Qwen’s tokenizer splits a word differently from Hugging Face’s. Which file do you open first?

  • tokenizer/bytelevel.rs (and nfc.rs if the word has accents)
    Qwen uses the byte-level tokenizer, and its text is normalized first.
  • tokenizer/llama2c.rs
    That tokenizer is only for stories15M.
  • model/sampler.rs
    The sampler picks output ids; it never splits input text.

Where is the arithmetic?

The forward pass is the part that runs for every token, and nearly all the time is spent there.

Where does the forward pass code decide whether to use NEON instructions or plain Rust?

  • Not in the forward pass: it calls kernels, which choose
    The model code calls op functions; the kernel layer picks the code path for the machine and format.
  • In each layer, with an if per matrix
    That would spread hardware details through the model code; they are kept in one layer instead.
  • At compile time only, by building two programs
    The choice depends on the target, but also on the weight format, so it is made inside the kernels.

A faster Q4_0 dot product is written. Which file does it go in, and what else changes?

  • kernels/neon_quant.rs, and nothing in the model code
    The model calls the same op; only the kernel behind it is new.
  • transformer.rs, next to the matrix it speeds up
    The forward pass never contains format-specific code.
  • quant.rs, with every caller updated
    quant.rs holds layouts and quantizers; the dot products are kernels.

A timed run looks 20 % slower than yesterday. Which file’s output do you read first?

  • monitor.rs’s: the clocks and temperatures during the run
    A lower clock cap is the common cause of such a change on this phone.
  • transformer.rs, to find the slow code
    If the code did not change, look at the conditions first.
  • eval.rs’s perplexity
    Perplexity measures accuracy, not speed.

What you should take away

A prompt enters through main.rs or ffi.rs and goes through Session. Loading ends in one Weights type for every model; the forward pass in transformer.rs calls kernels that choose the code for the machine and format. About a third of the code is the lab that measures and checks the rest.

Line counts are from the engine on 2026-10-29, tests included. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
