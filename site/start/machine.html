Inside the machine: one multiply-add, from math to silicon

What physically happens when a phone runs one piece of an AI model: memory, registers, NEON lanes, caches, GPU threads, NPU tensor units, and how an engine picks between them. One tiny example, followed all the way through.

Act I · The arithmetic

What is the machine trying to calculate?

Almost all the work in a language model is one shape of sum: a grid of weights A times a list of inputs x gives a list of outputs y. Written y = A × x.

Here it is tiny: 4 rows of 8 weights, 8 inputs, 4 outputs. The same 40 numbers, in the same colours, travel through every step of this page.

Everything below is about how a phone finds these four numbers.

How do you get the first output?

Take row 0 of A. Pair each weight with the input in the same position: 2 with 2, 1 with 3, 3 with 1, and so on. Multiply each pair.

Eight pairs give eight products: 4, 3, 3, 8, 0, 2, 2, 15.

One output needs one product per weight in its row.

What happens to the eight products?

They are added into a running sum, one at a time. The place that holds a running sum is an accumulator: 0, then 4, 7, 10, 18, 18, 20, 22, 37.

Multiply matching pairs, add up the products: that is a dot product. Its result, 37, is y[0].

A dot product is a chain of multiply-adds: make a product, add it to the accumulator, repeat.

And the other three outputs?

Each row of A does its own dot product with the same x: 34, 22 and 36. Matrix × vector is one dot product per row, 32 multiply-adds in all.

Real models do the same thing at a different size. stories15M does 15.2 million multiply-adds per token; Qwen2.5-0.5B about 494 million, roughly one per weight calculated.

Matrix multiplication is a huge number of small multiply-add steps. That step is the unit of work for the rest of the page.

Act II · One core, one number at a time

Where do the numbers actually live?

Hardware cannot multiply “the number 2”. It multiplies bits stored somewhere. Memory is a long row of numbered byte slots; a slot's number is its address.

A 32-bit float (f32) takes 4 bytes, so row 0's eight weights sit in eight neighbouring slots: 0x1000, 0x1004, 0x1008… The inputs x sit somewhere else, also side by side. Hexadecimal is only a naming habit; what matters is that neighbours in the math are neighbours in memory.

Before any arithmetic, each number has to be fetched from an address.

What does the core do for one multiply-add?

A core is one processor that runs a stream of instructions. On Arm, arithmetic only works on registers: a few dozen named slots inside the core, each holding one value, that the arithmetic units read and write directly.

So one multiply-add is four instructions: load the weight into s1, load the input into s2, multiply into s3, add s3 into the accumulator s0.

One multiply-add = load, load, multiply, add.

And for the whole row?

The Rust loop repeats those four instructions eight times, one pair at a time:

for i in 0..8 {
    acc += w[i] * x[i];
}
  • acc lives in register s0 for the whole loop.
  • The loop adds its own instructions: add 1 to i, compare with 8, branch back.
  • Each += needs the previous one's result, so the additions form a chain.

The CPU isn't “doing matrix multiplication”. It runs a sequence of small instructions that adds up to one.

How does a line of code become hardware activity?

Four layers stack up. The math becomes a Rust line; the compiler turns that line into instructions; each instruction keeps one hardware unit busy for a moment: loads go to the load/store unit, FMUL and FADD to the floating-point/SIMD unit, the loop counter to an integer unit, the branch to the branch unit.

A modern core overlaps several instructions at once. For this loop on this phone: 1.64 instructions per cycle measured, about 1.77 cycles per multiply-add calculated (Phase 2).

Each line of Rust is a few instructions; each instruction is a moment of work for one unit.

Act III · Many lanes

What if one instruction could handle several pairs?

SIMD means Single Instruction, Multiple Data: one instruction that works on a short row of numbers (a vector) at once. Each position in the vector is a lane.

On the left, four multiplies take four ticks. On the right, one instruction does all four in one tick.

This is still one core running one instruction stream. The multiplier is simply four lanes wide. SIMD is not four cores.

SIMD: same core, same instruction stream, several pairs per instruction.

What does SIMD look like on this phone?

NEON is Arm's SIMD. It has 32 registers, v0–v31, each 128 bits: room for 4 f32 lanes.

  • vld1q_f32 loads 4 neighbouring floats in one instruction. That is why neighbours in memory matter.
  • vfmaq_f32 is a fused multiply-add: acc += w × a in all 4 lanes, multiply and add in one step.
  • The 4 lanes keep 4 separate partial sums across chunks: [4, 3, 3, 8], then [4, 5, 5, 23].
  • vaddvq_f32 adds the lanes once, at the very end: 37.

Try 1, 4 and 8 lanes. Eight f32 lanes need 256-bit registers (x86 has them); this phone's NEON is 128-bit and gets 8 lanes only with 16-bit numbers.

Load 4, multiply-add 4, keep 4 partial sums, add the lanes once at the end.

So NEON makes it 4× faster?

Not by itself. Measured on one prime core, the first NEON version was 3.4× faster than scalar, not 4×: with one accumulator, every multiply-add has to wait a few cycles for the previous one's result. That wait is a dependency chain. Four accumulators make four independent chains, and the speed more than doubles again measured.

Switch the matrix to DRAM: the bars stop near the ~61 GB/s that one prime core can read from memory. The lanes are waiting for bytes.

SIMD multiplies the arithmetic. It does not bring bytes in faster. Speed is set by whichever runs out first.

What does waiting for memory look like?

When the data is already close, the SIMD unit stays busy. When each chunk has to come all the way from DRAM on request, the unit sits idle far longer than the multiply takes.

Streaming through an array is rescued by the prefetcher: a circuit that spots a steady pattern of addresses and fetches the next data before it is asked for. Then the limit becomes how many bytes per second memory can deliver, its bandwidth illustration.

A fast SIMD unit that is fed slowly is a slow SIMD unit.

Act IV · Feeding the lanes

Why is some memory fast and some slow?

Between the registers and DRAM sit caches: smaller, faster memories that keep copies of recently used data. On this phone: L1, 96 KB per core; L2, 12 MB shared by a cluster of cores; a system-level cache shared with the GPU and NPU; then gigabytes of DRAM.

Finding data in a cache is a hit; not finding it is a miss, and the request goes one level further. Data moves in 64-byte cache lines measured: one miss on x[0] brings 16 floats.

Load x[0] (a miss), then x[1] (a hit), then the far-away weight.

A miss that the prefetcher did not predict typically costs hundreds of cycles assumption, not measured here. Steady streams hide most of it: one prime core read ~102 GB/s from L1 and ~61 from DRAM measured.

Moving data can cost more than the arithmetic. Neighbours travel together, so layout matters.

What if each number were smaller?

The same 64-byte line holds 16 f32, 32 f16, 64 int8, or 128 4-bit values. The same 128-bit register holds 4, 8 or 16 lanes.

Generating a token reads every weight once, so bytes per weight set a ceiling on tokens per second. Halve the bytes and the ceiling doubles. That is quantization: storing weights in fewer bits.

Switch the number type and compare the ceiling with the measured speed in the table.

Quantization is a bandwidth trick: the same memory traffic carries more weights.

How can a small integer stand for 0.03?

Store an integer plus a scale, shared by a block of weights: value ≈ integer × scale.

If row 0's real weights were 0.02, 0.01, 0.03…, they would be stored as exactly the integers used all along, 2, 1, 3…, with scale 0.01 illustration. Q8_0, the format the engine uses, keeps 32 int8 weights and one 16-bit scale in 34 bytes.

Quantized weights are small integers plus a scale per block; the scale is applied after the integer arithmetic.

What does a quantized dot product do?

  • One vector load brings 16 int8 weights; another brings 16 int8 inputs.
  • sdot multiplies 16 pairs and adds each group of 4 products into one 32-bit lane: four int32 accumulators per instruction.
  • Integer sums are exact: 18 + 19 = 37.
  • Only then come floats: 37 × 0.01 × 0.1 = 0.037, once per block.

Using sdot instead of turning weights back into floats first took the Q8_0 GEMV from 12 to 32 GB/s measured (Phase 6).

Integer multiply-adds into int32, then one float multiply per block: the inner loop of a quantized LLM on this CPU.

Act V · Many workers: the GPU

What if many workers each took a row?

The four dot products do not depend on each other. Hand each row to its own worker. Each worker still does its 8 steps in order, but all four run at once.

NEON made one worker wider. This makes more workers.

A GPU's parallelism comes from outputs that do not depend on each other.

How many workers could a real layer keep busy?

Qwen2.5-0.5B's MLP up projection has 4864 rows: 4864 independent dot products, each 896 long.

A GPU is built to run thousands of lightweight threads. A thread is one worker running the same small program on its own piece of the data. They are not thousands of CPU cores: they are grouped, and a group shares one instruction stream.

One output, one thread: the GPU's natural shape.

How does a GPU organise thousands of threads?

Threads come in workgroups: threads scheduled together on one part of the GPU, which can share fast on-chip memory and wait for each other. Thread i computes y[i].

Inside a workgroup, threads run in waves that execute the same instruction together (SIMT, single instruction, multiple threads). That is the GPU's version of SIMD lanes, written one thread at a time conceptual model.

Change the workgroup size: the same 4864 threads, cut differently.

GPU = many threads, grouped into workgroups, executed in waves.

How does the GPU know what to run?

A kernel is the program every GPU thread runs. The CPU records a command (“run this kernel on 4864 threads”), submits it through the driver, and waits for a fence, a signal that the GPU has finished.

On a phone the CPU and GPU share the same memory chips, so there is often no copy. The start-up, the wait and the signal still cost time.

Switch between our 4 × 8 and a real 4864 × 896 matrix.

A dispatch has a fixed cost. Small work cannot pay for it.

So which one is faster?

Neither, in general. The CPU starts instantly and runs any code; the GPU has more arithmetic but must be started and waited for. The answer depends on how big the work is, how much is independent, how many bytes move, the number type, and the dispatch overhead.

For decode, both read every weight from the same DRAM, so both meet the same bandwidth limit.

“Faster” is a property of a workload on a processor, not of the processor.

Act VI · Built for neural networks: the NPU

What is special about neural-network work?

Zoom out: one multiply-add, a dot product of 896, a matrix of 4.4 million, a layer of 14.9 million, a model of about 494 million per token calculated.

It is the same few shapes over and over, in an order fixed before the model runs. Hardware can be built around that.

Neural networks are huge but predictable.

What does an NPU do with that?

An NPU (neural processing unit) is a processor built for these shapes. In this conceptual model it has a scalar unit for control, a vector unit, a tensor unit that multiplies a whole tile of numbers in one operation, and on-chip memory the units share conceptual model.

The CPU does not send it instructions one by one. An NPU runtime loads a compiled graph of operators (named steps such as MatMul, Add, Softmax) and asks the NPU to run it; data moves in planned blocks.

Qualcomm describes its Hexagon NPU as scalar, vector and tensor accelerators sharing memory. The sizes and details differ between Snapdragon generations; this picture is not a claim about this chip's internals.

An NPU runs whole operators on whole tiles, with the data movement planned ahead.

Are these three different kinds of machine?

Less than the names suggest. All three are multiply-add hardware fed from the same memory. NEON lanes and GPU waves are both “one instruction, many values”. GPUs and NPUs both take work that was planned ahead and handed over.

They differ in what they are tuned for: the CPU for any code and quick starts, the GPU for many independent threads, the NPU for fixed neural-network graphs.

Not three unrelated machines: three tunings of the same idea.

Act VII · Same answer, three routes

Does the answer depend on the processor?

Switch between CPU, GPU and NPU. The route changes: lanes and chunks, threads and a dispatch, or one tensor operation. The result does not.

With small integers the results match exactly. With real floats, a different order of additions can change the last bits, and an NPU usually works in int8 or fp16, so results are close rather than identical. Tests compare with a tolerance for that reason.

The math is fixed; the route is a choice.

Act VIII · The real model

Where does all this show up in an LLM?

A token passes through an embedding lookup, then 24 layers (for Qwen2.5-0.5B), then the output matrix that scores every possible next token. The copper boxes are matrix multiplies; during decode each one is a matrix × vector, a GEMV, run by a quantized NEON kernel.

In Phase 2, 97.6 % of CPU cycles went to matmul measured. Attention grows with the context; norms and sampling are small. Not every step suits the same processor.

An LLM on a CPU is mostly the quantized GEMV from Act IV, run hundreds of times per token.

Why are prefill and decode so different?

Prefill processes the whole prompt at once: matrix × matrix. Each weight is fetched once and used for every prompt token, so the arithmetic per byte grows with the prompt.

Decode makes one token per step: matrix × vector. Every weight is fetched again for every token and used once, so memory sets the pace.

Slide the number of tokens processed together and read the measured speeds.

Prefill is arithmetic, decode is memory. That is why the best processor can differ between them.

What is the KV cache, and how big does it get?

Each token leaves a key and a value vector in every layer. A new token's query is compared with every earlier key to decide which values to mix in. Keeping them, instead of recomputing them, is the KV cache.

It grows by the same amount with every token, and decode reads all of it at every step, on top of the weights.

Raise the context length, change the model, or add one token and watch it attend to every key.

Long contexts turn the KV cache into a second stream of bytes as large as the weights.

Act IX · The phone

Where do the processors sit in the phone?

On one chip: 8 Oryon CPU cores (6 performance, 2 prime), the Adreno GPU, the Hexagon NPU and a system-level cache, all reading the same DRAM. One prime core alone reads ~61 GB/s; all CPU cores together ~67 measured.

Handing work to another processor is not free: dispatch and synchronisation each cost time, and the phone's power and heat limits cap clocks (on battery, the cores ran at ~2.4 GHz, well below their maximum measured).

Compare the three routes for one decode step illustration.

Shared memory makes handoffs cheap, not free.

Where should optimisation effort go?

Look at where the time goes first. In this made-up profile, the quantized GEMV is 62 of 100 ms illustration.

Make the GEMV 2× faster: the total falls from 100 to 69 ms. Make the embedding 2× faster: 100 to 99 ms.

The same happened for real: matmul was 97.6 % of cycles, and NEON kernels took decode from 88.6 to 422 tokens per second on the same core measured.

Measure → find the biggest bar → improve it → measure again.

Act X · The whole picture

What is the whole mental model?

An LLM is transformer layers; a layer is matrix multiplies; a matrix multiply is dot products; a dot product is multiply-adds.

Each multiply-add can take a CPU route (NEON lanes in registers), a GPU route (a kernel on threads), or an NPU route (a tensor operation). Prefill and decode pull in different directions, and the runtime decides.

The hardware is not “running AI”. It is executing enormous numbers of simple operations, moving data through memory, registers, SIMD lanes, threads and specialised accelerators.

What does this give you when you read kernel code?

Read the two loops side by side, with the picture running:

  • vld1q_f32: four neighbouring weights, memory → one register.
  • vfmaq_f32: four multiply-adds in four lanes, into four partial sums.
  • step_by(4): the next chunk.
  • vaddvq_f32: add the lanes once, at the end.

Where speed is lost: waiting for bytes (layout, cache misses), one long dependency chain, and overhead around tiny pieces of work.

Every line of a kernel is a movement of data or a batch of lanes. Read it that way.

What you should take away

Inference is multiply-adds plus moving bytes. NEON makes one core do several multiply-adds per instruction; caches and quantization decide how fast the bytes arrive; GPUs and NPUs add more multiply-add hardware at the cost of handing work over. Decode is limited by memory, prefill by arithmetic, and a profile shows which one you are fighting.
