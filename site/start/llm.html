How an LLM makes text

What does a language model do?

How can a phone write a reply at all? The answer starts with one small job. A language model takes some text and scores every possible next piece of text. It picks a high-scoring piece, sticks it on the end, and asks again. Repeat until you have a paragraph. That is all “generating” means.

The keyboard on your phone suggesting the next word is the same idea at a tiny scale. An LLM (large language model) does it with hundreds of millions of learned numbers, so its guesses take the whole conversation into account.

Training vs inference

Training is how those numbers were learned, on huge computers, once. Inference is using them. This project is only inference: the numbers arrive in a file, and our job is to do the arithmetic with them correctly and quickly on a phone.

Takeaway: generating text is a loop that scores the next piece, appends it, and repeats.

How big is the model file?

The learned numbers are called weights, or parameters. They are grouped into big rectangular grids called matrices. They never change while you generate text. The model file is mostly just these numbers, one after another.

To find the size, multiply the number of weights by the bytes per weight. In f32, each weight is 4 bytes calculated:

Keep the last number in mind. A phone’s fast on-chip memory (the caches) holds a few megabytes. Two gigabytes does not fit. The weights have to sit in the phone’s main memory, which is far away by chip standards. That one fact is most of this project.

Takeaway: the weights are a fixed file of numbers, and a 2 GB file cannot fit in the phone’s caches.

How does text become numbers?

The model does not see letters. A tokenizer first chops text into tokens, common chunks like whole words, pieces of words, or punctuation. It replaces each token with its number in a fixed list called the vocabulary.

Each token ID then picks one row out of a big table, the embedding table. That row is a list of numbers, a vector, that stands for the token. For stories15M it is 288 numbers long; for Qwen2.5-0.5B, 896. From here on the model only does arithmetic on vectors.

Takeaway: text becomes token IDs, and each ID picks one vector for the model to work on.

Turning the current token into scores for the next one is called a forward pass. The vector goes through a stack of identical blocks called layers, then gets turned into one score per vocabulary entry:

Almost all the time in a forward pass goes into one kind of step: a weight matrix times the token’s vector. Normalisation and other steps exist, but they touch a few thousand numbers. The matrices hold hundreds of millions.

Takeaway: nearly every box in a forward pass multiplies a vector by a large matrix of weights.

What is the main operation, and how often does it run?

Multiplying a matrix by a vector means: for each row of the matrix, multiply it element by element with the vector, and add the results up. That sum is one number of the output. Do it for every row. This is called GEMV (general matrix times vector).

In decode, each weight is used once, for one multiply and one add, and then it is done for this token. That is 2 FLOPs for every 4 bytes read: 0.5 FLOP per byte. The arithmetic is trivial for a modern core. Getting the bytes there is not.

Switch to prefill and the same bytes do four times the work, because four tokens’ vectors share each weight once it has been loaded. That ratio, FLOPs per byte, is called arithmetic intensity. It decides whether a piece of code waits on memory or on arithmetic. Phase 1’s roofline page draws it.

Takeaway: in decode each weight is used once per token, so the bytes moved, not the arithmetic, set the pace.

The guesses and percentages are made up for illustration. The bytes are real arithmetic calculated; the 30 GB/s is an assumption, not this phone.

Two details in that demo:

  • Greedy decoding. The demo always takes the top guess. Real chat apps usually sample with some randomness, but greedy is deterministic, which is why Aether uses it to check its output token-for-token against a reference engine.
  • The KV cache. Attention needs information about every earlier token. Rather than recompute it each step, the engine saves it. That saved state is the KV cache. It grows by one entry per token, and it is the only thing that grows. The weights stay the same size, and they are read in full every step.

Takeaway: the prompt is one prefill pass, and each new token is one decode pass that reuses the KV cache.

Why is a phone slow at this?

Every decode step reads (nearly) every weight from main memory, uses each one for a single multiply-add, and then needs them all again for the next token. The weights do not fit in the caches, so nothing is still close by. The core spends most of its time waiting for bytes to arrive. Speeding up the arithmetic alone does not change that.

tokens per second ≤ memory bandwidth ÷ bytes of weights read per token.

Worked through: if the phone could move 30 GB/s assumption, a 2 GB f32 model allows at most 15 tokens per second calculated, no matter how fast the arithmetic is. Store the same weights in 4 bits instead of 32 and the bytes shrink about 7×, so the ceiling rises about 7×. That is why quantization matters so much on phones. The full argument, with a calculator, is the decode ceiling.

This is the sentence from the top of the page. Phase 1 measures the real bandwidth. Every later phase is judged against it.

Takeaway: tokens per second is capped by memory bandwidth divided by the bytes of weights read per token.

Check yourself

Generating 50 tokens after a 10-token prompt takes how many forward passes?

About 50: one prefill pass that handles all 10 prompt tokens together and produces the first new token, then 49 decode passes. Each of those passes reads the weights again.

Why does a faster CPU core not make decode much faster?

Because the core is mostly waiting for weights to arrive from memory. Each weight gets one multiply-add, which takes almost no time. The limit is how many bytes per second memory can deliver.

Why can prefill go faster per token than decode?

Many prompt tokens share each weight once it is loaded, so the same bytes feed many times more arithmetic. Decode has one token, so each weight read feeds one multiply-add.

What grows during a conversation, and what does not?

The KV cache grows by one entry per token. The weights stay the same. They are read in full for every new token either way.

What you should take away

A phone writes text by scoring one next token at a time, and each score is a forward pass over a matrix of weights.

Decode reads the weights for every token, so memory bandwidth sets the speed.

The one-sentence answer is the bandwidth ceiling: tokens per second cannot exceed bandwidth divided by the bytes read per token.

Model sizes are parameter counts × 4 bytes. Guesses and probabilities in the demo are illustrative. Teal is measured, blue is calculated, amber is an assumption.
