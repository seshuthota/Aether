How we know it’s right

An inference engine can be wrong in ways that still produce fluent text. A sign error in one layer, a token split differently, a rounding choice in a quantizer: the model still talks, just slightly worse. This page explains the one rule every test in Aether follows, the outside programs it checks against, and how close “right” has to be.

What are we trying to do here?

Text from a language model is hard to judge by eye. A broken engine often writes plausible sentences, so “it looks fine” proves very little. Aether therefore checks numbers, not impressions: each part of the engine is compared with the same computation done by an established program that other people wrote and use.

Those programs are the references: numpy for the kernels, llama2.c for the first model, Hugging Face transformers and tokenizers for the real models, and llama.cpp for its file formats, quantizers and quality numbers. Their outputs, saved to files, are the golden data the tests compare against. By the end you can say, for any part of the engine, what it is checked against and how close it must be.

Why can’t the code check itself?

A tempting way to test a fast kernel is to write a second, simple version and compare the two. If they agree, surely both are right?

You misread how RoPE pairs the numbers, and write both a fast and a simple version that way. What do the two versions do in a comparison test?

  • Agree perfectly, and the test passes
    Both carry the same misunderstanding, so they make the same mistake.
  • Disagree, because one of them is fast
    Speed does not change the result; both compute the same wrong thing.
  • The compiler catches it
    The code is valid; it just computes a different function than the model expects.

This is the reason for the project’s rule: no duplicate implementations for testing. A second copy written by the same person catches typing mistakes, but not mistakes in understanding, and those are the expensive ones. A program written by someone else and used by many people carries independent understanding. Agreement with it means something.

The same rule applies to speed. Our benchmark numbers are compared with llama.cpp’s llama-bench on the same phone, not with our own earlier claims.

Takeaway: a test is only as independent as its reference, so every reference is a program someone else wrote.

A new model family needs a different chat template. What is its reference?

  • transformers’ apply_chat_template on that model’s own files
    The model’s published template defines the prompt it was trained with.
  • Our ChatML function, which already passes its tests
    Those tests are for Qwen’s template; a new family needs its own reference.
  • Reading the generated text and seeing if it answers sensibly
    Fluent text is exactly what a slightly wrong prompt still produces.

Identical, or only close?

Floating-point addition rounds after every step, so the order of additions changes the last bits of a sum. (a + b) + c and a + (b + c) can differ.

Our NEON matmul adds products in four interleaved chains; numpy adds them in another order. What should the test require?

  • A small relative difference, growing slowly with the row length
    Rounding differences add up like a random walk, so about √n.
  • Identical bits
    Only possible if both add in exactly the same order, which they do not.
  • Anything within 1 %
    Far too loose; a real bug, such as a missing element, can hide inside 1 %.

So the kernel tests allow a relative error of 1e-6 × √n, where n is the number of terms in each sum. The bound is tight enough that dropping a single element of a long row fails it.

Two kinds of result are held to exact equality instead:

  • stories15M against llama2.c. Phase 2 did every operation in llama2.c’s order, so every activation of every layer matches to the last bit, and so do greedy and seeded generations.
  • Integers and bytes. Token ids, quantized blocks and tokenizer output have no rounding to excuse a difference. The quantizers write exactly llama.cpp’s bytes, with and without an importance matrix.

Takeaway: when the order of operations is the same, results must be identical; when it differs, the test allows a bound that grows like √n and no more.

A threaded matmul gives slightly different results depending on the number of threads. Is that acceptable here?

  • No: each output’s sum is done by one thread in a fixed order, so the bits must not depend on the thread count
    The split is by rows, not within a sum, so there is no reason for any difference.
  • Yes, within 1e-6 × √n
    That bound is for comparing with a different program; the same code must match itself exactly.
  • Yes, threads are never deterministic
    Their timing is not, but each output can still be computed by one thread in a fixed order.

Where do the reference answers live?

The references are Python and C programs, and the tests run on the phone in Rust. So the two meet through files. Scripts in tools/ run the reference once on the PC and save inputs and expected outputs to testdata/; the Rust tests read them back.

  • tools/gen_kernels.py writes numpy inputs and outputs for every kernel, at awkward sizes (odd lengths, tails) where SIMD bugs live.
  • tools/hf_dump.py runs transformers with hooks that save every layer’s activations.
  • tools/gen_quant.py and gen_quant_imatrix.py quantize with llama.cpp’s own code.
  • tools/fetch_models.sh downloads the models and builds GGUF files with llama.cpp’s converter.

Some of these files are hundreds of megabytes, so they are regenerated, not committed. A test that needs a missing file prints SKIP with the path and returns, instead of failing on a fresh checkout. The cargo runner copies testdata/ to the phone, so the same tests run there (cargo test --release --target aarch64-linux-android): 105 passed on the phone on 2026-10-29 measured.

Takeaway: references run once on the PC and leave their answers in files, which the Rust tests read on the PC and on the phone.

A test prints SKIP on your machine. What does that tell you about the code?

  • Nothing yet: its golden file is missing, so the comparison never ran
    A skip is not a pass; regenerate the file with the script in tools/ and run it again.
  • The code passed
    Nothing was compared, so nothing was shown.
  • The code failed
    Nothing was compared either way.

How do you check a quantized model?

A 4-bit model is meant to differ from the original: it rounds every weight. So “identical to f32” is the wrong test. The question becomes whether it loses the same amount of quality as llama.cpp’s version of the same file.

Two measures answer that, both computed on the same wikitext text by our engine and by llama-perplexity. Perplexity is how surprised the model is by real text. KL divergence is how far its predicted probabilities drift from the f32 model’s. For SmolLM2-135M Q4_0 quantized with an importance matrix, for example:

             ours       llama.cpp
perplexity   25.8604    25.8345 ± 1.093
mean KLD     0.269287   0.269190 ± 0.003723
  • The two engines agree well inside llama.cpp’s own error bar.
  • The error bar is a statistical one: it says how much the number would move with different text. A difference much larger than it would point to a bug.

Takeaway: for results that are meant to be approximate, the test is the same quality loss as the reference, within the reference’s error bar.

Our Q4_0 perplexity is 27.7 and llama.cpp’s 27.7 ± 1.2, but our KL divergence is twice llama.cpp’s. What do you conclude?

  • Something differs: KL is much more sensitive than perplexity, and it disagrees
    KL compares every probability, so it catches drift that averages out in perplexity.
  • All is well: perplexity matches
    Perplexity can match while the probabilities differ; both measures must agree.
  • llama.cpp is wrong
    Possible, but the reference is the program many people check against; look at ours first.

What you should take away

Every test compares against a program someone else wrote, never a second copy of our own. Results with the same order of operations must be identical; others must stay inside a bound that grows like √n. Quantized models are checked by matching the reference’s perplexity and KL divergence within its error bars.

Results are from results/phase-N.md and the test suite as of 2026-10-29. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
