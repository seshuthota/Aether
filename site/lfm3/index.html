LFM3 · overview

Built and checked on the CPU

LFM3-1.7B loads from its GGUF files and runs on the phone’s CPU. Its logits match Hugging Face transformers. Its perplexity on the Q4_K_M file is 24.8542 here and 24.8278 in llama.cpp. Decode is still behind llama.cpp for that file, and the pages say why.

What changes when not every layer is attention?

Every model before this one repeats one kind of layer: attention over all earlier tokens, then an MLP. LFM3-1.7B mixes in a cheaper kind. Thirteen of its 24 layers are short convolutions, which keep a small fixed state. The engine reads from the file which layer is which.

What is inside LFM3-1.7B?

Until now, every layer was attention followed by an MLP (the feed-forward block that mixes each position’s own numbers). Attention stores a key and a value for every token it has seen, in the KV cache, so its memory grows with the context. LFM3 uses two cheaper kinds of mixer as well.

  • Short convolution. Each position is mixed with the few positions just before it, using a fixed set of weights. The state is the last six vectors, whatever the context length.
  • Sliding-window attention. Attention over only the last 256 positions. Its cache is a fixed size too.

The model has 1.73 billion parameters (plans/lfm3.md, section 2). Of its 24 layers, 13 are short convolutions, 6 are full attention and 5 are sliding-window attention. The order below is the model’s own:

Takeaway: 18 of the 24 layers do not attend over the whole prefix. Only 6 do.

How does the engine know which layer is which?

The weights alone do not say what a layer is. A convolution layer and an attention layer store different tensors, so the loader needs a rule. The GGUF file carries the rule as metadata: a few arrays with one entry per layer. The loader reads them in src/model/gguf.rs.

  • attention.head_count_kv is an array of 24 numbers. A 0 means a convolution layer; any other number means attention. For layer 0 the value is 0, so layer 0 is a convolution.
  • attention.sliding_window_pattern is an array of true and false. True marks a sliding layer, and attention.sliding_window (256) gives its window.
  • RoPE. Full layers use rope.freq_base, and sliding layers use rope.freq_base_swa. The conv and sliding decisions are made only for the lfm3 architecture, so the Qwen and llama files load as before.
  • Conv width. shortconv.l_cache gives the number of taps, with 7 as the fallback.

Each layer then holds one Mixer: attention weights or convolution weights (src/model/transformer.rs). Config::kind(layer) in src/model/config.rs returns the kind for any layer index.

Takeaway: two metadata arrays set the kind of every layer, so one loader handles both kinds.

What else differs from Qwen2.5?

Qwen2.5-0.5B is the model the earlier phases were built around. Its 24 layers are all full attention, with one RoPE rule and one tokenizer rule. LFM3 changes four more things. Each one is a line here, with the page that explains it.

  • Per-head norm and gate. Query and key each get an RMSNorm per head before RoPE, and each head’s attention output is scaled by a sigmoid gate. Our Qwen loader has neither. See Sliding windows, partial RoPE and per-head norms.
  • Partial RoPE. A full layer rotates 32 of the 64 pairs in each head. The other 32 pairs are left unrotated. Qwen rotates every pair. See the attention page.
  • Sliding-window layers. Five layers see only the last 256 positions. In Qwen, every layer sees the whole prefix. See the attention page.
  • Tokenizer. The same byte-level BPE as Qwen, with three changes: digit groups of up to three, no NFC step, and ignore_merges. See byte-level BPE and NFC.

Takeaway: the decoder keeps Qwen’s shape. The mixer, the RoPE rule and the tokenizer rule are what changed.

Why is this the first model here limited by memory bandwidth?

Memory bandwidth is how many bytes per second the phone can read from its main memory (DRAM). Decode reads every weight once for each token, so the weight file’s size sets a limit on speed. The limit is bandwidth divided by bytes read per token, as the decode-ceiling page works out.

For LFM3 the file is 1,099,627,808 bytes, about 1.1 GB, for the Q4_K_M version. The plan’s rule of thumb is that 1.1 GB per token at about 60 GB/s allows at most about 55 tokens per second calculated.

Takeaway: LFM3 is the first model here where the bandwidth ceiling is the number to beat, and our kernels are well below it.

What is still open?

  • Decode speed. Decode for Q4_K_M is behind llama.cpp, and our K-quant kernels set the speed. The work that closes the gap is a separate plan, and its page is not written yet.
  • The GPU. The GPU path for LFM3 is a later plan (A8 in plans/lfm3.md). This page covers the CPU only.

What you should take away

Eighteen of LFM3’s 24 layers do not attend over the whole prefix: 13 are short convolutions and 5 are sliding windows.

Two metadata arrays in the GGUF file tell the loader the kind of each layer.

A 1.1 GB file puts the bandwidth ceiling in reach on the phone, and our kernels are still well below it.
