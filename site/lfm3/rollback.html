How do you undo a convolution?

Speculative decoding checks guessed tokens in one pass and throws away the wrong ones. For attention, throwing away is free. For a short-convolution layer, the rejected tokens have already changed its state, so the engine has to put that state back.

What are we trying to do here?

Speculative decoding guesses a few tokens ahead and checks all of them in one batched pass (see Several tokens per weight read). The guesses are draft tokens. They come from copying earlier text or from a small draft model. The model that decides the output is the target. Each draft is kept while it matches the target’s own choice. The first draft that does not match is thrown away, with every draft after it.

The pass writes into two kinds of memory. The KV cache of an attention layer holds one key and one value per position. The conv state of a short-convolution layer holds six rows, one per recent token, and it is the same size whatever the length of the text. A rollback makes each memory match the last token that was kept.

Can attention forget rejected tokens by moving back?

An attention layer keeps a KV cache, one key and one value for every position. A position counter says how many entries are in use. Rejected drafts have already written their keys and values past the point where the kept text ends.

Four drafts were rejected. Their keys and values sit at positions 19 and 20. What happens to them before the next pass?

  • Nothing: they are ignored, and the next pass overwrites them as it reaches those positions.
    Attention reads only up to the position counter, so entries past it are never read.
  • They are zeroed, so no stale value leaks into the next token.
    Nothing in the code clears them; the counter already hides them.
  • They are restored from a saved copy, as the conv state is.
    The conv state needs that because its rows change in place. A KV row is written once, at its own position.

For a full attention layer, a token at position pos writes its key and value into row pos. Its attention reads rows 0 through pos:

} else {
    att_pos = pos;
    at = pos * kv_dim;
}
  • att_pos is the last row that attention reads. Moving pos back moves it back too.
  • The rows above it stay in memory. The next token that reaches each position writes over them.
  • The comment on restore_conv says the same: “the KV entries of rejected drafts are simply overwritten later.”
  • A sliding-window layer keeps a ring of window + 256 rows and writes row pos % ring. The spare rows leave room for the drafts, so a rollback still finds the rows it needs.

Takeaway: for attention, a rollback is only moving the position counter back. The stale entries are never read, and the next pass overwrites them.

The position counter is at 19. Can the token at position 19 read the key stored at position 20?

  • No: attention reads positions 0 through 19 only.
    The counter bounds the read, so the stale key at 20 is never loaded.
  • Yes, the same prefix gives the same key.
    Position 20 holds a key from a rejected draft, not from this prefix. It is not read anyway.
  • Yes, but its score is masked to zero.
    A masked key is still loaded. The code never loads row 20.

Why can’t the conv state simply move back?

A short-convolution layer mixes each token with the few tokens before it. It keeps a conv state of six rows. Row n holds the layer’s gated input for one recent token (called u in the code). LFM3 has 13 such layers, and each row is 2048 values wide (results/phase-lfm3.md, A0 and A4). Every new token adds its row and drops the oldest.

Four drafts have been fed through a conv layer. What does its state hold now?

  • The six most recent rows, drafts included. The older rows were shifted out.
    The state is one window that moves with every token; no index brings old rows back.
  • One row per position, so setting the position back selects the old row.
    That is how the KV cache works. The conv state is one window, not a row per position.
  • Only the rows of the kept tokens, since the layer drops rejected ones.
    The layer cannot tell a rejected draft from an accepted one when it runs.

The update is two lines in short_conv_step (src/kernels/mod.rs):

state.copy_within(dim..6 * dim, 0);
state[5 * dim..].copy_from_slice(u);
  • copy_within moves rows 1 to 5 down to 0 to 4. The oldest row is overwritten.
  • u becomes row 5, the newest.
  • No copy of the old rows is kept, so there is no index to set back.
  • Once a rejected draft is in the state, the layer reads it. Without a restore, the rejected draft changes the layer’s output until six newer tokens have pushed it out.

Takeaway: the conv state has no row per position, so a rollback needs a saved copy of the state.

How does the engine put the conv state back?

The pass has already run through every conv layer, so each state holds the rejected rows. A rollback has to return each conv layer to the state after the last kept token.

A conv layer must go back to the state after the last kept token. Which of these does the engine do?

  • Copy a saved state back: one copy per conv layer, and no token is run again.
    The engine keeps a copy of each conv state for the last 33 positions.
  • Run the kept tokens through the conv layers again, from the start.
    That also works, but it runs every layer again. A saved copy costs a single memory copy.
  • Subtract the rejected rows from the state.
    The state is a window of rows, not a sum, so there is nothing to subtract.

After each conv token, conv_token copies the new state into a slot chosen by position:

let slot = base + (pos % (MAX_DRAFT + 1)) * 6 * dim;
s.conv_snap[slot..slot + 6 * dim]
    .copy_from_slice(state);

restore_conv copies the slot for one position back into the live state (src/model/transformer.rs):

let slot = off * (MAX_DRAFT + 1)
    + (pos % (MAX_DRAFT + 1)) * 6 * c.dim;
s.conv_state[off..off + 6 * c.dim]
    .copy_from_slice(&s.conv_snap[slot..slot + 6 * c.dim]);
  • MAX_DRAFT is 32, so there are 33 slots. The slots are reused by position, so the last 33 positions are kept.
  • generate_draft clamps the draft length to MAX_DRAFT - 1, that is 31, so one batch always fits in the slots.
  • Batches longer than 32 tokens, such as prompt chunks, skip the snapshots (the other branch of conv_batch). A rollback only ever goes back over a draft.
  • The rollback in generate_speculative is self.model.restore_conv(pos - 1). The counter has moved past the kept tokens, so pos - 1 is the last token kept.

Here is one pass, with the token c at position 16 and drafts d1 to d4 at 17 to 20. d1 and d2 are kept, and d3 is rejected. Rows are named by the token that wrote them.

stage                conv state (6 rows)     KV rows
-------------------  ----------------------  ---------------
before the pass      after 15: rows 10-15    0-15
after the pass       after 20: rows 15-20    0-20
rolled back to 18    after 18: rows 13-18    0-18 kept,
                                             19-20 stale
next pass starts at 19
  • After the pass, rows 10 to 14 have left the state. Row 15 is the oldest row still in it.
  • The restore brings back the snapshot after 18, the last kept token. Rows 19 and 20 are not in the state any more.
  • The KV rows 19 and 20 are stale. The next pass writes over them.

Takeaway: each conv layer keeps a copy of its state for the last 33 positions, and a rollback copies the one for the last kept token back.

Drafts d1 to d5 sit at positions 17 to 21, after the certain token at 16. d1, d2 and d3 are kept; d4 is rejected. Which snapshot is restored?

  • Position 19, the state after d3
    The last kept token is at 19, so its snapshot is the one copied back.
  • Position 21, the last one written
    That state has absorbed the rejected drafts; it is the one to undo.
  • Position 16, the certain token
    That throws away d1 to d3, which were kept.

How do we know the restore is exact?

The test is lfm3_conv_state_rolls_back in src/model/gguf.rs. It uses the real Q4_K_M file. One model decodes the kept tokens. A second model also runs two rejected drafts, 1234 and 5678, at positions 17 and 18, and then rolls back:

let want = plain.forward_batch_logits(
    &[next, 777, 4321], 16, 0)[vocab..3 * vocab].to_vec();
spec.forward_batch_logits(&[next, 1234, 5678], 16, 0);
if restore {
    spec.restore_conv(16);
}
let got = &spec.forward_batch_logits(
    &[777, 4321, 99], 17, 0)[..2 * vocab];
  • The logits at 17 and 18 must match want. The test asserts a relative error below 1e-5.
  • The same check without restore_conv must fail, with an error above 1e-2. The test would catch a missing rollback.
  • Both models run in 3-token batches. On the phone a single token takes another code path, with different rounding, so one token at a time would not match bit for bit.
  • On the phone, the log reads measured conv rollback: logits rel 0.00e0; without the restore 6.42e-1 (results/phase-lfm3/raw/phone-tests.txt).

Lookup and draft decoding use the same rollback. On the phone, the draft-decoding test ran 13 passes over 46 drafted tokens, and 30 were kept. The 16 tokens not kept are calculated from those counts. Its greedy text forked from plain decoding once, at token 22 (“ the” against “ brown”), where the two logits differ by a gap of 2.25e-3 of the largest logit. The test allows a fork only at a near tie.

Takeaway: with the restore, the logits match a run that never saw the drafts. Without it, they are far off.

Why does the test run both models in 3-token batches, not one token at a time?

  • On the phone a single token takes another code path with different rounding, so only equal batch sizes match bit for bit.
    Both runs must round alike; the rollback itself is the same either way.
  • A 3-token batch is faster to run in the test.
    Speed is not the reason; the test is about equal numbers.
  • The restore only works for batches of three.
    The restore copies a saved state; it does not depend on the batch size.

Does a draft model need the same restore?

A draft model is a second, smaller model with the same vocabulary. It keeps its own KV cache and conv state, and it makes the drafts that the target checks. Its history can differ from the real text after a rejection, because it ran the rejected drafts itself.

The target rejected some of the draft model’s tokens. The draft model has already run them. What should happen to its conv state?

  • It goes back to the last token the two models share, then the rest is fed again.
    The draft’s cache and conv state must match the text the target kept.
  • Nothing: the target decides the text, so a stale draft state cannot change the output.
    True for the text, but the stale state makes every later draft wrong, so the speed is lost.
  • It is rebuilt from scratch by re-reading the whole prompt.
    That would work, but the code restores a saved state instead.

Drafter::propose (src/session.rs) finds the shared prefix and restores the draft to its last token:

let keep = self.fed.iter().zip(hist)
    .take_while(|(a, b)| a == b).count()
    .min(hist.len() - 1);
// A hybrid draft model's conv state goes back with the cache (a
// no-op for all-attention models).
if keep > 0 && keep < self.fed.len() {
    self.model.restore_conv(keep - 1);
}
self.fed.truncate(keep);
  • fed is the draft’s history: the tokens its cache and conv state have absorbed. hist is the real text.
  • keep counts the shared tokens, so the last shared one is at index keep - 1.
  • truncate drops the draft’s KV rows past keep. The conv restore does the same job for the conv state.
  • An all-attention draft has no conv state, so the restore does nothing for it.

Takeaway: a draft model rolls back its conv state to the last shared token, just as the target does.

The draft has fed 20 tokens. The shared prefix with the real text is 19 tokens long, at positions 0 to 18. Which snapshot does the draft restore?

  • Position 18, the last shared token
    keep is 19, so keep - 1 is the last shared token’s index, 18.
  • Position 19, the first token that differs
    That state has already absorbed the wrong token, so restoring it keeps the error.
  • Position 0, the start of the prompt
    That throws away every shared token, which the draft need not re-read.

What you should take away

A rejected draft leaves attention rows that are never read and then overwritten. It leaves conv rows that have already changed the state, so the engine saves a copy of each conv state for the last 33 positions and copies one back.

Draft models roll back their own conv state to the last shared token. The test shows that with the restore the logits are exact, and without it they are far off.

Numbers on this page were measured on the iQOO 13 (SM8750) in 2026 unless tagged otherwise. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
