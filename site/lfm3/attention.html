LFM3 · 03

Sliding windows, partial RoPE and per-head norms

LFM3 changes four things about attention. Five of its eleven attention layers read only the last 256 positions, and they keep a ring buffer that holds just those rows. Full-attention layers rotate only half of each head. Every attention layer normalizes q and k per head and scales each head by a gate. This page covers each change and why the 2048-token check needed its own reference.

What are we trying to do here?

Attention lets a token read the keys and values of the tokens before it. A head is one slice of 128 values of a query, key or value vector. A position is a token’s place in the sequence, counting from 0. The KV cache keeps every earlier key and value, so a new token reads them without computing them again (the KV cache).

LFM3 has 24 layers. Thirteen are short convolutions, which keep a 6-row state instead (the hybrid layout). The other eleven attend. Six read every earlier position. Five are sliding-window layers, which read only a fixed number of recent positions. Full-attention layers also rotate only part of their heads. Every attention layer normalizes and gates its heads. By the end you can say what each of these changes, what it costs in memory, and what a wrong version would get wrong.

What does a sliding-window layer look at?

Attention scores the current token’s query against the key at each position it may see, then averages the values at those positions. A full layer may see every position from 0 up to the current one, so its work grows with the prompt. A sliding-window layer sees only the last W positions, where W is its window. For LFM3, W is 256 (attention covers the full case).

A sliding layer is at position 1000 and its window is 256. Which positions does it read for this token?

  • Positions 745 to 1000, which is 256 positions with the current one
    The window counts the current token: 1000 minus 255 is 745.
  • Positions 0 to 1000, all 1001 of them
    That is a full layer. Only the sliding layers are cut to the window.
  • Positions 744 to 999, the 256 before it
    A plausible off-by-one. The code counts the current position as one of the 256.

The window is set per layer when the model is loaded. The code computes the first position in the window, then attends from there to the current position:

// src/kernels/mod.rs
let start = (pos + 1).saturating_sub(window);
let n = pos + 1 - start;
  • pos + 1 counts the current token, so the window includes it.
  • saturating_sub stops at 0. Early tokens have fewer than W earlier positions, so they read all of them.
  • A full layer passes usize::MAX as its window, so the same code reads everything.
  • The loader in src/model/gguf.rs gives the five sliding layers Some(256) and the six full layers None.

The layers run in this order, where C is a conv layer, F a full attention layer and S a sliding one:

C C F C S C F C S C F C S C F C S C F C S C F C

Six F and five S: eleven attention layers, as the plan lists them. If a sliding layer read all positions, it would be a full layer, and the model would compute different numbers from the reference from position 256 on.

Takeaway: a sliding layer reads the last 256 positions, counting the current one; a full layer reads all of them.

A window of 4 is set on a layer, and the current token is at position 3. How many earlier positions does the layer read, and is the current one among them?

  • Four positions in all, 0 to 3, the current one included
    The window is the last 4 positions, and the current position counts as one of them.
  • Three earlier positions, and the current one is not counted
    That is the off-by-one: the window counts the current position too.
  • All four earlier positions, 0 to 4
    Position 4 is in the future for this token, so no layer can read it.

How does a sliding layer keep only its window?

A full layer’s cache has one row per position: 2048 rows at context 2048. A sliding layer needs only the last 256 rows at each step, so keeping all 2048 wastes memory. A ring buffer is a fixed array of rows with a write index. Each new token writes to the next row, and after the last row the index wraps back to row 0. The oldest row is overwritten.

A ring has 8 rows. Position 19 went into row 3. The write index moves one row per token and wraps after row 7. Which row does position 26 go into?

  • Row 2
    Rows 4 to 7 take positions 20 to 23, then 24 and 25 take rows 0 and 1, so 26 takes row 2.
  • Row 3, the row position 19 used
    Rows are reused after a wrap, but position 26 comes seven steps later, not in the same place.
  • Row 8, the next row past the end
    The ring does not grow; the index wraps back to row 0.

The engine sizes a sliding layer’s cache as the window plus one prefill chunk. In src/model/transformer.rs:

Some(w) => (w + PREFILL_CHUNK).min(c.seq_len),

With W = 256 and PREFILL_CHUNK = 256, that is 512 rows (or fewer, if the context is shorter). Each token writes its row with pos % ring:

let slot = layer_off + (pos % ring) * kv_dim;
  • The ring is 512 rows, not 256, because prefill runs in 256-token chunks. The code’s comment says the ring only has to keep the window plus one chunk.
  • Decode copies the 255 earlier positions in the window out of the ring into a straight buffer, then adds the current token. Attention runs on that straight copy.
  • Attention is over the window only. A row older than the window is never read again, so overwriting it is safe.

The memory sizes follow from the code, not from a measured process size. Each position stores 512 values for K and 512 for V, since LFM3 has 4 KV heads of 128 values, and the cache holds f32 values. calculated

  • One position, one layer, K and V: 512 × 2 × 4 bytes = 4 KiB. calculated
  • A full layer at context 2048: 2048 rows × 4 KiB = 8 MiB. calculated
  • A sliding layer’s 512-row ring: 2 MiB, so 6 MiB less per sliding layer. calculated
  • The 11 attention layers take 6 × 8 + 5 × 2 = 58 MiB, against 88 MiB if all 11 were full. calculated

A ring of only 256 rows would hold a decode step’s window, because a decode step reads 255 earlier rows and the current one. The extra 256 rows are for prefill chunks. calculated

Takeaway: a sliding layer’s ring keeps the window plus one prefill chunk, 512 rows here, and wraps its write index.

Prefill writes a 256-token chunk at a time. Why must the ring hold 256 rows beyond the window, not just the 256-row window?

  • So a chunk can read the 255 earlier positions and write its own 256 rows without overwriting either
    The window plus one chunk is 511 positions, so 512 rows hold them all.
  • Because the ring length is rounded up to a power of two
    The code uses the sum of the window and the chunk; there is no rounding step.
  • For the conv layers’ state, which shares the ring
    Conv layers keep their own 6-row state; they have no ring.

Why do sliding and full layers differ past 256?

The prefix of a token is the set of earlier positions a layer can read. For position i, a full layer’s prefix is 0 to i. A sliding layer’s prefix is i minus 255 to i. For the first 256 tokens the two prefixes are the same.

At position 300, does a sliding layer see the same earlier tokens as a full layer?

  • No. The sliding layer sees positions 45 to 300, and the full layer sees 0 to 300
    300 minus 255 is 45, so positions 0 to 44 are outside the window.
  • Yes, both see the last 256 tokens
    The full layer sees every earlier token, not only the last 256.
  • Yes, the windows only matter past 2048 positions
    The window is 256, so it cuts earlier than the context length.

From position 256 on, the sliding layer has dropped its oldest tokens and the full layer has not. So the model is not the same function as one with all layers full. Positions past 255 already differ at context 512, so the 20 × 512 perplexity runs cover this too.

Context 2048 is the longest check the engine has against an outside reference. The two runs disagree, so neither settles it alone. The team ran the same chunk through Hugging Face transformers in f32. That is the pinned repository’s own code, not a second engine.

The Q4_K_M gap is between two quantized paths. The engine rounds activations to Q8_0 in blocks of 32 values; llama.cpp rounds them to Q8_K in blocks of 256. Takeaway: past position 255 the sliding and full layers see different prefixes, so a long-context check needs a reference that matches.

The engine’s BF16 PPL equals HF’s, but its Q4_K_M PPL is 0.16 above llama.cpp’s. What does that gap show?

  • The window and the RoPE are right at depth; the gap is from how each engine rounds activations for quantized dot products
    The BF16 match shows the window is right; quantized rounding differs between the two engines.
  • The sliding ring is wrong at depth, because the quantized numbers differ
    The BF16 run uses the same ring and matches HF, so the ring is not what differs.
  • Nothing can be compared once a model is quantized
    Quantized perplexities are compared all the time; the question is which part differs.

Which part of each head does RoPE rotate?

RoPE (rotary position embedding) turns the values of each head in pairs, by an angle that grows with the token’s position (RoPE). LFM3 uses the rotate-half layout: element i pairs with element i + 64 in a 128-value head. Partial RoPE rotates only some of the pairs, and leaves the rest of the head alone.

A full-attention layer rotates pairs in each 128-value head. How many of the head’s values does it rotate?

  • 64, in two blocks: values 0 to 31 and 64 to 95
    Pairs 0 to 31 each use two values, one in each half of the head.
  • 32, one per pair
    A pair is two values, so 32 pairs cover 64 values.
  • All 128, as in ordinary RoPE
    Full layers rotate half the head; the other half stays as it is.

The number of rotated pairs comes from the model file. The GGUF has a rope_freqs.weight tensor with 64 entries: 32 of 1.0, then 32 of 1e30. The loader counts the entries below 1e29 measured:

// src/model/gguf.rs
factors.iter().filter(|&&f| f < 1e29).count()
  • The count is 32 pairs, which is 64 of 128 values. The plan’s config value, partial_rotary_factor 0.5, says the same.
  • An angle divided by 1e30 is about zero, so those pairs do not turn. This is llama.cpp’s reading of the same tensor (results A0).
  • The pair i frequency is 1e6 to the power −2i/128, the frequency of a full 128-value head. The usual partial RoPE uses a 64-value head’s frequencies instead, which gives different angles.

The rotation itself, in src/kernels/scalar.rs:

let rot = rotations(pos, head_size, theta);
for head in v.chunks_exact_mut(head_size) {
    for (i, &(sin, cos)) in rot.iter().take(pairs).enumerate() {
        let (v0, v1) = (head[i], head[i + half]);
  • rot holds an angle for all 64 pairs, so each pair keeps its full-head frequency.
  • take(pairs) is the cut-off. Pairs past it are not touched.
  • Sliding layers pass pairs = head_dim / 2 and θ = 10000, so all 64 pairs turn there.

Full layers use θ = 1e6 and rotate half of each head. Sliding layers use θ = 1e4 and rotate all of it.

Takeaway: full layers rotate 64 of 128 values using a full head’s frequencies; sliding layers rotate all 128.

An engineer switches a full layer to the usual partial RoPE: the first 64 values, with a 64-value head’s frequencies. What goes wrong?

  • Its angles differ from the reference’s, so the numbers drift even though the output still reads as text
    The frequencies are part of the rotation; a different set gives different values.
  • The shapes no longer match, so the code fails to run
    Both versions produce 128 values per head, so the shapes match.
  • Nothing: only the order of the rotated values changes
    The frequencies, not just the order, decide each pair’s angle.

What do the per-head norm and gate change?

Attention starts by projecting the normed input into q, k and v. Two more steps touch them. An RMSNorm divides a vector by the root mean square of its values, then multiplies by a learned gain. A sigmoid squashes any number into the range 0 to 1. The first step normalizes q and k. The second is a gate that scales attention’s output.

The output gate is a linear layer on the 2048-value input, with one result per query head. How many gate values does one token get?

  • 16, one per query head
    Each gate value scales one head’s 128 outputs.
  • 2048, one per input value
    The gate is per head, not per channel, so the input width does not set its size.
  • 128, one per value in a head
    The 128 gains of the norm are shared by heads; the gate has one value per head.

QK-norm. The layer has a gain vector of 128 values for q (attn_q_norm) and another for k (attn_k_norm). The same gain is used for every head. Each query head is normalized over its own 128 values, and so is each of the 4 KV heads for k. The norm runs before RoPE:

if let Some(n) = &a.q_norm {
    k::rmsnorm_heads(&mut s.q, n, hs, c.norm_eps);
}
  • The order is projection, then the norm, then RoPE, then attention. The code in src/model/transformer.rs runs them in that order.
  • rmsnorm_heads normalizes each 128-value chunk separately with the same gain.

The output gate. A linear layer, attn_gate, maps the same normed input (2048 values) to 16 numbers, one per query head. The sigmoid of each number scales that head’s output after attention and before the output projection:

let s = 1.0 / (1.0 + (-g).exp());
for v in head {
    *v *= s;
}
  • One scalar scales all 128 values of its head. Because a sigmoid is between 0 and 1, the gate can only shrink a head’s output.
  • The gate reads the normed input, the same as q, k and v. The code computes it before the q, k and v projections.
  • Both steps exist only in LFM3. The loader sets qk_norm, output_gate and the sandwich norms from the lfm3 architecture.

Takeaway: q and k get a per-head RMSNorm before RoPE, and each head’s output is scaled by one sigmoid gate before the output projection.

A head’s gate input is −20. The sigmoid of that is about 0. What happens to that head’s attention output before the output projection?

  • It is almost zeroed, because the gate multiplies it by a number near 0
    A sigmoid of −20 is about 2 × 10⁻⁹, so the head’s values shrink to nearly nothing.
  • It doubles, because a gate can scale values above 1
    A sigmoid stays between 0 and 1, so the gate can only shrink a head.
  • It is replaced by the value vector unchanged
    The gate multiplies the output; it does not swap in another vector.

What you should take away

Five of LFM3’s eleven attention layers read only the last 256 positions. Their cache is a 512-row ring, and it wraps.

Past position 255 those layers and the full ones see different prefixes, so the 2048-token check needed Hugging Face in f32 as its reference. The engine’s BF16 run matches it.

Full layers rotate half of each head with a full head’s frequencies. Every attention layer normalizes q and k per head, and scales each head’s output with a gate.

Perplexity and KL numbers on this page were measured on the PC (x86) on wikitext-2, one chunk at context 2048, as recorded in results/phase-lfm3.md (A5). Memory sizes are calculated from the code.
