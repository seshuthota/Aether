What is a short convolution layer, and what does it remember?

Thirteen of LFM3’s 24 layers are not attention. Each one mixes a token with the few tokens before it, and keeps a small fixed set of vectors between tokens instead of a cache that grows with every token.

What are we trying to do here?

A convolution gives each output a weighted sum of nearby inputs. The weights are fixed numbers, one per position, called taps. The list of taps is the kernel. Slide the same kernel along a sequence and every output sees the same neighbourhood shape.

A short convolution has a few taps. It is causal: each tap looks backwards, so no output sees a token that comes after it. It is depthwise: each of the 2,048 channels has its own kernel, and channels never mix inside the convolution.

LFM3 uses short convolutions for 13 of its 24 layers. The other 11 are attention, and 5 of those attention layers look only at the last 256 positions. By the end of this page you can say what one conv layer computes per token, how big its memory is, and why it costs less than attention as the context grows.

What does one conv layer compute?

A conv layer receives one vector per token, but its output must depend on earlier tokens too.

The output for token 10 mixes in how many earlier tokens?

  • Six, tokens 4 to 9, plus token 10 itself
    The kernel has seven taps: six for earlier tokens and one for the current token.
  • All of them, tokens 0 to 9, as attention does
    Attention reads every earlier token; a short kernel has a fixed number of taps.
  • Only token 9, the one just before
    The kernel has more than two taps, so it reaches further back than one token.

The layer runs these steps on one token’s vector x, from conv_token in src/model/transformer.rs. A single in_proj matrix makes three vectors, B, C and x, and the layer multiplies them in pairs:

[b, c, x] = split3(in_proj(h))   // B, C, x
u         = b * x                // input gate
y         = conv(u, last 6 u's)  // depthwise, causal
out       = out_proj(c * y)      // output gate
  • The first * is the input gate: B scales x element by element before the convolution.
  • The second is the output gate: C scales the convolution’s result before out_proj.
  • The gates are plain products. The convolution path has no sigmoid or SiLU.
  • The width comes from the GGUF key shortconv.l_cache (src/model/gguf.rs), which defaults to 7.

The convolution itself is short_conv_step in src/kernels/mod.rs. Its doc comment says what it computes, and its loop is the whole kernel:

for ch in 0..dim {
    let mut acc = 0.0;
    for k in 0..width - 1 {
        acc += state[k * dim + ch] * weight[ch * width + k];
    }
    acc += u[ch] * weight[ch * width + width - 1];
    out[ch] = acc;
}
  • weight[ch * width + k] is channel ch’s tap k. Each channel has its own seven taps.
  • The last tap multiplies the current token’s u. The first six multiply the saved rows.
  • The loop runs over channels, not over tokens: one step handles one token.

Takeaway: a conv layer’s output is a fixed-weight sum over the current token and the six before it, wrapped in two gates.

A conv layer has width 4, so its taps are w0 to w3. Which tap multiplies the current token’s u?

  • w3, the last one
    The current token uses the last tap, at index width minus one.
  • w0, the first one
    The first tap multiplies the oldest saved row, the one furthest back.
  • w4, one past the last
    Taps are numbered from zero, so width 4 has no tap 4.

What does the conv state remember?

A token’s output needs the u of earlier tokens, and those are not in the current input. So the layer keeps some of them. That kept memory is the conv state: the saved u vectors of one layer.

After 1,000 tokens, how many rows does one conv layer’s state hold?

  • Six, always
    The state is a window of fixed size: each step drops the oldest row and adds the newest.
  • One thousand, one per token
    That is the KV cache’s rule; the conv state does not store every token.
  • One, only the latest input
    The kernel needs six saved rows to reach back six tokens.

In short_conv_step, the state update is two lines:

state.copy_within(dim..6 * dim, 0);
state[5 * dim..].copy_from_slice(u);
  • The first line moves rows 1 to 5 up to positions 0 to 4. The oldest row is overwritten.
  • The second line writes the current u into the last row.
  • The state is f32, and it is zeroed at the start of a sequence (conv_state.fill(0.0) when pos == 0).

Size, from the real dimensions: 6 rows × 2,048 channels × 4 bytes is 49,152 bytes per layer calculated. Thirteen conv layers hold 638,976 bytes, about 639 kB calculated.

Takeaway: the conv state is six saved rows per layer, shifted by one each token.

Token 3 is the fourth token of a sequence. How many of its state rows hold a real earlier u?

  • Three, for tokens 0, 1 and 2
    The state starts at zero and each token fills one row, so three rows are real.
  • Six, because the state always holds six real rows
    The rows are real only once tokens have filled them.
  • None, the rows fill only after six tokens
    Each token fills one row as it arrives, starting with the first.

How does that compare with the KV cache?

An attention layer stores a key and a value for every position, so its cache grows with the text. The KV cache is explained in the KV cache page. LFM3 has six full-attention layers, with 4 KV heads of 128 values each. The five sliding-window layers keep only 256 positions.

The context grows from 2,048 to 32,768 tokens. What happens to one conv layer’s state?

  • It stays 49,152 bytes, the same size
    Its size depends on the kernel width and channel count, not on the number of tokens.
  • It grows sixteen-fold, like the KV cache
    The KV cache holds every position; the conv state holds six rows.
  • It grows, but stops at 256 tokens
    The 256 limit belongs to the sliding-window attention layers, not the conv layers.

The KV figures are 6 layers × 4 heads × 128 values × 2 (keys and values) × 4 bytes per position, then multiplied by the position count. Storing them as f16 halves the bytes. The engine’s own storage type is not stated here.

  • The conv state is the same size at 2,048 tokens and at 32,768.
  • The KV cache at 32,768 tokens is about 1,260 times the conv state (calculated, f32).
  • Not the same as the sliding layers: their cache stops at 256 positions, which is a window, not a state.

Takeaway: the conv state is a fixed-size window; the KV cache grows by a fixed amount with every token.

Why does a conv layer need no cache of earlier tokens’ keys and values?

  • It keeps only the last six u rows, which is enough for its seven taps
    A kernel of width seven reaches back six tokens, so six rows suffice.
  • It recomputes every earlier token each step
    That would cost more than a cache; the conv layer reads only six saved rows.
  • Its output does not depend on earlier tokens
    It does depend on them, through the six saved rows.

Why is it cheaper than attention at long context?

Attention, for one token, scores the current query against every cached key, then sums the values with those scores.

At a 2,048-token context, which layer does more multiply-adds per token for its mixing step?

  • The full-attention layer, by hundreds of times
    It scores 2,048 positions for each of 16 heads; the conv kernel does seven taps per channel.
  • The conv layer, because its matrices are bigger
    The matrices are the same cost at any length; the question is the mixing step.
  • They do the same work, since both take weighted sums
    The sums differ: one has a fixed length, the other grows with the context.

Counting only the mixing step, not the matrix products around it:

  • Conv: 7 multiply-adds per channel × 2,048 channels = 14,336 per conv layer, at any context length calculated.
  • Attention: 16 heads × 128 values × 2 (scores and weighted sum) = 4,096 per position, so 8,388,608 at 2,048 positions calculated.

The matrix products are not free. in_proj and out_proj run for every token and dominate the conv layer’s cost. They do not depend on depth, so they do not make long context slower.

In the decode profile (300 greedy tokens of Q4_K_M on the phone), short_conv_step took 0.07 % of the CPU cycles. The Q4_K and Q6_K dot-product kernels, which run every matrix product including in_proj and out_proj, took 87 %, and attention took 0.9 % at that depth measured.

Takeaway: a conv layer’s mixing step costs the same at any context length; attention’s grows with it.

Attention’s mixing step is 4,096 multiply-adds per cached position. How many does it take at 4,096 positions?

  • 16,777,216
    4,096 per position times 4,096 positions, calculated.
  • 8,192
    That doubles the cost per position, but the count also grows with the positions.
  • 14,336
    That is the conv kernel’s fixed count; attention’s grows with the positions.

What you should take away

A conv layer mixes each token with the six before it, through a fixed seven-tap kernel and two gates.

Its state is six saved rows of 2,048 values, 638,976 bytes for all 13 layers, and it does not grow with the text.

Its mixing step costs the same at any context length, while attention’s grows with every token.
