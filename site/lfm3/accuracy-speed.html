Is it right, and why is it slower than llama.cpp?

Aether gives llama.cpp’s perplexity on the same files, and its prompts run as fast. Its decode does not: 26.1 tokens a second for Q4_K_M, where llama.cpp does 44.3 on the same file. This page shows the accuracy checks, the same-session speed runs, and the part of the code that takes the time.

What are we trying to do here?

Two questions. First, is the answer right? Perplexity (PPL) measures how surprised a model is by the real next word in a text. Lower is better. The reference is an outside program: llama.cpp, run on the same GGUF files. GGUF is the file format llama.cpp reads, with the weights and their quantization in one file. For full precision we use Hugging Face transformers (HF).

Second, how fast is it, and what limits it? Decode makes one new token per step. Prompt processing reads many prompt tokens at once. Both were measured on the phone, in the same session as llama.cpp.

Does Aether give llama.cpp’s perplexity?

The test text is wikitext-2, a standard collection of English articles. Each run scores 20 chunks of 512 tokens. A second measure is KL divergence against the BF16 file, a 16-bit copy of the model used as the full-precision reference. KL measures how far one model’s next-token probabilities move from another’s. Zero means identical.

On the same chunks, Aether’s Q4_K_M scores 24.8542 and llama.cpp’s scores 24.8278. What does that gap mean?

  • Nothing is wrong: each score carries a ± of about 1.1, far larger than the gap
    Two correct engines round differently, so their scores differ a little. The spread between chunks is much larger.
  • One engine has a bug, because the two numbers differ at all
    Quantized weights are rounded differently by each engine, so exact equality is not the test.
  • Aether is wrong unless it matches to four decimal places
    A four-decimal match is not the standard for a quantized file, which both engines round their own way.

Over all 20 chunks, Aether’s KL against the BF16 file is 0.115041, and llama.cpp’s is 0.117968. Both put the most likely next token in the same place 83.392 % of the time measured.

Context 2048 is harder. The model has sliding-window layers, which see only the last 256 positions, and full layers, which see everything. At 2048 the two kinds see different prefixes, so the gap between the engines is about ten times larger than at 512. Aether’s BF16 run equals HF to four decimal places, so the sliding ring, its window edge and the full layers’ rotary positions are right at depth. The Q4_K_M gap lies between two quantized paths, not in the model. Aether rounds the activations to Q8_0, one scale per 32 values. llama.cpp rounds them to Q8_K, one scale per 256. Aether’s Q4_K_M ends up slightly nearer its own BF16 run. The two BF16 runs differ from each other by 0.1 %.

Takeaway: on the PC the perplexities differ from llama.cpp by at most 0.03, and the context 2048 gap comes from rounding, not from the model.

At context 2048 the BF16 run equals HF, and the Q4_K_M runs differ. What does that tell you about the Q4_K_M gap?

  • It comes from how the quantized paths round their activations, not from the sliding window or the rotary positions
    The BF16 run already matches HF at this depth, so those parts agree.
  • llama.cpp is wrong, because HF is the reference
    HF is the reference for the full-precision run. The two quantized runs are compared with each other.
  • The Q4_K_M file is damaged, so its scores differ
    Both engines read the same Q4_K_M file. The file is not the cause.

How fast is decode against llama.cpp?

Both engines ran in one session on the same phone: cores 2 to 7 (six threads), on battery, screen on. The phone was cooled to 45 °C before each run. The order was reversed in round 2, and round 2 is the Q4_K_M round quoted here. Prompt speed is measured at three prompt lengths. Decode speed is measured at 64 new tokens.

Same file, same phone. Aether decodes Q4_K_M at 26.1 tokens a second and llama.cpp at 44.3. Where is the gap?

  • In decode: prompt speed is level with llama.cpp
    The prompts run within 0.86 to 1.01 times llama.cpp’s; only the one-token-at-a-time phase falls behind.
  • In the prompt: Aether reads prompts slowly
    The prompt numbers are level. Only decode falls behind.
  • Equally in both, because the file is the same
    A file sets the bytes to read. The speed depends on the code that reads them.

Aether reads the same 1.09 GB Q4_K_M file as llama.cpp, and decodes slower. What is the most likely cause?

  • How fast the kernels turn those bytes into products, since the bytes are the same
    The file is shared, so the gap is in the code that reads it.
  • The conv layers read extra bytes on every token
    The conv layers take 0.07 % of decode time, so they are not the extra cost.
  • The phone ran out of memory and paged out
    Available memory was 5.4 to 6.7 GB at the start of the runs, and peak RSS was 1.13 to 1.19 GB.

Where does a decode token’s time go?

A profiler (simpleperf) interrupts the CPU many times a second and records which function it is in. Each record counts the cycles, the CPU’s clock ticks, spent there. A GEMV is a matrix times a vector: the weights, times one token’s activations. Decode is a long run of GEMVs, one for each weight matrix in every layer.

The model has 13 short-conv layers, 6 full-attention layers and 5 sliding-window layers. Which part takes the most decode cycles?

  • The two K-quant GEMVs, the products over Q4_K and Q6_K weights
    The profile below shows that most of the decode cycles are in these two functions.
  • The 13 conv layers, since they are the most of the 24 layers
    A conv step touches a 6-row state, not a cache that grows. Counting layers is not counting cost.
  • Attention, because it is the part that grows with depth
    At this depth attention takes under 1 % of the cycles.

54.1 + 32.9 = 87.0, so 87 % of decode is the two K-quant GEMVs calculated. The conv layers are nearly free beside them. Why are these kernels slow? The results give the reason:

  • The activation is Q8_0: one scale for every 32 values.
  • Each 32-value sub-block of a Q4_K or Q6_K row ends in its own int-to-float conversion and float multiply-add, with its own scale.
  • Q6_K adds an integer multiply by the sub-block scale.
  • llama.cpp’s Q8_K activation has one scale per 256 values. Its sub-blocks add in int32 and convert once per 256.

So the kernels are limited by arithmetic, not by how many bytes they read. The implied rates back that up. Bytes per second is the file size times tokens a second calculated. Q4_K_M: 1.09 GB × 26.1 gives 28.5 GB/s for Aether, and 48.3 GB/s for llama.cpp at 44.3 tokens a second. QAD-Q4_0: 44.7 GB/s for Aether against 51.7 GB/s for llama.cpp.

The results name the kernels as the cause. The sustained runs above show the phone slowing in its first minute at 86 to 88 °C, which the profile does not separate from the kernel cost.

Takeaway: 87 % of Q4_K_M decode is two K-quant products limited by arithmetic on per-32 scales, not by memory bytes.

A Q4_K row of 256 values, with activations in Q8_0, is converted from integer to float how many times in the current kernel?

  • 8, once per 32-value sub-block
    256 divided by 32 is 8. Each sub-block has its own scale, so it converts on its own.
  • 1, once per 256-value block, as Q8_K allows
    That is the count with Q8_K activations, which Aether does not use yet.
  • 32, once per value
    Values are multiplied one by one, but the conversion happens once per sub-block.

What would make Q4_K_M decode faster?

The results name the fix: give the K-quant kernels activations with one scale per 256 values, as Q8_K does, so each block converts to float once. That is its own step, after this plan. A second change under way repacks the weight rows so that one load serves several rows. The work is on a branch and has no phone numbers yet, so the speeds on this page are the current ones.

Takeaway: the next speed is unknown until the new kernels are measured on the phone.

The K-quant work has no phone numbers yet. How should the 26.1 tokens a second above be read?

  • As the measured speed of the current kernels, until the new ones are measured on the phone
    A kernel’s speed counts only once it is measured on the phone.
  • As the speed the kernels will reach once the Q8_K change is in
    A planned change has no speed until it is measured.
  • As llama.cpp’s Q8_K speed on this phone
    The 44.3 is llama.cpp’s measured decode on the same file, not a Q8_K figure.

What you should take away

Aether matches llama.cpp’s perplexity on the same files, within 0.03 on the PC, and its prompt speed is level.

Its Q4_K_M decode runs at 0.59 times llama.cpp’s speed, and 87 % of decode time is two K-quant products limited by arithmetic on per-32 scales.

The fix is K-quant decode work, which has no phone numbers yet.

Numbers on this page were measured on the iQOO 13 (SM8750) or on the PC as tagged, from results/phase-lfm3.md (A5, A7). Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
