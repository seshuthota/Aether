Notes for the engine you are building

Aether is a program that runs a language model on a phone, written from scratch in Rust. These pages explain every idea behind it, in the order you meet them. The engine itself lives in src/. This site is only the explanation.

What do the number tags mean?

Every number on these pages carries one of three tags. Mixing them up is how a learning project fools itself. Here is what each one means:

TagMeans
measuredObserved on this machine or this phone. The clock cost, the sum timings, the core frequencies, the CPU feature flags.
calculatedArithmetic from a formula. 0.5 billion parameters times 4 bytes is 2 GB. The formula is the point; the number is not a benchmark.
assumptionA stand-in used to learn the shape of an idea. 30 GB/s in the tokens-per-second exercise is one of these. It is not this phone’s bandwidth.

Which pages describe finished work? Phase 0 pages do: the project builds, cargo test runs on the phone, and the timing harness and the Tensor exist. Phase 1 pages were written before its measurements, to explain what the experiments are for. The measured table now has its own page. Phases 2 to 4 are written from code that is built and checked against outside references, with the numbers measured on this phone. Phases 5 to 8 have an overview page each, and Phases 6 and 7 have their first topic pages. The course outline tracks which pages are still to write.

Takeaway: a number is only as good as its label, so read the label before you trust the number.

Why build this on a phone?

The objective is to understand inference by building it, on a phone, from scratch. A fast engine at the end is a bonus. The plan is not a race against llama.cpp.

A phone is not a smaller desktop. Its hardware sets the design:

  • Memory bandwidth, not peak FLOPs, limits token generation. A phone has far less of it than a desktop GPU.
  • RAM is small and shared with Android. The OS will kill a process that uses too much.
  • No fan. The first 10 seconds are not the speed after 5 minutes.
  • Energy. Every token costs battery. Joules per token is a first-class number, not a footnote.
  • Cores are not identical. On this phone they are all Oryon, in two frequency classes. Older Snapdragons also have efficiency cores. The plan’s general story has to be checked against this chip.
  • CPU first. Every phone has ARM NEON. GPU and NPU come later, if at all.

Where does correctness come from? Not from a second copy of our own code. Golden outputs come from outside: numpy and PyTorch for kernels, llama2.c for stories15M, Hugging Face for SmolLM2 and Qwen, llama.cpp for quantization formats. If both of our implementations share a bug, a test against ourselves cannot see it.

When is a phase finished? When the engine is correct and the numbers can be explained: where the time went, and what limited it. A kernel at 40% of measured bandwidth is a finished lesson once the missing 60% has an explanation.

Takeaway: build for the phone, check against outside references, and explain every number.

Phase 0 has six concepts, learned in order. Together they get code onto the phone, make a timing believable, and turn a tensor (a block of numbers with a shape) into an address in a flat buffer. The Phase 0 overview maps them onto the files in the repo.

What does Phase 1 teach?

Phase 1 teaches the hardware and its memory model. The plan’s success criterion is a table in results/: cache bandwidths, single-core and all-core DRAM read bandwidth (DRAM is the phone’s main memory, outside the processor), throttled sustained bandwidth, and energy per GB on the two core classes. These pages explain the concepts that table depends on. They were written before it was measured.

What does Phase 2 build?

A whole model. Every part of stories15M is written simply, checked bit for bit against llama2.c, and timed: 88.6 tokens per second on one prime core. The forward pass is the calculation that turns the tokens so far into scores for the next one. Read the pages in order; each one is one step of that pass.

Takeaway: the forward pass is a series of steps, and the whole model matches llama2.c bit for bit.

How does Phase 3 make it fast?

The model stays the same. Phase 3 makes it faster by using four floats per instruction. The pages cover dependency chains (runs of calculations where each waits for the one before), GEMV (a matrix times a vector), tails (leftover numbers that do not fill a group of four), prefill and GEMM (a matrix times a matrix). On one core, speed goes from 88.6 to 422 tokens per second.

Takeaway: the same model runs almost five times faster once its kernels use four floats per instruction.

What do threads add in Phase 4?

Phase 4 splits each matrix product across cores. It uses a pool (a set of threads that stay alive and wait for work), hands out work in blocks, and chooses which cores are worth using. For SmolLM2-135M, speed goes from 160 tokens per second on one core to 335 on six. A sweep of twelve core sets measured it, and the speed stops growing at about six cores.

Takeaway: on this phone, more cores stop helping at about six, so pick the thread count by measuring.

How do I open the site later?

From the repo root, run this command. It starts a small web server on port 8765 that serves the site folder:

python3 -m http.server 8765 --directory site

Then open http://localhost:8765/. Opening site/index.html as a file also works, because the links are relative. The typefaces load from Google Fonts when the network is up, and fall back to the system fonts when it is not. On a phone on the same Wi-Fi, use the PC’s address instead of localhost.

Later phases get a section here as their pages are written.

Do not skip ahead in the engine. The early measurements are what the later kernels get compared against.

Takeaway: serve the folder over HTTP, and read the phases in order, because the early measurements are the baseline.
