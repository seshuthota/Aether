How to read a number

Three kinds of number show up, and mixing them up is how a learning project lies to itself.

TagMeans
measuredObserved on this machine or this phone. The clock cost, the sum timings, the core frequencies, the CPU feature flags.
calculatedArithmetic from a formula. 0.5 billion parameters times 4 bytes is 2 GB. The formula is the point; the number is not a benchmark.
assumptionA stand-in used to learn the shape of an idea. 30 GB/s in the tokens-per-second exercise is one of these. It is not this phone’s bandwidth.

Phase 0 pages describe work that is finished: the project builds, cargo test runs on the phone, the timing harness and the Tensor exist. Phase 1 pages were written before its measurements, to explain what the experiments are for; the measured table now has its own page. Phases 2 to 4 are written from code that is built and checked against outside references, with the numbers measured on this phone. Why this project

The objective is to understand inference by building it, on a phone, from scratch. A fast engine at the end is a bonus. The plan is not a race against llama.cpp.

Phone hardware is the design constraint, not a smaller desktop:

  • Memory bandwidth, not peak FLOPs, limits token generation. A phone has far less of it than a desktop GPU.
  • RAM is small and shared with Android. The OS will kill a process that uses too much.
  • No fan. The first 10 seconds are not the speed after 5 minutes.
  • Energy. Every token costs battery. Joules per token is a first-class number, not a footnote.
  • Cores are not identical. On this phone they are all Oryon, in two frequency classes. Older Snapdragons also have efficiency cores. The plan’s general story has to be checked against this chip.
  • CPU first. Every phone has ARM NEON. GPU and NPU come later, if at all.

Correctness does not come from a second copy of our own code. Golden outputs come from outside: numpy and PyTorch for kernels, llama2.c for stories15M, Hugging Face for SmolLM2 and Qwen, llama.cpp for quantization formats. If both of our implementations share a bug, a test against ourselves cannot see it.

A phase is finished when the engine is correct and the numbers can be explained: where the time went, and what limited it. A kernel at 40% of measured bandwidth is a finished lesson once the missing 60% has an explanation.

Phase 2, a whole model

Every part of a real model (stories15M), written simply, checked bit for bit against llama2.c, and timed: 88.6 tokens per second on one prime core. Read in order; each page is one step of the forward pass.

Phase 3, NEON kernels

The same model, made fast with four floats per instruction: dependency chains, GEMV, tails, prefill and GEMM. From 88.6 to 422 tokens per second on one core.

Phase 4, threads

Each matrix product split across cores: a pool of threads that stay, work handed out in blocks, and which cores are worth using. From 123.9 tokens per second on one core to 274.7 on six, for SmolLM2-135M. The speed-and-energy sweep against core set is still to run.

Open it later

From the repo root:

python3 -m http.server 8765 --directory site

Then open http://localhost:8765/. Opening site/index.html as a file also works; the links are relative. The typefaces load from Google Fonts when the network is up and fall back to the system stack when it is not. On a phone on the same Wi-Fi, use the PC’s address instead of localhost.

Later phases get a section here as their pages are written. Adding a page is two steps, written up in site/README.md: copy _template.html, and add one line to js/pages.js. The menu, the previous/next links and the cards above all update from that line.

Do not skip ahead in the engine. The early measurements are what the later kernels get compared against.
