A C door into Rust

The Android app cannot call Rust directly. The engine exports a small C interface: a handle C cannot look inside, error codes instead of crashes, and a callback that streams text out and lets the caller stop it.

What are we trying to do here?

Until Phase 8 the engine was a Rust library used by a Rust command-line tool. An app needs to call it from another language. The way almost every language can call into another is the C ABI (application binary interface): the rules C uses for passing arguments, returning values and naming functions in a compiled library.

The engine’s C interface is include/aether.h (the header, the contract) and src/ffi.rs (the Rust side). Cargo builds the library a second time as a cdylib, a shared library for C callers: libaether.so.

int  aether_open(path, cores, max_seq, &session);
int  aether_open_gpu(path, max_seq, &session);
int  aether_generate(session, prompt, chat, ...,
                     on_text, user, &stats);
int  aether_set_lookup(session, k, ngram);
const char *aether_last_error(void);
void aether_close(session);

By the end you can explain each rule these functions follow, and what goes wrong without it. examples/c/smoke.c calls them from plain C, and the test ffi::tests::c_abi_round_trip drives them from Rust the way C would and reproduces llama2.c’s greedy stories15M text.

Why can’t Kotlin call Rust directly?

Kotlin on Android runs on Android’s Java runtime. Its way to call compiled code is JNI (Java Native Interface), and JNI calls C functions with C types. A Rust function is not a C function by default.

What does Rust not promise about an ordinary pub fn in a compiled library?

  • Its symbol name or how it passes arguments
    Rust mangles names and may change its calling convention between compiler versions.
  • That it exists in the library
    A public function is compiled in; the problem is that C cannot find or call it reliably.
  • That it is memory-safe
    Safe Rust is memory-safe; the boundary problem is about names and conventions.

Rust mangles function names, encoding the module path and a hash into the symbol so two functions called open do not clash. It also keeps the right to change how arguments are passed. Two annotations turn both off for one function:

#[unsafe(no_mangle)]
pub unsafe extern "C" fn aether_close(
    session: *mut AetherSession) { ... }
  • extern "C" uses the C calling convention, so a C caller passes arguments where Rust expects them.
  • #[unsafe(no_mangle)] keeps the symbol name aether_close, so the C linker finds it. It is marked unsafe because two libraries exporting the same name would clash.
  • Structs that cross the boundary, like AetherStats, are #[repr(C)]: fields in declaration order, with C’s padding. Rust otherwise may reorder fields.

Takeaway: C is the one convention both sides share, and extern "C", no_mangle and repr(C) put a Rust function or struct into it.

AetherStats loses its #[repr(C)]. What can go wrong?

  • Rust may reorder its fields, and C reads the wrong ones
    C assumes declaration order; without repr(C), Rust may put the two f64s first to save padding.
  • It no longer compiles
    It compiles; nothing checks the layout against the C header.
  • Nothing; the fields are plain numbers
    Plain fields can still be reordered; only their order in memory matters to C.

How does C hold a Rust object it cannot see?

A loaded model is a Rust value with fields, borrowed data and a lifetime. C knows none of that. The header gives C an opaque handle: a pointer to a type that is declared but never defined, so C can store it and pass it back, but never look inside.

typedef struct AetherSession AetherSession;

On the Rust side, aether_open puts the session on the heap and gives up Rust’s ownership of it:

Box::into_raw(Box::new(AetherSession {
    engine, lookup_k: 0, lookup_ngram: 2 }))

After Box::into_raw, when does Rust free the session?

  • Only when the pointer comes back through Box::from_raw
    into_raw stops Rust from dropping it; only rebuilding the Box restores ownership.
  • When aether_open returns
    That would leave C with a dangling pointer; into_raw exists to prevent it.
  • When the garbage collector runs
    Rust has no garbage collector, and Java’s cannot see native memory.
/// # Safety
/// `session` must come from `aether_open` and not
/// have been closed.
pub unsafe extern "C" fn aether_close(
    session: *mut AetherSession) {
    let _ = guard(|| {
        if !session.is_null() {
            // SAFETY: created by Box::into_raw in
            // aether_open, freed once.
            drop(unsafe { Box::from_raw(session) });
        }
        AETHER_OK
    });
}
  • Closing twice frees the same memory twice, and a pointer from anywhere else frees memory Rust never owned. Rust cannot check either; the # Safety section is the contract, and the caller must keep it.
  • Null is allowed and does nothing, so cleanup code can close a session it never managed to open.
  • Because C never sees the fields, AetherSession could gain the GPU engine and the lookup settings without changing a line of the app.

Takeaway: C holds an opaque pointer made by Box::into_raw, and must hand it back exactly once.

The Kotlin wrapper sets its handle to 0 after close(). Which bug does that prevent?

  • A second close() freeing the session twice
    Closing 0 is a null close, which the engine allows and ignores.
  • A memory leak
    The session was already freed by the first close; zeroing frees nothing.
  • A panic in Rust
    A double free is undefined behaviour, not a panic; that is why it must not happen.

What happens if Rust panics inside a C call?

A panic is Rust’s response to a bug it detects at run time, such as an index out of range. It unwinds: it walks back up the stack, running each function’s cleanup, until something catches it or the thread ends.

A panic unwinds out of aether_generate into the C code that called it. What happens?

  • Undefined behaviour: anything, from a crash to corrupted state
    C frames have no Rust cleanup information; the language makes no promise at all.
  • C receives an error code
    Only if Rust catches the panic first and returns one; unwinding by itself returns nothing.
  • The C caller’s exception handler catches it
    C has no exceptions, and Rust panics are not Java exceptions either.

So every entry point runs its body inside guard:

fn guard(body: impl FnOnce() -> c_int) -> c_int {
    match catch_unwind(AssertUnwindSafe(body)) {
        Ok(code) => code,
        Err(p) => {
            // the panic's message, if it is a string
            set_error(format!("internal error: {msg}"));
            AETHER_ERR_PANIC
        }
    }
}
  • catch_unwind stops the unwinding at this function and returns Err with the panic’s payload.
  • AssertUnwindSafe is the programmer’s claim that nothing is left half-changed in a way that matters. Rust does not check it.
  • The guard is on every function, even aether_close: any of them can reach code that panics.

Takeaway: a panic must never cross into C, so each entry point catches it and returns AETHER_ERR_PANIC.

How does C find out what went wrong?

C functions usually report failure with a number. The header defines four:

#define AETHER_OK           0
#define AETHER_ERR_ARGUMENT 1 /* null, non-UTF-8,
                                 prompt too long */
#define AETHER_ERR_LOAD     2 /* file missing, bad */
#define AETHER_ERR_PANIC    3 /* a bug */

A number cannot say which file was missing. The message is stored separately, in a thread-local variable (one copy per thread), and aether_last_error() returns it.

Why per thread, and not one global message?

  • Two threads failing at once would overwrite each other’s message
    With one copy per thread, each caller reads its own last error.
  • Global variables are not allowed in Rust
    Rust allows them (with synchronisation); the problem is two writers, not the language.
  • It is faster
    Errors are rare; correctness, not speed, is the reason.
  • The returned pointer is valid until the next call on the same thread. A caller that needs it later must copy it; the JNI shim copies it into a Java IOException at once.
  • Too-long prompts are caught before any work: aether_generate encodes the prompt and fails with AETHER_ERR_ARGUMENT if prompt plus max_tokens exceeds the context, with both numbers in the message.
  • Strings from C must be NUL-terminated UTF-8, and are only read during the call. Bad UTF-8 is an argument error, not a panic.

Takeaway: the code tells the caller what kind of failure it was, and the per-thread message tells it the details.

aether_open is given a path to a file that does not exist. What does it return?

  • AETHER_ERR_LOAD, with the path in the message
    A missing or unreadable model is a load error; the message names the file.
  • AETHER_ERR_ARGUMENT
    The argument is a valid string; it is the file behind it that is missing.
  • AETHER_ERR_PANIC
    A missing file is an expected failure, handled as an error, not a bug.

How does text get out while it is being generated?

A reply takes seconds. The app wants each piece as soon as it exists, not the whole text at the end. So aether_generate takes a callback: a pointer to a function that the engine calls once per piece of text.

typedef int (*AetherTokenCallback)(
    const uint8_t *bytes, size_t len, void *user);

C has no closures. How does the callback reach the app’s own state, such as which text view to update?

  • Through the user pointer, passed in and handed back unchanged
    The engine never looks at it; it is the caller’s way to carry context into the callback.
  • Through a global variable
    That works for one caller, and breaks as soon as two exist.
  • The engine stores the app’s state
    The engine knows nothing about the app; it only passes the pointer through.
  • The pieces are bytes, not text. A token can end in the middle of a multi-byte character, so the header says the next piece completes it. The app page shows how the app puts the halves together.
  • The return value is the stop signal: non-zero means “go on”, 0 means “stop”. The app’s Stop button sets a flag, the callback returns 0, and the engine stops at the next token.
  • The callback runs on the thread that called aether_generate. That matters to JNI, whose environment pointer is only valid on its own thread.
  • When the call returns, stats (if not null) holds the prefill and decode token counts and times.

Takeaway: the callback streams bytes out, the user pointer carries the caller’s state in, and the return value lets the caller stop.

A callback always returns 1, and the user taps Stop. What happens?

  • Generation runs on until max_tokens or end of text
    The return value is the only stop signal the engine reads.
  • It stops at once
    The engine cannot see the button; it only sees what the callback returns.
  • The engine panics
    Nothing has gone wrong from the engine’s side; it keeps generating.

What you should take away

C is the shared convention: extern "C", no_mangle and repr(C) put Rust into it, and the header is the whole contract.

C holds an opaque handle and gives it back once; panics are caught at the door and become error codes.

A callback streams bytes out, and its return value is how the caller stops the engine.
