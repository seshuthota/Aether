Inside the Android app

The app is one screen of Kotlin over a small C shim. Three things need care: text crosses from Kotlin to C as real UTF-8, the engine runs on one background thread of its own, and characters split across tokens are held back until they are whole.

What are we trying to do here?

The plan’s test for Phase 8 is an installable app that streams a chat reply at the same speed as the command-line tool. The app is deliberately small: a model list, a prompt box, a few settings (cores, chat template, lookup, GPU), a Generate/Stop button and the reply.

Android apps are written in Kotlin and run on Android’s Java runtime. The engine is a Rust library with a C interface. This page follows one tap of Generate through the layers between them, and then asks what the app costs in memory and speed. The code is in android/; build steps are in android/README.md.

How does a Kotlin call reach the engine?

A call goes through three layers, and two shared libraries:

Kotlin  Aether.kt: external fun nativeGenerate(...)
  |        JNI
libaether_jni.so  aether_jni.c: converts types
  |        C ABI (include/aether.h)
libaether.so      the Rust engine (src/ffi.rs)
  • JNI looks a native method up by a fixed name, such as Java_dev_aether_chat_Aether_nativeGenerate. The shim provides those names and calls the plain aether_* functions.
  • scripts/android-native.sh builds both libraries into the app’s jniLibs/arm64-v8a folder.
  • An error code becomes a Java IOException carrying aether_last_error(), so Kotlin handles failures with ordinary try/catch.

JNI has GetStringUTFChars to turn a Java string into C bytes. Why does the app pass prompt.toByteArray() instead?

  • JNI’s function gives “modified UTF-8”, which writes emoji and NUL differently
    The engine expects real UTF-8; modified UTF-8 would change the bytes, and so the token ids.
  • Byte arrays are faster to pass
    Speed is not the reason; a prompt is copied once either way.
  • C cannot hold Java strings
    Both routes give C a byte buffer; what differs is the encoding inside it.

“Modified UTF-8” is Java’s internal variant: it writes the NUL character as two bytes, and characters outside the basic plane, like most emoji, as two 3-byte halves instead of one 4-byte sequence. A prompt with an emoji would reach the tokenizer as bytes the model never saw in training. Kotlin’s toByteArray() gives standard UTF-8, and the shim copies it into a NUL-terminated C string.

Takeaway: three layers lead from Kotlin to Rust, and strings cross as real UTF-8 bytes, not as JNI strings.

Which thread runs the engine?

Android draws the screen and handles taps on one thread, the UI thread (main thread). If it is busy for about five seconds, Android shows “app isn’t responding”. A reply takes several seconds, so the engine cannot run there.

The app runs each Generate on a fresh background thread. What can go wrong with the engine?

  • Two generates could use one session at once, which the engine forbids
    The header says a session must not be used from two threads at the same time.
  • Nothing; any background thread is fine
    A second tap while the first runs would start a second thread on the same session.
  • The callback could not update the screen
    That is solved by posting to the UI thread, whatever thread runs the engine.
// Every engine call runs on this one thread.
private val engine =
    Executors.newSingleThreadExecutor()

engine.execute {
    session = Aether.open(file.path, coreList, MAX_SEQ)
    val st = session!!.generate(text, ...) { bytes ->
        val piece = utf8.feed(bytes)
        ui { output.append(piece) }
        !stop.get()
    }
}
  • A single-thread executor runs its tasks one after another on one thread, so the session is never used twice at once.
  • Open and generate run on the same thread on purpose. The engine pins the thread that opens a session to the fastest core, and that thread then does the work of generate.
  • The callback runs on the engine thread, so it posts each piece to the UI thread with runOnUiThread (the ui { } helper). Views may only be changed there.
  • stop is an AtomicBoolean: the Stop button sets it on the UI thread, and the callback reads it on the engine thread and returns false.

Takeaway: one background thread owns the engine, and the UI thread only shows text and sets the stop flag.

Why is stop an AtomicBoolean and not a plain var?

  • It is written on one thread and read on another
    Atomic access makes the UI thread’s write visible to the engine thread.
  • Kotlin forbids plain booleans in lambdas
    Lambdas can capture plain vars; the issue is two threads, not the lambda.
  • It is faster
    It is not faster; it is correct across threads.

How do you show half an emoji?

The engine streams bytes, and a token can end inside a character: an emoji is four bytes, and the model may produce it as two tokens of two bytes each. Decoding each piece on its own would show two broken symbols instead of one emoji.

The first piece is the first two bytes of an emoji. What should the app show after it?

  • Nothing yet, and keep the two bytes
    They are not a character yet; the next piece will complete them.
  • A replacement character, �, for now
    Then the next piece would add a second �, and the emoji would never appear.
  • The two bytes as Latin-1 letters
    That shows the wrong characters; the bytes only mean something together.
class Utf8Stream {
    private val decoder = Charsets.UTF_8.newDecoder()
        .onMalformedInput(CodingErrorAction.REPLACE)
    private var pending = ByteArray(0)
    fun feed(bytes: ByteArray): String {
        val input = ByteBuffer.wrap(pending + bytes)
        val out = CharBuffer.allocate(input.remaining())
        decoder.decode(input, out, false)
        pending = ByteArray(input.remaining())
            .also { input.get(it) }
        return out.flip().toString()
    }
}
  • decode(..., false) means “more input may follow”: the decoder converts every complete character and stops before an incomplete one, without calling it an error.
  • Whatever it did not consume stays in pending and is put in front of the next piece.
  • REPLACE handles bytes that can never be valid UTF-8: they become �, not an exception.
  • There is no final flush. If a reply ended inside a character, the held bytes would be dropped silently. The model rarely stops there, so this is a gap to close, not an observed bug.

Takeaway: the engine streams bytes, and the app holds back the unfinished end of each piece until the character is whole.

Pieces arrive as: “a” plus the first byte of “é”, then the second byte of “é” plus “b”. What do the two feed calls return?

  • “a”, then “éb”
    The lone first byte of é waits in pending until the second byte arrives.
  • “a�”, then “�b”
    That is what decoding each piece alone would give.
  • “”, then “aéb”
    “a” is complete, so it is returned at once; only é waits.

How much memory does the model take on the phone?

A phone shares its RAM between every app and Android itself, and Android stops apps that use too much. The engine’s memory has two kinds. The weights come from a memory-mapped file (mmap): file-backed pages that Android can drop and re-read. Everything else (the KV cache, the activations, the tokenizer’s tables) is anonymous heap memory that exists only in RAM.

Qwen2.5-0.5B in Q4_0 has 278 MB of weights. The CLI’s peak resident memory was measured. Roughly what was it?

  • About 350 MB
    The weights, plus tens of megabytes of KV cache, buffers and tables.
  • About 278 MB, the weights alone
    The KV cache and working buffers are real memory too.
  • About 1 GB
    That would be the weights widened to f32; a Q4_0 file is used as it is.

The measured peak resident set (VmHWM, the most RAM the process held at once) was 348 MB on cores 2–7 and 349 MB on cores 6–7 measured, in the Phase 7 benchmark. For Q8_0, with 525 MB of weights, it was 589 MB measured.

  • About 70 MB is not weights. The KV cache is the biggest part that grows with context: Qwen2.5-0.5B stores 24 layers × 2 key/value heads × 64 numbers × 2 (keys and values) × 4 bytes = 24 KB per token in f32, so the app’s 2,048-token limit means up to 50 MB calculated.
  • Resident memory counts mapped weight pages once they are touched, but Android can drop those first. The anonymous part is what the low-memory killer weighs against the app.
  • The app’s own memory has not been measured. These are CLI numbers, and the app adds the Java runtime and its views on top.

Takeaway: the model costs its weights plus about 70 MB, and only the non-weight part is memory the phone cannot take back.

The app raises its limit from 2,048 to 8,192 tokens. How much more f32 KV cache can a full context need for Qwen2.5-0.5B?

  • About 150 MB more
    24 KB per token × 6,144 extra tokens ≈ 151 MB.
  • None; the cache size is fixed by the model
    The cache is sized by max_seq, which the caller chooses.
  • About 4 times the weights
    The cache grows with tokens, not with the weights; 8,192 tokens need about 200 MB.

Does the app slow the engine down?

The app and the CLI call the same engine. The only extra work in the app is JNI, one callback per token and a text view update, each a tiny cost next to a 10 ms decode step. On 2026-10-22 both ran the same prompt (“Why is the sky blue?”, 35 tokens with the chat template), on cores 2–7, at temperature 0.7, in one session:

RunPrefill, 35 tokensDecode
App, 1st after load262 ms measured94.6 tok/s measured
App, 2nd and 3rd205, 200 ms measured100.4, 93.6 tok/s measured
CLI, two seeds216, 215 ms measured98.0, 103.9 tok/s measured
  • The decode ranges overlap, which is run-to-run spread: the app does not slow the engine down.
  • The first prefill is slower because it is the first touch of the mapped weight pages, which are read from storage then.
  • Another app was playing a video in picture-in-picture during these runs, so the absolute speeds are below Phase 7’s; both sides ran under the same load. The numbers come from a debug build; the release build has not been measured.

Takeaway: once warm, the app runs at the CLI’s speed; only its first reply pays for reading the weights from storage.

Say one callback, with its JNI call and the UI post, costs 20 µs. At 100 tokens per second, how much does it slow decode?

  • About 0.2 %, far inside the run-to-run spread
    A step takes 10 ms; 20 µs is a fiftieth of a percent of it, times ten.
  • About 20 %
    That mixes up microseconds and milliseconds; 20 µs is 0.02 ms.
  • It cannot be known without measuring the app
    Measuring confirms it, but the arithmetic already bounds the cost.

What you should take away

Kotlin reaches Rust through a JNI shim and the C interface; strings cross as real UTF-8 bytes.

One background thread owns the engine; the UI thread shows text and sets the stop flag; unfinished characters wait for the next piece.

The model costs its weights plus about 70 MB, and once warm the app runs at the CLI’s speed.

Phase 8 numbers were measured on the iQOO 13 (SM8750) in October 2026 unless tagged otherwise. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
