Phase 8 · the app

Built and verified

The engine is a shared library with a C interface (include/aether.h), and a one-screen Android app calls it through a small C shim. A debug build was installed on the iQOO 13 and ran Qwen2.5-0.5B-Instruct Q4_0. The reply streamed in token by token and ended at the model's end-of-turn token. Once warm, the app's speed matched the command-line tool within run-to-run spread. This overview covers what was built and measured; the topic pages go deeper: the C interface and the Android app.

Phase 8 — on the phone, in an app

Everything so far ran from a shell. Phase 8 puts the engine inside an app: a text box, a reply that appears as it is written, and a background thread so the screen does not freeze. The engine is written in Rust, and Android apps are written in Kotlin. The two need a common language in between, and that language is C.

Why a C interface?

Kotlin code on Android runs on Android's Java runtime, and the way it calls native code is JNI, the Java Native Interface. JNI calls C functions, using C types. It cannot call Rust directly, because Rust does not promise the layout of its types or the names of its functions, unless you ask it to. C is the one language both sides agree on, so the engine exports a C interface and the app talks to that.

The interface is small on purpose. include/aether.h declares five functions and two structs. Anything Kotlin needs goes through them, and nothing else is exposed.

Illustration

Think of a plug and a socket. Kotlin has one socket shape (JNI, C types), Rust has another, and the C header is the adaptor between them. Neither side has to know the other's internals.

Takeaway: C is the shared language between the Kotlin app and the Rust engine, and the header is the whole contract.

How does C hold a Rust object?

A loaded model is a Rust value with fields, borrowed data and a lifetime. C cannot understand any of that, so it gets an opaque handle: a pointer to a type whose contents it never looks inside. The header declares the type without a body:

typedef struct AetherSession AetherSession;   /* the handle: C never sees inside */

int aether_open(const char *path, const char *cores, uint32_t max_seq, AetherSession **out);
void aether_close(AetherSession *session);

On the Rust side, the same name is a struct that wraps the real session:

/// What C holds: a loaded model.
pub struct AetherSession(Session);
  • C only passes the pointer back. It cannot read a field, so the layout can change without breaking the app.
  • aether_open makes the object with Box::into_raw, which gives up Rust's ownership and returns a raw pointer. Nothing frees it unless someone calls the matching close function.
  • aether_close takes the pointer back with Box::from_raw and drops it. Calling it twice, or on a pointer from elsewhere, is a bug in the caller. The contract in src/ffi.rs says the handle must be handed back to aether_close exactly once.

The function that frees the handle shows how the contract is written down. Its comment says what the caller must guarantee, and the one unsafe line says why the code is allowed to free:

/// Frees a session. Null is allowed (does nothing).
///
/// # Safety
/// `session` must come from `aether_open` and not have been closed.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn aether_close(session: *mut AetherSession) {
    let _ = guard(|| {
        if !session.is_null() {
            // SAFETY: created by Box::into_raw in aether_open, freed once.
            drop(unsafe { Box::from_raw(session) });
        }
        AETHER_OK
    });
}
  • extern "C" makes the function use the C calling convention. #[unsafe(no_mangle)] keeps its name as written, so the C linker can find it.
  • unsafe extern marks the function as one whose safety depends on the caller. Rust cannot check a pointer that came from C.
  • The SAFETY comment on the one unsafe line states the single fact that makes it sound: the pointer came from Box::into_raw, and it is freed once. If the app freed it twice, the program would crash or corrupt memory.
  • A null pointer is allowed, so an app that never opened a model can close it safely.

Takeaway: C gets an opaque pointer, and the rule "open once, close once" is written in the comment and enforced by no one else.

How does a Rust panic stay out of C?

A Rust panic is a crash in progress: a bug, such as an index out of range, that stops the current code. Normally it unwinds the stack and ends the thread. If it unwinds into C, the C code has no idea how to clean up, and the behaviour is undefined. The file header says so directly: "a Rust panic unwinding into C is undefined behaviour". So every entry point runs its body inside a guard:

/// Runs `body`, converting a panic into `AETHER_ERR_PANIC`.
fn guard(body: impl FnOnce() -> c_int) -> c_int {
    match catch_unwind(AssertUnwindSafe(body)) {
        Ok(code) => code,
        Err(p) => {
            let msg = p.downcast_ref::<&str>().map(|s| s.to_string()).or_else(|| p.downcast_ref::<String>().cloned()).unwrap_or_else(|| "panic".into());
            set_error(format!("internal error: {msg}"));
            AETHER_ERR_PANIC
        }
    }
}
  • catch_unwind runs the closure and returns Err if it panicked, instead of letting the panic travel further.
  • AssertUnwindSafe is a promise that the closure's state is safe to use afterwards. It is the programmer's claim, not a check.
  • The panic's message is pulled out of the payload and stored, so the app can show what went wrong.

Errors go back as codes, and the message goes in a separate call. The header defines four codes, and the app can branch on them:

#define AETHER_OK          0
#define AETHER_ERR_ARGUMENT 1  /* null / non-UTF-8 argument, prompt too long */
#define AETHER_ERR_LOAD    2   /* model file missing or unreadable */
#define AETHER_ERR_PANIC   3   /* internal error (a bug); see aether_last_error */

const char *aether_last_error(void);
  • Zero means success, so if (code != AETHER_OK) is the whole check.
  • The message is kept per thread. Calling aether_last_error on another thread gives that thread's last error, not this one's.
  • The message stays valid only until the next call on the same thread. Copy it if you need it later.

Every function in src/ffi.rs has this shape: guard, check the pointers, do the work. A prompt that is too long becomes AETHER_ERR_ARGUMENT, not a crash.

Takeaway: a panic becomes an error code at the boundary, so C never sees Rust's unwinding.

How does Kotlin reach the engine?

The path has three hops. Kotlin calls a native method. JNI calls a C function in a small shim. The shim calls the C ABI, which runs the Rust engine. The diagram is in android/README.md:

Kotlin (MainActivity, Aether.kt)
  |  external fun nativeGenerate(...)          JNI
  v
libaether_jni.so   app/src/main/cpp/aether_jni.c   byte[] <-> char*, callbacks
  |  aether_generate(...)                      C ABI, include/aether.h
  v
libaether.so       the Rust engine (src/ffi.rs)
  • There are two libraries. libaether.so is the engine, and libaether_jni.so is the shim. scripts/android-native.sh builds both into the app's jniLibs folder.
  • The shim converts types. Kotlin strings become byte[] holding UTF-8, because JNI's own string functions use a different encoding for some characters.
  • Errors cross back as a Java IOException carrying aether_last_error().

Generated text arrives through a callback. The app passes a function pointer and a context pointer, and the engine calls the function once per piece of text. The shim's callback is short:

static int on_text(const uint8_t *bytes, size_t len, void *user) {
    struct callback *cb = user;
    JNIEnv *env = cb->env;
    if (len == 0) return 1;
    jbyteArray a = (*env)->NewByteArray(env, (jsize)len);
    (*env)->SetByteArrayRegion(env, a, 0, (jsize)len, (const jbyte *)bytes);
    jboolean go = (*env)->CallBooleanMethod(env, cb->target, cb->on_text, a);
    (*env)->DeleteLocalRef(env, a);
    /* A Kotlin exception stops generation; it is rethrown on return. */
    return !(*env)->ExceptionCheck(env) && go;
}
  • The user pointer carries the JNI environment and the Kotlin object. C has no closures, so this is how state gets to the callback.
  • The engine calls the callback on the thread that called aether_generate. JNI's environment is only valid on its own thread, so this matters.
  • The return value is the stop signal. Returning 0 stops generation. A Kotlin exception also stops it, because the callback returns 0 when one is pending.

Takeaway: the callback is how the engine streams text out, and the return value is how the app stops it.

How is text streamed without broken characters?

A model does not produce characters. It produces tokens, and a token is a few bytes of UTF-8 text. An emoji is four bytes, and a token can end in the middle of it. If the engine decoded each token as a string, a character split across two tokens would show up as two broken halves. So the engine does not decode at all. It hands out bytes, and says so in its comment:

/// Bytes to print for `next` following `prev`. (Bytes, not text: one
/// character can be split across tokens.)
pub fn piece(&self, prev: usize, next: usize) -> Vec<u8> {

The engine's own Tokenizer::decode turns a whole list of tokens into a string, and it replaces broken bytes with U+FFFD, the replacement character. That is right for a finished reply, but wrong for a stream. The app's Kotlin class keeps the unfinished bytes until the next piece arrives. Here it is, shortened to the parts that matter:

class Utf8Stream {
    private val decoder = Charsets.UTF_8.newDecoder()
        .onMalformedInput(CodingErrorAction.REPLACE)
        .onUnmappableCharacter(CodingErrorAction.REPLACE)
    private var pending = ByteArray(0)

    fun feed(bytes: ByteArray): String {
        val input = ByteBuffer.wrap(pending + bytes)
        val out = CharBuffer.allocate(input.remaining())
        decoder.decode(input, out, false)
        pending = ByteArray(input.remaining()).also { input.get(it) }
        return out.flip().toString()
    }
}
  • pending + bytes puts the bytes left over from last time in front of the new piece.
  • decode(..., false) means "more input may follow". The decoder converts every complete character and stops at an incomplete one, without marking it as an error.
  • pending keeps whatever the decoder did not consume, so the next call can finish the character.
  • REPLACE handles bytes that are never valid UTF-8, so a bad byte gives a replacement character, not an exception.
Illustration

An emoji is four bytes. Say the first token carries the first two and the next token carries the last two. The first call returns nothing and keeps two bytes. The second call sees all four, and returns the emoji once.

Takeaway: the engine streams bytes, and the app holds back the unfinished tail of each piece.

One thing this code does not do: there is no flush when generation ends. If a reply stopped inside a character, the held bytes would be dropped, and nothing in the code would report it. The model rarely ends mid-character, so this is a gap to close, not a known bug.

How fast is the app?

The app and the command-line tool run the same engine, so the test is whether the app adds any cost. On 2026-10-22 the same prompt, cores and sampling were run in the app and in the CLI, in the same session. Prefill is the prompt's 35 tokens. Decode is the reply:

Conditions: on battery (54 %). Another app was playing a picture-in-picture video during these runs, so the absolute speeds are below the Phase 7 numbers on the same phone. The app and the CLI ran under the same load.

  • Once warm, the app matches the CLI. The app's decode lies between 93.6 and 100.4 tok/s, and the CLI's between 98.0 and 103.9. The ranges overlap, which is the run-to-run spread.
  • The first generate is slower. The model is memory-mapped, so each page is read from storage the first time it is touched. That happens during the first prefill, so the 262 ms includes the reads. This is not a cold-start time for the app.
  • No memory number yet. The results file has speeds only. The Phase 7 peak memory figures are for the CLI, not for the app.

Takeaway: the app does not slow the engine down, and the first reply is slower only because the model's pages are loaded on first use.

What is still open?

These are the gaps the phase leaves. Each is a measurement or a check that has not been done, not a known fault.

  • Release build. The numbers come from a debug APK. The release build is signed with the debug key and has not been measured.
  • Memory. The app's memory use is not recorded in results/phase-8.md.
  • Loading from shared storage. android/README.md notes that shared storage goes through Android's FUSE layer, and gives an alternative path. The two paths have not been timed against each other.
  • End of a reply. The UTF-8 stream has no flush, as described above.

Takeaway: the app's speed is measured; its memory, its release build and its load paths are not.

Check yourself

Why does the engine need catch_unwind at every entry point, rather than just in the ones that load a model?

Because any call can panic: a bad prompt, an index out of range, or a bug in a kernel. A panic that reaches C is undefined behaviour, and it can happen in any function, so every entry point has the guard.

The app gets a token that holds only the first two bytes of an emoji. What does Utf8Stream do, and what would go wrong if it decoded each piece on its own?

It keeps the two bytes in pending and returns an empty string. When the next piece brings the other two bytes, it decodes all four together and returns the emoji. Decoding each piece on its own would turn each half into a replacement character, so the emoji would appear as two broken symbols.

Why does aether_generate need the callback's return value?

It is the only way for the app to stop the engine part way through. The Stop button sets a flag, the callback returns 0, and the engine stops at the next token. Without the return value, the app could not stop a reply once it had started.

What you should take away

C is the common language. The header is a small, explicit contract, and the code behind it guards every call.

Text streams as bytes, and the app holds back the unfinished characters until they are complete.

Once warm, the app runs at the CLI's speed. Its memory, release build and load paths are the next things to measure.
