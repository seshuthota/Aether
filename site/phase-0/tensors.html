Tensors

A tensor here is not a nested list. Memory is a line. The shape is how you interpret that line, and the strides are how far you jump to take one step along each dimension. This module addresses elements. It does not add them.

Is a 2×3 grid stored as a grid?

No. A 2×3 grid of numbers is stored as one line of six f32s (4-byte floats). RAM has no rows or columns. The tensor adds metadata, the shape and strides, that turn a (row, col) position into an offset from the start of the line. One allocation with contiguous elements is what later kernels walk. Nested Vec<Vec<f32>> would cost a pointer chase per row (following an address stored in memory to reach the next item), and the rows might not sit next to each other.

Sizes and indices are usize, an unsigned integer that is never negative. A slice is indexed with usize.

Takeaway: a tensor is one contiguous line plus the shape and strides that read it.

Which neighbor is next in memory?

Neighbors in a grid are not always neighbors in memory. Row-major, also called C order, means the last dimension varies fastest. For shape [2, 3] filled with 0, 1, 2, 3, 4, 5, the first row sits in slots 0, 1 and 2, and the second row in slots 3, 4 and 5.

Column-major, Fortran order, is the other convention: the first index varies fastest, so (r, c) lives at c × rows + r. Same six numbers, different neighbor relation. This Tensor is row-major only. The stride field is what would let a later view look column-major without copying. That view is not written.

Takeaway: in row-major order the last index walks adjacent memory, and a step to the next row skips a whole row.

How far do you jump for each index?

Each index needs a jump size. A stride is how many buffer slots you skip to advance one step along a dimension. For row-major layout, each stride is the product of the sizes to its right (the sizes multiplied together), and the last stride is 1.

A worked example, shape [4, 5, 6]: 4 slabs, each with 5 rows of 6 numbers. Build the strides from right to left:

  1. Last dimension, size 6, stride 1. One step along dim 2 is one element.
  2. Dim 1 has stride 1 × 6 = 6. One step along dim 1 skips a row.
  3. Dim 0 has stride 6 × 5 = 30. One step along dim 0 skips a 5×6 slab.

So position (2, 3, 1) is 2×30 + 3×6 + 1×1 = 79 calculated. That is the test index_of_2_3_1_is_79. The general formula is a dot product: each index times its stride, added up. A fourth dimension adds one more term, and every earlier stride is multiplied by the new last size.

row_major_strides builds the list right to left. It starts from a vector of ones, so the last dimension keeps stride 1, and it walks every index except the last. saturating_sub(1) keeps that walk empty for a scalar ([]) and a vector. A plain len() - 1 would underflow (go below zero, which a usize cannot hold) on [].

Takeaway: each stride is the product of the sizes to its right, and len() - 1 breaks on an empty shape.

Can you transpose without copying?

Swapping the axes of a tensor can avoid a copy, if the strides say so. Reverse the shape [4, 5, 6] to [6, 5, 4] and the strides [30, 6, 1] to [1, 6, 30], together. You read the same bytes in a different order, and no data moves. Element (1, 3, 2) of the transposed view is 1×1 + 3×6 + 2×30 = 79, the same slot as (2, 3, 1) in the original. That is a transpose once strides are real metadata, not recomputed from the shape on every access. Tick “view as transpose” in the lab above to see it in 2D.

Why care: reading memory with stride 1 is fast, and jumping around is slow. Weight matrices get stored in the order the kernel reads them, because the layout is part of the speed. Phase 1 measures how large that gap is. The field is stored now so index does not have to change when views arrive. Views have not arrived.

Takeaway: a transpose is a change of strides, so the same bytes are read in a new order.

What does the Tensor struct hold?

Three fields: shape, strides, and data: Vec<f32>. Every constructor must keep two invariants, rules that are always true of a valid value:

  • shape.len() == strides.len()
  • data.len() == shape.iter().product()

zeros hands its work to from_vec, so the length check and the stride build happen in one place. from_vec moves the buffer in and does not reorder elements. A length mismatch panics. That is a programming error, and a silent wrong read would be worse.

numel (the element count) returns data.len() rather than a fresh product. The constructors already forced them to agree. size_bytes is numel × size_of::<f32>(), which is 4 today. A 1000×1000 tensor is 1,000,000 elements and 4,000,000 bytes. A 4096×4096 tensor, the one main prints, is 64 MiB calculated. That is one weight matrix, not a model.

get and set go through index. set resolves the index before the write, so the read-only hold on self that index takes ends before data is borrowed mutably. The split is for the reader; one line would compile the same.

Clone is a deep copy of the metadata and the whole buffer. PartialEq compares shape, strides, and values.

Takeaway: shape, strides and data must always agree, and the constructors enforce it.

What happens at the edges?

Empty and out-of-range shapes can break naive code, so each edge has a defined answer.

ShapeWhat happensWhy that is right
[]numel is 1, strides []The product of no dimensions is 1. A scalar is one element, not zero.
[7]strides [1]A vector is already contiguous.
[0, 5]numel is 0, strides [5, 1], any index panicsThe product includes a 0. No position is valid when a dimension has size 0. An empty tensor cannot be indexed.
[2, 3] with 5 elementsfrom_vec panicsRejected at construction, before any accessor trusts the shape.
[2, 3] index [0, 3]panics, “out of range”Dim 1 has size 3. Index 3 is one past the end. Computing a flat offset anyway would read a neighbor or off the buffer.

Alignment is not handled here. Vec<f32> guarantees 4-byte alignment (the address is a multiple of 4), because that is align_of::<f32>(). NEON wants 16. A cache line is 64. The fix is Phase 1’s job, described in alignment. Do not “fix” it inside Tensor until the allocator exists and a benchmark shows the difference.

Takeaway: empty and out-of-range shapes have defined answers, and alignment waits for Phase 1.

Check yourself

Where is (2, 3, 1) in a row-major [4, 5, 6] tensor?

Strides [30, 6, 1]. Flat index 79. If you got 79 by a different grouping, check that a step on dim 0 really skips 30 and not 4.

What should Tensor::zeros(&[3, 4]).strides() be?

[4, 1]. Three rows of four. The last dimension is contiguous. That assertion is in the repo and passed on the phone.

Why store strides if they are a pure function of the shape today?

So index is already written against the field. A transpose or a slice changes strides without changing the rule in index. Recomputing from the shape on every access would make those views impossible without a copy.

What you should take away

A tensor is one contiguous line of numbers, with a shape and strides that say how to read it.

Each stride is a product of sizes, so a flat index is a dot product of the position and the strides.

A transpose changes only the strides, so no data moves.
