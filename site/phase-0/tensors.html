Tensors

A tensor here is not a nested list. Memory is a line. The shape is how you interpret that line, and the strides are how far you jump to take one step along each dimension. This module addresses elements. It does not add them.

Memory is a line

A 2×3 grid of numbers does not exist as a grid in RAM. It exists as six f32s in a row, plus metadata that turns (row, col) into an offset. One allocation, contiguous elements. Later kernels want to walk that line. Nested Vec<Vec<f32>> would be a pointer chase per row, and the rows might not even sit next to each other.

Sizes and indices are usize. They are never negative, and usize is what a slice is indexed with.

Row-major

Row-major, also called C order, means the last dimension varies fastest. For shape [2, 3] filled with 0, 1, 2, 3, 4, 5:

Column-major, Fortran order, is the other convention: the first index varies fastest, so (r, c) lives at c × rows + r. Same six numbers, different neighbor relation. This Tensor is row-major only. The stride field is what would let a later view look column-major without copying. That view is not written.

Strides

A stride is how many buffer slots you skip to advance one step along a dimension. For row-major layout, each stride is the product of the dimension sizes to its right, and the last stride is 1.

A worked example, shape [4, 5, 6]. Picture it as 4 slabs, each slab 5 rows, each row 6 numbers:

  1. Last dimension, size 6, stride 1. One step along dim 2 is one element.
  2. Dim 1 has stride 1 × 6 = 6. One step along dim 1 skips a row.
  3. Dim 0 has stride 6 × 5 = 30. One step along dim 0 skips a 5×6 slab.

Position (2, 3, 1) is 2×30 + 3×6 + 1×1 = 79 calculated. That is the test index_of_2_3_1_is_79. The general formula is the dot product of the position and the strides. It does not change when you add a fourth dimension. You add one more term, and every earlier stride is multiplied by the new last size.

row_major_strides fills this right to left. It starts from a vector of ones, so the last dimension keeps stride 1, and walks every index except the last. saturating_sub(1) keeps that walk empty for a scalar ([]) and a vector. A plain len() - 1 would underflow on [].

Transpose without a copy

Reverse the shape [4, 5, 6] to [6, 5, 4] and the strides [30, 6, 1] to [1, 6, 30], together, and you read the same bytes in a different order. No data moves. Element (1, 3, 2) of the transposed view is 1×1 + 3×6 + 2×30 = 79, the same slot as (2, 3, 1) in the original. That is what a transpose is, once strides are real metadata and not recomputed from the shape on every access. Tick “view as transpose” in the lab above to see it in 2D.

Why care: reading memory with stride 1 is fast. Jumping around is slow. Weight matrices get stored in the order the kernel reads them, because the layout is part of the speed. Phase 1 measures how large that gap is. The field is stored now so index does not have to change when views arrive. Views have not arrived.

The struct

Three fields: shape, strides, data: Vec<f32>. Every constructor keeps two invariants:

  • shape.len() == strides.len()
  • data.len() == shape.iter().product()

zeros delegates to from_vec, so the length check and the stride build happen in one place. from_vec moves the buffer in. It does not reorder elements. A length mismatch panics. That is a programming error, and a silent wrong read would be worse.

numel returns data.len(), not a fresh product. The constructors already forced them to agree, and the buffer length is the fact the rest of the program relies on. size_bytes is numel × size_of::<f32>(), which is 4 today. A 1000×1000 tensor is 1,000,000 elements and 4,000,000 bytes. A 4096×4096 tensor, the one main prints, is 64 MiB calculated. That is one weight matrix, not a model.

get and set go through index. set resolves the index before the write so the shared borrow in index ends before data is borrowed mutably. The split is for the reader; one line would compile the same.

Clone is a deep copy of the metadata and the whole buffer. PartialEq compares shape, strides, and values.

Alignment is not handled. Vec<f32> guarantees 4-byte alignment, because that is align_of::<f32>(). NEON wants 16. A cache line is 64. That replacement is Phase 1, described in alignment. Do not “fix” it inside Tensor until the allocator exists and a benchmark shows the difference.

Check yourself

Where is (2, 3, 1) in a row-major [4, 5, 6] tensor?

Strides [30, 6, 1]. Flat index 79. If you got 79 by a different grouping, check that a step on dim 0 really skips 30 and not 4.

What should Tensor::zeros(&[3, 4]).strides() be?

[4, 1]. Three rows of four. The last dimension is contiguous. That assertion is in the repo and passed on the phone.

Why store strides if they are a pure function of the shape today?

So index is already written against the field. A transpose or a slice changes strides without changing the rule in index. Recomputing from the shape on every access would make those views impossible without a copy.
