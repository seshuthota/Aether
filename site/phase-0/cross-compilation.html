Cross-compilation

You compile on an x86 Linux PC. The binary has to run on an ARM phone, with Android’s C library, not the PC’s. Those are three different mismatches, and the first build failed on exactly one of them.

Host and target

The host is the machine that runs the compiler. Here that is the Linux PC. The target is the machine that will run the binary. Here that is the phone: aarch64, Android, Bionic.

Same source, different instructions. A PC CPU cannot execute AArch64 machine code. That is a separate fact from “both are Linux.” Linux is a kernel family. The instruction set and the C library are independent of that.

The triple

aarch64-linux-android is a target triple: architecture, kernel, environment.

PieceHereWhat it decides
architectureaarch6464-bit ARM instructions. Not x86-64.
kernellinuxLinux syscalls. Android is a Linux kernel.
environmentandroidBionic, Android’s C library, and Android’s dynamic linker. Not glibc.

Rust and the NDK both use this name, so they agree on what is being built. A normal Linux ARM binary is aarch64-unknown-linux-gnu. Same CPU, different C library and different loader. That binary will not run on Android even if you could get it onto the phone.

Two halves of the toolchain

A toolchain is compiler, linker, sysroot (the target’s headers and libraries), and C library. For this project the two halves come from different places:

  1. rustup target add aarch64-linux-android installs Rust’s standard library, already compiled for the phone. That is what lets println! and Vec exist in the ARM build. It does not link the final executable against Android.
  2. The linker is the NDK clang: aarch64-linux-android31-clang under ~/Android/Sdk/ndk/27.3.13750724/.... Only that linker knows Bionic and /system/bin/linker64.

Cargo is told about the linker in .cargo/config.toml, which is gitignored. The committed example is .cargo/config.toml.example. A new machine copies it and edits the path.

What actually broke

The first Android build failed with /usr/bin/ld: file in wrong format. Easy to misread as “the standard library is missing.” It was not.

Easy to get wrong

The standard library was the thing that worked. It is why Rust could emit ARM objects at all. The PC’s linker then refused those objects because they were the wrong architecture. Pointing Cargo at the NDK clang fixed the link, not the compile.

API level 31

The 31 in aarch64-linux-android31-clang is the minimum Android version the binary supports. 31 is Android 12. A binary built for 31 runs on Android 12 and everything newer, including this phone.

The phone itself reports SDK 36, Android 16 measured. Building for 36 would refuse to run on Android 12 through 15. Lower is more compatible. Go higher only when you need a C library function that was added later. Phase 0 does not need one.

Two different “won’t run”

An AArch64 binary on this x86 PC fails with Exec format error because the CPU is wrong. A glibc AArch64 binary on the phone would fail even though the CPU is right, because Android does not have ld-linux-aarch64.so.1 or glibc. The hello-world experiment showed the first. The interpreter path /system/bin/linker64 is the evidence for the second.

Check yourself

Why can’t the PC run the phone binary, even though both are Linux?

Linux is the kernel interface, not the instruction set. The phone binary is AArch64 machine code. The PC’s CPU is x86-64 and rejects it at exec time. The C library is a second, independent reason a “Linux ARM” binary can fail on Android.

What does Rust provide, and what does the NDK provide?

Rust provides the compiler and a prebuilt standard library for aarch64-linux-android. The NDK provides the linker, the Android sysroot, and Bionic. Cargo has to be told which linker to use; it does not guess the NDK path.

Why not target API 36, since that is the phone’s version?

The number is a minimum, not a match. 31 runs on this phone and on older ones. 36 would refuse Android 12–15. Raise it only for a symbol that did not exist yet at 31.
