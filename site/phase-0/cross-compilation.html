Cross-compilation

You compile on an x86 Linux PC, but the binary has to run on an ARM phone with Android’s C library. The C library is the standard set of system functions programs call. Three mismatches separate the two machines, and the first build failed on exactly one of them.

What are the host and the target?

Your code is compiled on one machine and run on another, so you need names for both. The host is the machine that runs the compiler: here, the Linux PC. The target is the machine that will run the binary: here, the phone, which is aarch64, Android and Bionic (Android’s C library).

Example: the same source file built for the PC runs x86 instructions, and built for the phone it runs ARM instructions. The PC CPU cannot execute AArch64 machine code. That is a separate fact from “both are Linux.” Linux is a kernel family. The instruction set and the C library are independent of that.

Takeaway: the PC and the phone both run Linux and still need different binaries.

What does aarch64-linux-android mean?

Rust and the NDK (Android’s native build kit) must agree on what they are building. aarch64-linux-android is a target triple: three parts that name the machine.

PieceHereWhat it decides
architectureaarch6464-bit ARM instructions. Not x86-64.
kernellinuxLinux syscalls. Android is a Linux kernel.
environmentandroidBionic, Android’s C library, and Android’s dynamic linker. Not glibc.

Example: a normal Linux ARM binary is aarch64-unknown-linux-gnu. It has the same CPU but a different C library and a different loader. That binary will not run on Android, even if you could get it onto the phone. Change one piece of the triple and you have named a different machine.

Takeaway: the triple names the CPU, the kernel and the C library, and every tool must use the same one.

Where do the two halves of the toolchain come from?

A toolchain is compiler, linker, sysroot (the target’s headers and libraries), and C library. For this project the two halves come from different places:

  1. rustup target add aarch64-linux-android installs Rust’s standard library, already compiled for the phone. That is what lets println! and Vec exist in the ARM build. Without it, they do not. It does not link the final executable against Android.
  2. The linker is the NDK clang: aarch64-linux-android31-clang under ~/Android/Sdk/ndk/27.3.13750724/.... Only that linker knows Bionic and /system/bin/linker64. Without it, the PC’s linker tries and fails.

Cargo is told about the linker in .cargo/config.toml, which is gitignored. The committed example is .cargo/config.toml.example. A new machine copies it and edits the path.

Takeaway: Rust compiles the code, and the NDK linker finishes it into an Android executable.

What actually broke in the first build?

The first Android build failed with /usr/bin/ld: file in wrong format. That looks like a missing library, but it was not. The table shows which layer did what.

LayerJobWho provides itFailed?
Compiler and stdRust source to ARM object coderustup target addNo. Objects were produced.
Linker and BionicObjects to a runnable ELFNDK clangYes, until Cargo was pointed at it.
Easy to get wrong

The standard library was the thing that worked. It is why Rust could emit ARM objects at all. The PC’s linker then refused those objects because they were the wrong architecture. Pointing Cargo at the NDK clang fixed the link, not the compile.

Takeaway: the error came from the linker, so the fix was pointing Cargo at the NDK linker.

Why build for API level 31?

The number in the linker’s name, aarch64-linux-android31-clang, is a choice, and it sets a version floor. The 31 is the minimum Android version the binary supports. 31 is Android 12. A binary built for 31 runs on Android 12 and everything newer, including this phone.

Example: the phone itself reports SDK 36, Android 16 measured. Building for 36 would refuse to run on Android 12 through 15. Lower is more compatible. Go higher only when you need a C library function that was added later. Phase 0 does not need one.

Takeaway: build for the lowest API level that has the functions you need, which is 31 here.

What did file show?

The file command reads a binary’s header and says what kind of program it is. That answers the question you need first: is this binary for the PC or for the phone?

ResultWhat it means
Host build: x86-64, interpreter /lib64/ld-linux-x86-64.so.2A PC binary, loaded by the PC’s glibc loader.
Android build: ARM aarch64, interpreter /system/bin/linker64Same container format (ELF), different instructions, Android’s loader. That loader is the Bionic difference.
Running the ARM binary on the PC: Exec format errorThe CPU cannot decode the instructions. This is the ISA mismatch, not the C-library mismatch.
Hello world on the phone: printedThe whole pipeline works.
Hello world was 482 KB and not stripped measuredMostly the standard library (formatting, stdout locking, panic, the code around main) plus debug symbols. println! itself is a few bytes of the call. Symbols are why simpleperf can later name functions. The release profile keeps them on purpose.
Two different “won’t run”

An AArch64 binary on this x86 PC fails with Exec format error because the CPU is wrong. A glibc AArch64 binary on the phone would fail even though the CPU is right, because Android does not have ld-linux-aarch64.so.1 or glibc. The hello-world experiment showed the first. The interpreter path /system/bin/linker64 is the evidence for the second.

Takeaway: file names the architecture and the loader, so read it before you guess at the cause.

Check yourself

Why can’t the PC run the phone binary, even though both are Linux?

Linux is the kernel interface, not the instruction set. The phone binary is AArch64 machine code. The PC’s CPU is x86-64 and rejects it at exec time. The C library is a second, independent reason a “Linux ARM” binary can fail on Android.

What does Rust provide, and what does the NDK provide?

Rust provides the compiler and a prebuilt standard library for aarch64-linux-android. The NDK provides the linker, the Android sysroot, and Bionic. Cargo has to be told which linker to use; it does not guess the NDK path.

Why not target API 36, since that is the phone’s version?

The number is a minimum, not a match. 31 runs on this phone and on older ones. 36 would refuse Android 12–15. Raise it only for a symbol that did not exist yet at 31.

What you should take away

Both run Linux, but the PC and the phone differ in CPU and C library, so the phone needs its own binary.

Rust supplies the ARM objects, and the NDK clang links them into an Android executable.

Build for API 31 and confirm the result with file.
