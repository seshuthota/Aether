The phone

What is adb, and how do you use it?

Your code is built on the PC, and the phone is a separate computer. You need a way to send it files and run commands there. That is adb, the Android Debug Bridge. Two commands cover Phase 0:

  • adb push <local> <remote> copies a file to the phone.
  • adb shell <command> runs one command there, the way a single SSH command would.

Example: this phone was attached over Wi-Fi, not USB, at 192.168.29.11 with a port. The port changed between sessions, from 45375 to 42065 measured, so the address you used last time may not work. When a run produces no test output, run adb devices first.

Android adds SELinux, a security layer that sits on top of the usual Unix file rules. Some things that work on a desktop Linux box are denied here, even when the read, write and execute flags look right. Ignore that and a copy that works on the PC can be refused here. The practical rule for Phase 0 is narrower than all of SELinux: there is one directory the shell user can both write and execute.

Takeaway: adb carries every file and command to the phone, so check it first when a run goes quiet.

Where is a binary allowed to run?

A file you copy to the phone can still be refused when you run it. The phone allows execution only in some folders. /data/local/tmp is the folder the shell user can write to and run from, and the runner uses /data/local/tmp/aether. Anything copied there still needs chmod +x, which marks a file as runnable.

Example: the same hello-world program, run from /sdcard, returned Permission denied measured. /sdcard is the shared storage a file manager shows you. It is mounted noexec, a mount setting that forbids running programs from it. Push there and every run is refused the same way.

Takeaway: copy binaries to /data/local/tmp/aether, because that is the one place here that can run them.

What does this chip report about itself?

Before you trust a benchmark, you need the exact chip, its core count and its clock speeds. The phone reports them through a few readers: getprop prints Android’s system properties (named settings such as ro.soc.model), /proc/cpuinfo lists each CPU, and cpuinfo_max_freq gives the fastest clock a core may run at. The table is what came back measured:

Example: cpuinfo_max_freq reports 3532800 for the performance cores. That is in kHz, thousands of hertz, so 3,532,800 ÷ 1,000,000 = 3.5328 GHz, the 3.53 GHz quoted below.

Qualcomm’s product brief (the chip maker’s spec sheet) for SM8750 describes an Oryon CPU with prime cores up to 4.32 GHz on this version of the platform (a faster bin exists; this phone is not it) and performance cores up to 3.53 GHz. A bin is one speed grade of the same chip. The sysfs frequencies match that bin exactly. There is no third, slower class.

The plan was too general

A generic Snapdragon story has prime, performance, and efficiency cores. This chip has no efficiency cores. One thread on a slow core dragging a parallel matmul is a real problem on older phones. Whether the 3.53 versus 4.32 split matters for bandwidth and energy is a Phase 1 question, not something to assume from the plan.

The clock a core is running at right now is a different file, scaling_cur_freq. It moves: idle cores sit slower and ramp up (climb to a higher clock) under load. That ramp is one reason a timing needs warm-up. Skip the warm-up and the timing can include the slow start. Phase 0 did not catch the ramp in the sum experiment, because the earlier experiments had already kept a core busy. The mechanism is still real, so Phase 1 reads this file while a benchmark runs.

Takeaway: eight cores in two speed classes, read from the phone’s own files and matching Qualcomm’s spec.

Which CPU features do the later phases need?

Later phases use optional instruction sets, and some chips have them while others do not. Each one is a CPU feature. The kernel lists a core’s features on the Features line of /proc/cpuinfo. Here is that line for the first core measured, with the flags Phase 3 and Phase 6 will care about:

FlagPresentLater use
asimdyesBase NEON. 128-bit vector registers. Phase 3.
asimddpyesDot-product instructions. Quantized GEMV in Phase 6.
i8mmyes8-bit matrix multiply (smmla). Quantized GEMM, if the intrinsics are stable on the toolchain.
bf16yesArithmetic on bfloat16 (“brain float”) numbers: BFDOT and BFMMLA multiply bf16 pairs and add into f32, BFCVT converts f32 to bf16. Safetensors weights are often bf16; just reading them needs no special instruction.
fphp, asimdhpyesHalf precision.
sve / sve2noDo not plan SVE kernels for this phone.

A flag marked yes is on this chip. A flag missing from the line is not, so code that needs it has no path on this phone. The full line also includes crypto and pointer-auth flags (aes, sha2, paca, and others). They do not change the inference plan.

Detect features at runtime with is_aarch64_feature_detected!, a Rust macro that asks the chip while the program runs, once kernels start to diverge. Hard-code “this is an 8 Elite” into the op instead, and the same binary picks the wrong code on any other phone. That habit starts in Phase 3; Phase 0 only needs the idea.

Qualcomm’s brief also lists LPDDR5X (the phone’s main memory type), up to 5300 MHz, and up to 24 GB. It does not publish a GB/s figure, and “5300 MHz” does not by itself say whether that is the clock or the transfer rate. The ~85 GB/s figure you may see (a 64-bit bus × ~10.6 billion transfers per second) is a back-of-envelope guess, a quick estimate from simple arithmetic, to verify. assumption Quote it as a measurement and you are reporting a guess. Phase 1 measures what one core and all cores actually move.

Takeaway: this chip has the dot-product and i8mm flags but no SVE, so do not plan SVE kernels for it.

What do you check when a run goes silent?

A test run can print nothing and still look like a code problem. After a config change, one did exactly that. The config was fine, but adb reported no devices, so the runner could not push the binary. Cargo’s output then showed only the failure from adb, which is easy to miss if you are looking for test result. Check the phone before you debug the linker path, or you will chase the wrong fault.

Both /proc and /sys are folders where the kernel shows its state as files. These are the ones you will read again in Phase 1, already confirmed to exist as a category of interface:

  • /proc/cpuinfo — features and CPU part.
  • /sys/devices/system/cpu/cpuN/cpufreq/ — max and current frequency.
  • /sys/class/thermal/ — temperatures. Not sampled in Phase 0.
  • /sys/class/power_supply/battery/ — current and voltage. Units and sign vary by device. Not sampled in Phase 0.

Takeaway: in this case the silent run came from adb, so check adb devices before the code or the linker.

Check yourself

Why /data/local/tmp and not /sdcard?

The adb shell user can write and execute under /data/local/tmp. /sdcard refused to execute the binary. The runner’s first lines create that directory, push, and chmod +x.

How many core classes does this phone have?

Two frequency classes, eight cores, one CPU part. Cores 0–5 max out at 3.53 GHz. Cores 6–7 max out at 4.32 GHz. No efficiency cores.

Which of those facts is a measurement, and which is a datasheet claim?

The frequencies, the CPU part, the feature flags, the model, and the SDK level were read off the phone. “Oryon”, the LPDDR5X line, and any cache size are from Qualcomm’s brief or launch coverage. Cache sizes were not read from sysfs in Phase 0. Do not treat them as measured until the working-set sweep shows the cliffs.

What you should take away

When a run goes quiet or fails to start, the cause is usually one of three plumbing facts: adb, the folder, the chip.

Check adb first, put binaries in /data/local/tmp, and plan only for features this chip has: two speed classes, dot-product and i8mm, no SVE.
