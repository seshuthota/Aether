Cargo and the runner

cargo test does not have a special “run on device” mode. It compiles your tests into an ordinary executable and runs that executable. A runner is a script that replaces the “run it here” step. That is the whole trick.

Library and binary

src/lib.rs is the engine. src/main.rs is a small program that uses the library. Tests and examples link the library without going through the command-line program. Keeping them separate means a benchmark can call Tensor and bench directly.

The library still has a placeholder add, so the crate was never empty, and a test that prints std::env::consts::ARCH. The same test printed x86_64 on the PC and aarch64 on the phone measured. That print is how you know the runner is not secretly executing on the host.

Profiles

cargo build is a debug build: little optimization, fast compiles. --release optimizes. For numeric code the gap can be 10–100×. A benchmark of a debug build measures the compiler’s lack of effort, not the phone.

The release profile in Cargo.toml sets three things that are easy to skip:

SettingWhy it is on
debug = trueKeep symbols in the release binary. simpleperf can then name functions. Without this, a profile is a list of addresses.
lto = "fat"Optimize across crate boundaries. A kernel that calls a helper can be inlined and scheduled as one unit.
codegen-units = 1One compilation unit. Slower builds, better optimization. The compiler sees more of the program at once.

Rule from here on: benchmarks are release builds. Correctness tests can be either; the on-device ones in this project are run with --release so the runner path matches the path you will time.

What the test file contains

cargo test --no-run compiles the tests and prints the path of the executable, then stops. That file is not “your test function.” It contains:

  • the library,
  • the test harness, which understands filters, --nocapture, and the pass/fail summary,
  • debug symbols.

The Android test binary was about 5.4 MB measured. Hello world was 482 KB. The extra size is the harness and the library, not the two assertions.

Without a runner, cargo test --target aarch64-linux-android builds, then fails with Exec format error. Same error as running hello world on the PC. Cargo tries to execute the ARM binary locally.

The manual three steps

The script automates a sequence that was run by hand once, so the automation has a meaning:

  1. cargo test --release --target aarch64-linux-android --no-run builds the test binary and prints its path.
  2. adb push that path to /data/local/tmp/aether.
  3. adb shell runs it, with --nocapture if you want the printlns. The shell’s exit code is the test binary’s exit code.

Each build hashes a different filename. The script uses basename of whatever Cargo passed, then deletes that remote file. Without the delete, old hashes pile up in /data/local/tmp.

The script, line by line

scripts/adb-run.sh. Cargo calls it as adb-run.sh <binary> <args…>.

scripts/adb-run.shthe runner
#!/usr/bin/env bash
set -euo pipefail

BIN="$1"      # path of the binary Cargo just built
shift         # what's left in "$@" are the arguments meant for that binary

# /data/local/tmp is the one place the adb shell user can both write and execute.
REMOTE_DIR=/data/local/tmp/aether
REMOTE_BIN="$REMOTE_DIR/$(basename "$BIN")"

adb shell "mkdir -p $REMOTE_DIR"
adb push "$BIN" "$REMOTE_BIN" >/dev/null

set +e
adb shell "chmod +x $REMOTE_BIN && $REMOTE_BIN $(printf '%q ' "$@")"
STATUS=$?
set -e

adb shell "rm -f $REMOTE_BIN"
exit $STATUS
PieceWhy it is there
set -euo pipefailStop on the first real error. A failed push should not continue into a run of a missing file.
set +e around the runA failing test is not a script bug. Cleanup still has to happen, so the script must not exit before rm.
STATUS=$?Save the exit code immediately. The next command overwrites $?.
printf '%q 'adb shell joins its arguments into one string for the phone’s shell. Without quoting, --test-threads 1 or a filter with a space splits in the wrong place.
exit $STATUSCargo decides pass or fail from the script’s exit code, not from text in the output.

Before relying on step 3, this adb was checked: true returned 0, false returned 1, exit 7 returned 7 measured. Not every adb version passes the remote code back. This one does, which is why the script can be this short.

Exit codes

The test harness exits 0 when every test passes. A deliberately failing test on the phone came back to Cargo as exit code 101 measured. 101 is rustc’s “tests failed” code. If the script had exited 0 after a failure, the host would have printed success for a phone that failed. That is the bug the STATUS line exists to prevent.

Doc-tests are the exception. Cargo runs those on the host, not through the runner. Harmless here, because we will not write doc-tests that depend on the phone. If a doc-test ever prints x86_64 while the unit tests print aarch64, that is this limitation, not a broken runner.

Commands

On the PC: cargo test

On the phone: cargo test --release --target aarch64-linux-android

One module: add a name filter, for example --lib tensor::

An example: cargo run --release --target aarch64-linux-android --example bench_sum

Check yourself

What is inside the file cargo test produces, besides your assertion?

The library, the test harness, and debug symbols. The harness is what prints the summary and honors --nocapture. That is why the file is megabytes.

Why must the runner return the phone’s exit code?

Cargo does not parse the phone’s stdout to decide pass or fail. It trusts the process it spawned. A script that always exits 0 hides a failing test.

Why keep debug symbols in a release build?

Profiling. simpleperf needs names. The symbols are not there to make the benchmark slower in a way we care about yet; they are there so a later profile is readable. Never benchmark a debug profile, which is a different switch: that one turns optimization off.
