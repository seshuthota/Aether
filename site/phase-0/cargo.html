Cargo and the runner

Tests should run on the phone, but cargo test only knows how to run programs on the PC. It has no “run on device” mode. It builds an ordinary executable and runs that. A runner is a script that replaces the “run it here” step, and that is the whole trick.

Why is the engine a library and not one program?

A benchmark needs to call the engine’s functions directly, such as Tensor and bench, without starting a whole program. A crate is a Rust package, and this one has two parts:

  • src/lib.rs is the library, the engine itself.
  • src/main.rs is a small program that uses the library.

Tests and examples link the library without going through the command-line program. The library still has a placeholder add, so the crate was never empty.

Example: a test prints std::env::consts::ARCH, the name of the CPU type it was built for. It printed x86_64 on the PC and aarch64 on the phone measured. That print is how you know the runner is not secretly executing on the host.

Takeaway: the engine is a library, so benchmarks and tests call its code directly.

Why must you benchmark a release build?

Rust has two builds. cargo build makes a debug build, with little optimization and fast compiles. --release turns the optimization on, which means the compiler rearranges code to run faster. For numeric code the gap can be 10–100×. A benchmark of a debug build measures the compiler’s lack of effort, not the phone.

A profile is a named set of compiler settings in Cargo.toml. The release profile sets three things that are easy to skip:

SettingWhy it is on
debug = trueKeep symbols in the release binary. simpleperf can then name functions. Without this, a profile is a list of addresses.
lto = "fat"Optimize across crate boundaries. A kernel that calls a helper can be inlined and scheduled as one unit.
codegen-units = 1One compilation unit. Slower builds, better optimization. The compiler sees more of the program at once.

Rule from here on: benchmarks are release builds. Correctness tests can be either; the on-device ones in this project are run with --release so the runner path matches the path you will time.

Takeaway: time release builds, and keep the debug symbols so a later profile can name functions.

What is inside the file cargo test makes?

You might expect the file to hold just your test function. Run cargo test --no-run to compile the tests and print the path of the executable, then stop. That file is not “your test function.” It contains:

  • the library,
  • the test harness, which understands filters, --nocapture, and the pass/fail summary,
  • debug symbols.

Example: the Android test binary was about 5.4 MB measured, and hello world was 482 KB. The extra size is the harness and the library, not the two assertions.

Without a runner, cargo test --target aarch64-linux-android builds, then fails with Exec format error. Cargo tries to execute the ARM binary locally.

Takeaway: the test file is the library, the harness and the symbols, not just your assertions.

What does the runner do by hand?

The script automates a sequence that was run by hand once, so each step has a known meaning:

  1. cargo test --release --target aarch64-linux-android --no-run builds the test binary and prints its path.
  2. adb push that path to /data/local/tmp/aether.
  3. adb shell runs it, with --nocapture if you want the printlns. The shell’s exit code is the test binary’s exit code.

Each build gives its file a different name, a hash that changes with the build. The script uses basename of whatever Cargo passed, then deletes that remote file. Without the delete, old hashes pile up in /data/local/tmp.

Takeaway: Cargo builds, and the runner pushes the binary, runs it on the phone, then deletes its copy.

What does each line of the runner do?

The file is scripts/adb-run.sh. Cargo calls it as adb-run.sh <binary> <args…>. Read it in six small steps, then see the whole file.

Step 1: say which shell runs it, and stop on errors

#!/usr/bin/env bash
set -euo pipefail
  • The first line says the file runs under bash, a shell (a program that reads commands).
  • set -euo pipefail makes the script stop at the first real error, so a failed push does not carry on into a run.

Step 2: take the binary path

BIN="$1"      # path of the binary Cargo just built
shift         # what's left in "$@" are the arguments meant for that binary
  • $1 is the first argument, the binary path Cargo passes in.
  • shift drops that first argument, so "$@" holds only the arguments for the test binary.

Step 3: name the file on the phone

# /data/local/tmp is the one place the adb shell user can both write and execute.
REMOTE_DIR=/data/local/tmp/aether
REMOTE_BIN="$REMOTE_DIR/$(basename "$BIN")"
  • REMOTE_DIR is the folder on the phone. REMOTE_BIN is the file inside it.
  • $(basename "$BIN") keeps only the file name without its folders. $(...) runs a command and puts its output in place.

Step 4: make the folder and copy the binary

adb shell "mkdir -p $REMOTE_DIR"
adb push "$BIN" "$REMOTE_BIN" >/dev/null
  • adb shell runs the quoted command on the phone. mkdir -p creates the folder and does nothing if it is already there.
  • adb push copies the binary. >/dev/null throws away its output.

Step 5: run it and save the exit code

set +e
adb shell "chmod +x $REMOTE_BIN && $REMOTE_BIN $(printf '%q ' "$@")"
STATUS=$?
set -e
  • set +e lets the script carry on after a failure, because a failing test is a result, not a script bug. set -e turns the stop-on-error rule back on.
  • && runs the binary only if chmod +x worked. printf '%q ' quotes each argument; the table below says why.
  • STATUS=$? saves the exit code (the number the run returned).

Step 6: delete the copy and exit with the result

adb shell "rm -f $REMOTE_BIN"
exit $STATUS
  • The copy is deleted before the script ends, even when the test failed.
  • exit $STATUS makes the script return the phone’s exit code, which is what Cargo reads.

Before the script relies on the adb shell run, this adb was checked: true returned 0, false returned 1, exit 7 returned 7 measured. Not every adb version passes the remote code back.

Takeaway: each line has one job, and the exit code is the one Cargo trusts.

How does a failed test reach Cargo?

Cargo decides pass or fail from one number, the exit code a program returns when it stops. The test harness exits 0 when every test passes. A deliberately failing test on the phone came back to Cargo as exit code 101 measured. 101 is the exit code the Rust test harness uses when a test fails. If the script had exited 0 after a failure, the host would have printed success for a phone that failed. That is the bug the STATUS line exists to prevent.

Doc-tests are the exception: Cargo runs them on the host, not through the runner. If a doc-test ever prints x86_64 while the unit tests print aarch64, that is this limitation, not a broken runner.

Commands

On the PC: cargo test

On the phone: cargo test --release --target aarch64-linux-android

One module: add a name filter, for example --lib tensor::

An example: cargo run --release --target aarch64-linux-android --example bench_sum

Takeaway: the script must return the phone’s exit code, because Cargo trusts that number and nothing else.

Check yourself

What is inside the file cargo test produces, besides your assertion?

The library, the test harness, and debug symbols. The harness is what prints the summary and honors --nocapture. That is why the file is megabytes.

Why must the runner return the phone’s exit code?

Cargo does not parse the phone’s stdout to decide pass or fail. It trusts the process it spawned. A script that always exits 0 hides a failing test.

Why keep debug symbols in a release build?

Profiling. simpleperf needs names. The symbols are not there to make the benchmark slower in a way we care about yet; they are there so a later profile is readable. Never benchmark a debug profile, which is a different switch: that one turns optimization off.

What you should take away

The engine is a library, so benchmarks call its code directly, and you time only release builds.

The runner builds, pushes and runs the binary, then deletes its copy and returns the phone’s exit code.

Cargo trusts the exit code, so a script that always exits 0 hides a failing test.
