Measuring time

A wrong timing is worse than no timing. It sends you off to optimize something that is not slow. Phase 0’s experiments were designed to show the three ways a number lies: the clock, the compiler, and a single noisy run.

Monotonic time

std::time::Instant is a monotonic clock. On Linux and Android that is CLOCK_MONOTONIC: it does not jump backward when the wall clock is corrected by NTP or by the user. Wall-clock time is the wrong tool for “how long did this loop take.”

Instant is good enough for microbenchmarks once each timed call is much longer than a clock read. It is not a substitute for thinking about what the compiler did to the call.

The clock has a cost

Experiment A timed a million calls to Instant::now(), wrapped in black_box so the calls were not deleted measured:

14 nsper call, PC
45 nsper call, phone

If the thing you are timing takes 50 ns, a pair of clock reads is the same size as the work. The number is mostly the clock. The rule: only trust a timing when the operation takes much longer than one clock read. For a tiny kernel, time a batch and divide. The harness does not do that yet, on purpose. Add it when a kernel needs it, not before.

How much of the number is the clock?

Slide the length of the work you are timing. One clock read on the phone costs about 45 ns measured, and roughly that much lands inside every timed interval.

The compiler deletes work

Experiment B summed 4 million f32s, ten times, in a release build. The function is #[inline(never)], and f32 addition is not associative, so the compiler may not reorder the adds inside one sum. It can still delete whole calls whose results nobody looks at.

result unused4.9 ms
black_box49.9 ms

Phone numbers above. The PC was 1.8 ms unused and 18.6 ms with black_box measured. The unused loop took about one sum, not zero and not ten. Compare 4.9 ms with the ~4.9 ms of a single sum in experiment C.

Easy to get wrong

This was not the second cargo run reusing a result from the first. The reuse happened at compile time. The compiler saw ten identical calls, nothing observing the result, inputs unchanged, and emitted about one call. The benchmark then reported a time for ten sums while doing about one sum of work. A kernel that looks 10× faster than it is will send you to optimize the wrong thing.

std::hint::black_box hides a value from the optimizer. The compiler must assume it cannot predict the value and cannot prove the result is unused. It does not make the CPU do extra work. It is a best-effort hint, so a timing still has to be checked against a number you can predict. The harness matching the hand-written loop was that check.

Warm-up, and the run that did not show it

The first executions of a path pay costs that are real and not the steady state:

  • Cold caches. Instructions and data are not in L1 yet.
  • Page faults. The OS maps a heap page when it is first touched, not when Vec reserves it.
  • Frequency ramp. A phone idles at a low clock and steps up under load. scaling_cur_freq is the file that moves.

Experiment C, 30 sums on the phone, was tight: about 4929–4988 µs measured. The ramp did not appear. Experiments A and B had already kept a core busy for ~100 ms, so the clock was already up by the time C started. The effect is real. That run is not evidence of it. To see it, sleep a few seconds at the start of main so the core drops, then time the first iteration. Phase 0 did not treat the small max gap in the harness runs as proof of warm-up either. A single slow sample among 30 can be the scheduler, not the clock ramp.

Median, min, mean, max

The PC’s 30 runs had outliers (2446 µs and 2761 µs against a typical ~1740) because other programs compete for the CPU measured. A few bad samples pull the mean up and barely move the median. The phone was quiet enough that min, median, and mean agreed. Report all of them anyway. The day the phone is not quiet, the mean will lie and the median will not.

Min to median is a few tenths of a percent. Max sits 4–7% above the median. When two kernels are compared later, a 3% difference is noise if the max is already 7% above the median. The median is the headline. The min is the best the hardware did in that sample. The gap from median to max is the noise band.

The harness

aether::bench has two pieces.

Stats::from_durations sorts a copy and reports min, median, mean, max, in nanoseconds as f64. Even counts have no middle element, so the median is the mean of the middle two. Empty input panics: a benchmark with zero runs is a bug. Order of the input does not matter.

bench(warmup, iters, f) runs f untimed warmup times, then times each of iters calls. The closure is FnMut, so a benchmark can fill or drain a buffer. Every result, including warm-up, goes through black_box. The duration vector is allocated up front so a realloc is not folded into one sample.

Per-call timing keeps an outlier visible in max without dragging the median. It also means each sample is one call, directly comparable. The cost is the clock overhead already measured. A call must be much longer than ~45 ns on this phone.

The known tests lock the statistics, not the phone:

  • odd count: median is the middle element after sorting,
  • even count: average of the two middle values,
  • one 100 ms outlier among four 10 ms samples: median 10, mean 28,
  • bench(3, 7, …) calls the closure 10 times and reports 7 runs.

The 3.3 GB/s trap

4 million f32s are 16×106 bytes. One sum took ~4.9 ms. That is about 3.3 GB/s calculated. The teaching ceiling we used for tokens per second was 30 GB/s, and even that was an assumption, not DRAM’s limit. So this sum is not a bandwidth measurement.

s += x cannot start the next add until the previous one finishes. The CPU’s width sits idle behind that chain. A rough latency model lands near the measurement; a bandwidth model does not. At 30 GB/s the same 16 MB would take about 0.53 ms calculated, not 4.9. Multiple independent accumulators are how Phase 3 will hide that latency. The number to remember now is the gap, not a cycle count for this core, which we have not measured.

Check yourself

Why is the median usually better than the mean?

Outliers hit some runs and not others. The mean includes them. The median is the middle of the sorted samples, so one slow run cannot drag it. On a quiet phone they agree, which is informative too: the noise band is small.

The unused loop took about 1/10 of the time. Why isn’t that evidence the compiler is a better benchmarker than you?

Because it did not do ten sums. When it compiled the program, the compiler decided nine of the calls were unobservable and dropped them. At run time the phone did one sum, and the printed time was labeled as ten. A fast number is not evidence the code is fast until you know the work still happened.

Name three reasons the first run can be slower.

Cold instruction and data caches, page faults on first touch, and the CPU frequency ramp. Phase 0’s experiment C did not show the third, because A and B had already warmed the core. Absence in that one run is not absence of the effect.
