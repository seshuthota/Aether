Measuring time

A wrong timing is worse than no timing. It sends you off to optimize something that is not slow. Phase 0’s experiments were designed to show the three ways a number lies: the clock, the compiler, and a single noisy run.

Which clock should you use?

A timing needs a clock that only moves forward. The wall clock, the one that shows the time of day, is corrected by NTP (a network time service) or by the user, so it can jump backward in the middle of a measurement. std::time::Instant is a monotonic clock: it never goes backward. On Linux and Android it is CLOCK_MONOTONIC, the kernel’s version of that clock. Wall-clock time is the wrong tool for “how long did this loop take.”

Instant is good enough for microbenchmarks (timings of a small piece of code) once each timed call is much longer than a clock read. It is not a substitute for thinking about what the compiler did to the call.

Takeaway: time with Instant, because it never goes backward.

Does reading the clock cost time?

Reading the clock is itself work, so it adds time to the number you are measuring. Experiment A timed a million calls to Instant::now(), wrapped in black_box (explained in the compiler section) so the calls were not deleted measured:

14 nsper call, PC
45 nsper call, phone

If the thing you are timing takes 50 ns, a pair of clock reads is about the same size as the work. The clock cost lands inside the interval, so the number is mostly the clock:

read clock ──► [ work: 50 ns ] ──► read clock
               ~45 ns of clock cost lands inside the interval

The rule: only trust a timing when the operation takes much longer than one clock read. For a tiny kernel, time a batch and divide. The harness does not do that yet, on purpose. Add it when a kernel needs it, not before. Skip the rule and a 50 ns kernel reports mostly the clock.

How much of the number is the clock?

Slide the length of the work you are timing. One clock read on the phone costs about 45 ns measured, and roughly that much lands inside every timed interval.

Takeaway: a clock read costs about 45 ns on this phone, so time a batch when the work is that small.

Can the compiler delete the work?

Yes, when nothing uses the result. Experiment B summed 4 million f32s (4-byte floats) ten times, in a release build (the optimized build). The sum function is marked #[inline(never)], which asks the compiler to keep it as a separate function. f32 addition is not associative, meaning the order of the adds changes the rounding, so the compiler may not reorder the adds inside one sum. It can still delete whole calls whose results nobody looks at.

result unused4.9 ms
black_box49.9 ms

Phone numbers, shown above. The PC was 1.8 ms unused and 18.6 ms with black_box measured. The unused loop took about one sum, not zero and not ten. Compare 4.9 ms with the ~4.9 ms of a single sum in experiment C.

Easy to get wrong

This was not a second cargo run reusing an earlier result. The compiler did it at compile time. It saw ten identical calls, with the same inputs and results nobody read, and emitted about one call. The benchmark still reported a time for ten sums, so a kernel can look 10× faster than it is. That sends you to optimize the wrong thing.

std::hint::black_box hides a value from the optimizer. The compiler has to assume it cannot predict the value, so it cannot prove the result is unused. It adds no work for the CPU. It is a best-effort hint, not a guarantee, so check any timing against a number you can predict. The harness matching the hand-written loop was that check.

Takeaway: a fast number is not evidence of fast code until you know the work still ran.

Why can the first run be slower?

The first executions of a path pay costs that are not part of the steady state. Three of them:

  • Cold caches. Instructions and data are not in L1 yet. L1 is the smallest, fastest cache.
  • Page faults. A page fault is the OS stopping to set up a memory page the first time your program touches it. The OS maps a heap page when it is first touched, not when Vec reserves it.
  • Frequency ramp. A phone idles at a low clock and steps up under load. scaling_cur_freq is the file that moves.

Experiment C, 30 sums on the phone, was tight: about 4929–4988 µs measured. The ramp did not appear. Experiments A and B had already kept a core busy for ~100 ms, so the clock was up by the time C started. The effect is real, but that run is not evidence of it. To see it, sleep a few seconds at the start of main so the core drops, then time the first iteration.

Phase 0 did not treat the small max gap in the harness runs as proof of warm-up either. A single slow sample among 30 can be the scheduler (the part of the OS that decides which program runs when), not the clock ramp. Skip the warm-up runs and those slow first samples land in your number.

Takeaway: the first run can carry warm-up costs, so one quiet run does not prove they are absent.

Which number should you report?

One run is one sample, and samples vary. The PC’s 30 runs had outliers, slow samples far from the rest: 2446 µs and 2761 µs against a typical ~1740, because other programs compete for the CPU measured. The median is the middle sample after sorting. The mean is the average. A few bad samples pull the mean up and barely move the median. The phone was quiet enough that min, median and mean agreed. Report all of them anyway. The day the phone is not quiet, the mean will lie and the median will not.

Min is a few tenths of a percent below the median. Max sits 4–7% above it. That gap from median to max is the noise band. If the band is 7%, a 3% difference between two kernels is inside it, so it is noise. Calling it a win is the mistake to avoid.

Takeaway: report the median, and read the gap from median to max as the noise band.

How does the harness compute them?

aether::bench has two pieces. Stats::from_durations sorts a copy of the times and reports min, median, mean and max, in nanoseconds as f64 (a 64-bit float). With an even count there is no single middle element, so the median is the average of the middle two. Empty input panics (stops the program with an error), because a benchmark with zero runs is a bug. The order of the input does not matter.

bench(warmup, iters, f) runs f untimed warmup times, then times each of iters calls. f is a closure (a function value that can use variables from outside it). It is FnMut, meaning it may change those variables, so a benchmark can fill or drain a buffer. Every result, including warm-up, goes through black_box. The duration vector is allocated up front, so a realloc (growing the vector’s memory) is not folded into one sample.

Timing each call separately keeps an outlier visible in max without dragging the median. Each sample is one call, so the samples are comparable. The price is the clock overhead measured above. A call must be much longer than ~45 ns on this phone.

The known tests lock the statistics, not the phone:

  • odd count: median is the middle element after sorting,
  • even count: average of the two middle values,
  • one 100 ms outlier among four 10 ms samples: median 10, mean 28,
  • bench(3, 7, …) calls the closure 10 times and reports 7 runs: 3 warm-up calls plus 7 timed ones.

Takeaway: the harness sorts the samples, takes the median, and runs warm-up calls that are never reported.

Is the 3.3 GB/s sum a bandwidth?

It looks like one. 4 million f32s are 4 million × 4 bytes, which is 16×106 bytes. One sum took about 4.9 ms. That is about 3.3 GB/s calculated. The teaching ceiling for tokens per second used 30 GB/s, and even that was an assumption, not DRAM’s limit. So this sum is not a bandwidth measurement.

s += x cannot start the next add until the previous one finishes. The CPU’s extra width sits idle behind that chain. An accumulator is a variable that holds a running total, and s is one. A latency model (time per dependent add) lands near the measurement; a bandwidth model does not. At 30 GB/s the same 16 MB would take about 0.53 ms calculated, not 4.9. Multiple independent accumulators are how Phase 3 will hide that latency. The number to remember now is the gap, not a cycle count for this core, which we have not measured.

Takeaway: a sum with a dependent chain measures latency, so do not read it as the phone’s bandwidth.

Check yourself

Why is the median usually better than the mean?

Outliers hit some runs and not others. The mean includes them. The median is the middle of the sorted samples, so one slow run cannot drag it. On a quiet phone they agree, which is informative too: the noise band is small.

The unused loop took about 1/10 of the time. Why isn’t that evidence the compiler is a better benchmarker than you?

Because it did not do ten sums. When it compiled the program, the compiler decided nine of the calls were unobservable and dropped them. At run time the phone did one sum, and the printed time was labeled as ten. A fast number is not evidence the code is fast until you know the work still happened.

Name three reasons the first run can be slower.

Cold instruction and data caches, page faults on first touch, and the CPU frequency ramp. Phase 0’s experiment C did not show the third, because A and B had already warmed the core. Absence in that one run is not absence of the effect.

What you should take away

A timing is only as good as its method: the clock, the work the compiler kept, and the statistic you report.

So know what a clock read costs, prove the work really ran, and quote the median with its noise band, never one lucky run.
