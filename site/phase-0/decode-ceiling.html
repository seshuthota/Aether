Phase 0 · the idea

The decode ceiling

This is the idea Phase 0 was building toward. During decode, generating one token, the model reads nearly every weight, uses each weight once, and then has to read them all again for the next token. Speed is capped by how fast those bytes can arrive.

tokens per second ≤ memory bandwidth ÷ bytes of weights read per token.

Memory bandwidth is how many bytes per second can move from memory to the processor. The formula above divides it by the bytes each token needs.

How big are the weights?

Every token needs the weights, so their size sets how many bytes must move. A parameter is one learned number in the model. A 0.5 billion parameter model has 500 million of them. At f32, which is 4 bytes per number (a 32-bit float), that is 2,000,000,000 bytes, or 2 GB:

FormatBytes eachWeight bytes
f3242 GB calculated
f16 or bf1621 GB
int810.5 GB
ideal 4-bit0.50.25 GB

“GB” here is 109 bytes, the same unit as GB/s. So 0.5×109 × 4 = 2×109. A cache is a small, fast memory close to the processor. A phone’s caches hold megabytes, so two gigabytes of weights do not fit. They come from DRAM, the main memory chips. If you assume the weights sit in cache, every ceiling below comes out too high.

Takeaway: at f32 the weights are 2 GB, which cannot fit in cache, so they come from DRAM.

What is the best speed the phone could reach?

Suppose the phone reads 30 GB/s, and each weight is read once per token assumption. Divide: 30 GB/s ÷ 2 GB = 15 tokens per second for f32. Smaller formats divide into bigger numbers:

FormatSizeMax tokens/sec
f322 GB15
int80.5 GB60
ideal 4-bit0.25 GB120

Halving the bytes per weight doubles the ceiling. Compute barely changes between these formats. The saving is moving fewer bytes. That is why quantization (storing each weight in fewer bits) is not optional on a phone if you care about tokens per second. Skip it and tokens per second stay capped at 15.

Takeaway: at 30 GB/s, f32 tops out at 15 tokens per second, and every halving of the bytes doubles that.

Why can’t faster math fix it?

Faster math sounds like the cure. It is not, because a token does not wait on the math. It waits on the bytes. Two facts show why.

  1. Each weight is used once per token. In decode, a weight matrix multiplies one input vector, a list of numbers for the current token. Each weight takes part in one multiply-add, one multiply plus one add, and is not needed again for that token. The page counts that as 2 FLOPs (floating-point operations). For f32 that is 2 FLOPs per 4 bytes read. That ratio is called arithmetic intensity, FLOPs per byte read, and it is very low. The CPU finishes the math long before the next weights arrive, even if compute were free. More peak FLOPs do not raise this ceiling.
  2. The weights do not fit in cache. Caches are megabytes. The model is gigabytes. The next token reads the weights from DRAM again. No reuse spreads the cost of that trip.
token 1:  read every weight from DRAM ──► multiply ──► token 1 out
token 2:  read every weight from DRAM ──► multiply ──► token 2 out
                 ^ the same weights again, because the cache is too small to keep them

So the bound is bandwidth ÷ bytes read. How wide the FMA units (the circuits that do a multiply-add) are does not enter it. Unlimited compute does not make a token faster than the weights can be fetched, because the weights are an input to the math. Ignore this and you can spend effort on the math, which cannot move the ceiling.

Takeaway: the ceiling is bandwidth ÷ bytes read, so faster math does not raise it.

Does reading the prompt hit the same limit?

Before the first new token, the model must read the whole prompt. That is prefill, and it is a different job, because many tokens go through the weights at once. Take 100 prompt tokens. Each weight can be used 100 times while it sits in a register (the CPU’s own tiny storage) or a cache, if the kernel works in blocks, or tiles, so that the activations are the small side. Intensity goes up by about that factor. Prefill can be compute-bound. Decode stays bandwidth-bound.

Same engine, two strategies. The plan splits GEMV (one token times a matrix) from GEMM (many tokens at once). Decode uses GEMV and prefill uses GEMM. Phase 0 writes neither kernel. It only needs the split to be clear before any kernel is written. Ignore it and you apply the decode ceiling to prompt processing, where it does not hold.

Takeaway: prefill can be compute-bound because it reuses each weight, while decode has one token and cannot.

Why does a smaller format go faster?

The ideal 4-bit row assumed 0.25 GB, which is exactly 4 bits per weight. Real 4-bit formats need more, because they store extra numbers alongside the weights. A nibble is 4 bits, half a byte. A block is a group of weights that share one stored scale, a number that turns the small stored integers back into real weights.

llama.cpp’s Q4_0 stores 32 weights as nibbles (16 bytes) plus one f16 scale (a 16-bit float, 2 bytes): 16 + 2 = 18 bytes per block, 4.5 bits per weight, about 0.28 GB for 0.5B parameters calculated. Q8_0 is 32 int8 values (8-bit integers) plus one f16 scale, 34/32 = 8.5 bits, about 0.53 GB. The ceiling moves, but not by the full ideal factor. Use the ideal 4-bit size and you overstate the ceiling, because the real formats are bigger.

Two other leaks, both still ahead of us:

  • Attention also reads the KV cache, which grows with context length. Weights are not the only bytes.
  • You will not get the full assumed bandwidth. A scalar sum of 16 MB already showed ~3.3 GB/s, and that was a latency chain, not DRAM. Phase 1 measures the DRAM number the ceiling should actually use.

Takeaway: fewer bytes per weight means fewer bytes to read per token, so a smaller format goes faster, but real 4-bit formats store a scale per block and so save a little less than the ideal 4 bits.

Check yourself

Why can’t unlimited compute beat “model size ÷ bandwidth”?

Each weight is an input. It has to arrive from DRAM, it is used once, and it does not stay in cache for the next token. The multiply cannot start on a weight that has not arrived, and a faster multiply does not make the next weight arrive sooner.

Why does prefill escape the same ceiling?

Many prompt tokens share one read of a weight, if the kernel keeps that weight live while it is applied to the tile. Intensity rises with the tile. Decode has a tile of one.

What would make the 15 tok/s figure wrong even if bandwidth really were 30 GB/s?

KV-cache traffic, scales and block overhead in a real quant format, and any byte the kernel reads that is not a weight. Also the assumption that the kernel actually reaches 30 GB/s. The figure is a ceiling, not a prediction.

What you should take away

Decode reads every weight from DRAM for every token, so the bytes per weight set the speed ceiling.

Faster math does not raise that ceiling, but smaller weights do.

Prefill is a different case, and every number here is an assumption or a calculation, not a measurement.
