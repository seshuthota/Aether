Phase 0 · the idea

The decode ceiling

This is the idea Phase 0 was building toward. During decode, generating one token, the model reads nearly every weight, uses each weight once, and then has to read them all again for the next token. Speed is capped by how fast those bytes can arrive.

tokens per second ≤ memory bandwidth ÷ bytes of weights read per token.

Bytes per parameter

Model size, for the weights, is parameters times bytes per parameter. A 0.5 billion parameter model:

“GB” here is 109 bytes, the same unit as GB/s. 0.5×109 × 4 = 2×109. A phone’s caches hold megabytes. Two gigabytes of weights do not fit. They come from DRAM.

Halving the bytes per weight doubles the ceiling. Compute barely changes between these formats. The saving is moving fewer bytes. That is why quantization is not optional on a phone if you care about tokens per second.

Why the ceiling is firm

Two facts, not one.

  1. Each weight is used once per token. In decode, a weight matrix multiplies one activation vector. Each weight takes part in one multiply-add and is not needed again for that token. About 2 FLOPs per 4 bytes in f32. That ratio is called arithmetic intensity, and it is very low. The CPU finishes the math long before the next weights arrive, even if compute were free. More FLOPs of peak do not raise this ceiling.
  2. The weights do not fit in cache. Caches are megabytes. The model is gigabytes. The next token reads the weights from DRAM again. There is no reuse to amortize the trip.

So the bound is bandwidth ÷ bytes read, not a function of how wide the FMA units are. Unlimited compute does not generate a token faster than the weights can be fetched, because the weights are an input to the math, not a side effect of it.

Prefill is a different problem

Processing the prompt is not one token. With 100 prompt tokens at once, each weight can be used 100 times while it is in a register or a cache, if the kernel is tiled so that the activations are the small side. Intensity goes up by about that factor. Prefill can be compute-bound. Decode stays bandwidth-bound.

Same engine, two strategies. That is why the plan separates GEMV (one token times a matrix, decode) from GEMM (many tokens, prefill). Phase 0 does not implement either. It only needs the split to be obvious before any kernel is written.

Why quantization is a bandwidth trick

Real 4-bit formats cost more than 4 bits. llama.cpp’s Q4_0 stores 32 weights as nibbles plus one f16 scale: 16 + 2 = 18 bytes per block, 4.5 bits per weight, about 0.28 GB for 0.5B parameters calculated. Q8_0 is 32 int8 values plus one f16 scale, 34/32 = 8.5 bits, about 0.53 GB. The ceiling moves, but not by the full ideal factor.

Two other leaks, both still ahead of us:

  • Attention also reads the KV cache, which grows with context length. Weights are not the only bytes.
  • You will not get the full assumed bandwidth. A scalar sum of 16 MB already showed ~3.3 GB/s, and that was a latency chain, not DRAM. Phase 1 measures the DRAM number the ceiling should actually use.

Why can’t unlimited compute beat “model size ÷ bandwidth”?

Each weight is an input. It has to arrive from DRAM, it is used once, and it does not stay in cache for the next token. The multiply cannot start on a weight that has not arrived, and a faster multiply does not make the next weight arrive sooner.

Why does prefill escape the same ceiling?

Many prompt tokens share one read of a weight, if the kernel keeps that weight live while it is applied to the tile. Intensity rises with the tile. Decode has a tile of one.

What would make the 15 tok/s figure wrong even if bandwidth really were 30 GB/s?

KV-cache traffic, scales and block overhead in a real quant format, and any byte the kernel reads that is not a weight. Also the assumption that the kernel actually reaches 30 GB/s. The figure is a ceiling, not a prediction.
