Phase 3 — NEON kernels

Phase 2 ended with a correct model that runs at 88.6 tokens per second, held back by one long chain of additions. Phase 3 rewrites the hot loops with the phone's vector instructions (NEON) and several independent accumulators. The same model on the same core goes to 422 tokens per second, and the main kernel to within reach of what memory can deliver.

Why is the plain loop slow, and what fixes it?

The plain loop asks the core for one multiply and one add at a time, so it uses only a fraction of the core. A core can do much more per cycle (one tick of its clock). Two things are missing. The first is width: one NEON instruction, the phone's vector instruction set, works on four floats at once. The second is independence: an addition takes several cycles to finish, so if each one waits for the last, the hardware sits idle. Keep four or eight separate running sums, called accumulators, and new additions can start every cycle. With both in place, the matrix-vector product stops being limited by its own chain and starts being limited by how fast memory can feed it, which is the limit that matters for decode.

Takeaway: use wide instructions and several accumulators, or the core waits on one addition at a time.

How much faster did it get?

Three numbers sum up the phase. Each one is measured on a prime core, which is the fastest class of core on this phone.

5.3 → 53.5 GB/smatrix-vector, one prime core, matrix in L2 measured
40.6 GB/sthe same on a 256 MB matrix, from DRAM: 67 % of the core's read bandwidth measured
88.6 → 422 tok/sstories15M decode, core 7, ×4.8 measured

Takeaway: the kernel went from 5.3 to 53.5 GB/s, and the whole model from 88.6 to 422 tokens per second.

Which page should I read first?

Read the pages in order. Each one builds on the idea before it: the instructions first, then the chains that limit speed, then the kernel that uses both.

  1. SIMD and NEON — four floats per instruction, the 32 vector registers, and how Rust lets you use them.
  2. Dependency chains — latency versus throughput, and why four accumulators beat one.
  3. GEMV in three steps — the main kernel built up one idea at a time, with every step measured.
  4. Tails and testing floats — sizes that are not multiples of 4, and checking against numpy with a tolerance.
  5. Prefill: many tokens at once — reusing each weight for every prompt token.
  6. Inside the GEMM micro-kernel — a 4 × 4 tile and the register budget.
  7. One API, two machines — NEON on the phone, scalar on the PC, and checking CPU features at run time.

Takeaway: read in order, because the GEMV page uses the instructions and chains the first two pages explain.

How do you know the kernels are right?

A fast kernel that gives wrong numbers is no use, so each one is checked before it is timed. numpy, a Python library for arrays, serves as the answer key here. A tolerance is the small difference you allow between two floats that should match.

  • Every kernel (GEMV, GEMM, RMSNorm, softmax, SwiGLU, both RoPE layouts, one attention head) matches numpy within a tolerance, on sizes from 1 up to the real layer shapes, including all the awkward sizes around multiples of 4, 8, 16 and 32.
  • stories15M's greedy tokens stay identical to llama2.c's, and every activation is within 10−4 relative error. Bit-identity is given up on purpose: a different order of additions changes the last bits (why).
  • Each step of the GEMV is benchmarked separately, so every speed-up can be explained, not just observed.

Takeaway: a kernel is done when numpy agrees with it and each of its speed-ups is measured on its own.

What you should take away

Wide instructions and several accumulators together let the matrix-vector product run at the speed of memory.

The same model went from 88.6 to 422 tokens per second, and every kernel still matches numpy.

Each speed-up was measured on its own, so each one can be explained, not only observed.

Measured numbers come from the iQOO 13 (SM8750) in October 2026, on battery, and are in results/ in the repo. Teal is measured, blue is calculated, amber is an assumption or an illustration.
