Prefill: many tokens at once

Before the model can write anything, it has to read the prompt. Decode goes one token at a time, because each token depends on the one before it. The prompt is different: all of its tokens are known at the start. So they can all pass through each weight matrix together. Each weight loaded from memory then gets used once per prompt token, not once. That turns a memory problem into an arithmetic problem.

What is the difference between prefill and decode?

A model answers in two stages. Prefill reads the whole prompt. Decode writes the answer one token at a time. Both stages run the same model, but the shape of the input differs, and the shape decides what limits each stage.

PrefillDecode
Inputthe whole prompt, known in advanceone new token, just sampled
Matrix workmatrix × matrix (GEMM)matrix × vector (GEMV)
Uses of each loaded weightone per prompt tokenone
Limited byarithmeticmemory bandwidth
What the user feelstime to first tokentokens per second while it writes

GEMM is a matrix times a matrix, and GEMV is a matrix times a vector. A chat app with a long system prompt and chat history spends much of its time in prefill, so both numbers matter. If you measure only decode, you miss the wait before the first word.

Takeaway: prefill handles many tokens at once and decode handles one, and that difference decides what limits each.

Why does a batch make each weight cheaper?

Start with decode. The model needs weight wij for one multiply-add: wij × xj. Most of the cost is loading that weight from memory, and the multiply-add uses it once.

Now take a prompt of T tokens. The same weight is needed T times: wij × xj(1), wij × xj(2), … wij × xj(T). Load it once and use it T times. The bytes per token fall by a factor of T. The number of multiply-adds per byte loaded, called arithmetic intensity, rises by T.

On the roofline, a chart of the limits on speed, decode sits far left, under the sloped memory roof. Prefill slides right as T grows, until it hits the flat compute roof. From there, only faster arithmetic helps, which is the GEMM micro-kernel’s job.

Takeaway: with T tokens, each loaded weight does T uses of work, so the bytes per token fall T-fold.

How does one forward pass handle many tokens?

A forward pass is one run of the whole model over its input. The decode step runs one forward pass per token. forward_batch(tokens, start) in src/model/transformer.rs runs one forward pass over all the prompt tokens. Every buffer becomes a matrix with one row per token. Where decode calls matmul (GEMV), prefill calls matmul_batch (GEMM):

// decode, one token:      out[d]    = W[d, n] · x[n]
// prefill, T tokens:      out[T, d] = x[T, n] · Wᵀ
k::matmul_batch(out, x, w, t);   // NEON gemm on the phone
  • The first line is a matrix times a vector. The second is a matrix times a matrix, with one row per token.
  • t is the number of tokens in the batch.
  • NEON is the vector instruction set of the phone’s ARM CPU. The GEMM kernel uses it.

The element-wise steps (RMSNorm, RoPE, SwiGLU, residual adds) run once per row. Each token’s keys and values go into the KV cache, the store of past keys and values, at that token’s own position. Decode would have written them the same way, so after prefill the cache matches the cache after T decode steps, and decoding continues from there. Write them to the wrong positions and decode reads the wrong history.

The test batched_prefill_matches_llama2c checks this. It prefills in batches of 5, 12 and 13 tokens (deliberately not multiples of the 4-token tile), then decodes. It compares every activation at every position with llama2.c’s one-token-at-a-time dump measured.

Takeaway: a batched pass swaps GEMV for GEMM and leaves the KV cache as decode would have left it.

What cannot be batched?

Attention is the step where each token looks back at earlier tokens. Token t may look only at tokens 0 to t, so its result depends on the tokens before it. The weights do not have this problem, but attention does.

The batched pass therefore runs attention for each prompt token in turn, against the keys written so far. For short prompts that is a small part of the work. For long prompts on bigger models it grows, because attention is quadratic in prompt length. That is one reason Aether’s long-prompt prefill is far behind llama.cpp’s (results/phase-7.md).

Takeaway: the matrix work batches, but attention runs one token at a time and grows fastest with prompt length.

What did the phone measure?

f32, one prime core (core 7), on battery measured (results/phase-6/raw/model-speed.txt):

ModelPrefillDecodeRatio
SmolLM2-135M, 65-token prompt231.8 tok/s39.2 tok/s5.9×
stories15M, 5-token prompt1,151 tok/s422 tok/s2.7×

Even a 5-token prompt is 2.7 times faster per token, because each weight is used up to 4 times per load in the 4 × 4 tile. A FLOP is one floating-point operation, and GFLOP/s is billions of them per second. For SmolLM2, 231.8 tokens per second × about 270 million FLOPs per token is roughly 60 GFLOP/s on one core calculated. Its decode at 39.2 tok/s is about 11 GFLOP/s. The GEMM’s own peak against the core’s FMA limit has not been measured yet (examples/gemm_bench.rs exists; its phone output was not saved).

Takeaway: on the phone, prefill runs 5.9 times faster per token than decode for SmolLM2, and 2.7 times for stories15M.

Check yourself

Why can the prompt be processed in one batch, but not the generated text?

All prompt tokens are known before starting. A generated token only exists after the previous step has been sampled, so decode is inherently one at a time.

With T = 32, what happens to the weight bytes per token?

They fall 32-fold, from 60.8 MB to 1.9 MB per token, if each weight is loaded once for all 32 tokens.

After prefilling 13 tokens, is the KV cache any different from 13 decode steps?

No (up to last-bit rounding from the different kernel): each token's k and v are written at its position, and attention for each token only sees tokens before it. The test compares this against llama2.c.

Why is prefill limited by arithmetic and decode by memory, with the same weights?

Decode does 2 FLOPs per 4-byte weight; prefill does 2T. With enough reuse, the core runs out of arithmetic throughput before memory runs out of bandwidth.

What you should take away

Prefill reads many prompt tokens at once, so each loaded weight is used many times.

The matrix work batches; attention still runs one token at a time.

On the phone, prefill is several times faster per token than decode, and the gap grows with the prompt.
