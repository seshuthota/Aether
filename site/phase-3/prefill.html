Prefill: many tokens at once

Before the model can write anything, it has to read the prompt. Decode goes one token at a time because each token depends on the one before. The prompt is different: all its tokens are known up front. So they can go through each weight matrix together, and every weight loaded from memory gets used once per prompt token instead of once. That turns a memory problem into an arithmetic problem.

Reuse: the whole idea

In decode, each weight wij is loaded and used for one multiply-add: wij × xj. With T prompt tokens, the same weight is needed for wij × xj(1), wij × xj(2), … wij × xj(T). Load it once, use it T times. The bytes per token fall by a factor of T, and the arithmetic per byte (the arithmetic intensity) rises by T.

On the roofline, decode sits far left, under the sloped memory roof. Prefill slides right as T grows, until it hits the flat compute roof. From there, only faster arithmetic helps, which is the GEMM micro-kernel's job.

The batched forward pass

forward_batch(tokens, start) in src/model/transformer.rs is the same forward pass, with every buffer turned into a matrix: one row per token. Where decode calls matmul (GEMV), prefill calls matmul_batch (GEMM):

// decode, one token:      out[d]    = W[d, n] · x[n]
// prefill, T tokens:      out[T, d] = x[T, n] · Wᵀ
k::matmul_batch(out, x, w, t);   // NEON gemm on the phone

The element-wise steps (RMSNorm, RoPE, SwiGLU, residual adds) simply run once per row. Each token's keys and values are written to the cache at its own position, exactly as decode would have done, so after prefill the cache is the same as after T decode steps, and decode carries on from there.

The test batched_prefill_matches_llama2c checks this: it prefills in batches of 5, 12 and 13 tokens (deliberately not multiples of the 4-token tile), then decodes, and compares every activation at every position with llama2.c's one-token-at-a-time dump measured.

What stays one-by-one

Attention cannot be batched the same way, because token t may only look at tokens 0 to t. The batched pass runs attention for each prompt token in turn, against the keys written so far. For short prompts that is a small part of the work; for long prompts on bigger models it grows (attention is quadratic in prompt length), and it is one reason Aether's long-prompt prefill is far behind llama.cpp's (results/phase-7.md).

Check yourself

Why can the prompt be processed in one batch, but not the generated text?

All prompt tokens are known before starting. A generated token only exists after the previous step has been sampled, so decode is inherently one at a time.

With T = 32, what happens to the weight bytes per token?

They fall 32-fold, from 60.8 MB to 1.9 MB per token, if each weight is loaded once for all 32 tokens.

After prefilling 13 tokens, is the KV cache any different from 13 decode steps?

No (up to last-bit rounding from the different kernel): each token's k and v are written at its position, and attention for each token only sees tokens before it. The test compares this against llama2.c.

Why is prefill limited by arithmetic and decode by memory, with the same weights?

Decode does 2 FLOPs per 4-byte weight; prefill does 2T. With enough reuse, the core runs out of arithmetic throughput before memory runs out of bandwidth.
