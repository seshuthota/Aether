SIMD and NEON

SIMD means single instruction, multiple data: one instruction that does the same operation on several numbers side by side. On ARM phones the SIMD instruction set is called NEON. Its registers are 128 bits wide, which is four f32s. This page covers the registers, the handful of instructions the engine's kernels use, and how Rust exposes them.

One instruction, four lanes

A scalar add takes two numbers and produces one. A NEON add takes two registers of four numbers each and produces four sums at once, lane by lane:

For a dot product of 288 numbers, that means 72 vector multiply-adds instead of 288 scalar ones. The catch, as the next page shows, is that being wide does not help if every instruction still waits for the previous one.

The registers

An AArch64 core has 32 vector registers, v0 to v31, each 128 bits. The same register can be viewed as 16 bytes, 8 × 16-bit, 4 × 32-bit or 2 × 64-bit numbers; for f32 work it is 4 lanes, written v0.4s in assembly (“4 singles”).

32 sounds like a lot, but a fast kernel wants to keep many running sums and the numbers it is about to use in registers at the same time. Running out means spilling values to memory and back, which costs more than it saves. That register budget decides the shape of the GEMM tile.

All 64-bit ARM cores have NEON; it is not optional, so code for aarch64 can always use it. The Snapdragon 8 Elite's Oryon cores also have extensions on top (dot product for 8-bit integers, i8mm, bf16, fp16), but no SVE, ARM's newer variable-width vectors.

The five instructions that matter

Rust intrinsicInstructionDoes
vdupq_n_f32(0.0)dup / movia register with the same value in all 4 lanes (here: zeros, for an accumulator)
vld1q_f32(ptr)ld1 / ldr qload 4 consecutive floats from memory
vfmaq_f32(acc, a, b)fmlaacc + a × b in every lane, one rounding
vaddq_f32(a, b)faddlane-wise add, to combine accumulators
vaddvq_f32(a)faddp ×2add the 4 lanes of one register into a single float

With just these, a dot product is: zero an accumulator; repeat “load 4 weights, load 4 inputs, fused multiply-add”; at the end, add the 4 lanes together. The attention kernel adds a store, vst1q_f32.

Intrinsics: NEON from Rust

An intrinsic looks like a function but compiles to (usually) one specific instruction. Rust provides ARM's standard names in std::arch::aarch64, with a type for each register shape (float32x4_t is a 4-lane f32 register). The compiler still chooses which physical registers to use and schedules the instructions; you choose the operations. This is the same API C programmers use from arm_neon.h, so ARM's documentation applies directly.

Step 1 of the GEMV, from src/kernels/neon.rs:

use std::arch::aarch64::*;

let mut acc = vdupq_n_f32(0.0);                      // [0, 0, 0, 0]
for j in (0..n4).step_by(4) {
    acc = vfmaq_f32(acc,
                    vld1q_f32(row.as_ptr().add(j)),  // 4 weights
                    vld1q_f32(x.as_ptr().add(j)));   // 4 inputs
}
let mut s = vaddvq_f32(acc);                          // lanes → one float
for j in n4..n { s += row[j] * x[j]; }                // leftovers, one by one

The last line handles the elements that do not fill a whole register. Those leftovers are called the tail, and they are where SIMD bugs like to live.

Why it is unsafe

vld1q_f32 takes a raw pointer and reads 16 bytes from it. It has no idea how long your array is. If j + 4 goes past the end, it reads whatever lies there: garbage at best, a crash at worst. Rust cannot check that, so the call must be inside an unsafe block, which means: “I, the programmer, have checked this.”

The project's rule is that every unsafe block carries a // SAFETY: comment saying why it is safe. For the loop above: “every load reads 4 floats starting at j < n4 ≤ n, inside row and x, both of length n.” The function also asserts the lengths at the top, so a wrong call panics instead of reading out of bounds. (Phase 1 explains unsafe in general.)

FMA: one rounding instead of two

vfmaq_f32 computes acc + a × b and rounds once, at the end. A separate multiply then add rounds twice. FMA is faster (one instruction) and slightly more accurate, but its results differ in the last bits from the scalar loop's, which is one of the two reasons Phase 3 gives up bit-identity with llama2.c (the other is the order of additions, next page).

Check yourself

How many f32s fit in one NEON register, and why?

Four: the register is 128 bits and an f32 is 32 bits.

A dot product over 288 numbers with one accumulator. How many vfmaq_f32 calls, and what is left at the end?

72 calls (288 ÷ 4), no tail. At the end the accumulator holds 4 partial sums, and vaddvq_f32 adds them into one float.

Why does vld1q_f32 need unsafe?

It reads 16 bytes from a raw pointer without any bounds check. The programmer must guarantee the 4 floats exist; the SAFETY comment records why they do.

If NEON does 4 multiply-adds per instruction, why isn't step 1 four times faster than scalar?

It is roughly 3–4× (5.3 → 17.8 GB/s measured), but no more, because every FMA still waits for the previous one on the same accumulator. Width alone does not break the chain: next page.
