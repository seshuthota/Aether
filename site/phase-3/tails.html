Tails and testing floats

A vector loop eats its input 4, 8 or 16 numbers at a time. When the length is not a multiple of that, something has to handle the leftovers, and an off-by-one there reads past the end of an array or skips the last numbers. The real model sizes are all nice multiples, so a test that only uses them will never find such a bug. This page covers tails, and how the kernels are tested against numpy when bit-identity is no longer possible.

What is left over when the length is not a multiple?

Take a row of 37 floats. The 16-float loop takes 32 of them and leaves 5. The 4-float loop takes 4 of those, and 1 is left. That leftover is the tail: the elements at the end that do not fill a whole step. dot_row handles a row in three stages:

  1. 16 floats per step, into 4 accumulators, for as long as 16 fit: up to n16 = n rounded down to a multiple of 16.
  2. 4 floats per step, into one accumulator, up to n4 = n rounded down to a multiple of 4.
  3. One float at a time, scalar, for the last 0–3.

Step 1: round the length down

let n16 = n / 16 * 16;      // integer division rounds down
let n4  = n / 4 * 4;
  • n / 16 is whole-number division, so it drops the remainder. Multiplying back by 16 gives the largest multiple of 16 that fits. For n = 37 that is 32.
  • The same idea gives n4. For n = 37 it is 36.

Step 2: the three loops

for j in (0..n16).step_by(16) { /* 4 FMAs */ }
for j in (n16..n4).step_by(4) { /* 1 FMA */ }
for j in n4..n                { /* scalar */ }
  • The first loop covers 0 up to n16, 16 floats at a time.
  • The second starts where the first stopped and moves 4 floats at a time.
  • The third handles the last 0–3 elements one by one.

All three steps together

let n16 = n / 16 * 16;      // integer division rounds down
let n4  = n / 4 * 4;
for j in (0..n16).step_by(16) { /* 4 FMAs */ }
for j in (n16..n4).step_by(4) { /* 1 FMA */ }
for j in n4..n                { /* scalar */ }

Takeaway: the length rounds down in two steps, and whatever is left runs through the 4-float loop and then the scalar tail.

At n = 288, 576 or 896, the real widths, everything goes through the first stage. The tail code never runs. That is precisely why it needs its own tests.

Takeaway: the real model widths never reach the tail, so the tail stays untested unless you test other sizes.

Which bugs hide in the leftovers?

The tail is easy to get wrong. Here are four common mistakes:

  • Reading past the end. Write the vector loop as while j < n instead of j + 4 <= n, and the last load reads up to 3 floats beyond the array. Usually that memory exists, so nothing crashes; the result is just slightly wrong. Sometimes it is the end of a page, and the program dies.
  • Skipping the leftovers. Forget stage 3 and the last 1–3 products are never added. With real sizes, invisible.
  • Double counting. Start stage 2 at 0 instead of n16 and part of the row is added twice.
  • Leftover rows. gemv handles four rows at a time; if the number of rows is not a multiple of 4, the last 1–3 rows need their own path. Same bug family, other dimension.

All of these produce plausible numbers. None of them would show up in the text a model generates, at least not in an obvious way.

Takeaway: each leftover mistake gives plausible numbers, so only a test at the right sizes will catch it.

How do you test sizes that break things?

A test that uses only the real sizes never runs the tail, so the test sizes have to be chosen on purpose. tools/gen_kernels.py uses numpy to generate random inputs and the correct outputs for every kernel, at sizes chosen to hit every boundary:

odd = [1, 3, 4, 5, 7, 8, 9, 15, 16, 17, 31, 32, 33, 63, 64, 65, 100, 127, 129]
shapes = [(d, n) for d in (1, 3, 8, 17) for n in odd] + [
    (288, 288), (768, 288), (288, 768), (576, 576), …, (4864, 896), (896, 4864), …]
  • odd lists lengths. Each one sits just below, on, or just above a multiple of 4, 8, 16 or 32.
  • shapes pairs each length with 1, 3, 8 or 17 rows, and then adds the real layer shapes of the models.

So every combination of stages runs: a tail of 1, 2 or 3; a 4-float loop with and without a 16-float loop before it; one row, three rows, seventeen rows. The real layer shapes of all three models are included too, so the sizes that matter are covered. The same goldens are used for RMSNorm, softmax, SwiGLU, both RoPE layouts and attention.

The reference is computed in float64 from the exact float32 inputs, then stored. numpy is an external reference (why that matters); the tests read its .npy files directly.

Takeaway: pick test sizes that hit every stage, and include the real shapes as well.

How close is close enough?

NEON results cannot equal the float64 reference exactly, and do not equal the scalar loop’s bits either. So the test asks for a small relative error, which is the error divided by the size of the answer. The test checks it in three steps.

Step 1: measure the error

let (_, rel) = max_errors(&out, &want);
  • max_errors compares the kernel output out with the reference want.
  • The underscore ignores the first value it returns. The test keeps rel, the relative error.

Step 2: set the bound

let bound = 1e-6 * (x.len() as f32).sqrt().max(4.0);
  • x.len() as f32 turns the length into a float, and sqrt() takes its square root.
  • .max(4.0) keeps the factor at least 4, so very short vectors still get a fair bound.

Step 3: compare

assert!(rel <= bound, …);
  • The test fails if the error is larger than the bound.

All three steps together

let (_, rel) = max_errors(&out, &want);
let bound = 1e-6 * (x.len() as f32).sqrt().max(4.0);
assert!(rel <= bound, …);

Two choices in those lines:

  • Relative to the vector’s largest value, not element by element. An output that happens to be 0.000001 would otherwise turn a harmless tiny difference into a huge “relative” error.
  • Growing with √n. A dot product of n terms accumulates n rounding errors. They are random in sign, so they grow roughly like √n, not like n. An f32 has about 7 decimal digits (relative precision about 6 × 10−8), so 10−6 × √n leaves headroom without letting a real bug through.

Why does this still catch the bugs above? A skipped tail or a double-counted block changes the result by a whole product, typically 10−2 or more relative to the output, while rounding is below 10−5. The gap between “rounding” and “bug” is several orders of magnitude, so a tolerance in between separates them cleanly.

Tested on the phone

The NEON kernels only exist on ARM, so these tests are only meaningful on the phone. cargo test --release --target aarch64-linux-android pushes the test binary and the goldens there through the runner script (Phase 0). On the PC the same tests check the scalar kernels.

Takeaway: the tolerance must sit between rounding error and bug error, so it grows with √n.

Check yourself

n = 37. How many elements go through each stage?

n16 = 32, n4 = 36. So 32 in the 16-float loop, 4 in the 4-float loop, 1 in the scalar tail.

Why would testing only with the real model sizes miss tail bugs?

288, 576, 896, 768, 4864 are all multiples of 16, so the 4-float loop and the scalar tail never run.

Why does the tolerance grow with √n?

Each of the n additions can round, and the roundings are random in sign, so their sum grows like √n. A fixed bound would be too loose for short vectors or too tight for long ones.

A kernel passes with relative error 3 × 10−7 at n = 17, and fails with 0.04 at n = 33. What do you suspect?

A tail or stage-boundary bug: 33 = 32 + 1 runs a tail of one element after two 16-float steps. 0.04 is the size of a missing or doubled product, not of rounding.

What you should take away

A length that is not a multiple of 16 leaves a tail, and the tail needs its own loop and its own tests.

Test at sizes that hit every boundary, because the real model sizes never reach the tail.

Judge the result by a relative error that grows with √n, sitting between rounding and real bugs.
