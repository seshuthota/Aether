GEMV in three steps

GEMV (general matrix-vector multiply) is decode’s main cost: 97.6 % of the Phase 2 profile. Phase 3 rebuilt it in three steps, each removing one limit, and benchmarked every step on six matrices. This page goes through the steps, the measurements, and the one case where the “best” kernel loses.

How do you measure a kernel’s speed?

examples/gemv_bench.rs runs each kernel on each matrix many times on prime core 7 and takes the median (Phase 0). The median is the middle of the timings, so one unlucky run does not decide the result. The result is given in GB/s of weights read: matrix bytes ÷ time. That unit makes the kernels comparable with Phase 1’s memory bandwidth, which is the ceiling decode cannot beat. All numbers from results/phase-3.md, on battery caps measured.

Takeaway: measure in GB/s of weights read, so every kernel can be compared with the memory limit.

How can one load of x serve four rows?

After step 2, each FMA needs two loads: 4 weights and 4 numbers of x. But every row multiplies by the same x. Load a piece of x once and use it for four rows. Each step then does 8 FMAs (4 rows × 2 halves) from 8 weight loads + 2 x loads: 1.25 loads per FMA instead of 2.

Step 1: load x once

let (x0, x1) = (vld1q_f32(xp.add(j)), vld1q_f32(xp.add(j + 4)));  // x: loaded once
  • vld1q_f32 loads four floats; xp.add(j + 4) moves the pointer four floats further on.
  • Two loads give x0 and x1, the two halves of this 8-float step.

Step 2: use it for four rows

for k in 0..4 {                                                   // … used by 4 rows
    lo[k] = vfmaq_f32(lo[k], vld1q_f32(r[k].add(j)), x0);
    hi[k] = vfmaq_f32(hi[k], vld1q_f32(r[k].add(j + 4)), x1);
}
  • The loop runs over the four rows. Each row loads its own 8 weights, four for each half.
  • Each row has two accumulators, lo[k] and hi[k], one per half.

All of it together

for j in (0..n8).step_by(8) {
    let (x0, x1) = (vld1q_f32(xp.add(j)), vld1q_f32(xp.add(j + 4)));  // x: loaded once
    for k in 0..4 {                                                   // … used by 4 rows
        lo[k] = vfmaq_f32(lo[k], vld1q_f32(r[k].add(j)), x0);
        hi[k] = vfmaq_f32(hi[k], vld1q_f32(r[k].add(j + 4)), x1);
    }
}

Two accumulators per row × four rows = 8 independent chains, using 8 + 2 + a few registers. Rows left over when the count is not a multiple of 4 go through step 2’s dot_row.

Takeaway: sharing one load of x across four rows cuts the loads from 2 per FMA to 1.25.

Why does the best kernel lose on two matrices?

On two matrices, step 3 is slower than step 2: the classifier (29.0 vs 41.4) and Qwen’s up projection (32.9 vs 40.2). What they have in common: they are big (they do not fit in cache) and their rows are short (288 and 896 floats, 1.1 and 3.5 KB).

Step 2 reads one row after another: one straight stream through memory. Step 3 reads four rows at once: four streams, each jumping ahead by four rows after only 1–3.5 KB. The hardware prefetcher, which fetches lines before the code asks for them, follows one long stream easily. Four short interleaved streams that keep jumping seem to suit it less well. That explanation is likely, not measured; a simpleperf count of cache misses per kernel would test it.

The lesson is a common one in performance work: the kernel that wins on one shape can lose on another, and only measuring every real shape finds out. The fix, choosing the kernel by row length, is not done yet.

Takeaway: the best kernel for one shape can lose on another, so measure each shape you run.

How close is it to the memory limit?

On the 256 MB matrix, which must come from DRAM, gemv reaches 40.6 GB/s. Phase 1 measured about 61 GB/s for a pure read on the same core: 67 % of it. The rest goes on the arithmetic and the final lane sums mixed in between the loads. For decode on one core, that is the point where the kernel is no longer the main problem; memory is. From here, the big gains come from reading fewer bytes (quantization, Phase 6) and more cores (Phase 4).

End to end: stories15M on core 7 went from 88.6 to 422 tokens per second measured.

Takeaway: at 40.6 GB/s the kernel is near the memory limit, so the next gains are fewer bytes and more cores.

Check yourself

Why does step 3 need fewer loads per FMA than step 2?

Each loaded piece of x is used by four rows instead of one: 8 weight loads + 2 x loads feed 8 FMAs (1.25 loads per FMA, vs 2).

Why are the scalar numbers almost the same (5.3 GB/s) for the small and the 36.9 MB matrices?

The scalar loop is limited by its add chain, not by memory, so where the data comes from barely matters. The prefetcher keeps up easily with such a slow loop.

Why measure in GB/s instead of FLOPs?

Because decode's ceiling is memory bandwidth: every weight is read once per token. GB/s compares the kernel directly with Phase 1's measured read speed.

The engine uses step 3 everywhere. Is that the best choice for the classifier?

No: on the classifier step 2 is faster (41.4 vs 29.0 GB/s). Choosing by row length would recover it; it is a known open item.

What you should take away

Each step removes one limit, and the next limit then shows up in the measurements.

Sharing one load of x across four rows cuts the loads per FMA, but not on every shape.

At about 40 GB/s the kernel is close to what DRAM delivers, so fewer bytes and more cores are the next gains.
