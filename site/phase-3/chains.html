Dependency chains

An instruction can take several cycles to give its result, yet the core can start a new one every cycle. Those are two different numbers, latency and throughput. The gap between them is where the scalar loop lost most of its speed. This page shows the gap and the fix: several running sums that do not wait on each other.

What is the difference between latency and throughput?

Picture a laundry with one machine that takes an hour per load. But the machine is really four drums in a row, so you can start a new load every 15 minutes. The latency is the time from putting one load in to taking it out: one hour. The throughput is how often loads come out: four an hour, but only if you always have four loads ready. If each load needs the previous one out first (you only own one shirt), you get one load an hour, however fast the machine is.

A CPU’s floating-point unit works the same way. It is pipelined, meaning it is split into stages so that several operations are in flight at once. An FMA passes through several stages, each taking a cycle, and a new FMA can enter the first stage every cycle. Take FMA latency as about 4 cycles assumption, a typical value for this class of core, not measured here.

Takeaway: latency is how long one operation takes, and throughput is how many can start per cycle, but only if they do not wait on each other.

Why does one running sum leave the core idle?

Here is a sum that adds one product at a time into a single accumulator, acc, the running total. The line vfmaq_f32 is a fused multiply-add: it multiplies two vectors and adds the result to acc, in one instruction.

acc = vfmaq_f32(acc, w0, x0);   // needs acc
acc = vfmaq_f32(acc, w1, x1);   // needs the acc from the line above
acc = vfmaq_f32(acc, w2, x2);   // needs the acc from the line above
…
  • Each line adds one more product to acc.
  • Each line needs the acc that the line above just wrote, so it cannot start until that result exists, about 4 cycles later.

So the unit starts one FMA every 4 cycles and sits idle the other 3. The core is not slow; the program gives it nothing else to do. A run of operations where each one needs the previous result is a dependency chain. It is the same kind of chain that limited the Phase 0 sum and the Phase 2 scalar matmul. (Those chained plain adds finish sooner than an FMA. That is how the scalar matmul reached 1.77 cycles per step.) Ignore the chain and the loop waits 3 cycles out of every 4, under the 4-cycle assumption above.

Takeaway: one running sum makes every operation wait for the one before it.

What does the pipeline look like with 1, 2 or 4 sums?

Each row in the widget is one accumulator, and each column is one cycle. A coloured block is one FMA in flight (4 cycles), and “+” marks where it started. Stripes are cycles where that accumulator has nothing in flight. Count the “+” signs: each is one FMA started illustration.

One, two or four accumulators

With four accumulators, FMA 0 goes to accumulator 0, FMA 1 to accumulator 1, and so on. FMA 4 goes back to accumulator 0, whose previous result is just ready. A new FMA starts every cycle: four times the work in the same time, from exactly the same instructions.

The price has two parts. You get four partial sums at the end instead of one, and they must be added together. And the additions now happen in a different order than in the scalar loop, so the result differs in the last bits (why that is fine). Leave one partial sum out of the final addition and the answer is wrong.

Takeaway: more sums keep the pipeline busy, at the cost of one final addition step and a slightly different order of additions.

How do you write four sums in code?

The dot_row function in src/kernels/neon.rs uses this idea. Build it in three pieces first.

Step 1: start four accumulators

let mut a = [vdupq_n_f32(0.0); 4];
  • […; 4] makes an array of four accumulators.
  • vdupq_n_f32(0.0) fills one NEON register, a vector of four float lanes, with zeros.
  • Four accumulators with four lanes each give 16 independent running sums.

Step 2: feed them in a loop

for j in (0..n16).step_by(16) {
    for (k, acc) in a.iter_mut().enumerate() {
        *acc = vfmaq_f32(*acc, vld1q_f32(row.add(j + 4 * k)), vld1q_f32(x.add(j + 4 * k)));
    }
}
  • (0..n16).step_by(16) visits the start of each 16-float block: 0, 16, 32, and so on.
  • a.iter_mut().enumerate() hands out each accumulator with its index k, from 0 to 3.
  • vld1q_f32 loads four floats, and row.add(j + 4 * k) moves the pointer to the right four.
  • *acc = … writes the new sum back into that accumulator.
  • The inner for k in 0..4 loop is unrolled by the compiler into four separate FMAs, each on its own register.

Step 3: add the four sums together

let s = vaddvq_f32(vaddq_f32(vaddq_f32(a[0], a[1]), vaddq_f32(a[2], a[3])));
  • vaddq_f32 adds two vectors lane by lane, so the four accumulators are paired and then combined.
  • vaddvq_f32 adds the four lanes of the last vector into one float, s.

All of it together

let mut a = [vdupq_n_f32(0.0); 4];
for j in (0..n16).step_by(16) {
    for (k, acc) in a.iter_mut().enumerate() {
        *acc = vfmaq_f32(*acc, vld1q_f32(row.add(j + 4 * k)), vld1q_f32(x.add(j + 4 * k)));
    }
}
// … a 4-float loop and a scalar tail for what is left …
let s = vaddvq_f32(vaddq_f32(vaddq_f32(a[0], a[1]), vaddq_f32(a[2], a[3])));

Skip the … code, which handles the leftover floats, and the last few floats of each row are missing from the dot product.

Takeaway: four accumulators, each fed by its own load and FMA, then combined once at the end.

How much faster is it on the phone?

The bars below measure the same 288 × 288 matrix (stories15M’s wq) on one prime core. The unit is GB/s, gigabytes of weights read per second, so longer bars are faster measured.

scalar (Phase 2)5.3 GB/s
NEON, 1 accumulator17.8 GB/s
NEON, 4 accumulators41.6 GB/s

Going from one to four accumulators is a 2.3× gain with no extra arithmetic. On this L2-sized matrix the kernel is now limited by how fast it can load, not by latency. The next page attacks the loads.

Takeaway: the same instructions with four accumulators went from 17.8 to 41.6 GB/s on this matrix.

How many chains are enough?

The rule is: enough chains to cover latency × the number of FMAs the core can start per cycle. If FMA latency is 4 cycles and the core has several FMA units, you would want more than four chains to keep them all busy. Too few chains and the core waits. Too many and you run out of registers.

Registers are the ceiling from the other side. Each chain needs a register, and the inputs need registers too, out of 32. The engine’s GEMV uses 8 chains (4 rows × 2), the GEMM 16. Past that point, the limit is usually loads or memory, not chains.

Takeaway: add chains until latency is covered, then the limit moves to loads, memory or registers.

Check yourself

What is the difference between latency and throughput?

Latency: how long one operation takes from start to result. Throughput: how many operations can be started per cycle when they do not depend on each other.

Why can't the compiler add accumulators to the scalar loop by itself?

Several accumulators change the order of float additions, which changes the result's last bits. The compiler is not allowed to change your answer without permission.

With FMA latency 4 and one FMA unit, how many accumulators do you need to keep it busy?

Four: while one waits 4 cycles for its result, the other three each start one FMA, and by then the first is ready again.

Why can't you just use 32 accumulators?

There are only 32 registers, and the loaded weights and inputs need some. Accumulators that do not fit spill to memory, which costs more than the extra chains gain.

What you should take away

A chain of operations that each wait for the last one leaves the core idle most of the time.

Several independent sums keep the pipeline busy, and they must be added together at the end.

Add sums until latency is covered; past that, registers and loads set the speed.
