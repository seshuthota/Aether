Dependency chains

An instruction can take several cycles to produce its result, yet the core can start a new one every cycle. Those are two different numbers, latency and throughput, and the gap between them is where the scalar loop lost most of its speed. This page shows the gap, and the fix: several independent running sums instead of one.

Latency and throughput

Think of a laundry with one washing machine that takes an hour, but where you can start a new load every 15 minutes because the machine is really four drums in a row. The latency is one hour: from putting a load in to getting it out. The throughput is four loads an hour, but only if you have four loads ready to go. If each load depends on the previous one coming out (you only own one shirt), you get one load per hour, whatever the machine can do.

A CPU's floating-point unit works the same way. It is pipelined: an FMA passes through several stages, each taking a cycle, and a new FMA can enter the first stage every cycle. Take FMA latency as about 4 cycles assumption, a typical value for this class of core, not measured here.

One accumulator is one chain

acc = vfmaq_f32(acc, w0, x0);   // needs acc
acc = vfmaq_f32(acc, w1, x1);   // needs the acc from the line above
acc = vfmaq_f32(acc, w2, x2);   // needs the acc from the line above
…

Each FMA reads the accumulator the previous one wrote. It cannot start until that result exists, about 4 cycles later. So the unit starts one FMA every 4 cycles and sits idle the other 3. The core is not slow; the program gives it nothing else to do. This is a dependency chain, the same kind that limited the Phase 0 sum and the Phase 2 scalar matmul. (Those chained plain adds, which finish sooner than an FMA; that is how the scalar matmul reached 1.77 cycles per step.)

One, two or four accumulators

With four accumulators, FMA 0 goes to accumulator 0, FMA 1 to accumulator 1, and so on; FMA 4 goes back to accumulator 0, whose previous result is just ready. A new FMA starts every cycle: four times the work in the same time, from exactly the same instructions.

The price: four partial sums at the end instead of one, which must be added together. And the additions now happen in a different order than the scalar loop's, so the result differs in the last bits (why that is fine).

Four accumulators in code

dot_row in src/kernels/neon.rs: each step of 16 floats feeds four registers that never depend on each other:

let mut a = [vdupq_n_f32(0.0); 4];
for j in (0..n16).step_by(16) {
    for (k, acc) in a.iter_mut().enumerate() {
        *acc = vfmaq_f32(*acc, vld1q_f32(row.add(j + 4 * k)), vld1q_f32(x.add(j + 4 * k)));
    }
}
// … a 4-float loop and a scalar tail for what is left …
let s = vaddvq_f32(vaddq_f32(vaddq_f32(a[0], a[1]), vaddq_f32(a[2], a[3])));

The inner for k in 0..4 loop is unrolled by the compiler into four separate FMAs, each on its own register. Four accumulators × 4 lanes = 16 independent running sums.

What it did, measured

The same 288 × 288 matrix (stories15M's wq), one prime core, GB/s of weights read measured:

scalar (Phase 2)5.3 GB/s
NEON, 1 accumulator17.8 GB/s
NEON, 4 accumulators41.6 GB/s

Going from one to four accumulators is a 2.3× gain with no extra arithmetic. On this L2-sized matrix the kernel is now limited by how fast it can load, not by latency. The next page attacks the loads.

How many chains are enough?

Enough to cover latency × the number of FMAs the core can start per cycle. If FMA latency is 4 cycles and the core has several FMA units, you would want more than four chains to keep them all busy. In practice there is a ceiling from the other side: each chain needs a register, and the inputs need registers too, out of 32. The engine's GEMV uses 8 chains (4 rows × 2), the GEMM 16. Past that point, the limit is usually loads or memory, not chains.

Check yourself

What is the difference between latency and throughput?

Latency: how long one operation takes from start to result. Throughput: how many operations can be started per cycle when they do not depend on each other.

Why can't the compiler add accumulators to the scalar loop by itself?

Several accumulators change the order of float additions, which changes the result's last bits. The compiler is not allowed to change your answer without permission.

With FMA latency 4 and one FMA unit, how many accumulators do you need to keep it busy?

Four: while one waits 4 cycles for its result, the other three each start one FMA, and by then the first is ready again.

Why can't you just use 32 accumulators?

There are only 32 registers, and the loaded weights and inputs need some. Accumulators that do not fit spill to memory, which costs more than the extra chains gain.
