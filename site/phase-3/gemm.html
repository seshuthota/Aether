Inside the GEMM micro-kernel

GEMM (general matrix-matrix multiply) is what prefill runs: the weight matrix times a whole batch of token vectors. Its inner loop, the micro-kernel, computes a small tile of the output, 4 weight rows × 4 tokens, entirely in registers. This page explains why a tile, why 4 × 4, and the loop order around it that makes each weight come from memory only once.

Why isn’t one GEMV per token enough?

The simplest GEMM runs the GEMV once per token. That is correct, but each token’s GEMV streams the whole matrix again. So T tokens read the weights T times: no reuse at all, and prefill would be no faster per token than decode. (The scalar matmul_batch does exactly that; it only exists as the fallback for the PC.)

To reuse weights, the work has to be reorganised. A weight, once in a register, should be multiplied by several tokens before it is thrown away. And a token vector, once in a register, should meet several weight rows.

Takeaway: one GEMV per token reads every weight once per token, so nothing is reused.

How does a 4 × 4 tile reuse its loads?

Take 4 weight rows and 4 tokens. For each 4-float slice j:

  1. Load 4 weight vectors (one per row) and 4 token vectors (one per token): 8 loads.
  2. Multiply every weight vector with every token vector, each pair into its own accumulator: 4 × 4 = 16 FMAs.

Each load now feeds 2 FMAs, against 0.5 for GEMV’s step 2 (2 loads per FMA) and 0.8 for GEMV’s step 3 (1.25 loads per FMA). After the last slice, accumulator (r, c) holds row r · token c in 4 lanes, which vaddvq_f32 folds into the output.

Tile size vs register budget

Copper: weight rows loaded per step. Blue: token vectors. Teal: one accumulator per pair.

Takeaway: a 4 × 4 tile does 16 FMAs for 8 loads, so each load is used twice or more.

Why not a bigger tile?

Bigger tiles mean more FMAs per load: 4 × 4 gives 16 per 8 loads, and 6 × 4 gives 24 per 10. But every accumulator needs a register, and so does every loaded vector. With 32 NEON registers, 4 × 4 uses 16 + 8 = 24, leaving room for addresses and loop bookkeeping in the general registers without spilling. 5 × 5 would need 35: too many. Fast libraries use tiles like 8 × 12 with tricks this kernel does not (loading one register and using its individual lanes, for example). 4 × 4 is a clear, safe first version.

Takeaway: a bigger tile reuses loads more, but once the registers run out, values spill to memory.

What does the micro-kernel look like in code?

This is gemm_rows in src/kernels/neon.rs. Build it in three steps.

Step 1: set up the rows, tokens and accumulators

let wr = [0, 1, 2, 3].map(|k| wp.add((i + k) * n));     // 4 weight rows
let xr = [0, 1, 2, 3].map(|k| xp.add((tt + k) * n));    // 4 tokens
let mut acc = [[vdupq_n_f32(0.0); 4]; 4];               // acc[row][token]
  • [0, 1, 2, 3].map(…) builds four pointers, one per row (or token), by adding an offset to a base pointer.
  • acc is a 4 × 4 grid of vector accumulators, one per (row, token) pair, all starting at zero.

Step 2: load one slice of each

for j in (0..n4).step_by(4) {
    let wv = wr.map(|p| vld1q_f32(p.add(j)));            // 4 loads
    let xv = xr.map(|p| vld1q_f32(p.add(j)));            // 4 loads
  • (0..n4).step_by(4) walks the row in 4-float slices.
  • wv holds the four weight vectors for this slice, and xv holds the four token vectors. That is 8 loads.

Step 3: multiply every pair

    for r in 0..4 {
        for c in 0..4 {
            acc[r][c] = vfmaq_f32(acc[r][c], wv[r], xv[c]);   // 16 FMAs
        }
    }
}
  • Each weight vector meets each token vector, so the 16 pairs each get one FMA.
  • The loops only pick which accumulator and which vectors to use. The compiler unrolls them into 16 separate instructions.

All of it together

let wr = [0, 1, 2, 3].map(|k| wp.add((i + k) * n));     // 4 weight rows
let xr = [0, 1, 2, 3].map(|k| xp.add((tt + k) * n));    // 4 tokens
let mut acc = [[vdupq_n_f32(0.0); 4]; 4];               // acc[row][token]
for j in (0..n4).step_by(4) {
    let wv = wr.map(|p| vld1q_f32(p.add(j)));            // 4 loads
    let xv = xr.map(|p| vld1q_f32(p.add(j)));            // 4 loads
    for r in 0..4 {
        for c in 0..4 {
            acc[r][c] = vfmaq_f32(acc[r][c], wv[r], xv[c]);   // 16 FMAs
        }
    }
}

The arrays of registers (acc, wv, xv) look like memory, but because their sizes are fixed and the loops are unrolled, the compiler can keep every element in its own register. Whether it did is visible in the generated assembly (objdump -d on the binary): no loads or stores of acc should appear inside the loop. That check has not been recorded yet. 16 accumulators is also 16 independent chains, so FMA latency is well covered.

Takeaway: the 16 sums stay in registers, and each step reloads only the 8 vectors it needs.

Which loop goes on the outside?

Around the micro-kernel there are two loops: one over blocks of 4 weight rows, and one over blocks of 4 tokens. Their order decides how often each weight comes from memory.

for i in (r0..r0 + k4).step_by(4) {          // each block of 4 weight rows …
    for tt in (0..t4).step_by(4) {            // … meets every block of 4 tokens
        /* micro-kernel */
    }
}

A block of 4 weight rows is 4 × n floats: 4.6 KB for stories15M, 78 KB for Qwen’s down projection. That fits in the L1 or L2 cache. While the token loop sweeps every token block, those 4 rows stay in cache, so they come from DRAM once per call. The tokens are re-read for every row block, but the batch of token vectors is small (for 64 tokens of 288 floats, 74 KB) and stays in cache too.

The other order (tokens outside, rows inside) would stream the whole weight matrix once per 4 tokens: reuse of 4 instead of T. That is the mistake this order avoids.

Takeaway: keep the weight-row loop outside, so each block of rows stays in cache while every token passes over it.

What happens when the batch is not a multiple of 4?

When the number of tokens or rows is not a multiple of 4, the leftovers fall back to the GEMV paths: leftover tokens go through gemv one by one over the tiled rows, leftover rows through dot_row per token. The tail problem again, one level up. The goldens include batch sizes like 2, 5, 7, 13 and 33, and the model test prefills batches of 5, 12 and 13, to exercise every edge.

The same function also takes a range of rows (gemm_rows), so that in Phase 4 several threads can each compute their own rows of the output at the same time without touching each other’s.

Takeaway: the leftovers take the slower GEMV paths, and the tests use batch sizes that hit every edge.

Check yourself

Per 4-float step, how many loads and FMAs does the 4 × 4 tile do?

8 loads (4 weight, 4 token) and 16 FMAs: 2 FMAs per load.

Why not a 6 × 6 tile?

36 accumulators + 12 loaded vectors = 48 registers. There are 32. The extra values would spill to memory inside the loop, costing more than the reuse gains.

Why put the weight-row loop outside the token loop?

So a block of 4 weight rows stays in cache while every token block passes over it: each weight comes from DRAM once per call. The opposite order re-streams the weights for every token block.

Running GEMV once per token gives the right answer. Why is it slow for prefill?

It reads the whole weight matrix once per token: no reuse, so prefill would be as memory-bound as decode.

What you should take away

A 4 × 4 tile turns 8 loads into 16 FMAs, and the 16 sums stay in registers.

The loop order decides whether a block of weight rows stays in cache while all the tokens pass over it.

Leftover rows and tokens take the slower paths, and the tests cover those sizes.
