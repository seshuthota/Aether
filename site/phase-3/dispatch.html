One API, two machines

The engine runs on the phone (ARM, with NEON) and its tests also run on the PC (x86, no NEON). The model code should not care which machine it runs on. So it calls one set of functions, and those functions pick the right kernel. This page shows the two ways that choice is made, at compile time and at run time, and the two places the engine drops to inline assembly.

What does the model call, and what sits behind it?

The model needs a matrix multiply, but it should not know which version runs. src/kernels/mod.rs is the only kernel module the model talks to. It offers matmul, matmul_batch, attention_head, rmsnorm and so on. The transformer never imports neon or scalar directly. When a faster version arrives (NEON in Phase 3), it replaces a body in this module, and the forward pass does not change. Threads (Phase 4) and quantized weights (Phase 6) need extra arguments, a thread pool and a weight format, so the module gains _on versions such as matmul_on and linear_on, and the forward pass’s call sites gain the pool argument (how the pool reaches the matrix products). The model still calls only this module.

Takeaway: the model calls one name, and the module behind it decides which body runs.

How does the build pick a body?

A compile-time choice is made when the program is built, not when it runs. The #[cfg(…)] attribute is that switch. Build the two lines one at a time.

Step 1: the NEON line

#[cfg(target_arch = "aarch64")]
neon::gemv(out, x, w);
  • #[cfg(target_arch = "aarch64")] keeps the line only when the target is AArch64, the 64-bit ARM architecture.

Step 2: the scalar line

#[cfg(not(target_arch = "aarch64"))]
scalar::matmul(out, x, w);
  • not(…) flips the test, so this line is kept for every other target.

All of it together

#[inline]
pub fn matmul(out: &mut [f32], x: &[f32], w: &[f32]) {
    #[cfg(target_arch = "aarch64")]
    neon::gemv(out, x, w);
    #[cfg(not(target_arch = "aarch64"))]
    scalar::matmul(out, x, w);
}

#[cfg(…)] is decided when the program is compiled, for the target it is compiled for (Phase 0). Building for aarch64-linux-android keeps only the NEON line; building for the PC keeps only the scalar line. The other line is not just skipped; it does not exist in that binary. There is no run-time cost at all, and with #[inline] the call disappears too. Ignore this and the PC build tries to compile NEON intrinsics that do not exist there, and it fails.

This works for NEON because every AArch64 CPU has it. It is part of the architecture’s baseline, so a binary built for aarch64 may always use it. The neon module itself is only compiled on AArch64 (#[cfg(target_arch = "aarch64")] pub mod neon;), since its intrinsics do not exist elsewhere.

One consequence: on the PC, cargo test tests the scalar kernels. The NEON kernels are only tested by running the tests on the phone. Both run against the same numpy goldens.

Takeaway: a compile-time switch costs nothing at run time, but the choice is fixed in the binary.

What if the phone lacks a CPU feature?

NEON is baseline, but not every feature is. The integer dot-product instruction sdot, which Phase 6’s quantized kernels rely on, is an optional extension (dotprod). This phone has it; an older ARM phone might not. A binary that used it unconditionally would crash there with an “illegal instruction” error. So those kernels ask the CPU when they run.

Step 1: ask the CPU

pub fn has_dotprod() -> bool {
    std::arch::is_aarch64_feature_detected!("dotprod")
}
  • is_aarch64_feature_detected! asks the operating system which features the CPU reported. It returns a bool.
  • The answer is cached after the first call, so checking it often is cheap.

Step 2: pick a path

pub fn dot_q8_0_q8_0(row: &[BlockQ8_0], x: &[BlockQ8_0]) -> f32 {
    if !has_dotprod() {
        return crate::quant::scalar::dot_q8_0_q8_0(row, x);   // safe fallback
    }
    // SAFETY: has_dotprod() just returned true, so the CPU has the dotprod feature sdot needs.
    unsafe { dot_q8_0_q8_0_sdot(row, x) }                    // fast path
}
  • The if returns early with the plain scalar version when the feature is missing.
  • The unsafe call runs only after that check passed. The // SAFETY: comment says what was checked.

Step 3: the fast function

#[target_feature(enable = "dotprod")]
unsafe fn dot_q8_0_q8_0_sdot(…) { … }
  • #[target_feature(enable = "dotprod")] lets the compiler use sdot inside that one function, even though the rest of the binary is built for plain AArch64.
  • The function is unsafe to call. Calling it on a CPU without the feature is exactly the crash we are avoiding.

All of it together

pub fn has_dotprod() -> bool {
    std::arch::is_aarch64_feature_detected!("dotprod")
}

pub fn dot_q8_0_q8_0(row: &[BlockQ8_0], x: &[BlockQ8_0]) -> f32 {
    if !has_dotprod() {
        return crate::quant::scalar::dot_q8_0_q8_0(row, x);   // safe fallback
    }
    // SAFETY: has_dotprod() just returned true, so the CPU has the dotprod feature sdot needs.
    unsafe { dot_q8_0_q8_0_sdot(row, x) }                    // fast path
}

#[target_feature(enable = "dotprod")]
unsafe fn dot_q8_0_q8_0_sdot(…) { … }

Phase 0’s look at the phone found dotprod, i8mm, bf16 and fp16 among its features, and no SVE. i8mm (the smmla matrix instruction) is not used yet; it is an open item for faster quantized prefill.

Takeaway: check the feature first, then call the fast path, or the phone that lacks it crashes.

When is an intrinsic not enough?

Intrinsics are Rust functions that map to one CPU instruction each. They cover almost everything. The engine has two exceptions, both written with Rust’s asm! macro, which puts a raw assembly instruction inside Rust code.

WhereInstructionWhy assembly
src/sys/cpu.rsmrs …, ctr_el0reads a system register that reports the cache line size; there is no intrinsic for it
src/kernels/neon_quant.rsfcvtl v.4s, v.4hwidens four f16 numbers to f32 in one instruction. It is part of base NEON, but Rust’s intrinsic for it needs a half-precision type that was not usable on stable Rust, so one instruction is written by hand

Each asm! block states what it touches (nomem: no memory; pure: same inputs give same output), so the compiler can still optimise around it. Writing whole kernels in assembly would give full control over registers and scheduling. But the intrinsic versions are already close to memory’s limit for decode, so the gain would not pay for the loss of readability.

Takeaway: write assembly only for the one instruction that has no intrinsic, and say what it touches.

What does this structure buy you?

  • Every faster version is tested the same way. The tests call the public functions with numpy goldens, so whichever body is compiled in gets tested.
  • The slow version never goes away. The scalar kernels stay as the PC path and as the readable statement of what each kernel computes. They are not a test oracle (numpy and llama2.c are), but they are the easiest code to read first.
  • Benchmarks can compare versions directly, since the steps (gemv_one_acc, gemv_row_4acc, gemv) stay public.

Takeaway: one name, many bodies, and each body is tested through that name.

Check yourself

Why can NEON be chosen at compile time, but sdot needs a run-time check?

NEON is part of every AArch64 CPU. dotprod is optional, so the same binary may meet CPUs with and without it.

On the PC, which matmul does cargo test test?

The scalar one. The neon module is not even compiled for x86. NEON kernels are tested by running the tests on the phone.

What would happen if a function marked #[target_feature(enable = "dotprod")] ran on a CPU without it?

The CPU would hit an instruction it does not know and the program would die with an illegal-instruction signal. That is why calling it is unsafe and guarded by the feature check.

Why does the transformer never call neon::gemv directly?

So that new kernel versions (threaded, quantized) can be swapped in at one place, without editing the model code, and so the model also builds on machines without NEON.

What you should take away

The model calls one set of functions, and the choice of body happens at compile time or at run time.

Check an optional CPU feature before you call the code that needs it.

Use assembly only for the one instruction that intrinsics cannot express.
