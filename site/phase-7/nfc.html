One text, two spellings

The word “café” can be stored as two different byte sequences that look identical on screen. Qwen’s tokenizer first rewrites every text into one agreed spelling, called NFC, so both get the same tokens. This page builds that rewrite from src/tokenizer/nfc.rs.

What are we trying to do here?

Unicode gives every character a number, its code point, written like U+00E9. Some characters can also be built from smaller pieces: a plain letter followed by a combining mark, such as an accent, that attaches to the letter before it. So one visible word can have several sequences of code points.

A tokenizer works on bytes, so two sequences mean two sets of tokens, and the model sees two different inputs. Normalization rewrites text into one standard form first. Qwen2.5’s tokenizer.json says "normalizer": {"type": "NFC"}. NFC stands for Normalization Form C (“composed”), defined in Unicode Standard Annex #15.

The rewrite has three steps: take every character apart, put the marks in a fixed order, then join them back wherever a single character exists. The code is src/tokenizer/nfc.rs, 144 lines with tests, plus tables generated from Python. By the end you can work out the NFC of a short string by hand.

How can one word have two spellings?

“é” exists as one code point, U+00E9 LATIN SMALL LETTER E WITH ACUTE. It can also be written as “e” (U+0065) followed by U+0301 COMBINING ACUTE ACCENT. Both draw the same glyph. In UTF-8 the first “café” is 5 bytes, the second 6. Text typed on one keyboard and pasted from another program can arrive in either form.

SmolLM2’s tokenizer has no normalizer. Does it give the two spellings of “café” the same token ids?

  • No: different bytes give different tokens
    The tokenizer only sees bytes, and the two spellings differ from the fourth byte on.
  • Yes: they show the same letters, so the ids match
    The screen shows glyphs; the tokenizer never sees glyphs, only the bytes underneath.
  • Yes: the vocabulary has one entry for “é”
    It does, for the one-code-point form; the two-piece form has other bytes and matches other entries.

Hugging Face’s tokenizers library, the reference, gives:

tokenizer  input            ids
SmolLM2    caf  U+00E9      [83, 1939, 2756]
SmolLM2    cafe U+0301      [83, 9980, 151, 219]
Qwen2.5    caf  U+00E9      [924, 58858]
Qwen2.5    cafe U+0301      [924, 58858]
  • Without normalization the second spelling is split as “afe” plus the two bytes of the accent, so the model sees a word it has met far less often.
  • Qwen normalizes first, so both become U+00E9 and both give the same two ids.

Takeaway: normalization makes text that looks the same tokenize the same.

What is the first step of the rewrite?

To compare two spellings, first bring both to their smallest pieces. Unicode lists, for each character that has one, its canonical decomposition: U+00E9 → U+0065 U+0301. A decomposition can contain characters that decompose again, so the table the engine uses is already applied fully (2,081 entries, generated by tools/gen_unicode_tables.py from Python’s unicodedata).

Korean Hangul is handled by a formula instead. There are 11,172 Hangul syllables, and each is built from a leading consonant (19 choices), a vowel (21) and an optional final consonant (27, or none), numbered in that order from U+AC00:

let s = c - S_BASE;                     // S_BASE = 0xAC00
out.push(L_BASE + s / N_COUNT);         // consonant
out.push(V_BASE + (s % N_COUNT) / T_COUNT); // vowel
if !s.is_multiple_of(T_COUNT) {
    out.push(T_BASE + s % T_COUNT);     // final consonant
}
  • N_COUNT = 21 × 28 = 588 syllables per leading consonant; T_COUNT = 28 is the 27 finals plus “none”.
  • A formula is a few instructions and needs no table of 11,172 rows.
  • Every other character is looked up by binary search in DECOMP; one with no entry stays as it is.

Takeaway: step 1 rewrites every character into its smallest canonical pieces.

U+212B ANGSTROM SIGN looks exactly like “Å”. What does step 1 turn it into?

  • A followed by U+030A COMBINING RING ABOVE
    Its decomposition is U+00C5, which decomposes again; the table stores the full result.
  • U+00C5, the letter Å
    That is one step of the chain; step 1 goes all the way to the smallest pieces.
  • Nothing: a sign is not a letter, so it has no decomposition
    Decompositions are listed for symbols too whenever Unicode says two forms mean the same.

In what order do the accents go?

A letter can carry more than one mark. Vietnamese “ậ” is “a” with a dot below (U+0323) and a circumflex above (U+0302). A user can type the two marks in either order, and both look the same, because one mark sits below and the other above.

Unicode gives every mark a number, its combining class: 220 for marks below, 230 for marks above, and so on. Letters, which marks attach to, have class 0 and are called starters.

“a”, then circumflex (class 230), then dot below (class 220). What should step 2 do with the two marks?

  • Swap them, so the dot below (220) comes first
    Sorting by class gives 220 before 230, the same as the other typing order.
  • Keep them in typed order; the order is the user’s choice
    Then the two typing orders would stay different, which is what normalization must remove.
  • Sort them by code point
    Code point order has no meaning here; the class says where a mark sits.

Step 2 sorts each run of marks between two starters by class. The sort must be stable: two marks of the same class, such as two accents above, stack in the order typed, and swapping them would change the picture.

let start = i;
while i < pairs.len() && pairs[i].1 != 0 {
    i += 1;                       // to the end of the run
}
pairs[start..i].sort_by_key(|&(_, k)| k); // stable
  • pairs holds each code point with its class (from the 934-entry CCC table; anything not listed is class 0).
  • Rust’s sort_by_key is stable, so marks of equal class keep their order.
  • Runs are a few marks long, so the cost is negligible.

Takeaway: step 2 sorts marks by combining class, which removes the typing order without changing the picture.

When do the pieces join back together?

After step 2, every spelling of the same text is the same sequence of pieces. That form is called NFD (“decomposed”). NFC goes one step further and joins pieces back into single characters wherever Unicode defines one, because that is the shorter form most text already uses.

The loop walks the pieces and remembers the last starter. Each mark tries to join it, using the 961-pair COMPOSE table (Hangul again by formula). A mark is blocked if a mark between it and the starter has the same or a higher class:

let blocked = matches!(last_class,
    Some(p) if p == 0 || p >= k);
if !blocked
    && let Some(comp) = compose_pair(out[si], c) {
    out[si] = comp;   // the starter absorbs the mark
    continue;
}
  • For “a” + dot below + circumflex: “a” + dot gives “ạ” (U+1EA1), then “ạ” + circumflex gives “ậ” (U+1EAD). One code point.
  • Blocking keeps the meaning. If an accent above already failed to join, a second accent above may not jump over it, because that would change which accent sits nearer the letter.
  • A mark that joins nothing stays where it is, so NFC can still contain combining marks.

Takeaway: step 3 joins each mark into the letter wherever a single character exists and nothing blocks it.

“q” + U+0301 (acute). Unicode has no “q with acute” character. What is the NFC?

  • “q” + U+0301, unchanged
    The pair is not in the composition table, so the mark stays separate.
  • “q” alone; a mark that cannot join is dropped
    NFC never removes text; it only chooses among spellings of the same text.
  • An error: the input is not valid Unicode
    Any letter may carry any mark; there is just no single character for this pair.

When does the engine run NFC?

NFC is part of the tokenizer’s definition, not something the engine adds on its own. The byte-level tokenizer reads the normalizer field from tokenizer.json and sets a flag. A GGUF file has no such field, so there the flag follows the pre-tokenizer name: tokenizer.ggml.pre = "qwen2" means NFC. Qwen2.5 has it; SmolLM2 does not, so its text is never changed.

let normalized = if self.nfc {
    super::nfc::nfc(text)
} else {
    Cow::Borrowed(text)
};
  • nfc returns a Cow (“copy on write”): either the original text, borrowed, or a new string.
  • Pure ASCII text has no marks and no composed letters, so nfc returns it borrowed without looking further. Most English prompts take this path and cost nothing.

Takeaway: NFC runs only for tokenizers that ask for it, and ASCII text passes through untouched.

The engine applied NFC to SmolLM2’s input too, “to be safe”. What would change?

  • Some inputs would get different ids from SmolLM2’s own tokenizer
    SmolLM2 was trained on unnormalized tokenization, so changing the text changes ids it expects.
  • Nothing; NFC only makes text more correct
    The goal is to match the model’s tokenizer exactly, and SmolLM2’s does not normalize.
  • Only speed would change
    For non-ASCII text the ids change too, as the café table shows.

How do we know it matches?

Normalization has many rare cases, so checking a handful by hand proves little. The reference is Python’s unicodedata.normalize("NFC", ·), which implements the standard (Unicode 16.0 in the Python used here). tools/gen_nfc_tests.py writes the test cases:

  • every code point whose NFC differs from itself, and every character with a canonical decomposition;
  • 4,000 random strings of letters (Latin, Greek, Cyrillic, Japanese kana), combining marks in scrambled order, and Hangul pieces.

That gives 17,253 pairs of input and expected output. The test matches_python_unicodedata runs every one through our nfc and requires identical output. The tables come from the same Python, so they and the tests describe the same Unicode version. The full tokenizer is checked on top of that: 433 strings give the same ids as Hugging Face.

Takeaway: our NFC is right because it gives Python’s output on 17,253 cases chosen to hit every table entry.

A new Unicode version adds a composed character. What must happen for the engine to handle it?

  • Regenerate the tables and the test cases with a Python that knows the new version
    Both come from unicodedata; the code itself does not change.
  • Edit the composition loop
    The loop is the same for every version; only the table data changes.
  • Nothing; the Hangul formula covers new characters
    The formula covers Hangul syllables only, which do not change between versions.

What you should take away

The same visible text can be different code points, and a tokenizer sees only the bytes. NFC rewrites text into one spelling: take characters apart, sort the marks by class, join them back where a single character exists. The engine does it only when the tokenizer asks, and checks it against Python on 17,253 cases.

Token ids are from Hugging Face tokenizers on the models’ own tokenizer.json. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
