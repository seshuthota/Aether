Where the time goes

At the end of Phase 7, Qwen2.5 decoded about as fast as llama.cpp but read prompts 2 to 6 times slower. A week later our prefill was ahead. This page explains why the two speeds have different limits, what closed the prefill gap, and why the same program can measure 20 % slower for no reason in the code.

What are we trying to do here?

Every piece of work on a processor is limited by something: how fast data arrives from memory, how fast the arithmetic units run, or how fast the clock ticks. Knowing which limit applies tells you which change can help and which cannot. The numbers here are Qwen2.5-0.5B on cores 2–7 of this phone, from results/phase-7.md (2026-10-21) and results/phase-6.md (2026-10-24 to 29), all in tokens per second.

By the end you can say, from a model’s size and a measured speed, how close decode is to its limit, and explain why prefill needed a different instruction rather than more threads.

What limits decode?

Decode makes one token per pass, and each pass multiplies one activation vector by every weight matrix. Each weight is read once and used for one multiply-add. The arithmetic is cheap; fetching the weights from DRAM is not.

Q8_0 weights are 525 MB, Q4_0 278 MB: 1.9× smaller. How much faster does Q4_0 decode?

  • Less than 1.9×: about 1.6×
    Fewer bytes help, but Q4_0 also spends instructions unpacking nibbles, so it is not purely bandwidth-bound.
  • Exactly 1.9×: decode is all bandwidth
    Nearly, but not entirely; the unpacking work is visible.
  • No faster: the arithmetic is the same
    The multiply-adds are the same, but decode time is mostly spent waiting for bytes.

Measured on 2026-10-29: Q4_0 158–163 tok/s, Q8_0 101–102, a ratio of about 1.6. Multiplying bytes per token by tokens per second gives the bandwidth decode actually used:

Q4_0  278 MB × 160 tok/s ≈ 44 GB/s
Q8_0  525 MB × 101 tok/s ≈ 53 GB/s
all-core DRAM read (Phase 1)   ~67 GB/s
  • Q4_0 uses about two thirds of the measured DRAM ceiling and Q8_0 about four fifths: decode is mostly waiting for memory.
  • Q8_0 gets closer to the ceiling because each byte needs less work. Q4_0 reads fewer bytes but does more per byte.
  • That is why decode got faster only through fewer bytes (quantization) and less work per byte (repacked weights, fewer instructions), not through more raw arithmetic.

Takeaway: decode reads every weight for every token, so its speed is bytes per second divided by bytes per token.

What limits prefill?

Prefill multiplies the same matrices by all N prompt tokens at once. Each weight is fetched once and used N times, so the bytes per token shrink as N grows. The limit moves from memory to the multiply units.

In prefill, which is faster: Q8_0 or Q4_0?

  • Q8_0, slightly
    Bytes hardly matter in prefill; Q4_0’s extra unpacking work does.
  • Q4_0, by about 1.6×, as in decode
    That gain came from fewer bytes, and in prefill each byte is reused many times.
  • Exactly the same
    Same multiply-adds, but Q4_0 adds nibble unpacking on top.

Measured at full clock caps, 2026-10-29: pp256 Q8_0 845 tok/s, Q4_0 761–782. The order is the opposite of decode. Once the work is arithmetic, the format that needs fewer instructions per weight wins, and Q4_0 needs extra ones to turn each 4-bit value into a byte.

Takeaway: prefill reuses each weight across the whole prompt, so it is limited by arithmetic, and the cheaper-to-unpack format wins.

Doubling DRAM bandwidth (and nothing else). Which speeds up most?

  • Decode
    Decode waits for bytes; prefill waits for arithmetic.
  • Prefill
    Prefill already reuses each byte hundreds of times; more bandwidth barely helps it.
  • Both by 2×
    Only work limited by bandwidth gets faster with bandwidth.

How did prefill catch up?

In Phase 7, prefill multiplied the weights with sdot, which computes dot products of four int8 pairs per lane for one token. llama.cpp used smmla (from the i8mm extension): one instruction multiplies a 2×8 block of int8 weights by a 2×8 block of int8 activations and adds the 2×2 result. Each weight loaded into a register serves two tokens instead of one.

Item 6.5 brought smmla into our engine in three steps, each an alternating A/B on the phone:

  • 2 rows × 2 tokens: Q4_0 prefill +22–37 %, because nibbles are unpacked once per pair of tokens.
  • 4 rows × 4 tokens: more results per loaded value.
  • Repacked weights: at load, four rows are stored interleaved 8 bytes at a time with their scales together, llama.cpp’s layout. The loop no longer shuffles weights into place, which also helped decode (Q4_0 tg64 113 → 149).

Prefill on Q4_0 went from 165 tok/s (pp512, 2026-10-21) to 715–718 at full caps on 2026-10-29, against llama.cpp’s 540 in the same session. Both engines use the same instruction now, so the remaining differences are in how the loops around it are arranged.

Takeaway: prefill caught up by using an instruction that serves two tokens per weight load, and by arranging the weights for it once, at load time.

Why does smmla not help decode the same way?

  • Decode has one token, so there is no second token to share each weight with
    Its gain is reuse across tokens, and decode has only one.
  • Decode uses f32, not int8
    Decode also uses int8 dot products (sdot) on quantized activations.
  • The phone cannot run smmla on all cores
    All eight Oryon cores support i8mm; the limit is the single token.

What does a long context add?

At depth D, each new token also reads D earlier keys and values from the KV cache and computes attention over them. For Qwen2.5 the cache holds 24 layers × 2 (keys and values) × 128 numbers × 4 bytes = 24.6 KB per position calculated.

At depth 512 the cache is 12.6 MB, against 278 MB of Q4_0 weights. How much slower should decode be, if bytes were the only cost?

  • About 5 %
    12.6 MB more on top of 278 MB per token is about 4.5 % more bytes.
  • About 2×
    That would need the cache to be as big as the weights.
  • Not at all
    The cache is read every token, so it adds some bytes.

The measured loss was larger: in the Phase 7 A/B, scalar attention cost about 2.5 ms per token at depth 512 on top of 9.0 ms at depth 0, NEON attention about 1.5 ms. Attention is not just reading: for every position it computes a dot product per head, an exponential for the softmax and a weighted sum, and the 14 query heads did not split evenly over 6 threads. Splitting each head’s positions into 64-position chunks (flash-decoding, results/phase-6.md) cut decode cycles at depth 1,024 by 18 %.

Takeaway: a long context adds few bytes but a lot of attention arithmetic, so it shows up as compute, not bandwidth.

Why did the same program get slower?

On the night of 2026-10-29, pp512 seemed to regress from about 540 to 440 tok/s. Bisecting the commits found no culprit: the same binary, byte for byte, gave either speed from one process to the next. Sampling the kernel’s scaling_max_freq every 0.25 s found the cause. Partway through the slow runs, the prime cores’ clock limit dropped from 1.69 GHz to 1.02 GHz and stayed there. This is a thermal and power cap applied after the earlier tests had warmed the phone.

  • Cycle counts did not change; only the clock did. A measurement in cycles (from simpleperf) is immune; one in seconds is not.
  • The benchmark script now records the lowest caps seen during each run, and capped runs are left out of comparisons.
  • The comparison above (715 vs 540) uses only runs where both engines had the full caps.

Takeaway: on a phone the clock limit itself moves, so a timed result needs the caps recorded with it, or a cycle count instead.

A change makes pp512 15 % slower in seconds, but the cycle count is unchanged. What is the likeliest reading?

  • The clock was lower during that run; the change did not slow the code
    Same cycles at a lower frequency take longer; check the recorded caps.
  • The change added 15 % more instructions
    More instructions would show up as more cycles.
  • The cycle counter is wrong
    Possible in principle, but a moving clock cap is the measured, common cause here.

What you should take away

Decode is limited by bytes: every weight, every token, so fewer bytes and less work per byte make it faster. Prefill is limited by arithmetic, and it caught up through smmla, which shares each weight load between two tokens, on weights repacked at load. On a phone, also record the clock caps, because the same code runs at different speeds when they move.

Numbers were measured on the iQOO 13 (SM8750) between 2026-10-21 and 2026-10-29 (results/phase-7.md, results/phase-6.md) unless tagged otherwise. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
