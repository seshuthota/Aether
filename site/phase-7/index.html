Phase 7 — a real chat model: Qwen2.5 and GGUF

Phases 2 to 6 ran on SmolLM2 and stories15M, small models with simple tokenizers. Phase 7 runs Qwen2.5-0.5B-Instruct, a chat model in the format llama.cpp uses, so the engine has to read a real GGUF file, a different architecture, and a much larger tokenizer. Then it has to match llama.cpp in speed, accuracy and energy, on the same bytes.

What changed from SmolLM2?

The model is the same kind of thing: a decoder that predicts the next token. Four things differ, and each one needed code.

  • The file. SmolLM2 was read from Hugging Face's safetensors and config.json. Qwen comes as a single GGUF file that holds the config, the tokenizer and the weights. The reader is in src/format/gguf.rs, and the GGUF page walks through it.
  • The architecture. Qwen2 has biases on the query, key and value projections, and the loader reads them when the file has them. Its RoPE base (θ, the number that sets how fast position rotations change) is 1,000,000 assumption, read from the file's rope.freq_base. Its rotation pairs the two halves of each head, not adjacent numbers, so the loader picks the layout from general.architecture. The embeddings are tied: no separate output matrix is stored, and the loader reuses the token embedding table for the final projection (src/model/gguf.rs).
  • The tokenizer. Qwen's tokenizer is byte-level BPE like SmolLM2's, but with a different pre-tokenizer: the rule that cuts text into words before merges happen. It is written by hand (qwen2_split in src/tokenizer/bytelevel.rs), and it needs Unicode category tables generated from Python's unicodedata. Its text is also normalised to NFC first (src/tokenizer/nfc.rs), so that the same accented letter always becomes the same bytes.
  • The chat format. Qwen is trained on ChatML, where each turn is wrapped in <|im_start|> and <|im_end|> markers. Without them the model continues the text instead of answering. src/chat.rs builds the prompt, and the --chat flag turns it on.

Takeaway: a new architecture is mostly a few config switches, but the tokenizer and the file format each needed a new piece of code.

How do we know it is right?

Four checks, each against an outside reference. None of them compares the engine with a second copy of itself.

  • Hugging Face, every layer. The model loaded from safetensors and from the f32 GGUF both match transformers at every layer, to within 1.4e-4 relative measured. Greedy decoding gives the same 48 tokens as HF measured.
  • Tokenizer. 433 strings tokenize to the same ids as tokenizers measured. NFC matches Python's unicodedata on 17,253 cases measured. The ChatML prompt tokenizes exactly like apply_chat_template.
  • Perplexity and KL against llama.cpp. Perplexity is how surprised the model is by a text (lower is better). KL divergence says how far one model's probabilities are from another's. Both were run on wikitext-2 (20 chunks of 512 tokens), with the f32 GGUF as the base measured.

How fast is it next to llama.cpp?

Decode and prefill are different kinds of work, and they land in different places. Decode makes one token at a time, and it has to read every weight once per token, so it is limited by memory bandwidth. Prefill processes the whole prompt in one batch, so each weight is reused for every prompt token, and it is limited by arithmetic. The table is for Q4_0 on cores 2–7, from results/phase-7.md. pp64 means a 64-token prompt; tg64 @ d0 means 64 decode steps from an empty cache, and @ d256 means after 256 tokens are already cached. The d512 row is probably a bad run: the same commit later gave 87.0 tok/s at that depth, and the results file does not trust this number. A ratio above 1 means llama.cpp is faster.

  • Decode is close. At short context the two engines are level. On 2026-10-22 the same engine was about 20 % behind in a re-run, so "within about 20 %" is the fair statement. Run-to-run spread is as large as that gap.
  • Prefill is 2.1 to 5.8 times slower. Our quantized prefill still uses a row-by-row sdot kernel for each group of tokens. llama.cpp uses smmla, an instruction that multiplies two 2 × 8 blocks of 8-bit numbers at once, on repacked weights.
  • The smmla follow-up. Two rows by two tokens per instruction, so each weight loaded serves two tokens. On 2026-10-24, Q4_0 prefill rose by 22 to 37 % over the sdot build, and the gap to llama.cpp in the same session fell from 2.9–3.7 times to 2.3–2.8 times calculated from results/phase-6.md. The Q8_0 prefill did not change, because its interleaving costs what the instruction saves. See the Phase 6 dot-products page, dot products and smmla.
  • Cores 6–7 are different. On the two prime cores, llama.cpp decodes 1.6 times faster (123.7 against 78.8 tok/s). Two of its threads already saturate the bandwidth decode needs, while our Q4_0 kernel spends instructions unpacking nibbles before every multiply.

Takeaway: decode is a memory problem and we are close to llama.cpp on it; prefill is an arithmetic problem and the gap is real.

What happens over five minutes, and what does a token cost?

A single burst can flatter a phone. Heat builds, and the system lowers the clock. So the benchmark also runs decode for five minutes, back to back, and records the speed over time and the battery's energy use. The conditions are the Q4_0 model on cores 2–7, starting from position 0.

85.7 tok/saverage over 301 s, 25,792 tokens measured
112 → 60–8910-second windows: 112 for the first 40 s, then dips as the SoC throttles measured

0.041 Jper token: 3.49 W average from the battery counter, divided by tokens per second calculated

The energy figure is easy to misread. It is total phone power with the screen on, measured from the battery's charge counter. It is not the energy of the CPU alone, so the display and everything else on the phone are counted too. It works out to about 24 tokens per joule calculated. This benchmark does not measure the CPU's share on its own.

Takeaway: the sustained number is lower than the first burst, and the energy number is for the whole phone.

What is still open?

Four things this phase did not finish. Each one is a question for a later run, not a result.

  • Prefill. The gap to llama.cpp is 2 to 3 times at best. The smmla kernel with interleaved activations, a 4 × 4 tile, and repacked weights are the next steps. The Phase 6 log says this work was paused on 2026-10-24.
  • Attention across positions. Work is split by head, so 14 heads over 6 threads gives some threads three heads and others two. Splitting across positions as well would even that out. It has not been done.
  • Decode at depth 512. The first table's 62.8 tok/s is probably a bad run. The later same-commit runs gave 110.6 → 87.0 with scalar attention. The cause of the drop at depth is not established.
  • The file writer. The engine reads GGUF files, but it has no writer. The files come from llama.cpp's converter and llama-quantize. The tracker still lists item 7.5 as in progress.

Takeaway: the open questions are prefill speed, attention balance and one unexplained depth result.

Check yourself

Why does the loader need to know the architecture name, when the tensors already say what shape they are?

The shapes do not say how the rotation pairs its numbers. Llama files have their query and key rows permuted by the converter, so adjacent-pair rotation is correct; Qwen files are not permuted, so the halves layout is correct. The shapes are the same either way, so only general.architecture tells the loader which one to use. The wrong layout still loads and runs, and it gives garbage.

Decode is close to llama.cpp but prefill is 2 to 6 times slower. Why do the two differ so much?

Decode reads every weight once per token, so its speed is set by memory bandwidth, and our Q4_0 decode reaches about 36 GB/s, half of what the phone can read. Prefill reuses each weight across the prompt tokens, so its speed is set by arithmetic. Our quantized prefill still uses a row kernel per token group, while llama.cpp uses a blocked integer multiply, so it does more work per weight load.

The energy figure is 0.041 J per token. Is that how much energy the CPU used?

No. It is the battery's measured power for the whole phone, with the screen on, divided by the tokens per second. The display and everything else are included, so the CPU's share is smaller. The page's sustained run says so for that reason.

What you should take away

A new model family is mostly config switches and a tokenizer, but the file format and the chat template each need their own code.

The engine matches llama.cpp's accuracy on the same files, so the speed gap is about the kernels.

Decode is close, prefill is not. The next work is the batched integer kernel for prefill.
