GGUF: one file for everything

A model is a set of weights plus the facts needed to run them: layer count, head count, the vocabulary and the merge rules. Before GGUF, a Hugging Face model came as several files that had to be read together. GGUF (the file format llama.cpp uses) puts all of it in one file with a small typed header, and it can be read in place from the memory map. This page builds the parser step by step from the code in src/format/gguf.rs.

Why not keep the safetensors files?

The SmolLM2 and Qwen2.5 checkpoints from Hugging Face come as a config.json (the sizes), a tokenizer.json (the vocabulary and merges) and one or more .safetensors files (the numbers). The loader has to open all of them, and their names and layouts are defined by other programs. A quantized model adds a fourth question: which tensors were converted, and to what.

A GGUF file answers all of that in one place. Its header holds metadata, typed key and value pairs such as the layer count, and tensor infos, one entry per weight that gives its name, shape, storage type and position. A tensor is a named block of numbers, here a weight matrix or a vector. One file means one path to open, one thing to copy to the phone, and one place where the tokenizer lives too.

Illustration

Think of a parcel with an itemised list on top. The list says what is inside, how big each item is and where it starts. The reader never has to guess the layout, because the list is part of the parcel.

Takeaway: GGUF moves the config, the tokenizer and the weight index into the same file that holds the weights.

What is inside one GGUF file?

Read the file from the top. Each part is followed by the next, and the last part is the big block of tensor data. Here is the layout the parser reads, drawn from Gguf::open:

offset 0   "GGUF"                      4 bytes   magic: rejects other files
           u32 version                  must be 3, or the loader refuses
           u64 tensor_count
           u64 metadata_kv_count
           metadata_kv_count × KV
             string key                 u64 length, then UTF-8 bytes
             u32 type                   which value layout follows
             value                      layout chosen by the type
           tensor_count × tensor info
             string name                e.g. "blk.0.attn_q.weight"
             u32 n_dims
             u64 dims[n_dims]           fastest-varying first
             u32 ggml_type              F32, F16, Q4_0, Q8_0, ...
             u64 offset                 relative to data_start
           zero padding up to a multiple of general.alignment (default 32)
data_start tensor data, each tensor at data_start + its offset

Three things the diagram hides:

  • The offsets in the tensor infos are relative to the start of the data, not to the start of the file. The parser adds data_start to each one.
  • A string has no terminator. It is a u64 length followed by that many bytes, and the parser rejects bytes that are not UTF-8.
  • Dimensions run fastest-varying first, the reverse of the [rows, cols] PyTorch prints. The module comment gives the example: a weight with 896 columns and 4864 rows has dims = [896, 4864] assumption.

Takeaway: the reader can walk the whole header without knowing any tensor name in advance.

How does the parser read the header?

A parser reads the bytes in order and checks each one before using it. The first step is the magic and the version. Start with a small piece of open:

let mut r = Reader { b: map.as_bytes(), at: 0 };
if r.take(4)? != b"GGUF" {
    return Err(bad(format!("{}: not a GGUF file", path.as_ref().display())));
}
let version = r.u32()?;
if version != 3 {
    return Err(bad(format!("GGUF version {version} (only 3 is supported)")));
}
  • Reader holds the mapped bytes and a position at. Each read moves the position forward.
  • take(4) returns the next four bytes, or an error if the file ends first. It never reads past the end.
  • If you skip the version check and the file is version 2, the next fields are read at the wrong offsets and the parser returns nonsense sizes. Refusing early keeps that from happening.

Next come the two counts, then the metadata loop:

let (n_tensors, n_kv) = (r.u64()? as usize, r.u64()? as usize);
let mut metadata = Vec::with_capacity(n_kv);
for _ in 0..n_kv {
    let key = r.string()?;
    let ty = r.u32()?;
    metadata.push((key, r.value(ty)?));
}
  • The counts come first, so the parser knows how many entries to expect.
  • Each entry is read in the same order as the file: key, then type, then value. The value's size depends on the type, so the type has to be read first.
  • Vec::with_capacity reserves room for the entries up front. It does not make the entries exist.

Then the tensor infos. The parser reads them into a plain tuple, and only converts them after the alignment is known:

let mut infos = Vec::with_capacity(n_tensors);
for _ in 0..n_tensors {
    let name = r.string()?;
    let n_dims = r.u32()? as usize;
    let dims = (0..n_dims).map(|_| r.u64().map(|d| d as usize)).collect::<io::Result<Vec<_>>>()?;
    let ty = GgmlType::from_id(r.u32()?);
    let offset = r.u64()? as usize;
    infos.push((name, dims, ty, offset));
}
  • dims has n_dims entries, so the number of dimensions is in the file, not fixed at two.
  • GgmlType::from_id maps the number to a type. Unknown numbers become GgmlType::Other(id) instead of an error, so the file still loads and only that tensor is refused when its data is asked for.
  • The offset is stored here as written, relative to the data start. Nothing has been placed in memory yet.

The full open function, with the alignment step and the bounds check added. The rest of the code is shortened only where marked:

pub fn open(path: impl AsRef<Path>) -> io::Result<Gguf> {
    let map = Arc::new(Mmap::open(path.as_ref())?);
    let mut r = Reader { b: map.as_bytes(), at: 0 };
    if r.take(4)? != b"GGUF" {
        return Err(bad(format!("{}: not a GGUF file", path.as_ref().display())));
    }
    let version = r.u32()?;
    if version != 3 {
        return Err(bad(format!("GGUF version {version} (only 3 is supported)")));
    }
    let (n_tensors, n_kv) = (r.u64()? as usize, r.u64()? as usize);
    let mut metadata = Vec::with_capacity(n_kv);
    for _ in 0..n_kv {
        let key = r.string()?;
        let ty = r.u32()?;
        metadata.push((key, r.value(ty)?));
    }
    let mut infos = Vec::with_capacity(n_tensors);
    for _ in 0..n_tensors {
        let name = r.string()?;
        let n_dims = r.u32()? as usize;
        let dims = (0..n_dims).map(|_| r.u64().map(|d| d as usize)).collect::<io::Result<Vec<_>>>()?;
        let ty = GgmlType::from_id(r.u32()?);
        let offset = r.u64()? as usize;
        infos.push((name, dims, ty, offset));
    }
    let mut g = Gguf { map: map.clone(), version, metadata, tensors: Vec::new() };
    let align = g.get("general.alignment").and_then(Value::as_u64).unwrap_or(32) as usize;
    let data_start = r.at.div_ceil(align) * align;
    for (name, dims, ty, offset) in infos {
        let info = TensorInfo { name, dims, ty, offset: data_start + offset };
        if let Some(n) = info.ty.bytes(info.numel())
            && info.offset + n > map.len()
        {
            return Err(bad(format!("{}: data runs past the end of the file", info.name)));
        }
        g.tensors.push(info);
    }
    Ok(g)
}
  • The loop that stores each tensor checks its size against the file length. A truncated download fails here, with the tensor's name, instead of crashing later.
  • info.ty.bytes(info.numel()) gives the byte size from the type and the element count. For a block type it is a formula, not a stored number (see the next section on why).
  • r.at.div_ceil(align) * align rounds the end of the header up to the next multiple of the alignment. That is where the data starts.

Takeaway: every size the parser trusts is either read from the file and checked against its length, or computed from a known type.

Which metadata types exist?

Each metadata value has a type number, and the type says how many bytes follow. The list is in Reader::value. Here are the cases, with the layouts they read:

Type idLayoutStored as
0, 1u8, i8U64, I64
2, 3u16, i16U64, I64
4, 5u32, i32U64, I64
6f32F64
7bool (1 byte)Bool
8string (u64 length, bytes)Str
9array: element type u32, count u64, then the elementsArr
10, 11u64, i64U64, I64
12f64F64

The parser folds the widths into three number kinds: unsigned integers become U64, signed become I64, floats become F64. Bool, string and array keep their own variants. Two lines show the pattern. The first reads a fixed-width number, the second reads a string:

4 => Value::U64(self.u32()? as u64),
8 => Value::Str(self.string()?),
  • The Value enum has six variants: U64, I64, F64, Bool, Str and Arr.
  • An array holds values of one element type, which the parser reads once and reuses for every element.
  • A type number that is not in the table stops the load with unknown metadata type. The parser cannot skip a value whose size it does not know, so it stops rather than guess.

Takeaway: the type number tells the reader how many bytes to take, so the reader never has to guess a size.

How does the architecture come from metadata?

The model's shape is not written in the code. It comes from keys. The prefix is the architecture name, and the loader reads the rest of the key from the same file. In src/model/gguf.rs, the architecture name picks the code path:

let arch = g.get("general.architecture").and_then(Value::as_str)...;
let rope_layout = match arch.as_str() {
    "llama" => RopeLayout::AdjacentPairs,
    "qwen2" => RopeLayout::Halves,
    other => return Err(bad(format!("architecture {other:?} is not supported (llama, qwen2)"))),
};
let key = |k: &str| g.get(&format!("{arch}.{k}"));
  • general.architecture is the key that names the model family. For these files it is "llama" or "qwen2".
  • The closure key joins the prefix and the name, so attention.head_count means qwen2.attention.head_count for a Qwen file.
  • The rope layout is the one thing the numbers do not tell the loader. Only the architecture name does. A Qwen file read with the llama layout still loads and runs, and it produces garbage. The module comment in src/model/gguf.rs gives the details.

The numbers come from keys the loader reads by name. These are the ones in the code:

Key (with the prefix)Becomes
embedding_lengthdim, the width of the residual stream
feed_forward_lengthhidden_dim
block_countn_layers
attention.head_countn_heads
attention.head_count_kvn_kv_heads; if missing, equal to n_heads
context_lengthseq_len, capped by the caller's maximum
rope.freq_baserope_theta; default 10000 if missing
attention.layer_norm_rms_epsilonnorm_eps; required

The vocabulary size is not a key at all. The loader reads it from the shape of the embedding tensor, token_embd.weight. Qwen2.5 has no separate output matrix when its embeddings are tied, so the loader checks for output.weight and reuses the embedding table when it is missing:

classifier: if g.tensor("output.weight").is_some() {
    Some(matrix("output.weight", c.vocab_size, dim)?)
} else {
    None
},
  • None means tied: the output projection is the embedding table. That saves one matrix, and it is why the Qwen file has no output.weight.
  • Keys with a default (such as rope.freq_base) can be missing. Keys without one stop the load with a message naming the key.

Takeaway: the same parser reads a Llama and a Qwen file, and the architecture name decides only the few things the files really differ on.

Why must the data be aligned?

Alignment means an address is a multiple of a size. A 4-byte f32 should start at an address divisible by 4. Many processors are fastest when that holds, and some instructions need it. Rust's rules are stricter: a reference such as &[f32] must always point at an aligned address. Creating a misaligned one is undefined behaviour, even before any element is read, so the compiler is free to assume it never happens.

The file is written so the data is aligned. The header ends, the parser rounds up to general.alignment (32 by default), and every tensor offset is itself a multiple of that. Illustration: if the header ends at byte 1234, the next multiple of 32 is 1248, so the data starts there calculated.

The parser still checks, because a file can be wrong. Mapped::new is the function that turns a byte range of the file into a typed slice. It refuses a range that runs past the end or an address that is not aligned for its type:

pub fn new(map: Arc<Mmap>, offset: usize, len: usize) -> std::io::Result<Mapped<T>> {
    let bytes = len * std::mem::size_of::<T>();
    let bad = |m: String| std::io::Error::new(std::io::ErrorKind::InvalidData, m);
    if offset + bytes > map.len() {
        return Err(bad(format!("tensor at {offset} (+{bytes} B) beyond the file")));
    }
    if !(map.as_bytes().as_ptr() as usize + offset).is_multiple_of(std::mem::align_of::<T>()) {
        return Err(bad(format!("tensor at {offset} is not aligned for its type")));
    }
    Ok(Mapped { map, offset, len, _t: PhantomData })
}
  • The doc comment above the function gives the reason: "a misaligned &[T] would be undefined behaviour".
  • size_of::<T>() is the byte size of one element, so bytes is the whole range.
  • The address check adds the mapping's start address to the offset. The mapping starts on a page boundary, so in practice the offset decides the result.
  • Only after both checks does the function build a Mapped. Every later use of the slice relies on these checks having passed.

The unsafe code that turns the bytes into the slice has its own comment, which states what the check guaranteed:

impl<T> Deref for Mapped<T> {
    type Target = [T];
    fn deref(&self) -> &[T] {
        // SAFETY: `new` checked bounds and alignment; T is a plain-old-data
        // type (f32 or a block of integers) for which any bytes are valid;
        // the mapping lives as long as `self.map`.
        unsafe { std::slice::from_raw_parts(self.map.as_bytes().as_ptr().add(self.offset) as *const T, self.len) }
    }
}
  • The three facts in the SAFETY comment are the three things that make the cast sound: the bounds, the alignment, and the lifetime.
  • "Any bytes are valid" holds for f32 and for the block types, but not for bool or a reference. That is why the module only stores plain numbers this way.
  • If the comment's last fact were false, the slice could point into unmapped memory after the file was closed.

Takeaway: alignment is a rule of the format, the loader checks it, and the one unsafe cast depends on that check.

Are the weights copied into memory?

For the quantized and f32 weights, no. The file is mapped with mmap (the operating system makes a file appear in the address space, and pages are read from storage when first touched), and a weight is just a slice into that mapping. The loader's matrix helper decides per tensor:

GgmlType::F32 => Weight::F32(Floats::Mapped(Mapped::new(g.map.clone(), t.offset, n)?)),
GgmlType::Q8_0 => Weight::Q8_0(Store::Mapped(Mapped::new(g.map.clone(), t.offset, n / 32)?)),
GgmlType::Q4_0 => Weight::Q4_0(Store::Mapped(Mapped::new(g.map.clone(), t.offset, n / 32)?)),
GgmlType::F16 | GgmlType::BF16 => Weight::from(widen(g.data(t)?, t.ty, n)),
  • F32, Q8_0 and Q4_0 all use Mapped::new. No bytes are copied, so the kernel can evict those pages under memory pressure and read them again later.
  • F16 and BF16 are converted to f32 and copied, because the kernels here read f32 only for those types. The copy costs memory, which is why the quantized files are the ones used on the phone.
  • For a Q4_0 matrix, n / 32 is the number of blocks, not the number of weights. A block is 32 weights stored together with one scale.

How much a block holds follows from its size. Q4_0 stores 18 bytes per 32 weights, Q8_0 stores 34 bytes per 32 calculated:

Q4_0: 18 bytes / 32 weights = 0.5625 bytes per weight
Q8_0: 34 bytes / 32 weights = 1.0625 bytes per weight
f32:   4 bytes /  1 weight  = 4 bytes per weight
  • The block sizes are asserted in src/quant.rs at compile time, so a change to the struct layout fails the build.
  • The reader works out a block tensor's size from the type and the element count, as shown earlier. The file does not store a byte count for each tensor.
  • Smaller per weight means fewer bytes to stream each token. That is the whole reason for quantization on a phone, and the decode ceiling page works through the arithmetic.

Takeaway: a quantized weight in a GGUF file is used where it sits in the file, so the Q4_0 weights of this model (278 MB) are not copied into a second buffer.

Why compare two engines on the same bytes?

A speed or accuracy comparison is only fair if both programs read the same numbers. If each engine converted the model itself, the rounding and the block layout could differ, and the comparison would measure the conversion. So the test files are made once, by llama.cpp's own tools: convert_hf_to_gguf.py writes an f32 GGUF from the Hugging Face checkpoint, and llama-quantize makes the Q8_0 and Q4_0 versions from it.

Both engines then read those files. Ours is the parser on this page. llama.cpp's llama-bench and llama-perplexity read the same bytes. The benchmark script says so in its header: "on the same GGUF files" measured, scripts/phase7-bench.sh.

The result is that a difference in perplexity or speed comes from the engine, not from the file. The perplexity table on the Phase 7 overview is built this way: our Q8_0 and llama.cpp's Q8_0 agree to within llama.cpp's error bar, and both read the same Q8_0 file measured.

Takeaway: one file, two readers. Any difference between them is the reader's, not the file's.

Check yourself

Why does the parser store each tensor's offset as relative to data_start?

Because the header's length changes with the metadata and the number of tensors. The tensor data starts after the header and its padding, so an offset counted from the start of the data stays the same whatever the header size is. The parser adds data_start once per tensor.

A file has a type 13 metadata value. What happens, and why is stopping better than skipping?

The reader does not know the size of type 13, so it cannot find the next key. It returns unknown metadata type 13. Skipping would read the following bytes at the wrong position, and the rest of the header would be garbage without any error.

Why does a Qwen file have no output.weight tensor, and what does the loader use instead?

The embeddings are tied: the output projection uses the same numbers as the token embedding. The loader sets classifier to None and reuses the embedding table for the final projection. Saving one matrix in the file is the point.

The loader reads a Q4_0 matrix through Mapped::new with n / 32 elements. Why not n?

Q4_0 is stored as blocks, and Mapped<BlockQ4_0> is a slice of blocks. Each block covers 32 weights, so a matrix of n weights has n / 32 blocks. Passing n would read eight times too far, since the slice counts blocks, not weights.

What you should take away

A GGUF file is a typed header, a tensor index and an aligned block of data, all in one file.

The parser checks every size it trusts. The one unsafe cast depends on the alignment and bounds checks that come before it.

Both engines read the same bytes, which is what makes the Phase 7 comparisons fair.
