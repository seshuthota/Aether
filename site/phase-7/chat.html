Talking to a chat model

An instruct model was trained on conversations written in one exact text format. Ask it a question in that format and it answers, then stops. Ask the same question as plain text and it just keeps writing. This page shows the format Qwen2.5 uses, ChatML, and the eight lines in src/chat.rs that build it.

What are we trying to do here?

A language model only ever does one thing: predict the next token of a text. A base model learned that from ordinary text, so it continues whatever it is given. An instruct model (Qwen2.5-0.5B-Instruct here) was trained further on conversations, each written in a fixed layout that marks who is speaking and where each turn ends. That layout is its chat template.

To get an answer, the engine must give the model a text that looks exactly like the start of one of those conversations, ending just where the assistant’s reply begins. Then it must notice when the model writes the end-of-turn marker and stop there. By the end of this page you can write a ChatML prompt by hand and say which token ends the answer.

What happens if you just ask?

Give the instruct model the plain text “Write a haiku about rain.” with no template. To the model this is not a question from a user. It is the first line of some document, and its job is to guess how such documents go on.

Greedy decoding, 120 positions, plain text “Write a haiku about rain.”. What does Qwen2.5-0.5B-Instruct write?

  • A haiku, then more text until the length limit
    Nothing in plain text says where an answer ends, so it continues the document.
  • A haiku, then it stops
    Stopping needs the end-of-turn token, which only follows an open assistant turn.
  • Nothing useful; an instruct model only works with a template
    It still predicts text well; it just treats the request as the start of a document.

This is what our engine wrote, on the PC, greedy, from the Q8_0 GGUF:

Write a haiku about rain. Raindrops dance on the ground,
Softly, a symphony of nature's tune,
Nature's beauty in every drop.

(10 points)

In your haiku, include at least one word that describes
the sound of rain, ... (15 points)

(10 points)
  • It did write a haiku: the training made it good at following instructions.
  • Then it went on as if the text were a homework sheet, with marks and further tasks, until it reached the 120-position limit (113 generated tokens).

Takeaway: without its template, an instruct model treats your request as text to continue, and never knows when to stop.

What does a ChatML prompt look like?

Qwen2.5 uses ChatML. Every turn starts with the special token <|im_start|>, then the speaker’s role and a newline, then the text, then <|im_end|> and a newline. The roles are system (instructions for the assistant), user and assistant. This is the whole of src/chat.rs (the string split over lines to fit):

pub fn chatml(system: &str, user: &str) -> String {
    format!(
        "<|im_start|>system\n{system}<|im_end|>\n\
         <|im_start|>user\n{user}<|im_end|>\n\
         <|im_start|>assistant\n"
    )
}
  • The last line opens an assistant turn and leaves it open. The most likely next tokens are now the assistant’s reply.
  • <|im_start|> is id 151644 and <|im_end|> 151645. The tokenizer matches them as whole strings, so each is one token, not eleven characters.
  • With Qwen’s default system message, the haiku request becomes 36 tokens instead of 7. Prefill pays for the extra 29.

Takeaway: a ChatML prompt is the conversation so far plus an open assistant turn for the model to fill.

The prompt ends with <|im_start|>assistant but without the newline after it. What does the model do?

  • Writes the newline itself, then the usual reply
    In training a newline always followed the role, so it is the likeliest next token (measured: same haiku, one extra token).
  • Nothing changes: newlines are ignored by the tokenizer
    A newline is a byte like any other and has its own token.
  • The tokenizer fails on an unclosed turn
    The tokenizer only turns text into ids; it does not check the turn structure.

How does the model say it is done?

In every training conversation, the assistant’s text was followed by <|im_end|>. So when the reply is complete, the most likely next token is that marker. The engine does not have to judge whether the answer is finished. It only has to watch for that one id.

With the template, the same haiku request runs with a limit of 120 positions. How many tokens does the reply take?

  • About 20: three lines, then the end marker
    The model writes the haiku and then <|im_end|>, which stops generation.
  • About 84, up to the limit (36 prompt + 84)
    That would happen only if no stop token were ever sampled.
  • Exactly 17, one per syllable
    Tokens are not syllables; a haiku’s 17 syllables take some other number of tokens.
<|im_start|>assistant
Raindrops dance on the ground,
A symphony of nature's music,
Peace and tranquility.
prefill: 36 tokens ... | decode: 20 tokens

After those 20 tokens of text, the 21st token sampled was <|im_end|>, and generation stopped there without printing it. The list of stop ids comes from the model file: the GGUF’s tokenizer.ggml.eos_token_id (151645, the same <|im_end|>), plus <|im_end|> and <|endoftext|> (151643) by name, so a file that names a different end token still stops on both.

Takeaway: the model ends its own turn by producing <|im_end|>, and the engine stops when it samples any stop id.

A bug drops 151645 from the stop list. What does a chat reply look like?

  • The answer, then the model writes a new turn of its own, until the limit
    After <|im_end|> the likely continuation is another <|im_start|>, so it invents the next turn.
  • No change; the model stops by itself
    The model only predicts tokens; stopping is the engine’s decision.
  • Nothing is generated at all
    The stop list is only checked after each token; generation starts as usual.

Where does the system message come from?

The prompt above starts with a system turn: “You are Qwen, created by Alibaba Cloud. You are a helpful assistant.” The user never typed it. It comes from Qwen’s template, which adds that exact text whenever a conversation has no system message of its own. The model was trained with it, so it is part of what “the start of a normal conversation” looks like.

The engine keeps the text as QWEN_DEFAULT_SYSTEM and uses it unless the command line gives --system TEXT. A different system message is allowed, and it changes the model’s behaviour, which is the point of having one.

Takeaway: the default system message is part of Qwen’s template, so leaving it out changes the prompt the model expects.

Someone removes the system turn to save its 21 tokens of prefill. Is that a correctness bug?

  • Yes, for matching the reference: the ids differ from the template’s
    Qwen’s template would insert the default text, so the prompt no longer matches it.
  • No: a system message is optional decoration
    The template itself is not optional about it; it inserts one when none is given.
  • No: the model ignores system messages
    It was trained with them, so they do affect what it writes.

Why is the template written by hand?

Model files do carry their template: tokenizer_config.json and the GGUF’s tokenizer.chat_template hold it as a small program in Jinja, a template language from Python, with loops over messages, conditions for tools and the default system message. Running it in general would mean writing a Jinja interpreter in Rust.

The engine needs one format, for one system message and one user question. So chatml writes that case directly, and a test checks it against the reference. tools/chat_golden.py calls transformers’ apply_chat_template(..., add_generation_prompt=True) on four messages and saves the ids. The test matches_transformers_chat_template renders each message with chatml, tokenizes it, and requires the same ids.

  • The test checks the whole path: template text, special-token matching and BPE.
  • The limit is honest: multi-turn chats, tools and other template families are not supported, and the test would not cover them.

Takeaway: one hand-written format is enough for this engine, because the reference test proves it gives the template’s exact ids.

Another instruct model uses the same ChatML layout, but its template inserts a different default system message. What does the engine need?

  • The same chatml with that model’s default text, and its own golden ids
    The layout is shared; only the inserted text differs, and the test must use that model’s template.
  • A Jinja interpreter
    Only if formats beyond ChatML must be supported; the layout here is the same.
  • Nothing: Qwen’s default message works for every ChatML model
    Each model was trained with its own default, so the ids would not match its template.

What you should take away

An instruct model answers only when the prompt looks like the conversations it was trained on: ChatML turns with an open assistant turn at the end. It ends its own reply by producing <|im_end|>, and the engine stops on that id. One hand-written format is enough, because a test proves it gives exactly the ids of the model’s own template.

Generated text was produced by this engine on the host PC (greedy, Qwen2.5-0.5B-Instruct Q8_0, 2026-10-29); token ids are from Hugging Face transformers. Teal is measured, blue is calculated, amber is an assumption or a published claim we have not checked on this phone.
