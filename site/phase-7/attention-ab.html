Phase 7 · 01

NEON attention, measured honestly

Attention was 1.1 % of stories15M's time, so Phase 3 left it scalar. On Qwen2.5-0.5B at long contexts it was not small any more, and a NEON version was written later. Measuring its benefit turned out to be the interesting part: a single before-and-after run overstated the problem it fixed, and only an alternating A/B test gave a number worth keeping.

Jumping ahead

This page is Phase 7 work, and the pages for Phases 4–6 are not written yet. It only needs Phases 2 and 3 to follow: Qwen2.5-0.5B is a bigger model of the same shape, Q4_0 is a format that stores weights in about a seventh of the bytes, and “cores 2–7” means six threads, one per core.

Why attention grew

The weights cost the same every decode step. Attention's cost grows with the number of tokens in the KV cache: each step scores the query against every cached key and mixes every cached value. Qwen2.5-0.5B has 24 layers and 14 query heads of 64 numbers. At depth 512, every step does 24 × 14 × 513 dot products of length 64, plus as many weighted adds. Meanwhile Q4_0 quantization had made the weights 7 times smaller to read, so attention's share went up from both sides.

The scalar score loop is one dependency chain per key: the same problem Phase 3’s chains page solved for GEMV. The compiler cannot reorder float additions, so it cannot vectorize it either.

The NEON kernel

neon::attention_head keeps the scalar version's four steps and changes two loops:

for (t, s) in scores.iter_mut().enumerate() {
    *s = unsafe { dot_row(keys(t).as_ptr(), q.as_ptr(), hs) } * scale;   // 4 chains × 4 lanes
}
super::scalar::softmax(scores);                                          // unchanged
for (t, &a) in scores.iter().enumerate() {
    let av = vdupq_n_f32(a);
    for j in (0..hs4).step_by(4) {                                        // 4 lanes of out per FMA
        vst1q_f32(op.add(j), vfmaq_f32(vld1q_f32(op.add(j)), av, vld1q_f32(v.as_ptr().add(j))));
    }
}

Scores reuse GEMV's dot_row (four accumulators). The weighted sum keeps the output in memory and adds four lanes per FMA: each value row is independent, so there is no chain to break. Softmax stays scalar because it needs exp, and is a small part of the work. It was checked against numpy goldens of up to 1,024 positions, and the model tests still pass.

The phone drifts

The first measurement was a single table of runs: decode at depth 512 came out at 62.8 tokens per second with scalar attention, against 128.8 at depth 0. That looked like attention costing half the decode time. But the phone is not a stable machine:

  • It heats up under load, and the governor lowers clock caps as it does (Phase 1).
  • The caps also change with battery level, screen state and whatever else is running. On the A/B day the prime-core cap under load was 1.96 GHz; the day before it had been 2.44 GHz.
  • Other apps run: during this session a picture-in-picture video was playing.

If you run all of version A and then all of version B, any drift during the session is charged to whichever version ran later. The difference you measure is the real difference plus the drift.

Sequential vs alternating

A simulated phone that slows down steadily as it warms. B is truly 10 % faster than A illustration.

Same two versions, two run orders

The alternating order ABBABAAB is balanced: A's runs and B's runs have the same average position in time, so a steady drift falls on both equally and cancels out of the difference. Taking the median of several such rounds also discards a single disturbed run.

The result

Scalar attention (commit 0f56ed4) and NEON attention (8ae105c) run alternately, three rounds, each run started only when the phone was below 48 °C. Qwen2.5-0.5B Q4_0, cores 2–7, median of three, tokens per second measured:

NEON attention is +10 % at depth 512 and changes nothing at depth 0, which is what you would expect: with an empty cache there is almost no attention work. In time per token: at depth 512 scalar attention cost about 2.5 ms per token (11.5 vs 9.0 ms at depth 0), NEON attention about 1.5 ms (10.4 vs 9.0) calculated.

What changed in the record

Scalar attention went from 110.6 to 87.0 between depth 0 and 512 in the A/B, a 21 % drop, not the 51 % that the single table suggested. The 62.8 did not reproduce, so results/phase-7.md now says so next to it, and the claim that attention cost half the decode time at depth 512 was withdrawn. The cause of that one slow run is not established (the memory bus frequency, a likely suspect, cannot be read from the shell).

llama.cpp still loses less with depth (134.9 → 117.5). The next step on record is to split attention across positions as well as heads, since 14 heads over 6 threads leaves some threads idle.

The habit to keep

A speed comparison on a phone needs: the two versions run alternately in a balanced order, several rounds, a median, a temperature gate before each run, and the conditions written down. And a number that cannot be reproduced gets corrected in the record, not quietly replaced.

Check yourself

Why did attention matter for Qwen at depth 512 but not for stories15M?

Attention grows with the number of cached tokens, and Qwen has more layers and heads; meanwhile quantization shrank the weight reads. stories15M never goes past 256 tokens and its weights are f32.

Why is AAAABBBB a bad run order on a phone?

The phone's speed drifts (heat, clock caps, background work). All of B runs in a different state from all of A, so the drift is counted as a difference between the versions.

Why did NEON attention change nothing at depth 0?

With an empty cache each step attends over one or a few positions: almost no work for the faster kernel to save.

A single run says your change made things 20 % slower. What do you do before believing it?

Run old and new alternately in a balanced order, several rounds, from the same temperature, take medians, and record the conditions. Then compare.
