Phase 7 · 02

NEON attention, measured honestly

Attention was 1.1 % of stories15M’s time, so Phase 3 left it scalar (plain code, one number at a time). On Qwen2.5-0.5B at long contexts it was no longer small, so a NEON version (ARM’s vector instructions) was written later. Measuring its benefit turned out to be the interesting part. A single before-and-after run overstated the problem it fixed. Only an alternating A/B test gave a number worth keeping.

Jumping ahead

This page is Phase 7 work, and it needs only Phases 2 and 3. The threads it uses are explained in Phase 4. Qwen2.5-0.5B is a bigger model of the same shape, Q4_0 is a format that stores weights in about a seventh of the bytes, and “cores 2–7” means six threads, one per core.

Why did attention start to matter?

The weights cost the same at every decode step. Attention’s cost grows with the number of tokens in the KV cache, the stored keys and values of earlier tokens. Each step scores the query against every cached key and mixes every cached value.

Qwen2.5-0.5B has 24 layers and 14 query heads of 64 numbers. At depth 512, every step does 24 × 14 × 513 dot products of length 64, plus as many weighted adds. Meanwhile Q4_0 quantization (storing each weight in fewer bits) had made the weights 7 times smaller to read, so attention’s share went up from both sides.

A dependency chain is a sum where each addition has to wait for the one before. The scalar score loop is one chain per key, the same problem Phase 3’s chains page solved for GEMV (matrix times vector). The compiler cannot reorder float additions, so it cannot vectorize the loop either.

Measured only at depth 0, attention looks free, and the speed you quote will be too high for a long chat.

Takeaway: attention’s cost grows with depth, so a benchmark at depth 0 hides it.

What does the NEON version change?

neon::attention_head keeps the scalar version’s steps and changes two loops. NEON is the ARM vector unit, which works on four floats in one instruction. Build the new code one loop at a time.

Step 1: score each cached position

for (t, s) in scores.iter_mut().enumerate() {
    // SAFETY: keys(t) and q each hold hs floats, so dot_row may read hs from both pointers.
    *s = unsafe { dot_row(keys(t).as_ptr(), q.as_ptr(), hs) } * scale;   // 4 chains × 4 lanes
}
  • iter_mut().enumerate() gives each score slot s and its position t.
  • dot_row is GEMV’s dot product with four accumulators, so four separate chains run side by side, four lanes each.
  • * scale is applied to each score after the dot product.

Step 2: softmax, unchanged

super::scalar::softmax(scores);                                          // unchanged
  • Softmax stays scalar because it needs exp, and it is a small part of the work.

Step 3: add the values, weighted by the scores

for (t, &a) in scores.iter().enumerate() {
    let av = vdupq_n_f32(a);
    for j in (0..hs4).step_by(4) {                                        // 4 lanes of out per FMA
        vst1q_f32(op.add(j), vfmaq_f32(vld1q_f32(op.add(j)), av, vld1q_f32(v.as_ptr().add(j))));
    }
}
  • vdupq_n_f32(a) copies the score into all four lanes.
  • vfmaq_f32 is a fused multiply-add: it computes the output plus score × value for four floats in one instruction.
  • step_by(4) moves j four floats at a time, and op.add(j) is the output position.
  • Each value row is independent, so there is no chain to wait on. The output stays in memory and gets four lanes per step.

All three together

for (t, s) in scores.iter_mut().enumerate() {
    // SAFETY: keys(t) and q each hold hs floats, so dot_row may read hs from both pointers.
    *s = unsafe { dot_row(keys(t).as_ptr(), q.as_ptr(), hs) } * scale;   // 4 chains × 4 lanes
}
super::scalar::softmax(scores);                                          // unchanged
for (t, &a) in scores.iter().enumerate() {
    let av = vdupq_n_f32(a);
    for j in (0..hs4).step_by(4) {                                        // 4 lanes of out per FMA
        vst1q_f32(op.add(j), vfmaq_f32(vld1q_f32(op.add(j)), av, vld1q_f32(v.as_ptr().add(j))));
    }
}

The scores reuse GEMV’s dot_row with its four accumulators. The weighted sum keeps the output in memory and adds four lanes per FMA. It was checked against numpy goldens of up to 1,024 positions, and the model tests still pass.

Takeaway: NEON does four floats per instruction, and the two changed loops are the ones with independent work.

Why can one timing run mislead you?

The first measurement was a single table of runs: decode at depth 512 came out at 62.8 tokens per second with scalar attention, against 128.8 at depth 0. That looked like attention costing half the decode time. But the phone is not a steady machine:

  • It heats up under load, and the governor (the part that sets clock speeds) lowers clock caps as it does (Phase 1).
  • The caps also change with battery level, screen state and whatever else is running. On the A/B day the prime-core cap under load was 1.96 GHz; the day before it had been 2.44 GHz.
  • Other apps run: during this session a picture-in-picture video was playing.

If you run all of version A and then all of version B, any drift during the session is charged to whichever version ran later. The difference you measure is the real difference plus the drift.

Takeaway: one run mixes the change with the phone’s drift, so it cannot tell them apart.

Why does run order matter?

Here is a simulated phone that slows down steadily as it warms. B is truly 10 % faster than A illustration. Compare the two run orders.

Same two versions, two run orders

In AAAABBBB, all of B runs later in the drift, so the drift is counted against B. The alternating order ABBABAAB is balanced: A’s runs and B’s runs have the same average position in time, so a steady drift falls on both equally and cancels out of the difference. Taking the median of several such rounds also discards a single disturbed run.

Takeaway: alternate the runs in a balanced order, and steady drift cancels out of the difference.

What did the alternating test find?

Scalar attention (commit 0f56ed4) and NEON attention (8ae105c) ran alternately for three rounds. Each run started only when the phone was below 48 °C. Qwen2.5-0.5B Q4_0, cores 2–7, median of three, tokens per second measured:

depth 0depth 256depth 512
scalar attention110.696.887.0
NEON attention111.5103.895.7
llama.cpp, same session134.9 ± 6.6114.0 ± 12.2117.5 ± 8.5

NEON attention is +10 % at depth 512 and changes nothing at depth 0, which is what you would expect: with an empty cache there is almost no attention work. In time per token: at depth 512 scalar attention cost about 2.5 ms per token (11.5 vs 9.0 ms at depth 0), NEON attention about 1.5 ms (10.45 vs 8.97) calculated.

Takeaway: at depth 512 NEON attention is 10 % faster, and at depth 0 it makes no difference.

What changed in the record?

Scalar attention went from 110.6 to 87.0 between depth 0 and 512 in the A/B, a 21 % drop, not the 51 % that the single table suggested. The 62.8 did not reproduce, so results/phase-7.md now says so next to it, and the claim that attention cost half the decode time at depth 512 was withdrawn. The cause of that one slow run is not established. The memory bus frequency is a likely suspect, but the shell cannot read it.

llama.cpp still loses less with depth (134.9 → 117.5). The next step on record is to split attention across positions as well as heads, since 14 heads over 6 threads leaves some threads idle.

The habit to keep

A speed comparison on a phone needs: the two versions run alternately in a balanced order, several rounds, a median, a temperature gate before each run, and the conditions written down. And a number that cannot be reproduced gets corrected in the record, not quietly replaced.

Takeaway: a number that does not reproduce is corrected in the record, not quietly replaced.

Check yourself

Why did attention matter for Qwen at depth 512 but not for stories15M?

Attention grows with the number of cached tokens, and Qwen has more layers and heads; meanwhile quantization shrank the weight reads. stories15M never goes past 256 tokens and its weights are f32.

Why is AAAABBBB a bad run order on a phone?

The phone's speed drifts (heat, clock caps, background work). All of B runs in a different state from all of A, so the drift is counted as a difference between the versions.

Why did NEON attention change nothing at depth 0?

With an empty cache each step attends over one or a few positions: almost no work for the faster kernel to save.

A single run says your change made things 20 % slower. What do you do before believing it?

Run old and new alternately in a balanced order, several rounds, from the same temperature, take medians, and record the conditions. Then compare.

What you should take away

A speed-up claim is trustworthy only when it was measured where the work happens and in a way the phone's drift cannot fake.

Measure at depth, alternate the two versions, and when a number fails to repeat, correct it in the record.
