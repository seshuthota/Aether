Benchmarking like llama-bench

“How fast is it?” has no single answer for a language model. Reading a prompt and writing a reply are different kinds of work, speed changes as the conversation grows, and a phone changes speed by itself. This page shows how examples/bench_suite.rs measures, following llama.cpp’s llama-bench so the two engines can be compared number for number.

What are we trying to do here?

A benchmark is a measurement made the same way every time, so that two results can be compared. For an inference engine the questions are: how fast does it read a prompt, how fast does it write, how does that change as the context grows, how soon does the first word appear, and how much memory does it take.

llama.cpp answers the speed questions with llama-bench, and its notation is widely used, so bench_suite copies it. Both ran on the same phone, on the same GGUF files made by llama.cpp’s own tools, through scripts/phase7-bench.sh. The numbers below are Qwen2.5-0.5B-Instruct Q4_0 from 2026-10-21 (results/phase-7.md). The engine has become faster since then; this page is about the method.

Why are there two speeds?

Prefill reads the whole prompt in one batched pass. Decode then makes one token at a time, each a full pass over the weights. llama-bench writes them as pp N (“prompt processing”, a prompt of N tokens from an empty cache) and tg N (“text generation”, N new tokens), both in tokens per second.

Same model, same cores. Which has more tokens per second, pp512 or tg64?

  • pp512, by a wide margin
    Prefill reads each weight once for many tokens; decode reads every weight for each token.
  • tg64: generating is the engine’s main job, so it is the fastest path
    Being the main job does not make it cheap; each new token needs a full pass.
  • About the same: a token is a token
    The same arithmetic per token, but very different memory traffic per token.

llama.cpp’s numbers on cores 2–7: pp512 432 tok/s, tg64 125 tok/s. Decode reads all 278 MB of Q4_0 weights for every token, so it is limited by memory bandwidth (278 MB × 125 tok/s ≈ 35 GB/s). Prefill reuses each weight across all 512 prompt tokens, so it is limited by arithmetic instead. A single “tokens per second” would mix the two and hide both.

Takeaway: prefill and decode are different work, so a benchmark reports them separately.

Why measure decode at several depths?

Each new token attends to every earlier token in the KV cache, so decode gets slower as the conversation grows. llama-bench writes tg64 @ d512: 64 decode steps after 512 tokens are already in the cache. bench_suite fills the cache with an untimed prefill of D tokens, then times 64 single steps, recording each token’s own time.

Ours on 2026-10-21, cores 2–7: tg64 @ d0 128.8 tok/s, @ d256 113.2, @ d512 62.8. That last number looked like a serious problem in attention. It was not: the next day the same commit gave 110.6 → 87.0 in three alternating runs, so the 62.8 was mostly one bad run.

Takeaway: decode speed depends on context length, so it is measured at several depths, and a surprising depth result needs a repeat before it is believed.

An app user has a 2,000-token conversation. Which number predicts their reply speed best?

  • tg at a depth near 2,000
    Each reply token attends to the whole conversation, so depth 2,000 is the matching test.
  • tg64 @ d0
    That is the speed with an empty cache, the best case, not this user’s case.
  • pp2000
    That times reading a 2,000-token prompt, not writing the reply after it.

Do the prompt’s words matter?

A benchmark needs a prompt. Real text would have to be tokenized first, and different texts give different lengths.

Is prefill of 512 copies of “the” faster than prefill of 512 tokens of a real article?

  • No: the same work for any 512 ids
    Every token goes through the same matrices; the values change, the amount of arithmetic does not.
  • Yes: repeated tokens can be cached
    The engine computes every position; nothing is skipped for repeats in plain prefill.
  • Yes: common words have smaller numbers
    Multiplying by small values costs the same as by large ones.

So, like llama-bench, bench_suite uses synthetic token ids: a fixed pseudo-random sequence, the same in every run.

// Fixed pseudo-random token ids (an LCG), away
// from special tokens.
let tokens: Vec<usize> = (0..max_seq as u64)
    .map(|i| 100 + ((i * 2654435761 + 12345)
        % (vocab as u64 - 200)) as usize)
    .collect();
  • An LCG (linear congruential generator) is the simplest pseudo-random formula; it is enough here because only the count matters.
  • Starting at 100 and leaving out the top 100 ids avoids special tokens, whose ids sit at the ends of some vocabularies.
  • One exception: prompt lookup decoding does depend on the text, so it is measured on real text instead.

Takeaway: plain prefill and decode cost the same for any token ids, so a fixed synthetic sequence makes every run identical.

Which run is the real number?

A phone does not run at one speed. Clocks rise and fall with temperature, battery state and whatever else is running. One run gives one sample of that.

Ours was level with llama.cpp at tg64 on 2026-10-21 (128.8 vs 125.0). What did the same commits give the next day?

  • Ours about 20 % behind (111.5 vs 134.9)
    Measured; the day-to-day spread was as large as the gap itself.
  • Level again, within 1 %
    That would need the phone to be in the same state both days; it was not.
  • Ours 20 % ahead
    Possible in principle, but not what was measured.

So both programs repeat each test: llama-bench 5 times by default (3 here), reporting mean ± standard deviation; bench_suite 3 times, reporting the median (the middle value, which one bad run cannot drag), plus each token’s median and 95th-percentile time. Even then, the honest summary from these two days is “within about 20 %”, not “level”. When the question is whether a change helps, the stronger method is to run old and new alternately, so drift affects both equally.

Takeaway: one run is one sample of a moving target, so repeat, report the median and the spread, and alternate when comparing.

What must both engines share?

A comparison only means something if the only difference is the engine. scripts/phase7-bench.sh fixes everything else it can:

  • The same bytes: both read the same GGUF files from llama.cpp’s llama-quantize, so neither gets a better-quantized model.
  • The same cores: llama-bench is pinned with taskset to the cores ours uses, one thread per core (-t 6 for cores 2–7).
  • The same start: each run waits until the hottest CPU zone is below 48 °C, wakes the screen (screen-off lowers the clock caps), and records battery state and time.
  • Written down: the commit, the llama.cpp version (d00685831) and its build flags go in results/phase-7.md.

Takeaway: same files, same cores, same thermal start, and the conditions recorded with the numbers.

Ours runs on a file made by our own quantizer, llama.cpp on its own file. Ours is 5 % faster. What is wrong with the comparison?

  • The files may differ in format or bytes, so the engine is not the only difference
    A different file can change both the work and the accuracy; the same file removes that.
  • Nothing, if both files are called Q4_0
    The name fixes the layout but not which tensors were converted or how.
  • Only that 5 % is too small to matter
    Size is a separate question; the setup must be fair first.

What does a person actually notice?

Tokens per second is an engine’s number. A person notices two other things: how long until the reply starts, and whether the app gets killed for using too much memory.

Time to first token is prefill plus choosing one token: for a 64-token prompt, ours took 569 ms on cores 2–7. Peak RSS (resident set size, the most RAM the process held at once, read from VmHWM in /proc/self/status) was 348 MB: the 278 MB of weights, the KV cache and the buffers. llama-bench reports neither, so bench_suite adds them.

Takeaway: time to first token and peak memory are what a person feels, so the suite measures them too.

Prefill doubles in speed and decode stays the same. Which user number improves most?

  • Time to first token
    It is almost all prefill, so it roughly halves.
  • Peak memory
    Speed does not change how much the process holds.
  • The time per reply word
    That is decode, which did not change.
