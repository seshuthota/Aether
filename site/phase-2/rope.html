RoPE: position as rotation

Attention compares a query with keys, but a dot product cannot tell where a key came from. “The dog bit the man” and “The man bit the dog” would look the same. Rotary position embedding (RoPE) fixes this by rotating q and k by an angle that grows with the position. After the rotation, how well a query matches a key depends on how far apart the two tokens are.

The problem: attention has no sense of order

The score between a query and a key is their dot product (page 6). A dot product only looks at the two vectors. If the same word appears at position 3 and at position 40, its key is the same vector both times, so the query cannot prefer the nearby one. Word order would be invisible.

The fix is to change q and k depending on where their tokens are, in a way that makes the dot product sensitive to position. RoPE's trick is to do this with rotations, because rotations have a neat property you can see in the widget below.

Pairs of numbers as arrows

Take a head's 48 numbers two at a time: (q₀, q₁), (q₂, q₃), … That gives 24 pairs. Each pair can be drawn as an arrow on a flat plane, with the first number as the x coordinate and the second as y.

Rotating an arrow by an angle θ keeps its length and turns it:

x′ = x cos θ − y sin θ     y′ = x sin θ + y cos θ

Rotate by position

RoPE rotates every pair of q by an angle proportional to the token's position m, and every pair of k by the same rule for its position n. A token at position 0 is not rotated at all; at position 10 it is rotated ten times as far as at position 1.

Why only the distance matters

The dot product of two arrows depends only on their lengths and the angle between them. Rotate q by m steps and k by n steps, and the angle between them changes by (m − n) steps. Move both tokens forward by the same amount and both arrows turn equally; the angle between them, and so the score, stays put. Press “Move both +7” to see it.

So after RoPE, a query can learn “I want the token just before me” or “I want something about 20 tokens back”, and that preference works at any point in the text. Position is encoded as relative distance, which is what language needs.

Many speeds

If every pair turned at the same speed, positions 0 and one full turn later would look identical. So each pair turns at its own speed:

It works like the hands of a clock: the second hand tells fine time but repeats every minute; the hour hand is coarse but does not repeat all day. Together, the 24 pairs give every position within the context a distinct pattern, and fast pairs can track nearby tokens while slow ones track far ones. calculated from the formula.

θ is a setting of the model. stories15M uses 10,000; SmolLM2 uses 100,000 and Qwen2.5 1,000,000, which slows every pair down so that longer contexts stay distinguishable.

The code, and the two layouts

rope_adjacent in src/kernels/scalar.rs, applied to q and to this token's k (v is not rotated: values carry content, not position):

for head in v.chunks_exact_mut(head_size) {
    for i in (0..head_size).step_by(2) {
        let freq = 1.0 / theta.powf(i as f32 / head_size as f32);
        let angle = pos as f32 * freq;
        let (sin, cos) = (angle.sin(), angle.cos());
        let (v0, v1) = (head[i], head[i + 1]);
        head[i]     = v0 * cos - v1 * sin;
        head[i + 1] = v0 * sin + v1 * cos;
    }
}

Keys are rotated once, when they are computed, and stored rotated in the cache. Since a token's position never changes, there is no need to rotate them again later.

Two ways to pair the numbers

llama2.c pairs neighbours: (0, 1), (2, 3), … Hugging Face models pair element i with element i + 24: (0, 24), (1, 25), … (“rotate half”). It is the same maths on a different pairing, and it depends on how the weights were saved. Use the wrong one and the model still runs, and writes nonsense. Aether has both (rope_adjacent, rope_halves), and the model's config says which; Phase 5 needed the second.

Check yourself

Why can't plain attention (without RoPE) tell word order?

The score is a dot product of q and k, and those depend only on the tokens, not on where they are. The same word at two positions gives the same key.

A query at position 50 and a key at 45. Then a query at 150 and a key at 145, same vectors before rotation. Same score?

Yes. Both pairs are 5 apart, so the angle between the rotated arrows is the same, and so is the dot product.

Why is v not rotated?

Rotation is there to make the q·k comparison depend on distance. v is what gets mixed into the output; it should carry the token's content unchanged.

Why does each pair spin at a different speed?

A single speed would repeat after one turn, making far positions look like near ones. Fast pairs resolve small distances, slow pairs large ones, like the hands of a clock.
