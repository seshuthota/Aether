The KV cache

To generate token 100, attention needs the keys and values of tokens 0 to 99. They could be recomputed from scratch every time, but that would make each new token slower than the last. Instead the engine keeps them in a cache, so each step computes only its own key and value. This page shows why that is allowed, what it costs in memory, and how it is laid out.

Without a cache

Attention at position pos needs kt and vt for every t ≤ pos, in every layer. Each of those came out of a matrix multiply on that token's vector at that layer. Without saving them, generating token pos would mean running the whole model again on all pos + 1 tokens. Writing 256 tokens would cost 1 + 2 + … + 256 ≈ 33,000 token-passes instead of 256: about 130 times the work calculated.

Why keeping them is allowed

Because attention is causal, a token never looks forward. So nothing about token 5, at any layer, depends on tokens 6, 7, 8… Once token 5's key and value are computed, they are final. Adding new tokens later cannot change them. That is the whole justification, and it is why a cache is not an approximation: the output is exactly the same as recomputing.

Queries are not cached. A query is used once, by its own token, to look back. Only keys and values are looked up later, hence “KV cache”.

Layout in memory

Two big buffers, key_cache and value_cache, each laid out as [layer][position][kv_dim]:

The forward pass computes this token's k and v directly into the cache row, so there is no copy:

let layer_off = l * c.seq_len * kv_dim;   // start of this layer's block
let at = layer_off + pos * kv_dim;        // this position's row
k::matmul(&mut s.key_cache[at..at + kv_dim], &s.xb, &lw.wk);

Within a row, the 288 numbers are the 6 heads of 48 one after another, so head h's key at position t is the 48 floats starting at t × 288 + h × 48. The cache is allocated once, at full size (256 positions), when the model is loaded. Nothing is allocated while generating.

How big it gets

cache bytes = layers × positions × kv_dim × 2 (K and V) × bytes per number

KV cache size

For stories15M the full cache is 6 × 256 × 288 × 2 × 4 bytes = 3.5 MB calculated, small next to its 60.8 MB of weights. For bigger models at long contexts the cache can rival the weights; then the answers are fewer key/value heads (grouped-query attention, which SmolLM2 and Qwen use), storing the cache in 16 or 8 bits, or both.

The cache is read every step

Memory is not the only cost. At position pos, each layer reads pos + 1 keys and pos + 1 values. So decode reads the weights plus a growing cache. For stories15M at position 255 that is 3.5 MB on top of 60.8 MB, a few percent. For Qwen2.5 at depth 512 it became visible: decode slowed from 110 to 87 tokens per second, which led to the NEON attention kernel in Phase 7 measured.

Check yourself

Why does caching k and v give exactly the same output as recomputing them?

Attention is causal: a token's k and v depend only on that token and earlier ones, so later tokens cannot change them. The cached copy is the value recomputing would produce.

Why is q not cached?

Each query is used once, by its own token. Later tokens compare their queries with earlier keys; they never need an earlier query.

How many bytes does one token add to stories15M's cache?

6 layers × 288 × 2 (K and V) × 4 bytes = 13,824 bytes, 13.5 KB.

Generation got slower as the text got longer, even with a cache. Why?

Each step still reads every cached key and value to compute attention, and there are more of them as the text grows. The weights cost the same every step; the cache part grows.

Measured numbers come from the iQOO 13 (SM8750) in October 2026, on battery, and are in results/ in the repo. Teal is measured, blue is calculated, amber is an assumption or an illustration.
