The KV cache

To generate token 100, attention needs the keys and values of tokens 0 to 99. Recomputing them for every token would make each new token slower than the last. So the engine keeps them in a cache, and each step computes only its own key and value. This page shows why that is allowed, what it costs in memory, and how it is laid out.

What happens without a cache?

Attention at position pos needs kt and vt for every t ≤ pos, in every layer. These are the key and value vectors (one of each per token, per layer) that attention compares and mixes. Each of them came out of a matrix multiply on that token’s vector at that layer. Without saving them, generating token pos would mean running the whole model again on all pos + 1 tokens. Writing 256 tokens would cost 1 + 2 + … + 256 ≈ 33,000 token-passes instead of 256: about 130 times the work calculated.

Takeaway: without the cache, each new token pays again for every earlier token.

Is it safe to keep them?

Keeping them is safe only if they never change. Attention is causal: a token looks at itself and the tokens before it, never after. So nothing about token 5, at any layer, depends on tokens 6, 7, 8… Once token 5’s key and value are computed, they are final, and new tokens cannot change them. That is why a cache is not an approximation: the output is exactly the same as recomputing.

Queries are not cached. A query is the vector a token uses to look back. It is used once, by its own token. Only keys and values are looked up later, hence “KV cache”.

Takeaway: keys and values are final once computed, so storing them changes the speed, not the output.

Where do the numbers sit in memory?

Two big buffers, key_cache and value_cache, each laid out as [layer][position][kv_dim]. Read it as nested blocks: all of layer 0 comes first, then layer 1, and within a layer each position is one row of kv_dim numbers.

The forward pass computes this token’s k and v directly into the cache row, so there is no copy:

let layer_off = l * c.seq_len * kv_dim;   // start of this layer's block
let at = layer_off + pos * kv_dim;        // this position's row
k::matmul(&mut s.key_cache[at..at + kv_dim], &s.xb, &lw.wk);
  • l * c.seq_len * kv_dim is where layer l’s block starts: the blocks of the layers before it come first.
  • pos * kv_dim is the row for this position inside that block.
  • &mut s.key_cache[at..at + kv_dim] is that one row as a slice, and the matmul writes straight into it.

Within a row, the 288 numbers are the 6 heads of 48 one after another (a head is one of several attention computations that run side by side), so head h’s key at position t is the 48 floats starting at t × 288 + h × 48. The cache is allocated once, at full size (256 positions), when the model is loaded. Nothing is allocated while generating.

Takeaway: one offset calculation finds any position’s row in any layer, and nothing is copied.

How big does the cache get?

cache bytes = layers × positions × kv_dim × 2 (K and V) × bytes per number

KV cache size

For stories15M the full cache is 6 × 256 × 288 × 2 × 4 bytes = 3.5 MB calculated, small next to its 60.8 MB of weights. For bigger models at long contexts the cache can rival the weights; then the answers are fewer key/value heads (grouped-query attention, where several query heads share one key/value head, as SmolLM2 and Qwen use), storing the cache in 16 or 8 bits, or both.

Takeaway: the cache grows with the context length; for stories15M it is small next to the weights.

Does reading the cache cost anything?

Memory is not the only cost. At position pos, each layer reads pos + 1 keys and pos + 1 values, so decode reads the weights plus a growing cache. For stories15M at position 255 that is 3.5 MB on top of 60.8 MB, about 6 % calculated. For Qwen2.5 at depth 512 it became visible: decode slowed from 110 to 87 tokens per second, which led to the NEON attention kernel in Phase 7 measured.

Takeaway: every step reads the cache as well as the weights, so long text slows decode.

Check yourself

Why does caching k and v give exactly the same output as recomputing them?

Attention is causal: a token's k and v depend only on that token and earlier ones, so later tokens cannot change them. The cached copy is the value recomputing would produce.

Why is q not cached?

Each query is used once, by its own token. Later tokens compare their queries with earlier keys; they never need an earlier query.

How many bytes does one token add to stories15M's cache?

6 layers × 288 × 2 (K and V) × 4 bytes = 13,824 bytes, 13.5 KB.

Generation got slower as the text got longer, even with a cache. Why?

Each step still reads every cached key and value to compute attention, and there are more of them as the text grows. The weights cost the same every step; the cache part grows.

What you should take away

Keys and values are computed once per token and kept, so each step computes only its own.

The cache is two buffers laid out by layer, then position, then head, and a position’s row is found by an offset.

The cache adds memory and read traffic that grow with the text, which matters for long contexts.
