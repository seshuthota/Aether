The MLP and the residual stream

After attention has mixed information between tokens, each layer’s second half works on every token by itself. It widens the vector to 768 numbers, lets a gate decide what passes, and narrows back to 288. This is the MLP, and it holds two thirds of each layer’s weights. Both halves add their result into one running vector, the residual stream, which carries the token through the whole model.

Why does each half add to x?

Look at how each half of a layer ends:

k::add_inplace(&mut s.x, &s.xb2);   // after attention:  x += attention(x)
k::add_inplace(&mut s.x, &s.xb);    // after the MLP:    x += mlp(x)
  • add_inplace adds its second buffer into the first, changing it in place.
  • &mut s.x is the running total, so x is the one that changes.
  • &s.xb2 is the attention result and &s.xb the MLP result; both are only read.

Neither block replaces x. Each reads a normalised copy, computes something, and adds it. So x is a running total: the embedding, plus layer 0’s attention, plus layer 0’s MLP, plus layer 1’s attention, and so on. This is the residual stream; the additions are residual connections.

Why build it this way? A block that has nothing useful to add can output nearly zero and leave x alone. Training a deep stack is much easier when each layer only has to learn a small correction instead of a whole new representation. For the engine, one buffer x lives through the whole token, and each block works in scratch buffers beside it.

Takeaway: each block adds a correction to x, and x is the one vector that lives through the whole token.

What shape does the MLP have?

The MLP starts from the same 288 numbers and must end with 288. Between them it widens. MLP stands for multi-layer perceptron, an old name for “matrix multiply, nonlinearity, matrix multiply”. Llama-family models use a variant with three matrices:

Name in the codellama2.c nameShapeDoes
w_gatew1768 × 288288 → 768, then through SiLU
w_upw3768 × 288288 → 768, multiplied by the gate
w_downw2288 × 768768 → 288, back to the stream

Widening to 768 gives the layer room: 768 channels, each of which can respond to some pattern in the input. Narrowing back writes a 288-number correction into the stream.

Takeaway: the MLP widens 288 to 768 and narrows back, so its output is a 288-number correction.

What does the gate do to each channel?

Without a nonlinearity, a step that bends the numbers instead of only scaling and adding them, two matrix multiplies are just one bigger matrix multiply, and stacking layers would add nothing. Here the nonlinearity is a gate:

hi = SiLU(gatei) × upi    for each of the 768 channels

The input is projected twice. The gate projection goes through the SiLU function and decides how much of the channel gets through; the up projection decides what gets through. A strongly negative gate shuts the channel (SiLU ≈ 0); a large positive gate lets up through, scaled by about the gate’s own value, because SiLU(g) ≈ g there. This gated design is called SwiGLU (Swish-Gated Linear Unit; Swish is another name for SiLU).

Takeaway: SiLU of the gate decides how much of each channel passes, and up decides what passes.

What does the SiLU curve look like?

The gate needs a function that shuts off for very negative inputs and passes large positive ones. SiLU does both. Its formula is:

SiLU(x) = x × sigmoid(x) = x ÷ (1 + e−x)

Take x = 1.5: SiLU is 1.5 ÷ (1 + e−1.5) ≈ 1.5 ÷ 1.223 ≈ 1.23. Take x = −6: SiLU is −6 ÷ 404 ≈ −0.015, almost 0.

SiLU, and what the gate does

The solid curve is SiLU; the dashed line is ReLU (max(0, x)), the older choice, for comparison. Move the gate value and the up value.

For large positive x, SiLU is almost x; for large negative x, almost 0; near zero it is smooth, with a small dip below zero (lowest about −0.28, at x ≈ −1.28). The smoothness is what training likes about it compared with ReLU’s sharp corner. At inference it is simply a function to compute, 768 times per layer.

Takeaway: SiLU is near x for large positive inputs and near 0 for large negative ones.

How does the code compute the MLP?

In the forward pass, the MLP is six calls:

k::rmsnorm(&mut s.xb, &s.x, &lw.ffn_norm, c.norm_eps);   // normalised copy of x
k::matmul(&mut s.hb,  &s.xb, &lw.w_gate);                  // gate: 768 numbers
k::matmul(&mut s.hb2, &s.xb, &lw.w_up);                    // up:   768 numbers
k::swiglu(&mut s.hb, &s.hb2);                              // hb = silu(gate) × up
k::matmul(&mut s.xb, &s.hb, &lw.w_down);                   // back to 288
k::add_inplace(&mut s.x, &s.xb);                            // x += mlp
  • The first call writes a normalised copy of x into xb, and the two matmuls read from that copy.
  • The gate and up each fill a 768-number buffer, hb and hb2.
  • swiglu writes into hb, so hb is its first argument.
  • The last matmul writes 288 numbers back into xb, and add_inplace adds them to x.

And swiglu itself, in llama2.c’s exact order of operations:

for (g, &u) in gate.iter_mut().zip(up) {
    let mut v = *g;
    v *= 1.0 / (1.0 + (-v).exp());   // silu
    v *= u;                           // × up
    *g = v;
}
  • zip walks the gate and up values together, one channel at a time.
  • let mut v = *g; copies the gate value out of its reference.
  • v *= 1.0 / (1.0 + (-v).exp()); is SiLU, with 1 ÷ (1 + e−v) computed first.
  • v *= u; is the gating, and *g = v; stores the result back.

Writing v * (1 / (1 + e−v)) instead of v / (1 + e−v) is mathematically the same but can round differently in the last bit. To be bit-identical with llama2.c, the code copies its form exactly.

Takeaway: the MLP is six calls, and the swiglu loop is where the gate is applied.

The MLP holds two thirds of every layer’s weights, and since decode time follows bytes read, about two thirds of each layer’s time calculated. Larger models keep roughly that ratio: Qwen2.5-0.5B’s MLP is 896 → 4,864 → 896.

Takeaway: the MLP holds two thirds of each layer’s weights, so it takes most of each layer’s time.

Check yourself

What would go wrong if a block did x = block(x) instead of x += block(x)?

Each block would have to rebuild the whole representation instead of adding a correction, and a block with nothing to add could not simply pass x through. Deep stacks become much harder to train. (For the engine, the trained weights only work with the structure they were trained with.)

SiLU(gate) is about 0. What does that channel contribute?

About nothing: SiLU(gate) × up ≈ 0 whatever up is. The gate has shut the channel.

Why is a nonlinearity needed between the matrices at all?

Two matrix multiplies in a row are equivalent to one matrix (their product). Without a nonlinearity, the MLP and indeed the whole stack would collapse into a single linear map.

The MLP multiplies by three matrices; attention by four. Why does the MLP still have more weights?

Its matrices are 768 × 288, attention's 288 × 288. Three of 221,184 is more than four of 82,944.

What you should take away

Each half of a layer adds a correction to x, and x carries the token through the model.

The MLP widens 288 to 768, gates each channel with SiLU, and narrows back to 288.

Without the nonlinearity, the MLP would collapse into a single matrix multiply.
