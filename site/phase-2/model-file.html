Inside a model file

A trained model is just a long list of numbers on disk. This page opens stories15M.bin: 28 bytes that describe the shapes, then 15.2 million floats in a fixed order. Once you know the order, loading the model is reading the file front to back.

What are “the weights”?

The file is a long run of unlabelled numbers. Which ones make the model? The answer starts with what training leaves behind.

Training a model means adjusting millions of numbers until the model predicts text well. When training stops, those numbers are frozen and saved. They are the weights, also called parameters. Running the model, which is all this engine does, never changes them; it only reads them.

Almost all of them are arranged as matrices: grids of numbers that turn one vector into another by matrix-vector multiplication. A few are single vectors, plain lists of numbers (the norm gains you will meet on page 3).

A file format has to answer two questions: what shapes are these matrices? and where in the file does each one start? Without the shapes, the bytes are just a list. Without the order, you read a matrix from the wrong place. llama2.c’s format answers the first with a tiny header and the second with a fixed order. There are no names, no offsets, no metadata. Phase 5 and Phase 6 meet richer formats (safetensors, GGUF) that do store names.

Takeaway: the weights are frozen numbers, and the file must give their shapes and the order they come in.

What does the 28-byte header tell you?

The loader needs the size of every block before it reads any weight. So the file opens with a header, a fixed-size block of bytes read first. This one is 28 bytes, which is seven whole numbers.

Each number is a 32-bit integer: a whole number stored in 4 bytes. They are little-endian, so the least significant byte (the low end of the number) comes first, which is how ARM and x86 store numbers in memory. The first four bytes are 20 01 00 00. Read low byte first, that is 0x0120, which is 288, the first field below.

Those seven numbers fix the size of everything after them. Every later position is worked out from these sizes, so one wrong number moves everything after it. If any of them is zero, or negative (except vocab_size), the file is broken and the loader refuses it.

Try it on your PC

xxd -l 28 stories15M.bin prints the header. The first four bytes are 20 01 00 00: 0x0120 = 288, stored low byte first.

Takeaway: the seven header numbers set the size of every block after them, so check them before you read any weight.

Where does each weight block start?

The weights are 60.8 MB of raw floats with no label on any of them. To load one block, you need its starting byte. The only way to know it is the order the file was written in.

After the header the weights follow as raw 32-bit floats, one block after another, always in the same order. A tensor here is one block of one kind of weight. Each tensor holds that kind of weight for all six layers back to back: first all six wq matrices, then all six wk, and so on. So layer 1’s wq sits directly after layer 0’s wq, not after the whole wk block.

Two things stand out:

  • The embedding is the biggest single tensor: 32,000 × 288 = 9.2 million floats, 36.9 MB, 61 % of the file. A small model with a big vocabulary spends most of its size on the vocabulary.
  • The norm gains are tiny: 288 floats per norm. They matter for the maths, not for memory.

Add up the matrices a token actually multiplies by (the 6 layers plus the classifier) and you get 15.19 million weights, 60.8 MB as f32 calculated. That is the number of bytes every generated token has to read, which is why it comes back on page 12.

Takeaway: the file is a fixed run of blocks, so the loader finds each one by its position, not by a name.

How does a matrix lie flat in a file?

A file is one line of numbers, but a matrix is a grid. The format has to pick one way to turn the grid into the line. Take a small 3 × 4 matrix in the figure below, with the letters a to l. llama2.c uses row-major order: each row is stored in full before the next one starts. Row 0 comes first, then row 1, and so on.

So element (row i, column j) sits at index i × 288 + j in a 288-wide matrix. In the figure, e is row 1, column 0, so its index is 1 × 4 + 0 = 4. If you used column × width + row instead, you would read a different number.

Every matrix in this file is stored as [outputs, inputs]: one row per output number. To compute output i you take the dot product of row i with the input vector. So wq (288 × 288) has one row per number of the query, and w1 (768 × 288) one row per number of the MLP's wide hidden vector.

Takeaway: row-major puts each row in one run, so element (i, j) is at i × width + j.

Do the embedding and classifier share one table?

The model needs a table at both ends, and both are 32,000 × 288. The embedding turns a token id into a vector at the start. The classifier turns the final vector back into one score per token at the end.

Many small models use the same table for both; this is called tying the embeddings. Tying saves 36.9 MB here. The header says which case you are in through the sign of vocab_size: positive means tied, negative means the classifier has its own weights at the end of the file. Read the sign wrong and you would expect 36.9 MB of classifier weights that a tied file does not contain. stories15M is tied.

Takeaway: check the sign of vocab_size first; a positive value means the classifier reuses the embedding table.

How does the loader walk the file without losing its place?

The loader must take 60.8 MB of bytes in exactly the order the format gives. One wrong size and every block after it is read from the wrong place. So it keeps a cursor: a position in the file that moves forward each time it hands out a block. src/model/llama2c.rs reads the whole file in one go, then walks it in four steps.

Step 1: the embedding

let token_embedding = cursor.take(c.vocab_size * dim)?;
  • take(n) hands out the next block of n floats and moves the cursor past it.
  • c.vocab_size * dim is 32,000 × 288, the whole embedding table.
  • ? passes an error up to the caller, if there is one.

Step 2: the per-layer weights

let rms_att = cursor.take_layers(layers, dim)?;
let wq = cursor.take_layers(layers, dim * dim)?;
let wk = cursor.take_layers(layers, kv_dim * dim)?;
// … wv, wo, rms_ffn, w1, w2, w3 …
  • take_layers takes the block that holds this kind of weight for all six layers, in layer order.
  • dim * dim is 288 × 288, so one wq layer is 82,944 floats.
  • kv_dim is the width of the key and value rows. For stories15M it equals dim, because the key/value heads equal the heads.

Step 3: the last norm and the skipped table

let final_norm = cursor.take(dim)?;
cursor.skip(c.seq_len * c.head_size())?; // old RoPE table, not needed
  • skip moves the cursor past bytes without copying them.
  • The RoPE table is skipped because the loader does not need it. Older llama2.c versions stored precomputed rotation angles. Aether computes them itself (page 5).

Step 4: check that every byte was used

if cursor.remaining() != 0 { /* refuse: the shapes did not add up */ }
  • remaining() counts the bytes the cursor did not use. Any left over means the shapes do not match the file.

All four together

let token_embedding = cursor.take(c.vocab_size * dim)?;
let rms_att = cursor.take_layers(layers, dim)?;
let wq = cursor.take_layers(layers, dim * dim)?;
let wk = cursor.take_layers(layers, kv_dim * dim)?;
// … wv, wo, rms_ffn, w1, w2, w3 …
let final_norm = cursor.take(dim)?;
cursor.skip(c.seq_len * c.head_size())?; // old RoPE table, not needed
if cursor.remaining() != 0 { /* refuse: the shapes did not add up */ }

Three details of the code:

  • Every tensor is copied into an aligned buffer (AlignedBuf, 64-byte aligned). The bytes in the file are not aligned for vector loads; the copies are.
  • The leftover RoPE table is skipped. Aether does not use it.
  • The loader checks that nothing is left over. If the header's shapes do not account for every byte, the file is refused. That one check catches a wrong header, a truncated download and a file in another format.

Loading copies 60.8 MB, which is fine for this model. Phase 5 switches to memory mapping (mmap) for files of hundreds of megabytes, so the operating system pages weights in on demand instead.

Takeaway: the loader takes each block in file order, and its last check catches a file whose sizes do not add up.

Check yourself

How many bytes is one layer's w1, and where does that number come from?

768 rows × 288 columns × 4 bytes = 884,736 bytes, about 864 KB. Rows = outputs (the hidden width), columns = inputs (dim), 4 bytes per f32.

The file has no names in it. How does the loader know which bytes are wk?

Only by position: the order is fixed by the format, and the header gives every size. wk starts right after the embedding, the six rms_att vectors and the six wq matrices.

Why is the classifier missing from the end of stories15M.bin?

Because the model is tied: vocab_size in the header is positive, so the classifier reuses the embedding table. The forward pass multiplies the final vector by the embedding matrix.

Element (row 2, column 5) of wq for layer 0. At what index inside the wq block is it?

2 × 288 + 5 = 581. For layer l you would add l × 288 × 288 first, because each layer's matrix follows the previous one.

What you should take away

A model file is just numbers, so the loader needs a map to them.

The header gives the sizes, the fixed block order gives each position, and the loader checks that the map and the file agree to the last byte.
