Inside a model file

A trained model is just a long list of numbers on disk. This page opens stories15M.bin: 28 bytes that describe the shapes, then 15.2 million floats in a fixed order. Once you know the order, loading the model is reading the file front to back.

What “the weights” are

Training a model means adjusting millions of numbers until the model predicts text well. When training stops, those numbers are frozen and saved. They are the weights (also called parameters). Running the model, which is all this engine does, never changes them; it only reads them.

Almost all of them are arranged as matrices: grids of numbers that turn one vector into another by matrix-vector multiplication. A few are single vectors (the norm gains you will meet on page 3).

A file format has to answer two questions: what shapes are these matrices? and where in the file does each one start? llama2.c's format answers the first with a tiny header and the second with a fixed order. There are no names, no offsets, no metadata. Phase 5 and Phase 6 meet richer formats (safetensors, GGUF) that do store names.

The 28-byte header

The file starts with seven 32-bit integers, 4 bytes each, little-endian (the least significant byte first, which is how ARM and x86 store numbers in memory):

BytesFieldstories15MUsed for
0–3dim288width of every token vector
4–7hidden_dim768width inside the MLP
8–11n_layers6how many blocks
12–15n_heads6attention heads (head size = 288 ÷ 6 = 48)
16–19n_kv_heads6key/value heads (equal here; fewer in Phase 5's models)
20–23vocab_size32000number of tokens; its sign also matters (see tied)
24–27seq_len256longest context the model was trained on

Those seven numbers fix the size of everything after them. If any of them is zero, or negative (except vocab_size), the file is broken and the loader refuses it.

Try it on your PC

xxd -l 28 stories15M.bin prints the header. The first four bytes are 20 01 00 00: 0x0120 = 288, stored low byte first.

The map of the file

After the header the weights follow as raw 32-bit floats, one tensor after another, always in the same order. Each tensor holds that kind of weight for all six layers back to back: first all six wq matrices, then all six wk, and so on.

Two things stand out:

  • The embedding is the biggest single tensor: 32,000 × 288 = 9.2 million floats, 36.9 MB, 61 % of the file. A small model with a big vocabulary spends most of its size on the vocabulary.
  • The norm gains are tiny: 288 floats per norm. They matter for the maths, not for memory.

Add up the matrices a token actually multiplies by (the 6 layers plus the classifier) and you get 15.19 million weights, 60.8 MB as f32 calculated. That is the number of bytes every generated token has to read, which is why it comes back on page 12.

Row-major: how a matrix lies flat

A file is one-dimensional, so a 288 × 288 matrix has to be laid out as a line of 82,944 numbers. llama2.c uses row-major order: all of row 0, then all of row 1, and so on. Element (row i, column j) sits at index i × 288 + j.

Every matrix in this file is stored as [outputs, inputs]: one row per output number. To compute output i you take the dot product of row i with the input vector. So wq (288 × 288) has one row per number of the query, and w1 (768 × 288) one row per number of the MLP's wide hidden vector.

Tied embeddings

The model needs a table at both ends: the embedding turns a token id into a vector at the start, and the classifier turns the final vector back into one score per token at the end. Both are 32,000 × 288.

Many small models use the same table for both; this is called tying the embeddings. It saves 36.9 MB here. The header says which case you are in through the sign of vocab_size: positive means tied, negative means the classifier has its own weights at the end of the file. stories15M is tied.

The loader in Rust

src/model/llama2c.rs reads the file in one go and walks it with a small cursor that hands out one tensor at a time, in file order:

let token_embedding = cursor.take(c.vocab_size * dim)?;
let rms_att = cursor.take_layers(layers, dim)?;
let wq = cursor.take_layers(layers, dim * dim)?;
let wk = cursor.take_layers(layers, kv_dim * dim)?;
// … wv, wo, rms_ffn, w1, w2, w3 …
let final_norm = cursor.take(dim)?;
cursor.skip(c.seq_len * c.head_size())?; // old RoPE table, not needed
if cursor.remaining() != 0 { /* refuse: the shapes did not add up */ }

Three details are worth noticing:

  • Every tensor is copied into an aligned buffer (AlignedBuf, 64-byte aligned). The bytes in the file are not aligned for vector loads; the copies are.
  • The leftover RoPE table is skipped. Older llama2.c versions stored precomputed rotation angles. Aether computes them itself (page 5).
  • The loader checks that nothing is left over. If the header's shapes do not account for every byte, the file is refused. That one check catches a wrong header, a truncated download and a file in another format.

Loading copies 60.8 MB, which is fine for this model. Phase 5 switches to memory mapping (mmap) for files of hundreds of megabytes, so the operating system pages weights in on demand instead.

Check yourself

How many bytes is one layer's w1, and where does that number come from?

768 rows × 288 columns × 4 bytes = 884,736 bytes, about 864 KB. Rows = outputs (the hidden width), columns = inputs (dim), 4 bytes per f32.

The file has no names in it. How does the loader know which bytes are wk?

Only by position: the order is fixed by the format, and the header gives every size. wk starts right after the embedding, the six rms_att vectors and the six wq matrices.

Why is the classifier missing from the end of stories15M.bin?

Because the model is tied: vocab_size in the header is positive, so the classifier reuses the embedding table. The forward pass multiplies the final vector by the embedding matrix.

Element (row 2, column 5) of wq for layer 0. At what index inside the wq block is it?

2 × 288 + 5 = 581. For layer l you would add l × 288 × 288 first, because each layer's matrix follows the previous one.
