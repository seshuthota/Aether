First speed: 88.6 tok/s

With the model correct, here is the first speed measurement: 88.6 tokens per second (tok/s) on one prime core, slightly ahead of llama2.c on the same phone. This page asks what that number means. The profile says 97.6 % of the time goes to matrix-vector products (one dot product per row of the weight matrix), and arithmetic on the measurements shows they are not waiting for memory. They are waiting for themselves.

How fast is it, and can you trust the number?

Speed numbers are easy to misread, so start with how this one was taken. The run used aether stories15M.bin -t 0 -n 256 -i "Once upon a time" -c CORE, greedy (-t 0, which always picks the most likely next token), three runs per core, on battery, on 2026-10-21 measured:

CoreAether (scalar, 1 thread)llama2.c run, NDK clang -O3
7 (prime)88.3 / 88.8 / 88.6 tok/s84.9 / 84.7 / 84.6 tok/s
0 (performance)58.6 / 58.4 / 58.3 tok/s58.1 / 58.1 / 57.4 tok/s

Run-to-run spread is under 1 %. The two engines are within 5 % of each other, which is what you would expect: they do the same arithmetic in the same order, in the same plain loops.

Conditions matter

A cap is a limit the phone sets on clock speed. On battery, the phone capped the prime cores at 2.44 GHz under load, far below their 4.32 GHz maximum (and the performance cores at 2.40 of 3.53 GHz). simpleperf counted an average of 2.38 GHz, confirming the cap. Every number on this site was taken under such caps; Phase 1 explains why they move. Compare numbers taken under different caps and you compare clocks, not code.

Takeaway: 88.6 tok/s is a real measurement, but only under the battery caps, so compare it only with numbers taken under the same caps.

Where does the time go?

simpleperf is Android’s profiler. simpleperf record samples which function the CPU is running, thousands of times a second (Phase 1). On core 7 measured:

scalar::matmul97.6 %
scalar::attention_head1.1 %
sampler, exp, rmsnorm, …< 0.4 % each

This is exactly what the work budget predicted: the matrix-vector products are the program. Everything else could be ten times slower and nobody would notice. So the question becomes: how fast is matmul, and what limits it? Optimise the 1.1 % first and you gain almost nothing.

Takeaway: matmul takes 97.6 % of the time, so only its speed moves the total much.

Is memory the limit?

A slow loop could be waiting for DRAM, the main memory. To rule that out, compare the bytes per second the loop needs with what memory can supply. Every token reads all 60.8 MB of weights. At 88.6 tokens per second:

60.8 MB × 88.6 per second = 5.4 GB/s calculated

Phase 1 measured that one prime core can read from DRAM at about 61 GB/s. The scalar loop uses under a tenth of that. If memory were the limit, the core would be waiting on loads; it is not. The counters agree: of 2.34 billion L1 data loads, only 5.4 million missed measured. (L1 is the small, fast cache closest to the core; a miss means the data came from further away.) The hardware prefetcher, which fetches memory ahead of need, sees the loop walking straight through each row and fetches the next lines long before they are needed. The slow loop gives it all the time in the world.

Takeaway: the loop uses about 5.4 GB/s of the roughly 61 GB/s a core can read, so memory is not the limit.

Why does one multiply-add take 1.77 cycles?

A cycle is one tick of the CPU clock. A modern core can start several floating-point operations per cycle, so this count is slow. Here it is, from the same counters: 6.10 billion cycles for the run, 97.6 % of them in matmul, which did 222 tokens × 15.19 million multiply-adds:

6.10 G × 0.976 ÷ (222 × 15.19 M) ≈ 1.77 cycles per multiply-add calculated

The reason is in the loop, built in steps.

Step 1: the running sum

let mut acc = 0.0f32;
  • acc is the accumulator: the running sum of the products. mut lets it change.
  • 0.0f32 starts it at zero as a 32-bit float.

Step 2: add each product

for (&wi, &xi) in row.iter().zip(x) {
    acc += wi * xi;          // needs the previous acc
}
  • zip pairs each weight wi in the row with the matching input xi.
  • acc += wi * xi multiplies the pair and adds the product into acc.
  • The comment is the point: each new acc needs the old one, so the additions form a chain.

All together

let mut acc = 0.0f32;
for (&wi, &xi) in row.iter().zip(x) {
    acc += wi * xi;          // needs the previous acc
}

Each acc += … needs the result of the previous one. The compiled loop (disassembled from this source) loads and multiplies four pairs at a time with NEON, the ARM vector instructions, then adds the four products into acc one by one with plain fadd instructions (floating-point add), keeping the source’s order. The multiplications are independent and run ahead, but every addition sits in one long chain. Each waits for the one before it to produce its result: that wait is its latency. This is the same kind of chain that held the Phase 0 sum to 3.3 GB/s.

1.77 is less than one add’s latency

The chain here is plain adds, not the fused multiply-adds (one instruction that multiplies and adds) of Phase 3’s chains page, which takes their latency as about 4 cycles. A plain add is quicker: take about 2 cycles on this core assumption. But one chain of 2-cycle adds cannot do better than 2 cycles per add, and 1.77 is below that. The likely reason: each output row has its own acc, so the next row’s chain does not depend on this one, and the out-of-order core starts it before the current row has finished. For part of the time, two chains overlap. Not checked yet: timing one very long row, where there is no next row to overlap with, would test it.

Why doesn’t the compiler fix it, by using several accumulators or vector instructions? Because that changes the order of the additions, and with floats that changes the result (page 11). The compiler is not allowed to change your answer, so it keeps the chain. To break it, you have to write the different order yourself and accept the different last bits. That is Phase 3.

Takeaway: each addition waits for the one before it, and the compiler will not reorder them, so the chain stays.

Why is the prime core faster than the performance core?

The prime core was 1.52 times faster than the performance core, although their caps were nearly equal (2.44 vs 2.40 GHz). A latency-bound loop should run at about the same speed on two cores of the same design at the same clock. This is not explained yet. The next things to check are Phase 1’s per-core sweeps and a simpleperf stat on core 0, to see whether its real clock under load was lower than the cap or its cycles per multiply-add are higher.

Takeaway: the prime core is 1.52 times faster at nearly the same cap, and the reason is not known yet.

What does Phase 3 do about it?

  • Several accumulators break the one chain into four or eight independent running sums, so several additions are in flight at once.
  • NEON does four multiply-adds per instruction.
  • Together they take the same matrix from 5.3 to 53 GB/s on one core, and stories15M from 88.6 to 422 tokens per second measured. At that point the loop finally is close to memory’s limit.

Read on: Phase 3 · NEON kernels.

Takeaway: Phase 3 breaks the chain into several sums and uses NEON, the two things this page points at.

Check yourself

How do you know the scalar loop is not limited by memory bandwidth?

It moves 5.4 GB/s while one core can read about 61 GB/s, and almost every load hits in L1 because the prefetcher has run ahead. The core is not waiting on memory.

Why can't the compiler just vectorize acc += w * x?

Vectorizing means summing in a different order, and float addition is not associative, so the result would change. The compiler must keep your order unless you allow otherwise.

The profile shows 97.6 % in matmul. What is the most anything else could ever save?

2.4 % of the time. Speeding up the rest, even to zero, cannot make the program more than about 2.5 % faster. Optimise matmul first.

Aether and llama2.c differ by 5 % but do identical arithmetic. Where might the 5 % come from?

Different code around the arithmetic: how loops are compiled, bounds checks, the allocator, how the matrix rows are walked. Small differences in instruction count per multiply-add move a latency-bound loop's speed by a few percent. (Not measured in detail.)

What you should take away

The first speed is 88.6 tok/s, and matrix-vector products do almost all of the work.

The loop is not limited by memory; it is limited by a chain of additions that must wait in order.

Phase 3 breaks that chain and uses NEON, and the prime-versus-performance gap is still open.
