First speed: 88.6 tok/s

With the model correct, the first speed measurement: 88.6 tokens per second on one prime core, slightly ahead of llama2.c on the same phone. This page is about what that number means. The profile says 97.6 % of the time is matrix-vector products, and arithmetic on the measurements shows they are not waiting for memory. They are waiting for themselves.

The measurements

aether stories15M.bin -t 0 -n 256 -i "Once upon a time" -c CORE, greedy, three runs per core, on battery, 2026-10-21 measured:

CoreAether (scalar, 1 thread)llama2.c run, NDK clang -O3
7 (prime)88.3 / 88.8 / 88.6 tok/s84.9 / 84.7 / 84.6 tok/s
0 (performance)58.6 / 58.4 / 58.3 tok/s58.1 / 58.1 / 57.4 tok/s

Run-to-run spread is under 1 %. The two engines are within 5 % of each other, which is what you would expect: they do the same arithmetic in the same order, in the same plain loops.

Conditions matter

On battery, the phone capped the prime cores at 2.44 GHz under load, far below their 4.32 GHz maximum (and the performance cores at 2.40 of 3.53 GHz). simpleperf counted an average of 2.38 GHz, confirming the cap. Every number on this site was taken under such caps; Phase 1 explains why they move.

Where the time goes

simpleperf record samples which function the CPU is in, thousands of times a second (Phase 1). On core 7 measured:

scalar::matmul97.6 %
scalar::attention_head1.1 %
sampler, exp, rmsnorm, …< 0.4 % each

Exactly what the work budget predicted: the matrix-vector products are the program. Everything else could be ten times slower and nobody would notice. So the question becomes: how fast is matmul, and what limits it?

It is not memory (yet)

Every token reads all 60.8 MB of weights. At 88.6 tokens per second:

60.8 MB × 88.6 per second = 5.4 GB/s calculated

Phase 1 measured that one prime core can read from DRAM at about 61 GB/s. The scalar loop uses under a tenth of that. If memory were the limit, the core would be waiting on loads; it is not. The counters agree: of 2.34 billion L1 data loads, only 5.4 million missed measured. The hardware prefetcher sees the loop walking straight through each row and fetches the next lines long before they are needed. The slow loop gives it all the time in the world.

It is a dependency chain

From the same counters: 6.10 billion cycles for the run, 97.6 % of them in matmul, which did 222 tokens × 15.19 million multiply-adds:

6.10 G × 0.976 ÷ (222 × 15.19 M) ≈ 1.77 cycles per multiply-add calculated

A modern core can start several floating-point operations per cycle, so 1.77 cycles for one multiply and one add is slow. The reason is in the loop:

let mut acc = 0.0f32;
for (&wi, &xi) in row.iter().zip(x) {
    acc += wi * xi;          // needs the previous acc
}

Each acc += … needs the result of the previous one. The compiled loop (disassembled from this source) loads and multiplies four pairs at a time with NEON, then adds the four products into acc one by one with plain fadd instructions, keeping the source’s order. The multiplications are independent and run ahead, but every addition sits in one long chain: each waits for the one before it to produce its result (its latency). This is the same kind of chain that held the Phase 0 sum to 3.3 GB/s.

1.77 is less than one add’s latency

The chain here is plain adds, not the fused multiply-adds of Phase 3’s chains page, which takes their latency as about 4 cycles. A plain add is quicker: take about 2 cycles on this core assumption. But one chain of 2-cycle adds cannot do better than 2 cycles per add, and 1.77 is below that. The likely reason: each output row has its own acc, so the next row’s chain does not depend on this one, and the out-of-order core starts it before the current row has finished. For part of the time, two chains overlap. Not checked yet: timing one very long row, where there is no next row to overlap with, would test it.

Why doesn't the compiler fix it, by using several accumulators or vector instructions? Because that changes the order of the additions, and with floats that changes the result (page 11). The compiler is not allowed to change your answer, so it keeps the chain. To break it, you have to write the different order yourself, and accept the different last bits. That is Phase 3.

Prime vs performance core

The prime core was 1.52 times faster than the performance core, although their caps were nearly equal (2.44 vs 2.40 GHz). A latency-bound loop should run at about the same speed on two cores of the same design at the same clock. This is not explained yet. The next things to check are Phase 1's per-core sweeps and a simpleperf stat on core 0, to see whether its real clock under load was lower than the cap or its cycles per multiply-add are higher.

What Phase 3 does about it

  • Several accumulators break the one chain into four or eight independent ones, so several additions are in flight at once.
  • NEON does four multiply-adds per instruction.
  • Together they take the same matrix from 5.3 to 53 GB/s on one core, and stories15M from 88.6 to 422 tokens per second measured. At that point the loop finally is close to memory's limit.

Check yourself

How do you know the scalar loop is not limited by memory bandwidth?

It moves 5.4 GB/s while one core can read about 61 GB/s, and almost every load hits in L1 because the prefetcher has run ahead. The core is not waiting on memory.

Why can't the compiler just vectorize acc += w * x?

Vectorizing means summing in a different order, and float addition is not associative, so the result would change. The compiler must keep your order unless you allow otherwise.

The profile shows 97.6 % in matmul. What is the most anything else could ever save?

2.4 % of the time. Speeding up the rest, even to zero, cannot make the program more than about 2.5 % faster. Optimise matmul first.

Aether and llama2.c differ by 5 % but do identical arithmetic. Where might the 5 % come from?

Different code around the arithmetic: how loops are compiled, bounds checks, the allocator, how the matrix rows are walked. Small differences in instruction count per multiply-add move a latency-bound loop's speed by a few percent. (Not measured in detail.)
