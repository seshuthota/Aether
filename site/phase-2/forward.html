The forward pass in code

Every part from pages 3 to 9 meets in one function: forward_traced in src/model/transformer.rs. It takes one token id and its position and returns 32,000 logits. This page walks through it line by line, with the work each line costs, so you can see where a token's time must go before measuring it.

What goes in, what comes out

pub fn forward(&mut self, token: usize, pos: usize) -> &[f32]

One token, one position, 32,000 logits back. Positions must come in order 0, 1, 2…, because step pos reads the cache entries that steps 0 to pos − 1 wrote. The function takes &mut self because it writes into the cache and the scratch buffers; the weights are only read.

The buffers

All working memory is allocated once, in Transformer::new, and reused for every token. Generating text allocates nothing.

BufferSize (stories15M)Holds

Everything except the cache adds up to about 150 KB, so it lives in the L1 and L2 caches the whole time. The weights are what streams from memory.

The work budget of one token

5.97 Mmultiply-adds in the 6 layers' matrices
9.22 Min the classifier alone
15.19 Mtotal, = weights read
≤ 0.9 Meverything else: attention, up to 0.88 M at position 255 (0.39 M on average over a 222-token story); norms, RoPE and SwiGLU about 0.02 M

Two lessons from this table, both confirmed by the profile on page 12:

  • Matrix-vector products are almost all of the work. Make matmul fast and the whole model is fast. Everything else can stay simple for a long time.
  • For this small model, the classifier is 61 % of it. A 32,000-word vocabulary on a 288-wide model is lopsided. In bigger models the layers dominate: Qwen2.5-0.5B's 24 layers hold about 2.6 times as many weights as its classifier calculated.

And since every weight is used for exactly one multiply-add, the number of multiply-adds equals the number of weights read: 15.19 M weights, 60.8 MB per token. That ratio, 2 FLOPs per 4 bytes, is the reason decode is a memory problem in the end (roofline).

The observer: watching from outside

The real function is forward_traced, which takes one more argument: an observer. After each step it calls obs.tap("name", layer, pos, data):

k::rmsnorm(&mut s.xb, &s.x, &lw.attn_norm, c.norm_eps);
obs.tap("attn_norm", Some(l), pos, &s.xb);

Normal generation passes NoTrace, whose tap is empty and marked #[inline(always)], so the compiler deletes every call: it costs nothing. The tests pass an observer that records every activation, which is how each of them is compared with llama2.c (next page). The same 14 names appear in the reference's dump, so a mismatch points straight at the first step that went wrong.

Check yourself

Why must positions be fed in order?

Step pos reads the keys and values that steps 0 to pos − 1 wrote into the cache. Skip one and attention reads an empty or stale row.

Which single line costs the most for stories15M?

The classifier: 32,000 × 288 = 9.2 M multiply-adds, more than all six layers together.

Why doesn't the tracing slow down normal generation?

With NoTrace every tap is an empty inlined function, so the compiler removes the calls. Rust's generics generate a separate copy of forward_traced for each observer type.

A matrix-vector product reads every weight once. What does that make the FLOPs per byte?

One multiply-add (2 FLOPs) per 4-byte weight: 0.5 FLOP per byte. Very low, which is why decode ends up limited by memory bandwidth once the arithmetic is fast.

Measured numbers come from the iQOO 13 (SM8750) in October 2026, on battery, and are in results/ in the repo. Teal is measured, blue is calculated, amber is an assumption or an illustration.
