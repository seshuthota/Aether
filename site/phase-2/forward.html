The forward pass in code

Every part from pages 3 to 9 meets in one function: forward_traced in src/model/transformer.rs. It takes one token id and its position and returns 32,000 logits, one raw score for each vocabulary entry. This page walks through it line by line, with the work each line costs, so you can see where a token’s time must go before measuring it.

What goes in, and what comes out?

Generation calls the model once per token, and each call needs to know where in the text it is. So the function takes two numbers and returns one array:

pub fn forward(&mut self, token: usize, pos: usize) -> &[f32]
  • token is the id from the tokenizer page, such as 9038.
  • pos is the position: 0 for the first token, 1 for the second, and so on.
  • &[f32] is a slice, a borrowed view of 32,000 floats: the logits.

One token, one position, 32,000 logits back. Positions must come in order 0, 1, 2…, because step pos reads the cache entries that steps 0 to pos − 1 wrote. The function takes &mut self because it writes into the cache and the scratch buffers; the weights are only read.

Takeaway: one call takes a token id and its position, and positions must arrive in order.

Where does the working memory live?

Each step needs scratch space: arrays for the stream, the normalised copy and the scores. All of it is allocated once, in Transformer::new, and reused for every token. Generating text allocates nothing. Allocating them again for each token would repeat that work.

Takeaway: the scratch space is allocated once, and the weights are what streams from memory.

What does each line cost?

Each line is one step of the forward pass. A multiply-add is one multiply and one add, the unit this table counts. The code with the observer calls (below) left out. Multiply-adds are for stories15M calculated.

Takeaway: the first argument of each call is the one it writes, and the multiply-add column says what it costs.

Where does a token’s time go?

Adding up the table gives the work for one token, in multiply-adds.

5.97 Mmultiply-adds in the 6 layers' matrices
9.22 Min the classifier alone
15.19 Mtotal, = weights read
≤ 0.9 Meverything else: attention, up to 0.88 M at position 255 (0.39 M on average over a 222-token story); norms, RoPE and SwiGLU about 0.02 M

Two lessons from this table, both confirmed by the profile on page 12:

  • Matrix-vector products are almost all of the work. Make matmul fast and the whole model is fast. Everything else can stay simple for a long time.
  • For this small model, the classifier is 61 % of it. A 32,000-word vocabulary on a 288-wide model is lopsided. In bigger models the layers dominate: Qwen2.5-0.5B's 24 layers hold about 2.6 times as many weights as its classifier calculated.

Every weight is used for exactly one multiply-add, so the multiply-adds equal the weights read: 15.19 M weights, 60.8 MB per token. That is 2 FLOPs (floating-point operations) per 4 bytes, and it is why decode, the step that makes one token at a time, ends up a memory problem (roofline).

Takeaway: nearly all the work is matrix-vector products, and for this model the classifier is most of it.

How do you watch the values without slowing it down?

To compare with llama2.c you need values from inside the function, not only the final logits. The real function, forward_traced, takes one more argument: an observer. After each step it calls obs.tap("name", layer, pos, data):

k::rmsnorm(&mut s.xb, &s.x, &lw.attn_norm, c.norm_eps);
obs.tap("attn_norm", Some(l), pos, &s.xb);
  • &mut s.xb is the output, &s.x the input, &lw.attn_norm the layer’s gain, c.norm_eps the epsilon (page 3).
  • tap hands the result to the observer: a name, the layer number (Some(l) wraps it, Rust’s way of saying “there is a value”), the position and the data.

Normal generation passes NoTrace, whose tap is empty and marked #[inline(always)], which asks the compiler to paste the body into each call. So the compiler deletes every call: it costs nothing. The tests pass an observer that records every activation, which is how each of them is compared with llama2.c (next page). The same 14 names appear in the reference’s dump, so a mismatch points straight at the first step that went wrong.

Takeaway: the observer costs nothing in normal runs, and it gives the tests a point to compare at each step.

Check yourself

Why must positions be fed in order?

Step pos reads the keys and values that steps 0 to pos − 1 wrote into the cache. Skip one and attention reads an empty or stale row.

Which single line costs the most for stories15M?

The classifier: 32,000 × 288 = 9.2 M multiply-adds, more than all six layers together.

Why doesn't the tracing slow down normal generation?

With NoTrace every tap is an empty inlined function, so the compiler removes the calls. Rust's generics generate a separate copy of forward_traced for each observer type.

A matrix-vector product reads every weight once. What does that make the FLOPs per byte?

One multiply-add (2 FLOPs) per 4-byte weight: 0.5 FLOP per byte. Very low, which is why decode ends up limited by memory bandwidth once the arithmetic is fast.

What you should take away

A token costs one call, and nearly all of it is weights streaming through matrix-vector products.

Because the call runs in a fixed order and writes known buffers, a test can compare it step by step against a reference at no cost to normal runs.
