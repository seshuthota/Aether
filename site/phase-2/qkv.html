Queries, keys, values, heads

Attention lets each token pull in information from the tokens before it. To do that, every token produces three vectors: a query (what am I looking for?), a key (what do I contain?) and a value (what do I hand over if chosen?). This page is about where those three vectors come from, and why they are cut into six heads.

What are a query, a key and a value?

A token has to decide which earlier tokens matter to it. A library shows how the three vectors do that job.

Picture a library. You walk in with a question (the query). Every book has a label on its spine (the key) and contents inside (the value). You compare your question with every label, and the books whose labels match best are the ones you read most from. You walk out with a blend of contents, weighted by how well each label matched.

In the model, the “books” are the earlier tokens, including the current one. The current token's query is compared with every earlier token's key, and the answer is a weighted mix of their values. Page 6 does that comparison. This page builds the three vectors.

Takeaway: a query asks, each key is matched against it, and the matching values are mixed into the answer.

How do three matrix multiplies make q, k and v?

A token needs a question, a label and contents, and all three come from the same input: the normalised vector xb (288 numbers). Each one goes through its own learned matrix:

q = Wq · xb    k = Wk · xb    v = Wv · xb

Each matrix is 288 × 288 in stories15M, so each of q, k, v is 288 numbers. They start from the same input but differ because the matrices differ: training taught Wq to produce good questions, Wk good labels and Wv useful contents.

The code in src/model/transformer.rs builds them in three steps, starting with the query.

Step 1: the query

k::matmul(&mut s.q, &s.xb, &lw.wq);
  • k::matmul is a matrix-vector multiply: for each of the 288 rows, a dot product of that row with xb.
  • It writes into s.q. The query is used only now, to look back, so it is not stored.

Step 2: the key

k::matmul(&mut s.key_cache[at..at + kv_dim], &s.xb, &lw.wk);
  • key_cache[at..at + kv_dim] is a slice of the KV cache: kv_dim numbers starting at at, this token's place in the cache.
  • The key goes straight into the cache, because every later token will need it. Leave this write out and later tokens have no key to compare against.

Step 3: the value

k::matmul(&mut s.value_cache[at..at + kv_dim], &s.xb, &lw.wv);
  • Same pattern as the key: the value goes into the cache at the same position, for the same reason.

All three together

k::matmul(&mut s.q, &s.xb, &lw.wq);
k::matmul(&mut s.key_cache[at..at + kv_dim], &s.xb, &lw.wk);
k::matmul(&mut s.value_cache[at..at + kv_dim], &s.xb, &lw.wv);

This is the Phase 2 code. Phase 4 later adds the pool argument and switches from matmul to linear_on (k::linear_on(pool, …)), so that several cores share the rows; the arithmetic stays the same. One matrix here is 82,944 multiply-adds (a multiply, then an add).

Takeaway: three matrix multiplies turn xb into q, k and v, and the key and value go into the cache.

Why cut the vectors into six heads?

One query can ask only one question, but a token often needs several things at once: the subject of the sentence, the previous word, whether a quote is open. So the 288 numbers are cut into 6 heads of 48 numbers. A head is one slice of the vectors, with its own attention.

Each head is a smaller copy of the library. Head 2's query is compared only with head 2's keys, and it mixes only head 2's values. Its slice is numbers 96 to 143 of q, k and v, and the figure shows the slice for every head.

Because the heads never interact, they can run in any order, or in parallel on different cores, which Phase 4 does.

Takeaway: a head is a slice of the same q, k and v, and it attends only within its own slice.

How do six heads become one vector again?

Each head outputs 48 numbers, and side by side the six outputs form a 288-number vector again. The heads have not exchanged anything yet. One more 288 × 288 matrix, Wo (the output projection), mixes them so information from different heads can combine. The result is added to the residual stream, the running vector that every layer adds its result to:

k::matmul(&mut s.xb2, &s.xb, &lw.wo);   // mix the heads
k::add_inplace(&mut s.x, &s.xb2);        // x += attention's contribution
  • The first line writes the mixed heads into xb2.
  • The second line adds xb2 into x, the residual stream. += adds to the old value; it does not replace it. Skip this line and the attention output never reaches the residual stream.

Takeaway: Wo mixes the heads, and the result is added to the residual stream rather than written over it.

Do all query heads need their own key/value head?

In stories15M every query head has its own key/value head (n_kv_heads = n_heads = 6). Bigger models save memory by letting several query heads share one key/value head. This is grouped-query attention. Phase 5 needs it: SmolLM2-135M has 9 query heads and 3 key/value heads, so each group of 3 query heads reads the same keys and values.

The code already handles this with one line, which picks the shared head:

let kv_off = (h / group) * hs;  // query head h reads K/V head h / group
  • h is the query head, and group is how many query heads share each key/value head.
  • hs is the head size, 48 here. kv_off is where that key/value head's 48 numbers start.
  • With group = 1, as in stories15M, that is just head h. A wrong group makes a query head read another head's keys.

Takeaway: grouped-query attention lets several query heads read one key/value head, and stories15M uses one each.

How much work does this cost?

Count the multiply-adds for one layer. The table lists the four projections and the attention itself.

MatrixShapeMultiply-adds per token, per layer
Wq288 × 28882,944
Wk288 × 28882,944
Wv288 × 28882,944
Wo288 × 28882,944
attention itself6 heads × (pos + 1) positions × 48 × 2576 × (pos + 1)

The four projections are fixed work: 331,776 multiply-adds per layer, whatever the position calculated. Attention grows with the number of earlier tokens. At stories15M's 256-token limit it is 147,456 multiply-adds per layer, less than half of the four projections, and the MLP is bigger again. Over a 222-token story, counting all six layers and the final classifier, it averages about 2.5 % of a token's multiply-adds calculated. That is why attention is only 1.1 % of the time on the profile, and why it only became worth optimising for a bigger model at longer contexts (Phase 7).

Takeaway: the four projections cost the same at every position, while attention grows with each earlier token.

Check yourself

q, k and v are all computed from the same xb. Why are they different?

Each is multiplied by its own learned matrix (Wq, Wk, Wv). Same input, different transformations.

Why are k and v written into the cache, but q is not?

Later tokens compare their own query with this token's key and mix in this token's value, so k and v are needed again. This token's query is only used now, to look back; nobody looks it up later.

How many numbers are in one head of stories15M, and where does that come from?

48: dim ÷ n_heads = 288 ÷ 6. A head is a slice, not a separate matrix.

SmolLM2-135M has 9 query heads and 3 key/value heads. Which key/value head does query head 7 read?

group = 9 ÷ 3 = 3, so head 7 ÷ 3 = 2 (integer division). Query heads 6, 7, 8 share key/value head 2.

What you should take away

Three matrices turn one vector into a query, a key and a value.

Keys and values go into the cache, and heads are slices that mix only at Wo.

Attention's share of the work grows with the context, while the four projections stay fixed.
