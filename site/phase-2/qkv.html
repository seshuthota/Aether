Queries, keys, values, heads

Attention lets each token pull in information from the tokens before it. To do that, every token produces three vectors: a query (what am I looking for?), a key (what do I contain?) and a value (what do I hand over if chosen?). This page is about where those three vectors come from, and why they are cut into six heads.

The idea, in a library

Picture a library. You walk in with a question (the query). Every book has a label on its spine (the key) and contents inside (the value). You compare your question with every label; the books whose labels match best are the ones you read most from. What you walk out with is a blend of contents, weighted by how well each label matched.

In the model, the “books” are the earlier tokens, including the current one. The current token's query is compared with every earlier token's key, and the answer is a weighted mix of their values. Page 6 does that comparison. This page builds the three vectors.

Three matrix multiplies

All three come from the same normalised vector xb (288 numbers), each through its own learned matrix:

q = Wq · xb    k = Wk · xb    v = Wv · xb

Each matrix is 288 × 288 in stories15M, so each of q, k, v is 288 numbers. They start from the same input but are different because the matrices are different: training taught Wq to produce good questions, Wk good labels and Wv useful contents.

In the code (src/model/transformer.rs), k and v are written straight into the KV cache, at this token's position, because every later token will need them:

k::matmul(&mut s.q, &s.xb, &lw.wq);
k::matmul(&mut s.key_cache[at..at + kv_dim], &s.xb, &lw.wk);
k::matmul(&mut s.value_cache[at..at + kv_dim], &s.xb, &lw.wv);

This is the Phase 2 code. Phase 4 later adds one argument, the thread pool (k::linear_on(pool, …)), so that several cores share the rows; the arithmetic stays the same. Each matmul is a matrix-vector multiply: for each of the 288 rows, a dot product of that row with xb. That is 82,944 multiply-adds per matrix.

Heads: six small attentions

One query can only ask one question. A token often needs several things at once: the subject of the sentence, the previous word, whether a quote is open. So the 288 numbers are cut into 6 heads of 48 numbers, and each head runs attention on its own.

Each head is a smaller copy of the library: head 2's query is compared only with head 2's keys and mixes only head 2's values. Because the heads never interact, they can run in any order, or in parallel on different cores, which Phase 4 does.

Putting the heads back together

Each head outputs 48 numbers. Laid side by side, the six outputs form a 288-number vector again. One more 288 × 288 matrix, Wo (the output projection), mixes them so information from different heads can combine. Its result is added into the residual stream:

k::matmul(&mut s.xb2, &s.xb, &lw.wo);   // mix the heads
k::add_inplace(&mut s.x, &s.xb2);        // x += attention's contribution

Fewer key/value heads (preview)

In stories15M every query head has its own key/value head (n_kv_heads = n_heads = 6). Bigger models save memory by letting several query heads share one key/value head. This is grouped-query attention, and Phase 5 needs it: SmolLM2-135M has 9 query heads and 3 key/value heads, so each group of 3 query heads reads the same keys and values. The code already handles it with one line, which picks the shared head:

let kv_off = (h / group) * hs;  // query head h reads K/V head h / group

With group = 1, as in stories15M, that is just head h.

The four projections are fixed work: 331,776 multiply-adds per layer, whatever the position calculated. Attention itself grows with the number of earlier tokens. Even at stories15M's 256-token limit it is 147,456 multiply-adds per layer, less than half of the four projections, and the MLP is bigger again. Over a 222-token story it averages about 2.5 % of a token's multiply-adds calculated. That is why attention is only 1.1 % of the time on the profile, and why it only became worth optimising for a bigger model at longer contexts (Phase 7).

Check yourself

q, k and v are all computed from the same xb. Why are they different?

Each is multiplied by its own learned matrix (Wq, Wk, Wv). Same input, different transformations.

Why are k and v written into the cache, but q is not?

Later tokens compare their own query with this token's key and mix in this token's value, so k and v are needed again. This token's query is only used now, to look back; nobody looks it up later.

How many numbers are in one head of stories15M, and where does that come from?

48: dim ÷ n_heads = 288 ÷ 6. A head is a slice, not a separate matrix.

SmolLM2-135M has 9 query heads and 3 key/value heads. Which key/value head does query head 7 read?

group = 9 ÷ 3 = 3, so head 7 ÷ 3 = 2 (integer division). Query heads 6, 7, 8 share key/value head 2.
