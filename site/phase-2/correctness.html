Bit-identical with llama2.c

How do you know an inference engine is right? Plausible-looking text is not proof: a model with a small bug still writes sentences. This project checks against an external reference, number by number, at every step of the forward pass. In Phase 2 every one of those numbers matched llama2.c to the last bit. This page shows how, and why “the same maths” is not enough for that.

Why text is not enough

Swap two RoPE pairs, forget the √48, or read the wrong cache row, and the model still produces English-looking words for a while. Errors in a transformer often degrade quality instead of crashing. A test that only looks at the output text would miss them, or catch them so late that the cause is unclear.

The rule in this project: correctness comes from external references only. Never a second implementation of our own (it would share our misunderstandings), always someone else's established code: llama2.c here, numpy for single kernels, Hugging Face transformers for SmolLM2 and Qwen, llama.cpp for quantized formats.

The reference: llama2.c

llama2.c's run.c is about 1,000 lines of plain C that runs stories15M. It is simple enough to read completely and widely used, so it is a good answer key. Aether's code is written independently in Rust; llama2.c is only run, never translated.

Golden dumps

To compare intermediate numbers, not just tokens, llama2.c needs to report them. tools/llama2c-dump.patch adds a dump() call after each step of its forward pass, writing every activation to a file:

static void dump(const char* name, int layer, int pos, const float* data, int n);
…
rmsnorm(s->xb, x, w->rms_att_weight + l*dim, dim);
dump("attn_norm", l, pos, s->xb, dim);

tools/stories15m_goldens.sh builds the patched llama2.c, runs “Once upon a time” for 64 positions (greedy, and seeded sampling), and saves the dumps. These are the golden files. They are regenerated from the script, not committed, because they are large.

The 14 names, in forward order: embed, attn_norm, q, k, v, attn, attn_out, resid_attn, ffn_norm, swiglu, ffn_out, resid_ffn, final_norm, logits. Aether's observer taps the same 14 places under the same names.

Replaying the reference

The test (greedy_matches_llama2c_at_every_layer in src/model/llama2c.rs) feeds Aether the same prompt tokens, lets it choose each next token itself, and checks two things:

  1. Every chosen token equals llama2.c's. The first difference stops the test with the position where it happened.
  2. Every activation is compared. For each of the 14 names, the worst error over all layers and positions is printed in forward order. A bug shows up as the first name where the error jumps from zero, which points to the step that is wrong.

Float addition depends on order

Why is “bit-identical” worth aiming for, and why is it hard? Because computer floats are rounded after every operation, and so (a + b) + c is not always equal to a + (b + c). Each addition rounds to the nearest representable f32, and different orders round at different moments.

Twelve numbers, four orders

The same twelve products, summed in f32 in four different orders. The hex is the exact bit pattern.


  




All four are correct to about seven digits, and none is “the” answer. So two engines that compute the same formula in different orders will differ in the last bits, and those differences grow a little through 6 layers.


That is why Aether's scalar kernels follow llama2.c's order exactly: left-to-right sums, w * (scale * x) in RMSNorm, the division by √48 after the dot product, v * (1 / (1 + e−v)) in SiLU. With the order matched, any non-zero difference is a real bug, and it stands out against a background of exact zeros. With a tolerance, a small bug could hide inside it.



The FMA trap


ARM CPUs have a fused multiply-add instruction: a × b + c with a single rounding at the end instead of two. It is faster and slightly more accurate, so compilers are sometimes allowed to use it for acc += w * x. That would round differently from llama2.c's separate multiply and add.


Rust never fuses a multiply and an add on its own; and the NDK's C compiler, as configured for llama2.c here, did not either. Both sides did two roundings, so the bits matched. Phase 3 then uses FMA on purpose, and gives up bit-identity in exchange for speed.



After Phase 2: tolerances


Phase 3's NEON kernels sum with several accumulators and fused multiply-adds: a different order, so different last bits. From then on the same test runs with a tolerance: every activation must be within 10−4 relative error of llama2.c's, and every greedy token must still be identical. The scalar build on the PC remains bit-identical, which keeps the zero-background check available.


The same approach scales up: SmolLM2 and Qwen are compared layer by layer with Hugging Face transformers (Phase 5), quantized formats with llama.cpp (Phase 6), and model quality by perplexity and KL divergence against llama.cpp (Phase 7).



Check yourself


Why compare every activation, not only the final tokens?

A bug can change numbers without changing the greedy token, at least for a while. And when tokens do differ, the activations tell you which step went wrong: the first name, in forward order, with a non-zero error.




Why not write a second, simple Rust version of the model and compare against that?

It would share our understanding, and so our misunderstandings: a misread formula would be wrong in both and the test would pass. An independent reference does not have our bugs.




The four sums in the widget differ. Which one is wrong?

None. All are correctly rounded results of a sequence of correctly rounded additions; they just round at different moments. Only the exact (float64) value is “the” sum, and every f32 order approximates it.




Why did Phase 3 accept losing bit-identity?

Several accumulators and FMA are what make the kernels fast (Phase 3, dependency chains), and both change the order of rounding. The check becomes a tolerance plus identical greedy tokens.
