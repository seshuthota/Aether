Embedding and RMSNorm

The forward pass, the run of steps that turns a token into a prediction, starts by turning a token id into a vector of 288 numbers. Before every block of work, RMSNorm then rescales that vector to a standard size. One is a table lookup; the other is a few lines of arithmetic.

How does a token id become a vector?

The model is given each token as a plain number, its id. Every later step does arithmetic on vectors, so the id must first become one. The embedding table does that. It is a matrix, a grid of numbers, with one row per token: 32,000 rows of 288 numbers (page 1). To embed token 9038 (“ Once”), copy row 9038. There is no multiplication.

w.token_embedding.row_f32(token, &mut s.x);   // x = row `token` of the table
  • w.token_embedding is the table. row_f32 copies one of its rows.
  • token picks the row: the id is the row number.
  • &mut s.x is where the copy goes. The &mut lets the function write into s.x.

The result, x, is the token’s starting point. It is called the residual stream, the running vector that each block reads and adds its result back into (page 8). By the end of the six layers, x describes “ Once” in context, shaped to predict the next token.

Copying one row reads 288 × 4 = 1,152 bytes out of 36.9 MB. This is the one weight table that decode does not read in full, except that stories15M reads all of it again at the end, as the tied classifier.

Takeaway: the embedding is a row copy; one token id picks one row of 288 numbers.

What do the 288 numbers mean?

A row of 288 numbers looks like noise. Nobody chose them by hand. Training adjusted each row until tokens used in similar ways ended up with similar vectors. Individual numbers rarely mean anything on their own; directions in the 288-dimensional space do. Picture each token as a point in a 288-axis space, where nearby points behave alike.

For this engine the meaning does not matter. What matters is that every token is a vector of exactly dim = 288 f32s (one f32 is one 32-bit float), and that every later step is arithmetic on such vectors. If a vector had a different length, that arithmetic would not line up.

Takeaway: the engine never needs to know what a number means; it needs every token to be exactly 288 floats.

Why do vectors need normalising?

Each block adds its output into the residual stream. After a dozen additions the numbers in x can be much larger (or smaller) than they were at the start. A matrix multiply scales with its input: double x and the output doubles. Without control, later layers would see inputs at unpredictable scales, which makes training unstable and the outputs meaningless.

So the fix runs before each block reads the vector. A normalisation layer is a small step that resets a vector’s overall size and keeps its direction, the pattern of which numbers are big and which are negative.

Takeaway: the residual stream’s size drifts with every addition, so the fix has to run before each block.

How does RMSNorm rescale a vector?

The size must be measured before it can be reset. RMSNorm uses the root mean square (RMS), an average size. Square every number, take the mean (the average), then take the square root.

RMS(x) = √( (x₀² + x₁² + … + x₂₈₇²) ÷ 288 )

Then every number is divided by it, so the result has RMS 1:

out_i = gain_i × x_i ÷ √( mean(x²) + ε )

ε (epsilon, 0.00001 here) is a tiny number added so that an all-zero vector does not cause a division by zero.

Take a small vector first. For x = [3, 4] the squares are 9 and 16, their mean is 12.5, and the RMS is √12.5, about 3.536. With gains of 1 and ε ignored, the output is about [0.849, 1.131]. Now try it with six numbers instead of 288:

Press “Double every input” and watch the bottom row: it does not move. Scaling the input by any factor gives the same output, which is exactly the point.

The Rust code in src/kernels/scalar.rs is the formula, built in four steps.

Step 1: add up the squares

let mut ss = 0.0f32;
for &v in x { ss += v * v; }          // sum of squares
  • let mut ss is a changeable variable, starting at 0.0f32 (a 32-bit float zero).
  • for &v in x visits each number of the vector. The & copies each number out, because the loop hands over references to them.
  • ss += v * v adds each square to the running total.

Step 2: mean and epsilon

ss /= x.len() as f32;                 // mean
ss += eps;
  • x.len() is the length, 288. as f32 converts it to a float, because Rust will not divide a float by an integer without being told how.
  • ss += eps adds the tiny ε before the square root. Without it, an all-zero vector would divide by zero.

Step 3: the scale

let scale = 1.0 / ss.sqrt();          // 1 / RMS
  • ss.sqrt() is the square root of the mean square, which is the RMS.
  • The division happens once, for the whole vector. The loop only multiplies.

Step 4: apply it with the gain

for ((o, &v), &w) in out.iter_mut().zip(x).zip(weight) {
    *o = w * (scale * v);             // gain × normalised value
}
  • zip walks three lists side by side: the output slots, the input numbers and the gains, one index at a time.
  • *o = ... writes into the output slot. The * means “the value that o points to”.
  • w * (scale * v) is gain × normalised value.

All four together

let mut ss = 0.0f32;
for &v in x { ss += v * v; }          // sum of squares
ss /= x.len() as f32;                 // mean
ss += eps;
let scale = 1.0 / ss.sqrt();          // 1 / RMS
for ((o, &v), &w) in out.iter_mut().zip(x).zip(weight) {
    *o = w * (scale * v);             // gain × normalised value
}

Keep this order. The same numbers summed in another order can round differently, so the bits can differ from llama2.c’s (page 11).

RMSNorm vs LayerNorm

The original transformer used LayerNorm, which also subtracts the mean before dividing. RMSNorm skips that step. It is cheaper and works as well in practice, so Llama-family models use it.

Takeaway: RMSNorm divides by the RMS, so scaling the input by any factor leaves the output unchanged.

What does the learned gain add?

The reset treats every channel (one of the 288 positions in the vector) the same. The gain restores control: a weight learned in training, one for each channel of each norm. After normalising, each of the 288 numbers is multiplied by its own gain (rms_att and rms_ffn in the file). So some channels can be turned up and others down. These gain vectors are the 288-float slivers in the file map.

Takeaway: after the reset, each of the 288 channels is scaled by its own learned gain.

Where do the norms sit in a layer?

Each layer normalises twice: once before attention, once before the MLP. One more norm runs after the last layer, before the classifier, the step that scores each token. That makes 6 × 2 + 1 = 13 RMSNorms per token.

In cost, the norms are nothing: 288 multiplies each, against 82,944 for one 288 × 288 matrix. On the profile they do not even reach 0.4 % of the time.

Takeaway: each token runs 13 RMSNorms, and each is cheap next to one 288 × 288 matrix.

Check yourself

What does the embedding step compute?

Nothing: it copies row id of the embedding table into the residual stream. No multiplications.

x = [3, 4]. What is RMSNorm(x), with gains of 1 and ε ignored?

mean(x²) = (9 + 16) ÷ 2 = 12.5; RMS = √12.5 ≈ 3.536. Output ≈ [0.849, 1.131]. Its RMS is 1.

Why does doubling every input leave the output unchanged?

Doubling x doubles its RMS too, and the output is x ÷ RMS. The factor of two cancels (up to the tiny ε).

How many RMSNorms does one token go through in stories15M?

13: two per layer for six layers, plus the final one before the classifier.

What you should take away

Each token starts as one row of the embedding table: 288 numbers.

RMSNorm divides by the vector’s RMS, so the output does not depend on the input’s scale; each channel then gets its gain.
