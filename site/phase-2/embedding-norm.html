Embedding and RMSNorm

The first step of the forward pass turns a token id into a vector of 288 numbers. Then, before every block of work, RMSNorm rescales that vector to a standard size. One is a table lookup; the other is three lines of arithmetic. Both are worth understanding exactly.

The embedding: an id picks a row

The embedding table is a matrix with one row per token: 32,000 rows of 288 numbers (page 1). To embed token 9038 (“ Once”), copy row 9038. That is all; there is no multiplication.

w.token_embedding.row_f32(token, &mut s.x);   // x = row `token` of the table

The result, x, is the token's starting point. It is called the residual stream because every block that follows reads from it and adds its result back into it (page 8). By the end of the six layers, x no longer describes “ Once” alone; it describes “ Once” in the context of everything before it, shaped to predict the next token.

Copying one row reads 288 × 4 = 1,152 bytes out of 36.9 MB. This is the one weight table that decode does not read in full, except that stories15M reads all of it again at the end, as the tied classifier.

What the 288 numbers are

Nobody chose them by hand. Training adjusted each row until tokens used in similar ways ended up with similar vectors. Individual numbers rarely mean anything on their own; directions in the 288-dimensional space do. A useful mental picture: each token is a point in a space with 288 axes, and nearby points behave alike.

For this engine the meaning does not matter. What matters is that every token is a vector of exactly dim = 288 f32s, and that every later step is arithmetic on such vectors.

Why vectors need normalising

Each block adds its output into the residual stream. After a dozen additions the numbers in x can be much larger (or smaller) than they were at the start, and different tokens end up at very different sizes. A matrix multiply scales with its input: double x and the output doubles. Without control, later layers would see inputs at unpredictable scales, which makes training unstable and the outputs meaningless.

A normalisation layer fixes the scale before each block reads the vector. It keeps the vector's direction (the pattern of which numbers are big and which negative) and resets its overall size.

RMSNorm, step by step

The size is measured by the root mean square (RMS): square every number, take the mean, take the square root.

RMS(x) = √( (x₀² + x₁² + … + x₂₈₇²) ÷ 288 )

Then every number is divided by it, so the result has RMS 1:

out_i = gain_i × x_i ÷ √( mean(x²) + ε )

ε (epsilon, 0.00001 here) is a tiny number added so that an all-zero vector does not cause a division by zero. Try it with six numbers instead of 288:

Normalise six numbers

Drag the inputs. The top bars are x, the bottom bars are RMSNorm(x) with every gain at 1. Copper bars are negative.

Press “Double every input” and watch the bottom row: it does not move. Scaling the input by any factor gives the same output, which is exactly the point.

The Rust code in src/kernels/scalar.rs is the formula written out, in the same order as llama2.c (that order matters, see page 11):

let mut ss = 0.0f32;
for &v in x { ss += v * v; }          // sum of squares
ss /= x.len() as f32;                 // mean
ss += eps;
let scale = 1.0 / ss.sqrt();          // 1 / RMS
for ((o, &v), &w) in out.iter_mut().zip(x).zip(weight) {
    *o = w * (scale * v);             // gain × normalised value
}
RMSNorm vs LayerNorm

The original transformer used LayerNorm, which also subtracts the mean before dividing. RMSNorm skips that step. It is cheaper and works as well in practice, so Llama-family models use it. If you read older code, that is the difference.

The learned gain

After normalising, each of the 288 numbers is multiplied by its own gain, a weight learned in training (rms_att and rms_ffn in the file). This lets the model turn some channels up and others down after the reset. These gain vectors are the 288-float slivers in the file map.

Where the norms sit

Each layer normalises twice: once before attention, once before the MLP. One more norm runs after the last layer, before the classifier. That makes 6 × 2 + 1 = 13 RMSNorms per token.

In cost, the norms are nothing: 288 multiplies each, against 82,944 for one 288 × 288 matrix. On the profile they do not even reach 0.4 % of the time.

Check yourself

What does the embedding step compute?

Nothing: it copies row id of the embedding table into the residual stream. No multiplications.

x = [3, 4]. What is RMSNorm(x), with gains of 1 and ε ignored?

mean(x²) = (9 + 16) ÷ 2 = 12.5; RMS = √12.5 ≈ 3.536. Output ≈ [0.849, 1.131]. Its RMS is 1.

Why does doubling every input leave the output unchanged?

Doubling x doubles its RMS too, and the output is x ÷ RMS. The factor of two cancels (up to the tiny ε).

How many RMSNorms does one token go through in stories15M?

13: two per layer for six layers, plus the final one before the classifier.
