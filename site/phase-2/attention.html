Attention, step by step

Attention is how a token gathers information from the tokens before it. For one head it takes four steps: score every earlier key against the query, scale the scores, turn them into weights with softmax, and add up the values using those weights. This page covers each step, a toy you can steer, and the overflow bug softmax has to avoid.

What does one head do, in four steps?

A token needs information from the tokens before it, but it cannot take all of them equally. It has to decide how much each one matters, and attention makes that decision with scores. The work happens in a head: one of several attention computations that run side by side in a layer.

Three lists take part. The query q (48 numbers) is what the current token is looking for. Each earlier position has a key k, which the query is matched against, and a value v, which is the information that position passes on. The keys and values come from the cache.

For position pos, the four steps are:

  1. Score. For every earlier position t, take the dot product q · kt: multiply the 48 pairs of numbers and add them up. For example, (1, 2) · (3, 4) = 1×3 + 2×4 = 11. A large score means the key points the same way as the query: a good match.
  2. Scale. Divide every score by √48 ≈ 6.93 (why).
  3. Softmax. Turn the scores into weights that are all positive and add up to 1. Bigger scores get bigger weights, and the gaps are exaggerated (how).
  4. Mix. The output is Σ weightt × vt: a blend of the values, mostly from the best-matching tokens.

out = Σt ≤ pos softmax( q · kt ÷ √48 ) × vt

Takeaway: each earlier token gets a score, the scores become weights that add up to 1, and the output is the weighted sum of the values.

What happens when you turn the query?

This toy uses two-number vectors instead of 48, so it fits on a page. It has five tokens, “The cat sat on the”. Each has a key and a value illustration. Turn the query and stretch it, and watch the weights change.

One query against five keys

Three things to try:

  • Direction picks the token. Point the query at about 10° and “cat” wins; at about 80°, “sat”.
  • Length sets the sharpness. A short query spreads weight over everyone; a long one gives nearly all of it to the best match. Training sets these lengths, so a head can learn to be focused or diffuse.
  • The future is hidden. Move the current token back to “cat”: “sat”, “on” and “the” disappear (why).

Takeaway: the direction of the query picks the winning token, and its length sets how sharp the weights are.

Why divide the scores by √48?

A dot product adds 48 products, so a longer list gives a bigger sum. If each number is about size 1 and random in sign, the sum grows like √48. Bigger scores make softmax extreme, as in the toy with a long query, and an almost all-or-nothing softmax trains badly.

Dividing by √(head size) keeps the typical score near size 1, whatever the head size. Skip the division and the typical score grows with the head size, so softmax gets more extreme. The divisor is a fixed constant.

Takeaway: divide by √(head size), because without it the scores grow with the head and softmax trains badly.

What is softmax, and why can it overflow?

Attention needs weights that are positive and add up to 1. Softmax is the function that turns scores into such weights:

wi = esi ÷ (es0 + es1 + …)

The exponential ex (e raised to the power x) makes every weight positive, and dividing by the total makes them add to 1. Because ex grows fast, a score 2 higher gets about 7.4 times the weight.

Written exactly like that, it has a bug. An f32 (a 32-bit float) cannot hold anything above about 3.4 × 1038, and e89 is already bigger. A score of 89 gives infinity, and infinity ÷ infinity is NaN (“not a number”), which then spreads through the rest of the model.

The fix: subtract the largest score, m, from every score first. The ratios do not change (ea−m ÷ eb−m = ea ÷ eb), but now every exponent is 0 or below, so every ex is between 0 and 1.

Naive vs stable softmax, in f32

Edit three scores. Both versions are computed in 32-bit floats, like the engine.





With the big scores, the naive version returns NaN for every weight while the stable one gives sensible numbers. The engine’s softmax always subtracts the maximum. Real attention scores are rarely that large, but the classifier’s 32,000 logits (its raw scores, one per candidate next token) go through the same softmax when sampling, and a bug that only appears on some inputs is the worst kind.


Takeaway: subtract the largest score before exponentiating, or large scores turn every weight into NaN.



Why can a token only look back?


A token may only attend to itself and earlier tokens, never later ones. During training this is enforced with a mask (a set of rules that hides some positions). At inference it happens by itself: the later tokens have not been generated yet, so their keys are not in the cache. The loop simply runs over positions 0 to pos.


This is called causal attention, and it is what lets a model generate text one token at a time: nothing computed for earlier tokens ever changes when a new one arrives. That is also the fact the KV cache relies on. Let a token see later tokens and that fact no longer holds.


Takeaway: a token looks only at itself and earlier tokens, so earlier work never changes and the cache can keep it.



What does the code look like?


The four steps are all in attention_head, in src/kernels/scalar.rs. It computes one head at one position.


Step 1: score


for (t, s) in scores.iter_mut().enumerate() {       // 1. score every position 0..=pos
    let k = keys(t);
    let mut dot = 0.0f32;
    for (&a, &b) in q.iter().zip(k) { dot += a * b; }


    
  
  • enumerate() gives each score its position t. iter_mut() gives s, a handle that lets the loop write into that score.
    • 
  
  • keys(t) finds position t’s 48 key numbers in the cache.
    • 
  
  • 0.0f32 is a 32-bit float zero. dot starts there and collects the sum of the 48 products.
    • 



Step 2: scale


let norm = (head_size as f32).sqrt();         // √48 ≈ 6.93
*s = dot / norm;                              // 2. scale


    
  
  • head_size as f32 turns the whole number 48 into a 32-bit float, and sqrt() takes its square root.
    • 
  
  • *s is the score that the loop points at. Writing to it stores the scaled score.
    • 



Step 3: softmax


softmax(scores);                              // 3. weights (max subtracted inside)


    
  
  • One call; the subtract-the-maximum fix happens inside it.
    • 



Step 4: mix


out.fill(0.0);
for (t, &a) in scores.iter().enumerate() {          // 4. weighted sum of values
    for (o, &v) in out.iter_mut().zip(values(t)) { *o += a * v; }
}


    
  
  • out.fill(0.0) resets the output to zero, so the sums start from nothing.
    • 
  
  • The outer loop takes each weight a. The inner loop adds a × v into each number of out, so every value contributes in proportion to its weight.
    • 



All four together


let norm = (head_size as f32).sqrt();
for (t, s) in scores.iter_mut().enumerate() {       // 1. score every position 0..=pos
    let k = keys(t);
    let mut dot = 0.0f32;
    for (&a, &b) in q.iter().zip(k) { dot += a * b; }
    *s = dot / norm;                                // 2. scale
}
softmax(scores);                                    // 3. weights (max subtracted inside)
out.fill(0.0);
for (t, &a) in scores.iter().enumerate() {          // 4. weighted sum of values
    for (o, &v) in out.iter_mut().zip(values(t)) { *o += a * v; }
}


keys(t) and values(t) are small functions that find position t’s 48 numbers in the cache. Passing functions instead of arrays lets the same code serve grouped-query attention (Phase 5), where several heads read the same cached keys. The forward pass calls this once per head, six times per layer.


Takeaway: the code runs the four steps in order, for one head at one position.



Check yourself


What are the weights after softmax guaranteed to be?

All positive (or zero after underflow) and adding up to 1. So the output is a weighted average of the values.




Scores [3, 1]. What are the softmax weights, roughly?

e³ ≈ 20.1, e¹ ≈ 2.72; total 22.8. Weights ≈ 0.88 and 0.12.




Why subtract the maximum score before exponentiating?

So that no exponent is above 0 and ex cannot overflow to infinity. It does not change the result, because the same factor cancels between numerator and denominator.




At position 0, what is the attention output?

There is only one key, so its weight is 1, and the output is just v0, the token's own value.





What you should take away


Attention scores each earlier token against the query, scales the scores, turns them into weights with softmax, and blends the values with those weights.


Divide by √(head size) and subtract the largest score, or softmax becomes extreme or overflows.


A token looks only at itself and earlier tokens, so past work never changes.
