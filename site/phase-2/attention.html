Attention, step by step

Attention is how a token gathers information from the tokens before it. For one head it is four steps: score every earlier key against the query, scale the scores, turn them into weights with softmax, and add up the values with those weights. This page goes through each, with a toy you can steer and the overflow bug that softmax has to avoid.

The four steps

For one head, at position pos, with the query q (48 numbers) and the keys k0 … kpos and values v0 … vpos from the cache:

  1. Score. For every earlier position t, the dot product q · kt: multiply the 48 pairs of numbers and add them up. A large score means the key points the same way as the query: a good match.
  2. Scale. Divide every score by √48 ≈ 6.93 (why).
  3. Softmax. Turn the scores into weights that are all positive and add up to 1. Bigger scores get bigger weights, and the gaps are exaggerated (how).
  4. Mix. The output is Σ weightt × vt: a blend of the values, mostly of the best-matching tokens.

out = Σt ≤ pos softmax( q · kt ÷ √48 ) × vt

Steer a query

A toy with two-number vectors instead of 48, so it fits on a page. Five tokens, “The cat sat on the”; each has a key and a value illustration. Turn the query and stretch it, and watch the weights.

One query against five keys

Three things to try:

  • Direction picks the token. Point the query at about 10° and “cat” wins; at about 80°, “sat”.
  • Length sets the sharpness. A short query spreads weight over everyone; a long one gives nearly all of it to the best match. Training sets these lengths, so a head can learn to be focused or diffuse.
  • The future is hidden. Move the current token back to “cat”: “sat”, “on” and “the” disappear (why).

Why divide by √48

A dot product adds 48 products. If each number is about size 1 and random in sign, the sum grows like √48: more numbers, bigger scores. Bigger scores make softmax extreme (as in the toy with a long query), and an almost-all-or-nothing softmax trains badly. Dividing by √(head size) keeps the typical score near size 1, whatever the head size. It is a fixed constant; at inference you just do it.

Softmax, and the overflow trap

Softmax turns a list of scores s into weights:

wi = esi ÷ (es0 + es1 + …)

The exponential makes every weight positive, and dividing by the total makes them add to 1. Because ex grows fast, a score 2 higher gets about 7.4 times the weight.

Written exactly like that, it has a bug. An f32 cannot hold anything above about 3.4 × 1038, and e89 is already bigger. A score of 89 gives infinity, and infinity ÷ infinity is NaN (“not a number”), which then spreads through the rest of the model.

The fix: subtract the largest score from every score first. The ratios do not change (ea−m ÷ eb−m = ea ÷ eb), but now every exponent is ≤ 0, so every ex is between 0 and 1.

Naive vs stable softmax, in f32

Edit three scores. Both versions are computed in 32-bit floats, like the engine.





With the big scores, the naive version returns NaN for every weight while the stable one gives sensible numbers. The engine's softmax always subtracts the maximum. Real attention scores are rarely that large, but the classifier's 32,000 logits go through the same softmax when sampling, and a bug that only appears on some inputs is the worst kind.



Only looking back


A token may only attend to itself and earlier tokens, never later ones. During training this is enforced with a mask; at inference it happens by itself: the later tokens have not been generated yet, so their keys are not in the cache. The loop simply runs over positions 0 to pos.


This is called causal attention, and it is what lets a model generate text one token at a time: nothing computed for earlier tokens ever changes when a new one arrives. That is also the fact the KV cache relies on.



The code


attention_head in src/kernels/scalar.rs, one head at one position. The four steps are visible one after another:


let norm = (head_size as f32).sqrt();
for (t, s) in scores.iter_mut().enumerate() {       // 1. score every position 0..=pos
    let k = keys(t);
    let mut dot = 0.0f32;
    for (&a, &b) in q.iter().zip(k) { dot += a * b; }
    *s = dot / norm;                                // 2. scale
}
softmax(scores);                                    // 3. weights (max subtracted inside)
out.fill(0.0);
for (t, &a) in scores.iter().enumerate() {          // 4. weighted sum of values
    for (o, &v) in out.iter_mut().zip(values(t)) { *o += a * v; }
}


keys(t) and values(t) are small functions that find position t's 48 numbers in the cache. Passing functions instead of arrays lets the same code serve grouped-query attention (Phase 5), where several heads read the same cached keys. The forward pass calls this once per head, six times per layer.



Check yourself


What are the weights after softmax guaranteed to be?

All positive (or zero after underflow) and adding up to 1. So the output is a weighted average of the values.




Scores [3, 1]. What are the softmax weights, roughly?

e³ ≈ 20.1, e¹ ≈ 2.72; total 22.8. Weights ≈ 0.88 and 0.12.




Why subtract the maximum score before exponentiating?

So that no exponent is above 0 and ex cannot overflow to infinity. It does not change the result, because the same factor cancels between numerator and denominator.




At position 0, what is the attention output?

There is only one key, so its weight is 1, and the output is just v0, the token's own value.
