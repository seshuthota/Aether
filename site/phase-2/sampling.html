Choosing the next token

The forward pass ends with 32,000 numbers, one score per token in the vocabulary. Something has to pick one. Always taking the best gives repetitive text; picking at random gives nonsense. Sampling sits between, with three dials: temperature, top-k and top-p. This page explains each, and how the engine's random choices can be replayed exactly.

Logits and probabilities

The classifier multiplies the final 288-number vector by the 32,000 × 288 table. Each of the 32,000 results is a logit: a raw score, any real number, higher meaning “more likely next”. Softmax turns logits into probabilities that add up to 1. Sampling is choosing a token from those probabilities.

Greedy

Pick the token with the highest logit (argmax). No randomness: the same prompt always gives the same text. That makes greedy the right mode for testing, and every correctness check in this project uses it (-t 0). For writing, it tends to loop: the model's single most likely continuation is often a phrase it has just said.

Temperature

Divide every logit by a number T before softmax.

  • T < 1 makes gaps between logits bigger, so the top tokens take more of the probability. Safer, duller.
  • T = 1 leaves the model's own distribution.
  • T > 1 shrinks the gaps, so unlikely tokens get a real chance. More surprising, eventually incoherent.
  • T → 0 approaches greedy, which is why -t 0 means greedy.

Top-k

Keep only the k most likely tokens, set the rest to zero, rescale the kept ones to add up to 1, and draw. It cuts off the long tail of thousands of tokens that are each unlikely but together add up to a real chance of a bad pick.

Top-p (nucleus)

Sort the tokens by probability and keep the smallest set from the top whose probabilities add up to more than p (say 0.9). Draw from that set. Unlike top-k, the set adapts: when the model is confident, one or two tokens already make 90 %; when it is unsure, the set grows. This is llama2.c's default (p = 0.9), and Aether's.

A neat speed trick from llama2.c, which the engine copies: a token with probability below (1 − p) ÷ (32,000 − 1) can never be in the nucleus, so those are dropped before sorting. A 32,000-item sort becomes a sort of a few hundred.

A random generator you can replay

A computer has no dice. Sampling uses a pseudo-random number generator: a small formula that turns one 64-bit number (the state) into the next, producing a sequence that looks random. Start from the same seed and you get exactly the same sequence.

Aether uses the same generator as llama2.c, xorshift*: three shifts and XORs to scramble the state, then one multiplication to produce the output:

fn next_u32(&mut self) -> u32 {
    self.rng ^= self.rng >> 12;
    self.rng ^= self.rng << 25;
    self.rng ^= self.rng >> 27;
    (self.rng.wrapping_mul(0x2545_F491_4F6C_DD1D) >> 32) as u32
}
fn next_f32(&mut self) -> f32 {
    (self.next_u32() >> 8) as f32 / 16_777_216.0   // 24 bits → [0, 1)
}

Then the draw itself: take a random number r in [0, 1), walk the kept tokens adding up their probabilities, and stop at the first one where the running total passes r. A token with probability 0.3 owns a stretch of 0.3 of that line, so it is hit 30 % of the time.

Why copy llama2.c's generator and its exact top-p procedure? Because then sampled runs can be checked too, not just greedy ones. With -t 0.8 -p 0.9 -s 42, Aether and llama2.c pick the same 64 tokens measured. The seed is the only thing that makes one sampled run differ from another. Pass -s to fix it; without it the CLI takes the current time, so every run is new.

The generation loop

Put together, generating text is:

  1. Tokenize the prompt: BOS + its tokens.
  2. Feed the prompt tokens through the model one by one (or all at once, Phase 3's prefill), filling the KV cache.
  3. From the logits of the last prompt token, sample the next token. Print its text.
  4. Feed that token in at the next position, get new logits, sample again.
  5. Stop when the model emits BOS (llama2.c's models mark the end of a story by starting a new one) or at the length limit (-n, 256 by default).

Step 3–4 is decode, and each turn of it is one full forward pass. Tokens per second, the number this project measures, counts those turns.

Check yourself

Why does every correctness test use temperature 0?

Greedy has no randomness, so the same model must produce the same tokens. Any difference from the reference is a bug, not chance.

Logits [2, 1]. With T = 0.5, what are the probabilities?

Scaled logits [4, 2]: e⁴ ≈ 54.6, e² ≈ 7.39; probabilities ≈ 0.88, 0.12. At T = 1 they would be 0.73, 0.27: lower temperature sharpened them.

The model is very sure: one token has probability 0.95. With top-p 0.9, how many tokens can be drawn?

One. That token alone already passes 0.9.

Two runs with the same seed, prompt and settings give different text. What does that tell you?

Something other than the sampler differs: the logits themselves changed (a bug, a different kernel or summation order) or the generator was used differently. The sampler alone is deterministic for a given seed.
