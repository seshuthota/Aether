Choosing the next token

The forward pass ends with 32,000 numbers, one score for each token in the vocabulary (the list of tokens the model knows). Something has to pick one. Always taking the best gives repetitive text. Picking at random gives nonsense. Sampling sits between the two, with three dials: temperature, top-k and top-p. This page explains each dial, and how to replay the engine’s random choices exactly.

What turns scores into probabilities?

The classifier produces one score per token, and those scores are not chances yet. The classifier multiplies the final 288-number vector by the 32,000 × 288 table. Each of the 32,000 results is a logit: a raw score, any real number, where higher means “more likely next”.

Softmax turns logits into probabilities that add up to 1. Sampling is then choosing one token at random, weighted by those probabilities.

Takeaway: the model outputs logits; softmax turns them into probabilities, and sampling draws one token from them.

Why not always take the best token?

The simplest choice is the token with the highest logit. That is argmax, the position of the largest value, and it needs no randomness. This is greedy decoding.

Greedy gives the same text for the same prompt every time. That makes it the right mode for testing, and every correctness check in this project uses it (-t 0). Random sampling can give a different text on each run, so a difference would no longer point to a bug. For writing, greedy tends to loop: the model’s single most likely continuation is often a phrase it has just said.

Takeaway: greedy is repeatable, so it is the mode for correctness tests, but it tends to repeat itself in writing.

How does temperature reshape the scores?

Temperature is a dial for how much the top token dominates. Divide every logit by a number T before softmax.

Take two logits, 2 and 1. At T = 1 they stay as they are, and softmax gives 0.73 and 0.27. At T = 0.5 they become 4 and 2, and the top token gets 0.88.

  • T < 1 makes gaps between logits bigger, so the top tokens take more of the probability. Safer, duller.
  • T = 1 leaves the model’s own distribution.
  • T > 1 shrinks the gaps, so unlikely tokens get a real chance. More surprising, eventually incoherent.
  • T → 0 approaches greedy, which is why -t 0 means greedy.

Takeaway: below 1 widens the gaps between logits, above 1 shrinks them, and near 0 the choice becomes greedy.

How do you cut off the unlikely tail?

The model spreads a little probability over thousands of tokens. Each one is unlikely, but together they can add up to a real chance of a bad pick. Top-k removes that tail by keeping only the k most likely tokens.

Keep only the k most likely tokens, set the rest to zero, rescale the kept ones to add up to 1, and draw. The rescale is needed because a draw works only when the probabilities add up to 1. With k = 2, only the two best tokens can ever be drawn.

If k is too large, the long tail comes back.

Takeaway: top-k keeps a fixed number of tokens, whatever the model thinks.

Can the cut-off adapt to how sure the model is?

Top-k always keeps k tokens, even when the model is nearly sure of one. Top-p, also called nucleus sampling, keeps as many tokens as it needs to reach a total probability p.

Sort the tokens by probability and keep the smallest set from the top whose probabilities add up to more than p (say 0.9). Draw from that set. Unlike top-k, the set adapts: when the model is confident, one or two tokens already make 90 %; when it is unsure, the set grows. This is llama2.c’s default (p = 0.9), and Aether’s.

llama2.c has a speed trick, which the engine copies: a token with probability below (1 − p) ÷ (32,000 − 1) can never be in the nucleus, so those are dropped before sorting. A 32,000-item sort becomes a sort of a few hundred.

Takeaway: top-p keeps the smallest set whose probability reaches p, so the set is small when the model is sure and larger when it is not.

Takeaway: each dial removes or reshapes the choices, and the grey words show exactly which ones it removed.

How does a computer pick at random, and can you replay it?

A computer has no dice, so sampling uses a pseudo-random number generator: a small formula that turns a 64-bit number, the state, into the next state and an output that looks random. Start from the same seed, the state it begins at, and you get the same sequence.

Aether uses llama2.c’s generator, xorshift*, in three steps.

Step 1: scramble the state

self.rng ^= self.rng >> 12;
self.rng ^= self.rng << 25;
self.rng ^= self.rng >> 27;
  • ^= is XOR, bit by bit: it mixes the state with a shifted copy of itself.
  • >> shifts bits right and << shifts them left.
  • Change any number here and the sequence changes, so the numbers must match llama2.c’s.

Step 2: produce a 32-bit number

(self.rng.wrapping_mul(0x2545_F491_4F6C_DD1D) >> 32) as u32
  • wrapping_mul multiplies and lets the result overflow, wrapping around rather than stopping the program.
  • >> 32 keeps the top 32 bits. as u32 names the type.

Step 3: turn it into a float from 0 to 1

(self.next_u32() >> 8) as f32 / 16_777_216.0   // 24 bits → [0, 1)
  • >> 8 drops the low 8 bits, leaving 24.
  • 24 bits give 224 = 16,777,216 values. Dividing by that puts the result in [0, 1), never reaching 1.

The draw: take a random number r in [0, 1), add up the kept tokens’ probabilities in order, and stop at the first one where the running total passes r. A token with probability 0.3 owns 0.3 of that line, so it is hit 30 % of the time.

0 ───────── 0.3 ────────────────────── 1
  token A        other tokens
  r below 0.3: token A is drawn

Copying llama2.c’s generator and its exact top-p procedure lets sampled runs be checked too, not just greedy ones. With -t 0.8 -p 0.9 -s 42, Aether and llama2.c pick the same 64 tokens measured. The seed is the only thing that makes one sampled run differ from another. Pass -s to fix it; without it the CLI takes the current time, so every run is new.

All three together

fn next_u32(&mut self) -> u32 {
    self.rng ^= self.rng >> 12;
    self.rng ^= self.rng << 25;
    self.rng ^= self.rng >> 27;
    (self.rng.wrapping_mul(0x2545_F491_4F6C_DD1D) >> 32) as u32
}
fn next_f32(&mut self) -> f32 {
    (self.next_u32() >> 8) as f32 / 16_777_216.0   // 24 bits → [0, 1)
}

Takeaway: the same seed gives the same sequence, so a sampled run can be replayed when the generator and the top-p procedure match llama2.c’s.

How do the pieces make one generated text?

Generating text repeats the pieces above, one token at a time:

  1. Tokenize the prompt: BOS + its tokens.
  2. Feed the prompt tokens through the model one by one (or all at once, Phase 3’s prefill), filling the KV cache.
  3. From the logits of the last prompt token, sample the next token. Print its text.
  4. Feed that token in at the next position, get new logits, sample again.
  5. Stop when the model emits BOS (llama2.c’s models mark the end of a story by starting a new one) or at the length limit (-n, 256 by default).

Step 3–4 is decode, and each turn of it is one full forward pass. Tokens per second, the number this project measures, counts those turns.

Takeaway: generation is sample, feed back, and repeat, with one full forward pass per token.

Check yourself

Why does every correctness test use temperature 0?

Greedy has no randomness, so the same model must produce the same tokens. Any difference from the reference is a bug, not chance.

Logits [2, 1]. With T = 0.5, what are the probabilities?

Scaled logits [4, 2]: e⁴ ≈ 54.6, e² ≈ 7.39; probabilities ≈ 0.88, 0.12. At T = 1 they would be 0.73, 0.27: lower temperature sharpened them.

The model is very sure: one token has probability 0.95. With top-p 0.9, how many tokens can be drawn?

One. That token alone already passes 0.9.

Two runs with the same seed, prompt and settings give different text. What does that tell you?

Something other than the sampler differs: the logits themselves changed (a bug, a different kernel or summation order) or the generator was used differently. The sampler alone is deterministic for a given seed.

What you should take away

Generation is a loop: the model scores every token, a sampler picks one, and the pick goes back in as the next input.

The sampler is a choice between repeatable (greedy, for tests) and varied (temperature, top-k, top-p, for writing).

Seeding the random generator makes even the varied mode replayable, so it can be checked against llama2.c.
