Text to tokens

A model cannot read letters. It reads token ids: whole numbers, each standing for a piece of text from a fixed list of 32,000. The tokenizer turns your prompt into ids on the way in and ids back into text on the way out. This page shows how, step by step, with the real merges stories15M makes.

Why not letters, why not words?

Two obvious choices both fail:

  • One token per letter. A tiny vocabulary, but a sentence becomes very long, and every token costs a full forward pass. The model would also have to learn spelling before it could learn meaning.
  • One token per word. Short sequences, but the vocabulary would need every word in every language, and any new word (a name, a typo) would be impossible to write.

Subword tokenizers sit in between. Common words are one token (“ time”, “ upon”); rare words are built from pieces (“ happ” + “ily”); and in the worst case, any text at all can still be written byte by byte. This is byte-pair encoding (BPE). A token is one such piece of text with its id.

Takeaway: pieces between letters and words keep sequences short, and the byte case means any text can be written.

What is in the vocabulary, and what is a score?

The model chooses from a fixed list, so the tokenizer file stores that list. tokenizer.bin stores, for each of the 32,000 tokens, its bytes and a score. A few ids are special:

IdTokenMeaning
0<unk>unknown (never produced here, thanks to byte fallback)
1<s>BOS, beginning of sequence: every prompt starts with it
2</s>EOS, end of sequence. (stories15M actually ends a story by emitting BOS, the start of the next one; the generator stops on that.)
3–258<0x00>…<0xFF>one token for every possible byte
259…“ t”, “ a”, “on”, “ the”, …merged pieces, roughly from most to least common

The score says how good a merge is: when two neighbouring pieces could be joined into a vocabulary token, the one with the higher score wins. Common pieces got high scores during the tokenizer’s training. (In this file the scores are negative numbers; “higher” means closer to zero.) Read “higher” as “more negative” and the merges happen in the wrong order.

Takeaway: the vocabulary is a fixed list of 32,000 pieces, and each score decides which merge wins.

How do you merge the best pair?

Start from single characters, glue neighbours together, best pair first, and stop when no neighbouring pair is a vocabulary token. The algorithm, as written in src/tokenizer/llama2c.rs:

  1. Start. Put BOS (id 1). Then the token for a single space (see below).
  2. Split into characters. Each character that is in the vocabulary becomes its token. Any other becomes one byte token per byte (byte fallback).
  3. Merge. Look at every adjacent pair. Of the pairs whose joined text is a vocabulary token, take the one with the highest score and merge it into one token. Repeat until no adjacent pair is in the vocabulary.

Watch the merges

Real merges from stories15M's tokenizer, traced from the file. ␣ is a space. The highlighted chip is the merge just made.

The merges run from common to rare. In “Once upon a time” the first merge is “ t”, then “ a”, then “on”: short, very common pairs, which have the highest scores. Whole words like “ Once” come last, because they need their pieces to exist first. Each loop looks at every pair, so this simple version does about n merges × n pairs of work. That is fine: a prompt is tokenized once, and it takes microseconds next to the model. Merging in a different order can give a different split, and then the ids no longer match llama2.c’s.

Takeaway: merge the highest-scoring neighbouring pair, repeat until none is left, and keep the order exact.

What if a character is not in the vocabulary?

Take a character the vocabulary does not have, say an emoji. The tokenizer falls back to bytes. Each character is stored as UTF-8 bytes, the standard way to write characters as numbers from 0 to 255. An emoji is 4 bytes, so it becomes 4 byte tokens. Each byte token is its byte value + 3, because the 256 byte tokens start at id 3.

So no input can fail to encode. The model may have seen little text like that, but it can still be written down. Skip the fallback and such a character has nowhere to go.

Step 1: look the piece up

match self.lookup.get(&b[i..end]) {
  • b[i..end] is the bytes from position i up to, not including, end: the piece being tried.
  • get returns Some with the id if the piece is in the vocabulary, and None if not. match branches on which one it is.

Step 2: the known case

Some(&id) => tokens.push(id),                  // a known character
  • Some(&id) unpacks the id. The & copies the number out of the reference that get returned.
  • tokens.push(id) adds it to the output list.

Step 3: the fallback case

None => tokens.extend(b[i..end].iter().map(|&byte| byte as usize + 3)), // its bytes
  • .iter() walks the bytes one at a time.
  • |&byte| byte as usize + 3 is a small function that turns each byte into its id. as usize changes the type, and + 3 skips the three special ids 0, 1 and 2.
  • extend adds all of those ids to the list, one per byte.

All three together

match self.lookup.get(&b[i..end]) {
    Some(&id) => tokens.push(id),                                   // a known character
    None => tokens.extend(b[i..end].iter().map(|&byte| byte as usize + 3)), // its bytes
}

Takeaway: a known piece maps to one id, and an unknown one falls back to one id per byte, so every input encodes.

Why does the first word get a space in front?

SentencePiece, the tokenizer family Llama uses, treats a space as part of the next word: the vocabulary has “ time” (with a space) far more often than “time”. So a word at the start of a prompt, with no space before it, would not look like the same word elsewhere in a sentence.

To make the first word look like every other word, the encoder puts a space token in front of the text. This is called the dummy prefix. That is why the traces above start with ␣.

When decoding, the opposite happens: if a token follows BOS and starts with a space, that space is dropped, so the output does not begin with a blank.

Takeaway: the encoder adds a leading space so the first word matches the usual pieces, and decoding removes it again.

How do ids turn back into text?

Decoding is the reverse, and it is simpler: a table lookup, id → bytes. The program looks up each id and writes out its bytes. Two small rules: the dummy-prefix space after BOS is dropped, and a byte token like <0xF0> turns back into the single byte 0xF0.

Byte tokens can arrive one at a time, half an emoji per step, so the program prints raw bytes, and the terminal shows the character once all of its bytes have arrived.

Takeaway: decoding is a table lookup from ids to bytes, with two rules for the leading space and byte tokens.

How do you know it matches llama2.c?

A tokenizer that is almost right still gives the model wrong ids, so the check has to be exact. The tokenizer is compared with llama2.c’s own encoder on 323 test strings generated by tools/gen_tokenizer_corpus.py: plain English, runs of whitespace, accented letters, Chinese and Japanese, emoji, control bytes and random mixtures. Every string gives exactly the same ids measured. A second test decodes every encoding and checks the original text comes back.

Phase 5 needs a different tokenizer for SmolLM2 and Qwen (byte-level BPE, which ranks merges from an explicit list instead of by score). It is checked the same way, against Hugging Face’s tokenizers library, on 433 strings.

Takeaway: the encoder must give identical ids on 323 strings, and decoding must give back the original text.

Check yourself

“Once upon a time” is 16 characters. Why are there 5 ids, and what is the first one?

The first is BOS (1). The merges turn the 17 starting pieces (space + 16 characters) into 4 tokens: “ Once”, “ upon”, “ a”, “ time”. 1 + 4 = 5.

Why can the tokenizer never fail, even on text in a script it has never seen?

Byte fallback: any character not in the vocabulary is written as its UTF-8 bytes, and all 256 byte values are tokens (ids 3–258).

Two different adjacent pairs could both be merged. Which one goes first?

The one whose merged token has the higher score. If two have the same score, the leftmost. The order matters: merging a different pair first can lead to a different final split.

Why does a token cost so much more than a character to the model?

Because the model runs one full forward pass per token, reading all 60.8 MB of weights. Fewer, longer tokens mean fewer passes for the same text.

What you should take away

A model reads token ids, so the tokenizer converts text to pieces and back, and byte fallback covers anything unseen.

Encoding merges the highest-scoring neighbouring pair until none is left; the leading-space and decoding rules make the round trip exact.

Encoding matches llama2.c exactly on 323 strings, and decoding gets the original text back.
