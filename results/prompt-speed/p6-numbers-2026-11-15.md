# P6's two measured costs: the handover copy and both models' memory (2026-11-15)

Raw logs, one per tool, in this directory; the design is
`aether-infer/plans/gpu-prompt-cpu-decode.md` (branch `prompt-speed-2`).
iQOO 13, on battery (56–58 %), screen on, every run cooled to 40 °C
(zone0) with the 2.40/2.44 GHz caps, through `scripts/phone_ab.py`.

## 1. The handover copy (`p6-host-read-2026-11-15.txt`)

`p6_host_read 256`: 256 MiB mapped GPU buffers, 6 threads on cores 2–7,
the GPU writes the buffer last; the median of 7 timings, 3 rounds.

| memory | handover, 42 MiB | stream | `MatQ4_0T` T-layout |
| --- | --- | --- | --- |
| coherent (today's) | 1.93–1.95 ms (22.6–22.8 GB/s) | 66–68 GB/s | 29.2–29.6 GB/s |
| `HOST_CACHED` | 1.94–2.01 ms (21.9–22.8 GB/s) | 65–67 GB/s | 29.5–29.7 GB/s |
| heap (reference) | 2.02–2.11 ms (20.9–21.8 GB/s) | 61–68 GB/s | 29.2–29.3 GB/s |

- **`HOST_CACHED` buys nothing** (22.8 GB/s both), so the cache keeps the
  engine's memory type. Decision 7 is answered.
- The copy is **1.93 ms for Gemma 4's 42.0 MiB** and 2.7 ms for LFM3's
  58.6 MiB, at the fast end of the design's 2–4.4 ms range (0.04 % of a
  5.1 s prompt at the 400 tok/s target).
- Ordinary heap is no faster, and the T-layout (decode's access pattern on
  the CPU's own weights) runs at 29 GB/s, half the contiguous stream.

### What it says

- **Peak with both models: ~4.6 GB for Gemma** (HWM 4608 MB, dumpsys PSS
  4569 MB) and **~3.3 GB for LFM3** (HWM 3283 MB). The release brings
  Gemma to **3.3 GB** (HWM 3312 MB, dumpsys 3240 MB) and LFM3 to
  **2.3 GB** (HWM 2299 MB).
- **The design's +2.8 GB CPU copy / ~6.2 GB peak is pessimistic.** The
  repacked copy is the anon Pss: **1.09 GB** after load and 1.54 GB after
  32 decode steps for Gemma; 1.11 GB for LFM3. The rest of the CPU model's
  Pss is the file's page cache, which both models share (the 1.3 GB PLE
  table and embedding stay mapped, not repacked). So the second model
  costs about **1.1–1.5 GB of private memory**, not 2.8 GB.
- **`release` drops ~1.4 GB for Gemma and ~1.0 GB for LFM3** of PSS/HWM:
  it drops the GPU model's mapping of the weight file. MemAvailable does
  not move, so part of that is the same physical file pages counted
  twice once the CPU model maps the file too; but `dumpsys meminfo` (what
  Android's LMK charges) falls from 4.57 to 3.24 GB, so it changes the
  app's memory budget all the same. It costs a pass over the matrix
  entries and leaves the embedding/table to page in on demand.
- **Ignore the decode rates across the pair.** 29.4 → 35.8 tok/s (Gemma)
  and 41.3 → 54.1 (LFM3) look like a release win, but `release` always ran
  second and the file was warm from the first run; this is not a
  controlled A/B. The memory deltas are within-process and solid.
- The GPU's buffers do not appear in `GL mtrack` (0 MB) or in smaps: the
  GPU model's 3.1 GB is its RSS/file Pss, and MemAvailable falls 1.37 GB
  on the upload. `dumpsys` total PSS is the number to quote.
- The prompt rates (171 Gemma, 305 LFM3) are with the CPU model resident
  and the tool's external 256-token chunks; they are not the P5b
  single-call numbers (285 Gemma at 2048) and are not for the speed table.
- One round and a drifting baseline (MemAvailable rose 6.6 → 7.8 GB over
  the session): the peak totals are ±0.1–0.2 GB; the release deltas are
  the reliable part.

## What this leaves for the decision

Decision 7 (the cache's memory type): **keep it**; measured 22.8 GB/s and
no `HOST_CACHED` gain. Decision 5 (the memory ceiling): Gemma peaks at
4.6 GB with both models and 3.3 GB with `release_uploaded`; LFM3 at 3.3
and 2.3 GB. Both fit the 12 GB phone; the release is cheap and is worth
making part of P6 rather than an option. The remaining decisions are the
API surface (new `Backend` variant vs `LoadOptions` vs automatic), the
first commit's scope (P6a GPU prompt at position 0 only), the model guard,
the first token, lookup/draft models and the names — §6 of the design.
