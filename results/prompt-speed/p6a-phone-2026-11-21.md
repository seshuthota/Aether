# P6a on the phone, and the 3× prompt slowdown explained (2026-11-21)

Branch `prompt-speed-2` (aether-infer), builds `aether-p6a2` (5777432, the
old one) and `aether-p6a3` (5777432 + the batch fix and the detached
harness). iQOO 13 (SM8750, Adreno 830), on battery, screen on, wireless
adb. Gemma 4 E2B Q4_0 and LFM3-1.7B-QAD-Q4_0, `aether bench -m … -dev gpu
--cores 2-7 -p 512,2048 -n 128 -pg 2048,128 -r 3`. `scripts/phone_ab.py`,
3 rounds, order reversed each round, cooled before each run. Every run
started at 40–43 °C (zone0) and 2.00/2.25 GHz caps except Gemma 4's plain
round 0 (2.75/2.65, after a long idle; the medians below land on the 2.00
rounds). Battery 62–68 %, not charging. Raw output:
`p6a-phone-2026-11-21.txt`, the old/new diagnostic:
`p6a-fix-2026-11-21.txt`.

## The cause: the benchmark chunked the prompt at the GPU's batch

`Engine::batch` returned the GPU's 256-token prompt batch for
`GpuWithCpuDecode` too. `aether bench`'s `run()` splits the prompt by
`Session::batch`, so the first 256 tokens went through the GPU pass and
then, after the handover, every later chunk went to the CPU — which is
the live cache in this mode. At 2048, 256/326 + 1792/88 = 20.3 s = 96.5
tok/s, the 99.0 measured on 2026-11-16. Decode was not slower at all: that
run had started at 2.40/2.44 GHz and ended at 59 °C / 1.56/1.40, so its
tg128 was thermally noisy.

Fixed by making `Session::batch` unlimited for this backend (as on the
CPU); `GpuSession::prefill` already splits the GPU pass at the model's own
batch. Old against new, same session, start caps 2.00/2.25 GHz:

| Gemma 4 Q4_0 | pp512 | pp2048 | tg128 | pp2048+tg128 |
| --- | --- | --- | --- | --- |
| old `aether-p6a2 --cpu-decode` (42–43 °C) | 153.5 | 84.1 | 29.6 | 63.1 |
| new `aether-p6a3 --cpu-decode` (42 °C) | 251.0 | 243.6 | 33.4 | 161.4 |

(The old run heated to 60 °C and 1.56/1.40 GHz; the new one ended at
56 °C and 1.79/1.96.)

## Three rounds: GPU against GPU prompt + CPU decode

Medians of three (min–max), tok/s:

| Gemma 4 Q4_0 | pp512 | pp2048 | tg128 | pp2048+tg128 |
| --- | --- | --- | --- | --- |
| `-dev gpu` | 264.99 (263.99–326.03) | 261.79 (257.48–320.48) | 18.79 (18.36–20.11) | 119.15 (119.01–124.12) |
| `-dev gpu --cpu-decode` | 252.71 (237.26–281.31) | 252.57 (247.28–259.43) | **35.18 (35.18–35.23)** | 164.27 (162.74–165.03) |

| LFM3 QAD-Q4_0 | pp512 | pp2048 | tg128 | pp2048+tg128 |
| --- | --- | --- | --- | --- |
| `-dev gpu` | 327.48 (326.14–327.53) | 291.35 (275.76–291.90) | 32.94 (32.83–33.29) | 181.45 (179.78–181.96) |
| `-dev gpu --cpu-decode` | 314.26 (313.71–316.44) | 279.01 (277.77–281.33) | **53.14 (41.47–53.51)** | 213.30 (208.96–216.18) |

- The prompt is 3.5–4.2 % under the plain GPU in both models, in all
  rounds; the GPU pass is the same shader sequence and the handover is
  1.9 ms (Gemma 4, 42 MiB) / 2.6 ms (LFM3, 58.6 MiB). The difference is
  the second model in memory: 1.1 GB of private pages on a phone with 13
  of 15 GB in use and zram active. It is the price of P6a, not the pass.
- Decode is the CPU's: Gemma 4 35.18 against the GPU's 18.79 (+87 %), LFM3
  53.14 against 32.94 (+61 %). The 2026-11-16 "no faster" decode was the
  59 °C run.
- `pp2048+tg128` is 2048 prompt + 128 decodes: the decodes run at depth
  2048–2175, where the CPU is slower than tg128's 0–127, so 164 is not
  `2048/252.6 + 128/35.2` (190); the 26-token gap is that depth.
- Time to first token for a 2048-token prompt: 2048/252.6 = 8.11 s on the
  GPU prompt at these caps (23.3 s on the CPU). Section 2's 5.5 s needs
  400 tok/s, i.e. P4/P5's products, not P6.

## One harness note

Wi-Fi adb dropped twice on 2026-11-16 and lost the round. `phone_ab.py`
now runs each command detached under `nohup` with its output and exit code
in files on the phone, disables Doze and keeps the link awake for the
session, and restores everything on every exit; `phone_bench.py` treats
"device offline/not found" as a reconnect. No round was lost here.
