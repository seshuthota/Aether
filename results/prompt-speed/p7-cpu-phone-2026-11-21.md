# P7 measured, not shipped: tiling the CPU attention is slower (2026-11-21)

Branch `prompt-speed-2`: `aether-p6a3` (`1c56478`, the old per-token
attention) against `aether-p4` (the same plus tiled `attention_tile`,
TILE_Q 8, 64-position blocks, NEON; P4 is GPU-only so the CPU A/B isolates
P7). iQOO 13, on battery, screen on, wireless adb. `scripts/phone_ab.py`,
3 rounds planned, cooled before each run. The session was stopped after the
matched-cap pairs (battery 50 %, no third round); every number below is at
the same 2.00/2.25 GHz caps and 40–43 °C start. Raw:
`p7-cpu-phone-2026-11-21.txt`.

## The kernel was right

`attention_tile` passes all 99 numpy cases (grouped causal, head sizes
64/128/256/512, groups 1/7/8, positions around tile and window edges,
window batches) on the phone's NEON, worst relative error **3.48e-6**; the
scalar fallback 4.35e-6. The models' transformers goldens also pass with it
(Gemma 4's 600-token long prompt, LFM3, Qwen2.5, SmolLM2).

## Why: the attention is f32-compute-bound, not K/V-bandwidth-bound

- The old CPU path is not naive: `group_fixed` (head sizes 64/48/128) reads
  a K row once and computes all `g` query heads' scores from it, and all
  `g` value sums from one V row. Gemma's generic path does one K and one V
  read per (token, head).
- The tiled kernel reads each K/V row once per *position block* but each
  (token, head) **dot product and value accumulate still re-reads it**, from
  L1/L2 instead of DRAM. It changes where the traffic goes, not how much the
  arithmetic reads, and it adds the online-softmax rescale. At these shapes
  the dots dominate: Gemma's depth cost is ~31 GFLOP/s of f32 work and
  Qwen's ~46 GFLOP/s (from the depth scaling), near what the f32 NEON loops
  reach — there is no 2–5× of DRAM stall to recover.
- So the 8× DRAM saving does not pay, and the extra L1/L2 re-reads and
  block rescale cost 3 % (Gemma) to 35 % (Qwen, where `group_fixed` was
  stronger than the tile's per-head `dot_row`).

## What would actually pay

The GPU's formulation on the CPU, not a tiling of the current loop:
`S = K·Qᵀ` and `O = P·V` as GEMMs with register blocking over several query
rows at once (one K load serves 4–8 query rows, which is the reuse the tile
did not have), with the online softmax between them; or i8mm/f16 scores
(the plan's second choice) with the accuracy gate. Both are a different
kernel from `attention_tile`, which is why this one was reverted rather
than tuned further.

The per-token path stays; section 2's CPU ratio target is not met and P7
is open.
