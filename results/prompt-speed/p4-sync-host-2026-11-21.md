# P4 fix: a queued prompt submission waits for the one before it (2026-11-21, PC)

The phone is away this session, so this is the PC's Intel RPL-P. Nothing here
is a phone number.

## What was wrong

`a2fc5fa` (P4) queued the prompt's per-layer submissions without waiting and
put a compute→compute memory barrier at the end of every buffer. That is not
enough between Vulkan submissions: a queue has no implicit dependency on the
submission before it. On the Adreno 830 P4 was bit-identical on Gemma 4 Q4_0;
on the PC's Intel GPU a Q4_K_M prompt (the slower f32 path) read stale rows.

Baselines on `prompt-speed-2` (`4735585`), Gemma 4 Q4_K_M, one chunk of the
KL base, `vk_gemma batch`:

| build | PPL | KL | prompt |
| --- | --- | --- | --- |
| `f04ad47` (P5b, before P4) | 51.0329 | 0.146456 | 163.1 s |
| `4735585` (P4), run 1 | 405.8976 | 1.34840 | — |
| `4735585` (P4), run 2 | 392.6180 | 1.31498 | 162.1 s |
| decode, `4735585` | 51.0949 | 0.149804 | 66.3 s |

The same build's Gemma 4 Q4_0, 4 chunks, is bit-identical to the record
(43.6921 / 0.342415 / 79.608 %), so the corruption is timing-dependent.

## The fix

`GemmaGpu::forward_batch` still records layer l while the GPU runs l-1, but
waits for l-1's fence **before submitting l** instead of four submissions
later. The CPU recording keeps overlapping the GPU; the GPU submissions are
serialized (they are dependent anyway).

Gemma 4 Q4_K_M, one chunk, after the fix:

| mode | PPL | KL | prompt |
| --- | --- | --- | --- |
| `batch-f32` (the old f32 products) | 50.9307 | 0.146345 | 210.7 s |
| `batch` (P1b int8 products) | 50.8264 | 0.148650 | 36.8 s |

Gemma 4 Q4_0, 4 chunks, after the fix: 43.6921 / 0.342415 / 79.608 %, the
recorded number to the digit. `batch-f32` reproduces the pre-P4 Q4_K_M f32
number (51.03), so the fix restores the prompt's accuracy.

(A first attempt also forced the per-layer PLE products of a Q4_0 file onto
the f32 path; that was wrong — the Q4_0 file stores `inp_gate`/`proj` as
Q4_0, so P1 had them on the int8 path. Q4_0 read 43.4996 until the products
went back to `i8`.)

## To measure on the phone

The Adreno did not show the corruption, so the queue change must be
re-timed there: P4's gain was CPU-recording overlap, which this keeps, but
the submit latency is now on the critical path once per layer. If the gain
shrinks, the async window can be re-enabled where the driver orders
submissions (a device/vendor switch), which needs the phone's numbers first.
