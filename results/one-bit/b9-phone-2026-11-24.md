# B9: Q2_0 regrouped at load (phone, 2026-11-24)

`BlockQ2_0t`: byte i, bits 2k..2k+1 hold weight 16k+i, so the four code
vectors are and / ushr of one load (the file layout needs tbl + ushl + and per
vector). Q2_0t x Q8_K decode loop 123 -> 99 instructions per 4 rows x 64
columns (unpack 48 -> 26 vector ops). The smmla prompt kernel takes the same
codes.

Build: one-bit at 4f69d02 plus the B9 changes (`aether-b9`) against
4f69d02's tree (`aether-b8`). `scripts/phone_ab.py`, 3 alternated rounds,
zone0 < 42 C, board < 39.5 C, cap floor 2.40 GHz, battery, screen timeout
raised to 30 min for the session. `bench -dev cpu --cores 2-7 -t 6 -p 0 -n 64`.
Every run started and ended at 2.40/2.44 GHz. Raw: `b9-phone-speed-2026-11-24.txt`.

| model | B8 tok/s | B9 tok/s | median change |
|---|---|---|---|
| Ternary-Bonsai-2 4B | 16.53, 16.42, 16.58 | 19.66, 19.72, 19.70 | +19 % |
| Ternary Bonsai 1.7B | 46.42, 46.11, 46.28 | 57.19, 57.39, 57.27 | +24 % |

KL on the phone (`b9-phone-kl-2026-11-24.txt`, 2 chunks; prompt path, so
Q8_0 smmla over the regrouped weights): Ternary-Bonsai-2 4B KLD 0.000186,
same top 99.216 % (B5b phone: 0.000186); Ternary Bonsai 1.7B 0.000240
(B5 phone: 0.000240). Phone kernel tests: 29 passed (both layouts, Q8_0 and
Q8_K activations, against gguf-py / llama.cpp goldens).

Prompt (pp) speed with the regrouped codes was not measured.
