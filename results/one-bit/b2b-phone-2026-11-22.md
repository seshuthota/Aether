# B2b on the phone: correctness, load time and memory

aether-infer `one-bit` (B2b: transposed Q1_0 layout + precomputed
activation sums), iQOO 13, 6 threads on cores 2–7.

## KL against llama.cpp

wikitext-2, 2 chunks of 512, against the same llama.cpp base files as B3.
The numbers are unchanged to every printed digit from B3: the transposed
layout only reorders the same integer sum and the activation sums are
exact.

| | 1.7B | 4B | 8B |
| --- | --- | --- | --- |
| PPL (Aether) | 20.211741 | 14.536940 | 13.167487 |
| PPL (base) | 19.887847 | 14.355021 | 13.046527 |
| **Mean KLD** | **0.000264** | **0.000169** | **0.000186** |
| Same top token | 99.608 % | 99.216 % | 98.824 % |
| 510 tokens | 7.4 s | 17.1 s | 31.1 s |

Raw: `b2b-phone-kl-2026-11-22.txt`.

## Greedy

"The capital of France is", `--temp 0`, 16 tokens, on all three models:
the output is byte-identical to the pre-repack `aether-b3` binary and to
`llama-completion --no-conversation` (1.7B's longer completion and the
4B/8B repeats both match). Raw: `b2b-phone-load-2026-11-22.txt`.

## Rounding

The new kernel's integer sums are exactly the old kernel's; only the
float order of the `+1` terms differs. The A/B test
(`q1_0_transposed_matches_row_major`) sees at most **1.05e-6 relative**
difference on the golden cases; the test bound is 1e-5. The golden
comparison against gguf-py's float64 dequantization still passes with the
same 1e-6·√n bound for both layouts.

## Load time

`aether run -n 0` (load only, no forward pass), wall time of the process,
same file and core set:

| | pre-repack | B2b | cost |
| --- | --- | --- | --- |
| 1.7B (242 MB, tied) | 0.272 s | 0.428 s | +0.156 s |
| 4B (566 MB, tied) | 0.331 s | 0.661 s | +0.330 s |
| 8B (1153 MB, untied) | 0.271 s | 1.264 s | +0.993 s |

The 8B's untied `token_embd` is left in the mapped file because it is only
row-looked-up, never multiplied; only its separate `output.weight` and the
layers are repacked.

## Peak RSS

`aether run -c 512 -n 16`, engine's `peak RSS`:

| | pre-repack | B2b | change |
| --- | --- | --- | --- |
| 1.7B | 410,116 kB | 404,584 kB | −1.3 % |
| 4B | 759,384 kB | 753,576 kB | −0.8 % |
| 8B | 1,247,392 kB | 1,251,748 kB | +0.4 % (+4.4 MB) |

At `-n 0` the new binary touches every Q1_0 page while repacking, so its
load-time RSS is the model size (402 MB / 752 MB / 1.25 GB) instead of the
old lazy-mmap figure (177 / 212 / 214 MB). The repack copies in 1.18 MB
chunks and `madvise`s each source chunk behind it; after a full run the
peak is the same or lower than before, except the 8B's +4.4 MB for the
chunk in flight.
