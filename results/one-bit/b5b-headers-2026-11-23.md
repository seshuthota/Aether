Tensor names and shapes are exactly what the engine's `qwen35` path
expects (`attn_qkv`, `attn_gate` as the z gate, `ssm_alpha`, `ssm_beta`,
`ssm_conv1d`, `ssm_a`, `ssm_dt.bias`, `ssm_norm`, `ssm_out`,
`post_attention_norm`; `attn_q/k/v/output` with `attn_q_norm`/`attn_k_norm`
on the full layers). The F32 tensors are the norms, conv, `ssm_a`,
`ssm_dt.bias`, `ssm_alpha` and `ssm_beta`; all 150 folded linear matrices
and `token_embd` are Q2_0. Q2_0 is already supported by B5.

## What the engine does not do

1. **The layer pattern key.** The file has
   `qwen35.full_attention_interval = 4`, not the
   `qwen35.attention.recurrent_layers` array the loader requires. Loading
   currently stops with `missing qwen35.attention.recurrent_layers`.
2. **The Hadamard weight basis.** `prism.hadamard.*` describes a runtime
   activation transform:

   | key | 2B value |
   | --- | --- |
   | version / tied_output | 2 / true |
   | block_size | 512 |
   | transform | `normalized-sylvester-walsh-hadamard` |
   | axis | `input-last-dimension` |
   | sign_mode | `explicit` |
   | sign_widths | [2048, 6144] |
   | sign_values | 8192 entries, all ±1 |
   | weight_names | 150 matrices |
   | inverse_weight_names | `token_embd.weight` |

   The stored weights are folded: `W_f = W · D · H`, with `D` the per-column
   ±1 signs and `H` the normalized block Hadamard. The runtime must turn
   the input `x` into `H(D x)` before every folded matmul. The tied token
   embedding is a latent lookup table and needs its inverse after the row
   lookup; as the tied output it is also a folded weight, so the classifier
   input is transformed. Our engine currently ignores all `prism.*` keys
   and would load the folded weights as if they were plain ones: wrong
   output, no error. Upstream llama.cpp b11556+ (our `d02b4c0d6` is later)
   implements this, so the oracle can run it.

3. **4B / 9B Gated DeltaNet.** Both have `ssm.group_count` 16 but
   `ssm.time_step_rank` 32 (32 v heads over 16 q/k heads); the engine
   explicitly refuses that at load. They also set
   `prism.hadamard.gdn_v_grouped = true`, which needs the ssm_out input
   permuted from tiled to grouped head order before the transform. The 9B
   uses `block_size` 4096 and `prism.hadamard.version` 1.

## Go / no-go

**No-go as a Q2_0-only job.** The 2B needs a new Hadamard activation
runtime and the new config key; the 4B/9B additionally need the GDN
v-head reorder and grouped ssm_out permutation. Estimate for the 2B:
1–2 focused days (metadata validation, block Hadamard + signs, wiring at
every folded matmul on both the one-token and batched paths, tied
embedding/output dual use, greedy/KLD tests against `d02b4c0d6`). The 4B
adds 1–2 days for the v-head reorder/permutation; once that is done the
9B is mostly the same code at block 4096.

Stopped here as instructed; waiting for the user's decision before
building.
