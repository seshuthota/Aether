`baff22b`. Host i7-13620H (x86) plus qemu-user 8.2.2 for aarch64
correctness; **no phone run in B2 yet** (the user's standing instruction
was no benchmark sessions, and the phone was not used for correctness
either; the earlier ask was declined).

## Kernels

`crates/aether/src/kernels/neon_quant.rs`:

- `dot_q1_0_q8_0` (+ `dot_q1_0_q8_0_sdot`): one row, `sdot`; two block
  accumulators, four quarters each.
- `dot4_q1_0_q8_0`: four rows, one activation block, reusing `fold4`.
- `mmla4_q1_0<P>`: `smmla`, block `b` = quarter `b % 4` of Q1_0 block
  `b / 4`, scales repeated per quarter. Q1_0 left `has_mmla_for` and its
  `unreachable!`; `has_mmla_for` is gone.
- No `Q1_0x4` repack: the expansion is per-block work, not a load-layout
  problem, and an expanded (sign-byte) copy would be 8× the file
  (248 MB → 2 GB). Not measured, deliberately not done.

Bit expansion, chosen without a phone timing (see below): register
expansion. For each quarter, `tbl` replicates the four sign bytes to the
32 lanes they govern, `cmtst` against {1,2,4,…,128} gives 0xFF for a set
bit, and OR 1 turns that into −1/+1 (the kernel negates its final sum).
LLVM lowers Rust's `vtstq_u8` to and + cmeq + orn (three instructions), so
the single `cmtst` is written with `asm!` like `smmla` and `sri`. The
256×8 `SIGNS` table variant is kept behind the `internals` feature
(`dot_q1_0_q8_0_table`, `dot4_q1_0_q8_0_table`, `mmla4_q1_0_table`) and
checked to be bit-identical; `kquant_bench --ab` times both on the phone.

Why registers as the default: the table costs four extra L1 loads per
quarter (16 per 128-weight block, four rows) next to the 18-byte weight
stream and adds a 2 KB read-only table to the hot L1; register expansion
uses only ALU after one 16-byte load. This is an argument, **not a
measurement**; the phone A/B is owed.

## Correctness

`kernels::tests::q1_0_matches_gguf_py` on aarch64 under qemu-user
(dotprod + i8mm): pass, all six golden cases (t = 1,2,3,5,9; rows 1..64,
including 5 and 17 which leave a `dot1` tail), bound 1e-6·sqrt(n).
`q1_0_table_expansion_matches_registers`: pass. Log:
`b2-qemu-kernel-test-2026-11-22.txt`.

The 2-chunk KL against `kl-base-llama-q1_0-wiki2.bin` was **not rerun**:
qemu is thousands of times slower than the phone at this model (a single
1024×2048 GEMV takes ~13 s), so 510 tokens would take many hours. B1's
phone number (KLD 0.000271, same top 99.608 %) stands; the new kernels are
exact against gguf-py per step, which is what B2 changed.

## Speed

Not measured (no phone session). llama.cpp reference from B1: pp128
~210, tg64 ~50 tok/s (Bonsai 1.7B, cores 2–7); Aether scalar was 5.3 /
4.0. B2's bench is ready:

  cargo run --release --target aarch64-linux-android -p aether-bench \
    --example kquant_bench -- hostdata/bonsai/Bonsai-1.7B-Q1_0.gguf \
    --q1_0 hostdata/bonsai/Bonsai-1.7B-Q1_0.gguf \
    --tokens 1,8,32,128 --ab

`--tokens` times t-token batches of deterministic activations (the kernel
cost, not a real prompt); `--ab` times registers vs table for `dot4` (t=1)
and `mmla4` (t=8). For end-to-end tok/s use `scripts/phone_bench.py` from
`prompt-speed-2` against `llama-bench`. Phone runs must keep the screen
awake (`adb shell svc power stayon true`) or the board locks mid-run.
